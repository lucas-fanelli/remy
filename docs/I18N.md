# Internationalisation

Remy speaks Spanish and English. Spanish is the default — the audience is Argentine.

Until now the app relied on the browser's auto-translate. It re-translated on every refresh,
so words moved around mid-read; it forgot the choice; and a logged-out visitor and a
logged-in user could see different languages on the same screen. The app owns its
translations now: one choice, remembered, applied on the server before the first byte of
HTML goes out.

## The shape of it

| Piece                                                                | Where                                                           |
| -------------------------------------------------------------------- | --------------------------------------------------------------- |
| Locales, cookie name, negotiation                                    | `src/i18n/config.ts`                                            |
| Server-side locale of the current request                            | `src/i18n/locale.ts`                                            |
| next-intl request config                                             | `src/i18n/request.ts`                                           |
| Message registry (static imports, one JSON per namespace per locale) | `src/i18n/messages.ts`                                          |
| Type augmentation (`t('...')` is checked)                            | `src/i18n/augment.d.ts`                                         |
| Test harness                                                         | `src/i18n/testing.tsx` + `jest.setup.js`                        |
| Typecheck of the keys written in tests                               | `tsconfig.i18n.json` (second half of `npm run typecheck`)       |
| Descriptors for pure functions                                       | `src/i18n/text.ts`                                              |
| Unit labels                                                          | `src/i18n/units.ts`                                             |
| date-fns locale                                                      | `src/i18n/dates.ts`                                             |
| API error codes                                                      | `src/lib/api/errorCodes.ts`, `src/lib/api/translateApiError.ts` |
| Switcher                                                             | `src/components/common/LanguageSwitcher.tsx`                    |
| Parity gate                                                          | `src/i18n/__tests__/messages.test.ts`                           |

There is **no locale in the URL**. next-intl runs "without i18n routing": the plugin in
`next.config.js` points at `src/i18n/request.ts`, and that resolves the language per request.

### How the language is decided and kept

1. The `remy_locale` cookie, if it holds `es` or `en`.
2. Otherwise `Accept-Language` — any `es*` means Spanish, anything else English.
3. Otherwise `es`.

On the **first** visit there is no cookie, so `src/middleware.ts` writes the negotiated value
(one year, `path=/`, `sameSite=lax`, **not** `httpOnly` so the switcher can rewrite it). From
the second request on it is a plain cookie read.

This is deliberately _not_ tied to the auth session. The language survives logging in,
logging out and switching accounts, and it is known **before** rendering — which is what
removes the flicker. `<html lang>` follows it, and `translate="no"` plus
`<meta name="google" content="notranslate">` stop Chrome from translating an already
translated page on top (that second pass is what made the words jump).

`LanguageSwitcher` writes the same cookie from the client and calls `router.refresh()`. The
server re-renders the current route in the new language and React reconciles it in — no
reload, no lost form state.

## Conventions

These are not suggestions. Six people are migrating different areas at the same time; the
value of the rules is that everyone follows the same ones.

### Namespaces and keys

- One namespace per area of the app. **Only edit your own namespaces** — that is how six
  branches merge without conflicts.
- Files are `src/i18n/messages/<locale>/<namespace>.json`. Never merge namespaces into one
  file, never add a namespace without registering it in `src/i18n/messages.ts` (the parity
  test fails if the directory and the registry disagree).
- Keys are `camelCase`, nested by screen or component, then by role:

  ```json
  {
    "header": {
      "title": "Your pantry",
      "subtitle": "{count, plural, one {# item} other {# items}}"
    },
    "empty": { "title": "Nothing in here yet", "action": "Add an ingredient" },
    "actions": { "addIngredient": "Add ingredient" }
  }
  ```

- Name keys after **what the text is for**, never after the text itself. `deleteConfirm`,
  not `areYouSure`.
- English is the source of truth for the shape. `src/i18n/augment.d.ts` feeds the English
  catalogue into next-intl's `AppConfig`, so an unknown key is a **compile error** and
  `t('nav.items.hom')` never reaches a review.

### Writing messages

- **Never concatenate translated fragments.** `t('a') + ' ' + name` is a bug: word order is
  not universal. One message, one sentence, with arguments:

  ```json
  { "likedBy": "{name} liked your recipe" }
  ```

- **Plurals are ICU**, not an `if`. Spanish and English happen to agree on one/other, but
  the message still has to carry the rule so the number and the noun stay together:

  ```json
  { "minutes": "{count, plural, one {# minute} other {# minutes}}" }
  ```

- **Choices are `select`**, not three keys glued together:

  ```json
  { "difficulty": "{level, select, easy {Easy} medium {Medium} hard {Hard} other {Unknown}}" }
  ```

- **Inline markup is `t.rich`** — the message decides where the link sits in the sentence,
  the component decides what the link is:

  ```json
  { "errorWithRetry": "Something went wrong. <retry>Try again</retry>." }
  ```

  ```tsx
  t.rich('states.errorWithRetry', { retry: (chunks) => <Link onClick={refetch}>{chunks}</Link> });
  ```

- **No dynamic keys**, with one exception: a **closed union** you control. `Navigation.tsx`
  is the reference — each nav item's `id` is `'home' | 'search' | 'add' | 'pantry'` and the
  key is ``t(`items.${item.id}`)``. Anything that could be an arbitrary string (a slug from
  the database, a server message) is not allowed: use `select` or a descriptor instead.
- An apostrophe is ICU's escape character. `"Anyone can cook"` is fine; `"it''s"` is how you
  write a literal apostrophe next to a brace. Prefer rewording.

### Pure functions that produce user-facing text

Several helpers build sentences and have no locale and no hooks: `validateRecipe`, the
free-text parser's "check this" reasons in `src/lib/utils/recipeText.ts`,
`RecipeSubmitError`, `imageUploadUtils`. They must stop returning English.

They return a **descriptor** — which message, and what to fill it with — and the component
renders it.

```ts
// src/components/recipe/form/validateRecipe.ts — still a plain .ts module, no React
import { text, type TextDescriptor } from '@/i18n/text';

export interface RecipeIssue {
  path: RecipeFieldPath;
  section: RecipeFormSection;
  label: TextDescriptor;
  message: TextDescriptor;
}

if (values.title.trim() === '') {
  add('title', text('recipeForm.fields.title'), text('recipeForm.issues.titleRequired'));
} else if (values.title.trim().length > RECIPE_LIMITS.title) {
  add(
    'title',
    text('recipeForm.fields.title'),
    text('recipeForm.issues.titleTooLong', { max: RECIPE_LIMITS.title })
  );
}
```

```tsx
// the component that shows them
const renderText = useTextDescriptor();

{
  issues.map((issue) => (
    <FormHelperText key={issue.path}>{renderText(issue.message)}</FormHelperText>
  ));
}
```

The key is the **full path including the namespace**, because the function has no namespace
of its own. It is type-checked like any other key.

The unit tests of those pure functions get **better**, not worse: they assert on
`{ key: 'recipeForm.issues.titleRequired', values: { max: 100 } }`, which is the intent,
instead of on an English sentence that was always going to change.

### API errors

41 route handlers answer `{ error: '<English sentence>' }`, about 100 different strings.
They are migrated **additively**, one route at a time, in any order:

- The server keeps the `error` string **exactly as it is** and adds a stable machine `code`
  from `src/lib/api/errorCodes.ts`. `ApiResponseHelper.badRequest(...)` and friends take it
  as an optional second argument, and it is omitted from the JSON when absent — a route
  nobody has touched answers byte-for-byte what it always did.
- The client shows `t('errors.<code>')` when it recognises the code and the server's own
  string when it does not.

```ts
// src/app/api/auth/change-password/route.ts
return ApiResponseHelper.badRequest('Current password is incorrect', 'currentPasswordIncorrect');
```

```tsx
// src/components/settings/ChangePasswordDialog.tsx
const apiErrorMessage = useApiErrorMessage();
...
if (!response.ok) throw new Error(apiErrorMessage(data, 'Failed to change password'));
```

A new code goes in `API_ERROR_CODES` **and** in `errors.json` for both languages; the parity
test then keeps the two languages honest.

**Do not attach a code when the generic message would say less than the English it
replaces.** The zod branch of `change-password` is the worked counter-example: its body is a
list of per-field messages, and `errors.invalidRequest` ("some of the data is not valid")
would throw that away. Those become translatable when the zod schemas move into the
`validation` namespace — that is owner F's job, not a code.

### Dates, times and numbers

Use next-intl's formatter. It already knows the locale and the pinned time zone
(`America/Argentina/Buenos_Aires`, so a server render and a client re-render agree):

```tsx
const format = useFormatter();
format.dateTime(recipe.createdAt, { dateStyle: 'medium' });
format.relativeTime(comment.createdAt, useNow());
format.number(recipe.servings);
```

Three components already use date-fns (`src/app/notifications/page.tsx`,
`NotificationDropdown`, `CommentsSection`). They do not have to be rewritten, they just have
to stop formatting in English:

```tsx
const locale = useDateFnsLocale();
formatDistanceToNow(new Date(notification.createdAt), { addSuffix: true, locale });
```

Never build a date by hand out of translated month names.

### Units

**Stored values never change language.** A recipe row keeps `cups`, `tbsp`, `to taste` in
English forever: the pantry matcher and the free-text parser compare against those exact
strings, and a Spanish user's recipe has to match an English user's pantry. Only the label on
screen is translated:

```tsx
const units = useUnitLabels();
units.label('cups', 2); // 'cups'  / 'tazas'
units.name('g'); // 'grams' / 'gramos'
units.option('g'); // 'g - grams' / 'g - gramos'
```

The `units` namespace is filled and belongs to the foundation — you should not need to touch
it. An unknown unit falls back to the stored value rather than a missing-key path.

## Spanish style guide

Rioplatense Spanish, **voseo**, informal, concise, sentence case.

- Second person is **vos**: _Iniciá sesión_, _Subí tu receta_, _Elegí una foto_, _Probá de
  nuevo_, _Revisalo_. Never _inicia sesión_ / _sube_ / _elige_, never _usted_.
- Sentence case for headings and buttons: _Guardar cambios_, not _Guardar Cambios_.
- Say it in as few words as the English does. Spanish runs longer; cut, don't wrap.
- Speak as the app, in the first person plural, when something failed on our side: _No
  pudimos conectarnos_.
- Keep `…` as three dots (`...`) to match the existing copy.
- Do not translate: the brand name (_Remy's_), _YouTube_, unit symbols (g, kg, mL, L, oz,
  lb), technology names.

## Tests

**You do not have to rewrite existing tests.** `jest.setup.js` replaces the `next-intl`
module, for every test file, with bindings backed by use-intl's **real ICU translator**
bound to the merged **English** catalogue. So:

- a component you migrate keeps rendering the same English text, and its existing
  `getByText('Save changes')` keeps passing — as long as the English message is the old
  literal, character for character. If a test breaks after your migration, you changed the
  copy; either put it back or update that one assertion on purpose.
- plurals, interpolation and `t.rich` really run, so a malformed ICU message fails a test
  instead of shipping.
- no provider is needed anywhere. `useTranslations()` works in a bare `render()`.

To assert on Spanish, opt in:

```tsx
import { renderWithLocale, setTestLocale } from '@/i18n/testing';

renderWithLocale(render, 'es', <Navigation />);
expect(screen.getByText('Iniciar sesión')).toBeInTheDocument();

// or, for a whole describe block
beforeEach(() => setTestLocale('es'));
```

`jest.setup.js` resets the locale to English before every test, so Spanish never leaks.

`src/components/__tests__/Navigation.i18n.test.tsx` is the pattern: the original
`Navigation.test.tsx` was not touched and asserts the English; the new file asserts the
Spanish. Add one small Spanish file per area rather than translating assertions in place.
Name it `<Area>.i18n.test.tsx` — that suffix is also what gets the file typechecked (below).

### Server Components

A page that translates its `generateMetadata` (or any `async` component) uses
`getTranslations` from `next-intl/server`, not the hooks. `jest.setup.js` mocks that entry
point too, from the same English translator, so it needs no mock of its own:

```tsx
const t = await getTranslations('metadata'); // English, or the locale setTestLocale set
```

Without that mock the real module resolves to next-intl's react-client build and throws
_"`getTranslations` is not supported in Client Components"_ — an error that says nothing
about the test harness. `getLocale`, `getFormatter`, `getMessages`, `getNow`, `getTimeZone`
and `getRequestConfig` are mocked alongside it;
`src/i18n/__tests__/harness.test.tsx` is the proof.

### What typechecking does and does not cover

`npm run typecheck` runs **two** projects:

- `tsconfig.check.json` — all production code, and it **excludes every test file**.
- `tsconfig.i18n.json` — `src/i18n/**` and every `src/**/*.i18n.test.tsx`.

So an unknown key is a compile error in production code and in the Spanish test file you are
asked to add, but **not** in the rest of the suite: jest compiles tests with next/jest's SWC
transform, which strips types without checking them (the `ts-jest` block in `jest.config.js`
is shadowed by it and inert). A key typo in, say, `RecipeCard.test.tsx` therefore fails only
when the assertion does — as a missing-key path in the rendered output. Put message-key
assertions in your `*.i18n.test.tsx` and you get the compile error instead.

### The ESM problem, and what was done about it

`next-intl`, `use-intl`, `intl-messageformat`, `icu-minify` and the `@formatjs/*` packages
publish **ES modules only** — no CommonJS build. Jest's runtime is CommonJS and, by default,
does not transform anything under `node_modules`, so importing the real translator threw
`Cannot use import statement outside a module`.

`next/jest` builds its `transformIgnorePatterns` from `transpilePackages` in
`next.config.js`, and a custom `transformIgnorePatterns` entry can only **add** ignores (the
patterns are OR-ed), so it cannot be fixed from `jest.config.js`. Those packages are
therefore listed in `transpilePackages`, which is one list serving both: webpack compiles
them for the app, and jest runs them through the same SWC transform as the app's own code.

## How to translate an area

1. **Find every string.** Not just JSX text:
   - props: `label`, `placeholder`, `helperText`, `title`, `alt`, `aria-label`,
     `aria-describedby`, `tooltip`/`Tooltip title`, `confirmText`, `cancelText`
   - toasts (`showSuccess` / `showError`), `Alert` and `Snackbar` bodies
   - confirm dialogs (`ConfirmDialog` title/message/buttons)
   - document titles and `generateMetadata`
   - validation messages and error states, empty states, loading text
   - text built in handlers and helpers, not only in the render
   ```bash
   # a decent first pass over your files
   grep -rnE '"[A-Z][a-z]+ [a-z]' src/<your area>
   ```
2. **Do not translate**: values stored in the database (units, difficulty keys, tags),
   `data-testid`, query keys, route paths, `console.*` and `logServerError` messages, server
   logs, Sentry breadcrumbs, the brand name.
3. **Move them** into _your_ namespaces. Something genuinely shared and missing from
   `common`? Add it to **your own** namespace — `common`, `units` and the generic `errors`
   keys belong to the foundation and are already filled.
4. **Both languages, same commit.** English keeps the exact old wording (that is what keeps
   the existing tests green); Spanish follows the style guide and the glossary.
5. **Pure functions** in your area return descriptors (`src/i18n/text.ts`), not sentences.
   Update their unit tests to assert on the descriptor.
6. **Routes** in your area add a `code` next to the unchanged `error`.
7. **Run:**
   ```bash
   npx jest src/i18n/__tests__/messages.test.ts   # the parity gate
   npx jest <your area>                           # existing tests, unchanged
   npm run typecheck                              # unknown key: error in src/** and *.i18n.test.tsx
   npx eslint <files you touched> --max-warnings 0
   ```
8. **Add one Spanish test** for the area, named `<Area>.i18n.test.tsx`, the way
   `Navigation.i18n.test.tsx` does — that is the test file `npm run typecheck` reads.

`errors` keys, the loader, `jest.setup.js`, `src/i18n/**` and this document belong to the

- **`NotificationDropdown` is D's**, not the foundation's, even though it sits in

- **`src/app/settings/page.tsx`, `src/app/auth/page.tsx` and `AuthPageShell.tsx`** already

  `API_ERROR_CODES`; nobody else edits `errorCodes.ts`.
- **`src/lib/validation/schemas.ts`** is split by intent: F owns the schemas themselves and
  the `validation` keys the server produces; B owns the recipe form's own messages. If a
  message is produced by zod on the server it is F's.
- **`src/contexts/AuthContext.tsx` is A's.** It throws `error.error || 'Login failed'` and

  though it comes from an API call. A replaces those fallbacks with `useApiErrorMessage()`
  (`src/lib/api/translateApiError.ts`); F adds the `code`s to `src/app/api/auth/**` in its
  own branch. Different files, so the two halves land in any order.
- **`src/lib/validation/passwordRules.ts` is A's**, even though it sits under
  `src/lib/validation/`. It is the one list behind both the checklist in `ResetPasswordForm`
  and the server's zod `passwordSchema`, so the split is by field, not by file: `label` and
  the message the **form** shows become descriptors in `auth` (A's work), while `message`
  stays the English string `getPasswordErrors` hands to zod on the server — that is exactly
  what F's additive contract requires the server to keep. F never edits this file.
- **`src/domain/**`and`src/infrastructure/services/**` are F's**, as a glob and not as a
  phrase: `INVALID_RESET_TOKEN_MESSAGE` in `src/domain/errors.ts` and the English `throw`s in
  `AuthService`, `UserService`, `PantryService` and `RecipeService` reach the client through
  a route, so they are migrated the way a route is — the English message stays, the route
  that catches it attaches a `code`.
- **`src/lib/auth/requireAdmin.ts`, `src/lib/utils/request.ts` and
  `src/lib/utils/cloudinary-validation.ts` are F's.** They answer `{ error: ... }` like a
  route handler does and are migrated identically.
- **`src/hooks/useRecipe.ts` is C's**, next to `useCreateRecipe.ts`/`useUpdateRecipe.ts`
  being B's: its `'Recipe not found'` and `'Failed to load recipe'` surface on C's recipe
  pages. `useAdminGuard.ts` and `useNotificationPolling.ts` have no user-facing text at all
  (only `console.error`), so they are nobody's.
