## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps in the middleware CSRF logic, a data-loss race in the cooked-recipes endpoint, and multiple instances of unbounded resource consumption.

### Findings

#### CRITICAL

**[CR-001]** Middleware CSRF bypass via missing Origin/Referer check for JSON requests

- **File:** `src/middleware.ts:196-204`
- **Issue:** The CSRF check accepts any request with `Content-Type: application/json` as proof of same-origin. However, `fetch()` from a cross-origin page can set `Content-Type: application/json` freely. The `Sec-Fetch-Site` check is correct but is only one branch of the OR — the JSON content-type branch bypasses it entirely. An attacker page can send `fetch('https://victim.com/api/recipes', { method: 'DELETE', headers: {'Content-Type': 'application/json'}, credentials: 'include' })` and the CSRF check passes.
- **Impact:** Cross-site state-changing requests (delete recipes, change passwords, follow/unfollow) for any logged-in user who visits an attacker page.
- **Suggested fix:** Remove `application/json` from the `hasCustomHeader` check. Rely solely on `Sec-Fetch-Site` (same-origin/none) or the `X-Requested-With` custom header:

```typescript
const hasCustomHeader = isSameOrigin || request.headers.has('x-requested-with');
```

Then add `headers: { 'X-Requested-With': 'fetch' }` to all client-side `fetch()` calls that use JSON. The existing multipart uploads already do this.

**[CR-002]** Rating aggregation not recalculated when comment (and its associated rating) is deleted by user

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:131-145` (DELETE handler)
- **Issue:** When a user deletes their comment, the associated `Rating` record is intentionally preserved (comment says "ratings are independent of comments"). However, the `averageRating` and `reviewCount` cached on the `Post` are never recalculated. If the user later deletes their rating through another flow, the cached values go stale. More critically, there is no user-facing way to delete a rating independently of a comment — so ratings from deleted comments become permanent ghost data.
- **Impact:** Recipe ratings become permanently inflated or deflated with no way for the user to remove their rating after deleting their comment.
- **Suggested fix:** Either (a) delete the rating when the comment is deleted and recalculate, or (b) provide a separate endpoint for rating deletion, or (c) document this as intentional behavior and add a rating update option to the comment edit flow.

**[CR-003]** `cooked-recipes` POST deducts pantry items but does not restore them if `cookedRecipe.create` fails

- **File:** `src/app/api/cooked-recipes/route.ts:85-100` (`deductPantryItems`) and lines 175-210
- **Issue:** Inside the transaction, `deductPantryItems` applies all pantry updates (Pass 2), then `cookedRecipe.create` runs afterward. If `cookedRecipe.create` throws (e.g., unique constraint violation on a race), the entire transaction rolls back — but only because it's wrapped in `$transaction`. However, the `INSUFFICIENT_INGREDIENTS` error is thrown _before_ any writes and propagates outside the transaction as a caught error, which is correct. The real issue: `deductedIngredients` is populated inside the transaction closure but referenced in the response _outside_ it. If the transaction is retried by Prisma (serialization failure), the outer `insufficientIngredients`/`deductedIngredients` arrays accumulate stale entries from previous attempts.
- **Impact:** Response may report duplicate deducted ingredients on transaction retry, confusing the client.
- **Suggested fix:** Move the `insufficientIngredients` and `deductedIngredients` declarations inside the transaction callback, and return them as part of the transaction result:

```typescript
const { cookedRecipe, insufficientIngredients, deductedIngredients } = await prisma.$transaction(async (tx) => {
  let insufficientIngredients: InsufficientIngredient[] = [];
  let deductedIngredients: DeductedIngredient[] = [];
  // ... rest of logic
  return { cookedRecipe: ..., insufficientIngredients, deductedIngredients };
});
```

#### HIGH

**[CR-004]** Admin user delete leaks user emails in `console.warn` for failed Cloudinary cleanup

- **File:** `src/app/api/admin/users/[id]/route.ts:79`
- **Issue:** `console.warn` logs the full list of image URLs (which may include avatar URLs containing usernames). More importantly, the `failedUrls` array is logged but the user ID is also logged — combined with the image URLs this could be PII in logs.
- **Impact:** PII (user content URLs, user IDs) in server logs.
- **Suggested fix:** Log only the count and user ID, not the full URLs: `console.warn(\`[ORPHANED IMAGES] Failed to cleanup ${failedUrls.length} images for deleted user ${id}\`)`.

**[CR-005]** `recipes/match` endpoint has no timeout on the application-level matching loop

- **File:** `src/app/api/recipes/match/route.ts:130-165`
- **Issue:** The DB queries have a 5s timeout, but the JavaScript matching loop that iterates over `allCandidates` (up to 200) and compares each against up to 100 pantry items has no time bound. With 200 candidates × 100 pantry items × ingredient lists, this could take significant CPU time on a single request, blocking the Node.js event loop.
- **Impact:** Potential DoS via authenticated users with large pantries, causing slow responses for all users on the same server instance.
- **Suggested fix:** Add an iteration budget (e.g., max 10,000 comparisons) or move matching to a worker thread. Alternatively, cap `allCandidates` to a lower number (e.g., 100).

**[CR-006]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:137-168`
- **Issue:** When `loadRecipes(reset=true)` is called, `setRecipes(data.recipes)` replaces the list. But if two filter changes fire in quick succession, the `requestIdRef` guard only prevents stale _responses_ — it doesn't prevent two sequential successful responses from both calling `setRecipes`. The abort controller mitigates this, but there's a window where the first response arrives before the abort signal propagates.
- **Impact:** Momentary display of wrong filter results, then correct results. Minor UX glitch.
- **Suggested fix:** This is mostly handled by the abort controller. Acceptable as-is but worth noting.

**[CR-007]** `useNotificationPolling` circuit breaker resets on success but doesn't cap `breakerTripCountRef`

- **File:** `src/hooks/useNotificationPolling.ts:88`
- **Issue:** `breakerTripCountRef` is capped with `Math.min(breakerTripCountRef.current, 10)` on the failure path, but after a successful fetch it's reset to 0. If the server flaps (alternating success/failure), the cooldown never escalates because success resets the counter. This means a flapping server will cause rapid repeated requests during the failure windows.
- **Impact:** Amplified load on a struggling notifications endpoint.
- **Suggested fix:** Only reset `breakerTripCountRef` after N consecutive successes, or decay it gradually instead of resetting to 0.

**[CR-008]** `logout` in `AuthContext` has duplicated retry logic

- **File:** `src/contexts/AuthContext.tsx:96-130`
- **Issue:** The retry logic is copy-pasted identically in both the `try` (non-ok response) and `catch` (network error) branches. This is ~20 lines of duplicated code that will drift.
- **Impact:** Maintenance burden; if retry logic needs updating, it must be changed in two places.
- **Suggested fix:** Extract the retry into a helper function:

```typescript
const retryLogout = () => setTimeout(async () => { ... }, 1000);
```

**[CR-011]** `PersistentSearchBar` creates AbortController outside setTimeout but aborts on cleanup

- **File:** `src/components/search/PersistentSearchBar.tsx:132-156`
- **Issue:** The comment says "AbortController is intentionally created OUTSIDE the setTimeout" but if the query changes before the timeout fires, the cleanup aborts the controller — which is correct. However, the `isMountedRef` check inside the timeout is redundant with the abort signal check in the catch block. Not a bug, just unnecessary complexity.
- **Impact:** Code clarity.
- **Suggested fix:** Remove the `isMountedRef` check inside the setTimeout callback since the abort signal already handles unmount/rerender cases.

**[CR-012]** `normalizeIngredientName` exception list will grow unboundedly

- **File:** `src/lib/utils/ingredients.ts:11-34`
- **Issue:** The `noStripSuffixWords` Set contains ~100 entries and will likely grow over time as edge cases are discovered. This is a maintenance concern — each new ingredient that gets incorrectly stemmed requires a code change.
- **Impact:** Ongoing maintenance burden for ingredient matching accuracy.
- **Suggested fix:** Consider using a stemming library (e.g., `stemmer` or `natural`) as noted in the code comment.

**[CR-013]** `EditProfileModal` does not validate avatar file size against `MAX_UPLOAD_SIZE` constant consistently

- **File:** `src/components/profile/EditProfileModal.tsx:89`
- **Issue:** Uses `MAX_UPLOAD_SIZE` from constants (good), but the error message says `${MAX_UPLOAD_SIZE / (1024 * 1024)}MB` which will show "5MB" — however the avatar upload route (`/api/upload/avatar`) also enforces 5MB independently. If either constant changes, they'll diverge.
- **Impact:** Potential inconsistency between client-side and server-side size limits.

**[CR-014]** `RecipeCard` logs console.warn in dev for every non-Cloudinary image on every render
