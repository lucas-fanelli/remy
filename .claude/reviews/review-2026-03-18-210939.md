## Code Review — 2026-03-18

### Summary

Large, well-structured Next.js recipe-sharing application with clean architecture (DI container, repository/service pattern). Multiple race conditions in client-side state management and a Cloudinary orphan leak are the most dangerous findings.

### Findings

#### CRITICAL

**[CR-001]** `loadRecipes` finally block runs after abort, prematurely clearing loading state

- **File:** `src/components/recipe/RecipeFeed.tsx:137-170`
- **Issue:** When a filter change aborts an in-flight fetch (reset=true), the aborted call's `catch` returns early but `finally` still executes, setting `loadingRef.current = false` while the replacement request is still in flight. A third call during this window bypasses the loading guard and runs concurrently.
- **Impact:** Concurrent duplicate fetches, potential duplicate recipes in the list, UI flicker.
- **Suggested fix:**

```typescript
} catch (error) {
  if (error instanceof DOMException && error.name === 'AbortError') return;
  console.error('Error loading recipes:', error);
} finally {
  // Only clear loading if this is still the active controller
  if (abortControllerRef.current === controller) {
    loadingRef.current = false;
    setLoading(false);
  }
}
```

#### HIGH

**[CR-002]** Cloudinary image orphan on comment creation failure

- **File:** `src/components/recipe/CommentsSection.tsx:111-146`
- **Issue:** `handleSubmitComment` uploads an image to Cloudinary first, then creates the comment. If the comment POST fails (network error, validation, server error), the uploaded image remains on Cloudinary with no reference and no cleanup.
- **Impact:** Accumulated orphan files on Cloudinary, increased storage costs over time.
- **Suggested fix:** Track the uploaded `publicId` and call a cleanup endpoint (or client-side delete) in the error path, or move the upload server-side so it's transactional with comment creation.

**[CR-003]** Pantry item limit bypass via concurrent requests (TOCTOU)

- **File:** `src/app/api/pantry/route.ts:99-106`
- **Issue:** The count check `itemCount >= MAX_PANTRY_ITEMS` and `pantryItem.create` inside the transaction are not serializable under PostgreSQL's default READ COMMITTED isolation. Two concurrent POST requests can both read `itemCount = 499`, both pass the check, and both create an item, exceeding the 500 limit.
- **Impact:** Users can exceed the pantry item limit via rapid concurrent requests.
- **Suggested fix:** Add `SELECT ... FOR UPDATE` on the pantry row to serialize concurrent inserts:

```typescript
const pantry = await tx.userPantry.findUnique({
  where: { userId: payload.userId },
});
// Lock the pantry row:
await tx.$executeRaw`SELECT id FROM "UserPantry" WHERE id = ${pantry.id} FOR UPDATE`;
const itemCount = await tx.pantryItem.count({ where: { pantryId: pantry.id } });
```

**[CR-004]** Visibility change handler leaks setTimeout reference

- **File:** `src/hooks/useNotificationPolling.ts:130-148`
- **Issue:** Inside `handleVisibility`, when the tab becomes visible, a `setTimeout` with random jitter is created but its ID is not stored. The useEffect cleanup (`return () => { clearPolling(); ... }`) cannot clear this timeout. If the component unmounts during the jitter window, `fetchNotifications()` fires on an unmounted component. The `isMountedRef` check prevents state updates but still fires a network request.
- **Impact:** Wasted network request after unmount; potential console warnings in StrictMode.
- **Suggested fix:**

```typescript
const visibilityTimeoutRef = useRef<ReturnType<typeof setTimeout> | null>(null);

const handleVisibility = () => {
  if (document.visibilityState === 'hidden') {
    clearPolling();
    if (visibilityTimeoutRef.current) clearTimeout(visibilityTimeoutRef.current);
  } else {
    // ...
    visibilityTimeoutRef.current = setTimeout(() => {
      if (!isMountedRef.current) return;
      fetchNotifications();
      scheduleNext();
    }, jitter);
  }
};

return () => {
  clearPolling();
  if (visibilityTimeoutRef.current) clearTimeout(visibilityTimeoutRef.current);
  notificationAbortRef.current?.abort();
  // ...
};
```

**[CR-006]** Like response parse failure silently reverts UI without user feedback

- **File:** `src/components/recipe/RecipeFeed.tsx:298-305`
- **Issue:** If the like API returns 200 OK but the response body isn't valid JSON, the catch block reverts the optimistic UI update and logs a `console.warn`. The user sees their like toggle back with no explanation. The server recorded the like, but the client shows it as un-liked — data inconsistency.
- **Impact:** Silent UI/server state divergence on edge-case network corruption.
- **Suggested fix:** Show a snackbar error so the user knows something went wrong, and/or refetch like status to reconcile:

```typescript
} catch (parseError) {
  console.warn('Like response parse failed, reverting:', parseError);
  setRecipeLikes(prev => ({ ...prev, [recipeId]: currentLikeState }));
  setSnackbar({ open: true, message: 'Like may not have saved. Please try again.', severity: 'warning' });
}
```

**[CR-007]** `validateUpdateData` is public but should be private

**[CR-008]** Notification polling exponential backoff uses failure count, not consecutive failures

- **File:** `src/hooks/useNotificationPolling.ts:113-118`
- **Issue:** The backoff formula uses `failureTimestampsRef.current.length` (total failures in the sliding window). After the circuit breaker resets and one successful poll clears the array, the backoff drops to base interval. But if a transient issue causes 5 failures then 1 success then 5 more failures, the backoff resets to minimum after each success, hammering the server.
- **Impact:** Under intermittent failure conditions, the polling doesn't back off effectively and can amplify load on a struggling server.
- **Suggested fix:** Use consecutive failure count instead, or don't clear the failure array on success — just let the sliding window expire naturally.

#### LOW

**[CR-009]** Recipe match pre-filter limited to first 50 pantry items

- **File:** `src/app/api/recipes/match/route.ts:96`
- **Issue:** `.slice(0, 50)` on `pantryNames` means users with >50 pantry items only use the first 50 for the DB-level pre-filter. Items after index 50 are completely ignored for candidate selection.
- **Impact:** Missed recipe matches for power users with large pantries.
- **Suggested fix:** If the limit is for SQL query size, consider batching the query or increasing the limit with a comment explaining the tradeoff.

**[CR-010]** `normalizeIngredientName` simple stemming produces incorrect results

- **File:** `src/lib/utils/ingredients.ts:22-35`
- **Issue:** The plural normalization logic turns "cheese" → "chees" (strips trailing 's'), "lettuce" → "lettuc". These are false positives that won't match their singular forms correctly in reverse lookups.
- **Impact:** Ingredient matching may fail for common words ending in 's' or 'e' that aren't plurals.
- **Suggested fix:** Consider using a stemming library (e.g., `natural` or `stemmer`) or maintaining an exceptions list for common cooking ingredients.

**[CR-011]** `Navigation.tsx` is a ~700-line monolith component

- **File:** `src/components/Navigation.tsx`
- **Issue:** Single component handles desktop nav, mobile nav, drawer, notification dropdown, create recipe dialog, search dialog, and tab management. Already partially extracted (`CreateRecipeDialog`, `NotificationDropdown`) but the main file is still massive.
- **Impact:** Difficult to reason about, test, and modify. High risk of regression when changing any navigation behavior.
- **Suggested fix:** Extract `MobileDrawer`, `DesktopMenu`, and `MobileBottomNav` into separate components. The parent `Navigation` should only orchestrate state.
