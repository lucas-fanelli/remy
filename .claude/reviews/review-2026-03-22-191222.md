## Code Review — 2026-03-22

### Summary

Auth routes are reasonably structured but share significant duplication. The upload route has a content-type reflection vulnerability and missing rate limiting on a resource-intensive endpoint.

### Findings

#### CRITICAL

**[CR-001]** Content-Type header value reflected in error response without sanitization

- **File:** `src/app/api/upload/route.ts:41`
- **Issue:** The raw `contentType` header value is interpolated directly into the JSON error response. An attacker can craft a malicious Content-Type header containing HTML/script payloads. While JSON responses typically have `application/json` content-type, some older browsers or misconfigured proxies may sniff content, and the reflected value could be used in XSS chains if the response is rendered in a non-JSON context.
- **Impact:** Reflected XSS via header injection in environments with content sniffing enabled; log poisoning if this value propagates to logging or monitoring dashboards.
- **Suggested fix:**

```typescript
return NextResponse.json(
  { error: 'Invalid Content-Type. Expected multipart/form-data.' },
  { status: 400 }
);
```

Do not echo user-controlled input in error messages.

#### HIGH

**[CR-002]** No rate limiting on login endpoint — brute-force vector

- **File:** `src/app/api/auth/login/route.ts`
- **Issue:** No rate limiting on the login endpoint. An attacker can make unlimited login attempts to brute-force credentials. The generic "Invalid credentials" message is good (no user enumeration), but without rate limiting it's still trivially brute-forceable.
- **Impact:** Credential compromise through brute-force attacks.
- **Suggested fix:** Add rate limiting middleware — either at the Next.js middleware level, via an in-memory store (e.g., `rate-limiter-flexible`), or at the infrastructure layer (reverse proxy / WAF). At minimum, limit to ~10 attempts per IP per minute.

**[CR-003]** No rate limiting on registration endpoint — account spam vector

- **File:** `src/app/api/auth/register/route.ts`
- **Issue:** Same as CR-002 but for registration. Unlimited account creation is possible.
- **Impact:** Mass account creation, resource exhaustion, abuse of the platform.
- **Suggested fix:** Same as CR-002. Rate limit registrations more aggressively (~5/hour per IP).

**[CR-004]** No rate limiting on file upload — resource exhaustion

- **File:** `src/app/api/upload/route.ts`
- **Issue:** An authenticated user can upload unlimited files. Each upload triggers a Cloudinary API call and buffer allocation. No throttling exists.
- **Impact:** Cloudinary bill explosion, memory exhaustion on the server from rapid concurrent uploads, potential DoS.
- **Suggested fix:** Rate limit uploads per user (e.g., 20/hour). Track upload count in-memory or in the database.

**[CR-005]** Timing side-channel on credential validation

- **File:** `src/app/api/auth/login/route.ts:39`
- **Issue:** The error matching uses `error.message.includes('Invalid credentials')`. If the underlying `authService.login` returns faster for "user not found" than for "wrong password" (e.g., skipping bcrypt comparison when user doesn't exist), the response time leaks whether a username exists despite the generic error message.
- **Impact:** User enumeration via timing analysis, undermining the benefit of the generic error message.
- **Suggested fix:** Ensure `authService.login` always performs a bcrypt comparison (against a dummy hash) even when the user is not found. Verify this in the service implementation.

**[CR-006]** Error string matching is fragile and couples route to service internals

- **File:** `src/app/api/auth/login/route.ts:39`, `src/app/api/auth/register/route.ts:39`
- **Issue:** `error.message.includes('Invalid credentials')` and `error.message.includes('already exists')` are brittle. If anyone changes the error message text in the service layer, these routes silently break and start returning 500s instead of 401/409.
- **Impact:** Silent behavior change from seemingly unrelated edits; incorrect HTTP status codes returned to clients.
- **Suggested fix:** Use typed error classes instead of string matching:

```typescript
// domain/errors.ts
export class InvalidCredentialsError extends Error { ... }
export class ConflictError extends Error { ... }

// In route:
if (error instanceof InvalidCredentialsError) {
  return ApiResponseHelper.unauthorized(error.message);
}
```

#### MEDIUM

**[CR-007]** Login and register routes are ~90% duplicated

- **File:** `src/app/api/auth/login/route.ts`, `src/app/api/auth/register/route.ts`
- **Issue:** Both routes share identical patterns: content-type check, JSON parsing, Zod validation, destructuring token from result, setting cookie, error handling. The only differences are the schema, service method, status code, and message.
- **Impact:** Maintenance burden — any fix to the pattern must be applied in both places (and any future auth routes).
- **Suggested fix:** Extract a shared `handleAuthRoute` helper:

```typescript
async function handleAuthRoute(request, schema, action, statusCode, successMessage) { ... }
```

**[CR-008]** `formData.get('file') as File` type assertion before null/type check

- **File:** `src/app/api/upload/route.ts:48`
- **Issue:** The `as File` cast happens before the null check on line 50 and the `instanceof` check on line 55. If `formData.get('file')` returns a string (which is valid per the FormData spec for non-file fields), the `as File` silently lies about the type. The `instanceof` check on line 55 catches this, but the cast on line 48 is misleading.
- **Impact:** Code readability — the cast implies confidence that contradicts the subsequent checks.
- **Suggested fix:**

```typescript
const file = formData.get('file');

if (!file || !(file instanceof File)) {
  return NextResponse.json({ error: 'No valid file provided' }, { status: 400 });
}
// TypeScript now narrows `file` to `File` without a cast
```

**[CR-009]** Entire file buffered into memory before validation

- **File:** `src/app/api/upload/route.ts:71-72`
- **Issue:** `file.arrayBuffer()` reads the entire file into memory. While there's a 5MB size check on `file.size` beforehand, `file.size` is client-reported metadata and may not match actual payload size. A malicious client could report `size: 100` but send a much larger body.
- **Impact:** Memory exhaustion if the actual payload exceeds the reported size.
- **Suggested fix:** Either enforce the size limit at the infrastructure layer (Next.js `bodyParser` config, reverse proxy), or read the buffer in chunks and abort if cumulative size exceeds the limit. At minimum, add a post-read size check:

```typescript
if (buffer.byteLength > maxSize) {
  return NextResponse.json({ error: 'File too large.' }, { status: 400 });
}
```

**[CR-010]** Upload response exposes file metadata unnecessarily

- **File:** `src/app/api/upload/route.ts:85-89`
- **Issue:** The response includes `size` and `type` — both are client-provided values echoed back. The client already knows these. Returning them adds no value and increases the attack surface (client-provided data reflected in responses).
- **Impact:** Low direct risk, but unnecessary data exposure is a defense-in-depth violation.
- **Suggested fix:**

```typescript
return NextResponse.json({ success: true, url: fileUrl });
```

#### LOW

**[CR-011]** Inconsistent error response format between upload route and auth routes

- **File:** `src/app/api/upload/route.ts:29,33,41,51,56,62,67,78,92`
- **Issue:** The upload route uses `{ error: '...' }` while auth routes use `ApiResponseHelper` which presumably returns `{ success: false, error: '...' }` or similar. Clients must handle two different error response shapes.
- **Impact:** Client-side error handling complexity; inconsistent API contract.
- **Suggested fix:** Use `ApiResponseHelper` in the upload route as well for consistent error response shape.

**[CR-012]** `image/jpg` is not a valid MIME type

- **File:** `src/app/api/upload/route.ts:58`
- **Issue:** The allowed types list includes `image/jpg`, which is not a registered IANA MIME type. The correct type is `image/jpeg`. Browsers always send `image/jpeg`, so `image/jpg` is dead code that creates false confidence.
- **Impact:** Dead code; misleading allowed-types list.
- **Suggested fix:** Remove `'image/jpg'` from the array.
