## Code Review — 2026-03-22

### Summary

File upload endpoint with decent validation but missing rate limiting, no file name sanitization, and a silent type coercion that bypasses the instanceof check.

### Findings

#### CRITICAL

**[CR-001]** `as File` cast silently bypasses the `instanceof` check on the next line

- **File:** `src/app/api/upload/route.ts:44`
- **Issue:** `formData.get('file')` returns `FormDataEntryValue | null`, which is `string | File | null`. The `as File` cast on line 44 tells TypeScript it's a `File`, but if the user submits a plain string field named `file`, the value is a `string`. In the Node.js `FormData` implementation, a plain string will **not** be an instance of `File` — but the cast hides the type mismatch from the compiler. More critically, if the runtime `FormData` implementation wraps values differently (e.g., in edge runtimes or polyfills), the `instanceof File` check on line 49 can pass for non-File objects. The safe pattern is to check before casting.
- **Impact:** Depending on runtime, a crafted request with a string field named `file` could bypass validation or cause unexpected behavior.
- **Suggested fix:**

  ```typescript
  const fileEntry = formData.get('file');

  if (!fileEntry || !(fileEntry instanceof File)) {
    return NextResponse.json({ error: 'No valid file provided' }, { status: 400 });
  }

  const file = fileEntry; // TypeScript now narrows to File
  ```

#### HIGH

**[CR-002]** No rate limiting on file upload endpoint

- **File:** `src/app/api/upload/route.ts:22`
- **Issue:** Any authenticated user can call this endpoint in a tight loop, uploading unlimited files to Cloudinary. There is no per-user or global rate limit.
- **Impact:** A single compromised or malicious account can exhaust your Cloudinary storage/bandwidth quota and run up costs. This is a denial-of-wallet attack vector.
- **Suggested fix:** Apply a rate limiter (e.g., per-user, 10 uploads per minute) either in middleware or at the top of this handler.

**[CR-003]** `file.type` is client-supplied and trusted for MIME validation before magic bytes check

- **File:** `src/app/api/upload/route.ts:55-61`
- **Issue:** `file.type` comes from the `Content-Type` of the multipart part, which is entirely client-controlled. While you do validate magic bytes later (good), the early `file.type` check gives a false sense of security and the `file.type` value is returned verbatim in the response on line 90. A client can send `type: "image/jpeg"` with a valid JPEG but the actual intent is to pair that with a misleading filename. More importantly, you rely on `file.type` in the response — the consumer of this API might trust that `type` field.
- **Impact:** The response `type` field can lie about the actual image format. Downstream consumers trusting this value could mishandle the file.
- **Suggested fix:** Derive the MIME type from the magic bytes validation rather than trusting the client-supplied value. Return the detected type, not `file.type`.

**[CR-004]** No file name or metadata sanitization

- **File:** `src/app/api/upload/route.ts:44`
- **Issue:** `file.name` is never inspected or sanitized. While it's not directly used in a file path here (Cloudinary generates its own ID), the `File` object's name travels through `uploadToCloudinary`. If `uploadToCloudinary` ever uses `file.name` for the Cloudinary `public_id` or passes it through, path traversal or injection is possible.
- **Impact:** Depends on `uploadToCloudinary` internals — if the filename is ever used, it's an injection vector.
- **Suggested fix:** Either explicitly strip `file.name` before passing downstream, or verify that `uploadToCloudinary` never uses it. Document the assumption.

#### MEDIUM

**[CR-005]** `allowedTypes` array is hardcoded and duplicated

- **File:** `src/app/api/upload/route.ts:55`
- **Issue:** `image/jpg` is not a valid IANA MIME type — the correct type is `image/jpeg`. Including it suggests confusion. Also, this allowed-types list is likely duplicated in the avatar upload route (`/api/upload/avatar/route.ts`) and possibly in client-side validation. Any change requires updating multiple files.
- **Impact:** Maintenance burden; possible inconsistency between upload endpoints if one is updated and the other isn't.
- **Suggested fix:** Extract to a shared constant (e.g., `ALLOWED_IMAGE_TYPES` in `src/lib/constants.ts`), remove the bogus `image/jpg`, and import it in both routes.

**[CR-006]** `5MB` max size is hardcoded

- **File:** `src/app/api/upload/route.ts:64`
- **Issue:** The max file size is a magic number. If you ever need to change it (e.g., different limits for free vs. paid users, or different limits for recipe images vs. avatars), you'd need to find and update every occurrence.
- **Impact:** Configuration scattered in code rather than centralized.
- **Suggested fix:** Move to `src/lib/constants.ts`:
  ```typescript
  export const MAX_UPLOAD_SIZE_BYTES = 5 * 1024 * 1024;
  ```

**[CR-007]** Full `arrayBuffer` loaded into memory — no streaming

- **File:** `src/app/api/upload/route.ts:70-71`
- **Issue:** The entire file is read into memory as an `ArrayBuffer` and then copied into a `Buffer`. For a 5MB file this is fine, but if `maxSize` is ever increased or if many concurrent uploads happen, this creates significant memory pressure (two copies: `ArrayBuffer` + `Buffer`).
- **Impact:** Under concurrent load, memory usage spikes to `~10MB * concurrent_uploads` just for buffer duplication.
- **Suggested fix:** At minimum, document the constraint. Ideally, stream the file to Cloudinary using its stream upload API to avoid double-buffering.

**[CR-008]** `tokenService.verify` failure mode is ambiguous

- **File:** `src/app/api/upload/route.ts:29-33`
- **Issue:** If `verify` throws (e.g., expired token, malformed JWT), the error is caught by the outer try/catch and returns a generic 500 error instead of a 401. Only a `null` return is handled as unauthorized.
- **Impact:** Expired or malformed tokens return 500 instead of 401, confusing clients and leaking implementation details in logs.
- **Suggested fix:** Either wrap `verify` in its own try/catch returning 401, or ensure `verify` never throws and always returns `null` on failure.

#### LOW

**[CR-009]** Response leaks file metadata unnecessarily

- **File:** `src/app/api/upload/route.ts:86-91`
- **Issue:** The response includes `size` and `type` from the uploaded file. The caller already knows these (they sent the file). Returning them adds no value and slightly increases the response surface.
- **Impact:** Minor information exposure; negligible but unnecessary.
- **Suggested fix:** Return only `{ success: true, url: fileUrl }`.

**[CR-010]** Comment says "Disable body parsing" but doesn't actually disable it

- **File:** `src/app/api/upload/route.ts:9`
- **Issue:** `export const runtime = 'nodejs'` sets the runtime but doesn't disable body parsing. In Next.js App Router, body parsing for `formData()` is handled automatically — the comment is misleading. In the Pages Router you'd need `export const config = { api: { bodyParser: false } }`, but that doesn't apply here.
- **Impact:** Misleading comment; someone may think this line is load-bearing for file uploads when it isn't.
- **Suggested fix:** Remove the comment or replace it with an accurate one explaining why the Node.js runtime is selected (e.g., `Buffer` usage, Cloudinary SDK compatibility).
