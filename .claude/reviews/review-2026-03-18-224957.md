## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured with good auth patterns (httpOnly cookies, CSRF protection, atomic DB operations). Several security gaps, race conditions, and data integrity issues found across API routes and client components.

### Findings

#### CRITICAL

**[CR-001]** Recipe image URL validation bypass via double-encoding

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:48-58`
- **Issue:** Comment says `new URL() normalizes %2e%2e to .. before this check runs` but this is incorrect for all URL parsers. A path like `/%2e%2e/%2e%2e/etc/passwd` may not be normalized to `../../etc/passwd` by `new URL()` in all runtimes — Node's `URL` class preserves percent-encoding in `pathname`. The `..` traversal check is ineffective against encoded variants.
- **Impact:** Path traversal in Cloudinary URL validation could allow storing arbitrary URLs in comment imageUrl field.
- **Suggested fix:** Decode the pathname before checking:

```typescript
const decodedPath = decodeURIComponent(url.pathname);
if (decodedPath.includes('..') || !decodedPath.startsWith(`/${cloudName}/`)) {
```

**[CR-002]** `insufficientIngredients` array leaks data on unrelated errors

- **File:** `src/app/api/cooked-recipes/route.ts:80,196-204`
- **Issue:** `insufficientIngredients` is declared _outside_ the try block at line 80. If an unrelated error occurs after partial ingredient checking but before the transaction completes, the catch block at line 196 returns a 500 but the array may contain partial pantry data from a failed run. More critically, the INSUFFICIENT_INGREDIENTS error handler at line 191 returns the array, but it was populated inside a transaction that was rolled back — the data reflects a state that no longer exists.
- **Impact:** Information disclosure of pantry contents in error responses; confusing client-side behavior with stale data.
- **Suggested fix:** Move the declaration inside the try block, or clear it in the catch before returning:

```typescript
// Move declaration inside the try, or:
} catch (error) {
  insufficientIngredients.length = 0; // Clear before any error response
```

**[CR-003]** No CSRF protection on logout endpoint

- **File:** `src/app/api/auth/logout/route.ts:4-15`
- **Issue:** The comment claims "CSRF protection is handled by middleware" but the middleware CSRF check requires `Content-Type: application/json` OR `Sec-Fetch-Site: same-origin` OR `X-Requested-With` header. A cross-site `<form method="POST">` with `Content-Type: text/plain` would bypass the middleware check if the browser doesn't send `Sec-Fetch-Site`. The logout endpoint then clears the cookie, logging the user out. This is a CSRF logout attack.
- **Impact:** Attacker can force-logout any user by tricking them into visiting a malicious page.
- **Suggested fix:** Require `Content-Type: application/json` explicitly in the logout handler, or verify a CSRF token:

```typescript
const contentType = request.headers.get('content-type');
if (!contentType?.includes('application/json')) {
  return NextResponse.json({ error: 'Invalid content type' }, { status: 400 });
}
```

#### HIGH

**[CR-004]** Admin user deletion has no cascading image cleanup

- **File:** `src/app/api/admin/users/[id]/route.ts:30-39`
- **Issue:** When an admin deletes a user, all their recipes are cascade-deleted by Prisma, but the Cloudinary images for those recipes are never cleaned up. This creates permanent orphaned images in Cloudinary.
- **Impact:** Storage costs grow unbounded; orphaned images persist forever in Cloudinary.
- **Suggested fix:** Before deleting the user, query all their post imageUrls and queue Cloudinary deletions (or at minimum, log them for the cleanup script).

**[CR-005]** Recipe match endpoint loads all pantry items and recipes into memory

- **File:** `src/app/api/recipes/match/route.ts:65-170`
- **Issue:** The endpoint loads the entire pantry (no limit), then fetches up to 500 candidate recipe IDs, then loads them in batches. For a user with a large pantry and a database with many recipes, this can consume significant memory per request. The `nameConditions` array is capped at 100 but each generates a SQL `LIKE` with `%` wildcards — this is an O(N\*M) scan that won't use indexes effectively.
- **Impact:** Memory exhaustion under load; slow queries with large datasets; potential DoS vector for authenticated users.
- **Suggested fix:** Add pagination to the match results, cap pantry items loaded, and consider a GIN index-based approach instead of LIKE patterns.

**[CR-006]** Notification polling has no server-side pagination guard

- **File:** `src/app/api/notifications/route.ts:31`
- **Issue:** The `limit` parameter accepts up to 100 and `offset` is unbounded. A malicious user could request `limit=100&offset=0`, then `offset=100`, etc., performing a full table scan of their notifications. Combined with the 60-second polling interval, this is manageable, but the absence of a total count means the client can poll indefinitely.
- **Impact:** Unnecessary database load from unbounded offset queries.
- **Suggested fix:** Return `total` count in the response and have the client stop polling when all notifications are fetched. Consider cursor-based pagination.

**[CR-007]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:130-175`
- **Issue:** When filters change, `loadRecipes(true)` resets the recipe list. But if the abort controller races with the state update, recipes from the old filter set could be appended after the reset. The deduplication at line 161 only checks existing IDs, not whether the recipes match the current filters.
- **Impact:** Users may see recipes that don't match their selected filters after rapid filter changes.
- **Suggested fix:** Tag each fetch with a generation counter and discard results from stale generations.

**[CR-008]** Comment image upload creates orphaned Cloudinary images on failure

- **File:** `src/components/recipe/CommentsSection.tsx:118-145`
- **Issue:** If the image upload succeeds but the comment POST fails, the uploaded image is orphaned in Cloudinary. The code acknowledges this with comments ("can be cleaned by a periodic server-side cron job") but the cleanup script (`cleanup-orphaned-images.ts`) only checks `Post.imageUrl`, `Comment.imageUrl`, and `User.avatar` — it would correctly identify these orphans, but only if run.
- **Impact:** Cloudinary storage leak; no automated cleanup is configured.
- **Suggested fix:** Either delete the uploaded image on comment failure, or ensure the cleanup cron is actually scheduled.

#### MEDIUM

**[CR-009]** `useNotificationPolling` circuit breaker never fully resets failure history

- **File:** `src/hooks/useNotificationPolling.ts:126-128`
- **Issue:** When the circuit breaker trips (10 failures in 10 minutes), `pollingStoppedRef` is set to true. In `scheduleNext`, if 5 minutes pass, it resets `pollingStoppedRef` and clears `failureTimestampsRef`. But in `handleVisibility`, it only resets `pollingStoppedRef` without clearing `failureTimestampsRef`. This means the sliding window still has old timestamps, and a single new failure could re-trip the breaker immediately.
- **Impact:** Notification polling may stay broken longer than intended after transient errors.
- **Suggested fix:** Also clear `failureTimestampsRef` in the visibility handler, or let the sliding window naturally expire old timestamps (the comment says this but the code resets it in `scheduleNext`).

**[CR-010]** Admin dashboard stats use `|| 0` which hides null stats

- **File:** `src/app/admin/page.tsx:89-114`
- **Issue:** `stats?.totalUsers || 0` — if the API returns `0` for any stat, `|| 0` would preserve it, but the optional chaining `stats?.` combined with `|| 0` means a `null` stats object silently shows zeros instead of an error state. The `error` state is set but the statCards still render with zeros.
- **Impact:** Admin sees a dashboard full of zeros when the API fails, instead of an error message.
- **Suggested fix:** Don't render stat cards when `stats` is null; only render them after a successful fetch.

**[CR-011]** `PersistentSearchBar` debounce timer not cleared on unmount in all paths

- **File:** `src/components/search/PersistentSearchBar.tsx:120-145`
- **Issue:** The `useEffect` cleanup aborts the controller and clears the timeout, but if the component unmounts during the 300ms debounce window, the abort controller is created but the timeout's fetch hasn't started yet. The cleanup correctly handles this, but `setLiveResults` and `setIsSearching` are called without checking if the component is still mounted after the async fetch completes (line 133).
- **Impact:** React "Can't perform a React state update on an unmounted component" warning (non-critical but noisy).
- **Suggested fix:** The AbortController signal will cause the fetch to throw AbortError which is already caught, so this is actually handled. However, `setIsSearching(true)` at line 129 runs synchronously before the fetch and wouldn't be cleaned up. Add an isMounted ref check.

**[CR-012]** `safeRating` function conflates "unrated" (null) with "rated zero"

- **File:** `src/lib/utils/recipe.ts:11`
- **Issue:** The comment says "A return value of 0 means 'no rating' (the recipe has not been rated yet), not a valid score" but the function converts `null` to `0`. Downstream code checks `averageRating > 0` to decide whether to show ratings, but if a recipe somehow gets a 0 average (impossible with 1-5 scale), it would be hidden. More importantly, serializing null as 0 loses information for API consumers.
- **Impact:** API consumers cannot distinguish between "unrated" and "zero average" without reading documentation.
- **Suggested fix:** Return `null` instead of `0` for unrated recipes, and handle null in display components.

**[CR-013]** `EditProfileModal` avatar upload doesn't validate magic bytes

- **File:** `src/components/profile/EditProfileModal.tsx:89-96`
- **Issue:** The client-side avatar selection validates MIME type and file size, but unlike the server-side `/api/upload/avatar` endpoint which validates magic bytes, the client only checks `file.type` which is spoofable. If the server-side validation rejects a file after the user already sees a preview, the UX is confusing.
- **Impact:** Poor UX when a user selects a file with a valid extension but invalid content; no client-side feedback until submission.
- **Suggested fix:** Validate magic bytes client-side before showing the preview, or at minimum show a clear error when the server rejects the file.

**[CR-014]** Pantry page doesn't handle concurrent edits

- **File:** `src/app/pantry/page.tsx:175-214`
- **Issue:** The `handleSubmit` function checks for duplicate ingredients client-side using the stale `items` array. If two browser tabs add the same ingredient simultaneously, both would pass the client-side check. The server-side pantry POST endpoint doesn't check for duplicates either — it only enforces the item count limit.
- **Impact:** Duplicate pantry items can be created.
- **Suggested fix:** Add a unique constraint on `(pantryId, name)` in the database, or check for duplicates inside the server-side transaction.
