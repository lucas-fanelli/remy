## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps in the middleware, a data loss race condition in the cooked-recipes flow, and multiple instances of sensitive data leaking in error responses.

### Findings

#### CRITICAL

**[CR-001]** Middleware CSRF check is bypassable for multipart uploads without `X-Requested-With`

- **File:** `src/middleware.ts:186-196`
- **Issue:** The CSRF check relies on `Content-Type: application/json` OR `X-Requested-With` header OR `Sec-Fetch-Site`. Browsers send `multipart/form-data` for standard form submissions, which won't have `application/json`. If a client forgets `X-Requested-With` and the browser doesn't send `Sec-Fetch-Site` (older browsers), a cross-site form POST to `/api/upload` could succeed with the victim's cookies.
- **Impact:** Cross-site file upload or profile modification via form submission on older browsers.
- **Suggested fix:** The upload routes already require `X-Requested-With: fetch` — enforce this in middleware by explicitly rejecting `multipart/form-data` requests that lack either `Sec-Fetch-Site: same-origin` or `X-Requested-With`:

```ts
if (
  contentType?.includes('multipart/form-data') &&
  !isSameOrigin &&
  !request.headers.has('x-requested-with')
) {
  return NextResponse.json({ error: 'Missing required request header' }, { status: 403 });
}
```

**[CR-002]** `recalc-ratings` raw SQL is vulnerable to lock key collision

- **File:** `src/app/api/admin/recalc-ratings/route.ts:24`
- **Issue:** `PG_ADVISORY_LOCK_RECALC_RATINGS = 48879` is a hardcoded magic number with no namespace. Any other feature using `pg_advisory_xact_lock(48879)` will deadlock or serialize against this endpoint. Additionally, the advisory lock is transaction-scoped but there's no timeout — a long-running transaction holds the lock indefinitely.
- **Impact:** Potential deadlock if another feature uses the same lock ID. No timeout means a slow query blocks all subsequent recalc attempts.
- **Suggested fix:** Use a 2-key advisory lock with a namespace: `SELECT pg_advisory_xact_lock(0xDEAD, 0xBEEF)` and add `SET LOCAL statement_timeout = '30s'` inside the transaction.

**[CR-003]** Upload cleanup endpoint allows any authenticated user to delete any Cloudinary image

- **File:** `src/app/api/upload/cleanup/route.ts:27-43`
- **Issue:** The endpoint only checks that the user is authenticated, then deletes whatever Cloudinary public_id is extracted from the provided URL. There's no ownership check — any logged-in user can delete another user's recipe images or avatars.
- **Impact:** Data loss. Any authenticated user can destroy images belonging to other users.
- **Suggested fix:** Either remove this public endpoint entirely (handle orphan cleanup via a cron/background job), or verify that the image URL belongs to a resource owned by the requesting user before deleting.

#### HIGH

**[CR-004]** Cooked-recipes pantry deduction has insufficient-ingredients race with concurrent requests

- **File:** `src/app/api/cooked-recipes/route.ts:107-145`
- **Issue:** The pantry read + deduction logic inside the transaction doesn't lock the pantry row. Two concurrent "mark as cooked" requests for different recipes could read the same pantry quantities, both decide they have enough, and both deduct — resulting in negative quantities or deleting items that the other request already claimed. The pantry POST endpoint correctly uses `FOR UPDATE` but this route does not.
- **Impact:** Pantry quantities can go negative or items can be double-deducted.
- **Suggested fix:** Add `SELECT ... FOR UPDATE` on the UserPantry row before reading items:

```ts
await tx.$executeRaw`SELECT id FROM "UserPantry" WHERE "userId" = ${payload.userId} FOR UPDATE`;
```

**[CR-005]** Admin user deletion has no self-protection for the last admin

- **File:** `src/app/api/admin/users/[id]/route.ts:18-33`
- **Issue:** While there's a check preventing admins from deleting themselves, there's no check preventing an admin from deleting the only _other_ admin, leaving just themselves. More critically, if two admins simultaneously try to delete each other, both requests pass the self-check and both deletions succeed, leaving zero admins.
- **Impact:** Platform can end up with zero admin users, with no way to recover without direct database access.
- **Suggested fix:** Count admins before deletion and reject if it would leave fewer than 1 (or 2 for safety):

```ts
const adminCount = await prisma.user.count({ where: { role: 'ADMIN' } });
if (adminCount <= 1) {
  return NextResponse.json({ error: 'Cannot delete the last admin' }, { status: 400 });
}
```

**[CR-006]** `search` API route leaks user emails despite defense-in-depth comment

- **File:** `src/app/api/search/route.ts:33-35`
- **Issue:** The code strips `email` from the destructured result with `({ email, ...rest }) => rest`, but the `UserRepository.search()` already excludes email at the query level. The comment claims "defense-in-depth" but the actual risk is that if `UserRepository.search` is ever changed to include email, the TypeScript type wouldn't catch it because `email` is destructured silently. More importantly, the `email` field is typed on `User` — the `.map` destructuring works but `rest` still satisfies `UserPublicProfile` which includes `email?: string`. The real issue: there is **no test** verifying that email is actually absent from the response.
- **Impact:** If repository implementation changes, emails could leak to unauthenticated users.
- **Suggested fix:** Add an explicit assertion in the API test that the response objects do not contain `email` fields.

**[CR-007]** Recipe match endpoint loads up to 500 candidate IDs then fetches them in batches — no index guarantee

- **File:** `src/app/api/recipes/match/route.ts:87-98`
- **Issue:** The raw SQL query uses `jsonb_array_elements` with `LIKE` patterns for pre-filtering. This performs a full sequential scan on the `Post` table's `ingredients` JSONB column. The comment mentions "a GIN index... migration already exists" but there's no validation that the index is actually deployed. With a large recipe table, this query will be extremely slow.
- **Impact:** Performance degradation under load. The endpoint could time out with thousands of recipes.
- **Suggested fix:** Add a startup check or migration assertion that the GIN index exists. Consider using `@>` containment operator with GIN instead of `LIKE` on `jsonb_array_elements`.

#### MEDIUM

**[CR-008]** `AuthContext` logout retry loop can silently fail, leaving stale cookies

- **File:** `src/contexts/AuthContext.tsx:96-112`
- **Issue:** The logout function clears local state immediately (optimistic) then tries to clear the server cookie with 2 retry attempts. If both fail (e.g., network down), only a `console.warn` is emitted. The user sees "logged out" but the httpOnly cookie persists until expiry (7 days). On the next page load, `/api/auth/me` will succeed and re-authenticate them.
- **Impact:** User believes they're logged out but auth persists for up to 7 days on shared/public devices.
- **Suggested fix:** Show a user-facing toast/alert when cookie clearance fails, suggesting they clear browser cookies. Consider a shorter cookie maxAge.

**[CR-009]** Notification polling circuit breaker never fully resets failure history

- **File:** `src/hooks/useNotificationPolling.ts:78-80`
- **Issue:** After a successful fetch, the comment says "Don't clear failureTimestampsRef — let the sliding window expire naturally." But the backoff calculation in `scheduleNext` uses `failureTimestampsRef.current.length` for `Math.pow(2, length)`. Old failures within the 10-minute window will keep the backoff elevated even after multiple successes. This means after a transient network blip that causes 3 failures, the polling interval stays at `BASE_INTERVAL * 8` for up to 10 minutes even though the network recovered.
- **Impact:** Delayed notification delivery after transient failures.
- **Suggested fix:** Clear or reduce failure timestamps on successful fetch:

```ts
if (response.ok) {
  failureTimestampsRef.current = []; // Reset on success
```

**[CR-010]** `recipe/[id]/page.tsx` performs client-side image rendering without sanitization

- **File:** `src/app/recipe/[id]/page.tsx:~multiple locations`
- **Issue:** Instruction images and comment images are rendered via `<Box component="img" src={instruction.image}>`. While the image URLs are validated as Cloudinary URLs on write, if the validation is ever bypassed (e.g., direct DB edit, migration issue), arbitrary URLs would be rendered as images. Combined with the fullscreen image viewer dialog, this could render unexpected content.
- **Impact:** Low probability but high impact if image URL validation is bypassed.
- **Suggested fix:** Add a client-side guard that only renders images from `res.cloudinary.com`:

```ts
const isCloudinaryUrl = (url: string) => url.startsWith('https://res.cloudinary.com/');
```

**[CR-011]** `RecipeFeed` infinite scroll sentinel has no debounce beyond 500ms timestamp check

- **File:** `src/components/recipe/RecipeFeed.tsx:~IntersectionObserver`
- **Issue:** The IntersectionObserver callback checks `Date.now() - lastLoadTimeRef.current > 500` but the observer has `rootMargin: '500px'`, meaning it fires when the sentinel is 500px from the viewport. On fast scrolling, the observer can fire multiple times within the 500ms window, and the `loadingRef.current` guard may not yet be true if the fetch hasn't started. This can cause duplicate fetches.
- **Impact:** Duplicate recipe pages loaded, duplicate items in the feed.
- **Suggested fix:** Set `loadingRef.current = true` synchronously inside the observer callback before calling `loadRecipes()`, or use a proper debounce.

**[CR-012]** `about/page.tsx` hardcodes brand name in text but uses `BRANDING` constant elsewhere

- **File:** `src/app/about/page.tsx:93,113,119`
- **Issue:** Text strings like "About Remy's", "What is Remy's?", "Remy's is a recipe sharing..." are hardcoded while `BRANDING.name`, `BRANDING.creator.name`, etc. are used elsewhere. This means rebranding requires updating these strings manually.
- **Impact:** Branding inconsistency if the app is rebranded.
- **Suggested fix:** Replace hardcoded strings with `BRANDING.name` template literals.

**[CR-013]** `EditProfileModal` avatar upload doesn't clean up orphaned Cloudinary image on profile save failure

- **File:** `src/components/profile/EditProfileModal.tsx:103-131`
- **Issue:** If avatar upload succeeds but `updateProfile()` fails, the uploaded image remains in Cloudinary as an orphan. Unlike `CommentsSection` which has orphan cleanup, `EditProfileModal` does not.
- **Impact:** Cloudinary storage leak — orphaned images accumulate over time.
- **Suggested fix:** Add cleanup logic in the catch block:

```ts
if (avatarUrl && avatarUrl !== user?.avatar) {
  fetch('/api/upload/cleanup', { method: 'POST', ... }).catch(() => {});
}
```

**[CR-015]** `getDifficultyColor` logs warning to console in development for unknown difficulties

- **File:** `src/lib/utils/recipe.ts:16-18`
- **Issue:** `console.warn` in a utility function called during render will fire on every render cycle for recipes with non-standard difficulty values. This pollutes dev console.
- **Impact:** Dev console noise.
- **Suggested fix:** Log once using a `Set` to track already-warned values, or remove the warning entirely.

**[CR-016]** Multiple admin pages import `useAuth` but only use `isAdmin` from `useAdminGuard`

- **File:** `src/app/admin/comments/page.tsx:29`, `src/app/admin/recipes/page.tsx:30`, etc.
- **Issue:** `isAuthenticated` from `useAuth` is used in `fetchComments`/`fetchRecipes` but `useAdminGuard` already ensures the user is admin (which implies authenticated). The `isAuthenticated` guard is redundant.
- **Impact:** Minor code smell — unnecessary coupling to `useAuth`.
- **Suggested fix:** Remove the `isAuthenticated` check from fetch callbacks since `useAdminGuard.isReady` already guarantees authentication.
