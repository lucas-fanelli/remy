## Code Review — 2026-03-18

### Summary

Large recipe-sharing platform with generally solid architecture (DI container, repository pattern, clean separation). Several data-integrity bugs, a double-write in profile editing, and silent error swallowing across admin and feed interactions.

### Findings

#### CRITICAL

**[CR-001]** Double API call when saving edited profile

- **File:** `src/components/profile/EditProfileModal.tsx:130-155`
- **Issue:** `handleSubmit` first calls `fetch('/api/users/profile', { method: 'PUT', ... })` directly, then immediately calls `await updateProfile(...)` from AuthContext, which ALSO sends a PUT to `/api/users/profile`. The profile is updated twice per save.
- **Impact:** Wasted network request on every profile edit. If the server has side effects (audit logs, webhooks), they fire twice. Race conditions are possible if another user/tab modifies the profile between the two calls.
- **Suggested fix:** Remove the direct `fetch` call and only use `updateProfile` from AuthContext, or vice versa — update the local AuthContext user state from the first response without making a second request.

```tsx
// In handleSubmit, replace both calls with:
const profileData = {
  fullName: formData.fullName.trim() || null,
  bio: formData.bio.trim() || null,
  website: formData.website.trim() || null,
  avatar: avatarUrl,
  isPrivate: formData.isPrivate,
};
await updateProfile(profileData); // Single call, updates server + local state
```

```tsx
} catch (error) {

```

#### HIGH

**[CR-003]** No runtime validation of JSON `ingredients`/`instructions` from database

- **File:** `src/app/api/recipes/match/route.ts:109`, `src/app/api/cooked-recipes/route.ts:108`
- **Issue:** `recipe.ingredients as Array<{ name: string; amount: string; unit: string }>` and similar casts are used everywhere without runtime validation. If any recipe has malformed JSON (missing `name` field, wrong types), the cast silently succeeds and the code throws at runtime with an unhelpful error.
- **Impact:** A single corrupt recipe row crashes the entire `/api/recipes/match` endpoint for ALL users. Runtime `TypeError: Cannot read property 'name' of undefined` with no indication of which recipe is broken.
- **Suggested fix:** Add a guard in the matching loop:

```typescript
for (const candidate of candidates) {
  if (!candidate.ingredients || !Array.isArray(candidate.ingredients)) continue;
  const recipeIngredients = candidate.ingredients as unknown as Ingredient[];
  // Validate shape before processing
  if (!recipeIngredients.every(i => typeof i?.name === 'string')) continue;
```

**[CR-004]** `handleLike` in RecipeFeed silently swallows JSON parse failure

- **File:** `src/components/recipe/RecipeFeed.tsx:296-298`
- **Issue:** Inside the `response.ok` branch, there's `try { ... } catch { /* JSON parse failed — keep optimistic state */ }`. If the server returns a 200 with malformed JSON, the UI keeps the optimistic like state that may not match the server.
- **Impact:** User sees "liked" but the server may have returned a different state. Like count drifts from reality with no way to detect or recover.
- **Suggested fix:** At minimum, log the error. Better: revert optimistic state on parse failure.

```typescript
} catch (parseError) {
  console.warn('Like response parse failed, reverting:', parseError);
  setRecipeLikes((prev) => ({
    ...prev,
    [recipeId]: currentLikeState,
  }));
}
```

**[CR-005]** Followers/following pages don't show error on failed follow toggle

- **File:** `src/app/profile/[username]/followers/page.tsx:60-72`, `src/app/profile/[username]/following/page.tsx:60-72`
- **Issue:** When `response.ok` is false, the code reverts the optimistic state but doesn't inform the user. `console.error` is only called on exception, not on non-ok response.
- **Impact:** User clicks "Follow", sees it revert with no explanation. Confusing UX, especially if the failure is due to a business rule (e.g., private account).
- **Suggested fix:** Add a snackbar/toast or at minimum set an error state when `!response.ok`.

**[CR-006]** `src/app/api/recipes/[id]/route.ts` DELETE regex for Cloudinary public ID is fragile

- **File:** `src/app/api/recipes/[id]/route.ts:128-131`
- **Issue:** The regex `imageUrl.match(/\/upload\/(?:v\d+\/)?(.+?)(?:\.\w+)?(?:\?.*)?$/)` to extract the Cloudinary public ID doesn't handle all Cloudinary URL formats (e.g., URLs with transformations like `/upload/w_300,h_200/v123/folder/image.jpg`, or URLs with multiple dots in folder names).
- **Impact:** Cloudinary images are orphaned after recipe deletion, accumulating storage costs.
- **Suggested fix:** Use a more robust extraction that handles transformation segments:

```typescript
const match = imageUrl.match(/\/upload\/(?:[^/]+\/)*v\d+\/(.+?)(?:\.\w+)?(?:\?.*)?$/);
```

Or better, store the `publicId` returned from upload alongside the URL.

#### MEDIUM

**[CR-007]** Inconsistent naming: `reviewCount` vs `totalRatings`

- **File:** Multiple files (`src/app/api/recipes/route.ts:104`, `src/app/api/recipes/[id]/route.ts:29`, `src/domain/types/recipe.ts:39-40`)
- **Issue:** The database field is `reviewCount`, the domain type has both `reviewCount` and `totalRatings`, and API responses use `totalRatings`. Different files use different names for the same concept. `RecipeRepository.mapToRecipe` maps it to `totalRatings`, but `Recipe` type has both `reviewCount?: number` and `totalRatings?: number`.
- **Impact:** Confusing for developers. Risk of using the wrong field name and getting `undefined`.
- **Suggested fix:** Pick one name and use it consistently. Remove the duplicate from the domain type.

**[CR-008]** Navigation component is 1100+ lines with 7+ responsibilities

- **File:** `src/components/Navigation.tsx`
- **Issue:** This single component handles: desktop nav, mobile nav, drawer, notification polling with exponential backoff, notification dropdown, search dialog, create recipe dialog, profile menu, theme toggle, and tab state management. It's the largest component in the codebase.
- **Impact:** Extremely difficult to test, modify, or debug. High coupling makes changes risky.
- **Suggested fix:** Extract into focused sub-components: `NotificationBell`, `MobileDrawer`, `DesktopNav`, `MobileBottomNav`. Move notification polling into a custom hook.

**[CR-009]** `src/app/api/users/[username]/recipes/route.ts` missing pagination

- **File:** `src/app/api/users/[username]/recipes/route.ts:43-50`
- **Issue:** The endpoint fetches ALL recipes for a user with no `take`/`skip` parameters. A user with hundreds of recipes will return an unbounded response.
- **Impact:** Slow response times, excessive memory usage on both server and client for prolific users.
- **Suggested fix:** Add pagination parameters matching other endpoints:

```typescript
const limit = Math.min(
  100,
  Math.max(1, parseInt(request.nextUrl.searchParams.get('limit') || '50') || 50)
);
const offset = Math.max(0, parseInt(request.nextUrl.searchParams.get('offset') || '0') || 0);
// ... add take: limit, skip: offset to the query
```
