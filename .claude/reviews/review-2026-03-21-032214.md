## Code Review — 2026-03-21

### Summary

Several API routes with solid transactional logic but containing race conditions, missing validations, a potential DoS vector, and inconsistent error handling patterns across files.

### Findings

#### CRITICAL

**[CR-001]** Unhandled floating Promise in account deletion

- **File:** `src/app/api/users/profile/route.ts:83-88`
- **Issue:** `Promise.allSettled(...)` is called without `await` and without being assigned to a variable that's consumed. The `Promise.allSettled` return value is used with `.then()`, but the outer Promise itself floats. If the runtime terminates the request handler early (e.g., serverless cold shutdown), the `.then()` callback silently drops — losing the error log. More critically, the linter or strict Promise rules should flag this, but the real problem is that `failed` array logs the URLs, not the rejection reasons, making debugging impossible.
- **Impact:** Orphaned images silently accumulate with no actionable error information.
- **Suggested fix:**

```typescript
// Log rejection reasons, not just URLs
Promise.allSettled(imageUrls.map((url) => cleanupCloudinaryImage(url)))
  .then((results) => {
    const failures = results
      .map((r, i) => (r.status === 'rejected' ? { url: imageUrls[i], reason: r.reason } : null))
      .filter(Boolean);
    if (failures.length > 0)
      logServerError('Failed to cleanup images for deleted account', failures);
  })
  .catch(() => {}); // prevent unhandled rejection
```

**[CR-002]** `instruction.image` field in recipe creation schema accepts arbitrary URLs

- **File:** `src/app/api/recipes/route.ts:27`
- **Issue:** `instructionSchema` has `image: z.string().optional()` with no URL validation or Cloudinary URL check. The main `imageUrl` is validated against Cloudinary, but per-step instruction images are not. An attacker can inject arbitrary URLs (including `javascript:` URIs or tracking pixels) that will be stored and rendered.
- **Impact:** Stored XSS via `javascript:` URIs, SSRF if these URLs are fetched server-side, or tracking/phishing via external image URLs.
- **Suggested fix:**

```typescript
const instructionSchema = z
  .object({
    step: z.number().int().positive(),
    description: z.string().min(1).max(5000),
    image: z.string().url().optional(),
  })
  .strict();
// And validate each instruction image against Cloudinary in the POST handler
```

**[CR-003]** TOCTOU race in `deductPantryItems` — pantry read and deduction not locked

- **File:** `src/app/api/cooked-recipes/route.ts:175-178`
- **Issue:** The advisory lock is acquired at line 175, but `pantryItems` are passed into `deductPantryItems` as a pre-read array. The function then does `findMany`-style matching on this snapshot. However, `deductPantryItems` calls `tx.pantryItem.update` and `tx.pantryItem.delete` using `where: { id }` without `SELECT FOR UPDATE` on the pantry items themselves. If another transaction (e.g., pantry edit API) modifies the same pantry item concurrently (outside the advisory lock scope), the quantity could go negative.
- **Impact:** Pantry quantities can become negative or inconsistent if pantry items are modified concurrently via a different API endpoint that doesn't use the same advisory lock.
- **Suggested fix:** Either use `SELECT ... FOR UPDATE` on pantry items within the transaction, or ensure all pantry-modifying endpoints use the same advisory lock namespace.

#### HIGH

**[CR-004]** Recipe match endpoint is a DoS vector despite rate limiting

- **File:** `src/app/api/recipes/match/route.ts:89-93`
- **Issue:** The advisory lock serializes per-user, but the `statement_timeout` is 10 seconds and the outer transaction timeout is 15 seconds. With 30 requests per 15 minutes allowed, a single user can hold a database connection for up to 10 seconds per request. With multiple users hitting this endpoint simultaneously, each holds a DB connection from the pool for the full duration. The `jsonb_array_elements` lateral join with `LIKE ANY` on up to 50 patterns is expensive and not bounded by result set size at the DB planner level.
- **Impact:** Connection pool exhaustion under moderate concurrent load; database performance degradation.
- **Suggested fix:** Reduce `statement_timeout` to 3-5 seconds, add connection pool limits per endpoint, or move matching to a background job/queue.

**[CR-005]** `hasMore` calculation is unreliable

- **File:** `src/components/recipe/RecipeFeed.tsx:145`
- **Issue:** `setHasMore(data.hasMore ?? data.recipes.length === PAGE_SIZE)` — if the API returns exactly `PAGE_SIZE` recipes but there are no more, the fallback incorrectly sets `hasMore = true`, causing an extra empty fetch. The API does return `hasMore` based on the same logic (`recipes.length === limit`), so both sides have the same bug: if exactly `limit` recipes remain, `hasMore` is true, triggering one wasted request.
- **Impact:** Unnecessary API call on every feed that has a total count that's an exact multiple of PAGE_SIZE.
- **Suggested fix:** In `src/app/api/recipes/route.ts`, change:

```typescript
hasMore: offset + recipes.length < total,
```

**[CR-007]** `markAllAsRead` doesn't send `Content-Type` header

- **File:** `src/hooks/useNotificationPolling.ts:186-189`
- **Issue:** The POST to `/api/notifications` includes `X-Requested-With` but no `Content-Type`. If the `requireJsonContentType` middleware is applied to this route's POST handler, the request will be rejected. If it's not, this is inconsistent with other mutation endpoints.
- **Impact:** Either silent 415 errors or inconsistent CSRF protection depending on route configuration.
- **Suggested fix:** Verify whether the notifications POST route requires JSON content type. If it does, add the header. If it doesn't need a body, document why `requireJsonContentType` is skipped.

**[CR-008]** `UpdateUserProfileDTO` allows clearing `avatar` without Cloudinary cleanup

- **File:** `src/domain/services/IUserService.ts:5-11` and `src/app/api/users/profile/route.ts:35-38`
- **Issue:** The PUT handler validates that if `avatar` is provided, it must be a Cloudinary URL. But `updateProfileSchema` likely allows `avatar: null` (to clear the field). The cleanup logic at line 49-52 only triggers if `currentUser.avatar !== updatedUser.avatar`. If the user sets `avatar: null`, the old Cloudinary image is cleaned up — but there's no validation that the user actually owns that Cloudinary image. Any authenticated user could trigger cleanup of an arbitrary Cloudinary URL if they previously set it as their avatar.
- **Impact:** Minimal direct impact since cleanup only targets the user's own previous avatar, but the pattern of trusting stored URLs for cleanup operations is fragile.
- **Suggested fix:** This is acceptable as-is since the avatar was previously validated on upload. Document the assumption.

**[CR-009]** Duplicated circuit breaker logic in notification polling

- **File:** `src/hooks/useNotificationPolling.ts:113-127` and `src/hooks/useNotificationPolling.ts:133-146`
- **Issue:** The failure tracking + circuit breaker trip logic is copy-pasted verbatim in both the `!response.ok` branch and the `catch` branch. This is a maintenance hazard — any change to the breaker logic must be applied in two places.
- **Impact:** Future bug if one copy is updated and the other is missed.
- **Suggested fix:** Extract to a helper:

```typescript
const recordFailure = () => {
  const now = Date.now();
  failureTimestampsRef.current.push(now);
  if (failureTimestampsRef.current.length > 20) {
    failureTimestampsRef.current = failureTimestampsRef.current.slice(-20);
  }
  const tenMinAgo = now - 10 * 60 * 1000;
  failureTimestampsRef.current = failureTimestampsRef.current.filter((t) => t > tenMinAgo);
  lastFailureTimeRef.current = now;
  if (failureTimestampsRef.current.length >= 10) {
    breakerTripCountRef.current = Math.min(breakerTripCountRef.current + 1, 10);
    pollingStoppedRef.current = true;
    if (!isMountedRef.current) return;
    setIsPollingPaused(true);
    breakerTrippedAtRef.current = Date.now();
  }
};
```

**[CR-010]** `createRecipeSchema` validates `imageUrl` with `z.string().min(1)` — no URL format validation

- **File:** `src/app/api/recipes/route.ts:33`
- **Issue:** While `validateCloudinaryUrl` is called later, the Zod schema itself doesn't enforce URL format. If `validateCloudinaryUrl` has a bug or is bypassed, any non-empty string is accepted as an image URL.
- **Impact:** Defense-in-depth gap; malformed URLs stored in database.
- **Suggested fix:**

```typescript
imageUrl: z.string().min(1).url(),
```

**[CR-011]** `isFetchingRef` not reset on abort

- **File:** `src/hooks/useNotificationPolling.ts:151-154`
- **Issue:** In the `finally` block: `if (!controller.signal.aborted) { isFetchingRef.current = false; }`. If the fetch is aborted, `isFetchingRef` stays `true` permanently until the next successful non-aborted fetch. But the next fetch starts by aborting the previous one (line 67), which means the previous fetch's `finally` won't reset the flag. The new fetch then sets `isFetchingRef.current = true` at line 72, and if it completes normally, the flag is reset. However, if two rapid aborts happen, there's a window where `isFetchingRef` is stuck `true`.
- **Impact:** Polling could stall until a successful fetch completes, missing notifications.
- **Suggested fix:** Reset `isFetchingRef` unconditionally in `finally`, or reset it at the start of `fetchNotifications` before setting it to `true`.

**[CR-013]** `recipesLengthRef` shadow state duplicates `recipes.length`

- **File:** `src/components/recipe/RecipeFeed.tsx:56`
- **Issue:** `recipesLengthRef` manually tracks `recipes.length` and must be updated in every place `setRecipes` is called (lines 136, 139, 144, 207). Missing an update site would cause offset calculation bugs in `loadRecipes`. This is fragile — if someone adds a new `setRecipes` call, they must remember to also update the ref.
- **Impact:** Potential pagination bugs if `recipesLengthRef` diverges from actual `recipes` length.
- **Suggested fix:** Use a ref that reads from the state setter's callback form, or compute offset from a stable source. At minimum, add a comment on the ref declaration listing all update sites.
