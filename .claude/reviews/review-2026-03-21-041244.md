### Findings

#### CRITICAL

**[CR-001]** Fire-and-forget async IIFE in DELETE handler can silently lose errors and run after response is sent

- **File:** `src/app/api/users/profile/route.ts:96-107`
- **Issue:** The account deletion endpoint fires off an async IIFE for Cloudinary cleanup that runs unbounded after the response is returned. In serverless/edge environments (Vercel), the runtime may kill the function after the response is sent, silently dropping cleanup work. The `.catch()` on the IIFE only catches the outer wrapper — individual batch failures inside `Promise.allSettled` are logged but the entire cleanup can be interrupted mid-batch.
- **Impact:** Orphaned Cloudinary images accumulate with no indication of failure. In serverless deployments, cleanup may never complete.
- **Suggested fix:** Use `waitUntil` from Next.js to extend the function lifetime, or perform cleanup synchronously before returning the response:

```ts
import { after } from 'next/server';
// ...
after(async () => {
  for (const batch of batches) {
    const results = await Promise.allSettled(batch.map((url) => cleanupCloudinaryImage(url)));
    // ... logging
  }
});
```

**[CR-002]** `SET LOCAL statement_timeout` has no effect outside a transaction in the match endpoint's Phase 3

- **File:** `src/app/api/recipes/match/route.ts:101`
- **Issue:** `SET LOCAL statement_timeout = '5s'` is set inside the Phase 1 transaction, but Phase 3 (`prisma.post.findMany` at line ~178) runs outside any transaction with no timeout. A slow query on a large `Post` table with `id: { in: matchedIds }` (up to 60 IDs) has no timeout protection.
- **Impact:** Under load or with a degraded database, Phase 3 can hang indefinitely, exhausting the connection pool.
- **Suggested fix:** Wrap Phase 3 in a transaction with its own timeout, or use `prisma.$queryRaw` with an explicit timeout:

```ts
const recipes = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SET LOCAL statement_timeout = '5s'`;
  return tx.post.findMany({ where: { id: { in: matchedIds }, user: { isPrivate: false } }, ... });
}, { timeout: 6000 });
```

**[CR-003]** DELETE cooked-recipe restores pantry without verifying the recipe wasn't already restored

- **File:** `src/app/api/cooked-recipes/route.ts:250-304`
- **Issue:** The pantry restoration logic in DELETE uses an advisory lock per-user, but if the transaction fails _after_ pantry items are restored but _before_ the `cookedRecipe.delete` succeeds (e.g., a transient DB error), a retry would restore pantry items a second time. The P2025 catch at line ~330 handles the case where delete races, but any error between restoration and deletion leaves the DB in an inconsistent state where items are restored but the cooked recipe still exists, allowing another DELETE to restore again.
- **Impact:** Pantry quantities can be inflated beyond correct values through retries on transient failures.
- **Suggested fix:** Move `cookedRecipe.delete` to execute _before_ pantry restoration. If the delete succeeds, restoration is safe. If the delete throws P2025, skip restoration entirely:

```ts
// Delete first — if this throws P2025, the entire transaction rolls back
await tx.cookedRecipe.delete({ where: { id: cookedRecipeId } });
// Now restore pantry (safe because delete succeeded and advisory lock prevents concurrency)
for (const d of validDeducted) { ... }
```

**[CR-004]** No `statement_timeout` on DELETE account transaction — cascade delete can lock the database

- **File:** `src/app/api/users/profile/route.ts:91-116`
- **Issue:** The DELETE handler sets `SET LOCAL statement_timeout = '10s'` but this is inside a transaction that performs `findMany` on posts, comments, plus `user.delete` which cascade-deletes across many tables (posts, comments, likes, ratings, follows, notifications, pantry). For a prolific user, this cascade can far exceed 10 seconds. The `statement_timeout` applies per-statement, not per-transaction, so each individual CASCADE step gets 10s, meaning the total transaction time is unbounded.
- **Impact:** A user with thousands of posts/comments can lock rows across multiple tables for minutes, causing timeouts and connection pool exhaustion for other users.
- **Suggested fix:** Add a transaction-level timeout and consider batched deletion for prolific users:

```ts
const imageUrls = await prisma.$transaction(
  async (tx) => {
    await tx.$executeRaw`SET LOCAL statement_timeout = '10s'`;
    await tx.$executeRaw`SET LOCAL idle_in_transaction_session_timeout = '30s'`;
    // ... existing logic
  },
  { timeout: 35000 }
);
```

**[CR-007]** Ingredient `amount` type mismatch between schema and runtime validation

- **File:** `src/app/api/recipes/match/route.ts:140`
- **Issue:** The `Ingredient` interface (line 18) declares `amount: number`, but the runtime validation (line 140) checks `typeof i?.amount === 'string' || typeof i?.amount === 'number'`. The same inconsistency exists in `cooked-recipes/route.ts:195`. The `parseAmount` function in the cooked-recipes handler expects strings, while the match endpoint's `Ingredient` type expects numbers. If ingredients are stored as strings (from the creation schema which uses `z.string().max(50)`), the match endpoint will accept them but TypeScript will treat them as numbers, causing silent bugs in comparisons.
- **Impact:** Ingredient matching and deduction calculations could silently produce wrong results when `amount` is a string like `"1/2"` that gets compared numerically.
- **Suggested fix:** Align the `Ingredient` interface with reality — `amount` should be `string | number`, and all arithmetic should go through `parseAmount`:

```ts
interface Ingredient {
  name: string;
  amount: string | number;
  unit: string;
}
```
