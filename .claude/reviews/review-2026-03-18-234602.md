## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes, middleware, and client components.

### Findings

#### CRITICAL

**[CR-001]** Logout endpoint Origin check is bypassable — no Origin header means no check

- **File:** `src/app/api/auth/logout/route.ts:12-15`
- **Issue:** The Origin check only runs `if (origin && origin !== appOrigin)`. When no `Origin` header is present (e.g., server-side requests, some browser extensions, or non-browser HTTP clients), the check is skipped entirely. Combined with the `content-type` check, this is weak CSRF protection for a cookie-clearing endpoint.
- **Impact:** An attacker could force-logout users via cross-origin requests that omit the Origin header.
- **Suggested fix:** Require Origin header to be present for POST requests, or rely solely on the middleware CSRF checks (which already cover this route):

```ts
if (!origin || origin !== appOrigin) {
  return NextResponse.json({ error: 'Invalid origin' }, { status: 403 });
}
```

**[CR-002]** Recipe match endpoint loads full ingredient JSON for up to 200 recipes into memory

- **File:** `src/app/api/recipes/match/route.ts:100-110`
- **Issue:** The raw SQL query `SELECT DISTINCT p.id, p.ingredients FROM "Post"` loads the entire `ingredients` JSONB column for up to 200 rows. For recipes with large ingredient lists or long descriptions, this can consume significant server memory per request. There is no per-user rate limiting on this GET endpoint.
- **Impact:** Memory exhaustion under concurrent load; potential OOM on constrained serverless instances.
- **Suggested fix:** Limit the `ingredients` column size at write time, or paginate the matching in smaller batches. Consider caching match results per-user.

**[CR-003]** `cooked-recipes` POST uses `pg_advisory_xact_lock(hashtext(...))` which can collide across users

- **File:** `src/app/api/cooked-recipes/route.ts:116`
- **Issue:** `hashtext()` returns a 32-bit integer. With enough users, two different `userId` strings will hash to the same value, causing unrelated users' cook operations to serialize against each other. This creates unnecessary lock contention and potential deadlocks if combined with other locks.
- **Impact:** Performance degradation under load; false serialization between unrelated users.
- **Suggested fix:** Use a two-key advisory lock with the user's actual ID to avoid collisions:

```sql
SELECT pg_advisory_xact_lock(hashtext('cooked-recipe'), hashtext(${payload.userId}))
```

#### HIGH

**[CR-004]** `RecipeFeed` infinite scroll has no deduplication guard on concurrent IntersectionObserver triggers

- **File:** `src/components/recipe/RecipeFeed.tsx:100-110`
- **Issue:** The `loadingRef` guard prevents concurrent calls, but the `lastLoadTimeRef` throttle (500ms) combined with IntersectionObserver `rootMargin: '500px'` can still produce duplicate recipe loads when scrolling quickly. The deduplication in `setRecipes` uses a Set, but this runs in a callback that may close over stale `prev` values.
- **Impact:** Duplicate recipe cards rendered in the feed; wasted API calls.
- **Suggested fix:** Use a `pageRef` based cursor that is atomically incremented before the fetch, not after.

**[CR-005]** Admin user deletion race condition — admin count check uses raw SQL `FOR UPDATE` but doesn't lock the target user row

- **File:** `src/app/api/admin/users/[id]/route.ts:37-47`
- **Issue:** The transaction reads `userToDelete.role`, then counts admins with `FOR UPDATE`. But between reading the user's role and the count query, another transaction could promote this user to ADMIN. The `FOR UPDATE` on the count query locks existing admin rows but doesn't prevent a concurrent `UPDATE "User" SET role='ADMIN'` on the target user.
- **Impact:** Could allow deletion of the last admin if two concurrent requests race: one demotes an admin while another deletes them.
- **Suggested fix:** Lock the target user row with `SELECT ... FOR UPDATE` before checking their role:

```sql
const userToDelete = await tx.$queryRaw`SELECT role FROM "User" WHERE id = ${id} FOR UPDATE`;
```

**[CR-006]** `useNotificationPolling` circuit breaker resets silently — user never knows polling stopped

- **File:** `src/hooks/useNotificationPolling.ts:105-108`
- **Issue:** When 10+ failures trip the circuit breaker, polling stops for 5 minutes. The user sees no indication that notifications have stopped updating. After 5 minutes, the breaker auto-resets and resumes, but stale notifications may have been missed.
- **Impact:** Users miss notifications during outage windows without any visual feedback.
- **Suggested fix:** Expose a `circuitBreakerTripped` state so the UI can show a warning banner.

**[CR-007]** Comment image URLs are not validated with `validateCloudinaryUrl` on the GET path

- **File:** `src/app/api/recipes/[id]/comments/route.ts:27-47`
- **Issue:** Comments fetched via GET include `imageUrl` fields that were validated on write, but if the database was seeded or migrated with invalid URLs, they pass through to the client. The `RecipeCard` component only checks `isCloudinaryUrl` for recipe images, but `CommentsSection` renders `comment.imageUrl` directly without validation.
- **Impact:** Stored XSS or SSRF if an attacker manages to inject a non-Cloudinary URL into the comments table through a migration or direct DB access.
- **Suggested fix:** Add `isCloudinaryUrl` check in `CommentsSection.tsx` before rendering comment images, similar to `RecipeCard.tsx`.

#### MEDIUM

**[CR-008]** `AuthContext` logout retry logic navigates away on second failure, losing React state

- **File:** `src/contexts/AuthContext.tsx:97-105`
- **Issue:** On the second failed logout attempt, the code does `window.location.href = '/auth'` which is a hard navigation, destroying all React state including the QueryClient cache. This is inconsistent with the optimistic `setUser(null)` at the top of the function.
- **Impact:** Inconsistent user experience — state is cleared optimistically but then a hard navigation occurs.
- **Suggested fix:** Either remove the hard navigation (the cookie will expire naturally) or make it consistent by not clearing state optimistically.

**[CR-009]** `RecipeFeed` does not reset `pageRef` when filters change — potential offset miscalculation

- **File:** `src/components/recipe/RecipeFeed.tsx:110-115`
- **Issue:** When `loadRecipes(true)` is called for a filter change, `pageRef.current` is set to `1` after the fetch succeeds. But if the fetch fails (e.g., network error), `pageRef` stays at its previous value. The next `loadRecipes(false)` call will use the wrong offset.
- **Impact:** Missing or duplicated recipes after a failed filter change.
- **Suggested fix:** Reset `pageRef.current = 0` at the start of `loadRecipes(true)`, before the fetch.

**[CR-010]** `about/page.tsx` uses `motion.create(Box)` and `motion.create(Paper)` at module scope — SSR mismatch risk

- **File:** `src/app/about/page.tsx:24-25`
- **Issue:** `motion.create()` at module scope works, but the component has `'use client'` and uses `BRANDING` which is a const object. The `features` array is also at module scope. This is fine for now, but if `BRANDING` ever becomes dynamic (e.g., i18n), the module-scope initialization will break.
- **Impact:** Low — currently functional, but fragile to future changes.
- **Suggested fix:** No immediate action needed, but document the constraint.

**[CR-011]** `PersistentSearchBar` fires live search on every keystroke with 300ms debounce — no minimum query length enforced in the UI

- **File:** `src/components/search/PersistentSearchBar.tsx:118-120`
- **Issue:** The debounce effect correctly skips queries < 2 chars, but the `onQueryChange` callback fires on every keystroke without any debounce. If a parent component does expensive work in `onQueryChange`, this will cause performance issues.
- **Impact:** Unnecessary re-renders in parent components.
- **Suggested fix:** Document that `onQueryChange` is called on every keystroke, or debounce it internally.

**[CR-012]** `EditProfileModal` client-side magic byte validation reads only first 12 bytes but WebP requires bytes 8-11

- **File:** `src/components/profile/EditProfileModal.tsx:77-84`
- **Issue:** The `file.slice(0, 12)` call reads exactly 12 bytes. WebP validation checks bytes at indices 8-11 (WEBP), which are the last 4 bytes of the slice. If `FileReader.readAsArrayBuffer` returns fewer than 12 bytes for a very small file, the WebP check will fail silently (accessing undefined array indices returns `undefined`, which !== the expected byte values).
- **Impact:** Very small WebP files (< 12 bytes) would be rejected with a misleading error. Practically unlikely but the validation is fragile.
- **Suggested fix:** Add `if (bytes.length < 12)` guard before the WebP check, which is already done server-side in `image-validation.ts`.

**[CR-013]** Middleware rate limit map has no TTL-based automatic cleanup — relies on probabilistic eviction

- **File:** `src/middleware.ts:66-69`
- **Issue:** The `rateLimitMap` cleanup only runs on 5% of requests (probabilistic) and when the map exceeds 500 entries. Under low traffic, expired entries accumulate indefinitely. Under burst traffic, the 500-entry hard cap may evict valid rate limit entries, effectively resetting rate limits for active abusers.
- **Impact:** Memory leak under low traffic; rate limit bypass under burst traffic.
- **Suggested fix:** Use a `setInterval` for periodic cleanup, or switch to a proper LRU/TTL cache like `lru-cache`.

#### LOW

**[CR-014]** Unused import `email` destructured but intentionally discarded in multiple search endpoints

- **File:** `src/app/api/search/route.ts:31`, `src/app/api/users/search/route.ts:16`
- **Issue:** `({ email, ...rest }) => rest` pattern works but the `email` variable is unused. ESLint `no-unused-vars` should catch this with `_email` convention.
- **Impact:** Code clarity — readers must check whether email stripping is intentional.
- **Suggested fix:** Rename to `({ email: _email, ...rest }) => rest` or add an ESLint ignore comment.

**[CR-015]** `RecipeCard` component renders non-Cloudinary image URLs as `/chef-logo.png` fallback — silent data quality issue

- **File:** `src/components/recipe/RecipeCard.tsx:95-96`
- **Issue:** `isCloudinaryUrl(recipe.imageUrl) ? recipe.imageUrl : '/chef-logo.png'` silently swallows non-Cloudinary URLs. If image upload breaks and starts storing different URLs, all recipe cards show the fallback with no logging or error reporting.
- **Impact:** Silent data quality degradation — broken images are invisible to monitoring.
- **Suggested fix:** Log a warning to Sentry when a non-Cloudinary URL is encountered:

```ts
if (!isCloudinaryUrl(recipe.imageUrl)) {
  console.warn(`Non-Cloudinary image URL: ${recipe.imageUrl}`);
}
```

**[CR-016]** `settings/page.tsx` test file imports `fireEvent` but doesn't use it

- **File:** `src/app/settings/__tests__/page.test.tsx:1`
- **Issue:** `fireEvent` is imported from `@testing-library/react` but never used in the test file — only `userEvent` is used.
- **Impact:** Dead import; minor code hygiene.
- **Suggested fix:** Remove `fireEvent` from the import.
