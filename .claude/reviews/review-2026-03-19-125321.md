## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing app with generally solid architecture (clean DI, proper auth, good test coverage). However, several security gaps, race conditions, and data integrity issues exist across the API layer and client components.

### Findings

#### CRITICAL

**[CR-001]** ReDoS vulnerability in ingredient normalization

- **File:** `src/lib/utils/ingredients.ts:72-85`
- **Issue:** The plural-stripping logic chains multiple `endsWith` checks and regex replacements, but `normalizeIngredientName` is called in hot loops (recipe matching with up to 50,000 comparisons). More critically, user-controlled ingredient names from pantry items are passed directly to `normalizeIngredientName` without length limits at this layer — a crafted long string could cause excessive processing.
- **Impact:** CPU exhaustion on the recipe match endpoint, potential DoS.
- **Suggested fix:** Add an early-return length guard at the top of `normalizeIngredientName`:

```ts
export function normalizeIngredientName(name: string): string {
  if (name.length > 200) return name.slice(0, 200).toLowerCase().trim();
  // ... rest of function
}
```

**[CR-002]** Admin user delete race window leaks new content between query and cascade

- **File:** `src/app/api/admin/users/[id]/route.ts:49-56`
- **Issue:** The comment at line 47 acknowledges a race window: posts/comments created between the image-collection queries and the `user.delete` cascade will have orphaned images. However, the code collects `userPosts` and `userComments` **before** `user.delete`, meaning any content created in that window is cascade-deleted but its Cloudinary images are never collected for cleanup. The advisory lock only serializes admin deletes, not user content creation.
- **Impact:** Permanent orphaned Cloudinary images that even the cleanup script may not catch (it scans folders, not individual URLs).
- **Suggested fix:** Move image collection to **after** the delete by querying the deleted data, or use `ON DELETE` triggers at the DB level to log image URLs to a cleanup queue table.

**[CR-003]** `cooked-recipes` POST endpoint allows unbounded JSON body parsing before auth check

- **File:** `src/app/api/cooked-recipes/route.ts:113-125`
- **Issue:** The `requireJsonContentType` and `requireAuth` checks happen before body parsing, which is correct. However, the `cookedRecipeSchema` validation happens after `request.json()`, which will parse the entire body into memory. A malicious user could send a very large JSON body. The `z.string().max(MAX_NOTES_LENGTH)` on `notes` helps, but the `force` boolean and other fields don't prevent a payload with thousands of extra keys.
- **Impact:** Memory exhaustion if an attacker sends a multi-MB JSON body with extra fields.
- **Suggested fix:** Add a request body size check in middleware for API routes, or use `z.strict()` to reject unknown keys.

#### HIGH

**[CR-004]** `RecipeFeed` infinite scroll has no deduplication guard on rapid intersection observer triggers

- **File:** `src/components/recipe/RecipeFeed.tsx:137-170`
- **Issue:** The `loadingRef` guard prevents concurrent fetches, but the `lastLoadTimeRef` throttle of 500ms combined with the IntersectionObserver `rootMargin: '500px'` means rapid scroll can queue multiple fetches in quick succession. The `abortControllerRef` cancels the previous request, but if two requests complete before the abort fires (e.g., fast responses), `setRecipes` could append duplicates despite the `existingIds` check — because the check runs against the state at the time of the **first** update, not the second.
- **Impact:** Duplicate recipe cards in the feed, React key warnings, incorrect UI state.
- **Suggested fix:** Use a functional `setRecipes` update with the `existingIds` check inside the callback (which you already do), but also check `thisRequestId !== requestIdRef.current` **before** state updates (which you also do). The real issue is the `abortControllerRef.current === controller` check in `finally` — if a second request starts and replaces the controller before the first completes, the first request's `finally` block won't clear loading state, leaving it stuck. Add `loadingRef.current = false` unconditionally in the `finally` or track per-request loading.

**[CR-005]** Notification polling `fetchNotifications` doesn't guard against unmounted state updates after abort

- **File:** `src/hooks/useNotificationPolling.ts:73-126`
- **Issue:** When `AbortError` is caught on line 116, the function returns early — but for non-abort errors (line 118-127), `setIsPollingPaused(true)` may be called after the component unmounts. The `isMountedRef` check on line 82 guards the success path but not all error paths.
- **Impact:** React "can't perform state update on unmounted component" warning; potential memory leak.
- **Suggested fix:** Add `if (!isMountedRef.current) return;` before `setIsPollingPaused(true)` in the error handler at line 121.

**[CR-006]** `recipes/match/route.ts` SQL injection via `Prisma.join` with user-controlled pantry names

- **File:** `src/app/api/recipes/match/route.ts:95-100`
- **Issue:** Pantry item names are passed through `normalizeIngredientName` then into `Prisma.sql` tagged template literals. While `Prisma.sql` parameterizes values correctly, the `Prisma.join` on line 100 creates a dynamic SQL fragment from `nameConditions`. Each condition uses `Prisma.sql` with a parameterized value, so this is actually safe. However, the comment "SAFETY: Prisma.sql tagged templates parameterize values" is misleading — the safety comes from each individual `Prisma.sql` call, not from `Prisma.join`. If anyone refactors this to use string interpolation instead of `Prisma.sql`, it becomes injectable.
- **Impact:** Currently safe, but fragile. Reclassifying as HIGH for maintainability risk.
- **Suggested fix:** Add a unit test that verifies pantry names with SQL metacharacters (`'; DROP TABLE "Post"; --`) don't cause issues, to prevent regressions.

**[CR-007]** `EditProfileModal` avatar upload doesn't validate magic bytes on server before storing URL

- **File:** `src/components/profile/EditProfileModal.tsx:86-106`
- **Issue:** Client-side magic byte validation is performed (lines 86-106), but if the client is bypassed (e.g., curl), the `/api/upload/avatar` route does validate magic bytes server-side via `validateImageMagicBytes`. This is correctly implemented. However, the client-side validation reads only 12 bytes (`file.slice(0, 12)`) and checks WebP requires all 12 bytes to be present — but `bytes.length < 12` check on line 93 would reject valid small image headers. A JPEG header is only 3 bytes; the 12-byte check is overly strict for JPEG/PNG/GIF.
- **Impact:** Valid small image files (unlikely but possible) could be falsely rejected on the client side. Server-side validation would still accept them, creating an inconsistent UX.
- **Suggested fix:** Change the minimum check to `bytes.length < 4` (minimum needed for JPEG/PNG/GIF detection), and only check WebP if `bytes.length >= 12`.

**[CR-008]** `AdminService.getStats` cache is never invalidated by organic activity

- **File:** `src/infrastructure/services/AdminService.ts:21-23`
- **Issue:** The comment on line 21 acknowledges this: "Organic activity (new user signups, recipe creation, likes, comments) will not appear in stats until the TTL expires." The TTL is 30 seconds. However, there's no cache invalidation on **admin mutations** either — `deleteComment` calls `statsCache = null` but `getAllUsers`, `getAllRecipes`, and `getAllComments` don't invalidate. This means after an admin views stats, then deletes a recipe, the next stats call within 30s will show stale data (the deleted recipe still counted).
- **Impact:** Admin dashboard shows stale statistics. Already documented as a known limitation but the 30s TTL makes it tolerable.
- **Suggested fix:** No action needed given the 30s TTL, but consider documenting this in the admin UI.

#### MEDIUM

**[CR-009]** `PersistentSearchBar` live search creates AbortController outside setTimeout, causing premature abort

- **File:** `src/components/search/PersistentSearchBar.tsx:118-148`
- **Issue:** The comment on line 117 says "the AbortController is intentionally created OUTSIDE the setTimeout so the cleanup function can abort it immediately." This is correct for cleanup, but it means that if the user types "a", then "ab" within 300ms, the first effect's cleanup aborts the controller before the setTimeout even fires. This is fine. However, `searchAbortRef.current?.abort()` on line 126 aborts the **previous** request's controller, but the new controller (`const controller = new AbortController()` on line 123) is created before the timeout — so if the cleanup runs before the fetch starts, the new controller is aborted by the next keystroke's cleanup, not by `searchAbortRef`. This is actually correct because the cleanup on line 143 calls `controller.abort()` which is the local variable.
- **Impact:** No bug — the logic is correct but unnecessarily complex. The dual abort mechanism (ref + cleanup) is confusing.
- **Suggested fix:** Simplify by creating the AbortController inside the setTimeout callback and only using the cleanup function for cancellation.

**[CR-010]** `Footer` contact form mailto link length check uses hardcoded 1500 character limit

- **File:** `src/components/Footer.tsx:57`
- **Issue:** The `mailtoLink.length > 1500` check is a reasonable guard, but different browsers/OS have different mailto URL length limits (IE was 2083, modern browsers are higher). The limit should be documented or configurable.
- **Impact:** Users with legitimate long messages may be blocked unnecessarily, or the limit may be too high for some environments.
- **Suggested fix:** Add a comment explaining the 1500-char choice, or use a more conservative 1000-char limit.

**[CR-011]** `RecipeCard` image fallback creates infinite loop potential

- **File:** `src/components/recipe/RecipeCard.tsx:79-85`
- **Issue:** The `onError` handler sets `imgFallbackUsed` to true on first error, then falls back to `/chef-logo.png`. On second error, it sets `imgHidden` to true. But if `/chef-logo.png` itself doesn't exist (e.g., in a test environment or if the public folder is misconfigured), the component will render the fallback icon. This is fine, but the state transition `imgFallbackUsed -> imgHidden` causes two re-renders for a missing image.
- **Impact:** Minor performance issue; two unnecessary re-renders per broken image.
- **Suggested fix:** Check `isCloudinaryUrl(recipe.imageUrl)` first; if false, go directly to `imgHidden` without trying the fallback.

**[CR-012]** `useNotificationPolling` exponential backoff cooldown can grow unbounded

- **File:** `src/hooks/useNotificationPolling.ts:149`
- **Issue:** `breakerTripCountRef.current` is capped at 10 on line 102, but the cooldown formula `5 * 60 * 1000 * Math.pow(2, breakerTripCountRef.current - 1)` with tripCount=10 yields `5 * 60000 * 512 = 153,600,000ms` (~42 hours). The cap at 30 minutes on line 150 handles this, but if `breakerTripCountRef` weren't capped, `Math.pow(2, n)` would overflow to Infinity. The cap at 10 is correct but should be documented.
- **Impact:** No bug due to existing caps, but fragile if caps are removed during refactoring.
- **Suggested fix:** Add a comment explaining the relationship between `breakerTripCountRef` cap and cooldown cap.

**[CR-013]** `pantry/route.ts` POST doesn't sanitize `name` for HTML before `striptags`

- **File:** `src/app/api/pantry/route.ts:92`
- **Issue:** The `name` field is sanitized with `striptags(name.trim())` before being stored, which strips HTML tags. However, `striptags` doesn't handle HTML entities like `&lt;script&gt;`. If the name contains encoded HTML entities, they would be stored as-is and could be decoded by a client-side renderer that uses `dangerouslySetInnerHTML`.
- **Impact:** Low — React's JSX auto-escaping prevents XSS in normal rendering. Only relevant if raw HTML rendering is ever used.
- **Suggested fix:** No immediate action needed; the defense-in-depth comment in `RecipeService.ts` correctly notes React's auto-escaping is the primary defense.

**[CR-014]** `search/route.ts` strips email but still includes `role` and `isVerified` in public search results

- **File:** `src/app/api/search/route.ts:30-32`
- **Issue:** The search endpoint strips `email` from user results (defense-in-depth), but the `UserRepository.search` method still returns `role`, `isVerified`, `isPrivate`, `createdAt`, and `updatedAt`. These are leaked to unauthenticated users in public search results.
- **Impact:** Information disclosure — attackers can enumerate admin users via the public search endpoint by checking the `role` field.
- **Suggested fix:** Strip `role`, `isVerified`, and other internal fields from public search results:

```ts
const users = (await userService.searchUsers(query.trim(), limit, offset)).map(
  ({ email: _email, role: _role, isVerified: _isVerified, ...rest }) => rest
);
```

#### LOW

**[CR-015]** `about/page.tsx` animation delay cap `Math.min(0.1 * index, 0.5)` limits to 5 cards

- **File:** `src/app/about/page.tsx:149`
- **Issue:** With 6 feature cards, the last card gets delay `0.5` (same as the 5th card at `Math.min(0.5, 0.5)`). The animation stagger effect is lost for the 6th card.
- **Impact:** Minor visual issue — last card animates simultaneously with the 5th.
- **Suggested fix:** Use `Math.min(0.1 * index, 0.6)` or remove the cap entirely since 6 cards only reaches 0.5s.

**[CR-016]** `RecipeFeed` `MAX_PAGES` constant is 25 but message says "first 300 recipes"

- **File:** `src/components/recipe/RecipeFeed.tsx:42,384`
- **Issue:** `MAX_PAGES = 25` with 12 recipes per page = 300 recipes. The message on line 384 uses template literal `${MAX_PAGES * 12}` which correctly shows 300. But if `limit` changes from 12, the message would be wrong since `MAX_PAGES * 12` is hardcoded.
- **Impact:** Minor maintainability issue.
- **Suggested fix:** Extract `PAGE_SIZE = 12` as a constant and use `MAX_PAGES * PAGE_SIZE`.

**[CR-017]** `CommentsSection` image preview object URL not revoked on successful submit

- **File:** `src/components/recipe/CommentsSection.tsx:91-94`
- **Issue:** After successful comment submission (line 91), `URL.revokeObjectURL(imagePreview)` is called before clearing state. This is correct. However, the cleanup effect on line 64 (`return () => { if (imagePreview) URL.revokeObjectURL(imagePreview); }`) may also try to revoke the same URL if the component re-renders before the state update propagates.
- **Impact:** Double `revokeObjectURL` call — harmless (no-op on already-revoked URLs) but unnecessary.
- **Suggested fix:** No action needed; double revoke is safe.

**[CR-018]** `middleware.ts` rate limit map cleanup uses probabilistic approach that may miss entries

- **File:** `src/middleware.ts:71-73`
- **Issue:** The 5% probabilistic cleanup (`Math.random() < 0.05`) means under low traffic, expired entries may persist for many requests. The hard cap at 500 entries with eviction handles the worst case.
- **Impact:** Minor memory overhead under low traffic; mitigated by the hard cap.
- **Suggested fix:** Acceptable as-is for the current scale. Document the trade-off.
