## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured with good security patterns (httpOnly cookies, CSRF protection, advisory locks). Several real bugs and security gaps found across API routes, client components, and data handling.

### Findings

#### CRITICAL

**[CR-001]** Race condition in cooked-recipe DELETE: rating deleted without checking if it came from a cooked recipe

- **File:** `src/app/api/cooked-recipes/route.ts:233-242`
- **Issue:** When deleting a cooked recipe, the associated `Rating` is unconditionally deleted via `deleteMany({ userId, postId })`. If the user also left a rating via a comment (separate from the cooked recipe), that rating is destroyed too. The rating and cookedRecipe are independent entities — deleting one should not blindly wipe the other.
- **Impact:** Users lose their comment-based ratings when un-cooking a recipe. Average ratings become inaccurate.
- **Suggested fix:** Only delete the rating if no other mechanism (comment) references it, or track which entity created the rating.

**[CR-002]** `deductPantryItems` applies updates and deletions concurrently but deletions sequentially — inconsistent atomicity

- **File:** `src/app/api/cooked-recipes/route.ts:79-93`
- **Issue:** `Promise.all` is used for updates (line 85), but if any single update fails mid-batch, some pantry items are already modified while others are not. The transaction will roll back, but `Promise.all` short-circuits on the first rejection, leaving unresolved promises that may still execute against the transaction context.
- **Impact:** In edge cases, partial pantry deductions could appear transiently or cause confusing error states.
- **Suggested fix:** Use `Promise.allSettled` or sequential updates within the transaction to ensure predictable behavior on partial failure.

**[CR-003]** `search` API route leaks user `id` field in public search results

- **File:** `src/app/api/search/route.ts:32-34`
- **Issue:** The search endpoint strips `email` from user results via `UserRepository.search`, but still returns the internal `id` field. The user search at `/api/users/search/route.ts:22` uses destructuring to strip `email` but also leaks `id`. Internal UUIDs in public search results enable user enumeration.
- **Impact:** Attackers can enumerate user IDs for targeted attacks against user-specific endpoints.
- **Suggested fix:** Explicitly select only public fields: `username`, `fullName`, `avatar`, `bio`.

**[CR-004]** `cleanupCloudinaryImage` regex fails for images in nested folders

- **File:** `src/lib/utils/cloudinary-cleanup.ts:9`
- **Issue:** The regex `/\/upload\/(?:[^/]+\/)*([^/.]+)/` extracts only the filename as `publicId`, but Cloudinary's `destroy` API requires the full public ID including folder path (e.g., `recipes/abc123`, not just `abc123`). Images in folders like `recipes/` or `avatars/` will never be deleted.
- **Impact:** All Cloudinary cleanup is silently failing. Orphaned images accumulate indefinitely, increasing storage costs.
- **Suggested fix:**

```ts
const match = imageUrl.match(/\/upload\/(?:v\d+\/)?(.+)\.[^.]+$/);
if (match) await deleteFromCloudinary(match[1]);
```

#### HIGH

**[CR-005]** Admin user delete exposes user emails in `getAllUsers` response despite masking

- **File:** `src/infrastructure/services/AdminService.ts:67`
- **Issue:** `maskEmail` shows first 2 characters of the local part and the full domain. For short emails like `ab@company.com`, this reveals the entire email. For corporate domains, the domain alone can identify the user.
- **Impact:** Partial email disclosure to admin users viewing the admin panel. If an admin account is compromised, this aids in targeted attacks.
- **Suggested fix:** Only show first character + asterisks, or mask the domain too: `a****@c****.com`.

**[CR-006]** `POST /api/notifications` (mark all as read) has no Content-Type requirement but uses `X-Requested-With` header for CSRF

- **File:** `src/app/api/notifications/route.ts:44-56`
- **Issue:** The POST endpoint for marking notifications as read doesn't call `requireJsonContentType` and accepts any content type. While CSRF is mitigated by the middleware's custom header check, the endpoint doesn't parse a body — this is fine. However, the middleware CSRF check requires `X-Requested-With` header, which the notification polling mark-all-as-read in `Navigation.tsx:338` sends correctly. But the individual notification PATCH at `src/app/api/notifications/[id]/route.ts` does NOT send `X-Requested-With` (line in Navigation.tsx uses `{ method: 'PATCH', headers: { 'X-Requested-With': 'fetch' } }` — actually it does). Disregard this specific finding, but note the inconsistency in which endpoints require `requireJsonContentType`.
- **Impact:** Minor inconsistency, not a security issue.
- **Suggested fix:** N/A — retracted.

**[CR-007]** `useNotificationPolling` confirms auth via `/api/auth/me` on 401 but doesn't abort on unmount

- **File:** `src/hooks/useNotificationPolling.ts:93-103`
- **Issue:** When a 401 is received, a confirmation fetch to `/api/auth/me` is made with `meAbortRef.current`, but if the component unmounts between the 401 response and the `/api/auth/me` response, `isMountedRef.current` is checked but the `meController` abort is only triggered in the polling effect's cleanup (line 175). The `meAbortRef` is correctly aborted in cleanup, so this is actually handled. However, the `catch` block at line 100 unconditionally pauses polling and sets `isPollingPaused` without checking `isMountedRef`.
- **Impact:** Could trigger state update on unmounted component in the catch block.
- **Suggested fix:** Add `if (!isMountedRef.current) return;` before `setIsPollingPaused(true)` in the catch block at line 101.

**[CR-008]** `RecipeFeed` uses `pageRef` but never resets on filter change — stale page count

- **File:** `src/components/recipe/RecipeFeed.tsx:140`
- **Issue:** When `loadRecipes(true)` is called on filter change, `pageRef.current` is set to 1 (line 158). But the `offset` calculation on line 137 uses `pageRef.current` directly: `offset: String(reset ? 0 : (pageRef.current) * PAGE_SIZE)`. On the initial filter-change call, `reset=true` so offset=0, which is correct. But `pageRef.current` is set to 1 AFTER the fetch completes (line 158). If the user scrolls while the filter-change fetch is in-flight, `loadRecipes(false)` could fire with the old `pageRef.current` value. The abort controller mitigates this, but there's a window where the ref is stale.
- **Impact:** Possible duplicate or skipped recipes on rapid filter change + scroll.
- **Suggested fix:** Set `pageRef.current = 0` at the start of `loadRecipes` when `reset=true`, before the fetch.

**[CR-009]** `recipe/[id]/page.tsx` performs clipboard fallback using deprecated `document.execCommand('copy')`

- **File:** `src/app/recipe/[id]/page.tsx:251-258`
- **Issue:** The fallback clipboard method uses `document.execCommand('copy')` which is deprecated and removed in some browsers. The textarea is also created with `position: fixed; opacity: 0` which may not work in all contexts.
- **Impact:** Share functionality silently fails on newer browsers without `navigator.clipboard` API in non-secure contexts.
- **Suggested fix:** Remove the fallback and only use `navigator.clipboard.writeText`. If in a non-secure context, show an error message instead of silently failing.

**[CR-010]** `POST /api/recipes/suggest` doesn't validate `ingredients` array contents

- **File:** `src/app/api/recipes/suggest/route.ts:36-38`
- **Issue:** When `usePantry` is false and `ingredients` is provided, the array is used directly without validating that each element is a string, has reasonable length, or doesn't contain injection payloads. These strings are passed to `ingredientMatchService.findRecipesByIngredients` which does string operations on them.
- **Impact:** Malformed or oversized ingredient arrays could cause excessive memory usage or unexpected behavior in the matching algorithm.
- **Suggested fix:**

```ts
if (
  !Array.isArray(ingredients) ||
  !ingredients.every((i) => typeof i === 'string' && i.length <= 200)
) {
  return NextResponse.json({ error: 'Invalid ingredients format' }, { status: 400 });
}
userIngredients = ingredients.slice(0, 100); // cap at 100
```

#### MEDIUM

**[CR-011]** `AdminService.getStats` uses module-level cache without considering multi-tenant scenarios

- **File:** `src/infrastructure/services/AdminService.ts:17-18`
- **Issue:** `statsCache` is a module-level variable. In serverless environments, module-level state is unreliable (may persist across invocations or not). The `_clearStatsCache` export is only used in tests, so stale stats will persist for 30s even after mutations in the same instance, but may not persist at all across serverless invocations.
- **Impact:** Admin dashboard shows stale or inconsistent statistics depending on deployment model.
- **Suggested fix:** Document the behavior clearly. For serverless, either disable caching or accept the 30s staleness.

**[CR-012]** `EditProfileModal` doesn't validate avatar URL before display — XSS via blob URL injection

- **File:** `src/components/profile/EditProfileModal.tsx:117`
- **Issue:** `URL.createObjectURL(file)` is safe, but the `avatarPreview` state could theoretically be set to a `javascript:` URL if the component logic were modified. Currently safe, but no URL validation is applied to `avatarPreview` before rendering it as an `<img src>`.
- **Impact:** Low — currently mitigated by the code flow, but fragile.
- **Suggested fix:** Validate that `avatarPreview` starts with `blob:` or `https://` before rendering.

**[CR-013]** `Footer.tsx` mailto link length check uses encoded length but the 1500 limit is conservative

- **File:** `src/components/Footer.tsx:63-67`
- **Issue:** The mailto link length check at 1500 characters is after encoding. The comment says "1500 chars is a conservative limit", but the check `mailtoLink.length > 1500` is on the full URI including `mailto:` prefix and encoded characters. With `maxLength: 2000` on the message field and encoding overhead, legitimate messages will frequently hit this limit.
- **Impact:** Users with moderately long messages see an unhelpful error.
- **Suggested fix:** Either increase the limit to 2000 or reduce the message textarea `maxLength` to 1000 to prevent hitting the limit.

**[CR-014]** `PersistentSearchBar` creates a new `AbortController` before the timeout fires, but the comment says this is intentional

- **File:** `src/components/search/PersistentSearchBar.tsx:121-124`
- **Issue:** The code creates the `AbortController` outside `setTimeout`, and the cleanup function aborts it. This is correct for cancellation, but `searchAbortRef.current?.abort()` at line 120 aborts the PREVIOUS controller, and the new controller is assigned at line 122. If the effect re-runs before the timeout fires, the old controller is aborted (correct) and a new one is created (correct). This is actually fine — the comment is accurate.
- **Impact:** None — code is correct as documented.
- **Suggested fix:** N/A — retracted.

**[CR-015]** `cooked-recipes` POST validates ingredients with `i.name.length <= 200` but doesn't sanitize HTML

- **File:** `src/app/api/cooked-recipes/route.ts:173-176`
- **Issue:** Recipe ingredients are read from `recipe.ingredients` (from DB) and validated for length, but not sanitized. Since these come from the database (stored by `RecipeService` which does strip HTML), this is defense-in-depth, but `notes` field on the cooked recipe is stored without HTML stripping.
- **Impact:** If `notes` is ever rendered as raw HTML, XSS is possible. Currently React auto-escapes, but stored XSS in the database is a latent risk.
- **Suggested fix:** Strip HTML from `notes` before storing: `notes: notes ? striptags(notes.trim()) : null`.

**[CR-016]** `middleware.ts` rate limit map has no size tracking — `rateLimitMap.size > 500` check is O(1) but eviction is O(n log n)

- **File:** `src/middleware.ts:58-66`
- **Issue:** When the map exceeds 500 entries, expired entries are cleaned first, then the oldest 50 are evicted. The sorting at line 64 is `O(n log n)` where n is map size. Under high traffic, this could add latency to requests that trigger the eviction.
- **Impact:** Occasional request latency spikes under sustained high traffic.
- **Suggested fix:** Use a simpler eviction strategy: iterate and delete entries with the lowest `resetTime` without sorting, or switch to a proper LRU cache.

**[CR-017]** `RecipeCard` dev warning set grows unbounded, cleared at 100

- **File:** `src/components/recipe/RecipeCard.tsx:43-44`
- **Issue:** `warnedRecipeIds` grows to 100 then clears entirely. This means warnings will re-trigger after clear, creating noisy console output in development.
- **Impact:** Noisy development console.
- **Suggested fix:** Use a fixed-size LRU-like approach or just clear the oldest entries.

**[CR-018]** `about/page.tsx` hardcodes animation delay cap at 0.3 for features

- **File:** `src/app/about/page.tsx:144`
- **Issue:** `Math.min(0.1 * index, 0.3)` caps delay at 0.3s. With 6 features (indices 0-5), features 4 and 5 animate at the same time as feature 3. This looks like the first 3 stagger and the last 3 all appear together.
- **Impact:** Minor visual inconsistency — may be intentional UX choice.
- **Suggested fix:** Increase cap to `0.5` or use `0.05 * index` for smoother stagger across all 6 items.

**[CR-019]** `pantry/page.tsx` uses `parseFloat(String(quantity))` double conversion

- **File:** `src/app/pantry/page.tsx:270`
- **Issue:** `quantity` is already a number from `parseFloat(formData.quantity)` or 0, then it's converted to string then back to float: `parseFloat(String(quantity)) || 0`. This is redundant.
- **Impact:** No functional impact, just confusing code.
- **Suggested fix:** Just use `quantity` directly: `quantity: quantity`.

**[CR-020]** `useRecipe` hook `staleTime` of 60s means recipe data goes stale quickly after navigation

- **File:** `src/hooks/useRecipe.ts:56`
- **Issue:** After viewing a recipe, navigating away for 61 seconds, and coming back triggers a refetch. Combined with `refetchOnWindowFocus: false` from the QueryProvider, this means stale data is shown until the user explicitly navigates to the recipe again.
- **Impact:** Users may see outdated rating/comment counts. Minor UX issue.
- **Suggested fix:** Consider increasing `staleTime` to 5 minutes or enabling `refetchOnWindowFocus`.
