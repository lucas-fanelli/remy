## Code Review — 2026-03-21

### Summary

Auth routes are clean but the cooked-recipes and match endpoints have complexity-driven issues. Several error handling gaps, a potential information leak, and inconsistent response patterns across the API surface.

### Findings

#### CRITICAL

**[CR-001]** Change-password leaks arbitrary service error messages to clients

- **File:** `src/app/api/auth/change-password/route.ts:43-45`
- **Issue:** The catch block returns `error.message` for any `Error` instance that isn't auth or Zod. If `authService.changePassword` throws an unexpected error (DB connection string, internal state), it gets returned verbatim to the client.
- **Impact:** Information disclosure — internal error details (table names, connection info, stack traces embedded in messages) exposed to attackers.
- **Suggested fix:**

```typescript
if (error instanceof Error) {
  // Only return known domain errors; treat everything else as internal
  const KNOWN_ERRORS = ['Current password is incorrect', 'User not found'];
  if (KNOWN_ERRORS.includes(error.message)) {
    return ApiResponseHelper.badRequest(error.message);
  }
}
logServerError('Change password error:', error);
return ApiResponseHelper.internalError();
```

**[CR-002]** Login route leaks arbitrary error messages

- **File:** `src/app/api/auth/login/route.ts:40-43`
- **Issue:** Same pattern as CR-001. Any `Error` that doesn't contain `'Invalid credentials'` gets its raw message returned via `badRequest`.
- **Impact:** Internal error details leak to unauthenticated users on a public endpoint.
- **Suggested fix:** Same allowlist approach — only return known domain error messages.

**[CR-003]** Register route leaks arbitrary error messages

- **File:** `src/app/api/auth/register/route.ts:40-44`
- **Issue:** Same pattern. Any `Error` that doesn't match `'already exists'` leaks via `badRequest`.
- **Impact:** Information disclosure on a public, unauthenticated endpoint.
- **Suggested fix:** Allowlist known domain errors, return generic 500 for everything else.

**[CR-004]** Pantry restoration on DELETE can create unbounded items without pantry-level cap

- **File:** `src/app/api/cooked-recipes/route.ts:251-279`
- **Issue:** When restoring pantry items on cooked-recipe deletion, new items are created without checking how many items the pantry already has. The `deductedArraySchema` caps at 100 items, but each deletion adds items. Repeated cook-then-delete cycles with different recipes could grow the pantry well beyond any expected limit.
- **Impact:** Unbounded pantry growth; potential storage/performance abuse.
- **Suggested fix:** Before creating new pantry items, count existing items and refuse to create more beyond a configurable max (e.g., 500).

#### HIGH

**[CR-005]** `deductedIngredients` stored as JSON is not validated on write — only on read

- **File:** `src/app/api/cooked-recipes/route.ts:212-215`
- **Issue:** On POST, `deductedIngredients` is written to the DB via `JSON.parse(JSON.stringify(deductedIngredients))` without schema validation. The Zod validation (`deductedItemSchema`/`deductedArraySchema`) only happens on DELETE when reading it back. If `deductPantryItems` returns malformed data (e.g., NaN amount after a future refactor), it gets persisted and then silently skipped during restoration.
- **Impact:** Corrupted deduction records that can't be restored, causing permanent pantry data loss on delete.
- **Suggested fix:** Validate `deductedIngredients` against `deductedArraySchema` before persisting in the POST handler.

**[CR-006]** `striptags` applied after data already used in DB operations

- **File:** `src/app/api/cooked-recipes/route.ts:80-85`
- **Issue:** In `deductPantryItems`, `striptags` is applied to `ingredient.name`/`ingredient.unit` only when building `insufficientIngredients` and `deductedIngredients` return values. But the raw (unsanitized) `ingredient.name` was already used in `normalizeIngredientName()` for matching. If `normalizeIngredientName` doesn't strip HTML, a stored XSS payload in recipe ingredients could persist through the matching logic.
- **Impact:** Inconsistent sanitization — matching uses raw input, output uses sanitized input. Could lead to mismatches or missed deductions.
- **Suggested fix:** Sanitize ingredient names at the top of the loop before any operations:

```typescript
for (const ingredient of recipeIngredients) {
  const safeName = striptags(ingredient.name);
  const safeUnit = striptags(ingredient.unit);
  // Use safeName/safeUnit throughout
```

**[CR-007]** Login response includes token in JSON body AND httpOnly cookie

- **File:** `src/app/api/auth/login/route.ts:27-31`
- **Issue:** `result.token` is returned in the JSON response body (`data: result`) while also set as an httpOnly cookie. The whole point of httpOnly cookies is to prevent JavaScript access to the token. Returning it in the body defeats that protection.
- **Impact:** XSS vulnerability can steal auth tokens from the response body, negating the httpOnly cookie security measure.
- **Suggested fix:**

```typescript
const { token, ...safeResult } = result;
const response = NextResponse.json(
  { success: true, data: safeResult, message: 'Login successful' },
  { status: 200 }
);
setAuthCookie(response, token);
```

**[CR-008]** Same token-in-body issue on register

- **File:** `src/app/api/auth/register/route.ts:27-30`
- **Issue:** Same as CR-007 — token returned in JSON body alongside httpOnly cookie.
- **Impact:** Same XSS token theft vector.
- **Suggested fix:** Same — strip `token` from the response body.

**[CR-009]** Admin user delete transaction timeout of 60s is dangerously long

- **File:** `src/app/api/admin/users/[id]/route.ts:93`
- **Issue:** The transaction has a 60s timeout with a 50s statement timeout. A user with many posts (each with cascade-deleted comments, likes, ratings) could hold an advisory lock and a transaction open for nearly a minute, blocking all other admin deletes.
- **Impact:** Connection pool exhaustion under concurrent admin operations; potential denial of service.
- **Suggested fix:** Consider batched deletion or soft-delete pattern for users with large amounts of content. At minimum, reduce timeouts and add a content-count check before proceeding.

**[CR-010]** Match endpoint `Ingredient` type mismatch — amount is `number` in interface but validated as `string | number`

- **File:** `src/app/api/recipes/match/route.ts:18-22` vs `route.ts:136-140`
- **Issue:** The `Ingredient` interface declares `amount: number`, but the validation check accepts `typeof i?.amount === 'string' || typeof i?.amount === 'number'`. The array is then cast as `Ingredient[]` at line 134, meaning string amounts bypass the type system.
- **Impact:** `missingIngredients` array returned to client may contain string amounts where the type contract says number, causing client-side type errors.
- **Suggested fix:** Either update the `Ingredient` interface to `amount: string | number` or coerce strings to numbers during validation.

#### MEDIUM

**[CR-011]** Inconsistent error response format across routes

- **File:** Multiple files
- **Issue:** Auth routes use `ApiResponseHelper` (structured `{ success, data, message }` format). Cooked-recipes and match routes use raw `NextResponse.json({ error: ... })`. Admin routes also use raw format. Clients must handle two different response shapes.
- **Impact:** Frontend error handling complexity; easy to miss error cases when response shape varies by endpoint.
- **Suggested fix:** Pick one response format and use it consistently. `ApiResponseHelper` already exists — use it everywhere.

**[CR-012]** `maskEmail` doesn't handle edge cases

- **File:** `src/app/api/admin/users/[id]/route.ts:14-23`
- **Issue:** `maskEmail` doesn't handle emails with no local part before `@` (e.g., `@domain.com` — technically invalid but could exist in DB), or emails with multiple `@` signs. `email.indexOf('@')` finds the first `@`, so `user@name@domain.com` would mask incorrectly.
- **Impact:** Potential unmasked email data leakage for malformed email addresses.
- **Suggested fix:** Validate email format or use `lastIndexOf('@')` for the split point.

**[CR-013]** `hashtext` collision risk documented but not mitigated

- **File:** `src/app/api/cooked-recipes/route.ts:183`
- **Issue:** Comment says "collision risk is acceptable at <1M users" but there's no monitoring, metric, or log when collisions occur. Two users with colliding hashes will serialize each other's cooked-recipe operations unnecessarily, causing latency spikes with no visibility.
- **Impact:** Silent performance degradation for affected users with no diagnostic path.
- **Suggested fix:** At minimum, log advisory lock wait times. Better: use two-key form with UUID split into two int4 values now rather than deferring.

**[CR-014]** Recalc-ratings endpoint lacks idempotency/progress tracking

- **File:** `src/app/api/admin/recalc-ratings/route.ts:23-40`
- **Issue:** The bulk `UPDATE` touches every post in a single statement. For a large table, this acquires row-level locks on all posts simultaneously, blocking all concurrent rating writes for up to 30s.
- **Impact:** Rating writes (from cooked-recipes POST, comment flows) will block or timeout during recalculation.
- **Suggested fix:** Process in batches of ~1000 posts per iteration with `LIMIT`/`OFFSET` or cursor-based pagination, committing between batches.

**[CR-015]** DELETE cooked-recipe doesn't verify `cookedAt` recency for restoration

- **File:** `src/app/api/cooked-recipes/route.ts:232-290`
- **Issue:** A cooked recipe from months ago can be deleted, restoring pantry items that were deducted long ago. The pantry state may have changed completely since then, making the restoration semantically incorrect.
- **Impact:** Stale pantry restoration produces incorrect inventory state.
- **Suggested fix:** Add a time window (e.g., 24-48 hours) after which deletion is allowed but pantry restoration is skipped. Log a warning for old deletions.

#### LOW

**[CR-016]** `JSON.parse(JSON.stringify(deductedIngredients))` is unnecessary

- **File:** `src/app/api/cooked-recipes/route.ts:213`
- **Issue:** `deductedIngredients` is already a plain array of plain objects. The `JSON.parse(JSON.stringify(...))` round-trip does nothing useful. Prisma handles JSON serialization.
- **Impact:** Unnecessary CPU work on every cooked-recipe creation.
- **Suggested fix:** Pass `deductedIngredients` directly.

**[CR-017]** Logout doesn't invalidate the token server-side

- **File:** `src/app/api/auth/logout/route.ts`
- **Issue:** Logout only clears the cookie. If the token was captured (see CR-007/CR-008), it remains valid until expiry. There's no server-side token revocation.
- **Impact:** Stolen tokens remain usable after logout.
- **Suggested fix:** Implement a token blocklist (Redis or DB) checked during `requireAuth`, or switch to short-lived tokens with refresh token rotation.

**[CR-018]** Magic strings for error messages used as control flow

- **File:** Multiple files (`'RECIPE_NOT_FOUND'`, `'ALREADY_COOKED'`, `'Authentication required'`, etc.)
- **Issue:** Error routing depends on exact string matching of `error.message`. A typo or refactor silently changes behavior from a handled error to a 500.
- **Impact:** Fragile error handling; silent regressions on string changes.
- **Suggested fix:** Use typed error classes:

```typescript
class RecipeNotFoundError extends Error {
  readonly code = 'RECIPE_NOT_FOUND' as const;
}
// Then: if (error instanceof RecipeNotFoundError)
```

**[CR-019]** Admin `PATCH` for promote doesn't use a transaction with advisory lock

- **File:** `src/app/api/admin/users/[id]/route.ts:138-140`
- **Issue:** `adminService.promoteToAdmin(id)` runs outside a transaction. While promotion is less dangerous than demotion, if `promoteToAdmin` does a read-then-write internally, a concurrent request could cause a race.
- **Impact:** Minor — promotion is idempotent, but inconsistent with the demotion path's rigor.
- **Suggested fix:** Wrap in a transaction with the same advisory lock for consistency.
