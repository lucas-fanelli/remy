## Code Review — 2026-03-17

### Summary

Large Next.js recipe-sharing application with clean architecture. The codebase has solid structure (DI container, repository pattern, domain types) but contains a critical race condition that can corrupt user data, inconsistent input validation across API routes, and an auth token storage strategy vulnerable to XSS.

### Findings

#### CRITICAL

**[CR-001]** Race condition in cooked-recipes causes double pantry deduction

- **File:** `src/app/api/cooked-recipes/route.ts:96-104`
- **Issue:** The "already cooked today" check (`existingCooked`) runs outside the transaction. Two concurrent POST requests for the same recipe will both pass the check, both deduct ingredients from the pantry, and both create `cookedRecipe` entries. There is no unique constraint on `(userId, postId, date)` to catch this.
- **Impact:** Users lose double the pantry ingredients. Data corruption that silently degrades the user experience.
- **Suggested fix:**

```typescript
const cookedRecipe = await prisma.$transaction(async (tx) => {
  // Move duplicate check INSIDE the transaction
  const today = new Date();
  today.setHours(0, 0, 0, 0);
  const existingCooked = await tx.cookedRecipe.findFirst({
    where: { userId: payload.userId, postId, cookedAt: { gte: today } },
  });
  if (existingCooked) {
    throw new Error('ALREADY_COOKED');
  }

  const pantry = await tx.userPantry.findUnique({ ... });
  // ... deduction logic ...
  return tx.cookedRecipe.create({ ... });
});
```

And catch `ALREADY_COOKED` in the outer catch to return 409.

**[CR-002]** Login and register routes leak internal error details on malformed JSON

- **File:** `src/app/api/auth/login/route.ts:12`, `src/app/api/auth/register/route.ts:12`
- **Issue:** `request.json()` is called without try-catch. On malformed JSON, the SyntaxError falls through to the generic `error instanceof Error` handler, which returns `error.message` verbatim (e.g., `"Unexpected token < in JSON at position 0"`). Every other route in the codebase wraps this in try-catch and returns a sanitized "Invalid JSON body" message.
- **Impact:** Information disclosure. The raw parse error can reveal server internals and is inconsistent with the rest of the API surface.
- **Suggested fix:**

```typescript
let body;
try {
  body = await request.json();
} catch {
  return ApiResponseHelper.badRequest('Invalid JSON body');
}
```

#### HIGH

**[CR-003]** Authentication tokens stored in localStorage are vulnerable to XSS theft

- **File:** `src/contexts/AuthContext.tsx:42,95,107`
- **Issue:** JWT tokens are stored in `localStorage` via `safeStorage.setItem('auth_token', ...)`. Any XSS vulnerability anywhere in the app (including third-party scripts like `@vercel/analytics`) allows an attacker to steal the token with `localStorage.getItem('auth_token')` and impersonate the user indefinitely.
- **Impact:** Full account takeover if any XSS exists. Tokens persist until manually cleared.
- **Suggested fix:** Use HttpOnly, Secure, SameSite cookies for token storage. The server sets the cookie; the client never touches it. This eliminates XSS-based token theft entirely.

**[CR-004]** No integration or unit tests for any API route handler

- **File:** `src/app/api/**/*.ts` (all route files)
- **Issue:** There are zero test files under `src/app/api/`. The test suite covers services, repositories, and React components thoroughly, but every API route — the actual HTTP boundary — is completely untested. Route-level validation, error handling branches, auth checks, and response shapes are unverified.
- **Impact:** Regressions in routing logic, auth middleware, input validation, or response format will not be caught by CI.
- **Suggested fix:** Add integration tests for critical routes (auth, recipes CRUD, comments, admin) using `NextRequest` mocks or a test server.

**[CR-005]** In-memory rate limiting is ineffective in serverless/multi-instance deployments

- **File:** `src/middleware.ts:8-10`
- **Issue:** `rateLimitMap` is a `Map` local to the process. On Vercel (serverless), every cold start creates a new empty map. On multi-instance K8s, each pod has its own map. An attacker can bypass the limit by waiting for a new instance or distributing requests.
- **Impact:** Rate limiting provides zero protection in production serverless deployments. Auth endpoints (login brute-force) and upload endpoints are unprotected.
- **Suggested fix:** Replace with Redis/Upstash/Vercel KV. The code already has a comment acknowledging this — it needs to be fixed, not deferred.

**[CR-006]** Recipe suggest endpoint has unhandled JSON parse error

- **File:** `src/app/api/recipes/suggest/route.ts:17`
- **Issue:** `const body = await request.json();` without try-catch — identical to CR-002. Malformed JSON returns a 500 with internal error details instead of 400.
- **Impact:** Information disclosure and incorrect HTTP status code.
- **Suggested fix:** Same pattern as CR-002 — wrap in try-catch, return 400 with "Invalid JSON body".

#### MEDIUM

**[CR-007]** Admin route params lack UUID validation before database queries

- **File:** `src/app/api/admin/comments/[id]/route.ts:13`, `src/app/api/admin/recipes/[id]/route.ts:13`, `src/app/api/admin/users/[id]/route.ts:13`
- **Issue:** The `id` parameter from URL is passed directly to Prisma without validating it matches UUID format. Non-UUID strings cause Prisma to throw uncaught errors that are caught as generic 500s. The `cooked-recipes` DELETE route validates with `UUID_REGEX` — admin routes do not.
- **Impact:** Inconsistent error responses (500 instead of 400). Could expose Prisma error internals in logs.
- **Suggested fix:**

```typescript
const { id } = await params;
if (!UUID_REGEX.test(id)) {
  return NextResponse.json({ error: 'Invalid ID format' }, { status: 400 });
}
```

**[CR-008]** `AdminService.deleteComment` does not guard against null comment before rating recalculation

- **File:** `src/infrastructure/services/AdminService.ts:196-215`
- **Issue:** Inside the transaction, `findUnique` may return null, but the code proceeds to `delete` (which fails) and never reaches the rating recalculation. If the comment doesn't exist, the delete throws `Record to delete does not exist`, which bubbles up as a generic "Failed to delete comment" 500 instead of a 404.
- **Impact:** Missing 404 for nonexistent comments. The transaction rollback is correct, but the error is misclassified.
- **Suggested fix:**

```typescript
const comment = await tx.comment.findUnique({ where: { id: commentId } });
if (!comment) throw new Error('COMMENT_NOT_FOUND');
await tx.comment.delete({ where: { id: commentId } });
```

**[CR-009]** Recipe match endpoint fetches 100 full recipes into memory with no cursor pagination

- **File:** `src/app/api/recipes/match/route.ts:56-73`
- **Issue:** Fetches up to 100 recipes with all ingredients as JSON, then iterates over every ingredient of every recipe against every pantry item in memory. As the recipe count grows, this will become slow and memory-intensive. There's no way for the client to paginate results or specify a smaller working set.
- **Impact:** At scale, this endpoint becomes a latency and memory bottleneck. 100 recipes × 20 ingredients × 500 pantry items = 1M comparisons.
- **Suggested fix:** Move matching logic to a database query (PostgreSQL JSON operators or a materialized view), or at minimum add cursor-based pagination and limit ingredient data to names only.

**[CR-010]** Notification polling at 60-second interval creates linear server load

- **File:** `src/components/Navigation.tsx:151-165`
- **Issue:** Every connected client polls `GET /api/notifications` every 60 seconds. With N concurrent users, this creates N requests/minute regardless of whether new notifications exist. The visibility change handler helps but doesn't eliminate the problem.
- **Impact:** Unnecessary database load proportional to user count. At 10K concurrent users = 10K req/min just for notification checks.
- **Suggested fix:** Use Server-Sent Events (SSE) or WebSocket for push-based notifications, or at minimum increase the interval and use `If-Modified-Since` / ETag caching.

**[CR-011]** `RecipeFeed` infinite scroll uses window scroll events with throttle instead of IntersectionObserver

- **File:** `src/components/recipe/RecipeFeed.tsx:117-130`
- **Issue:** Scroll-based infinite loading uses `window.scrollY` and `document.documentElement.scrollHeight` with a 200ms throttle. This doesn't work correctly in containers with their own scroll context (modals, nested scrollable areas) and fires constantly during scrolling.
- **Impact:** Potential layout bugs in nested scroll contexts; unnecessary event processing.
- **Suggested fix:** Use `IntersectionObserver` on a sentinel element at the bottom of the list.

#### LOW

**[CR-012]** CSP allows `unsafe-inline` for scripts

- **File:** `src/middleware.ts:76`
- **Issue:** `script-src 'self' 'unsafe-inline'` allows inline script injection, significantly weakening XSS protection. This is required for Next.js inline scripts but negates much of the CSP benefit.
- **Impact:** XSS attacks via inline script injection are not blocked by CSP.
- **Suggested fix:** Use nonce-based CSP (`script-src 'self' 'nonce-xxx'`) with Next.js `nonce` support, or at minimum document this as an accepted risk.

**[CR-013]** Multiple `as any` type assertions in UI components suppress type checking

- **File:** `src/app/profile/[username]/page.tsx:305`, `src/components/recipe/MatchedRecipes.tsx:185`, `src/components/recipe/RecipeCard.tsx` (difficulty color)
- **Issue:** `color={getDifficultyColor(recipe.difficulty) as any}` appears in multiple components. The `getDifficultyColor` return type is `'success' | 'warning' | 'error' | 'default'` which is compatible with MUI's `ChipProps['color']` — the cast is unnecessary and hides potential type errors.
- **Impact:** Type errors in color props would be silently ignored.
- **Suggested fix:** Remove `as any` casts. If MUI types don't align, use a proper type assertion or extend the type.

**[CR-014]** `RecipeCard` image `onError` handler can loop if placeholder also fails

- **File:** `src/components/recipe/RecipeCard.tsx:118-121`
- **Issue:**

```typescript
onError={(e: React.SyntheticEvent<HTMLImageElement>) => {
  if (!e.currentTarget.src.endsWith('/placeholder-recipe.png')) {
    e.currentTarget.src = '/placeholder-recipe.png';
  }
}}
```

If `/placeholder-recipe.png` doesn't exist, the `onError` fires again. The guard prevents infinite loops but the image will show as broken with no visual feedback.

- **Impact:** Broken image displayed if placeholder is missing.
- **Suggested fix:** Set a data attribute to track fallback attempts, or use a base64 inline fallback that cannot fail.
