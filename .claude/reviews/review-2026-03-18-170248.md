## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured with good test coverage, but contains several security gaps, race conditions, and data integrity issues that need attention.

### Findings

#### CRITICAL

**[CR-001]** Notification polling logs out user on transient 401, no re-auth attempt

- **File:** `src/components/Navigation.tsx:206-211`
- **Issue:** A single 401 from `/api/notifications` immediately calls `logout()`, clearing all user state. If the server returns 401 due to a transient issue (clock skew, brief token rotation window), the user is silently logged out mid-session.
- **Impact:** Users randomly logged out during normal usage. Combined with the retry-on-visibility logic resetting `consecutiveFailuresRef`, this creates a loop: tab focus -> fetch -> 401 -> logout -> tab focus -> fetch as guest.
- **Suggested fix:** Add a confirmation check before logout — verify the token is truly expired by calling `/api/auth/me` before destroying the session:

```ts
} else if (response.status === 401) {
  // Confirm auth is truly invalid before destroying session
  const meResp = await fetch('/api/auth/me', { signal: controller.signal });
  if (!meResp.ok) {
    pollingStoppedRef.current = true;
    logout();
  }
  return;
}
```

**[CR-002]** `cooked-recipes` POST deducts pantry items without rollback on partial failure

- **File:** `src/app/api/cooked-recipes/route.ts:120-145`
- **Issue:** The pantry deduction loop inside the transaction deletes/updates pantry items one by one. If any individual `tx.pantryItem.delete` or `tx.pantryItem.update` fails mid-loop, the transaction rolls back — but the code catches no per-item errors. More critically, the `ingredientMatches` fuzzy matching could match the wrong pantry item, silently deducting the wrong ingredient.
- **Impact:** Users lose incorrect pantry items with no way to recover. The fuzzy match (`ingredientMatches`) does substring matching — "rice" matches "rice vinegar".
- **Suggested fix:** Use exact ingredient ID matching from the recipe rather than fuzzy name matching for deduction. Or at minimum, match on normalized name + unit combination:

```ts
const pantryItem = pantry.items.find(
  (item) =>
    !matchedPantryIds.has(item.id) &&
    normalizeIngredientName(item.name) === normalizeIngredientName(ingredient.name) &&
    unitsMatch(item.unit, ingredient.unit)
);
```

**[CR-003]** Middleware JWT verification uses `atob()` which fails on non-ASCII payloads

- **File:** `src/middleware.ts:115-140`
- **Issue:** The admin route check uses `atob()` to decode JWT payload. `atob()` only handles Latin1 characters — if any JWT claim contains non-ASCII characters (e.g., a username with accented characters), `atob()` throws and the entire admin check silently fails, defaulting to redirect.
- **Impact:** Admin users with non-ASCII usernames are permanently locked out of the admin panel.
- **Suggested fix:** Use proper base64url decoding:

```ts
function base64UrlDecode(str: string): string {
  const base64 = str.replace(/-/g, '+').replace(/_/g, '/');
  const padded = base64 + '='.repeat((4 - (base64.length % 4)) % 4);
  const bytes = Uint8Array.from(atob(padded), (c) => c.charCodeAt(0));
  return new TextDecoder().decode(bytes);
}
```

#### HIGH

**[CR-004]** Recipe match endpoint has no pagination on final output, loads all candidate data into memory

- **File:** `src/app/api/recipes/match/route.ts:100-160`
- **Issue:** After the DB pre-filter returns up to 500 candidate IDs, the code fetches all 500 full recipe objects, then does in-memory matching on all of them, building three arrays (`readyToCook`, `almostThere`, `needMore`) with up to 20 items each. For users with many pantry items, this loads significant data into memory per request.
- **Impact:** Memory pressure under load. Each request can hold ~500 full recipe objects in memory simultaneously.
- **Suggested fix:** Apply the 30% match threshold during the candidate fetch phase, and limit the full-data fetch to only matched IDs:

```ts
// Only fetch full data for recipes that passed the match threshold
const matchedIds = matchResults.map(m => m.id);
const recipes = matchedIds.length > 0
  ? await prisma.post.findMany({ where: { id: { in: matchedIds } }, ... })
  : [];
```

(This is already done — good. But the initial `candidates` fetch of 500 full objects at line 127 should use `select: { id: true, ingredients: true }` only.)

**[CR-005]** `searchUsers` leaks email in `/api/search/route.ts` despite stripping

- **File:** `src/app/api/search/route.ts:28`
- **Issue:** The code calls `userService.searchUsers()` which returns `UserPublicProfile` (which already excludes password but includes email), then strips email with `.map(({ email, ...rest }) => rest)`. However, the `IUserService` interface declares the return type as `UserPublicProfile` which includes email — this is fragile. If `searchUsers` ever returns the raw Prisma type, email leaks.
- **Impact:** Email enumeration risk if the destructuring is ever removed or the service return type changes.
- **Suggested fix:** The `UserService.searchUsers` should not return email at all. Add a `searchUsersPublic` method that uses a Prisma `select` excluding email at the query level.

**[CR-006]** No CSRF protection for multipart/form-data uploads when `Sec-Fetch-Site` is absent

- **File:** `src/middleware.ts:155-170`
- **Issue:** The CSRF check allows requests through if `contentType.includes('application/json')` OR `request.headers.has('authorization')` OR `request.headers.has('x-requested-with')`. For file uploads using `multipart/form-data`, the code relies on `x-requested-with` header. However, the upload components at `src/components/common/ImageUpload.tsx:68` and `src/components/recipe/CommentsSection.tsx:114` do send `X-Requested-With: fetch`, but `src/components/profile/EditProfileModal.tsx:112` also sends it. This is correct but fragile — if any upload path forgets the header, CSRF protection is bypassed.
- **Impact:** If a developer adds a new upload endpoint without the custom header, it would be CSRF-vulnerable for `multipart/form-data` requests.
- **Suggested fix:** Document this requirement explicitly or enforce it by rejecting multipart requests that lack both `Sec-Fetch-Site: same-origin` and `X-Requested-With`.

**[CR-007]** `RecipeFeed` infinite scroll can fire duplicate requests

- **File:** `src/components/recipe/RecipeFeed.tsx:123-175`
- **Issue:** The `loadingRef` guard prevents concurrent calls, but the `IntersectionObserver` callback at line 182 doesn't check if a load is already in progress before calling `loadRecipes()`. The `loadRecipes` function checks `loadingRef.current` internally, but between the observer callback firing and `loadingRef.current` being set to `true`, React's event loop could allow multiple calls through.
- **Impact:** Duplicate recipe fetches, duplicate entries in the feed (mitigated by the dedup filter at line 159, but still wastes network requests).
- **Suggested fix:** Already mostly handled by the ref guard. Low risk but could add the check in the observer callback too:

```ts
if (entries[0].isIntersecting && hasMore && !loadingRef.current) {
  loadRecipes();
}
```

#### MEDIUM

**[CR-008]** `env-validation.ts` production secret check is bypassable

- **File:** `src/lib/env-validation.ts:82-100`
- **Issue:** The production validation checks if `JWT_SECRET.length < 32` and if it matches known placeholders. But it doesn't check for common weak secrets like `"secret"`, `"password"`, or repeated characters like `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"`. A 32-character weak secret passes validation.
- **Impact:** Weak JWT secrets in production could lead to token forgery.
- **Suggested fix:** Add entropy check — reject secrets with Shannon entropy below a threshold, or require secrets generated by `openssl rand -base64 32`.

**[CR-009]** `PersistentSearchBar` live search fires on every keystroke after debounce

- **File:** `src/components/search/PersistentSearchBar.tsx:117-150`
- **Issue:** The AbortController is created per effect run, but when the user types fast, each character creates a new timeout. The previous timeout is cleared, but the AbortController from the previous effect run is also created unnecessarily. This is fine functionally but creates unnecessary object allocations.
- **Impact:** Minor performance concern on low-end devices.
- **Suggested fix:** Move AbortController creation inside the timeout callback so it's only created when a request is actually made.

**[CR-010]** `about/page.tsx` renders JSX icons in module-scope array

- **File:** `src/app/about/page.tsx:31-69`
- **Issue:** The `features` array is defined at module scope with JSX elements (`<Restaurant sx={{ fontSize: 40 }} />`). These create React elements at import time, before any provider context. While this works for MUI icons, it prevents tree-shaking and the elements are created even if the page is never visited.
- **Impact:** Slightly increased bundle initialization time. Not a bug but suboptimal.
- **Suggested fix:** Use icon components as values and render them in the component:

```ts
const features = [
  { icon: Restaurant, title: 'Share Recipes', ... },
];
// In render: <feature.icon sx={{ fontSize: 40 }} />
```

**[CR-011]** Admin pages perform client-side auth check with visible loading spinner

- **File:** `src/app/admin/comments/page.tsx:82-88`, `src/app/admin/recipes/page.tsx:92-98`, `src/app/admin/users/page.tsx:100-106`
- **Issue:** All admin pages show a `CircularProgress` spinner while checking `authLoading || !isAdmin`. A non-admin user briefly sees the spinner before being redirected. The middleware already blocks non-admin access, but the client-side check still renders the loading state.
- **Impact:** Minor UX issue — brief flash of spinner for unauthorized users before redirect.
- **Suggested fix:** Return `null` instead of spinner when `!isAdmin && !authLoading` to avoid the flash.

**[CR-012]** `UserService.updateProfile` doesn't validate `website` for embedded credentials but `UserService` does

- **File:** `src/infrastructure/services/UserService.ts:37-48`
- **Issue:** The service validates for embedded credentials (`url.username || url.password`) but the API route at `src/app/api/users/profile/route.ts:35-47` only validates it's a Cloudinary URL for the avatar field, not the website field. The Zod schema at `src/lib/validation/schemas.ts:40-46` validates URL format but doesn't check for embedded credentials. The defense is split across layers inconsistently.
- **Impact:** If the Zod schema validation runs before the service, an attacker could set a website URL with embedded credentials (though the service would catch it).
- **Suggested fix:** Add the credential check to the Zod schema:

```ts
website: z.string()
  .url()
  .refine((url) => {
    const parsed = new URL(url);
    return !parsed.username && !parsed.password;
  }, 'URL must not contain credentials');
```

**[CR-013]** `Navigation.tsx` notification polling doesn't cancel on component unmount during active fetch

- **File:** `src/components/Navigation.tsx:183-260`
- **Issue:** The cleanup function calls `notificationAbortRef.current?.abort()` and `clearPolling()`, but there's a timing window: if the visibility handler fires `fetchNotifications()` right before unmount, the new AbortController may not be captured in `notificationAbortRef` before cleanup runs.
- **Impact:** Potential memory leak from orphaned fetch promises updating state on unmounted component. React 18 suppresses the warning but the state update still happens.
- **Suggested fix:** Add an `isMounted` ref check before `setNotifications` and `setUnreadNotifications` calls inside `fetchNotifications`.
