#### CRITICAL

**[CR-001]** Unhandled floating Promise in DELETE account route

- **File:** `src/app/api/users/profile/route.ts:83`
- **Issue:** `Promise.allSettled(...)` is called without `await` and the result is a floating promise. While the `.catch(() => {})` at the end prevents unhandled rejection crashes, the `Promise.allSettled` itself is not awaited or stored. In serverless/edge environments (Vercel, etc.), the runtime may terminate the function context immediately after the `return` statement on line 95, killing all in-flight Cloudinary cleanup requests before they complete. The comment says "fire-and-forget" but serverless runtimes don't support that pattern — the execution context is frozen/killed after the response is sent.
- **Impact:** Cloudinary images for deleted accounts are never cleaned up in serverless deployments, leading to accumulating orphaned images and storage costs.
- **Suggested fix:** Either `await` the cleanup before returning, or use `waitUntil` if available in Next.js edge/serverless context:

```typescript
// Option 1: await before returning
await Promise.allSettled(imageUrls.map((url) => cleanupCloudinaryImage(url))).then((results) => {
  const failures = results
    .map((r, i) => (r.status === 'rejected' ? { url: imageUrls[i], reason: r.reason } : null))
    .filter(Boolean);
  if (failures.length > 0) logServerError('Failed to cleanup images for deleted account', failures);
});

// Option 2: Use Next.js waitUntil (if on a supported runtime)
// import { waitUntil } from 'next/server';
// waitUntil(Promise.allSettled(...));
```

**[CR-002]** `IUserService.updateProfile` returns `UserPublicProfile` which includes `email` — leaked to client

- **File:** `src/domain/services/IUserService.ts:14` / `src/app/api/users/profile/route.ts:52`
- **Issue:** `UserPublicProfile` is `Omit<User, 'password'>`, which still includes `email`, `role`, and every other User field. The PUT handler returns `updatedUser` directly via `ApiResponseHelper.success(updatedUser, ...)`. If `userService.updateProfile` returns the full `UserPublicProfile` (which it does per the interface), the user's email and internal fields are sent to the client on every profile update.
- **Impact:** Email address and internal user metadata (role, isVerified, etc.) are exposed in the API response. This is a data leak — particularly problematic if the user has set their profile to private, expecting their email to be hidden.
- **Suggested fix:** Select only the fields needed for the response:

```typescript
const { password, email, role, ...safeUser } = updatedUser as Record<string, unknown>;
return ApiResponseHelper.success(safeUser, 'Profile updated successfully');
```

Or better, define a proper response DTO in the service layer that excludes sensitive fields.

**[CR-003]** Recipe match endpoint raw SQL is vulnerable to unbounded `jsonb_array_elements` expansion

- **File:** `src/app/api/recipes/match/route.ts:109-117`
- **Issue:** The `jsonb_array_elements(p.ingredients)` call in the raw SQL expands every element of every recipe's ingredients array into a row before the `LIMIT` is applied. The `jsonb_array_length(p.ingredients) <= 100` filter is in the `WHERE` clause, but `jsonb_array_elements` is in the `FROM` clause — PostgreSQL may expand all elements before filtering. A recipe with, say, 100 ingredients produces 100 rows in the intermediate result. With thousands of recipes, this can produce millions of intermediate rows, causing high memory usage and slow queries. The `statement_timeout` mitigates total time but not memory pressure — a single query that allocates gigabytes of intermediate rows before timeout can still OOM the database connection.
- **Impact:** Database memory exhaustion or severe performance degradation under normal load, especially as the recipe count grows. This is a denial-of-service vector since any authenticated user can trigger it.
- **Suggested fix:** Use a subquery or `EXISTS` to avoid row multiplication:

```sql
SELECT p.id, p.ingredients
FROM "Post" p
JOIN "User" u ON u.id = p."userId"
WHERE u."isPrivate" = false
  AND p.ingredients IS NOT NULL
  AND jsonb_typeof(p.ingredients) = 'array'
  AND jsonb_array_length(p.ingredients) <= 100
  AND EXISTS (
    SELECT 1 FROM jsonb_array_elements(p.ingredients) AS elem
    WHERE lower(elem->>'name') LIKE ANY(ARRAY[${Prisma.join(likePatterns)}]) ESCAPE '\\'
  )
ORDER BY p.id
LIMIT ${limit}
```

This evaluates `jsonb_array_elements` per-row via `EXISTS` and short-circuits on first match, avoiding the cross-join amplification.

**[CR-004]** `instruction.image` URL in recipe creation schema allows arbitrary URLs — stored XSS / SSRF

- **File:** `src/app/api/recipes/route.ts:25`
- **Issue:** The `instructionSchema` accepts any valid URL for the `image` field (`z.string().url().optional()`), but unlike the top-level `imageUrl` which is validated against Cloudinary via `validateCloudinaryUrl`, instruction-level images have no such validation. An attacker can inject `javascript:` URIs (if the frontend renders them in `<img>` or `<a>` tags), `data:` URIs with malicious payloads, or arbitrary external URLs that could be used for SSRF if the server ever fetches them. The main `imageUrl` is validated — the instruction images are not.
- **Impact:** Stored XSS if instruction images are rendered as links/iframes, or SSRF if any server-side process fetches these URLs. Even if the current frontend safely renders them as `<img src>`, future code changes could introduce the vulnerability.
- **Suggested fix:** Apply the same Cloudinary URL validation to instruction images:

```typescript
const instructionSchema = z
  .object({
    step: z.number().int().positive(),
    description: z.string().min(1).max(5000),
    image: z.string().url().optional(),
  })
  .strict();

// In POST handler, after schema validation:
for (const instruction of validated.instructions) {
  if (instruction.image) {
    const cloudinaryError = validateCloudinaryUrl(instruction.image);
    if (cloudinaryError) return cloudinaryError;
  }
}
```

**[CR-005]** Race condition in DELETE cooked-recipe: pantry restoration uses stale `existingItem.quantity`

- **File:** `src/app/api/cooked-recipes/route.ts:240-248`
- **Issue:** The pantry item restoration loop reads `existingItem.quantity` and then updates with `existingItem.quantity + d.amount`. While there is an advisory lock keyed on user ID (`PG_ADVISORY_LOCK_COOKED_RECIPE`), the lock is acquired _after_ the `findFirst` for the cooked recipe (line 226). If a user sends two concurrent DELETE requests for different cooked recipes, both acquire the advisory lock sequentially, but each reads the pantry quantity _after_ the lock — however, the `findFirst` to get `existingItem` and the `update` are not atomic. More critically: if the user concurrently creates a new cooked recipe (which uses the same advisory lock key), the POST handler's `deductPantryItems` could interleave with the DELETE handler's restoration, because both use `pantryItem.update` with absolute values derived from a prior read. The advisory lock serializes within the same lock key, but a failed lock acquisition due to timeout or deadlock would break the invariant.
- **Impact:** Pantry quantities can drift from their correct values over time — items may show negative quantities or incorrect amounts after concurrent cook/uncook operations that race on lock acquisition failures.
- **Suggested fix:** Use `increment` instead of absolute value updates to make the operation atomic regardless of interleaving:

```typescript
await tx.pantryItem.update({
  where: { id: existingItem.id },
  data: { quantity: { increment: d.amount as number } },
});
```
