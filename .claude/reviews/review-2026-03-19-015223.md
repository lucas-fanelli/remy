## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured, but several security gaps, race conditions, and data integrity issues exist across API routes and client components.

### Findings

#### CRITICAL

**[CR-001]** Unbounded recipe matching loads entire ingredient sets into memory

- **File:** `src/app/api/recipes/match/route.ts:89-95`
- **Issue:** The raw SQL query uses `jsonb_array_elements` which explodes rows per ingredient per recipe. With 200 recipes averaging 10 ingredients each, that's 2000 rows before DISTINCT. The `LIMIT` applies after the explosion, not before, so PostgreSQL must process all matching rows first. A malicious user with many pantry items could trigger expensive full-table scans.
- **Impact:** Database CPU saturation, slow response times under load, potential DoS.
- **Suggested fix:** Add a subquery that limits candidate recipes first, then joins ingredients:

```sql
WITH candidates AS (
  SELECT id, ingredients FROM "Post"
  WHERE ingredients IS NOT NULL
  LIMIT ${limit}
)
SELECT DISTINCT c.id, c.ingredients
FROM candidates c, jsonb_array_elements(c.ingredients) AS elem
WHERE (${Prisma.join(nameConditions, ' OR ')})
```

**[CR-002]** Comment image URL not validated on PATCH (edit)

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:47-49`
- **Issue:** The `imageUrl` field in comment PATCH uses `validateCloudinaryUrl` but this validation returns a `NextResponse` which is checked, however on the POST route (`comments/route.ts:72-73`) the same pattern is used. The issue is that existing comments could be edited to inject any `imageUrl` if the validation is bypassed — but more critically, the comment update at line 73 uses `...(imageUrl !== undefined && { imageUrl: imageUrl || null })` which means sending `imageUrl: ""` stores `null`, but sending `imageUrl: undefined` skips the field. An attacker could send `imageUrl: "javascript:alert(1)"` if `validateCloudinaryUrl` has a bypass.
- **Impact:** Stored XSS if Cloudinary validation is bypassed, image URL spoofing.
- **Suggested fix:** Also validate that imageUrl starts with `https://res.cloudinary.com/` at the database layer or add a Prisma middleware.

**[CR-003]** Admin user delete has TOCTOU between advisory lock hash and actual user ID

- **File:** `src/app/api/admin/users/[id]/route.ts:46`
- **Issue:** `hashtext(${id})` generates the advisory lock key from the user ID string. If two different admin requests target the same user simultaneously, they serialize correctly. However, the `requester` re-verification at line 50 queries by `authResult.userId` which was validated outside the transaction. If the admin's role was revoked between the outer `requireAdmin()` check and the inner `SELECT role`, the `NOT_ADMIN` error fires correctly — but there's a window where `authResult.userId` could be stale if the token was just generated. This is defense-in-depth and works, but the `$queryRaw` at line 50 doesn't use parameterized UUID validation, trusting the `authResult.userId` from token parsing.
- **Impact:** Low probability, but raw query with token-derived value could be exploited if token signing is compromised.
- **Suggested fix:** Use Prisma's typed `findUnique` instead of `$queryRaw` for the requester check:

```ts
const requester = await tx.user.findUnique({
  where: { id: authResult.userId },
  select: { role: true },
});
```

**[CR-004]** `cooked-recipes` POST has no Content-Type validation for non-JSON bodies

- **File:** `src/app/api/cooked-recipes/route.ts:118`
- **Issue:** The POST handler calls `requireJsonContentType` correctly, but the GET and DELETE handlers don't need it. However, the advisory lock in the transaction uses `hashtext(${user.id})` — if `user.id` contains unexpected characters (it shouldn't with UUID validation, but the user object comes from `requireAuth` which returns the full user), the hashtext is safe. The real issue: **the `force` parameter is user-controlled and used to bypass the insufficient ingredients check**. A client can always send `force: true` to skip pantry validation entirely, making the whole pantry deduction feature bypassable.
- **Impact:** Users can always bypass pantry checks, defeating the purpose of the feature. Pantry items won't be deducted if user always forces.
- **Suggested fix:** This may be intentional UX. If not, remove the `force` flag from the public API and handle it server-side with a confirmation flow.

#### HIGH

**[CR-005]** Recipe match endpoint leaks full ingredient lists in response

- **File:** `src/app/api/recipes/match/route.ts:163-172`
- **Issue:** The `MatchedRecipeData` type includes full `ingredients` array and `missingIngredients` for every matched recipe. For 20 recipes per category with 10+ ingredients each, this response can be 50KB+. More importantly, the ingredients include amounts — exposing other users' full recipes for free without visiting the recipe page.
- **Impact:** Performance degradation on mobile, content scraping of recipe data.
- **Suggested fix:** Return only ingredient names (not amounts/units) in the match response, or just counts.

**[CR-006]** No rate limiting on recipe matching endpoint

- **File:** `src/app/api/recipes/match/route.ts`
- **Issue:** The `/api/recipes/match` endpoint runs expensive database queries (jsonb_array_elements + IN-memory matching) but isn't subject to stricter rate limiting than the default 100 requests/15min. A single user could hammer this endpoint to DoS the database.
- **Impact:** Database resource exhaustion.
- **Suggested fix:** Add this endpoint to a stricter rate limit tier (e.g., 10 requests per minute) in middleware.

**[CR-007]** `RecipeFeed` infinite scroll has no deduplication on filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:140-146`
- **Issue:** When filters change, `loadRecipes(true)` is called which resets the page. But the `AbortController` race between the old and new request means if the old request completes after `reset=true` but before the new request returns, stale data could appear briefly. The `requestIdRef` check at line 154 mitigates this, but the `setRecipes(data.recipes)` at line 155 doesn't check the requestId — it only checks inside the `if (thisRequestId !== requestIdRef.current) return` guard. This is correct, but the abort + requestId double-guard means the abort error catch at line 164 could mask other errors.
- **Impact:** Brief flicker of wrong data on rapid filter changes. Minor UX issue.
- **Suggested fix:** This is already well-handled. Low priority.

**[CR-008]** Notification polling doesn't validate response schema

- **File:** `src/hooks/useNotificationPolling.ts:72-78`
- **Issue:** `data.notifications` and `data.unreadCount` are used directly from the API response without any type checking. If the API response shape changes or returns unexpected data, the component will silently break.
- **Impact:** Silent UI failures if API contract changes.
- **Suggested fix:** Add runtime validation or at least defensive checks:

```ts
const notificationsArray = Array.isArray(data?.notifications) ? data.notifications : [];
```

**[CR-009]** `FileReader.readAsDataURL` used for comment image previews — memory leak risk

- **File:** `src/components/recipe/CommentsSection.tsx:195-197`
- **Issue:** `reader.readAsDataURL(file)` converts the entire file to a base64 data URL stored in React state. For a 5MB image, this creates a ~6.7MB string in memory that persists until the component unmounts. The `EditProfileModal` correctly uses `URL.createObjectURL` (line 107) but `CommentsSection` doesn't.
- **Impact:** Memory bloat on mobile devices when attaching images to comments.
- **Suggested fix:** Use `URL.createObjectURL(file)` instead of `readAsDataURL`, and revoke the URL on cleanup:

```ts
setImagePreview(URL.createObjectURL(file));
// In cleanup or removeSelectedImage:
if (imagePreview?.startsWith('blob:')) URL.revokeObjectURL(imagePreview);
```

**[CR-010]** `averageRating` set to `0` instead of `null` when all ratings are removed

- **File:** `src/app/api/recipes/[id]/comments/route.ts:117` and `src/app/api/recipes/[id]/comments/[commentId]/route.ts:97`
- **Issue:** When recalculating average rating: `averageRating: ratingAggregation._avg.rating != null ? Math.round(...) : 0`. Setting `averageRating` to `0` when there are no ratings is semantically wrong — `0` implies "rated zero stars" while `null` means "not yet rated". The `recalc-ratings` admin route correctly uses `NULL` for unrated recipes (line 32), but the per-comment rating update uses `0`.
- **Impact:** Recipes that lose all ratings show "0 stars" instead of "No ratings yet". Data inconsistency between admin recalc and per-comment updates.
- **Suggested fix:**

```ts
averageRating: ratingAggregation._avg.rating != null
  ? Math.round(ratingAggregation._avg.rating * 10) / 10
  : null,
```

#### MEDIUM

**[CR-011]** `SearchResults` component uses `lastIndexOf(' ', maxLen)` which returns -1 for single-word strings

- **File:** `src/components/SearchResults.tsx:39`
- **Issue:** `truncateAtWord` calls `text.lastIndexOf(' ', maxLen)`. If the text has no spaces before `maxLen`, `idx` is -1, and `idx > 0` is false, so it falls back to `text.substring(0, maxLen)` which could split a word mid-character in multi-byte strings.
- **Impact:** Broken text rendering for non-English recipe descriptions with long words.
- **Suggested fix:** Use `idx >= 0` or handle single-word case explicitly.

**[CR-012]** `useNotificationPolling` circuit breaker cooldown calculation can overflow

- **File:** `src/hooks/useNotificationPolling.ts:137`
- **Issue:** `5 * 60 * 1000 * Math.pow(2, breakerTripCountRef.current - 1)` — if the breaker trips many times (e.g., persistent server failure), `Math.pow(2, n)` grows exponentially. After ~30 trips, this exceeds `Number.MAX_SAFE_INTEGER`. The `Math.min(..., 60 * 60 * 1000)` cap prevents the final value from being too large, but the intermediate calculation could still be `Infinity`.
- **Impact:** No practical impact due to the `Math.min` cap, but worth noting for correctness.
- **Suggested fix:** Cap `breakerTripCountRef.current` at a reasonable max (e.g., 10).

**[CR-013]** Admin pages use MUI `Grid` v1 deprecated API

- **File:** `src/app/admin/page.tsx`, `src/app/admin/recipes/page.tsx`, `src/app/admin/users/page.tsx`
- **Issue:** Uses `<Grid item xs={6} sm={4} md={2}>` which is the MUI Grid v1 API. MUI has been migrating to Grid v2 with different prop names.
- **Impact:** Will break on MUI major version upgrade.
- **Suggested fix:** Migrate to `Grid2` component or pin MUI version.

**[CR-014]** `pantry/[id]/route.ts` PUT handler doesn't validate `category` field content

- **File:** `src/app/api/pantry/[id]/route.ts:60-64`
- **Issue:** Category length is validated but content is not. A user could store arbitrary HTML/script as a category name (e.g., `<script>alert(1)</script>`). While React auto-escapes in JSX, the category is used in filter dropdowns and could be rendered differently in future features.
- **Impact:** Low risk due to React's auto-escaping, but violates defense-in-depth.
- **Suggested fix:** Sanitize or whitelist category values.

**[CR-015]** `Footer` component sanitizes newlines but not the full `subject` field for mailto

- **File:** `src/components/Footer.tsx:54-56`
- **Issue:** The `sanitize` function removes `\r\n` from subject/name/email to prevent header injection. However, `formData.subject` is used both as the email subject AND as the message body. The body section uses the raw `formData.subject` without sanitization: `body=${encodeURIComponent(\`...\n\nMessage:\n${formData.subject}\`)}`. Since `encodeURIComponent` handles special characters, this is actually safe — but the intent is confusing (subject = message).
- **Impact:** None (encodeURIComponent is sufficient), but the naming is misleading.
- **Suggested fix:** Rename `subject` to `message` in the form state to clarify intent.

**[CR-016]** `RecipeCard` module-level `warnedIds` set grows unbounded

- **File:** `src/components/recipe/RecipeCard.tsx:22`
- **Issue:** `const warnedIds = new Set<string>()` at module scope never gets cleared in production. If a user browses thousands of recipes, this set grows indefinitely.
- **Impact:** Minor memory leak in long-running browser sessions.
- **Suggested fix:** Use a bounded cache (e.g., LRU with max 100 entries) or clear on route change.

#### LOW

**[CR-017]** `home page` motion animation doesn't respect reduced motion preference

- **File:** `src/app/page.tsx:37-40`
- **Issue:** The home page uses `motion.div` with `initial`/`animate` without checking `useReducedMotion()`. The about page correctly implements this (line 68), but the home page and several other pages don't.
- **Impact:** Accessibility issue for users with vestibular disorders.
- **Suggested fix:** Add `useReducedMotion()` check like the about page does.

**[CR-018]** `LoadingBar` triggers on every pathname change including same-page navigation

- **File:** `src/components/LoadingBar.tsx:14-19`
- **Issue:** The loading bar shows on every `pathname` or `searchParams` change, even when navigating to the same page (e.g., clicking the current nav item). The 500ms timer hides it, but it still flashes briefly.
- **Impact:** Minor UX annoyance.
- **Suggested fix:** Compare previous and current pathname before showing the bar.

**[CR-019]** Test file imports use `any` type extensively

- **File:** Multiple test files (e.g., `src/components/recipe/__tests__/RecipeFeed.test.tsx:41`)
- **Issue:** `const mockMotion: any = ...` and similar patterns bypass TypeScript's type checking in tests.
- **Impact:** Tests may pass but mask type errors that would occur in production.
- **Suggested fix:** Create proper typed mock utilities.

**[CR-020]** `isCloudinaryUrl` duplicated across two files

- **File:** `src/lib/utils/cloudinary.ts:2` and `src/lib/utils/cloudinary-validation.ts:4`
- **Issue:** Same function `isCloudinaryUrl` defined in two different files with identical implementation.
- **Impact:** Maintenance burden — changes to one won't propagate to the other.
- **Suggested fix:** Export from one file and import in the other.
