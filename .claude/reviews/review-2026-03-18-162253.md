## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Cookie-based auth, Prisma ORM, DI container, comprehensive tests. Several security and data-integrity issues found, most notably an auth cookie misconfiguration and TOCTOU races in pantry routes.

### Findings

#### CRITICAL

**[CR-001]** Auth cookie `SameSite: strict` breaks external navigation

- **File:** `src/lib/utils/cookies.ts:11`
- **Issue:** `sameSite: 'strict'` prevents the auth cookie from being sent on any cross-site navigation — including clicking a link to the app from email, Slack, social media, or search results. Users will appear logged out on first page load from any external source.
- **Impact:** Every user who arrives via an external link sees the logged-out state, then appears logged in after a single internal navigation. Confusing UX, support tickets, potential data loss if users re-login assuming their session expired.
- **Suggested fix:**

```typescript
// src/lib/utils/cookies.ts
sameSite: 'lax', // 'lax' sends cookie on top-level navigations (GET) but blocks cross-site POST
```

**[CR-002]** Pantry item PUT/DELETE routes have TOCTOU race conditions

- **File:** `src/app/api/pantry/[id]/route.ts:25-50` (PUT) and `src/app/api/pantry/[id]/route.ts:100-130` (DELETE)
- **Issue:** Both handlers perform a `findUnique` to check ownership, then a separate `update`/`delete`. Between the check and the mutation, a concurrent request could delete or reassign the item. The cooked-recipes route correctly uses a transaction for similar logic, but pantry routes do not.
- **Impact:** Concurrent requests can cause confusing 500 errors instead of proper 404s. In theory, a timing attack could update an item right after ownership transfers (though no such mechanism exists today, this is fragile by design).
- **Suggested fix:**

```typescript
// Use atomic update with ownership in where clause
const updatedItem = await prisma.pantryItem.updateMany({
  where: { id: itemId, pantry: { userId: payload.userId } },
  data: { ... },
});
if (updatedItem.count === 0) {
  return NextResponse.json({ error: 'Item not found or unauthorized' }, { status: 404 });
}
```

#### HIGH

**[CR-003]** Recipe match endpoint scans only 1000 most recent recipes

- **File:** `src/app/api/recipes/match/route.ts:72-80`
- **Issue:** `take: 1000` with `orderBy: { createdAt: 'desc' }` means older recipes are never considered for matching. As the database grows, high-quality older recipes are permanently excluded from pantry matching.
- **Impact:** Feature degradation at scale. Users with 1001+ recipes in the DB will get incomplete match results with no indication that results are truncated.
- **Suggested fix:** Remove the arbitrary limit and use a database-level ingredient matching approach (e.g., GIN index on ingredients JSONB), or at minimum paginate through all recipes. If a limit is needed for memory, document it and sort by relevance (e.g., `averageRating DESC`) instead of recency.

**[CR-004]** Comment image validation returns 500 when env var missing, blocking all image comments

- **File:** `src/app/api/recipes/[id]/comments/route.ts:113-117`
- **Issue:** If `CLOUDINARY_CLOUD_NAME` is not set, any comment containing an image returns HTTP 500 `"Image upload is currently unavailable"`. The recipe create/update routes return 400 for the same scenario. Inconsistent error handling.
- **Impact:** A missing env var in one environment takes down image-comment functionality silently. The 500 status suggests a server bug rather than a config issue, making debugging harder.
- **Suggested fix:** Validate `CLOUDINARY_CLOUD_NAME` at startup in `env-validation.ts` (add it to required vars), or return 400 consistently:

```typescript
if (!cloudName) {
  return NextResponse.json({ error: 'Image uploads are not configured' }, { status: 400 });
}
```

**[CR-005]** Navigation notification polling doesn't back off on non-401 HTTP errors

- **File:** `src/components/Navigation.tsx:207-213`
- **Issue:** When `response.ok` is false but status is not 401 (e.g., 500, 503), `consecutiveFailuresRef.current++` increments but there's no cap or circuit breaker. The exponential backoff formula `BASE_INTERVAL * 2^failures` is capped at `MAX_INTERVAL` (5 min), but every non-401 failure logs to console. A sustained 500 from the API fills the console and wastes bandwidth polling every 5 minutes indefinitely.
- **Impact:** During API outages, every connected client hammers the notification endpoint every 5 minutes with console.error spam.
- **Suggested fix:** Add a circuit breaker — stop polling after N consecutive failures and only resume on visibility change:

```typescript
if (consecutiveFailuresRef.current >= 10) {
  pollingStoppedRef.current = true;
  return;
}
```

#### MEDIUM

**[CR-006]** Advisory lock uses undocumented magic number

- **File:** `src/app/api/admin/recalc-ratings/route.ts:22`
- **Issue:** `pg_advisory_xact_lock(48879)` — the number `48879` (0xBEEF) is not defined as a constant and has no documentation explaining what it locks or how to avoid collisions with other advisory locks in the system.
- **Impact:** If another developer adds a second advisory lock, they might accidentally reuse this number, causing unexpected serialization. The hex joke obscures the purpose.
- **Suggested fix:**

```typescript
// In src/lib/constants.ts
export const PG_ADVISORY_LOCK_RECALC_RATINGS = 48879;

// In route
await tx.$executeRaw`SELECT pg_advisory_xact_lock(${PG_ADVISORY_LOCK_RECALC_RATINGS})`;
```

**[CR-007]** followers/following endpoints missing total count for pagination

- **File:** `src/app/api/users/[username]/followers/route.ts` and `following/route.ts`
- **Issue:** Both endpoints accept `limit` and `offset` params but never return a `total` count. The client cannot determine if there are more pages to load.
- **Impact:** Infinite scroll or "load more" buttons can't know when to stop. Clients must infer pagination completion from empty responses.
- **Suggested fix:** Add `Promise.all` with a `count` query and return `{ followers, total }`.

**[CR-008]** `RecipeFeed` handles stale like state with optimistic update but no rollback on non-Error exceptions

- **File:** `src/components/recipe/RecipeFeed.tsx:285-330`
- **Issue:** The optimistic like update catches errors and reverts, but the catch block at line 321 only handles `response.ok === false`. If `fetch` itself throws (network error), the catch at line 325 reverts. However, if `response.json()` throws (malformed JSON), the like state is updated from the server but the error snackbar fires with the stale optimistic state already applied.
- **Impact:** Edge case: corrupted API response leaves the UI in an inconsistent like state.
- **Suggested fix:** Move the `setRecipeLikes` server update inside a try-catch that reverts on any JSON parse failure.

**[CR-009]** `unfollow` route doesn't validate self-unfollow

- **File:** `src/app/api/users/[username]/unfollow/route.ts`
- **Issue:** The `follow` route correctly checks `userToFollow.id === payload.userId` and returns 400 "Cannot follow yourself". The `unfollow` route has no such check. While self-unfollowing is a no-op (the follow record wouldn't exist), the inconsistency means the API returns "Not following this user" instead of a more descriptive "Cannot unfollow yourself".
- **Impact:** Inconsistent API behavior. Minor UX issue if a client bug triggers self-unfollow.
- **Suggested fix:** Add the same guard to the unfollow route.

**[CR-011]** `techStack` array in about page is a hardcoded list that could drift from actual dependencies

- **File:** `src/app/about/page.tsx:73-81`
- **Issue:** The tech stack display (`['Next.js', 'React', 'TypeScript', ...]`) is manually maintained and doesn't include actually-used technologies like Sentry, Cloudinary, Serwist/PWA, React Query, Zod.
- **Impact:** Marketing page shows inaccurate tech stack to users.
- **Suggested fix:** Either generate from `package.json` or keep the list updated. Add missing entries.

**[CR-012]** Multiple `console.error` calls in production API routes

- **File:** Multiple API routes (e.g., `src/app/api/recipes/[id]/route.ts:154`, `src/app/api/cooked-recipes/route.ts:184`)
- **Issue:** Production error logging goes to `console.error` rather than a structured logger. Sentry is configured for client errors but server-side API errors rely on console output.
- **Impact:** In serverless environments, console logs are ephemeral and hard to search. Error details may be lost. Sentry captures unhandled exceptions but these are handled (caught) errors that only log to console.
- **Suggested fix:** Use `Sentry.captureException(error)` for server-side caught errors, or integrate a structured logger (e.g., pino) that outputs JSON for log aggregation.
