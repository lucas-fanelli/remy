## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. The codebase is structurally solid but contains a scoping bug that silently breaks comment notifications, a public endpoint leaking user emails, and a CSRF bypass via `multipart/form-data` content type.

### Findings

#### CRITICAL

**[CR-001]** `recipe` variable used out of scope — comment notifications silently broken

- **File:** `src/app/api/recipes/[id]/comments/route.ts:139`
- **Issue:** The `recipe` variable is declared inside the `$transaction` callback scope but referenced outside it when creating the notification. This throws `ReferenceError: recipe is not defined`, which is swallowed by the `try/catch`, so comment notifications **never fire**.
- **Impact:** No users receive notifications when someone comments on their recipe. Silent data loss of notification events.
- **Suggested fix:**

```typescript
// Return recipe userId from the transaction alongside the comment
const { comment, recipeAuthorId } = await prisma.$transaction(async (tx) => {
  const recipe = await tx.post.findUnique({ where: { id: recipeId } });
  if (!recipe) throw new Error('RECIPE_NOT_FOUND');
  // ... existing comment/rating logic ...
  return { comment: newComment, recipeAuthorId: recipe.userId };
});

// Now use recipeAuthorId instead of recipe.userId
await notificationService.createCommentNotification(
  payload.userId,
  recipeId,
  recipeAuthorId,
  comment.id
);
```

**[CR-002]** CSRF protection bypassed by `multipart/form-data`

- **File:** `src/middleware.ts:118`
- **Issue:** The CSRF check treats `multipart/form-data` content-type as a "custom header", but it is a simple content type that browsers send with standard `<form enctype="multipart/form-data">` submissions. A cross-origin form can target any state-changing API endpoint with this content type. On older browsers that don't enforce `SameSite=strict` or send `Sec-Fetch-Site`, this is exploitable.
- **Impact:** Cross-site request forgery on all POST/PUT/PATCH/DELETE API endpoints for users on older browsers.
- **Suggested fix:**

```typescript
const hasCustomHeader =
  isSameOrigin ||
  (contentType && contentType.includes('application/json')) || // remove multipart/form-data
  request.headers.has('authorization') ||
  request.headers.has('x-requested-with');
```

For file upload endpoints that legitimately use multipart, require an additional header (e.g., `X-Requested-With`) from the client.

#### HIGH

**[CR-003]** Public API endpoint leaks user email addresses

- **File:** `src/app/api/users/[username]/route.ts:18`
- **Issue:** `getUserByUsername` returns `UserPublicProfile` which is `Omit<User, 'password'>` — it still includes `email`. The response sends this directly to any anonymous caller.
- **Impact:** Any user's email is exposed to unauthenticated requests via `GET /api/users/{username}`. Enables spam, phishing, and account enumeration.
- **Suggested fix:**

```typescript
const { email, ...publicUser } = user;
return ApiResponseHelper.success({ user: publicUser });
```

**[CR-004]** Race condition — recipe existence check outside transaction in like toggle

- **File:** `src/app/api/recipes/[id]/like/route.ts:27-31`
- **Issue:** The recipe existence check (`prisma.post.findUnique`) runs before the transaction. If the recipe is deleted between the check and the transaction's `like.create`, a foreign key constraint violation occurs, returning an opaque 500 error instead of 404.
- **Impact:** Intermittent 500 errors on like/unlike when recipes are deleted concurrently.
- **Suggested fix:** Move the recipe existence check inside the transaction:

```typescript
const result = await prisma.$transaction(async (tx) => {
  const recipe = await tx.post.findUnique({ where: { id: recipeId } });
  if (!recipe) throw new Error('RECIPE_NOT_FOUND');
  // ... existing toggle logic ...
});
```

**[CR-005]** Avatar URL not validated on profile update — allows arbitrary external URLs

- **File:** `src/app/api/users/profile/route.ts:22-30`
- **Issue:** The `updateProfileSchema` accepts any string for `avatar`. Unlike recipe image URLs which are validated against Cloudinary, avatar URLs via the profile PUT endpoint have no server-side URL validation. A direct API call can set the avatar to any external URL.
- **Impact:** Stored tracking pixels, potential SSRF if avatars are ever server-side fetched, and abuse of the platform to host redirects.
- **Suggested fix:** Add Cloudinary URL validation for avatar in the PUT handler, matching what `/api/upload/avatar` produces:

```typescript
if (validatedData.avatar && validatedData.avatar !== user.avatar) {
  const url = new URL(validatedData.avatar);
  const cloudName = process.env.CLOUDINARY_CLOUD_NAME;
  if (
    !cloudName ||
    url.hostname !== 'res.cloudinary.com' ||
    !url.pathname.startsWith(`/${cloudName}/`)
  ) {
    return ApiResponseHelper.badRequest('Avatar must be uploaded through the app');
  }
}
```

#### MEDIUM

**[CR-006]** Upload size limit hardcoded in multiple files instead of using constant

- **Files:** `src/app/api/upload/route.ts:42`, `src/app/api/upload/avatar/route.ts:48`, `src/components/common/ImageUpload.tsx:34`
- **Issue:** The 5MB limit is hardcoded as `5 * 1024 * 1024` in three separate locations while `MAX_UPLOAD_SIZE` exists in `src/lib/constants.ts`.
- **Impact:** If the limit needs to change, it must be updated in multiple files, risking inconsistency.
- **Suggested fix:** Import and use `MAX_UPLOAD_SIZE` from `@/lib/constants` in all three files.

**[CR-007]** Same-recipe save toggle has unnecessary try/catch for `Record to delete does not exist`

- **File:** `src/app/api/recipes/[id]/save/route.ts:72-77`
- **Issue:** Inside a serializable transaction, the code catches `Record to delete does not exist` from `savedRecipe.delete`. But since `existingSave` was just found in the same transaction, this condition is unreachable — it's dead code that obscures the actual logic.
- **Impact:** Misleading error handling; developers may assume concurrent issues are handled when they aren't (the transaction isolation handles it).
- **Suggested fix:** Remove the inner try/catch blocks. The transaction already provides atomicity.

**[CR-008]** `loadProfile` dependency array includes `isAuthenticated` but callback doesn't reference it

- **File:** `src/app/profile/[username]/page.tsx:112`
- **Issue:** `isAuthenticated` is in the `useCallback` dependency array but is not used in the callback body. Cookies are sent automatically. This causes an unnecessary profile refetch when auth state changes.
- **Impact:** Extra network request and potential UI flicker on login/logout while viewing a profile.
- **Suggested fix:** Remove `isAuthenticated` from the dependency array. The cookie-based auth means the server sees the auth state regardless.

**[CR-009]** No total count returned from comments GET endpoint

- **File:** `src/app/api/recipes/[id]/comments/route.ts:39`
- **Issue:** The GET endpoint returns `{ comments }` but no `total` count, making it impossible for clients to implement pagination indicators or "load more" UI correctly.
- **Impact:** Clients cannot determine if more comments exist beyond the current page.
- **Suggested fix:** Add a parallel `prisma.comment.count({ where: { postId: recipeId } })` and include `total` in the response.

**[CR-010]** Notification polling defensive check for `undefined` response masks real bugs

- **File:** `src/components/Navigation.tsx:177-179`
- **Issue:** `if (!response) { return; }` after `fetch()` is unreachable in production — `fetch` always returns a Response or throws. The comment says it's for tests. This is a test smell that papers over improperly mocked tests.
- **Impact:** If `fetch` is improperly mocked in production (e.g., a service worker interceptor returns undefined), this silently drops the error instead of surfacing it.
- **Suggested fix:** Remove the check. Fix test mocks to always return proper Response objects.

#### LOW

**[CR-011]** `techStack` array in about page will go stale

- **File:** `src/app/about/page.tsx:66-74`
- **Issue:** The tech stack is hardcoded as a string array. It doesn't include Serwist (used for PWA), Cloudinary (used for uploads), Sentry (used for error tracking), or Zod (used for validation).
- **Impact:** Inaccurate public-facing information.
- **Suggested fix:** Either keep it current or derive it from `package.json` dependencies.

**[CR-012]** `recipe.title` in `RecipeCard` image `onError` uses dataset to prevent infinite loop, but `alt` text could be XSS if title is user-controlled

- **File:** `src/components/recipe/RecipeCard.tsx:120-125`
- **Issue:** The `alt` attribute uses `recipe.title` which is user-provided. While React escapes `alt` values in JSX, the `onError` handler modifies the DOM directly. The pattern is safe but fragile.
- **Impact:** No current vulnerability, but worth noting for future DOM manipulation.
- **Suggested fix:** No action needed, but add a comment noting the safety relies on React's JSX escaping.
