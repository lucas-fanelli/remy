## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes, middleware, and client components.

### Findings

#### CRITICAL

**[CR-001]** Logout endpoint CSRF protection is bypassable

- **File:** `src/app/api/auth/logout/route.ts:8-10`
- **Issue:** The logout route only checks `Content-Type` header but does NOT verify `Sec-Fetch-Site` or `X-Requested-With`. The middleware CSRF check runs before route handlers, but the comment claims CSRF is handled by middleware while the logout endpoint also does its own Content-Type check — creating a confusing dual-validation. More critically, the `POST /api/notifications` (mark-all-read) endpoint has NO Content-Type check and no `requireJsonContentType` call, so the middleware's `application/json` check is the only defense.
- **Impact:** A cross-origin form POST with `Content-Type: application/json` could mark all notifications as read. Modern browsers do add CORS preflight for `application/json`, but older or non-standard clients may not.
- **Suggested fix:** Add `requireJsonContentType` to the notifications POST handler, or at minimum add a comment explaining the middleware dependency.

**[CR-002]** Recipe match endpoint has no rate limiting for expensive DB queries

- **File:** `src/app/api/recipes/match/route.ts:48-50`
- **Issue:** The comment acknowledges this: "consider adding per-user rate limiting". The endpoint runs a `jsonb_array_elements` join across potentially all posts, plus two follow-up batch queries. The middleware only rate-limits write operations per user; GET requests use only IP-based rate limiting (100/15min shared across ALL API calls). An authenticated user can hammer this endpoint.
- **Impact:** A single user can cause significant DB load with repeated requests, potentially degrading service for all users.
- **Suggested fix:** Add per-user GET rate limiting for this endpoint, or cache results with a short TTL (e.g., 60s) keyed on userId.

**[CR-003]** Admin user deletion race condition — `LAST_ADMIN` check is incomplete

- **File:** `src/app/api/admin/users/[id]/route.ts:38-44`
- **Issue:** The `FOR UPDATE` lock on the admin count query prevents two concurrent deletions from both passing, which is good. However, the `SELECT role FROM "User" WHERE id = ${id} FOR UPDATE` can return undefined if the user doesn't exist, and `userToDelete?.role` silently skips the admin count check for non-existent users — the delete will then fail with P2025 which is handled, but the LAST_ADMIN path is never reached. More importantly, the raw query uses template literals with Prisma's `$queryRaw` but the `bigint` cast `::int` in the count query will overflow if there are somehow >2B admins (pedantic but the cast is unnecessary).
- **Impact:** Low practical impact due to P2025 handling, but the logic flow is confusing and could mask bugs in future refactoring.
- **Suggested fix:** Add explicit `if (!userToDelete) throw new Error('USER_NOT_FOUND')` before the role check.

**[CR-004]** `cooked-recipes` POST does not validate `Content-Type` on `force` parameter

- **File:** `src/app/api/cooked-recipes/route.ts:76`
- **Issue:** The `force` field from the request body is compared directly with `!== true`. If a client sends `force: "true"` (string), it won't match, which is actually correct behavior but inconsistent with the API's lack of schema validation. More critically, the `rating` field has type checking but `notes` only checks length after a `typeof` check — if `notes` is a number, it passes the `!== undefined && !== null` check but fails silently on `.length`.
- **Impact:** Malformed requests could produce unexpected behavior or bypass intended validation.
- **Suggested fix:** Use Zod schema validation for the entire request body instead of manual field-by-field checks.

#### HIGH

**[CR-005]** Notification polling circuit breaker auto-recovers but never clears stale state

- **File:** `src/hooks/useNotificationPolling.ts:126-130`
- **Issue:** When the circuit breaker trips (10 failures in 10 min), it sets `breakerTrippedAtRef`. After 5 minutes, `scheduleNext` resets `pollingStoppedRef` and clears `failureTimestampsRef`. However, `isPollingPaused` state is set to `false` via `setIsPollingPaused(false)` inside `scheduleNext`, but if the component re-renders between the trip and recovery, the UI shows "paused" even though polling may have silently resumed. The `failureTimestampsRef` is cleared on reset but not after a single successful fetch in the recovery window — if recovery fails immediately, it starts counting from 0 again, giving 10 more tries before re-tripping.
- **Impact:** Inconsistent UI state; potential for rapid-fire requests during recovery attempts.
- **Suggested fix:** Centralize the breaker state reset in `fetchNotifications` on success, and ensure `setIsPollingPaused(false)` is called only after a confirmed successful fetch.

**[CR-006]** `RecipeFeed` infinite scroll has no duplicate prevention during rapid filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:131-170`
- **Issue:** When filters change, `loadRecipes(true)` is called which increments `generationRef`. However, the `generationRef` check on line 156 (`if (currentGeneration !== generationRef.current) return`) only prevents stale responses from being applied — it doesn't prevent the aborted request's `finally` block from clearing `loadingRef.current` before the new request completes. The `abortControllerRef.current === controller` check in `finally` mitigates this, but there's a brief window where both `loadingRef.current` is true AND a new request hasn't yet been dispatched.
- **Impact:** Under rapid filter changes, users could see flash of empty content or duplicate recipe cards.
- **Suggested fix:** The current implementation is mostly correct but would benefit from moving the abort+reset logic into a single synchronous block at the start of `loadRecipes`.

**[CR-007]** `EditProfileModal` avatar upload doesn't validate magic bytes client-side before upload

- **File:** `src/components/profile/EditProfileModal.tsx:84-102`
- **Issue:** The modal validates magic bytes client-side (good), but the validation reads only the first 12 bytes via `file.slice(0, 12)`. For WebP, this is sufficient, but the check happens asynchronously — if the FileReader `onerror` fires, the error is silently swallowed via `reject` which propagates to the promise but is never caught in `handleAvatarChange`. The `e.target.value = ''` on error is correct but the user gets no error feedback.
- **Impact:** Silent failure on corrupted files; user sees no indication of why the file wasn't accepted.
- **Suggested fix:** Wrap the `readAsArrayBuffer` promise in a try/catch in `handleAvatarChange` and call `showError('Failed to read file')`.

**[CR-008]** Search endpoint exposes recipe data without privacy checks

- **File:** `src/app/api/search/route.ts:41-65`
- **Issue:** The search endpoint returns recipes from all users, including those with `isPrivate: true` profiles. While recipes themselves aren't private (only the profile is), the search results include the author's username and avatar, allowing enumeration of private users' content.
- **Impact:** Private profile users' recipes are discoverable via search, partially defeating the purpose of profile privacy.
- **Suggested fix:** Either filter out recipes from private profiles in search results, or document that recipe privacy is separate from profile privacy.

**[CR-009]** `handleMarkAsCooked` doesn't handle `force` flow

- **File:** `src/app/recipe/[id]/page.tsx:289-323`
- **Issue:** When the API returns a 409 with `insufficientIngredients`, the client shows an error but never offers to retry with `force: true`. The API supports this flow, but the UI doesn't implement it.
- **Impact:** Users with insufficient pantry ingredients cannot mark recipes as cooked from the recipe detail page.
- **Suggested fix:** Show a confirmation dialog with the insufficient ingredients list and a "Cook anyway" button that re-sends with `force: true`.

#### MEDIUM

**[CR-010]** `normalizeIngredientName` exception list is large but not comprehensive

- **File:** `src/lib/utils/ingredients.ts:18-32`
- **Issue:** The `noStripSuffixWords` set contains ~80 hardcoded exceptions. Any new ingredient not in this list that ends in 's' will be incorrectly stemmed. For example, "hummus" is in the list, but "couscous" appears twice (duplicate entry). Also, "lemongrass" is in the list but "crabgrass" or any new compound word ending in 's' would be stripped.
- **Impact:** Incorrect ingredient matching for unlisted ingredients ending in 's'.
- **Suggested fix:** Remove the duplicate "couscous" entry. Consider a more robust stemming approach or at minimum add a comment warning about the maintenance burden.

**[CR-011]** `PersistentSearchBar` fires search on every route change

- **File:** `src/components/search/PersistentSearchBar.tsx:115-147`
- **Issue:** The debounced search effect depends on `query` state. However, the `pathname` change triggers a re-render via `usePathname()`, and the `AnimatePresence` with `key={pathname}` remounts the inner content. If the user has typed a query and navigates, the search effect may re-fire with the stale query.
- **Impact:** Unnecessary API calls on navigation when search bar has text.
- **Suggested fix:** Clear the `query` state on pathname change, or skip the search effect when the component is not focused.

**[CR-012]** Admin pages use `useTheme()` directly instead of MUI's `sx` theme callback

- **File:** `src/app/admin/comments/page.tsx:111`, `src/app/admin/recipes/page.tsx:121`, `src/app/admin/users/page.tsx:148`
- **Issue:** All admin pages call `useTheme()` and reference `theme.palette.background.default` in `sx` props. This works but creates an unnecessary hook dependency. The `sx` prop already supports theme callback syntax `(theme) => ...` which avoids the extra render.
- **Impact:** Minor performance waste; extra re-renders when theme changes.
- **Suggested fix:** Replace `backgroundColor: theme.palette.background.default` with `backgroundColor: 'background.default'` (MUI shorthand) or use the `sx` theme callback.

**[CR-013]** `RecipeCard` warning set grows unboundedly

- **File:** `src/components/recipe/RecipeCard.tsx:57-60`
- **Issue:** `warnedRecipeImages` is a module-level `Set<string>` that accumulates recipe IDs across the app's lifetime. In a long-running session with many recipes, this set grows without bound.
- **Impact:** Memory leak in long-running browser sessions.
- **Suggested fix:** Use a bounded LRU set or clear it periodically.

**[CR-014]** Missing `Content-Type` validation on `POST /api/recipes/suggest`

- **File:** `src/app/api/recipes/suggest/route.ts:12`
- **Issue:** This POST endpoint parses JSON from `request.json()` but doesn't call `requireJsonContentType`. Other POST endpoints consistently validate Content-Type.
- **Impact:** Inconsistent API behavior; could accept non-JSON content types.
- **Suggested fix:** Add `const ctError = requireJsonContentType(request); if (ctError) return ctError;`

**[CR-015]** `useAuth` logout retry swallows non-network errors

- **File:** `src/contexts/AuthContext.tsx:93-107`
- **Issue:** The logout retry loop catches all errors and only warns on the second attempt. If the server returns a 500 (bug), the client retries once and then gives up, dispatching `auth:logout-failed`. The user sees a warning but the cookie remains, and the next page load will re-authenticate them.
- **Impact:** Failed logouts can leave users in a confused auth state.
- **Suggested fix:** On permanent failure, additionally clear the cookie client-side via `document.cookie` as a last resort (won't work for httpOnly, but at least log the specific error status for debugging).

**[CR-018]** `isCloudinaryUrl` check is duplicated across 3 files

- **Impact:** Maintenance burden; risk of inconsistency.
