## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing application with clean architecture (DI container, repository pattern, domain services). Generally well-structured with good security hardening (CSP, CSRF, rate limiting, httpOnly cookies). However, inconsistent auth patterns across API routes, incomplete HTML sanitization coverage, and several type/validation gaps exist.

### Findings

#### CRITICAL

**[CR-001]** Incomplete HTML sanitization — XSS vector in stored fields

- **File:** `src/infrastructure/services/RecipeService.ts:19-21`
- **Issue:** `stripHtml` is applied only to `title` and `description` during create/update. `caption`, ingredient `name`, and instruction `description` are stored unsanitized. If any downstream consumer renders these without escaping (email notifications, RSS feeds, SSR meta tags), stored XSS is possible.
- **Impact:** Stored XSS if any future rendering context doesn't escape output. Defense-in-depth violation.
- **Suggested fix:**

```typescript
async createRecipe(data: CreateRecipeDTO): Promise<Recipe> {
  if (data.title) data.title = this.stripHtml(data.title);
  if (data.description) data.description = this.stripHtml(data.description);
  if (data.caption) data.caption = this.stripHtml(data.caption);
  if (data.ingredients) {
    data.ingredients = data.ingredients.map(i => ({
      ...i, name: this.stripHtml(i.name)
    }));
  }
  if (data.instructions) {
    data.instructions = data.instructions.map(i => ({
      ...i, description: this.stripHtml(i.description)
    }));
  }
  // ... same for updateRecipe
```

**[CR-002]** `stripHtml` regex is bypassable

- **File:** `src/infrastructure/services/RecipeService.ts:17-19`
- **Issue:** `/<[^>]*>?/g` fails on edge cases like `<svg/onload=alert(1)>`, nested/malformed tags, or HTML entities. Regex-based HTML stripping is a known anti-pattern for security.
- **Impact:** Sanitization can be bypassed with crafted input.
- **Suggested fix:** Use a proper sanitization library like `sanitize-html` or `DOMPurify` (server-side via `jsdom`), or at minimum use a stricter approach that also strips event handler attributes and known dangerous patterns.

#### HIGH

**[CR-003]** Inconsistent auth pattern — most routes bypass `requireAuth` helper

- **Files:** `src/app/api/cooked-recipes/route.ts`, `src/app/api/pantry/route.ts`, `src/app/api/recipes/[id]/like/route.ts`, `src/app/api/recipes/[id]/save/route.ts`, `src/app/api/notifications/route.ts`, and ~15 more
- **Issue:** Most API routes manually call `extractAuthToken` + `tokenService.verify` instead of using the centralized `requireAuth` from `src/lib/api/auth.ts`. If auth logic changes (e.g., token rotation, session invalidation), every route must be updated independently.
- **Impact:** Auth logic fragmentation. A change to auth validation requires touching 20+ files. Risk of inconsistent behavior across routes.
- **Suggested fix:** Refactor all authenticated routes to use `requireAuth(request)` which already handles token extraction, verification, and error responses. Only 4 routes currently use it (`change-password`, `me`, `profile PUT/DELETE`).

**[CR-004]** `cooked-recipes/route.ts` POST handler is 200+ lines with mixed concerns

- **File:** `src/app/api/cooked-recipes/route.ts:72-230`
- **Issue:** Single function handles auth, validation, Zod parsing, pantry deduction planning, insufficient ingredient detection, advisory locking, pantry mutation, and cooked recipe creation. This violates SRP and makes the code difficult to test, review, and maintain.
- **Impact:** High cognitive load, difficult to unit test individual behaviors, high change risk.
- **Suggested fix:** Extract into a `CookedRecipeService` with methods like `markAsCooked(userId, postId, options)` that encapsulates the transaction logic. The route handler should only handle HTTP concerns.

**[CR-005]** Type mismatch in admin user deletion query

- **File:** `src/app/api/admin/users/[id]/route.ts:43`
- **Issue:** TypeScript type says `{ count: bigint }` but SQL casts with `COUNT(*)::int`. Prisma maps PostgreSQL `int` to JavaScript `number`, not `bigint`. The `Number(count)` call works either way, but the type annotation is incorrect.
- **Impact:** Type system lies about the actual runtime type. Could cause bugs if someone removes the `Number()` wrapper trusting the `bigint` annotation.
- **Suggested fix:**

```typescript
const [{ count }] = await tx.$queryRaw<[{ count: number }]>`
  SELECT COUNT(*)::int as count FROM "User" WHERE role = 'ADMIN' FOR UPDATE
`;
if (count <= 1) throw new Error('LAST_ADMIN');
```

**[CR-006]** GET `/api/recipes/[id]` doesn't validate UUID format

- **File:** `src/app/api/recipes/[id]/route.ts:19-31`
- **Issue:** The GET handler passes the `id` directly to `recipeService.getRecipeById(id)` without UUID validation. PUT and DELETE on the same route validate with `UUID_REGEX`. Malformed IDs will hit the database unnecessarily.
- **Impact:** Unnecessary database queries for malformed IDs; inconsistency with sibling methods.
- **Suggested fix:**

```typescript
export async function GET(request: NextRequest, { params }: { params: Promise<{ id: string }> }) {
  try {
    const { id } = await params;
    if (!UUID_REGEX.test(id)) {
      return NextResponse.json({ error: 'Invalid ID format' }, { status: 400 });
    }
    // ...
```

#### MEDIUM

**[CR-007]** Empty string website bypasses URL validation

- **File:** `src/lib/validation/schemas.ts:49-64` and `src/infrastructure/services/UserService.ts:35`
- **Issue:** The `updateProfileSchema` allows empty string via `.or(z.literal(''))`. In `UserService.updateProfile`, `if (data.website)` is falsy for empty string, so URL validation is skipped. An empty string is stored in the DB instead of `null`.
- **Impact:** Inconsistent data — some profiles have `website: ""` and others have `website: null` for "no website". Frontend code checking `profile.website && ...` would render an empty link.
- **Suggested fix:** Transform empty string to `null` in the schema:

```typescript
website: z.string().url().refine(/* ... */)
  .or(z.literal(''))
  .nullable()
  .optional()
  .transform(v => v === '' ? null : v),
```

**[CR-008]** Recipe match endpoint hardcoded to 200 candidate limit

- **File:** `src/app/api/recipes/match/route.ts:78,93`
- **Issue:** `LIMIT 200` caps the candidate set. As the recipe database grows beyond a few hundred, relevant matches will be silently dropped. No pagination or cursor-based approach exists.
- **Impact:** Users with well-stocked pantries may miss matching recipes as the platform grows.
- **Suggested fix:** Make the limit configurable via query parameter (with a max cap), or implement a two-phase approach: first get IDs via the GIN index query without limit, then batch-fetch full data.

**[CR-009]** Notification polling circuit breaker has no user-visible recovery action

- **File:** `src/hooks/useNotificationPolling.ts:107-110`
- **Issue:** When 10+ failures occur in 10 minutes, the circuit breaker trips and `isPollingPaused` is set to `true`. The only recovery is a 5-minute automatic cooldown. The Navigation UI shows a tooltip ("Notifications temporarily paused") but provides no manual retry button.
- **Impact:** Users may not receive notifications for 5+ minutes with no way to recover other than refreshing the page.
- **Suggested fix:** Expose a `retryNow` function that resets the breaker and immediately fetches. Add a clickable element in the UI when `isPollingPaused` is true.

**[CR-010]** Client-side file preview generates base64 from full ArrayBuffer

- **File:** `src/components/profile/EditProfileModal.tsx:91-100`
- **Issue:** The avatar preview reads the entire file into an `ArrayBuffer`, then converts to base64 via `String.fromCharCode` + `btoa`. For files near the 5MB limit, this creates a ~6.7MB base64 string in memory and uses synchronous string operations.
- **Impact:** UI jank on lower-end devices when selecting large avatar images.
- **Suggested fix:** Use `URL.createObjectURL(file)` for the preview instead of base64 conversion:

```typescript
setAvatarPreview(URL.createObjectURL(file));
// Clean up in useEffect return: URL.revokeObjectURL(avatarPreview)
```

**[CR-011]** `DELETE /api/cooked-recipes` uses query parameter instead of path parameter

- **File:** `src/app/api/cooked-recipes/route.ts:251-253`
- **Issue:** `DELETE /api/cooked-recipes?id=<uuid>` takes the ID from search params. REST convention for resource deletion is `DELETE /api/cooked-recipes/<id>`.
- **Impact:** Non-standard API design; confusing for API consumers.
- **Suggested fix:** Move to `DELETE /api/cooked-recipes/[id]/route.ts` with path parameter.

#### LOW

**[CR-012]** Inconsistent error logging — mix of `console.error`, `console.warn`, and `logServerError`

- **Files:** `src/app/api/admin/recipes/[id]/route.ts:39` (`console.warn`), `src/app/api/recipes/[id]/comments/route.ts:129` (`console.warn`), `src/components/recipe/CommentsSection.tsx` (`console.error`), vs routes using `logServerError`
- **Issue:** Some server-side error logging uses raw `console.warn`/`console.error` while others use the centralized `logServerError` utility that integrates with Sentry.
- **Impact:** Errors logged via `console` won't reach Sentry monitoring.
- **Suggested fix:** Replace all server-side `console.warn`/`console.error` for operational errors with `logServerError`.

**[CR-013]** `about/page.tsx` animation delays not gated by `useReducedMotion`

- **File:** `src/app/about/page.tsx:76-82`
- **Issue:** Multiple `MotionBox`/`MotionPaper` components with `initial={{ opacity: 0, y: 20 }}` animations. These are not gated by a reduced-motion preference check.
- **Impact:** Users with `prefers-reduced-motion` enabled still see animations, which is an accessibility concern.
- **Suggested fix:** Use framer-motion's `useReducedMotion` hook or the `MotionContext` already present in the codebase to conditionally disable animations.

**[CR-014]** `RecipeCard` renders dev-only warning on every mount

- **File:** `src/components/recipe/RecipeCard.tsx:67-70`
- **Issue:** The `useEffect` that warns about non-Cloudinary URLs runs on every mount in development. For the recipe feed with 12+ cards, this produces noisy console output.
- **Impact:** Console noise in development; no production impact.
- **Suggested fix:** Move the check to a one-time validation utility or use a `Set` to deduplicate warnings per recipe ID.
