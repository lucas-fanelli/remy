## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured, but contains several security gaps in the middleware CSRF logic, a data-loss race condition in pantry deduction, missing authorization on sensitive endpoints, and inconsistent error handling patterns.

### Findings

#### CRITICAL

**[CR-001]** Middleware CSRF check is bypassable via `Authorization` header

- **File:** `src/middleware.ts:186-193`
- **Issue:** The CSRF check considers a request safe if it has an `authorization` header. But `Authorization` is a "simple" header when its value is a valid token format — an attacker who steals or guesses a token (or uses a leaked one) can forge cross-site POST requests that pass this check. More critically, the `authorization` check is redundant with cookie auth: the cookie is always sent, so the `Authorization` header shouldn't count as CSRF evidence.
- **Impact:** Cross-site state-changing requests possible for authenticated users if any token is exposed.
- **Suggested fix:** Remove `request.headers.has('authorization')` from the CSRF check. Rely only on `Sec-Fetch-Site` and `Content-Type: application/json` (which is not a "simple" content type and triggers CORS preflight).

**[CR-002]** Recipe match endpoint has no pagination guard on candidate fetching

- **File:** `src/app/api/recipes/match/route.ts:89-96`
- **Issue:** The `LIMIT 500` raw SQL cap prevents unbounded queries, but `candidateIds` are then used in a `WHERE id IN (...)` clause with up to 500 UUIDs. If the pantry has many items with short names, the fallback path fetches 500 recipes sorted by `averageRating` — this scans the entire `Post` table without the GIN index benefit.
- **Impact:** Slow queries under load; potential database timeouts on large datasets.
- **Suggested fix:** Add `LIMIT 200` to the fallback query and ensure a composite index on `(averageRating DESC, id)` exists.

**[CR-003]** Cooked recipe pantry deduction has no unit conversion, silently deducts wrong amounts

- **File:** `src/app/api/cooked-recipes/route.ts:117-145`
- **Issue:** `unitsMatch()` uses exact normalized unit comparison. If a pantry item is in "kg" and the recipe calls for "g", no deduction happens (correct). But if both are "g" and the pantry has 100g while the recipe needs 500g, it checks `pantryQuantity >= recipeAmount` and skips deduction silently — the user gets no feedback that their pantry didn't have enough.
- **Impact:** Users think ingredients were deducted when they weren't, leading to stale pantry data.
- **Suggested fix:** Return `insufficientIngredients` in the response so the client can display which items couldn't be deducted.

**[CR-004]** `SameSite: lax` on auth cookie, but middleware comment says `strict`

- **File:** `src/lib/utils/cookies.ts:12` vs `src/middleware.ts:166`
- **Issue:** The cookie is set with `sameSite: 'lax'`, but the middleware CSRF comment says "Layer 1: SameSite: strict cookie". `lax` sends cookies on top-level GET navigations from external sites, which means a malicious link like `<a href="https://app.com/api/auth/logout">click</a>` would include the cookie. The logout endpoint does accept POST only, but other GET endpoints that return sensitive data would be exposed.
- **Impact:** Documentation mismatch creates false confidence. Any future GET endpoint that mutates state would be vulnerable.
- **Suggested fix:** Either change to `sameSite: 'strict'` (breaking OAuth/email flows) or fix the comment to accurately say `lax` and document the implications.

#### HIGH

**[CR-005]** No rate limiting on notification polling endpoint

- **File:** `src/app/api/notifications/route.ts` + `src/middleware.ts`
- **Issue:** The notifications GET endpoint is polled every 60s per user. The middleware rate limit is 100 requests per 15 minutes per IP. A single user polling every 60s only uses ~15 requests in 15 minutes, but if multiple users share an IP (corporate NAT, VPN), they'll collectively hit the limit and get 429s on legitimate requests.
- **Impact:** Legitimate users behind shared IPs get rate-limited by notification polling from other users.
- **Suggested fix:** Exempt `/api/notifications` GET from the global IP rate limit, or use per-user rate limiting (already implemented for writes) for reads too.

**[CR-006]** Admin recipe delete doesn't clean up Cloudinary images

- **File:** `src/app/api/admin/recipes/[id]/route.ts:18-38`
- **Issue:** When an admin deletes a recipe, it calls `adminService.deleteRecipe(id)` which only deletes the database record. The regular user delete in `src/app/api/recipes/[id]/route.ts:130-143` has Cloudinary cleanup logic, but the admin endpoint doesn't.
- **Impact:** Orphaned images accumulate in Cloudinary, increasing storage costs.
- **Suggested fix:** Extract the Cloudinary cleanup into a shared function and call it from both delete endpoints.

**[CR-007]** `useNotificationPolling` circuit breaker resets on visibility change without verifying server health

- **File:** `src/hooks/useNotificationPolling.ts:131-137`
- **Issue:** When the tab regains visibility, if 2+ minutes have passed since the last failure, the circuit breaker resets and immediately fires a fetch. If the server is still down, this creates a thundering herd when many users return to their tabs simultaneously.
- **Impact:** Server recovery is delayed by a burst of notification requests from all returning users.
- **Suggested fix:** Add jitter to the visibility-change fetch, or only reset the breaker after a successful fetch rather than on time alone.

**[CR-008]** `extractBearerToken` falls back to Authorization header, creating dual-auth confusion

- **File:** `src/lib/utils/auth.ts:8-21`
- **Issue:** Cookie takes precedence, but if the cookie is absent, the Bearer header is used. This means a request can be authenticated via header even after the user has "logged out" (cookie cleared) if they still have a valid JWT in their app state. The comment says "used during login/register before cookie is set" but there's no mechanism preventing it from being used anytime.
- **Impact:** Logout doesn't fully invalidate authentication; tokens remain valid until expiry.
- **Suggested fix:** After cookie migration is complete, remove the Authorization header fallback, or implement a token blocklist on logout.

#### MEDIUM

**[CR-009]** Search API uses `LIKE` with user-controlled input — no input sanitization for special characters

- **File:** `src/app/api/recipes/match/route.ts:78`
- **Issue:** `escapeLike` handles `%`, `_`, and `\`, but the Prisma `contains` mode in other search endpoints (`/api/recipes/route.ts:38`, `/api/search/route.ts:48`) passes user input directly to `contains` without escaping. Prisma's `contains` auto-escapes for the ORM layer, but the raw SQL in `match/route.ts` does manual escaping — inconsistent approach.
- **Impact:** Not a SQL injection (Prisma parameterizes), but a user searching for `%` in the non-raw endpoints would match all records, causing unexpected results and potential performance issues.
- **Suggested fix:** Standardize: either always escape special chars before passing to `contains`, or document that Prisma handles it.

**[CR-010]** `RecipeFeed` uses mutable ref for abort controller but doesn't abort on filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:115-118`
- **Issue:** `abortControllerRef.current?.abort()` is called at the start of `loadRecipes`, but between a filter change triggering `useEffect` and `loadRecipes` being called, the `loadingRef.current` guard may prevent the abort from being reached if a previous request is still in flight.
- **Impact:** Stale responses from the previous filter setting may overwrite results from the new filter.
- **Suggested fix:** Move the abort call before the `loadingRef` check, or use the abort controller in the `useEffect` cleanup.

**[CR-011]** `about/page.tsx` hardcodes YouTube URL in BRANDING but also uses `BRANDING.youtube`

- **File:** `src/app/about/page.tsx:238` + `src/config/branding.ts:28`
- **Issue:** The about page correctly uses `BRANDING.youtube`, but the YouTube link in `BRANDING` is a raw URL that includes a specific channel ID. If the channel ID changes, it's a single point of failure, which is fine — but the Footer component also references `BRANDING.youtube`. No issue currently, but the pattern is fragile if someone adds a YouTube link without using the constant.
- **Impact:** Low — consistency concern only.
- **Suggested fix:** No action needed, but consider adding a lint rule or comment documenting that all YouTube links must use `BRANDING.youtube`.

**[CR-012]** `PersistentSearchBar` live search doesn't debounce `onQueryChange` callback

- **File:** `src/components/search/PersistentSearchBar.tsx:214-217`
- **Issue:** `onQueryChange` is called synchronously on every keystroke, while the internal fetch is debounced at 300ms. If a parent component does expensive work on `onQueryChange`, it runs on every keystroke.
- **Impact:** Potential jank if parent performs heavy operations on query change.
- **Suggested fix:** Document that `onQueryChange` fires on every keystroke, or provide a debounced variant.

**[CR-013]** Notification `PATCH` endpoint doesn't verify ownership before marking as read

- **File:** `src/app/api/notifications/[id]/route.ts:27-43`
- **Issue:** The code correctly checks `recipientId: decoded.userId` in the `findFirst` query, which is good. However, the error message "Notification not found" for a non-matching recipient leaks information — an attacker can enumerate notification IDs and determine which ones exist (404 vs other errors).
- **Impact:** Minor information disclosure — attacker can probe for valid notification IDs.
- **Suggested fix:** Return the same 404 for all failure cases (already done — this is informational).

**[CR-014]** `RecipeCard` image fallback creates infinite loop if `/chef-logo.png` also fails

- **File:** `src/components/recipe/RecipeCard.tsx:106-112`
- **Issue:** The `imgFallbackUsed` state prevents the second fallback attempt, but `setImgHidden(true)` only hides the image without providing alternative content. The card renders with an empty space where the image should be.
- **Impact:** Broken UI when both the recipe image and fallback image fail to load.
- **Suggested fix:** Show a placeholder `<Box>` with a recipe icon when `imgHidden` is true.

#### LOW

**[CR-015]** Unused import in `RecipeFeed`

- **File:** `src/components/recipe/RecipeFeed.tsx:1`
- **Issue:** `MutableRefObject` is imported from React but `useRef` already infers the type. The explicit type annotation `MutableRefObject<AbortController | null>` on `abortControllerRef` is unnecessary.
- **Impact:** Dead code.
- **Suggested fix:** Remove `MutableRefObject` import and type annotation.

**[CR-016]** `motion.create` used at module scope is correct, but comment is duplicated 15+ times

- **File:** Multiple files (about/page.tsx, pantry/page.tsx, followers/page.tsx, etc.)
- **Issue:** The exact same comment `// motion.create must be at module scope — calling inside a component creates // a new type each render, breaking React reconciliation.` appears in 15+ files verbatim.
- **Impact:** Noise; makes diffs larger and harder to review.
- **Suggested fix:** Remove the comment from all files except one central location (e.g., a `motion-helpers.ts` utility), or reduce to a single-line comment.

**[CR-017]** `env-validation.ts` Shannon entropy check threshold may reject legitimate hex secrets

- **File:** `src/lib/env-validation.ts:28-33`
- **Issue:** The entropy threshold of 3.0 bits/char is documented as catching repeated-character secrets, but a 32-char hex string (0-9, a-f) has maximum entropy of 4.0 bits/char. A hex secret with skewed distribution (e.g., many `a`s) could legitimately fall below 3.0.
- **Impact:** False positives on some legitimate but low-diversity hex secrets.
- **Suggested fix:** Lower threshold to 2.5 or add a comment noting hex secrets should use base64 encoding.
