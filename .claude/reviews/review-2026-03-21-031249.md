### Findings

#### CRITICAL

**[CR-001]** PUT profile allows clearing avatar without cleaning up old Cloudinary image

- **File:** `src/app/api/users/profile/route.ts:35-38`
- **Issue:** When a user updates their avatar to a new URL (or sets it to null/undefined), the old avatar image on Cloudinary is never cleaned up. The code validates the _new_ URL but never fetches the _current_ avatar to schedule deletion.
- **Impact:** Orphaned Cloudinary images accumulate indefinitely, increasing storage costs. Unlike the DELETE path which has explicit cleanup, the PUT path silently leaks images every time a user changes their avatar.
- **Suggested fix:**

```typescript
const currentUser = await prisma.user.findUnique({
  where: { id: user.id },
  select: { avatar: true },
});
const updatedUser = await userService.updateProfile(user.id, profileData);
if (
  currentUser?.avatar &&
  currentUser.avatar !== updatedUser.avatar &&
  isCloudinaryUrl(currentUser.avatar)
) {
  await cleanupCloudinaryImage(currentUser.avatar).catch(() => {});
}
```

**[CR-002]** `deductPantryItems` returns insufficient ingredients even when `force=true`, but they are silently discarded

- **File:** `src/app/api/cooked-recipes/route.ts:88-91`
- **Issue:** When `force=true` and there are insufficient ingredients, the function skips the throw but still populates `insufficientIngredients`. However, it does NOT deduct the partial amount available. The pantry item with insufficient quantity is simply skipped — no deduction happens at all for that ingredient.
- **Impact:** When forcing a cook with insufficient ingredients, the pantry quantity is never reduced for partially-available items. User expects "deduct what you can" but gets "deduct nothing for that ingredient."
- **Suggested fix:** When `force=true` and quantity is insufficient, deduct whatever is available:

```typescript
if (pantryQuantity >= recipeAmount) {
  // ... existing logic
} else {
  insufficientIngredients.push({ ... });
  if (force) {
    // Deduct whatever is available
    deletions.push({ id: pantryItem.id, name: ingredient.name, amount: pantryQuantity, unit: ingredient.unit });
  }
}
```

**[CR-003]** Race condition in recipe match endpoint — `statement_timeout` reset inside transaction

- **File:** `src/app/api/recipes/match/route.ts:96-97`
- **Issue:** The code sets `SET LOCAL statement_timeout = '10s'` then later resets it to `'5s'`. `SET LOCAL` scopes to the transaction, but the second `SET LOCAL statement_timeout = '5s'` (line ~130) applies to ALL subsequent statements in the transaction, including the batch `post.findMany` calls and the application-level matching loop's DB queries. If the first query takes 9s, the second `SET LOCAL` won't retroactively limit it — it only affects subsequent statements. The real problem: the 5s timeout applies to each individual statement but the entire transaction timeout is 15s. The wall-clock matching loop (4s) plus multiple DB round-trips could easily exceed this.
- **Impact:** Under load, the transaction could timeout mid-way through batch fetches, returning 500 errors to users.
- **Suggested fix:** Use a single consistent `statement_timeout` for the entire transaction (e.g., `'8s'`) rather than resetting it mid-transaction. The outer `{ timeout: 15000 }` is the real safeguard.

#### HIGH

**[CR-004]** Pantry restoration on DELETE does not validate `deductedIngredients` shape beyond basic checks

- **File:** `src/app/api/cooked-recipes/route.ts:264-296`
- **Issue:** The `deductedIngredients` field is stored as a JSON column and cast via `as unknown[]`. If the stored JSON was corrupted or tampered with (e.g., negative `amount`), the code would restore negative quantities to pantry items since it only checks `typeof d.amount !== 'number'` but not `d.amount > 0`.
- **Impact:** A corrupted or maliciously crafted `deductedIngredients` record could set pantry quantities to unexpected values (including via `existingItem.quantity + negativeAmount`).
- **Suggested fix:**

```typescript
if (typeof d.amount !== 'number' || d.amount <= 0 || !d.name || typeof d.name !== 'string')
  continue;
```

**[CR-005]** `hasMore` pagination logic is unreliable

- **File:** `src/components/recipe/RecipeFeed.tsx:148`
- **Issue:** `setHasMore(data.recipes.length === PAGE_SIZE)` is a common but flawed heuristic. If the total number of recipes is exactly a multiple of `PAGE_SIZE`, the client will make one extra request that returns 0 results. More importantly, after deduplication (`existingIds` filter), the actual number of new recipes added to state could be less than `PAGE_SIZE`, but `hasMore` is based on the raw API response length, not the deduplicated count. This means the sentinel could stop triggering even though there are more unique recipes to load.
- **Impact:** Users may see incomplete feeds or unnecessary extra API calls at the boundary.
- **Suggested fix:** Use the `total` field from the API response: `setHasMore(recipesLengthRef.current < data.total)`.

**[CR-006]** `escapeLike` does not handle bracket characters

- **File:** `src/app/api/recipes/match/route.ts:11-14`
- **Issue:** PostgreSQL `LIKE` with `ESCAPE '\\'` doesn't use brackets, so this is technically fine for standard LIKE. However, if the DB driver or future migration switches to `SIMILAR TO` or regex-based matching, square brackets and other special chars could cause injection. More immediately: the function doesn't escape the backslash-escape character correctly for the `ESCAPE '\\'` clause — a pantry item named `test\%` would become `test\\\\%` which after SQL processing becomes the literal `test\\` followed by a wildcard `%`.
- **Impact:** Pantry items containing backslashes could produce incorrect LIKE patterns, causing wrong recipe matches or no matches.
- **Suggested fix:** The double-escaping of backslash is actually correct for the `ESCAPE '\\'` clause (one level for JS string, one for SQL), but verify with a test case. Add a unit test for `escapeLike` with inputs like `test\name`, `100%`, `under_score`.

**[CR-007]** Admin PATCH `promote` action bypasses the advisory lock

- **File:** `src/app/api/admin/users/[id]/route.ts:122-125`
- **Issue:** The `demote` action correctly uses `pg_advisory_xact_lock` + admin count check inside a transaction. But `promote` calls `adminService.promoteToAdmin(id)` directly without any such protection. If `promoteToAdmin` doesn't have its own concurrency controls, this could be fine for promotion (which only adds admins). However, there's no check that the target user exists before promotion — if the service throws an unhandled error, it falls through to the generic 500.
- **Impact:** Promoting a non-existent user ID returns a 500 instead of a 404.
- **Suggested fix:** Wrap the promote call in a try-catch that handles P2025:

```typescript
try {
  const result = await adminService.promoteToAdmin(id);
  return NextResponse.json({ success: true, user: { ...result, email: maskEmail(result.email) } });
} catch (err) {
  if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === 'P2025') {
    return NextResponse.json({ error: 'User not found' }, { status: 404 });
  }
  throw err;
}
```

**[CR-008]** Duplicated error handling pattern for auth across all routes

- **Files:** Multiple — `cooked-recipes/route.ts:108-111`, `recipes/route.ts:158-163`, `recipes/match/route.ts:60-65`, `notifications/[id]/route.ts:15-20`
- **Issue:** Every route has the same try/catch-and-return-401 pattern for `requireAuth`. This is duplicated ~15+ times across the codebase. The profile route (`users/profile/route.ts`) uses a different pattern (catching the error message string). These inconsistencies make it easy to introduce bugs.
- **Impact:** Maintenance burden. If `requireAuth` error behavior changes, every route must be updated individually.
- **Suggested fix:** Create a wrapper or middleware that handles auth uniformly, or have `requireAuth` return a `NextResponse` directly on failure (like `requireAdmin` does with `isAdminAuthError`).

**[CR-009]** `notifications/[id]/route.ts` returns success even when notification doesn't exist

- **File:** `src/app/api/notifications/[id]/route.ts:30-33`
- **Issue:** When `updateMany` returns `count === 0`, the code returns `{ success: true }`. The comment says "Could be not found, not owned, or already read - return success for idempotency." While idempotency for "already read" is correct, returning success for "not found" or "not owned" hides bugs in the client. A notification ID typo or an authorization bypass attempt would silently succeed.
- **Impact:** Client-side bugs that send wrong notification IDs will never surface. An attacker probing notification IDs gets no signal about which are valid.
- **Suggested fix:** This is actually a reasonable security choice (prevents enumeration), but document the trade-off explicitly. If you want to distinguish, do a separate `findFirst` to check existence vs ownership vs already-read.

**[CR-010]** `RecipeFeed` animation delay resets on page boundary but not on scroll position

- **File:** `src/components/recipe/RecipeFeed.tsx:315`
- **Issue:** `transition={{ delay: (index % PAGE_SIZE) * 0.05 }}` means the 12th recipe (index 11) gets a 550ms delay. On subsequent pages, `index` keeps growing (e.g., index 24 % 12 = 0), so the pattern repeats. But if the user scrolls fast and two pages load in quick succession, animations from the first page may still be running while the second page starts at delay 0, causing visual jank.
- **Impact:** Minor visual inconsistency on fast scrolling.
- **Suggested fix:** Consider using a ref to track the starting index of each batch and only animate newly added recipes, or disable animation for paginated loads entirely.

**[CR-011]** `profileData` null-to-undefined conversion is fragile

- **File:** `src/app/api/users/profile/route.ts:42-48`
- **Issue:** The code manually converts `null` to `undefined` for four fields using nullish coalescing. If `updateProfileSchema` adds a new nullable field, this conversion must be manually updated. Also, `validatedData.avatar ?? undefined` means sending `avatar: ""` (empty string) would pass through as `""`, not `undefined`, which may cause downstream issues.
- **Impact:** New nullable fields will silently pass `null` to the service layer if not added to this mapping.
- **Suggested fix:** Use a generic transform:

```typescript
const profileData = Object.fromEntries(
  Object.entries(validatedData).map(([k, v]) => [k, v ?? undefined])
);
```

**[CR-012]** `useNotificationPolling` duplicates failure tracking logic in two catch blocks

- **File:** `src/hooks/useNotificationPolling.ts:107-120` and `src/hooks/useNotificationPolling.ts:127-140`
- **Issue:** The non-OK response handler and the catch block contain identical failure tracking code (push timestamp, filter window, check threshold, trip breaker). This is a maintenance hazard — fixing a bug in one path requires fixing it in the other.
- **Impact:** If the breaker logic needs to change, there are two places to update, and they can drift.

**[CR-013]** `maskEmail` doesn't handle edge cases

- **File:** `src/app/api/admin/users/[id]/route.ts:11-20`
- **Issue:** If the local part is exactly 1 character (e.g., `a@b.com`), `maskedLocal` becomes `a**` (3 chars). The `Math.max(local.length - 1, 2)` ensures at least 2 asterisks, but this inflates the apparent length. Similarly, single-char domain names get inflated.

- **Suggested fix:** Minor, but consider consistent masking like `a***@b***.com` regardless of length.

**[CR-015]** `isFetchingRef` not reset on abort

- **File:** `src/hooks/useNotificationPolling.ts:145-148`
- **Issue:** The `finally` block only resets `isFetchingRef.current = false` when `!controller.signal.aborted`. If the fetch is aborted (e.g., on unmount or rapid re-fetch), `isFetchingRef` stays `true`. On the next poll cycle, `scheduleNext` checks `if (isFetchingRef.current) { scheduleNext(); return; }` and reschedules, which eventually calls `fetchNotifications` again which sets a new controller and resets the flag via a successful fetch. So it self-heals, but there's a window where polling skips a cycle unnecessarily.
- **Impact:** After an abort, one polling cycle may be skipped. Self-healing but suboptimal.
- **Suggested fix:** Reset `isFetchingRef.current = false` unconditionally in `finally`, since the abort itself means the fetch is no longer in flight.
