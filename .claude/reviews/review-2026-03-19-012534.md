## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. The codebase has been through multiple review passes and shows maturity in its patterns. However, several security gaps, data integrity risks, and correctness issues remain.

### Findings

#### CRITICAL

**[CR-001]** XSS via unsanitized `recipe.caption` in template literal

- **File:** `src/app/recipe/[id]/page.tsx:~line 580`
- **Issue:** `recipe.caption` is rendered inside `&ldquo;{recipe.caption}&rdquo;` — React auto-escapes JSX, but the `RecipeService.stripHtml` sanitizer is only applied on create/update. Recipes created before the sanitizer was added, or data inserted directly into the DB, will render unsanitized. More critically, `stripHtml` uses a regex that doesn't handle attribute-based XSS like `<img src=x onerror=alert(1)>` in all edge cases.
- **Impact:** Stored XSS if recipe data predates the sanitizer or is inserted via direct DB access.
- **Suggested fix:** Use a proper HTML sanitization library (e.g., `DOMPurify` or `sanitize-html`) instead of the regex-based `stripHtml`. Also sanitize on read, not just write.

**[CR-002]** `recalc-ratings` endpoint has no transaction timeout enforcement on the caller

- **File:** `src/app/api/admin/recalc-ratings/route.ts:22-36`
- **Issue:** The `SET LOCAL statement_timeout = '30s'` is set inside the transaction, but a Prisma `$transaction` has its own default timeout (usually 5s). If the Prisma transaction timeout fires before the Postgres statement timeout, the transaction will abort with a confusing error. The advisory lock wait is also unbounded — if another instance holds it, this request blocks indefinitely.
- **Impact:** Blocked admin requests, potential connection pool exhaustion under contention.
- **Suggested fix:** Add `timeout` option to `$transaction`: `prisma.$transaction(async (tx) => { ... }, { timeout: 35000 })`.

**[CR-003]** Admin user delete race condition — advisory lock key is static

- **File:** `src/app/api/admin/users/[id]/route.ts:43`
- **Issue:** `pg_advisory_xact_lock(${PG_ADVISORY_LOCK_ADMIN_DELETE}, 0)` uses a single global lock for ALL user deletions. This serializes all admin user deletions, creating a bottleneck. If one deletion is slow (cleaning up many posts/images), all other deletions queue behind it.
- **Impact:** Admin panel becomes unresponsive during bulk user management.
- **Suggested fix:** Use per-user advisory locks: `pg_advisory_xact_lock(${PG_ADVISORY_LOCK_ADMIN_DELETE}, hashtext(${id}))`.

#### HIGH

**[CR-004]** `cooked-recipes` route doesn't restore pantry on transaction failure after deductions

- **File:** `src/app/api/cooked-recipes/route.ts:68-85`
- **Issue:** `deductPantryItems` performs pantry updates inside the transaction, and the `cookedRecipe.create` happens after. If `create` fails (e.g., unique constraint), the entire transaction rolls back — but this is correct because it's in a `$transaction`. However, if `force=true` and there are insufficient ingredients, the function returns `insufficientIngredients` but still deducts available items. The caller then returns a 201 with both the cooked recipe AND the insufficient list, but no indication of what WAS deducted vs what wasn't.
- **Impact:** User confusion about pantry state after forced cooking.
- **Suggested fix:** Include `deductedIngredients` in the response alongside `insufficientIngredients`.

**[CR-005]** Recipe match endpoint performs unbounded in-memory computation

- **File:** `src/app/api/recipes/match/route.ts:100-140`
- **Issue:** The endpoint fetches up to 500 candidate recipes, then performs O(candidates _ ingredients _ pantryItems) matching in memory. With 500 recipes averaging 10 ingredients each and a pantry of 500 items, this is 2.5M string comparisons per request. The `normalizeIngredientName` function is called for every comparison (no memoization).
- **Impact:** Slow response times and high CPU usage under load. No per-user rate limiting on this read endpoint.
- **Suggested fix:** Memoize `normalizeIngredientName` results within the request. Consider caching match results with a short TTL keyed by pantry hash.

**[CR-006]** `useNotificationPolling` circuit breaker auto-reset happens silently

- **File:** `src/hooks/useNotificationPolling.ts:131-135`
- **Issue:** After the circuit breaker trips (10 failures in 10 minutes), `scheduleNext` auto-resets after 5 minutes. But `isPollingPaused` state isn't updated until the next `fetchNotifications` succeeds or fails, leaving the UI in a stale "paused" state while polling silently resumes.
- **Impact:** User sees "paused" indicator but polling is actually running, or vice versa.
- **Suggested fix:** Update `setIsPollingPaused(false)` when the breaker auto-resets in `scheduleNext`.

**[CR-007]** Comment image upload doesn't validate Cloudinary URL before saving

- **File:** `src/app/api/recipes/[id]/comments/route.ts:77-78`
- **Issue:** The POST endpoint calls `validateCloudinaryUrl(imageUrl)` to check the URL, but if an attacker modifies the request between validation and the `comment.create` call, the validated URL might differ. More importantly, the PATCH endpoint at `[commentId]/route.ts` also validates `imageUrl`, but neither endpoint verifies that the uploaded image's `publicId` matches the authenticated user's upload session.
- **Impact:** Users could associate any Cloudinary image (uploaded by anyone) with their comment.
- **Suggested fix:** Track upload ownership by storing `publicId -> userId` mappings, or generate signed upload URLs scoped to the user.

**[CR-008]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:135-160`
- **Issue:** When filters change, `loadRecipes(true)` resets the page and replaces recipes. But due to the `AbortController` pattern, if a filter change races with an in-flight load, the abort may not fire before the response arrives, leading to stale data being set. The `existingIds` dedup set only prevents duplicates within an append, not between a reset and a concurrent append.
- **Impact:** Duplicate recipe cards appearing briefly during rapid filter changes.
- **Suggested fix:** Track a `requestId` counter and ignore responses from stale requests.

#### MEDIUM

**[CR-009]** `Footer` contact form constructs mailto URI without length validation on individual fields

- **File:** `src/components/Footer.tsx:55-60`
- **Issue:** The `handleSendEmail` checks total `mailtoLink.length > 2000` but doesn't validate individual field lengths before constructing the URI. The `maxLength` attributes on inputs (100, 254, 2000) allow up to ~2354 chars of input, which after URI encoding could exceed OS limits for `mailto:` URIs (varies by OS, often ~32K, but some email clients have lower limits).
- **Impact:** Silently truncated email content on some platforms.
- **Suggested fix:** The current 2000-char check is reasonable. Add `encodeURIComponent` length check instead of raw string length.

**[CR-010]** `EditProfileModal` avatar magic-byte validation reads entire file into memory

- **File:** `src/components/profile/EditProfileModal.tsx:92-105`
- **Issue:** `reader.readAsArrayBuffer(file)` reads the entire file (up to 5MB) into memory just to check the first 12 bytes of magic bytes. This is wasteful for large images.
- **Impact:** Unnecessary memory allocation on client, potential jank on low-memory devices.
- **Suggested fix:** Use `file.slice(0, 12)` before reading: `const slice = file.slice(0, 12); reader.readAsArrayBuffer(slice);`

**[CR-011]** `PersistentSearchBar` creates new `AbortController` per debounce cycle but doesn't abort on unmount cleanup

- **File:** `src/components/search/PersistentSearchBar.tsx:127-155`
- **Issue:** The `useEffect` cleanup calls `controller.abort()`, but a new controller is created inside the `setTimeout` callback. If the component unmounts after the timeout fires but before the fetch completes, the `isMountedRef` check prevents state updates but the fetch still runs to completion.
- **Impact:** Wasted network requests after navigation away from search.
- **Suggested fix:** Move the `AbortController` creation outside the timeout and abort in the cleanup.

**[CR-012]** `safeRating` utility returns `null` for `undefined` but `0` is a valid "unrated" value in DB

- **File:** `src/lib/utils/recipe.ts:12-14`
- **Issue:** `averageRating` defaults to `0` in the DB (not `null`), so recipes with no ratings have `averageRating = 0`. `safeRating` passes `0` through unchanged, but the UI checks `averageRating > 0` to decide whether to show ratings. This means a recipe with a single 0-star rating (impossible with 1-5 scale) and a truly unrated recipe look the same.
- **Impact:** No current bug (1-5 scale), but fragile if scale changes. The DB schema allows `Float?` (nullable) but the `recalc-ratings` route sets it to `COALESCE(..., 0)`, converting null to 0.
- **Suggested fix:** Use `null` instead of `0` for "no ratings" in the recalc query: `NULLIF(COALESCE(r.avg_rating, 0), 0)`.

**[CR-013]** `normalizeIngredientName` strips plurals aggressively, breaking short ingredient names

- **File:** `src/lib/utils/ingredients.ts:44-58`
- **Issue:** The length guard `normalized.length > 5` for the final `s`-stripping means "lemons" (6 chars) becomes "lemon" but "beans" (5 chars) stays "beans". The `> 4` guards for `ies`/`ves` are inconsistent. "olives" (6 chars) hits the `s`-strip becoming "olive", but "chives" (6 chars) also becomes "chive" which is correct. However, "fries" (5 chars > 4) would become "fry" via the `ies` rule, which is correct, but "dies" would also match.
- **Impact:** Inconsistent pantry-recipe matching for short ingredient names.
- **Suggested fix:** Consider using a proper stemming library (e.g., `natural` or `stemmer`) instead of hand-rolled rules.

**[CR-014]** `RecipeCard` dev warning uses module-level `Set` that persists across tests

- **File:** `src/components/recipe/RecipeCard.tsx:20`
- **Issue:** `const warnedIds = new Set<string>()` at module scope means in test environments, warnings suppressed in one test bleed into subsequent tests. This isn't a production bug but makes debugging test failures harder.
- **Impact:** Flaky test diagnostics.
- **Suggested fix:** Clear `warnedIds` in test `afterEach` or use a WeakRef-based approach.

#### LOW

**[CR-015]** Inconsistent auth pattern across API routes

- **File:** Multiple API routes
- **Issue:** Some routes use `requireAuth(request)` (e.g., `change-password`, `pantry`), while others manually call `extractAuthToken` + `tokenService.verify` (e.g., `comments`, `like`, `save`). The manual pattern doesn't check if the user still exists in the DB, only that the JWT is valid.
- **Impact:** A deleted user with a still-valid JWT can interact with some endpoints.
- **Suggested fix:** Standardize on `requireAuth` which validates the token AND fetches the user from the DB.

**[CR-016]** `motion.create` called at module scope in multiple components is fine, but `MotionBox` naming collision

- **File:** Multiple files (about/page.tsx, Navigation.tsx, recipe/[id]/page.tsx, etc.)
- **Issue:** `const MotionBox = motion.create(Box)` is declared in at least 6 different files with the same name. This isn't a bug, but if any file imports from another, it would shadow the local declaration.
- **Impact:** Maintenance confusion only.
- **Suggested fix:** No action needed, just be aware when refactoring.

**[CR-017]** `template.tsx` recipe template uses `isClient` state that delays first render

- **File:** `src/app/recipe/[id]/template.tsx:22-25`
- **Issue:** `useState(false)` + `useEffect(() => setIsClient(true), [pathname])` means the AnimatePresence wrapper is skipped on the first render of every navigation. This defeats the purpose of exit animations — the old content disappears instantly.
- **Impact:** Exit animations never play on first navigation to a recipe.
- **Suggested fix:** Initialize `isClient` to `true` if `typeof window !== 'undefined'`, or remove the SSR guard entirely since this is a `'use client'` component.
