## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured with good security practices (httpOnly cookies, CSRF protection, advisory locks). However, several critical and high-severity issues exist around security, data integrity, and reliability.

### Findings

#### CRITICAL

**[CR-001]** Recipe match endpoint has no LIMIT on the DISTINCT query, can return unbounded rows

- **File:** `src/app/api/recipes/match/route.ts:109-116`
- **Issue:** The `LIMIT ${limit}` is inside the CTE `candidates`, but the outer `DISTINCT` query joining `candidates` with `jsonb_array_elements` has no LIMIT. If a recipe has many matching ingredients, the element-level join can produce many rows per candidate. While `DISTINCT` collapses them back, the intermediate result set and sort can be very large.
- **Impact:** Memory exhaustion / slow queries under load when recipes have large ingredient arrays.
- **Suggested fix:** Add `LIMIT ${limit}` to the outer query as well:

```sql
SELECT DISTINCT c.id, c.ingredients
FROM candidates c, jsonb_array_elements(c.ingredients) AS elem
WHERE (${Prisma.join(nameConditions, ' OR ')})
ORDER BY c.id
LIMIT ${limit}
```

**[CR-002]** `cooked-recipes` POST uses `hashtext()` which has collision risk for advisory locks

- **File:** `src/app/api/cooked-recipes/route.ts:157`
- **Issue:** `hashtext('cooked-recipe')` returns a 32-bit int. `hashtext(${user.id})` also returns 32-bit. The comment acknowledges collision risk but dismisses it. Two different users whose UUIDs hash to the same value will serialize against each other. More critically, `hashtext('cooked-recipe')` could collide with `PG_ADVISORY_LOCK_ADMIN_DELETE` (48880) or `PG_ADVISORY_LOCK_RECALC_RATINGS` (48879) since hashtext returns arbitrary int32 values.
- **Impact:** Cross-feature lock contention or accidental serialization between unrelated operations.
- **Suggested fix:** Register the cooked-recipe lock namespace in `constants.ts` with a fixed key instead of using `hashtext`:

```ts
export const PG_ADVISORY_LOCK_COOKED_RECIPE = 48881;
// Then: pg_advisory_xact_lock(48881, hashtext(${user.id}))
```

**[CR-003]** Admin user deletion leaks image URLs on transaction failure after partial Cloudinary cleanup

- **File:** `src/app/api/admin/users/[id]/route.ts:66-68`
- **Issue:** `Promise.allSettled` runs Cloudinary deletions after the transaction commits. If the server crashes between transaction commit and Cloudinary cleanup, images are orphaned. This is documented as "best-effort" but the real issue is the reverse: if `Promise.allSettled` partially succeeds and then the response fails to reach the client, the client may retry the DELETE, which will 404 because the user is already deleted, leaving remaining images orphaned with no retry mechanism.
- **Impact:** Orphaned Cloudinary images accumulating over time with no automatic cleanup.
- **Suggested fix:** Log orphaned image URLs to a dead-letter table for the cleanup script to process, or queue them in a background job.

#### HIGH

**[CR-004]** `RecipeFeed` infinite scroll has no deduplication guard for concurrent IntersectionObserver callbacks

- **File:** `src/components/recipe/RecipeFeed.tsx:130-133`
- **Issue:** `loadingRef.current` is checked and set to true, but `abortControllerRef.current?.abort()` always runs first, which cancels the previous request. If the IntersectionObserver fires twice in rapid succession (common on mobile), the first call aborts, then the second call sets `loadingRef.current = true` and starts fetching. But since the first call's `abort()` runs before the second call's `if (loadingRef.current && !reset) return`, both can proceed.
- **Impact:** Duplicate recipe entries in the feed, or skipped pages.
- **Suggested fix:** Check `loadingRef.current` before aborting:

```ts
if (loadingRef.current && !reset) return;
abortControllerRef.current?.abort();
```

**[CR-005]** `useNotificationPolling` leaks timer references across user changes

- **File:** `src/hooks/useNotificationPolling.ts:108-110`
- **Issue:** When `user` changes (logout/login), the effect cleanup cancels the old timer and abort controller. But `failureTimestampsRef`, `pollingStoppedRef`, and `breakerTripCountRef` are reset at the start of the new effect run (line 108-112), which is correct. However, `breakerTrippedAtRef` is never reset, so a new user inherits the previous user's breaker trip timestamp, potentially keeping polling paused for a new user who just logged in.
- **Impact:** New user after login may have notifications paused due to previous user's failures.
- **Suggested fix:** Add `breakerTrippedAtRef.current = 0;` alongside the other resets at line 111.

**[CR-006]** `pantry/[id]/route.ts` PUT allows updating quantity to exactly `MAX_QUANTITY` but comparison uses `>` not `>=` inconsistently with POST

- **File:** `src/app/api/pantry/[id]/route.ts:60` vs `src/app/api/pantry/route.ts:91`
- **Issue:** PUT uses `parsed > MAX_QUANTITY` while POST also uses `parsed > MAX_QUANTITY`. This is consistent but allows `MAX_QUANTITY` itself. The name suggests it should be the maximum allowed, so `>=` would be more appropriate if 999999 is meant to be excluded. More importantly, the `quantity` field in PUT accepts a string from the body but compares with `parseFloat(quantity)`, while the `data` object also calls `parseFloat(quantity)`. If `quantity` is `"Infinity"` or `"NaN"` as a string, `isNaN(parsed)` and `!isFinite(parsed)` catch these. But `quantity: "-0"` passes all checks and stores `-0`.
- **Impact:** Minor data integrity issue with edge case inputs.
- **Suggested fix:** Add `parsed === 0 ? 0 : parsed` to normalize negative zero, or simply use `Math.abs(parsed)` after the negative check.

**[CR-007]** `src/app/api/recipes/match/route.ts` builds SQL WHERE clause with `Prisma.join` but doesn't handle the case where all pantry names are filtered out

- **File:** `src/app/api/recipes/match/route.ts:99-103`
- **Issue:** `nameConditions` filters by `n.length >= 2` and `slice(0, 50)`. If all pantry item names are 0-1 characters, `nameConditions` is empty, and the fallback path runs. But the check `if (nameConditions.length > 0)` correctly handles this. However, a single pantry item named `"a"` (length 1) would hit the fallback path which fetches by `averageRating desc` — a completely different ordering than the primary path, causing inconsistent UX.
- **Impact:** Inconsistent recipe matching results for users with very short ingredient names.
- **Suggested fix:** Use `createdAt desc` in the fallback to match primary path ordering, or lower the minimum length to 1.

**[CR-008]** `EditProfileModal` avatar upload does not validate file type on the server path

- **File:** `src/components/profile/EditProfileModal.tsx:92-98`
- **Issue:** Client-side magic byte validation is done (good), but the upload uses `accept="image/*"` on the input. A user can bypass client-side validation by modifying the DOM or using developer tools. The server-side `/api/upload/avatar` does validate, but the client-side error message from `showError('File content does not match...')` will confuse users since it appears before upload, while the server would catch it again anyway.
- **Impact:** UX issue — redundant validation with different error messages.
- **Suggested fix:** Remove the client-side magic byte check or align its error message with the server's.

#### MEDIUM

**[CR-009]** `logServerError` silently swallows Sentry import failures

- **File:** `src/lib/utils/logger.ts:8-10`
- **Issue:** `import('@sentry/nextjs').then(...).catch(() => {})` silently swallows all errors. If Sentry is installed but misconfigured, errors will be silently lost without any indication.
- **Impact:** Errors may never reach monitoring in production.
- **Suggested fix:** Log to console.warn in the catch:

```ts
.catch((e) => { if (process.env.NODE_ENV === 'development') console.warn('Sentry unavailable:', e.message); });
```

**[CR-010]** `middleware.ts` rate limiter's hard cap eviction sorts all entries on every over-cap request

- **File:** `src/middleware.ts:76-82`
- **Issue:** When `rateLimitMap.size >= 500`, sorting all entries by count is O(n log n). Under a DDoS with many unique IPs, this runs on every request, adding latency to all API calls.
- **Impact:** Performance degradation under high-cardinality attack traffic.
- **Suggested fix:** Use a simpler eviction strategy — delete the oldest entries (by resetTime) instead of sorting by count, or use a fixed-size LRU.

**[CR-011]** `Footer.tsx` mailto link length check uses 2000 but doesn't account for URL encoding expansion

- **File:** `src/components/Footer.tsx:60-62`
- **Issue:** The 2000-character check runs after `encodeURIComponent`, so the actual check is correct. But `sanitize()` only strips `\r\n` — it doesn't strip other control characters that could affect email client behavior.
- **Impact:** Minor — email clients handle this, but unusual characters could cause display issues.
- **Suggested fix:** Strip all control characters: `s.replace(/[\x00-\x1F\x7F]/g, '')`

**[CR-012]** `CommentsSection` creates object URLs for image previews without cleanup on component unmount

- **File:** `src/components/recipe/CommentsSection.tsx:170-175`
- **Issue:** `URL.createObjectURL(file)` is called on image selection, and `URL.revokeObjectURL` is called on remove and successful submit. But if the component unmounts while an image is selected (e.g., user navigates away), the object URL is never revoked.
- **Impact:** Memory leak — each unreleased blob URL holds the file data in memory.
- **Suggested fix:** Add a cleanup effect:

```ts
useEffect(() => {
  return () => {
    if (imagePreview) URL.revokeObjectURL(imagePreview);
  };
}, [imagePreview]);
```

**[CR-013]** `RecipeCard` module-level `warnedIds` set grows unboundedly in long-lived processes

- **File:** `src/components/recipe/RecipeCard.tsx:29`
- **Issue:** The set is cleared when size > 100, but this is checked per-recipe render. In SSR or long-lived dev server, hundreds of unique recipe IDs accumulate before the 100 threshold triggers.
- **Impact:** Minor memory leak in development/SSR contexts.
- **Suggested fix:** Use a `WeakRef`-based approach or simply remove the dev warning since it's not actionable at runtime.

**[CR-014]** `useNotificationPolling` visibility handler uses random jitter but doesn't cancel the previous jitter timer

- **File:** `src/hooks/useNotificationPolling.ts:148-159`
- **Issue:** When `visibilityState` changes to `'visible'`, a `visibilityTimeoutId` is set with a random jitter delay. If the user rapidly switches tabs (visible → hidden → visible), the previous `visibilityTimeoutId` is cleared on hidden, but if hidden fires before the jitter timer, it's fine. However, if visible fires twice without an intervening hidden (possible with some browser behaviors), the old timer is not cancelled because `visibilityTimeoutId` is only cleared on hidden.
- **Impact:** Potential double-fetch of notifications on rapid tab switching.
- **Suggested fix:** Clear `visibilityTimeoutId` at the start of the visible handler too:

```ts
if (visibilityTimeoutId) {
  clearTimeout(visibilityTimeoutId);
  visibilityTimeoutId = null;
}
```

**[CR-016]** `src/app/api/recipes/route.ts` GET has two separate `orderBy` tiebreakers — `id: 'asc'` for newest but not for other sorts

- **File:** `src/app/api/recipes/route.ts:48-61`
- **Issue:** `newest` sort uses `[{ createdAt: 'desc' }, { id: 'asc' }]` for stable pagination, but `rating_desc`, `rating_asc`, and `most_reviewed` only use `createdAt` as tiebreaker, not `id`. This means recipes with identical ratings and creation timestamps may appear in inconsistent order across pages.
- **Impact:** Minor pagination instability for edge cases.
- **Suggested fix:** Add `{ id: 'asc' }` as final tiebreaker to all sort options.

**[CR-017]** `MatchedRecipes` component's `missingIngredients` type mismatch

- **File:** `src/components/recipe/MatchedRecipes.tsx:30`
- **Issue:** Interface declares `missingIngredients: Array<{ name: string; amount: number; unit: string }>` but the API response at `src/app/api/recipes/match/route.ts:184` maps to `missingIngredients: match.missingIngredients.map(i => i.name)` which returns `string[]`. The component accesses `.map((ing) => ing.name)` on line 316, which would fail on strings.
- **Impact:** Runtime error when rendering "Almost There" recipes with missing ingredients — `ing.name` on a string returns `undefined`.
- **Suggested fix:** Fix the interface to `missingIngredients: string[]` and change line 316 to just use the strings directly:

```ts
Missing: {
  recipe.missingIngredients.join(', ');
}
```
