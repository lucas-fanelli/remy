## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured with good security practices (CSRF, CSP, advisory locks), but several real bugs, race conditions, and security gaps exist across the codebase.

### Findings

#### CRITICAL

**[CR-001]** Cooked recipe rating is never persisted to the Post record

- **File:** `src/app/api/cooked-recipes/route.ts:149`
- **Issue:** The `cookedRecipeSchema` accepts a `rating` field, and the `cookedRecipe.create` stores it on the `CookedRecipe` record, but unlike the comments endpoint, the code never upserts to the `Rating` table and never recalculates `Post.averageRating`/`Post.reviewCount`. Ratings submitted via "mark as cooked" are silently discarded from the recipe's aggregate.
- **Impact:** Users think they rated a recipe when cooking it, but the rating has no effect on the recipe's displayed average.
- **Suggested fix:** After creating the `cookedRecipe`, upsert into the `Rating` table and recalculate `Post.averageRating`/`Post.reviewCount` the same way `comments/[commentId]/route.ts` does.

**[CR-002]** Admin user delete leaks `imageUrl` strings that are not Cloudinary URLs

- **File:** `src/app/api/admin/users/[id]/route.ts:60-63`
- **Issue:** `postImages` is collected via `filter(Boolean)` on `Post.imageUrl`, but `imageUrl` is a non-nullable `String` in the schema — it's always truthy even if it's an empty string or a non-Cloudinary URL. These get passed to `cleanupCloudinaryImage`, which silently fails, but the code also passes ALL collected URLs to `Promise.allSettled` without checking `imageUrl.includes('cloudinary.com')` first. The `failedUrls` warning then logs false positives.
- **Impact:** Noisy logs, wasted Cloudinary API calls on non-Cloudinary URLs.
- **Suggested fix:** Filter URLs with `isCloudinaryUrl()` before passing to `cleanupCloudinaryImage`.

**[CR-003]** `deductPantryItems` applies deductions even when `insufficientIngredients` exist with `force=true`

- **File:** `src/app/api/cooked-recipes/route.ts:87-95`
- **Issue:** When `force=true` and some ingredients are insufficient, the code skips the throw but still applies the `deductions` array (which only contains items that HAD sufficient quantity). The insufficient items are silently left unchanged. However, the response includes `insufficientIngredients` and `deductedIngredients`, misleading the client into thinking pantry was partially deducted — but the "insufficient" items' available quantities were never touched. This is arguably correct behavior, but the response message says "ingredients removed from pantry" without distinguishing which ones were actually removed.
- **Impact:** User confusion about pantry state after forced cook.
- **Suggested fix:** Clarify the response message or deduct available quantity (reduce to 0) for insufficient items when forced.

#### HIGH

**[CR-004]** `RecipeFeed` uses `useRef` for `pageRef` but doesn't reset it properly on filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:125-127`
- **Issue:** When `loadRecipes(true)` is called (reset), `pageRef.current` is set to 0 before fetch, then set to 1 after. But if the fetch is aborted (e.g., rapid filter changes), the `finally` block still runs `loadingRef.current = false`, but `pageRef` stays at 0 because the stale response guard returns early before `pageRef.current = 1`. The next non-reset fetch then sends `offset: 0` again, causing duplicate recipes.
- **Impact:** Duplicate recipe cards in feed after rapid filter toggling.
- **Suggested fix:** Move `pageRef.current = 1` to before the fetch for reset mode, or guard pagination state inside the stale-response check.

**[CR-005]** `handleShare` in recipe detail page uses `navigator.clipboard.writeText` without checking for secure context

- **File:** `src/app/recipe/[id]/page.tsx:290-296`
- **Issue:** `navigator.clipboard.writeText` requires a secure context (HTTPS) and user activation. The catch block shows "Failed to copy link" but doesn't distinguish between permission denial and other errors. On HTTP (dev), this silently fails.
- **Impact:** Users on HTTP or in certain browser contexts see a generic error with no actionable guidance.
- **Suggested fix:** Check `navigator.clipboard` existence before calling, and provide a fallback (e.g., `document.execCommand('copy')` or show the URL in a selectable input).

**[CR-006]** `search/route.ts` exposes `user.id` in public search results

- **File:** `src/app/api/search/route.ts:51`
- **Issue:** The user object spread (`({ email, role, isVerified, isPrivate, createdAt, updatedAt, ...rest }) => rest`) strips several fields but keeps `id`, `username`, `fullName`, `bio`, `avatar`, and `website`. Exposing internal user IDs in public search results enables enumeration attacks and could be used to craft targeted API calls.
- **Impact:** Information disclosure — internal UUIDs leaked to unauthenticated callers.
- **Suggested fix:** Explicitly select only the fields needed for display: `{ username, fullName, avatar, bio }`.

**[CR-007]** `notifications/page.tsx` doesn't mark notifications as read when navigating to them

- **File:** `src/app/notifications/page.tsx:97-107`
- **Issue:** `handleNotificationClick` navigates to the relevant page but never calls the PATCH endpoint to mark the individual notification as read. Unlike `Navigation.tsx` which does call `PATCH /api/notifications/${notification.id}`, the dedicated notifications page skips this step.
- **Impact:** Notifications remain unread even after the user clicks on them from the notifications page, causing badge count to stay elevated.
- **Suggested fix:** Add the same PATCH call that `Navigation.tsx:handleNotificationClick` uses.

**[CR-008]** Admin recipe delete extracts Cloudinary public ID incorrectly for nested folders

- **File:** `src/app/api/admin/recipes/[id]/route.ts:37`
- **Issue:** The regex `/\/upload\/(?:[^/]+\/)*([^/.]+)/` captures only the last path segment before the extension. But Cloudinary public IDs include the folder prefix (e.g., `recipes/abc123`). Calling `deleteFromCloudinary('abc123')` instead of `deleteFromCloudinary('recipes/abc123')` will fail silently or delete a wrong image.
- **Impact:** Cloudinary images are never actually deleted when admin deletes recipes; they become orphans.
- **Suggested fix:** Use `cleanupCloudinaryImage` from `@/lib/utils/cloudinary-cleanup` (which handles this correctly) instead of inline regex extraction, or fix the regex to capture the full path including folder.

#### MEDIUM

**[CR-009]** `RecipeCard` fires `console.warn` on every render cycle for non-Cloudinary images

- **File:** `src/components/recipe/RecipeCard.tsx:65-70`
- **Issue:** The `useEffect` with `warnedRef` only prevents re-warning per component instance. If the component is unmounted and remounted (e.g., during infinite scroll recycling), `warnedRef` resets and the warning fires again. This creates log noise in development.
- **Impact:** Developer console pollution during development.
- **Suggested fix:** Use a module-level `Set` to track warned recipe IDs, similar to how `getDifficultyColor` tracks warned difficulties.

**[CR-010]** `useNotificationPolling` creates a new AbortController on every `fetchNotifications` call without awaiting the previous one

- **File:** `src/hooks/useNotificationPolling.ts:73-75`
- **Issue:** `notificationAbortRef.current?.abort()` is called before the new controller is assigned, but the polling `scheduleNext` can fire concurrently with a visibility-change-triggered fetch. While `isFetchingRef` guards against overlapping fetches in the visibility handler, the polling timeout callback doesn't check `isFetchingRef`.
- **Impact:** Potential concurrent notification fetches under specific timing conditions (tab focus + polling timeout firing simultaneously).
- **Suggested fix:** Add `if (isFetchingRef.current) return;` at the start of the polling timeout callback.

**[CR-011]** `Footer` contact form has no length validation before constructing mailto URL

- **File:** `src/components/Footer.tsx:67-72`
- **Issue:** While `maxLength` attributes are set on inputs (100, 254, 2000), these are advisory in HTML. A programmatic submission or browser extension could bypass them. The 1500-char mailto limit check happens after sanitization but before URL encoding. After `encodeURIComponent`, the URL could still exceed browser limits since encoded characters expand (e.g., spaces become `%20`).
- **Impact:** Silently truncated emails on very long messages that pass the 1500-char pre-encoding check.
- **Suggested fix:** Check the length after `encodeURIComponent` encoding, not before.

**[CR-012]** `pantry/[id]/route.ts` PUT doesn't sanitize `name` for HTML but does sanitize `category`

- **File:** `src/app/api/pantry/[id]/route.ts:87`
- **Issue:** The `name` field is passed through `striptags(name.trim())` at line 87, which is correct. However, the `notes` field at line 91 is NOT sanitized with striptags — it's stored with `notes?.trim() || null`. If notes are ever rendered as raw HTML (unlikely with React but possible in emails/exports), this could be an XSS vector.
- **Impact:** Low risk due to React's auto-escaping, but inconsistent sanitization is a code smell.
- **Suggested fix:** Apply `striptags` to `notes` as well for consistency with other text fields.

**[CR-013]** `recipe/[id]/page.tsx` `toEditableRecipe` silently drops unknown difficulty values

- **File:** `src/app/recipe/[id]/page.tsx:37-40`
- **Issue:** If `apiRecipe.difficulty` is a valid string that isn't in the `validDifficulties` array (e.g., `'expert'` from a future schema change), it silently defaults to `'medium'`. This could cause data loss when editing — the user opens the edit modal, sees "Medium" (incorrect), saves, and overwrites the original difficulty.
- **Impact:** Silent data corruption on edit for recipes with non-standard difficulty values.
- **Suggested fix:** Preserve the original value and let the edit form validate, or show a warning if the difficulty is unknown.

**[CR-014]** `AuthContext` logout retry fires `auth:logout-failed` even on AbortError

- **File:** `src/contexts/AuthContext.tsx:107-115`
- **Issue:** The `retryLogout` function's catch block fires `auth:logout-failed` event for ANY error, including `AbortError` (e.g., if the component unmounts during the retry). This could trigger a false warning snackbar.
- **Impact:** False "Could not fully sign out" warning shown to users who navigate quickly after logout.
- **Suggested fix:** Check for `AbortError` before dispatching the event.

**[CR-015]** `recipes/match/route.ts` builds SQL with `Prisma.join` on user-influenced data

- **File:** `src/app/api/recipes/match/route.ts:88-90`
- **Issue:** `pantryNames` are derived from `normalizeIngredientName(item.name)` and then interpolated into SQL via `Prisma.sql` tagged templates. While Prisma's tagged templates parameterize values (preventing SQL injection), the `nameConditions` array is joined with `Prisma.join(..., ' OR ')`. If `pantryNames` contains very many items (capped at 50), the resulting query could be extremely large. The `normalizeIngredientName` function strips non-alphanumeric chars, providing defense-in-depth.
- **Impact:** Performance degradation with many pantry items (50 OR conditions), not a security issue.
- **Suggested fix:** Consider using `ANY(ARRAY[...])` instead of multiple OR conditions for better query plan caching.

**[CR-017]** `PersistentSearchBar` creates `AbortController` outside `setTimeout` with incorrect cleanup comment

- **File:** `src/components/search/PersistentSearchBar.tsx:129-133`
- **Issue:** The comment says "The AbortController is intentionally created OUTSIDE the setTimeout" but the actual cleanup function only calls `controller.abort()`. If the component unmounts before the timeout fires, the controller is aborted before any fetch happens, which is correct. However, `searchAbortRef.current?.abort()` inside the timeout aborts the previous request, and then immediately assigns the same `controller` to `searchAbortRef`. If the cleanup runs after the timeout fires but before the fetch completes, the abort cancels the in-flight request correctly. The logic is actually correct despite the confusing code structure.
- **Impact:** None — code is correct but confusing.
- **Suggested fix:** Add a brief comment explaining the lifecycle more clearly.

**[CR-018]** `about/page.tsx` animation delay scales linearly with feature count

- **File:** `src/app/about/page.tsx:140`
- **Issue:** `transition={{ duration: 0.4, delay: 0.1 * index }}` creates increasingly long delays as features are added. With 6 features, the last card waits 0.5s. If more features are added, the page will feel sluggish.
- **Impact:** Minor UX degradation if feature list grows.
- **Suggested fix:** Cap the delay at a maximum value, e.g., `delay: Math.min(0.1 * index, 0.3)`.
