## Code Review — 2026-03-17

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security vulnerabilities in auth flow, race conditions in data mutations, and inconsistent error handling across API routes.

### Findings

#### CRITICAL

**[CR-001]** Auth cookie token mismatch — client sends literal string "cookie-auth" as Bearer token

- **File:** `src/contexts/AuthContext.tsx:57`
- **Issue:** On mount, `fetchCurrentUser` sets `token` to the literal string `'cookie-auth'`. Components then send `Authorization: Bearer cookie-auth` to API routes. Routes calling `extractBearerToken` get `"cookie-auth"` back and pass it to `tokenService.verify()`, which fails. The only reason the app works is because `extractBearerToken` falls back to the httpOnly cookie. But any route that checks `if (!token)` before extracting will accept this garbage string as "valid".
- **Impact:** Every authenticated client-side fetch sends a meaningless Bearer token. If any middleware or route trusts the Bearer header without cookie fallback, auth breaks. The `login` and `register` flows correctly set the real JWT, so after login the token is real — but after a page refresh, it's `"cookie-auth"` again.
- **Suggested fix:**

```ts
// AuthContext.tsx:57 — don't set a fake token
setToken(null); // Let components know auth is cookie-based
// OR extract the real token from the response if the /me endpoint returns it
```

**[CR-002]** Admin middleware JWT verification uses HS256 but `jsonwebtoken` default may differ

- **File:** `src/middleware.ts:113-131`
- **Issue:** The middleware manually verifies JWT signatures using `HMAC` with `SHA-256` via Web Crypto API. But `TokenService` uses `jsonwebtoken` which defaults to HS256. If the token was signed with a different algorithm (e.g., someone passes `algorithm: 'HS384'`), the middleware would reject valid tokens or, worse, accept crafted ones. There's no algorithm validation — the middleware blindly assumes HS256.
- **Impact:** Algorithm confusion could allow bypass of admin page protection.
- **Suggested fix:** Parse the JWT header to verify `alg === 'HS256'` before signature verification, or use a proper JWT library in the middleware.

**[CR-003]** `recalc-ratings` endpoint uses raw SQL without parameterized inputs

- **File:** `src/app/api/admin/recalc-ratings/route.ts:17-30`
- **Issue:** While the current raw SQL queries don't take user input (they operate on all rows), the pattern of `$executeRaw` with template literals is safe here only because there are no interpolated values. However, the second query (`WHERE NOT EXISTS`) runs as a separate statement — if the transaction fails between the two queries, ratings could be left in an inconsistent state (first query updates recipes with ratings, second resets those without, but a partial failure leaves some recipes with stale data).
- **Impact:** Inconsistent rating data if transaction partially fails. Low severity currently but the pattern is fragile.
- **Suggested fix:** Both queries are already in a `$transaction`, which is correct. Add error handling specific to each query to identify which failed.

**[CR-004]** No CSRF protection on state-changing cookie-authenticated endpoints

- **File:** `src/middleware.ts` / `src/lib/utils/auth.ts:13-15`
- **Issue:** After migrating to httpOnly cookies, all POST/PUT/DELETE endpoints accept authentication via the cookie alone (no Bearer token required). The `SameSite: strict` cookie flag helps, but `extractBearerToken` falls back to cookie auth without any CSRF token validation. A malicious site could craft form submissions or fetch requests that piggyback on the cookie.
- **Impact:** CSRF attacks could modify user data, delete recipes, follow users, etc.
- **Suggested fix:** Implement CSRF token validation for all state-changing requests when using cookie auth. Either require a custom header (e.g., `X-CSRF-Token`) or use the double-submit cookie pattern.

#### HIGH

**[CR-005]** Race condition in cooked recipe creation despite transaction

- **File:** `src/app/api/cooked-recipes/route.ts:93-100`
- **Issue:** The duplicate check inside the transaction uses `findFirst` with `cookedAt: { gte: today }`, but `today` is computed outside the transaction (line 83-84). Between computing `today` and entering the transaction, the clock could tick past midnight, causing the check to use a stale date boundary.
- **Impact:** Potential duplicate cooked recipe entries near midnight.
- **Suggested fix:** Move `today` computation inside the transaction callback.

**[CR-006]** `DELETE /api/cooked-recipes` is not atomic — ownership check and delete are separate queries

- **File:** `src/app/api/cooked-recipes/route.ts:164-175`
- **Issue:** Two separate queries: `findFirst` to verify ownership, then `delete`. Between the two, another request could delete the same record, causing the delete to throw.
- **Impact:** 500 errors under concurrent requests.
- **Suggested fix:** Use `deleteMany` with both `id` and `userId` in the where clause, then check the count.

**[CR-007]** Comment PATCH endpoint reads comment outside transaction, then writes inside

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:42-57`
- **Issue:** `existingComment` is fetched before the transaction starts (line 42). The ownership check and the update are not atomic. Between the read and the transaction, the comment could be deleted or modified by another request.
- **Impact:** Stale data issues, potential 500 errors on race conditions.
- **Suggested fix:** Move the `findUnique` and all checks inside the transaction.

**[CR-008]** Notification polling has no authentication check for `fetchNotifications` return value

- **File:** `src/components/Navigation.tsx:192-194`
- **Issue:** `if (!response)` check on line 192 guards against undefined responses, but there's no handling for 401/403 responses. If the token expires during a session, the component will silently fail with `console.error` and keep polling with the stale token, incrementing `consecutiveFailures` but never logging the user out or refreshing the token.
- **Impact:** Stale sessions continue polling indefinitely with expired tokens, wasting server resources.
- **Suggested fix:** On 401 response, trigger logout or token refresh instead of just logging.

**[CR-009]** `GET /api/recipes/[id]/comments` does not validate `recipeId` format

- **File:** `src/app/api/recipes/[id]/comments/route.ts:10-12`
- **Issue:** The GET handler uses `recipeId` directly in a Prisma query without UUID validation. The POST handler validates with `UUID_REGEX`, but GET does not. Invalid IDs will cause Prisma to throw.
- **Impact:** Unhandled exceptions returning 500 instead of 400 for malformed IDs.
- **Suggested fix:** Add `if (!UUID_REGEX.test(recipeId))` check at the start of the GET handler.

**[CR-010]** `GET /api/recipes/match` loads up to 100 recipes into memory and iterates all of them

- **File:** `src/app/api/recipes/match/route.ts:62-66`
- **Issue:** Fetches 100 recipes with all their ingredients into memory, then iterates through all of them with nested loops for matching. With large ingredient lists, this is O(recipes _ ingredients _ pantryItems).
- **Impact:** Memory and CPU pressure under load. Will degrade as recipe count grows.
- **Suggested fix:** Consider database-level ingredient matching or limit recipes fetched based on ingredient overlap. At minimum, increase the `take` limit gradually with pagination rather than loading 100 at once.

#### MEDIUM

**[CR-011]** `search` API route exposes user emails in raw query, relies on client-side stripping

- **File:** `src/app/api/search/route.ts:29`
- **Issue:** `userService.searchUsers` returns users including email, then the route strips it with `.map(({ email, ...rest }) => rest)`. But `searchUsers` in `UserService` uses `userRepository.search()` which returns full `User` objects including password hash. The password is stripped in `UserService.searchUsers`, but the email leaks to the API response before being stripped. If someone adds a new consumer of `searchUsers` without stripping, emails leak.
- **Impact:** Emails could leak if the stripping pattern is not consistently applied.
- **Suggested fix:** Have the repository `search` method use `select` to exclude sensitive fields at the query level.

**[CR-012]** `profile/route.ts` fetches up to 50 saved recipes without pagination controls

- **File:** `src/app/api/users/[username]/profile/route.ts:114-119`
- **Issue:** `savedRecipes` are fetched with `take: 50` hardcoded. No pagination parameters are accepted. For users with many saved recipes, this returns incomplete data with no way to load more.
- **Impact:** Users cannot see all their saved recipes on their profile.
- **Suggested fix:** Accept pagination parameters or document the 50-item limit in the response.

**[CR-013]** `PersistentSearchBar` creates a new `AbortController` on every query change but doesn't abort previous

- **File:** `src/components/search/PersistentSearchBar.tsx:122-145`
- **Issue:** The `useEffect` cleanup calls `controller.abort()`, but since the debounced `setTimeout` captures the controller in closure, if the timeout fires before cleanup, the fetch starts and can't be aborted by the new effect's controller. The cleanup clears the timeout AND aborts, but there's a window where the fetch has started (timeout fired) but the cleanup hasn't run yet (React batching).
- **Impact:** Stale search results could overwrite newer ones under rapid typing.
- **Suggested fix:** Use a ref for the AbortController so the latest one is always accessible.

**[CR-014]** `RecipeFeed` infinite scroll uses `window.scrollY` which doesn't account for all scroll containers

- **File:** `src/components/recipe/RecipeFeed.tsx:173-180`
- **Issue:** The scroll handler checks `window.innerHeight + window.scrollY >= document.documentElement.scrollHeight - 500`. This only works when the page itself scrolls. If the feed is inside a scrollable container (not the case currently, but fragile), it breaks.
- **Impact:** Infinite scroll could stop working if layout changes.
- **Suggested fix:** Use `IntersectionObserver` on a sentinel element at the bottom of the list instead of scroll event listeners.

**[CR-015]** `layout.tsx` inline script uses `dangerouslySetInnerHTML` with theme detection

- **File:** `src/app/layout.tsx:91-114`
- **Issue:** While the nonce is applied, the inline script accesses `localStorage` and manipulates DOM classes. If `localStorage.getItem('themeMode')` returns an unexpected value (e.g., injected via devtools), the script doesn't sanitize it. The current code only checks `=== 'dark'` which is safe, but the pattern is fragile.
- **Impact:** Low risk currently due to strict equality check, but the pattern invites future vulnerabilities.
- **Suggested fix:** No immediate action needed, but add a comment noting the security consideration.

**[CR-016]** Cloudinary URL validation doesn't check protocol in `comments/route.ts`

- **File:** `src/app/api/recipes/[id]/comments/route.ts:94-105`
- **Issue:** The imageUrl validation checks `url.protocol` is `http:` or `https:` and hostname is `res.cloudinary.com`. But the `URL` constructor accepts protocols like `javascript:` if the hostname check passes first. Actually, `javascript:` URLs wouldn't have `res.cloudinary.com` as hostname, so this is safe. However, the validation in `recipes/[id]/route.ts:55-63` (PUT handler) does NOT check the protocol at all — it only checks hostname and pathname.
- **Impact:** Recipe image URLs could potentially use non-HTTPS protocols.
- **Suggested fix:** Add protocol check to `recipes/[id]/route.ts` PUT handler:

```ts
if (!['http:', 'https:'].includes(imgUrl.protocol)) {
  return NextResponse.json({ error: 'Invalid image URL protocol' }, { status: 400 });
}
```

**[CR-017]** `username` route parameter is not sanitized across multiple endpoints

- **File:** `src/app/api/users/[username]/follow/route.ts`, `unfollow/route.ts`, `followers/route.ts`, etc.
- **Issue:** The `username` parameter from the URL is passed directly to `userService.getUserByUsername()` which queries the database. While Prisma parameterizes queries (preventing SQL injection), there's no length or format validation. Extremely long usernames or special characters could cause unexpected behavior.
- **Impact:** Potential for DoS via very long username parameters.
- **Suggested fix:** Add username format validation (alphanumeric + underscore, max 30 chars) at the route level.

**[CR-020]** Multiple admin pages duplicate the same auth redirect pattern

- **File:** `src/app/admin/comments/page.tsx:58-62`, `admin/recipes/page.tsx`, `admin/users/page.tsx`
- **Issue:** Every admin page has the same `if (!authLoading && (!user || !isAdmin)) { router.push('/'); return; }` pattern. This is duplicated across 4 files.
- **Impact:** Maintenance burden — changes to auth redirect logic must be applied in all files.
- **Suggested fix:** Extract into a shared `useAdminGuard()` hook or wrap admin pages in a shared layout component.

**[CR-021]** `toLocaleDateString()` used without locale parameter in admin tables

- **File:** `src/app/admin/comments/page.tsx:133`, `admin/recipes/page.tsx:175`, `admin/users/page.tsx:205`
- **Issue:** `new Date(comment.createdAt).toLocaleDateString()` uses the browser's default locale, which varies between users and SSR.
- **Impact:** Inconsistent date formatting between server and client, potential hydration mismatches.
- **Suggested fix:** Pass explicit locale: `toLocaleDateString('en-US')` or use `date-fns` format.
