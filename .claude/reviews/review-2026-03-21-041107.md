### Findings

#### CRITICAL

**[CR-001]** Fire-and-forget image cleanup batches are not awaited and lose backpressure

- **File:** `src/app/api/users/profile/route.ts:97-107` (DELETE handler)
- **Issue:** The `for` loop fires `Promise.allSettled` for each batch but never `await`s them. Each iteration spawns a new untracked promise. If `imageUrls` contains hundreds of URLs (user with many posts), all batches launch concurrently — the `BATCH_SIZE = 10` provides zero throttling because the outer loop doesn't wait for each batch to settle before starting the next.
- **Impact:** Under load this defeats the stated "10 at a time" concurrency limit, potentially spawning hundreds of concurrent Cloudinary API calls, exhausting outbound connections or hitting Cloudinary rate limits. The response returns before any cleanup starts, so failures are silently lost if the process exits.
- **Suggested fix:**

```ts
if (imageUrls.length > 0) {
  const BATCH_SIZE = 10;
  // Fire-and-forget but respect batch concurrency
  (async () => {
    for (let i = 0; i < imageUrls.length; i += BATCH_SIZE) {
      const batch = imageUrls.slice(i, i + BATCH_SIZE);
      const results = await Promise.allSettled(batch.map((url) => cleanupCloudinaryImage(url)));
      const failures = results
        .map((r, j) => (r.status === 'rejected' ? { url: batch[j], reason: r.reason } : null))
        .filter(Boolean);
      if (failures.length > 0)
        logServerError('Failed to cleanup images for deleted account', failures);
    }
  })().catch((err) => logServerError('Unhandled error during account image cleanup', err));
}
```

**[CR-002]** `POST /api/recipes` swallows service-layer validation errors that don't start with a specific prefix

- **File:** `src/app/api/recipes/route.ts:228-232`
- **Issue:** The outer catch checks `error.message.startsWith('Recipe validation failed:')`. If `recipeService.validateRecipeData` throws an error with a different message format (e.g., from a downstream dependency or future refactor), it falls through to the generic 500 response, hiding the actual problem from the client and masking bugs.
- **Impact:** Legitimate validation failures surface as opaque 500 errors. Debugging requires log trawling. Any change to the service layer's error message format silently breaks client-facing error reporting.
- **Suggested fix:** Use a typed error class instead of string-prefix matching:

```ts
// In domain/errors.ts
export class RecipeValidationError extends Error {
  constructor(public errors: string[]) {
    super(`Recipe validation failed: ${errors.join(', ')}`);
    this.name = 'RecipeValidationError';
  }
}

// In the catch block
if (error instanceof RecipeValidationError) {
  return NextResponse.json({ error: error.message }, { status: 400 });
}
```

**[CR-004]** `DELETE /api/users/profile` — transaction timeout unbounded with potentially large data sets

- **File:** `src/app/api/users/profile/route.ts:85-113`
- **Issue:** The transaction reads all user posts (with full `instructions` JSON), all comments, and deletes the user — all without any `SET LOCAL statement_timeout`. A user with thousands of posts each containing large instruction JSON blobs could cause this transaction to run for a very long time, holding locks and a DB connection.
- **Impact:** Connection pool exhaustion under concurrent account deletions. Long-held locks on cascade-deleted rows block other queries.
- **Suggested fix:** Add a statement timeout inside the transaction and paginate if needed:

```ts
const imageUrls = await prisma.$transaction(
  async (tx) => {
    await tx.$executeRaw`SET LOCAL statement_timeout = '10s'`;
    // ... rest of transaction
  },
  { timeout: 12000 }
);
```

**[CR-005]** Recipe match endpoint leaks ingredient data from private users' recipes in edge case

- **File:** `src/app/api/recipes/match/route.ts:154-160`
- **Issue:** Phase 3 re-fetches recipes with `user: { isPrivate: false }` filter, but the `missingIngredients` array in `matchLookup` was computed in Phase 2 from `allCandidates` fetched in Phase 1. If a user's account is toggled to private between Phase 1 and Phase 3, the recipe is filtered out of the final response — correct. However, if the privacy filter in Phase 1's raw SQL or Prisma query is ever accidentally removed or bypassed, `missingIngredients` would contain ingredient names from private users' recipes. More immediately: the Phase 1 raw SQL query filters on `u."isPrivate" = false` but the `else` branch (line ~117 of match/route.ts) uses Prisma `findMany` with `user: { isPrivate: false }` — these two filters are semantically equivalent but maintained separately, creating drift risk.
- **Impact:** If the raw SQL branch is modified without updating the privacy filter, private recipe data leaks.
- **Suggested fix:** Extract the privacy filter into a shared constant or apply it only once in a canonical location. Consider moving the Prisma branch to also use the same raw SQL to eliminate the divergence.

**[CR-006]** `cookedRecipeSchema` allows `notes: null` which bypasses `striptags` sanitization path

- **File:** `src/app/api/cooked-recipes/route.ts:12` and `src/app/api/cooked-recipes/route.ts:157`
- **Issue:** The schema allows `notes` to be `nullable()`, and the sanitization at line 157 only runs `striptags` when `typeof notes === 'string'`. When `notes` is explicitly `null`, `validatedNotes` is set to `null` — this is fine. But when `notes` is `undefined` (field omitted), `validatedNotes` becomes `undefined`, which Prisma interprets as "don't update this field" on create. This inconsistency means the behavior differs between `{ notes: null }` (explicitly set to null in DB) and omitting notes (keeps whatever default Prisma has). This is not a security issue per se, but the comment says "Strip HTML from notes to prevent XSS" while the code has a path where `notes` value flows through unexamined.
- **Impact:** Inconsistent data state. If the schema default for `notes` ever changes from `null`, omitted notes could retain stale values on future update endpoints that reuse this pattern.
- **Suggested fix:**

```ts
const validatedNotes = typeof notes === 'string' ? striptags(notes.trim()) || null : null;
```

Always normalize to `null` when not a string, eliminating the `undefined` ambiguity.
