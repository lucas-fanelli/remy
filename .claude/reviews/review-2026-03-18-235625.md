## Code Review — 2026-03-18

### Summary

Solid architecture with clean separation of concerns and good test coverage. However, there are several security-hardening gaps, a bug in the admin user deletion flow, and the logout endpoint has overly strict origin validation that can lock users out.

### Findings

#### CRITICAL

**[CR-001]** Logout origin check denies logout when `Origin` header is absent

- **File:** `src/app/api/auth/logout/route.ts:12-15`
- **Issue:** The route requires `origin` to match `NEXT_PUBLIC_APP_URL`. Privacy extensions, non-browser clients, and some older browsers don't send `Origin` on same-origin requests. The check `if (!origin || origin !== appOrigin)` blocks these users from logging out entirely.
- **Impact:** Users are permanently stuck with an active session cookie they cannot clear. This is a denial-of-service on a security-critical function.
- **Suggested fix:** Remove the redundant origin check — the middleware already enforces CSRF via `Sec-Fetch-Site` + `Content-Type` for all POST requests. The `SameSite: lax` cookie provides the primary cross-site protection.

```typescript
// Remove lines 11-15. The middleware's CSRF check (Sec-Fetch-Site / Content-Type)
// already protects this endpoint. The SameSite:lax cookie prevents cross-site POST.
```

#### HIGH

**[CR-002]** Admin user DELETE returns 500 instead of 404 for non-existent users

- **File:** `src/app/api/admin/users/[id]/route.ts:34-45`
- **Issue:** If the target user doesn't exist, `tx.user.delete({ where: { id } })` throws Prisma `P2025`, which is not caught — only `LAST_ADMIN` is handled. The generic catch returns 500.
- **Impact:** Admin dashboard shows generic "Failed to delete user" instead of "User not found". Silent error masking makes debugging harder.
- **Suggested fix:**

```typescript
} catch (error) {
  if (error instanceof Error && error.message === 'LAST_ADMIN') {
    return NextResponse.json({ error: 'Cannot delete the last admin' }, { status: 400 });
  }
  if (
    error instanceof Prisma.PrismaClientKnownRequestError &&
    error.code === 'P2025'
  ) {
    return NextResponse.json({ error: 'User not found' }, { status: 404 });
  }
  console.error('Error deleting user:', error);
  return NextResponse.json({ error: 'Failed to delete user' }, { status: 500 });
}
```

**[CR-003]** Logout retry loop silently ignores HTTP error responses

- **File:** `src/contexts/AuthContext.tsx:106-118`
- **Issue:** The retry loop catches network exceptions but ignores non-ok HTTP responses (e.g., 403 from the origin check in CR-001). If `response.ok` is false, the loop continues to the next attempt with no error handling, then exits silently.
- **Impact:** The cookie is never cleared and the user believes they logged out. The `auth:logout-failed` event only fires on network exceptions, not HTTP errors.
- **Suggested fix:**

```typescript
for (let attempt = 0; attempt < 2; attempt++) {
  try {
    const response = await fetch('/api/auth/logout', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      credentials: 'same-origin',
    });
    if (response.ok) return; // Success — done
    if (attempt === 1) {
      console.warn('Logout failed with status:', response.status);
      window.dispatchEvent(new CustomEvent('auth:logout-failed'));
    }
  } catch {
    if (attempt === 1) {
      console.warn('Failed to clear auth cookie server-side.');
      window.dispatchEvent(new CustomEvent('auth:logout-failed'));
    }
  }
}
```

**[CR-004]** Recipe match SQL query bypasses GIN index with leading-wildcard LIKE

- **File:** `src/app/api/recipes/match/route.ts:96-101`
- **Issue:** The query builds `lower(elem->>'name') LIKE '%chicken%' ESCAPE '\\'` conditions. Leading `%` wildcards prevent PostgreSQL from using the GIN index on `ingredients`. This forces a sequential scan of all recipe ingredient arrays.
- **Impact:** At scale (thousands of recipes), this endpoint becomes a database bottleneck. The `LIMIT 200` mitigates but doesn't fix the fundamental scan cost.
- **Suggested fix:** Use jsonb `@>` containment or `EXISTS` with `jsonb_array_elements` and exact equality after normalization, which can leverage the GIN index:

```sql
-- Instead of LIKE, use normalized name equality:
WHERE EXISTS (
  SELECT 1 FROM jsonb_array_elements(p.ingredients) elem
  WHERE lower(elem->>'name') = ${normalizedName}
)
```

#### MEDIUM

**[CR-005]** Pagination count query not transactional with data query

- **File:** `src/app/api/recipes/route.ts:102,135`
- **Issue:** `prisma.post.findMany` and `prisma.post.count` are separate queries without a transaction. Between the two calls, recipes can be created or deleted, causing `total` to be inconsistent with the actual result set.
- **Impact:** Clients may calculate incorrect pagination (e.g., showing "Page 5 of 3" or missing the last page). Race condition probability increases under load.
- **Suggested fix:** Run both in parallel via `Promise.all` (still not transactional but reduces the window) or wrap in `prisma.$transaction`:

```typescript
const [recipes, total] = await Promise.all([
  prisma.post.findMany({ where, include: {...}, orderBy, take: limit, skip: offset }),
  prisma.post.count({ where }),
]);
```

**[CR-006]** RecipeCard console.warn fires on every render for non-Cloudinary images

- **File:** `src/components/recipe/RecipeCard.tsx:62-64`
- **Issue:** `console.warn` about non-Cloudinary URLs runs unconditionally in the component body. Each re-render produces another warning line.
- **Impact:** Console spam in development and production, obscuring real warnings.
- **Suggested fix:** Use a `useEffect` with the recipe ID as dependency, or a module-level `Set` to warn once per recipe:

```typescript
const warnedRecipes = new Set<string>();
// Inside component:
if (recipe.imageUrl && !isCloudinaryUrl(recipe.imageUrl) && !warnedRecipes.has(recipe.id)) {
  warnedRecipes.add(recipe.id);
  console.warn(`RecipeCard: non-Cloudinary image URL for recipe ${recipe.id}`);
}
```

**[CR-007]** Notification polling jitter on tab focus is excessive (up to 30 seconds)

- **File:** `src/hooks/useNotificationPolling.ts:143`
- **Issue:** `Math.random() * 30000` delays notification fetch by up to 30 seconds when the user returns to the tab. Users expect notifications to update promptly when they switch back.
- **Impact:** Degraded UX — users see stale notification counts for up to 30 seconds after tab switch.
- **Suggested fix:** Reduce to 1-3 seconds:

```typescript
const jitter = Math.random() * 3000; // 0-3 seconds, not 0-30
```

**[CR-008]** Static arrays recreated on every render in Navigation component

- **File:** `src/components/Navigation.tsx:258-271`
- **Issue:** `desktopNavItems` and `mobileNavItems` are declared inside the component body. They're pure constants that don't depend on state, but are recreated on every render.
- **Impact:** Unnecessary GC pressure and reference changes that could trigger child re-renders. Move to module scope.

**[CR-009]** Client-side avatar magic byte validation less strict than server

- **File:** `src/components/profile/EditProfileModal.tsx:96-100`
- **Issue:** Client validates JPEG as `bytes[0] === 0xFF && bytes[1] === 0xD8` (2 bytes), but the server's `validateImageMagicBytes` checks `buffer[0] === 0xff && buffer[1] === 0xd8 && buffer[2] === 0xff` (3 bytes). A file passing client validation may fail server validation.
- **Impact:** User selects a file, sees "New photo selected", clicks Save, then gets an upload error. Confusing UX.
- **Suggested fix:** Add the third byte check on the client:

```typescript
const isJpeg = bytes[0] === 0xff && bytes[1] === 0xd8 && bytes[2] === 0xff;
```
