## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured, but has several security gaps in CSRF/auth handling, race conditions in client-side state, missing input sanitization, and inconsistent error handling patterns across API routes.

### Findings

#### CRITICAL

**[CR-001]** Cloudinary URL validation bypass via double-encoding

- **File:** `src/app/api/recipes/[id]/comments/route.ts:89-100`, also in `[commentId]/route.ts`, `recipes/route.ts`, `recipes/[id]/route.ts`, `users/profile/route.ts`
- **Issue:** `decodeURIComponent(url.pathname)` is called once, but an attacker can double-encode `..` as `%252e%252e`. After one decode it becomes `%2e%2e`, passing the `includes('..')` check. The browser/Cloudinary then decodes it again to `..`, enabling path traversal within the Cloudinary domain.
- **Impact:** Attacker could reference arbitrary Cloudinary resources or potentially inject URLs that resolve to unintended images.
- **Suggested fix:** Decode in a loop until stable, or reject any URL containing `%` after decoding:

```ts
const decodedPath = decodeURIComponent(url.pathname);
if (decodedPath.includes('..') || decodedPath.includes('%')) {
  return NextResponse.json({ error: 'Invalid image URL' }, { status: 400 });
}
```

**[CR-002]** Logout endpoint lacks CSRF protection for cookie-clearing

- **File:** `src/app/api/auth/logout/route.ts:6-8`
- **Issue:** The logout endpoint only checks `Content-Type: application/json`. The middleware CSRF check allows `application/json` as proof of same-origin, but a crafted cross-origin fetch with `Content-Type: application/json` will trigger a CORS preflight which blocks it — _unless_ the victim's browser has a bug or extension that bypasses preflight. The comment claims this is safe, but a malicious site could use `navigator.sendBeacon` with a Blob of type `application/json` to bypass preflight on some browsers.
- **Impact:** Cross-site logout attack — attacker can force-logout users, causing session disruption.
- **Suggested fix:** Check the `Origin` or `Referer` header matches the app's own origin, or require the auth token in the request body.

**[CR-003]** `cooked-recipes` POST has no rate limit for pantry deduction

- **File:** `src/app/api/cooked-recipes/route.ts:85-95`
- **Issue:** The 24-hour duplicate check uses `cookedAt >= twentyFourHoursAgo`, but a user can mark the same recipe as cooked once per rolling 24h window, each time deducting pantry ingredients. There's no cap on total deductions — a user could drain their pantry by cooking the same recipe repeatedly on a 24h cycle, or different recipes rapidly.
- **Impact:** Pantry quantities could go negative or be drained unintentionally if the client sends rapid requests for different recipes. The `force: true` flag bypasses insufficient-ingredient checks entirely.
- **Suggested fix:** Add a configurable daily cook limit per user, or make `force` require re-authentication.

#### HIGH

**[CR-004]** Recipe match endpoint is vulnerable to ReDoS via crafted pantry names

- **File:** `src/app/api/recipes/match/route.ts:73-80`
- **Issue:** `escapeLike` handles `%`, `_`, `\` but the pantry item names themselves are user-controlled strings inserted into a `LIKE` pattern via `%${escapeLike(name)}%`. While Prisma's tagged template parameterizes the value, the `LIKE` pattern matching itself can be slow with certain patterns on unindexed columns. More critically, `nameConditions` builds up to 100 SQL `OR` conditions, which on large tables without the GIN index can cause full table scans.
- **Impact:** Slow queries that could cause request timeouts or database resource exhaustion.
- **Suggested fix:** Enforce the GIN index as required (fail fast if missing), and cap `nameConditions` to 20 instead of 100.

**[CR-005]** Admin user deletion race condition — admin count check is outside the delete transaction's SELECT...FOR UPDATE

- **File:** `src/app/api/admin/users/[id]/route.ts:36-45`
- **Issue:** The transaction reads `userToDelete.role` and counts admins, but there's no `SELECT ... FOR UPDATE` on the users being counted. Two concurrent requests could both read `adminCount = 2`, then both proceed to delete, leaving zero admins.
- **Impact:** All admin users could be deleted, locking everyone out of admin functionality.
- **Suggested fix:** Add `FOR UPDATE` on the admin count query:

```ts
const adminCount = await tx.$queryRaw`SELECT COUNT(*) FROM "User" WHERE role = 'ADMIN' FOR UPDATE`;
```

**[CR-006]** `AuthContext` logout is optimistic but doesn't redirect to login

- **File:** `src/contexts/AuthContext.tsx:101-119`
- **Issue:** `logout()` clears `user` state immediately (optimistic), but the server-side cookie clear can fail silently (caught in the retry loop). If both retries fail, the httpOnly cookie persists and the user appears logged out in the UI but is still authenticated server-side. The `auth:logout-failed` event is dispatched, but the Navigation component only shows a warning snackbar — it doesn't force-clear state or redirect.
- **Impact:** User thinks they're logged out but the auth cookie is still valid. If someone else accesses the browser, they're still authenticated.
- **Suggested fix:** On logout failure, redirect to the login page anyway and show a prominent warning that the session may persist.

**[CR-007]** `RecipeFeed` optimistic like can show wrong state on JSON parse failure

- **File:** `src/components/recipe/RecipeFeed.tsx:285-310`
- **Issue:** When the like API returns `200 OK` but the response body isn't valid JSON (e.g., empty body from a proxy), the catch block tries to refetch the status. If the refetch also fails, it reverts to `currentLikeState` and shows a warning. However, the actual like _was_ created server-side (the POST returned 200). The UI now shows the wrong state.
- **Impact:** UI shows unliked but the like exists in DB, causing confusion on reload.
- **Suggested fix:** On parse failure after 200, keep the optimistic state (it's likely correct since the server returned 200).

#### MEDIUM

**[CR-008]** `useNotificationPolling` circuit breaker resets on visibility change even when breaker was tripped due to server errors

- **File:** `src/hooks/useNotificationPolling.ts:126-133`
- **Issue:** When the tab becomes visible, if `timeSinceLastFailure > 2 minutes`, the circuit breaker and failure timestamps are fully reset. This means a server that's consistently returning 500s will be hammered again every time the user switches tabs, defeating the purpose of the circuit breaker.
- **Impact:** Server under load receives additional traffic from clients that should be backing off.
- **Suggested fix:** Only reset on visibility change if the circuit breaker hasn't been tripped, or require a longer cooldown (e.g., 5 minutes matching `breakerTrippedAt`).

**[CR-009]** `normalizeIngredientName` strips legitimate ingredient names

- **File:** `src/lib/utils/ingredients.ts:20-43`
- **Issue:** The `noStripSuffixWords` set is hardcoded and incomplete. Words like "molasses", "couscous" are in the set, but common ingredients like "quinoa", "hummus" variants, or compound names like "cream cheese" (which ends in "e") could be incorrectly stemmed. The plural stripping of `oes` (line 37) would turn "quinoas" → "quinoa" correctly but "heroes" → "hero" (an ingredient name nobody uses, but shows fragility).
- **Impact:** Pantry-to-recipe matching produces false negatives for ingredients with edge-case names.
- **Suggested fix:** Use a well-tested stemming library (e.g., `natural` or `stemmer`) instead of hand-rolled suffix stripping.

**[CR-010]** `CommentsSection` orphaned Cloudinary images on failed comment POST

- **File:** `src/components/recipe/CommentsSection.tsx:137-145`
- **Issue:** If the image upload succeeds but the comment POST fails, the uploaded image remains in Cloudinary with no database reference. The code acknowledges this with comments about a "periodic server-side cron job," but no such job is configured in the codebase.
- **Impact:** Cloudinary storage grows unboundedly with orphaned images over time.
- **Suggested fix:** Either implement the cleanup script as a cron job (the script exists at `src/scripts/cleanup-orphaned-images.ts` but isn't scheduled), or delete the uploaded image in the catch block.

**[CR-011]** Missing `Content-Type` check on most API POST/PUT/PATCH routes

- **File:** Multiple API routes (e.g., `src/app/api/recipes/route.ts`, `src/app/api/pantry/route.ts`)
- **Issue:** Only the logout endpoint checks `Content-Type`. Other mutation endpoints call `request.json()` which will throw on non-JSON bodies, but the error is caught as a generic 400 "Invalid JSON body" — not a 415 Unsupported Media Type. This is inconsistent and could mask CSRF-like attacks using form submissions.
- **Impact:** Unclear error messages; middleware CSRF check already covers this partially but defense-in-depth is missing.
- **Suggested fix:** Add a shared helper that validates Content-Type before parsing JSON.

**[CR-012]** `EditProfileModal` client-side magic byte validation is insufficient

- **File:** `src/components/profile/EditProfileModal.tsx:83-91`
- **Issue:** The client reads only the first 4 bytes via `file.slice(0, 4)` to check magic bytes. WebP requires checking bytes 8-11 (`WEBP`), so a WebP file would fail the client-side check despite being allowed by the server.
- **Impact:** Users uploading WebP avatars get a client-side rejection error even though the format is allowed.
- **Suggested fix:** Read at least 12 bytes (matching `validateImageMagicBytes` which checks `buffer[8..11]`).

**[CR-013]** `PersistentSearchBar` search results don't escape HTML in recipe titles

- **File:** `src/components/search/PersistentSearchBar.tsx:400-425`
- **Issue:** Recipe titles and user names are rendered directly via `{recipe.title}` in `ListItemText`. React escapes these by default, so there's no XSS. However, if a recipe title contains characters like `<script>`, it'll display as literal text which could confuse users.
- **Impact:** Low — React's JSX escaping prevents actual XSS, but displayed content could be misleading.
- **Suggested fix:** Sanitize recipe titles on creation/update (server-side validation).

**[CR-014]** `recalc-ratings` advisory lock uses single-key form with hardcoded second key

- **File:** `src/app/api/admin/recalc-ratings/route.ts:22`
- **Issue:** `pg_advisory_xact_lock(${PG_ADVISORY_LOCK_RECALC_RATINGS}, 0)` uses two-key form but the second key is always 0. The constant `48879` (0xBEEF) is fine but undocumented — if another feature uses the same pair, they'll deadlock.
- **Impact:** Potential deadlock if another feature accidentally uses the same advisory lock keys.
- **Suggested fix:** Document the lock key registry in a central location, or use the single-key `bigint` form instead.

#### LOW

**[CR-015]** `about/page.tsx` hardcodes `BRANDING.colors.primary` in inline gradient

- **File:** `src/app/about/page.tsx:88-89`
- **Issue:** Uses `BRANDING.colors.primary` and `BRANDING.colors.secondary` in a CSS `linear-gradient` string but doesn't use the MUI theme palette. This means the gradient won't adapt to dark mode.
- **Impact:** Minor visual inconsistency in dark mode.
- **Suggested fix:** Use `theme.palette.primary.main` via the `sx` prop's callback form.

**[CR-016]** `Footer` email validation regex doesn't match RFC 5322

- **File:** `src/components/Footer.tsx:53`
- **Issue:** `isValidEmail` uses `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` which allows strings like `a@b.c` (single char TLD) and `user@-domain.com`. This is a client-side mailto link, so it's low-risk.
- **Impact:** Users can enter technically invalid emails for the contact form.
- **Suggested fix:** Use a stricter regex or just rely on `<input type="email">` browser validation.

**[CR-017]** `SearchResults` component truncates description at character 50 without word boundary

- **File:** `src/components/SearchResults.tsx:174`
- **Issue:** `recipe.description.substring(0, 50)` can cut mid-word. Should use word boundary truncation.
- **Impact:** Poor UX — truncated words look broken.
- **Suggested fix:** Find the last space before index 50 and truncate there.

**[CR-018]** Test file uses `any` type extensively

- **File:** `src/components/recipe/__tests__/RecipeFeed.test.tsx:86` and many other test files
- **Issue:** `mockMotion: any`, `const { rerender } = render(...)`, mock functions typed as `any`. While acceptable in tests, it reduces confidence that mocks match actual interfaces.
- **Impact:** Tests may pass but not catch type-level regressions.
- **Suggested fix:** Use proper type annotations for mocks where feasible.
