**[CR-001]** Pantry item restoration on DELETE doesn't verify pantry ownership

- **File:** `src/app/api/cooked-recipes/route.ts:247-262`

**[CR-002]** `deductedIngredients` stored as JSON is trusted without schema validation on restore

- **File:** `src/app/api/cooked-recipes/route.ts:238-239`
- **Issue:** The `deductedIngredients` field is cast via `as unknown[]` and then individual fields are accessed with loose runtime checks. If the stored JSON was corrupted or tampered with (e.g., via direct DB access), the `amount` check passes but `name` could contain anything. The `striptags` call on create is good, but on restore the `name` is used in a `findFirst` query filter without sanitization — and a new `pantryItem` is created with `striptags(d.name)`, which is inconsistent with the original deduction path.
- **Impact:** Corrupted JSON could cause silent failures or inject unexpected pantry items.
- **Suggested fix:** Define a Zod schema for `DeductedIngredient[]` and parse the stored JSON through it before processing:

```typescript
const deductedSchema = z.array(
  z.object({
    name: z.string().min(1).max(200),
    amount: z.number().positive(),
    unit: z.string().max(50),
    pantryItemId: z.string().uuid().optional(),
  })
);
const parsed = deductedSchema.safeParse(cookedRecipe.deductedIngredients);
if (!parsed.success) {
  console.warn('Invalid deductedIngredients, skipping restore');
} else {
  for (const d of parsed.data) {
    /* ... */
  }
}
```

**[CR-003]** `validatedNotes` retains `null` but `striptags(null)` is never called — `undefined` passes through unchecked

- **File:** `src/app/api/cooked-recipes/route.ts:156`
- **Issue:** `notes` can be `null | undefined | string`. The expression `notes ? striptags(notes.trim()) : notes` means if `notes` is `null`, `validatedNotes` is `null`; if `notes` is `undefined`, `validatedNotes` is `undefined`. However, if `notes` is an empty string `""`, `striptags` is skipped and `validatedNotes` is `""` (falsy). This is fine, but the real issue is that `notes` is typed as `string | null | undefined` from Zod's `.optional().nullable()`, so `trim()` on a non-null, non-undefined empty string still works. The logic is correct but fragile — a future schema change allowing `0` or other falsy values would silently bypass sanitization.
- **Impact:** Low immediate risk, but a latent XSS vector if schema changes.
- **Suggested fix:**

```typescript
const validatedNotes = typeof notes === 'string' ? striptags(notes.trim()) || null : notes;
```

**[CR-004]** `hasMore` logic is incorrect when duplicates are filtered

- **File:** `src/components/recipe/RecipeFeed.tsx:139`
- **Issue:** `setHasMore(data.recipes.length === PAGE_SIZE)` is set based on the raw API response count, but duplicates are filtered out on line 129. If the API returns 12 recipes but 3 are duplicates, only 9 are added, yet `hasMore` is `true`. The next page fetch uses `recipesLengthRef.current` as offset, which is 9 less than expected, causing the same recipes to be fetched again — creating an infinite loop of duplicate fetches that never advances.
- **Impact:** Infinite scroll gets stuck in a loop, wasting bandwidth and CPU.
- **Suggested fix:**

```typescript
// Use the actual count of new recipes added to determine hasMore
const newRecipes = data.recipes.filter((r: Recipe) => !existingIds.has(r.id));
setHasMore(newRecipes.length > 0 && data.recipes.length === PAGE_SIZE);
```

**[CR-005]** `rating_asc` sort puts `null` ratings first, surfacing unrated recipes

- **File:** `src/app/api/recipes/route.ts:98`
- **Issue:** Prisma sorts `null` values first in ascending order by default. `rating_asc` will show all unrated recipes (with `null` averageRating) before any rated ones, which is almost certainly not the intended UX.
- **Impact:** Users selecting "Lowest Rated" see a wall of unrated recipes instead of low-rated ones.
- **Suggested fix:** Add a filter to exclude null ratings for rating sorts, or use `nulls: 'last'`:

```typescript
case 'rating_asc':
  orderBy = [{ averageRating: { sort: 'asc', nulls: 'last' } }, { createdAt: 'desc' }, { id: 'asc' }];
  break;
```

**[CR-006]** Profile PUT allows setting avatar to `null` via `undefined` coercion, bypassing cleanup

- **File:** `src/app/api/users/profile/route.ts:43-48`
- **Issue:** `validatedData.avatar ?? undefined` converts `null` to `undefined`. If the user sends `{ avatar: null }` to clear their avatar, `profileData.avatar` becomes `undefined`, which Prisma interprets as "don't update this field" — so the avatar is never cleared. Meanwhile, the cleanup check on line 57 compares `currentUser.avatar !== updatedUser.avatar`, which will be equal (both the old URL), so no cleanup happens. The user cannot remove their avatar.
- **Impact:** Users cannot clear their avatar once set.
- **Suggested fix:** Handle `null` explicitly to clear the avatar:

```typescript
const profileData = {
  ...validatedData,
  fullName: validatedData.fullName === null ? null : validatedData.fullName,
  bio: validatedData.bio === null ? null : validatedData.bio,
  avatar: validatedData.avatar === null ? null : validatedData.avatar,
  website: validatedData.website === null ? null : validatedData.website,
};
```

**[CR-009]** `recipesLengthRef` can drift from actual `recipes` state

- **File:** `src/components/recipe/RecipeFeed.tsx:54,121,132-134`
- **Issue:** `recipesLengthRef.current` is updated inside `setRecipes` callbacks and in the reset path, but `setRecipes` is asynchronous — React batches state updates. If `loadRecipes` is called again before React flushes the state update, `recipesLengthRef` may be stale because it's set inside the state updater function (which hasn't run yet if React hasn't committed). The ref is then used as the `offset` for the next fetch.
- **Impact:** Could skip or duplicate recipes in rapid scroll scenarios.
- **Suggested fix:** Compute offset from a ref that's updated synchronously outside the state updater, or use a reducer pattern.

**[CR-012]** `scheduleNext` doesn't call itself after breaker auto-reset

- **File:** `src/hooks/useNotificationPolling.ts:152-161`
- **Issue:** When the circuit breaker cooldown expires (line 158-161), `pollingStoppedRef` is reset and `setIsPollingPaused(false)` is called, but `scheduleNext` only reaches this code path when it's already been called. After the breaker trips, `scheduleNext` returns early on line 162 (`return`). No timer calls `scheduleNext` again after the cooldown expires — the polling is permanently stopped until a visibility change or `retryNow` is called.
- **Impact:** Notification polling silently dies after a circuit breaker trip until the user manually switches tabs.
- **Suggested fix:** When the breaker trips, schedule a timeout for the cooldown duration:

```typescript
if (failureTimestampsRef.current.length >= 10) {
  // ... existing breaker code ...
  // Schedule auto-recovery
  polling.timeoutId = setTimeout(() => scheduleNext(), cooldownMs);
}
```

**[CR-013]** `allCandidates` SQL query doesn't exclude private users' recipes
