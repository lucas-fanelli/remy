## Code Review — 2026-03-21

### Summary

Several API routes with transaction-heavy logic, notification polling, and recipe matching. The code is generally well-structured with good concurrency controls, but there are real bugs and security gaps that need attention.

### Findings

#### CRITICAL

**[CR-001]** DELETE account cleanup runs fire-and-forget async IIFE that can silently lose errors after response is sent

- **File:** `src/app/api/users/profile/route.ts:97-112`
- **Issue:** The batched Cloudinary cleanup runs in a detached `(async () => { ... })()` after the user is already deleted and the response is being sent. In serverless/edge environments (Vercel, etc.), the runtime may kill the function after the response is returned, silently dropping in-progress image deletions. The `.catch()` on the IIFE only catches the outer wrapper — individual batch iterations that throw after the response is sent will be swallowed by the runtime shutdown.
- **Impact:** Orphaned Cloudinary images accumulate with no indication they were missed. The comment says a cron script handles this, but if that script isn't running (or hasn't been deployed), images leak indefinitely.
- **Suggested fix:** Use `waitUntil()` from Next.js to keep the serverless function alive, or perform cleanup synchronously before returning the response:

```typescript
// Option 1: Use waitUntil (Next.js 14+)
import { waitUntil } from 'next/server';

const cleanupPromise = (async () => {
  for (const batch of batches) {
    const results = await Promise.allSettled(batch.map((url) => cleanupCloudinaryImage(url)));
    // ...logging...
  }
})();
waitUntil(cleanupPromise);
```

**[CR-002]** `statement_timeout` SET LOCAL in DELETE account transaction is ineffective against cascade deletes

- **File:** `src/app/api/users/profile/route.ts:93`
- **Issue:** `SET LOCAL statement_timeout = '10s'` applies per-statement, not per-transaction. The `tx.user.delete()` triggers CASCADE deletes across posts, comments, likes, ratings, follows, notifications, and pantry. Each cascaded DELETE is a separate statement. A user with thousands of posts, each with comments and likes, will produce cascaded deletes that individually stay under 10s but collectively hold the transaction (and its locks) for minutes, blocking other operations on those tables.
- **Impact:** Database connection pool exhaustion under load when deleting users with large amounts of content. Other requests queue up waiting for connections.
- **Suggested fix:** Add a transaction-level timeout alongside the statement timeout, and consider batching the cascade or using a background job for large accounts:

```typescript
await tx.$executeRaw`SET LOCAL statement_timeout = '10s'`;
// Add idle_in_transaction_session_timeout as a safety net
await tx.$executeRaw`SET LOCAL idle_in_transaction_session_timeout = '30s'`;
```

Or pass `{ timeout: 30000 }` to `prisma.$transaction()` as is done in the admin delete route.

**[CR-003]** Race condition: admin DELETE and user self-DELETE can execute concurrently on the same user

- **File:** `src/app/api/admin/users/[id]/route.ts:50-89` and `src/app/api/users/profile/route.ts:86-113`
- **Issue:** Admin delete uses `PG_ADVISORY_LOCK_ADMIN_DELETE` with key `0` (global admin lock). User self-delete in `profile/route.ts` uses no advisory lock at all. These two code paths can run concurrently on the same user. If the admin delete completes first and cascades all records, the user's self-delete transaction will fail with P2025 on `tx.user.delete()` — but the image collection queries (`tx.post.findMany`, `tx.comment.findMany`) would have already returned empty results (records already cascaded), so the self-delete path returns success but never cleans up images that the admin path collected. Meanwhile the admin path's cleanup may also fail if the serverless function was killed.
- **Impact:** Double-delete race can cause inconsistent cleanup, and neither path may successfully clean up all Cloudinary images.
- **Suggested fix:** Add a `SELECT ... FOR UPDATE` on the user row in the self-delete transaction, or use the same advisory lock namespace:

```typescript
// In profile/route.ts DELETE handler, inside the transaction:
await tx.$executeRaw`SELECT id FROM "User" WHERE id = ${user.id} FOR UPDATE`;
```

**[CR-004]** `IUserService.updateProfile` is unused — profile update bypasses the service layer

- **File:** `src/domain/services/IUserService.ts:15` and `src/app/api/users/profile/route.ts:16-68`
- **Issue:** The PUT handler in `profile/route.ts` directly calls `prisma.$transaction()` with raw Prisma queries instead of going through `IUserService.updateProfile()`. The service interface declares `updateProfile` but the route ignores it entirely. This means any business logic, validation, or side effects implemented in `UserService.updateProfile()` are silently bypassed.
- **Impact:** If business rules are added to `UserService.updateProfile()` (e.g., username change cooldown, bio content moderation), they won't apply to the actual profile update endpoint. The service layer becomes a lie — callers cannot trust the interface contract.
- **Suggested fix:** Route the update through the service layer, or if the service layer adds no value here, remove `updateProfile` from the interface to avoid confusion.

**[CR-005]** `deductPantryItems` matches only the first pantry item per ingredient — duplicate pantry entries are silently ignored

- **File:** `src/app/api/cooked-recipes/route.ts:56-63`
- **Issue:** `pantryItems.find()` returns the first match and adds it to `matchedPantryIds`. If a user has two pantry items with the same normalized name and unit (e.g., "flour 500g" and "flour 200g"), only the first is ever considered. If the first has insufficient quantity but the second could cover the difference, the recipe is flagged as insufficient.
- **Impact:** Users with split pantry entries (common after partial restocking) get false "insufficient ingredients" errors and must manually consolidate pantry items.
- **Suggested fix:** Aggregate quantities across all matching pantry items before checking sufficiency:

```typescript
const matchingItems = pantryItems.filter(
  (item) =>
    !matchedPantryIds.has(item.id) &&
    normalizeIngredientName(item.name) === normalizeIngredientName(ingredient.name) &&
    unitsMatch(item.unit, ingredient.unit)
);
const totalAvailable = matchingItems.reduce((sum, item) => sum + item.quantity, 0);
```

**[CR-006]** Pantry restoration in DELETE cooked-recipe has N+1 query pattern despite comment claiming otherwise

- **File:** `src/app/api/cooked-recipes/route.ts:261-290`
- **Issue:** The comment says "Hoist pantry lookup outside the loop to avoid N+1 queries" and `UserPantry` is fetched once, but inside the loop each iteration calls `tx.pantryItem.findFirst()` (by ID) and potentially `tx.pantryItem.findFirst()` again (by name). For a recipe with 20 deducted ingredients, this is up to 40 queries inside the transaction while holding an advisory lock.
- **Impact:** Transaction duration scales linearly with ingredient count, holding the advisory lock and blocking other cooked-recipe operations for that user.
- **Suggested fix:** Batch-fetch all relevant pantry items upfront:

```typescript
const pantryItemIds = validDeducted.map((d) => d.pantryItemId).filter(Boolean) as string[];
const existingItems = await tx.pantryItem.findMany({
  where: { id: { in: pantryItemIds }, pantry: { userId: user.id } },
});
const itemsById = new Map(existingItems.map((i) => [i.id, i]));
```

**[CR-007]** Recipe match endpoint returns `ingredients` JSON blob to the client in Phase 3 fetch but never uses it

- **File:** `src/app/api/recipes/match/route.ts:136`
- **Issue:** The Phase 3 query selects `ingredients: true` from the database, fetching potentially large JSON blobs (up to 100 ingredients per recipe, up to 60 recipes = 6000 ingredient objects). This data is never used in the response construction — `missingIngredients` comes from the Phase 2 match results, not from the Phase 3 query.
- **Impact:** Unnecessary data transfer from the database, increasing query time and memory usage. For 60 recipes with full ingredient lists, this could be 100KB+ of wasted I/O per request.
- **Suggested fix:** Remove `ingredients: true` from the Phase 3 select:

```typescript
select: {
  id: true,
  title: true,
  description: true,
  imageUrl: true,
  difficulty: true,
  cookingTime: true,
  prepTime: true,
  servings: true,
  // ingredients: true,  ← remove
  _count: { select: { likes: true, comments: true } },
  user: { select: { id: true, username: true, avatar: true } },
},
```

**[CR-008]** `RecipeFeed` never fetches the user's own like status — `liked` is always `false`

- **File:** `src/components/recipe/RecipeFeed.tsx:118`
- **Issue:** When building `newLikes`, the code hardcodes `liked: false` for every recipe. The `/api/recipes` endpoint does not return per-user like status, and no subsequent request fetches it. Users who previously liked a recipe will see an unfilled heart, and clicking it will attempt to unlike (toggling), producing confusing behavior.
- **Impact:** Like state is always wrong for returning users. Clicking "like" on an already-liked recipe will unlike it, and the UI will show the wrong count until the server response corrects it.
- **Suggested fix:** Either have the `/api/recipes` endpoint return `isLiked` when the user is authenticated, or fetch like status in a separate batch request after loading recipes.

**[CR-009]** Notification polling `markAllAsRead` sends POST without Content-Type but server may require it

- **File:** `src/hooks/useNotificationPolling.ts:186-191`
- **Issue:** `markAllAsRead` sends a POST to `/api/notifications` with `X-Requested-With: 'fetch'` but no `Content-Type` header and no body. If the notifications POST handler calls `requireJsonContentType()` (as other POST handlers in this codebase do), it will reject the request with 415. The function silently catches this error and logs it to console, so users never know their "mark all read" failed.
- **Impact:** "Mark all as read" may silently fail, leaving notifications permanently unread. The UI optimistically updates but the server state doesn't change, so notifications reappear as unread on next poll.
- **Suggested fix:** Verify the notifications POST endpoint's content-type requirements. If it requires JSON, add the header and body:

```typescript
const response = await fetch('/api/notifications', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-Requested-With': 'fetch',
  },
  body: JSON.stringify({}),
});
```
