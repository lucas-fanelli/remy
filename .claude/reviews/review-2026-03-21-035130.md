**[CR-001]** Double pantry restoration via concurrent DELETE race condition

- **File:** `src/app/api/cooked-recipes/route.ts:230-240`
- **Issue:** The advisory lock is acquired **after** `findFirst`. Two concurrent DELETE requests for the same cooked recipe both execute `findFirst` (both see the record before either commits), then serialize on the lock. The first request restores pantry items and deletes the record. The second request — which already passed the `if (!cookedRecipe) return null` check — proceeds to restore pantry items **a second time**, then fails on `delete` with P2025 (caught gracefully as 404). The pantry quantities are now inflated.
- **Impact:** Users can exploit this to **duplicate pantry items indefinitely**: cook a recipe (deducts ingredients), wait 1 hour, then fire two simultaneous DELETE requests. Each successful restoration doubles the returned amount. This is a data integrity violation and an economic exploit in any system where pantry items have value.
- **Suggested fix:** Move the advisory lock acquisition before the `findFirst` so the entire read-check-restore-delete sequence is serialized:

```typescript
const deleted = await prisma.$transaction(async (tx) => {
  // 1. Acquire per-user advisory lock FIRST to serialize the entire operation
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(${PG_ADVISORY_LOCK_COOKED_RECIPE}, hashtext(${user.id}))`;

  // 2. Now find the cooked recipe (only one concurrent request can reach this)
  const cookedRecipe = await tx.cookedRecipe.findFirst({
    where: { id: cookedRecipeId, userId: user.id },
    select: { id: true, postId: true, deductedIngredients: true, cookedAt: true },
  });

  if (!cookedRecipe) return null;

  // ... rest of restore + delete logic unchanged
});
```

**[CR-002]** Recipe creation daily limit bypass via TOCTOU race

- **File:** `src/app/api/recipes/route.ts:168-175`
- **Issue:** The daily recipe count check (`prisma.post.count`) and the subsequent recipe creation (`recipeService.createRecipe`) are not inside a transaction or protected by any lock. N concurrent POST requests all pass the count check simultaneously, then all create recipes, allowing a user to exceed `MAX_DAILY_RECIPES` by a factor of N.
- **Impact:** An attacker can spam-create recipes far beyond the daily limit by issuing concurrent requests, filling the database with content and consuming Cloudinary upload slots. The rate limit in middleware only throttles sequential requests — a single burst bypasses it.
- **Suggested fix:** Wrap the count check and creation in a serializable transaction, or use a per-user advisory lock similar to the cooked-recipes route:

```typescript
const recipe = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(${PG_ADVISORY_LOCK_RECIPE_CREATE}, hashtext(${user.id}))`;

  const twentyFourHoursAgo = new Date(Date.now() - 24 * 60 * 60 * 1000);
  const dailyPostCount = await tx.post.count({
    where: { userId: user.id, createdAt: { gte: twentyFourHoursAgo } },
  });
  if (dailyPostCount >= MAX_DAILY_RECIPES) {
    throw new Error('DAILY_LIMIT_REACHED');
  }

  // create recipe inside the same transaction...
});
```
