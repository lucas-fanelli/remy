### Summary

Three API route files with generally solid defensive coding, but several critical issues around data integrity, security, and error handling.

### Findings

#### CRITICAL

**[CR-001]** DELETE account cleanup IIFE silently swallows all errors

- **File:** `src/app/api/users/profile/route.ts:119`
- **Issue:** The fire-and-forget IIFE for Cloudinary cleanup catches and discards all errors with `.catch(() => {})`. While individual batch failures are logged inside the loop, if the entire async IIFE throws before entering the loop (e.g., `batches` iteration fails), the error is silently swallowed with no logging.
- **Impact:** Complete silent failure of image cleanup for deleted accounts — orphaned images accumulate in Cloudinary with zero visibility.
- **Suggested fix:**

```ts
})().catch((err) => logServerError('Unhandled error during account image cleanup', err));
```

**[CR-002]** `instructions` field treated as `unknown[]` without JSON type guard — runtime crash on malformed data

- **File:** `src/app/api/users/profile/route.ts:107-113`
- **Issue:** `post.instructions` is typed as `Prisma.JsonValue` (could be string, number, boolean, null, object, or array). The code checks `Array.isArray(post.instructions)` but then iterates and accesses `instr` properties without verifying each element is a non-null object. The `'image' in instr` check will throw a `TypeError` if `instr` is a primitive (e.g., `[1, "foo", null]`), crashing the entire transaction and preventing account deletion.
- **Impact:** A single recipe with malformed instruction JSON prevents the user from deleting their account — permanent data lock-in.
- **Suggested fix:** The existing guard `instr && typeof instr === 'object' && !Array.isArray(instr)` does handle this — disregard, the check is correct. Let me re-examine... The guard `if (instr && typeof instr === 'object' && !Array.isArray(instr) && 'image' in instr)` is actually safe. Retracted.

**[CR-003]** Race condition: `clearAuthCookie` called on a response that may have already been sent

- **File:** `src/app/api/users/profile/route.ts:133-134`
- **Issue:** `ApiResponseHelper.success()` returns a `NextResponse`. `clearAuthCookie(response)` mutates the response headers after construction. This is fine in Next.js (response isn't sent until returned), but the real issue is that `clearAuthCookie` is called only on the success response. If the transaction succeeds but the Cloudinary cleanup IIFE throws synchronously before the return (impossible in current code since it's async), the cookie is still cleared. However — the actual critical issue is: **if the user has multiple active sessions, the comment block claims other sessions are invalidated by DB lookup, but this is an assumption about `AuthService.validateToken` that is not enforced by code**. If someone adds JWT caching or token validation that skips the DB lookup, all other sessions remain valid after account deletion, with a deleted user's token still granting access to endpoints that don't query the user table.
- **Impact:** If `validateToken` is ever optimized (JWT-only), deleted users retain access across all other sessions. The comment documents this risk but there is no programmatic safeguard.
- **Suggested fix:** Add a runtime assertion or integration test that validates `validateToken` always performs a DB lookup:

```ts
// In a test file:
it('validateToken always queries the database', async () => {
  const user = await createTestUser();
  const token = await authService.createToken(user.id);
  await prisma.user.delete({ where: { id: user.id } });
  const result = await authService.validateToken(token);
  expect(result).toBeNull();
});
```

**[CR-004]** Unbounded `ingredients` JSON cast without size validation in recipe creation

- **File:** `src/app/api/recipes/route.ts:178-183`
- **Issue:** The Zod schema validates `ingredients` array to max 100 items and `instructions` to max 50, but `sanitizedIngredients` and `sanitizedInstructions` are stored as JSON (`Prisma.JsonValue`). The `amount` field in `ingredientSchema` is `z.string().max(50)` — but `striptags` is not applied to `amount` or `unit`, only to `name` and `description`. A malicious user can inject HTML/script tags in `amount` and `unit` fields.
- **Impact:** Stored XSS via `ingredient.amount` or `ingredient.unit` fields. If any frontend renders these without escaping (common in recipe display), arbitrary JavaScript execution in other users' browsers.
- **Suggested fix:**

```ts
const sanitizedIngredients = validated.ingredients.map((i) => ({
  name: stripHtml(i.name),
  amount: stripHtml(i.amount),
  unit: stripHtml(i.unit),
}));
```

**[CR-005]** `instructionSchema` accepts arbitrary URLs for `image` field — SSRF and non-Cloudinary image injection

- **File:** `src/app/api/recipes/route.ts:26-29`
- **Issue:** The `instructionSchema` validates `image` as `z.string().url()` — any URL passes. While there is a secondary `validateCloudinaryUrl` check in the POST handler (lines 179-182), the schema itself is reused elsewhere (e.g., in the cooked-recipes route for casting `post.instructions`). Any code path that trusts the schema alone without the secondary check allows non-Cloudinary URLs. Additionally, the GET endpoint at `src/app/api/recipes/route.ts` returns `instructions` directly from the DB without sanitization, so if a non-Cloudinary URL was stored historically (before the check was added), it is served to clients.
- **Impact:** Stored arbitrary URLs in instruction images could be used for phishing (attacker-controlled image hosting), tracking pixels, or exploiting image rendering vulnerabilities in clients.
- **Suggested fix:** Move the Cloudinary constraint into the schema itself:

```ts
const instructionSchema = z
  .object({
    step: z.number().int().positive(),
    description: z.string().min(1).max(5000),
    image: z
      .string()
      .url()
      .refine(
        (url) => url.startsWith('https://res.cloudinary.com/'),
        'Instruction image must be a Cloudinary URL'
      )
      .optional(),
  })
  .strict();
```

**[CR-006]** `recipe.ingredients` cast to `RecipeIngredient[]` without validation in match endpoint

- **File:** `src/app/api/recipes/match/route.ts:135`
- **Issue:** The raw SQL query returns `ingredients` as `unknown`, which is then cast with `as unknown as Ingredient[]`. The subsequent validation check (`recipeIngredients.every(...)`) validates structure but only after the cast. If `candidate.ingredients` is a JSON object (not array) — e.g., `{"name": "..."}` — the `Array.isArray` guard catches it. However, the SQL query already filters `jsonb_typeof(p.ingredients) = 'array'`, but the **fallback Prisma query** (line 119-123, when `pantryPatterns.length === 0`) does **not** apply this filter. A recipe with `ingredients: "string"` or `ingredients: 42` would pass `{ not: Prisma.DbNull }` and then `Array.isArray` would return false, causing it to be skipped — which is correct but silent. The real issue: the Prisma fallback path also has no `jsonb_array_length` bound, so a recipe with 10,000 ingredients in the JSON would be loaded into memory.
- **Impact:** Memory exhaustion if a recipe with an extremely large ingredients JSON array exists in the database. The raw SQL path caps at 100, but the Prisma fallback does not.
- **Suggested fix:** Add ingredient array length validation to the fallback path or use raw SQL for both paths:

```ts
// After the Prisma fallback query, filter out oversized ingredient arrays:
allCandidates = allCandidates.filter(
  (c) => Array.isArray(c.ingredients) && (c.ingredients as unknown[]).length <= 100
);
```

**[CR-007]** `SET LOCAL statement_timeout` inside transaction is user-session scoped, not transaction-scoped on connection pool

- **File:** `src/app/api/recipes/match/route.ts:68`
- **Issue:** `SET LOCAL statement_timeout = '5s'` applies to the current transaction. However, if the Prisma connection pool reuses this connection and a subsequent transaction inherits the session-level timeout (which `SET LOCAL` should NOT cause — it resets after transaction end), this is fine. But the real problem: the `statement_timeout` of 5s applies to **each individual statement** within the transaction, not the total transaction time. The `$queryRaw` with `LIKE ANY(ARRAY[...])` on potentially hundreds of thousands of rows could individually stay under 5s while the total transaction takes much longer. The outer `{ timeout: 8000 }` on the `$transaction` call is a Prisma-level timeout (client-side), which may kill the transaction but leave a running query on PostgreSQL consuming resources.
- **Impact:** Under load, the PostgreSQL server accumulates zombie queries that exceed the Prisma client timeout but haven't hit the per-statement timeout, consuming connections and degrading database performance for all users.
- **Suggested fix:** Use `SET LOCAL lock_timeout` alongside `statement_timeout`, and set a total transaction timeout at the PostgreSQL level:

```ts
await tx.$executeRaw`SET LOCAL statement_timeout = '5s'`;
await tx.$executeRaw`SET LOCAL lock_timeout = '2s'`;
```

Also consider adding `idle_in_transaction_session_timeout` at the PostgreSQL configuration level.
