## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes and client components.

### Findings

#### CRITICAL

**[CR-001]** Cloudinary URL validation bypass via path traversal

- **File:** `src/app/api/recipes/[id]/comments/route.ts:96`, `src/app/api/recipes/[id]/comments/[commentId]/route.ts:56`
- **Issue:** The Cloudinary URL check validates `pathname.startsWith(\`/${cloudName}/\`)`but does not verify there are no`..`segments. An attacker could submit`https://res.cloudinary.com/<cloudName>/../<other-cloud>/image/upload/malicious.jpg` to bypass the origin check and inject arbitrary Cloudinary-hosted content.
- **Impact:** Stored XSS via malicious image URLs, content injection, phishing.
- **Suggested fix:**

```ts
if (url.pathname.includes('..')) {
  return NextResponse.json({ error: 'Invalid image URL' }, { status: 400 });
}
```

**[CR-002]** `recalc-ratings` resets recipes with no ratings but doesn't handle concurrent rating inserts

- **File:** `src/app/api/admin/recalc-ratings/route.ts:30-43`
- **Issue:** The two `UPDATE` statements run sequentially. A new rating can be inserted between the first UPDATE (which recalculates recipes with ratings) and the second UPDATE (which zeroes recipes without ratings). If a recipe gets its first rating in that gap, the second UPDATE will overwrite the freshly-calculated value with 0.
- **Impact:** Data corruption — recipe ratings silently reset to zero.
- **Suggested fix:** Combine into a single statement using `LEFT JOIN` or use a CTE:

```sql
UPDATE "Post" p
SET "averageRating" = COALESCE(r.avg_rating, 0),
    "reviewCount" = COALESCE(r.cnt, 0)
FROM (SELECT p2.id, ROUND(AVG(rt."rating")::numeric, 1)::float as avg_rating, COUNT(rt.id)::int as cnt
      FROM "Post" p2
      LEFT JOIN "Rating" rt ON rt."postId" = p2.id
      GROUP BY p2.id) r
WHERE p.id = r.id
```

**[CR-003]** Missing `averageRating`/`reviewCount` fields in `Post` model returned by `RecipeRepository.mapToRecipe`

- **File:** `src/infrastructure/repositories/RecipeRepository.ts:190-192`
- **Issue:** `mapToRecipe` reads `post.averageRating` and `post.reviewCount` but these fields are not included in the `select`/`include` for `findByUserId`, `getRecent`, `getByDifficulty`, `create`, or `update`. The values come from Prisma's default `select *` behavior, but this is fragile — any future `select` clause will break rating display.
- **Impact:** Silent data loss if any query switches to explicit `select`.
- **Suggested fix:** Document the dependency or explicitly select these fields.

#### HIGH

**[CR-004]** No CSRF protection on `/api/auth/logout`

- **File:** `src/app/api/auth/logout/route.ts:6-16`
- **Issue:** The logout route only checks for cookie presence, but the middleware CSRF check requires `application/json` content-type or `authorization` header or `x-requested-with`. A simple cross-site form POST with `Content-Type: text/plain` would be blocked by middleware. However, the comment says "prevents cross-site forced logout since we only clear when the cookie is present" — but `SameSite: lax` allows the cookie on top-level POSTs in some browsers. The real protection comes from middleware, but the comment is misleading.
- **Impact:** Potential forced logout in edge cases where SameSite is not enforced.
- **Suggested fix:** Remove misleading comment or add explicit CSRF token check.

**[CR-005]** `cooked-recipes` POST doesn't validate rating is integer in range before transaction

- **File:** `src/app/api/cooked-recipes/route.ts:83-89`
- **Issue:** The rating validation rejects non-integer and out-of-range values, but the cooked recipe is still created without a rating field being used in any aggregate. However, the rating value is stored directly in the DB. If the Prisma schema allows null but the client sends `rating: 0`, this passes validation (`0 < 1` fails the `rating < 1` check, so 0 is rejected). But `rating: 1.5` is also rejected since `Number.isInteger(1.5)` is false. This is correct, but the validation is done before the transaction while the DB write is inside — if the schema changes to use this rating, there's no in-transaction constraint.
- **Impact:** Low risk currently, but fragile design.
- **Suggested fix:** Add a DB-level constraint or move validation closer to the write.

**[CR-006]** `useNotificationPolling` circuit breaker never recovers automatically

- **File:** `src/hooks/useNotificationPolling.ts:91-93`
- **Issue:** When 10+ failures occur in a 10-minute window, `pollingStoppedRef` is set to `true` and never automatically reset. The `visibilitychange` handler has a 2-minute cooldown check, but if the page stays visible continuously, polling stops forever until the component remounts (page refresh or navigation).
- **Impact:** Users permanently lose real-time notifications until they refresh the page.
- **Suggested fix:** Add a recovery timeout (e.g., 5 minutes after last failure, reset the circuit breaker).

**[CR-007]** `RecipeFeed` abortController race condition

- **File:** `src/components/recipe/RecipeFeed.tsx:119-120`
- **Issue:** `abortControllerRef.current?.abort()` is called before `loadingRef.current = true`, meaning if two `loadRecipes` calls fire in the same tick, both can pass the `if (loadingRef.current) return` guard before either sets it to `true`.
- **Impact:** Duplicate concurrent fetches, potential stale data rendering.
- **Suggested fix:** Set `loadingRef.current = true` before aborting the previous controller.

**[CR-008]** Admin comment/recipe delete routes leak error details

- **File:** `src/app/api/admin/recipes/[id]/route.ts:30-32`
- **Issue:** The Prisma error check `error instanceof Prisma.PrismaClientKnownRequestError` only catches P2025. Other Prisma errors (P2003 foreign key, P2014 relation violation) fall through to the generic 500 handler which logs the full error to console but returns a generic message. This is fine, but the inconsistency with `admin/comments/[id]/route.ts` (which checks `error.message === 'COMMENT_NOT_FOUND'`) suggests the error handling strategy is inconsistent across admin routes.
- **Impact:** Maintenance burden, inconsistent error responses.
- **Suggested fix:** Standardize error handling across admin routes.

#### MEDIUM

**[CR-009]** `about/page.tsx` is a client component but could be server-rendered

- **File:** `src/app/about/page.tsx:1`
- **Issue:** The `'use client'` directive is used because of `useTheme()`, but the page is entirely static content. The theme values could be accessed via `sx` prop shorthand (e.g., `'primary.main'`) which works without `useTheme()`, or the page could use CSS variables.
- **Impact:** Larger client bundle, unnecessary hydration for a static page.
- **Suggested fix:** Remove `useTheme()` calls and use `sx` prop theme references like `color="primary.main"` (already done in some places). The gradient could use CSS custom properties.

**[CR-010]** `PersistentSearchBar` live search has no result limit at the API level

- **File:** `src/components/search/PersistentSearchBar.tsx:127`
- **Issue:** The live search calls `/api/search?q=...` without a `limit` parameter. The search API defaults to `limit=20` which is reasonable, but the component only displays 3 recipes and 2 users. Fetching 20 of each when only 5 are shown wastes bandwidth.
- **Impact:** Unnecessary network traffic on every keystroke (after debounce).
- **Suggested fix:** Add `&limit=5` to the search URL.

**[CR-011]** `EditRecipeModal` `canProceed` for step 1 (ingredients) requires ALL rows to be filled

- **File:** `src/components/recipe/EditRecipeModal.tsx:106-114`
- **Issue:** Unlike `CreateRecipeForm` which filters empty rows on submit, `EditRecipeModal.canProceed` for step 1 requires `ingredients.every(...)` — meaning every row including blank placeholder rows must be filled. This forces users to delete empty rows before proceeding, while `CreateRecipeForm` allows empty rows.
- **Impact:** Inconsistent UX between create and edit flows.
- **Suggested fix:** Match `CreateRecipeForm`'s behavior: filter empty rows in `canProceed`.

**[CR-012]** `env-validation.ts` Shannon entropy check uses magic threshold

- **File:** `src/lib/env-validation.ts:111-117`
- **Issue:** The entropy threshold of 3.0 is undocumented and could reject valid secrets. For example, a 32-char hex string (characters 0-9, a-f) has a maximum entropy of ~4.0 bits, but a hex string with skewed distribution could fall below 3.0. The check is reasonable but the threshold should be documented with rationale.
- **Impact:** False positives blocking deployment with valid but low-variety secrets.
- **Suggested fix:** Add a comment explaining why 3.0 was chosen, or use a well-known threshold.

**[CR-013]** `notifications/page.tsx` doesn't handle pagination

- **File:** `src/app/notifications/page.tsx:37`
- **Issue:** `fetchNotifications` calls `/api/notifications` without limit/offset parameters. The API defaults to `limit=50`. If a user has >50 notifications, they'll never see older ones — there's no "load more" or pagination.
- **Impact:** Users with many notifications lose access to older ones.
- **Suggested fix:** Add infinite scroll or pagination.

**[CR-014]** `RecipeCard` image `onError` fallback can cause infinite loop in edge cases

- **File:** `src/components/recipe/RecipeCard.tsx:107-112`
- **Issue:** The `imgFallbackUsed` state prevents infinite loops, but if the fallback image `/chef-logo.png` itself fails to load (e.g., CDN down), the `onError` fires once more with `imgFallbackUsed = true` and does nothing — the broken image icon shows. This is technically handled but the UX is poor.
- **Impact:** Broken image display when fallback also fails.
- **Suggested fix:** Use a data URI as the ultimate fallback, or hide the image entirely.

**[CR-015]** `middleware.ts` rate limit map grows unbounded in long-running processes

- **File:** `src/middleware.ts:30`
- **Issue:** The bulk cleanup at `size > 1000` only removes expired entries, but if 1000+ unique IPs hit the server within a 15-minute window with non-expired entries, the map stays large. In a long-running Node process (non-serverless), this can consume significant memory.
- **Impact:** Memory leak in non-serverless deployments under sustained load.
- **Suggested fix:** Use an LRU cache with a max size, or switch to Redis.

**[CR-017]** `SearchResults` component exposes user email in props interface

- **File:** `src/components/SearchResults.tsx:15`
- **Issue:** The `User` interface includes `email: string` even though the search API strips email from responses. The component displays `user.email` on desktop. If the API ever leaks email back, it would be displayed publicly.
- **Impact:** Defense-in-depth concern.
- **Suggested fix:** Remove `email` from the `User` interface in SearchResults since the API shouldn't return it.

**[CR-018]** `pantry/page.tsx` duplicate ingredient check is case-insensitive but not normalized

- **File:** `src/app/pantry/page.tsx:193-199`
- **Issue:** The duplicate check uses `item.name.toLowerCase() === formData.name.trim().toLowerCase()` but doesn't normalize whitespace or special characters. "Bell Pepper" and "bell pepper" (double space) would be treated as different ingredients.
- **Impact:** Duplicate pantry items with slightly different formatting.
- **Suggested fix:** Use `normalizeIngredientName` from `src/lib/utils/ingredients.ts`.

**[CR-019]** `test-recipe-matching.ts` script has its own `normalizeIngredient` that diverges from production code

- **File:** `src/scripts/test-recipe-matching.ts:131-139`
