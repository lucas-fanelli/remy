## Code Review — 2026-03-19

### Summary

Three pages will crash at runtime due to missing `motion` import. Admin role-change endpoint has a race condition that can leave the system with zero admins. Several data integrity and over-fetching issues in API routes.

### Findings

#### CRITICAL

**[CR-001]** `motion` not imported — ReferenceError on 3 pages

- **File:** `src/app/profile/[username]/page.tsx`, `src/app/recipe/[id]/page.tsx`, `src/app/pantry/page.tsx`
- **Issue:** All three pages use `<motion.div>` in JSX but never import `motion` from `framer-motion`. This causes `ReferenceError: motion is not defined` when any of these pages render.
- **Impact:** Pages crash for every user. These are core pages (profile, recipe detail, pantry).
- **Suggested fix:**

```tsx
// Add to imports in each file:
import { motion } from 'framer-motion';
```

**[CR-002]** Admin PATCH (demote) has no last-admin guard — race condition

- **File:** `src/app/api/admin/users/[id]/route.ts:103-131`
- **Issue:** The PATCH handler for demoting admins only checks `if (action === 'demote' && id === authResult.userId)` (self-demotion). It has no advisory lock and no check for remaining admin count. Two concurrent demote requests between two admins (A demotes B, B demotes A) will both succeed, leaving zero admins. The DELETE handler has this protection via `PG_ADVISORY_LOCK_ADMIN_DELETE` — PATCH does not.
- **Impact:** System can be left with zero admin users, requiring manual database intervention to recover.
- **Suggested fix:**

```ts
if (action === 'demote') {
  const result = await prisma.$transaction(async (tx) => {
    await tx.$executeRaw`SELECT pg_advisory_xact_lock(${PG_ADVISORY_LOCK_ADMIN_DELETE}, 0)`;
    const [{ count }] = await tx.$queryRaw<[{ count: number }]>`
      SELECT COUNT(*)::int as count FROM "User" WHERE role = 'ADMIN'
    `;
    if (count <= 1) throw new Error('LAST_ADMIN');
    return adminService.demoteToUser(id);
  });
  return NextResponse.json(result);
}
```

#### HIGH

**[CR-003]** Cooked recipe DELETE doesn't remove associated rating or recalculate averages

- **File:** `src/app/api/cooked-recipes/route.ts:222-246`
- **Issue:** When a cooked recipe is deleted via `DELETE /api/cooked-recipes?id=`, the `Rating` record created during the POST is not deleted and the post's `averageRating`/`reviewCount` are not recalculated. The POST handler creates a `Rating` entry and recalculates averages (lines 177-196), but DELETE only removes the `CookedRecipe` row.
- **Impact:** Stale ratings persist after un-cooking a recipe. Users cannot truly "undo" marking a recipe as cooked since their rating remains, skewing averages.
- **Suggested fix:** In the DELETE handler, after deleting the cooked recipe, also delete the associated `Rating` and recalculate the post's aggregate rating (same pattern as comment DELETE in `src/app/api/recipes/[id]/comments/[commentId]/route.ts`).

**[CR-004]** `hashtext` advisory lock collision risk undocumented for multi-feature usage

- **File:** `src/app/api/cooked-recipes/route.ts:157`
- **Issue:** `pg_advisory_xact_lock(${PG_ADVISORY_LOCK_COOKED_RECIPE}, hashtext(${user.id}))` uses a 32-bit hash of the user ID as the second key. The comment acknowledges collision risk, but `PG_ADVISORY_LOCK_COOKED_RECIPE` (48881) is used as the namespace. If any future feature also uses `hashtext(userId)` with a different namespace key, collisions are fine. However, if the same namespace key 48881 is reused (copy-paste from this code), two unrelated features will serialize on the same user unnecessarily. The advisory lock registry in `constants.ts` documents key allocation but doesn't document the second key semantics.
- **Impact:** Future developers may inadvertently create lock contention by reusing patterns without understanding the two-key scheme.
- **Suggested fix:** Add a comment in `src/lib/constants.ts` documenting that the second key is feature-specific and should never be shared across features:

```ts
/**
 * Advisory lock keys use two-key form: pg_advisory_xact_lock(FEATURE_KEY, ENTITY_HASH)
 * FEATURE_KEY: unique per feature (allocated below)
 * ENTITY_HASH: typically hashtext(userId) — same hash in different features won't collide
 *              because the FEATURE_KEY differs
 */
```

**[CR-005]** Saved recipes endpoint over-fetches all Post fields

- **File:** `src/app/api/users/[username]/saved/route.ts:58-73`
- **Issue:** Uses `include: { post: { include: { _count: ... } } }` which fetches ALL Post columns (including `ingredients`, `instructions` — large JSON blobs), then maps to a subset of fields. Should use `select` to only fetch needed columns.
- **Impact:** Unnecessary database load and memory usage, especially for users with many saved recipes containing large ingredient/instruction lists.
- **Suggested fix:**

```ts
post: {
  select: {
    id: true,
    title: true,
    description: true,
    imageUrl: true,
    difficulty: true,
    cookingTime: true,
    prepTime: true,
    servings: true,
    averageRating: true,
    reviewCount: true,
    createdAt: true,
    _count: { select: { likes: true, comments: true } },
  },
},
```

#### MEDIUM

**[CR-006]** `useNotificationPolling` — stale closure in `markAllAsRead`

- **File:** `src/hooks/useNotificationPolling.ts:178-196`
- **Issue:** `markAllAsRead` depends on `markingAsRead` in its `useCallback` dependency array. If React batches state updates, the `markingAsRead` guard could be stale, allowing two concurrent POST requests if `markAllAsRead` is called rapidly (e.g., double-click).
- **Impact:** Duplicate POST requests to mark all as read (benign but wasteful).
- **Suggested fix:** Use a ref for the guard instead of state:

```ts
const markingAsReadRef = useRef(false);
const markAllAsRead = useCallback(async () => {
  if (!user || markingAsReadRef.current) return;
  markingAsReadRef.current = true;
  // ...
  markingAsReadRef.current = false;
}, [user]);
```

**[CR-007]** RecipeFeed — `loadingRef` race with AbortController

- **File:** `src/components/recipe/RecipeFeed.tsx:117-119`
- **Issue:** `loadingRef.current` is checked at line 117 to guard against concurrent calls, but the abort controller is only created at line 119. If a second call arrives between lines 117-119 (unlikely in single-threaded JS but possible with React concurrent mode), the first fetch won't be aborted.
- **Impact:** Minimal in practice, but the guard logic is ordered incorrectly.
- **Suggested fix:** Move the `loadingRef` guard after the abort:

```ts
abortControllerRef.current?.abort();
if (loadingRef.current && !reset) return;
```

**[CR-008]** `AdminService.getStats` cache not invalidated by organic activity

- **File:** `src/infrastructure/services/AdminService.ts:14-15`
- **Issue:** `statsCache` (30s TTL) is only invalidated by admin mutations (promote, demote, delete). The `newUsersToday` and `newRecipesToday` counts will be stale by up to 30 seconds, which is documented in a comment. However, the comment says "This is acceptable for an admin dashboard" — but the cache is never invalidated when users sign up or create recipes, which means `newUsersToday` could be off by the number of signups in the last 30 seconds.
- **Impact:** Admin dashboard shows stale "new today" counts. Acceptable for dashboard use but the comment should explicitly state the trade-off.
- **Suggested fix:** No code change needed, but consider reducing TTL to 10s or making it configurable.

**[CR-009]** Search API returns user `id` field publicly

- **File:** `src/app/api/search/route.ts:41-43`
- **Issue:** The search endpoint strips `email` from user results but still exposes the internal `id` field. While UUIDs are not sequential, exposing internal IDs in public search results is unnecessary.
- **Impact:** Information disclosure — internal user IDs are leaked to unauthenticated users.
- **Suggested fix:** Strip `id` from the user mapping along with `email`:

```ts
(u) => ({ username: u.username, fullName: u.fullName, avatar: u.avatar, bio: u.bio });
```

**[CR-010]** `PersistentSearchBar` — AbortController created outside setTimeout

- **File:** `src/components/search/PersistentSearchBar.tsx:126-145`
- **Issue:** The comment says "AbortController is intentionally created OUTSIDE the setTimeout so the cleanup function can abort it immediately" — but the `searchAbortRef.current?.abort()` inside the timeout fires AFTER the controller is assigned to `searchAbortRef`, meaning a new search might abort its own controller if the ref is overwritten between creation and the abort line. The logic is actually correct because abort happens before the new assignment, but the code is fragile and confusing.
- **Impact:** No bug currently, but future refactoring could easily introduce a race.
- **Suggested fix:** Move the `searchAbortRef.current?.abort()` outside the setTimeout and reassign after:

```ts
searchAbortRef.current?.abort();
const controller = new AbortController();
searchAbortRef.current = controller;
searchTimeoutRef.current = setTimeout(async () => {
  // use controller directly, not ref
}, 300);
```
