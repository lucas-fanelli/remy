## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes, client components, and infrastructure layers.

### Findings

#### CRITICAL

**[CR-001]** XSS via unsanitized `recipe.description` in `SearchResults.tsx`

- **File:** `src/components/SearchResults.tsx:195`
- **Issue:** `truncateAtWord` slices raw description text mid-word. If the description contains partial HTML entities (e.g., `&amp` truncated from `&amp;`), it could break rendering. More importantly, `recipe.description` from the search API is rendered without sanitization while the API response includes raw DB content.
- **Impact:** Stored XSS if a recipe description bypasses server-side sanitization (e.g., via direct DB manipulation or a sanitization bug).
- **Suggested fix:** The `RecipeService` already strips HTML on create/update. Add defense-in-depth by using `striptags` or escaping in the search API response serialization.

**[CR-002]** `cooked-recipes` DELETE does not restore pantry deductions

- **File:** `src/app/api/cooked-recipes/route.ts:225-230`
- **Issue:** The TODO comment acknowledges this but it's not tracked as a bug. When a user deletes a cooked recipe entry, the pantry items that were deducted during POST are permanently lost. The `deductedIngredients` data is returned in the POST response but never persisted.
- **Impact:** Data loss — users lose pantry quantities with no way to recover them.
- **Suggested fix:** Add a `deductedIngredients` JSON column to `CookedRecipe` model. Persist deductions on POST, restore on DELETE.

**[CR-003]** Race condition in recipe match endpoint — no isolation for pantry reads

- **File:** `src/app/api/recipes/match/route.ts:60-65`
- **Issue:** Pantry items are read outside any transaction, then used for matching against recipes fetched in a separate transaction. If pantry items change between reads, match results could be stale or incorrect.
- **Impact:** Incorrect recipe match results shown to user; minor data integrity issue.
- **Suggested fix:** Read pantry inside the same transaction as recipe candidates, or accept eventual consistency with a comment documenting the trade-off.

**[CR-004]** `auth_token` cookie not cleared on account deletion

- **File:** `src/app/api/users/profile/route.ts:60-72`
- **Issue:** The `DELETE` handler for account deletion calls `userService.deleteUser(user.id)` but does not clear the `auth_token` cookie. The deleted user's JWT remains valid until expiry, and subsequent API calls will fail with 500s (user not found) rather than 401s.
- **Impact:** Orphaned session cookie causes confusing errors post-deletion.
- **Suggested fix:**

```typescript
const response = ApiResponseHelper.success(null, 'Account deleted successfully');
clearAuthCookie(response);
return response;
```

#### HIGH

**[CR-005]** Admin user deletion lacks Cloudinary cleanup error logging for individual URLs

- **File:** `src/app/api/admin/users/[id]/route.ts:82-85`
- **Issue:** `Promise.allSettled` catches failures but only logs the count of failed URLs, not which specific URLs failed. The cleanup-orphaned-images script is supposed to catch these, but without logging the actual URLs, debugging orphan accumulation is impossible.
- **Impact:** Orphaned Cloudinary images accumulate silently with no way to trace them.
- **Suggested fix:** Log the actual failed URLs:

```typescript
if (failedUrls.length > 0) {
  console.warn(`[ORPHANED IMAGES] Failed to cleanup for deleted user ${id}:`, failedUrls);
}
```

**[CR-006]** `notifications/[id]/route.ts` PATCH does not verify `isRead` wasn't already true

- **File:** `src/app/api/notifications/[id]/route.ts:33-42`
- **Issue:** `updateMany` with `count === 0` returns 404, but this also happens when the notification is already read. A user marking an already-read notification gets a misleading 404 error.
- **Impact:** False 404 errors on idempotent mark-as-read operations.
- **Suggested fix:** Use `findFirst` to check existence before returning 404, or make the operation truly idempotent by returning success regardless.

**[CR-007]** `RecipeFeed` infinite scroll can skip pages on rapid scrolling

- **File:** `src/components/recipe/RecipeFeed.tsx:130-170`
- **Issue:** `pageRef.current` is incremented inside the `requestId` guard, but if the sentinel fires while a previous request is still in-flight (despite the `loadingRef` guard), the `abortControllerRef.current?.abort()` at line 132 cancels the previous request. The previous request's `finally` block sets `loadingRef.current = false`, but the response is discarded (stale requestId). Meanwhile `pageRef` was never incremented for the aborted request, so the next fetch re-requests the same page.
- **Impact:** Duplicate recipes in the feed or skipped pages under rapid scroll.
- **Suggested fix:** Move `pageRef` increment to before the fetch, and decrement on failure. Or use the offset directly from `recipes.length`.

**[CR-008]** `useNotificationPolling` does not abort in-flight fetch on user change

- **File:** `src/hooks/useNotificationPolling.ts:84`
- **Issue:** When `user` changes (e.g., login as different user), the polling effect re-runs and calls `fetchNotifications()` immediately. But `fetchNotifications` aborts the _previous_ controller and creates a new one. If the effect cleanup hasn't run yet (React batches), the old poll timer may still fire for the previous user.
- **Impact:** Notifications from previous user briefly shown to new user.
- **Suggested fix:** The effect cleanup does abort, but the `fetchNotifications()` call on line 155 runs before cleanup of the previous effect. Add `cancelled` check before `fetchNotifications()` in the new effect.

**[CR-009]** `striptags` is not imported in `cooked-recipes/route.ts` ESM-compatible way

- **File:** `src/app/api/cooked-recipes/route.ts:10`
- **Issue:** `import striptags from 'striptags'` — `striptags` v3+ is ESM-only. If the build resolves to CJS, this import may fail at runtime.
- **Impact:** Runtime crash on the cooked-recipes endpoint.
- **Suggested fix:** Verify `striptags` version is compatible with the project's module resolution, or pin to v3.x with `"type": "module"` support confirmed.

#### MEDIUM

**[CR-010]** `Footer.tsx` mailto link susceptible to content injection via line breaks

- **File:** `src/components/Footer.tsx:62`
- **Issue:** The `sanitize` function strips control characters `[\x00-\x1F\x7F]`, but `encodeURIComponent` properly handles everything. The real issue is the 1500-char limit check happens after encoding, which is correct — but the sanitize function is redundant since `encodeURIComponent` handles all dangerous characters. The `window.open` with `_blank` and no `noopener` could be a minor issue.
- **Impact:** Minor — the mailto link already uses `encodeURIComponent` which is sufficient.
- **Suggested fix:** Remove the redundant `sanitize` function to reduce complexity, or keep it as defense-in-depth but document why.

**[CR-011]** `EditProfileModal` does not validate avatar upload magic bytes for WebP with correct length

- **File:** `src/components/profile/EditProfileModal.tsx:93-104`
- **Issue:** Client-side magic byte validation reads `file.slice(0, 12)` which is correct for WebP (12 bytes needed). However, the `if (bytes.length < 4)` check should be `if (bytes.length < 12)` for WebP validation to be reliable. A 4-byte file would pass the length check but fail all format checks silently.
- **Impact:** Confusing UX — a corrupted file passes the length check but fails all format checks, resulting in a generic "Invalid image file" error rather than "File is too small."
- **Suggested fix:** Change to `if (bytes.length < 12)`.

**[CR-012]** `PersistentSearchBar` AbortController created outside setTimeout

- **File:** `src/components/search/PersistentSearchBar.tsx:127-145`
- **Issue:** Comment says this is intentional, but creating the AbortController outside the timeout means that if the cleanup runs before the timeout fires, the `controller.abort()` in cleanup correctly cancels. However, a new effect run (query change) creates a NEW controller and immediately `searchAbortRef.current?.abort()` the old one. If the old timeout hasn't fired, the abort is a no-op on a never-used controller. This is actually fine — but the `searchAbortRef` and the closure's `controller` could diverge.
- **Impact:** Potential for a stale search result to appear briefly if timing aligns.
- **Suggested fix:** Move `searchAbortRef.current = controller` inside the setTimeout to avoid the ref/closure divergence, or document the current behavior more clearly.

**[CR-013]** `RecipeCard` image fallback chain silently hides broken images

- **File:** `src/components/recipe/RecipeCard.tsx:133-148`
- **Issue:** Non-Cloudinary URLs immediately use `/chef-logo.png` as src. If `/chef-logo.png` also fails (e.g., during deployment), the fallback chain hits `setImgHidden(true)` showing a placeholder icon. No error is reported to monitoring.
- **Impact:** Broken images silently replaced with placeholder; no observability.
- **Suggested fix:** Log to Sentry when the fallback image also fails (the second `onError`).

**[CR-014]** Admin stats cache not invalidated by organic activity

- **File:** `src/infrastructure/services/AdminService.ts:24-27`
- **Issue:** Documented in comments but worth flagging: new user signups, recipe creation, likes, and comments don't invalidate the stats cache. In serverless, the cache has low hit rate anyway.
- **Impact:** Admin dashboard shows stale stats for up to 30 seconds.
- **Suggested fix:** Accept as documented or reduce TTL to 10 seconds for more responsive stats.

**[CR-015]** `handleShare` in recipe detail page doesn't handle missing `navigator.share` gracefully on insecure contexts

- **File:** `src/app/recipe/[id]/page.tsx:284-295`
- **Issue:** On HTTP (non-localhost dev), both `navigator.share` and `navigator.clipboard` are unavailable. The code falls through to the `else` branch showing "Cannot copy link — please copy the URL manually" which is correct, but it also swallows clipboard write errors silently.
- **Impact:** Minor UX issue — user sees a warning snackbar which is appropriate.
- **Suggested fix:** No change needed, behavior is correct.

#### LOW

**[CR-016]** Inconsistent error response format across API routes

- **File:** Multiple API routes
- **Issue:** Some routes use `ApiResponseHelper` (which wraps in `{ success, error, data }`), others use raw `NextResponse.json({ error })`. The `ApiResponseHelper` comment at `src/lib/api/response.ts:4` acknowledges this but doesn't enforce consistency.
- **Impact:** Client code must handle two response formats, increasing complexity.
- **Suggested fix:** Standardize on one format. The comment recommends `{ error }` for new routes — enforce via lint rule or code review checklist.

**[CR-017]** `useAdminGuard` hook redirects on every render while loading

- **File:** `src/hooks/useAdminGuard.ts:9-11`
- **Issue:** When `isLoading` is false and `!user || !isAdmin`, the hook calls `router.push('/')`. If the component re-renders before navigation completes, this fires multiple times.
- **Impact:** Multiple navigation calls (harmless but wasteful).
- **Suggested fix:** Add a ref to track if redirect has been initiated.

**[CR-018]** `getDifficultyColor` warns on unknown difficulty values but doesn't cap the Set size effectively

- **File:** `src/lib/utils/recipe.ts:18`
- **Issue:** `warnedDifficulties` Set clears at 100 entries, but in a server-side context with many recipes, this could cycle frequently. The clear-at-100 threshold is arbitrary.
- **Impact:** Negligible performance impact; warning deduplication is a nice-to-have.
- **Suggested fix:** Use a proper LRU cache or just remove the deduplication — `console.warn` is cheap.

**[CR-019]** Test files use `any` type extensively

- **File:** Multiple test files (e.g., `CommentsSection.test.tsx`, `RecipeFeed.test.tsx`)
- **Issue:** Mock types use `any` throughout, reducing type safety in tests and making refactoring harder.
- **Impact:** Tests may pass despite type-breaking changes in production code.
- **Suggested fix:** Create typed mock factories for common patterns (auth context, fetch responses).

**[CR-020]** `cleanup-orphaned-images.ts` has no protection against running concurrently

- **File:** `src/scripts/cleanup-orphaned-images.ts`
- **Issue:** If the cron job overlaps (previous run still executing), two instances could delete the same images or race on the Cloudinary API, causing rate limiting.
- **Impact:** Cloudinary API rate limit errors; double-deletion attempts (harmless but noisy).
- **Suggested fix:** Use a file-based or DB-based lock, or use an advisory lock at the start of the script.
