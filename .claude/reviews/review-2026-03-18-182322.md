## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes, middleware, and client components.

### Findings

#### CRITICAL

**[CR-001]** XSS via unsanitized `website` field rendered as raw `href`

- **File:** `src/app/profile/[username]/page.tsx:338`
- **Issue:** `profile.website` is rendered as `<a href={profile.website}>` without sanitization. The `updateProfileSchema` validates URL format, but `javascript:` URLs pass the `z.string().url()` check in Zod. An attacker can set `javascript:alert(1)` as their website.
- **Impact:** Stored XSS — any user viewing the profile executes arbitrary JavaScript.
- **Suggested fix:**

```typescript
// In updateProfileSchema, add protocol validation:
website: z.string()
  .url()
  .refine((url) => !url || /^https?:\/\//.test(url), 'Website must start with http:// or https://');
```

Wait — this refine already exists. Let me recheck. The schema has `.refine((url) => !url || /^https?:\/\//.test(url))` and the `UserService.updateProfile` also validates protocol. However, the `.or(z.literal(''))` branch bypasses validation. And the schema allows `nullable()` — so this is actually fine. Let me re-examine... The `z.string().url()` in Zod v3 does reject `javascript:` URIs. Withdrawing this finding.

**[CR-002]** `averageRating` field on `Post` not typed as nullable — silent NaN propagation

- **File:** `src/infrastructure/repositories/RecipeRepository.ts:196`
- **Issue:** `mapToRecipe` reads `post.averageRating` which is a Prisma `Float?` (nullable). The `Recipe` type declares `averageRating?: number` (optional, but not `number | null`). When `averageRating` is `null` from Prisma, it's assigned directly without coercion. Downstream code in `safeRating()` handles `null` correctly, but the type system doesn't enforce it — any code path that skips `safeRating()` will propagate `null` where `number` is expected.
- **Impact:** Potential NaN in arithmetic or rendering if any code path skips `safeRating()`.
- **Suggested fix:** Change `Recipe.averageRating` type to `number | null` and audit all consumers.

**[CR-003]** Cloudinary public ID extraction regex misses transformation segments

- **File:** `src/app/api/recipes/[id]/route.ts:133`
- **Issue:** The regex `\/upload\/(?:(?:v\d+|[a-z]_[^/]+)\/)*(.+?)(?:\.\w+)?(?:\?.*)?$` attempts to strip version/transformation segments, but transformation segments can contain digits and uppercase (e.g., `c_fill,w_300,h_200`). The pattern `[a-z]_[^/]+` won't match multi-param transforms like `c_fill,w_300`.
- **Impact:** Cloudinary images with transformations in the URL won't be cleaned up on recipe deletion, causing orphaned storage.
- **Suggested fix:**

```typescript
const match = imageUrl.match(/\/upload\/(?:[^/]+\/)*([^/.]+)/);
```

**[CR-004]** Avatar Cloudinary cleanup regex also misses transformations

- **File:** `src/app/api/upload/avatar/route.ts:80`
- **Issue:** Same pattern: `\/upload\/(?:v\d+\/)?(.+)\.\w+$` only handles optional version segment but not transformation segments.
- **Impact:** Old avatars with transformations in URL are never cleaned up from Cloudinary.
- **Suggested fix:** Use the same broader regex as suggested in CR-003.

#### HIGH

**[CR-005]** No CSRF token on logout — cookie can be cleared by cross-site request

- **File:** `src/app/api/auth/logout/route.ts:1-10`
- **Issue:** The logout endpoint accepts `POST` with no body, no auth check, and the middleware CSRF protection only requires `Content-Type: application/json` header OR `authorization` header. A simple `fetch('/api/auth/logout', {method:'POST', headers:{'Content-Type':'application/json'}})` from any same-origin page clears the session. While the SameSite cookie helps, `lax` mode still allows top-level POST navigations.
- **Impact:** Logout CSRF — an attacker can force-logout any user.
- **Suggested fix:** Require the auth cookie to be present and valid before clearing it, or accept this as low-risk since logout CSRF is generally considered non-critical.

**[CR-006]** Recipe match endpoint loads up to 500 candidates without cursor pagination

- **File:** `src/app/api/recipes/match/route.ts:78-87`
- **Issue:** The `LIMIT 500` raw SQL query loads all candidate IDs into memory, then fetches full recipe data for all matches. For a database with many recipes, this creates significant memory pressure and slow queries.
- **Impact:** Performance degradation and potential OOM under load as recipe count grows.
- **Suggested fix:** Add cursor-based pagination or reduce the limit. Consider caching match results per user with a short TTL.

**[CR-007]** `cooked-recipes` POST doesn't validate `notes` type before length check

- **File:** `src/app/api/cooked-recipes/route.ts:90-95`
- **Issue:** `notes` is checked with `typeof notes === 'string'` before length check, but if `notes` is a non-string truthy value (e.g., an object), the check silently passes and the object is stored in the database.
- **Impact:** Non-string values can be stored in `notes` field, potentially causing rendering issues or data corruption.
- **Suggested fix:**

```typescript
if (notes !== undefined && notes !== null) {
  if (typeof notes !== 'string') {
    return NextResponse.json({ error: 'Notes must be a string' }, { status: 400 });
  }
  if (notes.length > MAX_NOTES_LENGTH) { ... }
}
```

**[CR-008]** `handleSubmit` in `PantryPage` sends `quantity` as string to API

- **File:** `src/app/pantry/page.tsx:208`
- **Issue:** `formData.quantity` is a string from the text input, and when editing (`PUT`), the API at `src/app/api/pantry/[id]/route.ts:56` calls `parseFloat(quantity)`. However, in the POST handler at `src/app/api/pantry/route.ts:80`, the `parseFloat(quantity)` is only called when `quantity !== undefined && quantity !== null`. The pantry page sends `quantity: 0` (a number) when empty but sends the raw string from `parseFloat(formData.quantity)` when filled. This inconsistency works but is fragile.
- **Impact:** Type confusion between string and number for quantity field.
- **Suggested fix:** Always send `quantity` as a number from the client, or add server-side type coercion consistently.

**[CR-009]** `RecipeFeed` like response parse failure silently reverts optimistic update

- **File:** `src/components/recipe/RecipeFeed.tsx:292-296`
- **Issue:** When `response.ok` is true but `response.json()` throws (e.g., empty body), the catch block reverts the optimistic update and logs a warning, but the user sees a brief flash of the liked state followed by a silent revert with no error notification.
- **Impact:** Confusing UX — user thinks they liked a recipe but the like silently disappears.
- **Suggested fix:** Show an error snackbar in the parse error catch block.

#### MEDIUM

**[CR-010]** Admin pages use client-side auth check — flash of admin content before redirect

- **File:** `src/app/admin/comments/page.tsx:68-82`, `src/app/admin/recipes/page.tsx:86-100`, `src/app/admin/users/page.tsx:101-115`
- **Issue:** All admin pages check `isAdmin` in a `useEffect` and redirect. Between mount and effect execution, `!isAdmin` returns `null` to avoid flash, but the page still renders the outer layout (AppBar, etc.) briefly.
- **Impact:** Non-admin users briefly see admin page layout before redirect. The middleware already blocks at the edge, so this is defense-in-depth only.
- **Suggested fix:** Return a full-page loading spinner instead of `null` in the `!isAdmin` case, or use Next.js middleware redirect (already done) and remove the client-side check.

**[CR-011]** `search` API returns user emails in the internal query before stripping

- **File:** `src/app/api/search/route.ts:32-33`
- **Issue:** `userService.searchUsers` returns `UserPublicProfile` which includes `email`. The search route then strips email with `.map(({ email, ...rest }) => rest)`. The `UserRepository.search()` at line 94 already excludes email from the select. However, the TypeScript type still includes `email`, and there's a redundant destructure. If `UserRepository.search` is changed to include email in the future, the API would expose it.
- **Impact:** Low — currently safe due to repository-level exclusion, but the double-defense is fragile if one layer changes.
- **Suggested fix:** Keep the stripping at the API layer for defense-in-depth, but add a comment explaining it's intentionally redundant.

**[CR-012]** `useNotificationPolling` circuit breaker has no reset mechanism on success after visibility change

- **File:** `src/hooks/useNotificationPolling.ts:117-122`
- **Issue:** When `visibilitychange` fires and `timeSinceLastFailure > 2 minutes`, the circuit breaker resets. But if the tab stays visible and failures resume, the counter restarts from 0, requiring another 10 consecutive failures to trip. This means intermittent failures never trip the breaker.
- **Impact:** Continuous polling with intermittent failures wastes bandwidth without ever stopping.
- **Suggested fix:** Track failures in a sliding window rather than a consecutive counter.

**[CR-013]** `formatDistanceToNow` in `Navigation` uses `mounted` flag for hydration but notifications page doesn't

- **File:** `src/app/notifications/page.tsx:137` vs `src/components/Navigation.tsx:479`
- **Issue:** The notifications page renders `formatDistanceToNow` directly without a `mounted` guard, while Navigation uses one. This can cause hydration mismatches on the notifications page.
- **Impact:** React hydration warning in development, potential visual flicker in production.
- **Suggested fix:** Add the same `mounted` pattern to the notifications page, or use `suppressHydrationWarning` on the timestamp element.

**[CR-014]** `EditRecipeModal` canProceed step 1 allows empty-name ingredients to pass validation

- **File:** `src/components/recipe/EditRecipeModal.tsx:101-110`
- **Issue:** `canProceed` for step 1 requires `every` ingredient to have name, unit, and amount (or "to taste"). But if user has a single ingredient with all fields filled and adds a second empty one, the form rejects proceeding. This is correct behavior but different from `CreateRecipeForm` which uses `some` + `filter` logic. The inconsistency confuses users.
- **Impact:** UX inconsistency — create form allows empty ingredient rows but edit form doesn't.
- **Suggested fix:** Use the same validation logic in both forms. Prefer the edit form's stricter validation and apply it to create form too.

**[CR-015]** `RecipeFeed` uses `loadingRef` to prevent concurrent calls but doesn't handle filter changes during loading

- **File:** `src/components/recipe/RecipeFeed.tsx:133`
- **Issue:** When `loadingRef.current` is true, `loadRecipes` returns early. If a user changes filters while a request is in flight, the filter change triggers `useEffect` which calls `loadRecipes(true)`, but it returns early because the previous request is still loading. The filter change is lost.
- **Impact:** Filter changes during loading are silently ignored — user must wait and re-apply.
- **Suggested fix:** Use `AbortController` to cancel in-flight requests when filters change, or queue the filter change.

#### LOW

**[CR-016]** `about/page.tsx` uses `'use client'` unnecessarily

- **File:** `src/app/about/page.tsx:1`
- **Issue:** The about page uses `useTheme()` forcing it to be a client component, but the entire page is static content. The theme could be passed via CSS variables or the page could be split into a server component with a small client wrapper.
- **Impact:** Larger client bundle, no SSR benefit for static marketing content.
- **Suggested fix:** Consider making this a server component with theme-aware CSS variables.

**[CR-017]** `Post.averageRating` has implicit `any` type in `RecipeRepository` cast

- **File:** `src/infrastructure/repositories/RecipeRepository.ts:196`
- **Issue:** `post.averageRating` is typed as `number` (from Post model), but the Prisma schema has it as `Float?`. The generated type may be `number | null`. The direct assignment to `Recipe.averageRating` (typed as `number | undefined`) silently converts `null` to the `number` slot.
- **Impact:** TypeScript doesn't catch null-to-undefined mismatch.
- **Suggested fix:** Explicitly handle: `averageRating: post.averageRating ?? undefined`

**[CR-018]** Missing `aria-label` on several icon buttons in admin pages

- **File:** `src/app/admin/comments/page.tsx:136`, `src/app/admin/recipes/page.tsx:174`
- **Issue:** `<IconButton onClick={() => router.push('/admin')}>` has no `aria-label`, making it inaccessible to screen readers.
- **Impact:** Accessibility violation — screen readers announce "button" with no description.
- **Suggested fix:** Add `aria-label="Go back to admin dashboard"`.
