## Code Review — 2026-03-21

### Summary

Generally well-hardened code with proper transaction isolation, advisory locks, and XSS sanitization. However, there are several concurrency bugs, missing validations, and a data integrity issue in the account deletion flow.

### Findings

#### CRITICAL

**[CR-001]** Account deletion collects post images but ignores instruction step images in admin DELETE

- **File:** `src/app/api/admin/users/[id]/route.ts:82-88`
- **Issue:** The admin user deletion collects `post.imageUrl`, `comment.imageUrl`, and `avatar`, but does NOT collect instruction step images (`post.instructions[].image`). The user's own account deletion at `src/app/api/users/profile/route.ts:106-117` does collect these. This means admin-initiated deletions will orphan all instruction step images permanently until the cron job runs.
- **Impact:** Cloudinary storage leak. If the cron job is delayed or misconfigured, instruction images accumulate indefinitely.
- **Suggested fix:**

```typescript
// In admin DELETE, add instructions to the select and collect images:
const userPosts = await tx.post.findMany({
  where: { userId: id },
  select: { imageUrl: true, instructions: true },
});
// ... then iterate post.instructions same as profile/route.ts:106-117
```

**[CR-002]** `SET LOCAL statement_timeout` is PostgreSQL-only and not validated by Prisma

- **File:** `src/app/api/cooked-recipes/route.ts:100` (`SET LOCAL statement_timeout = '10s'`), `src/app/api/recipes/match/route.ts:81-82`, `src/app/api/admin/users/[id]/route.ts:55`
- **Issue:** `SET LOCAL statement_timeout` applies to the current transaction in PostgreSQL, but Prisma may use connection pooling (PgBouncer) in transaction mode, where `SET LOCAL` is unreliable because the session can be reused. If the app ever moves to PgBouncer or Prisma Accelerate, these timeouts silently stop working.
- **Impact:** Under connection pooling, long-running queries could run unbounded, causing connection starvation under load.
- **Suggested fix:** Use Prisma's `$transaction({ timeout })` option (already used in some places) as the primary timeout mechanism, and document the `SET LOCAL` dependency on session-mode pooling.

#### HIGH

**[CR-003]** `deductPantryItems` matches pantry items by name+unit but ignores case differences

- **File:** `src/app/api/cooked-recipes/route.ts:53-57`
- **Issue:** `normalizeIngredientName` is used for name comparison, but `unitsMatch` is a separate function. If `unitsMatch` is case-sensitive and a user stores "Tbsp" while the recipe has "tbsp", no match occurs, and pantry items are silently not deducted.
- **Impact:** Pantry deductions silently fail for legitimate ingredient matches with unit case differences, causing incorrect pantry state.
- **Suggested fix:** Verify `unitsMatch` handles case insensitivity. If not:

```typescript
unitsMatch(item.unit.toLowerCase(), ingredient.unit.toLowerCase());
```

**[CR-004]** `isFetchingRef` never reset to `false` when fetch is aborted

- **File:** `src/hooks/useNotificationPolling.ts:130-133`
- **Issue:** In the `finally` block, `isFetchingRef.current` is only set to `false` when `!controller.signal.aborted`. If the controller is aborted (e.g., rapid tab switches), `isFetchingRef` stays `true` permanently, and the `scheduleNext` function at line 168 skips all future fetches (`if (isFetchingRef.current) { scheduleNext(); return; }`), causing an infinite reschedule loop that never actually fetches.
- **Impact:** After any aborted notification fetch, polling permanently stops until component remounts.
- **Suggested fix:**

```typescript
finally {
  isFetchingRef.current = false;
}
```

The abort guard was presumably meant to prevent state updates on unmounted components, but `isFetchingRef` is a ref, not state — setting it is safe after abort.

**[CR-005]** `UserPublicProfile` exposes password hash via `Omit<User, 'password'>` type erasure

- **File:** `src/domain/services/IUserService.ts:11`
- **Issue:** `Omit<User, 'password'>` is a TypeScript-only construct. At runtime, if any implementation returns a full Prisma `User` object and the caller serializes it to JSON, the `password` field WILL be included in the response. The type system does not strip fields at runtime. The safety depends entirely on every repository query using `select` to exclude `password` — a single missing `select` leaks bcrypt hashes.
- **Impact:** Potential password hash exposure if any code path returns a full User object through this interface.
- **Suggested fix:** Either enforce `select` at the repository level with a shared constant, or add a runtime sanitization layer:

```typescript
function stripPassword<T extends { password?: unknown }>(user: T): Omit<T, 'password'> {
  const { password, ...rest } = user;
  return rest;
}
```

**[CR-006]** Recipe GET endpoint exposes private users' recipes when `userId` filter is provided

- **File:** `src/app/api/recipes/route.ts:76-79`
- **Issue:** The `where` clause starts with `user: { isPrivate: false }`, but when a `userId` is provided (line 97), it's added alongside the privacy filter. However, the privacy check is on `user.isPrivate`, and the `userId` filter is on `post.userId`. If a private user's ID is known, their recipes are still filtered out. BUT — the `userId` query parameter lacks any authorization check. Any authenticated or unauthenticated user can enumerate recipes by userId. While private users are filtered, this is fragile — if the privacy filter is ever removed or refactored, all private recipes leak.
- **Impact:** Low immediate risk due to existing filter, but the missing authorization check is a design smell that could become a vulnerability.
- **Suggested fix:** Add a comment documenting the privacy filter dependency, or explicitly check user privacy when `userId` is provided.

#### MEDIUM

**[CR-007]** Notification polling `scheduleNext` creates unbounded recursive setTimeout chain without cleanup on user change

- **File:** `src/hooks/useNotificationPolling.ts:155-176`
- **Issue:** `scheduleNext` calls itself recursively via `setTimeout`. The cleanup function (line 199) sets `cancelled = true` and calls `clearPolling()`, but `scheduleNext` only checks `cancelled` at the top — if the async `fetchNotifications()` at line 172 is already in-flight when cleanup runs, the subsequent `scheduleNext()` call at line 174 will execute with `cancelled = true` and exit. This works correctly. However, the `fetchNotifications` dependency in the `useEffect` causes the effect to re-run on every render where `fetchNotifications` changes identity, which happens every time `user` or `onAuthInvalid` changes. This resets all backoff state (line 148-153) even when only `onAuthInvalid` changes due to a parent re-render.
- **Impact:** Backoff state resets spuriously on parent re-renders that create a new `onAuthInvalid` callback, defeating the circuit breaker.
- **Suggested fix:** Wrap `onAuthInvalid` in a ref to stabilize `fetchNotifications`:

```typescript
const onAuthInvalidRef = useRef(onAuthInvalid);
onAuthInvalidRef.current = onAuthInvalid;
// Use onAuthInvalidRef.current inside fetchNotifications instead of onAuthInvalid
```

**[CR-008]** `RecipeFeed` animation delay leaks visual order across pages

- **File:** `src/components/recipe/RecipeFeed.tsx:295`
- **Issue:** `transition={{ delay: (index % PAGE_SIZE) * 0.05 }}` uses the array index, which for appended pages means items 12-23 get delays 0-0.55s again. But visually, all 24 items are rendered simultaneously after state update, so the second page's items animate in with the same stagger pattern as the first, creating a visual stutter where already-visible items appear to re-animate.
- **Impact:** Minor UX jank on infinite scroll load.
- **Suggested fix:** Only animate items that are newly added (e.g., track which items are new and only apply initial animation to those).

**[CR-009]** `markAllAsRead` does not send `Content-Type` header for POST

- **File:** `src/hooks/useNotificationPolling.ts:210-213`
- **Issue:** The POST to `/api/notifications` has `X-Requested-With` but no `Content-Type` header and no body. If the notifications route uses `requireJsonContentType`, this will fail with a 415. If it doesn't, the missing `Content-Type` is fine, but it's inconsistent with the rest of the codebase.
- **Impact:** If the notification route adds content-type validation, this breaks silently.
- **Suggested fix:** Either add `headers: { 'Content-Type': 'application/json', 'X-Requested-With': 'fetch' }` and `body: '{}'`, or verify the route doesn't require it and add a comment.

**[CR-010]** Recipe match endpoint returns stale `isPrivate` status between Phase 1 and Phase 3

- **File:** `src/app/api/recipes/match/route.ts:139-145`
- **Issue:** Phase 1 fetches candidate IDs with `isPrivate: false`. Phase 3 (line 139) re-checks `isPrivate: false` in a separate transaction. Between phases, a user could change their profile to private, and Phase 3 would correctly filter them out. However, the `matchResults` array still contains entries for those filtered-out recipes, inflating the `cappedResults` count and potentially returning fewer results than expected (e.g., 18 instead of 20 in `readyToCook`).
- **Impact:** Users occasionally see fewer matched recipes than available. Minor data consistency issue.
- **Suggested fix:** After Phase 3, filter `cappedResults` to only include IDs present in the `recipes` result before categorizing.

**[CR-011]** `maskEmail` in admin route doesn't handle emails with `+` addressing

- **File:** `src/app/api/admin/users/[id]/route.ts:12-21`
- **Issue:** The function masks `user+tag@example.com` as `u*****@e*****e.com`, which is fine for masking. However, if the local part is a single character (e.g., `a@b.com`), `local[0] + '*'.repeat(Math.max(local.length - 1, 2))` produces `a**` — padding to 3 characters, which leaks that the local part was very short (1-2 chars).
- **Impact:** Minor information leak about email structure.
- **Suggested fix:** Use a fixed mask length regardless of input: `maskedLocal = '***'`.

**[CR-014]** `cookedRecipe.delete` inside transaction will throw P2025, but advisory lock prevents concurrent deletes — the outer catch is unreachable

- **File:** `src/app/api/cooked-recipes/route.ts:284-290`
- **Issue:** The advisory lock serializes all cooked-recipe operations per user. Since `findFirst` precedes `delete` inside the lock, the only way `delete` throws P2025 is if another feature deletes the cooked recipe (e.g., cascade from user deletion). The outer P2025 catch (line 299) handles this case, but the comment says "another request already deleted it" which is misleading.
- **Impact:** Misleading comment; no runtime bug.
- **Suggested fix:** Update comment: `// P2025: Record deleted by a concurrent operation (e.g., user account deletion cascade)`
