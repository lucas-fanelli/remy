## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured with good patterns (DI, atomic DB ops, advisory locks). However, several security gaps, race conditions, and data integrity issues exist across the codebase.

### Findings

#### CRITICAL

**[CR-001]** Recipe match endpoint has no GIN index enforcement and unbounded CPU cost

- **File:** `src/app/api/recipes/match/route.ts:110-120`
- **Issue:** The `WITH candidates` CTE scans ALL posts with `LIMIT 200` before the WHERE filter on ingredient names. The `jsonb_array_elements` lateral join runs for every candidate row. Without the GIN index, this is a full table scan + JSON expansion on every request. The comment says "requires the GIN index" but there's no runtime check that it exists — `instrumentation.ts` only warns.
- **Impact:** On a table with 10K+ recipes, this query becomes a full-scan + lateral join = potential multi-second query that can be used for DoS by any authenticated user.
- **Suggested fix:** Add a `SET LOCAL statement_timeout = '5s'` before the query, or fail fast if the GIN index doesn't exist. Also, the LIMIT should be applied after the WHERE filter, not before:

```sql
-- Current (broken): scans 200 rows THEN filters
WITH candidates AS (SELECT ... LIMIT 200) SELECT ... FROM candidates WHERE ...
-- Fixed: filter then limit
SELECT DISTINCT ... FROM "Post", jsonb_array_elements(...) WHERE ... LIMIT 200
```

**[CR-002]** Cooked recipes endpoint lacks Content-Type validation on DELETE

- **File:** `src/app/api/cooked-recipes/route.ts:188-215`
- **Issue:** The DELETE handler doesn't call `requireJsonContentType`. While it reads from query params not body, the POST handler does validate. More critically, the DELETE handler uses `searchParams.get('id')` which is unusual for a REST API and documented as a legacy choice, but the bigger issue is that there's no rate limiting specific to the cooked-recipes endpoint, and the `MAX_DAILY_COOKS` check only applies to POST.
- **Impact:** A malicious user could spam DELETE requests to remove all their cooked recipe history. Low severity but inconsistent with the POST handler's protections.
- **Suggested fix:** Add a comment-level audit log for DELETE like POST has, and consider rate limiting.

**[CR-003]** User deletion race condition between image collection and cascade delete

- **File:** `src/app/api/admin/users/[id]/route.ts:62-73`
- **Issue:** The comment on line 58 acknowledges a race window, but the real issue is more subtle: `tx.post.findMany` and `tx.comment.findMany` read images, then `tx.user.delete` cascades. If a post/comment was created between the reads and the delete, its image won't be in the `imageUrls` array and will be orphaned. The advisory lock only prevents concurrent deletes of the same user, not concurrent content creation.
- **Impact:** Orphaned Cloudinary images accumulate over time, costing storage money.
- **Suggested fix:** The comment mentions a cleanup script handles this. Verify the cleanup script (`cleanup-orphaned-images.ts`) is actually scheduled to run periodically (it's not — it's a manual script).

**[CR-004]** `deductPantryItems` can produce negative quantities under concurrent requests despite advisory lock

- **File:** `src/app/api/cooked-recipes/route.ts:48-95`
- **Issue:** The advisory lock uses `hashtext(${user.id})` as the second key. If the same user submits two cooked recipe requests nearly simultaneously for different recipes that share pantry items, the lock serializes them correctly. However, if `force: true` is sent, insufficient ingredients are deducted anyway (line 81-82: deductions still happen even when `insufficientIngredients.length > 0` and `force` is true). The function returns insufficient list but still applies all planned deductions from Pass 1, which were planned assuming the full amount was available.
- **Impact:** With `force: true`, a pantry item could go negative if it was insufficient. The deduction plan from Pass 1 includes items that WERE sufficient — but insufficient items are still reported without blocking deduction of sufficient ones. Actually on re-read, the insufficient items are NOT in the `deductions` or `deletions` arrays, they're only in `insufficientIngredients`. So this is actually fine. Retracting this finding.

**[CR-005]** No CSRF token on logout endpoint

- **File:** `src/app/api/auth/logout/route.ts:1-15`
- **Issue:** The logout endpoint accepts any POST request and clears the auth cookie. While the middleware has CSRF protection requiring `application/json` Content-Type or `Sec-Fetch-Site: same-origin`, the logout endpoint skips JSON content-type check entirely. An attacker could craft a cross-site form POST with `Content-Type: application/json` (which browsers do allow via fetch from any origin without CORS preflight for simple requests — actually, `application/json` IS a non-simple content type, so this triggers a preflight). So this is mitigated by CORS. Retracting severity.

#### HIGH

**[CR-006]** `recipes/match` endpoint has no pagination — returns up to 60 recipes (20 per category) in a single response

- **File:** `src/app/api/recipes/match/route.ts:170-175`
- **Issue:** Each category is capped at 20, but with 3 categories that's 60 full recipe objects (with ingredients arrays) in one response. Each recipe includes `ingredients: Ingredient[]` which can be large. No cursor-based pagination is offered.
- **Impact:** Large JSON responses (potentially 100KB+) on every pantry page load, wasting bandwidth on mobile.
- **Suggested fix:** Add pagination params or return only recipe IDs + match metadata, fetching full details on demand.

**[CR-007]** `RecipeFeed` component doesn't deduplicate when filter changes race with infinite scroll

- **File:** `src/components/recipe/RecipeFeed.tsx:132-175`
- **Issue:** `abortControllerRef.current?.abort()` cancels the previous request, and `thisRequestId` guards against stale responses. However, there's a gap: if the abort happens after the fetch completes but before the `.json()` call, the abort won't take effect and two responses could update state. The `thisRequestId` check on line 162 covers this case. Actually this looks correct on closer inspection. Retracting.

**[CR-008]** Upload endpoints don't associate images with users — documented but unfixed

- **File:** `src/app/api/upload/route.ts:14-19`
- **Issue:** The comment explicitly documents this: "Uploaded images are not tracked per-user in the database. Any authenticated user can reference any Cloudinary URL." While Cloudinary URLs aren't guessable, this means a user who obtains a URL (e.g., from viewing page source) can set it as their recipe image, effectively "stealing" another user's upload.
- **Impact:** Minor data integrity issue. A user could reference someone else's uploaded image for their recipe.
- **Suggested fix:** As documented, this requires a new DB table. At minimum, add a comment tracking upload ownership so it can be enforced later.

**[CR-009]** `useNotificationPolling` circuit breaker cooldown grows exponentially without bound

- **File:** `src/hooks/useNotificationPolling.ts:97-101`
- **Issue:** `breakerTripCountRef.current` is incremented on every 10-failure window, capped at 10 (line 98). The cooldown is `5min * 2^(tripCount-1)`, so at tripCount=10, cooldown = 5 \* 512 = 2560 minutes = ~42 hours. This means after repeated failures, the user must wait 42 hours or manually click "Retry".
- **Impact:** Users on flaky networks get locked out of notifications for days.
- **Suggested fix:** Cap the cooldown at 30 minutes: `Math.min(5 * 60 * 1000 * Math.pow(2, breakerTripCountRef.current - 1), 30 * 60 * 1000)`

**[CR-010]** Admin stats endpoint uses 7 sequential COUNT subqueries in a single raw SQL

- **File:** `src/infrastructure/services/AdminService.ts:237-251`
- **Issue:** Each `(SELECT COUNT(*) FROM ...)` is a full table scan. With large tables, this single query does 7 sequential scans. No caching is applied.
- **Impact:** Slow admin dashboard load. Each admin page visit triggers 7 table scans.
- **Suggested fix:** Cache stats with a short TTL (30-60s) or use materialized views / approximate counts (`reltuples`).

#### MEDIUM

**[CR-011]** `normalizeIngredientName` exception list is maintained manually and will drift

- **File:** `src/lib/utils/ingredients.ts:15-34`
- **Issue:** The `noStripSuffixWords` set has ~100 hardcoded words. This will inevitably miss edge cases and produce wrong matches (e.g., "molasses" could be stripped to "molasse" without the exception).
- **Impact:** Incorrect pantry-to-recipe matching for unlisted ingredients.
- **Suggested fix:** Consider a stemming library (e.g., `stemmer` npm package) instead of manual suffix stripping.

**[CR-012]** `PersistentSearchBar` creates a new `AbortController` inside `setTimeout` but aborts it outside

- **File:** `src/components/search/PersistentSearchBar.tsx:120-150`
- **Issue:** The comment says "AbortController is intentionally created OUTSIDE the setTimeout" but looking at the code, the controller IS created outside and aborted in cleanup. However, if the component unmounts between query changes, the `isMountedRef` guard prevents state updates but the fetch still completes and processes the response body unnecessarily.
- **Impact:** Minor: wasted network/CPU on unmounted components. Not a memory leak since state updates are guarded.
- **Suggested fix:** The current implementation is acceptable; the comment is accurate.

**[CR-013]** `EditProfileModal` doesn't validate website URL before sending to API

- **File:** `src/components/profile/EditProfileModal.tsx:130-145`
- **Issue:** The client sends `website` directly to `/api/users/profile`. While the server validates via Zod schema (`updateProfileSchema`), the client provides no feedback if the website URL is invalid before submission. The user has to wait for a server round-trip to see the error.
- **Impact:** Poor UX — no client-side validation for website URL format.
- **Suggested fix:** Add `type="url"` validation or a regex check before submitting.

**[CR-014]** `RecipeCard` warns in development for every non-Cloudinary image on every render

- **File:** `src/components/recipe/RecipeCard.tsx:69-71`
- **Issue:** `console.warn` runs on every render, not just once per recipe. If a recipe has an invalid imageUrl and the feed has 12 cards, this logs 12+ warnings per render cycle.
- **Impact:** Console spam in development, performance drag from string operations on every render.
- **Suggested fix:** Move the check to a `useEffect` with the recipe ID as dependency, or use a `Set` to warn once per ID.

**[CR-015]** `Footer` contact form has no server-side handling — relies on `mailto:` links

- **File:** `src/components/Footer.tsx:47-63`
- **Issue:** The "Send Email" button constructs a `mailto:` link and opens it in a new tab. If the user has no email client configured, nothing happens. The 2000-char URL limit check is good but the entire contact flow is fragile.
- **Impact:** Users without desktop email clients (common on web-only setups) can't contact the team.
- **Suggested fix:** Consider a server-side contact form endpoint that sends email via a service like SendGrid/Resend.

**[CR-016]** `SearchResults` component uses substring matching for recipe descriptions without XSS escaping

- **File:** `src/components/SearchResults.tsx:39-43`
- **Issue:** `truncateAtWord` truncates text but React's JSX rendering auto-escapes, so this isn't an XSS risk. However, the `truncateAtWord` function has an edge case: if `maxLen` equals text length, it returns the full text without "..." — this is correct behavior but the function name implies truncation.
- **Impact:** None (retracting, this is fine).

**[CR-017]** `ThemeContext` uses `useLayoutEffect` which warns during SSR

- **File:** `src/contexts/ThemeContext.tsx:36-42`
- **Issue:** `useLayoutEffect` fires a warning in Next.js SSR: "useLayoutEffect does nothing on the server." While this doesn't cause bugs (Next.js suppresses it), it adds noise to server logs.
- **Impact:** Console warnings in development and server-side rendering.
- **Suggested fix:** Use `useIsomorphicLayoutEffect` pattern: `const useIsomorphicLayoutEffect = typeof window !== 'undefined' ? useLayoutEffect : useEffect;`

**[CR-018]** Pantry route POST doesn't sanitize `name` field with `striptags`

- **File:** `src/app/api/pantry/route.ts:78-80`
- **Issue:** The `category` field is sanitized with `striptags` but `name` is only trimmed. While React auto-escapes on render, the raw value is stored in the DB and used in `normalizeIngredientName` for matching, which could produce unexpected results with HTML entities.
- **Impact:** Low — React escapes on render, but stored HTML in ingredient names could confuse matching logic.
- **Suggested fix:** Apply `striptags` to `name` as well for consistency.

#### LOW

**[CR-019]** `MotionContext` fallback returns no-op functions without logging

- **File:** `src/contexts/MotionContext.tsx:56-65`
- **Issue:** When `useMotionContext` is used outside the provider, it silently returns no-ops. This makes debugging difficult if someone accidentally uses it outside the provider tree.
- **Impact:** Silent failures in development if provider is missing.

**[CR-020]** Multiple `loading.tsx` files that return `null` — could be a single shared component

- **Files:** `src/app/notifications/loading.tsx`, `src/app/pantry/loading.tsx`, `src/app/profile/[username]/loading.tsx`, `src/app/recipe/[id]/loading.tsx`, `src/app/settings/loading.tsx`
- **Issue:** Five identical files that each export `function Loading() { return null; }`.
- **Impact:** Minor code duplication.
- **Suggested fix:** Next.js requires `loading.tsx` in each route segment, so these can't be shared. This is fine as-is.

**[CR-021]** `instrumentation.ts` swallows environment validation errors

- **File:** `src/instrumentation.ts:6-9`
- **Issue:** `validateEnvironment()` errors are caught and logged but the app continues to start. In production, this means the app can start with missing required env vars.
- **Impact:** App starts in a broken state without clear indication.
- **Suggested fix:** In production, re-throw the error to prevent startup: `if (process.env.NODE_ENV === 'production') throw error;`

**[CR-022]** `getDifficultyColor` imports Sentry dynamically on every unknown difficulty value

- **File:** `src/lib/utils/recipe.ts:25-30`
- **Issue:** For each new unknown difficulty value, a dynamic `import('@sentry/nextjs')` is triggered. While the `warnedDifficulties` Set prevents repeated calls for the same value, the dynamic import is still unnecessary overhead.
- **Impact:** Minor performance cost from dynamic imports in production.
- **Suggested fix:** Use the pre-cached Sentry from `logger.ts` pattern or import statically.
