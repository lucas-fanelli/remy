## Code Review — 2026-03-21

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes and client components.

### Findings

#### CRITICAL

**[CR-001]** Upload endpoints accept any authenticated user's Cloudinary URL — no ownership tracking

- **File:** `src/app/api/upload/route.ts:17-22`
- **Issue:** Uploaded images are not linked to the uploading user. Any authenticated user can reference any Cloudinary URL in their recipe/comment. The TODO has been there for multiple commits with no progress.
- **Impact:** User A uploads an image, User B uses that URL in their recipe. If User A deletes their account, the image cleanup script deletes the image, breaking User B's recipe. Also enables image theft between users.
- **Suggested fix:** Create an `Upload` table (`id, publicId, userId, createdAt`) and validate ownership on recipe/comment create/update.

**[CR-002]** `cooked-recipes` DELETE restores pantry items from user-controlled JSON without adequate validation

- **File:** `src/app/api/cooked-recipes/route.ts:187-230`
- **Issue:** `deductedIngredients` is stored in the DB as JSON and restored to the pantry on DELETE. While Zod validation is applied, the `amount` field accepts up to 10000 per item and up to 100 items — a single DELETE could inject 1,000,000 units into a pantry. The `restoredQuantity` is capped at 10000 per item but this is per-restoration, not per-pantry total.
- **Impact:** Pantry quantity inflation. A user could manipulate the stored JSON (if they had DB access) or exploit the generous limits to inflate pantry quantities far beyond realistic values.
- **Suggested fix:** Cap total pantry item quantity at a reasonable maximum (e.g., MAX_QUANTITY) after restoration, not just per-operation. Also validate that the cookedRecipe wasn't already restored (the P2025 catch helps but add explicit `restoredAt` tracking).

**[CR-003]** Recipe match endpoint raw SQL with `LIKE ANY` is vulnerable to ReDoS via crafted pantry names

- **File:** `src/app/api/recipes/match/route.ts:97-100`
- **Issue:** While the code filters pantry names to `/^[\p{L}\p{N}\s\-'.]+$/u`, this regex itself uses Unicode property escapes that match extremely large character classes. The `escapeLike` function only escapes SQL wildcards but the names are used in PostgreSQL `LIKE` patterns. More critically, the 20-pattern LIKE ANY array against potentially millions of rows with `jsonb_array_elements` is an expensive query with only a 5-second timeout.
- **Impact:** A user with 20 carefully crafted pantry items could cause significant DB load. The advisory lock only prevents concurrent requests from the same user, not different users.
- **Suggested fix:** Add a global concurrency limit (e.g., semaphore) for the match endpoint, not just per-user. Consider using a GIN index with `@>` operator instead of LIKE patterns.

**[CR-004]** No CSRF protection on logout endpoint

- **File:** `src/app/api/auth/logout/route.ts:3-14`
- **Issue:** The logout endpoint doesn't require `X-Requested-With` header or any CSRF protection. The middleware CSRF check requires the header for POST requests, but the logout route exits early if no cookie is present without hitting the middleware check. A cross-site request could log users out.
- **Impact:** Cross-site logout attack. While lower severity than CSRF on state-changing endpoints, it degrades user experience and could be used as part of a larger attack chain.
- **Suggested fix:** The middleware should already catch this since it's a POST to `/api/*`. Verify the middleware CSRF check runs before the route handler. The early return for missing cookies is fine but happens after middleware.

#### HIGH

**[CR-005]** `handleShare` in recipe detail page leaks full URL to Web Share API without sanitization

- **File:** `src/app/recipe/[id]/page.tsx:244-267`
- **Issue:** `window.location.href` is passed directly to `navigator.share()` and `navigator.clipboard.writeText()`. If the URL contains user-controlled fragments or query params, these are shared verbatim.
- **Impact:** Low risk in current implementation since recipe IDs are UUIDs, but if URL params are ever added (e.g., referral codes), they could be leaked.
- **Suggested fix:** Construct the share URL explicitly: `${window.location.origin}/recipe/${recipeId}` instead of using `window.location.href`.

**[CR-006]** Admin user emails are masked but the masking is trivially reversible

- **File:** `src/app/api/admin/users/[id]/route.ts:18-26`, `src/infrastructure/services/AdminService.ts:14-23`
- **Issue:** `maskEmail` preserves the first character of local and domain parts, plus the full TLD and domain length. For emails like `j***@g***.com`, reversing to `john@gmail.com` is trivial via dictionary attack. The function is duplicated in two files.
- **Impact:** Email enumeration by admin users. Admins can reconstruct most email addresses.
- **Suggested fix:** If admins shouldn't see emails, don't return them at all. If they should, don't mask. The current approach provides false security. Also deduplicate the function.

**[CR-007]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:141-170`
- **Issue:** When filters change, `loadRecipes(true)` resets the list. But during the reset, if the previous request's response arrives (despite AbortController), the `requestIdRef` guard can fail if the stale response resolves between the abort and the new request assignment. The `existingIds` Set dedup only protects append mode, not reset mode.
- **Impact:** Potential duplicate recipes in the feed after rapid filter changes, causing React key warnings and visual duplication.
- **Suggested fix:** In the reset branch (`if (reset)`), clear `recipesLengthRef.current = 0` before the fetch, not after. Also set recipes atomically: `setRecipes(data.recipes)` already handles this, but the `requestIdRef` check needs to happen earlier.

**[CR-008]** `deductPantryItems` uses sequential updates inside transaction — N+1 writes

- **File:** `src/app/api/cooked-recipes/route.ts:73-87`
- **Issue:** Each pantry deduction is a separate `tx.pantryItem.update` or `tx.pantryItem.delete` call inside a loop. For a recipe with 20 ingredients, this is 20 sequential DB writes.
- **Impact:** Slow transactions holding advisory locks longer than necessary, increasing contention under load.
- **Suggested fix:** Batch the updates using `tx.$executeRaw` with a single UPDATE/DELETE statement, or use `updateMany` with computed values.

**[CR-009]** Footer contact form `mailto:` link has no URL length validation before `window.location.href` assignment

- **File:** `src/components/Footer.tsx:65-74`
- **Issue:** The 1500-char limit is checked after encoding, but the error is shown via state update which races with `window.location.href` assignment. Actually, looking more carefully, the length check happens before the assignment — but the `sending` guard at line 59 doesn't prevent resubmission if the first click passed validation but hadn't set `sending` yet (no debounce).
- **Impact:** Minor — double-submission of mailto link opening two email windows.
- **Suggested fix:** Set `setSending(true)` at the very beginning of `handleSendEmail`, before validation.

#### MEDIUM

**[CR-010]** `useNotificationPolling` circuit breaker cooldown can reach 30 minutes — no user feedback

- **File:** `src/hooks/useNotificationPolling.ts:107-112`
- **Issue:** The exponential backoff caps at 30 minutes. During this time, `isPollingPaused` is true but the only UI feedback is a small "Retry" text in the navigation. Users may not notice notifications are paused for up to 30 minutes.
- **Impact:** Users miss notifications silently. The Retry button is easy to miss on mobile.
- **Suggested fix:** Show a more prominent indicator (e.g., a banner or badge color change) when polling is paused for more than 5 minutes.

**[CR-011]** `PersistentSearchBar` fires live search on every keystroke despite 300ms debounce — AbortController cleanup race

- **File:** `src/components/search/PersistentSearchBar.tsx:117-148`
- **Issue:** The cleanup function creates a new `AbortController` outside `setTimeout`, but `searchAbortRef.current` is only assigned inside the timeout. If the component unmounts between `clearTimeout` and the timeout firing, the controller.abort() in cleanup works correctly. However, if two rapid keystrokes happen within 300ms, the first timeout's controller is aborted before it runs, but the ref still points to a previous controller.
- **Impact:** Potential stale search results appearing briefly. Minor UX issue.
- **Suggested fix:** Assign `searchAbortRef.current = controller` immediately (outside setTimeout), not inside it. The current code comment says this is intentional but the reasoning is flawed.

**[CR-012]** `EditProfileModal` website URL validation doesn't check for `javascript:` protocol

- **File:** `src/components/profile/EditProfileModal.tsx:117-127`
- **Issue:** Client-side validation checks for `http:` or `https:` protocol, but the `new URL()` constructor accepts `javascript:` URLs on some browsers. The server-side schema also validates, but the client-side check should be equally strict.
- **Impact:** If server-side validation is ever bypassed, stored XSS via `javascript:` URL in the website field. Defense-in-depth gap.
- **Suggested fix:** The current check `!['http:', 'https:'].includes(parsed.protocol)` already blocks `javascript:`, so this is actually fine. Withdrawing this finding.

**[CR-013]** `RecipeCard` non-Cloudinary image fallback chain is fragile

- **File:** `src/components/recipe/RecipeCard.tsx:128-140`
- **Issue:** When a non-Cloudinary URL is provided, `src` is set to `/chef-logo.png` (fallback). If the fallback also fails, `setImgHidden(true)` is called. But the `onError` handler checks `isCloudinaryUrl(recipe.imageUrl)` — for non-Cloudinary URLs, it immediately sets `imgHidden` even on first error, bypassing the fallback entirely.
- **Impact:** Recipes with non-Cloudinary images (data integrity issue) show a placeholder icon instead of attempting the fallback image. Acceptable degradation but could be confusing during development.
- **Suggested fix:** This is actually correct behavior (comment on line 128-132 documents this). The issue is that non-Cloudinary URLs shouldn't exist in production. Add a DB constraint or migration to validate existing data.

**[CR-014]** `striptags` used for XSS prevention is insufficient for attribute-based attacks

- **File:** `src/infrastructure/services/RecipeService.ts:5-6`
- **Issue:** Comment in the code acknowledges this: "striptags strips HTML tags but NOT attribute-based XSS vectors." However, if any future rendering uses `dangerouslySetInnerHTML`, this sanitization is insufficient.
- **Impact:** No current impact since React auto-escapes JSX. Future risk if raw HTML rendering is added.
- **Suggested fix:** Document this limitation in a central security doc. Consider adding DOMPurify as a dependency for any future raw HTML rendering needs.

**[CR-015]** Admin stats endpoint has a 15-second in-memory cache but no invalidation

- **File:** `src/infrastructure/services/AdminService.ts:253-260`
- **Issue:** `getStats()` caches results for 15 seconds in a static property. In serverless environments (Vercel), this cache is per-instance and effectively useless. In long-running servers, 15 seconds of stale data is acceptable, but there's no way to force a refresh.
- **Impact:** Admin dashboard may show stale stats for up to 15 seconds. Minor but misleading.
- **Suggested fix:** Accept a `forceRefresh` parameter, or remove the cache since the single-query approach is already efficient.

#### LOW

**[CR-016]** Duplicated `maskEmail` function

- **File:** `src/app/api/admin/users/[id]/route.ts:18-26` and `src/infrastructure/services/AdminService.ts:14-23`
- **Issue:** Same function implemented twice with identical logic.
- **Impact:** Maintenance burden — a fix in one won't automatically apply to the other.
- **Suggested fix:** Extract to `src/lib/utils/email.ts` and import in both locations.

**[CR-017]** `motion.create` called at module scope in `RecipeCard` but inside component in other files

- **File:** `src/components/recipe/RecipeCard.tsx:30-31` vs `src/components/motion.ts`
- **Issue:** `RecipeCard` correctly calls `motion.create(Card)` at module scope with a comment explaining why. But other components import from `@/components/motion` which does the same. The pattern is inconsistent — some components use `MotionCard` from motion.ts, others create their own.
- **Impact:** No functional impact. Code inconsistency.
- **Suggested fix:** Standardize on importing from `@/components/motion.ts` everywhere.

**[CR-018]** `SearchResults` component has a `truncateAtWord` function that doesn't handle edge cases

- **File:** `src/components/SearchResults.tsx:40-44`
- **Issue:** `truncateAtWord` with `maxLen <= 0` returns empty string, but `lastIndexOf(' ', 0)` returns 0 for strings starting with a space, which would return `"..."` (empty + ellipsis).
- **Impact:** Unlikely edge case in practice. Description field would need to start with a space.
- **Suggested fix:** Add `if (idx === 0) return text.substring(0, maxLen) + '...'`.

**[CR-019]** Test files use `any` type extensively for framer-motion mocks

- **File:** Multiple test files (e.g., `src/components/recipe/__tests__/CommentsSection.test.tsx`)
- **Issue:** Every test file has its own framer-motion mock with `any` types. A shared mock exists at `src/__tests__/mocks/framer-motion.ts` but isn't wired up via moduleNameMapper.
- **Impact:** Maintenance burden. Each new test file must copy-paste the mock.
- **Suggested fix:** Add `'framer-motion': '<rootDir>/src/__tests__/mocks/framer-motion.ts'` to jest.config.js moduleNameMapper and remove inline mocks.
