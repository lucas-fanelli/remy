## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security-sensitive patterns are implemented correctly (CSRF, httpOnly cookies, Cloudinary URL validation), but a critical CSP misconfiguration will break all MUI styling in production, and an information disclosure exists in the recipe DELETE flow.

### Findings

#### CRITICAL

**[CR-001]** CSP nonce not passed to MUI AppRouterCacheProvider — all styles blocked

- **File:** `src/app/layout.tsx:80-81`
- **Issue:** The nonce is extracted from headers and used for the inline `<script>`, but never passed to `<AppRouterCacheProvider>`. MUI Emotion injects `<style>` tags at runtime without the nonce attribute. The middleware's CSP directive `style-src 'self' 'nonce-${nonce}'` will block every Emotion-injected style tag.
- **Impact:** The entire application renders unstyled in any browser enforcing CSP. Every MUI component loses its styling.
- **Suggested fix:**

```tsx
<AppRouterCacheProvider options={{ key: 'mui', nonce }}>
```

**[CR-002]** Recipe DELETE leaks imageUrl before ownership check

- **File:** `src/app/api/recipes/[id]/route.ts:96-100`
- **Issue:** `recipeForCleanup` fetches the recipe's `imageUrl` via `prisma.post.findUnique` before `recipeService.deleteRecipe` performs the ownership check. Any authenticated user can learn any recipe's Cloudinary image URL by calling DELETE — even when the delete itself is rejected with 403.
- **Impact:** Information disclosure. Attacker can enumerate all recipe image URLs.
- **Suggested fix:** Move the Cloudinary URL fetch inside the service or after the ownership-checked delete succeeds:

```typescript
const recipeService = container.getRecipeService();
// Fetch imageUrl only after confirming ownership
const recipe = await prisma.post.findUnique({
  where: { id },
  select: { imageUrl: true, userId: true },
});
if (!recipe || recipe.userId !== payload.userId) {
  // Let deleteRecipe throw the appropriate error
}
await recipeService.deleteRecipe(id, payload.userId);
// Now safe to use recipe.imageUrl for cleanup
```

#### HIGH

**[CR-003]** Recipe matching loads unbounded data into memory

- **File:** `src/app/api/recipes/match/route.ts:56-63`
- **Issue:** Fetches up to 100 recipes with full ingredient arrays into memory, then performs O(recipes × ingredients × pantryItems) matching in the API route. As recipe count grows, this will spike memory usage and response time per request.
- **Impact:** OOM crashes or extreme latency under load. A single endpoint call can allocate megabytes of JSON.
- **Suggested fix:** Move matching logic to a database query (e.g., `jsonb` containment in PostgreSQL) or implement pagination with cursor-based fetching and streaming results.

**[CR-004]** Logout silently fails — cookie persists, user re-authenticated on refresh

- **File:** `src/contexts/AuthContext.tsx:85-93`
- **Issue:** `logout()` catches the `fetch('/api/auth/logout')` error and continues with client-side cleanup (`setUser(null)`). If the server call fails (network error, timeout), the httpOnly `auth_token` cookie is never cleared. On next page load, `/api/auth/me` succeeds and the user is logged back in.
- **Impact:** User believes they logged out but remain authenticated. Critical on shared devices.
- **Suggested fix:** Retry the logout call, or redirect to a server-side logout route that always clears the cookie:

```typescript
const logout = async () => {
  setUser(null);
  try {
    getQueryClient()?.clear();
  } catch {}
  // Navigate to server endpoint that always clears cookie
  window.location.href = '/api/auth/logout-redirect';
};
```

**[CR-005]** `normalizeIngredientName` produces incorrect output for common plurals

- **File:** `src/lib/utils/ingredients.ts:18-28`
- **Issue:** "tomatoes" does not match any of the special plural rules (`ies`, `ves`, `ses`, `xes`, `zes`, `ches`, `shes`), so it falls through to the simple `endsWith('s')` removal, producing "tomatoe" instead of "tomato". Same for "potatoes" → "potatoe".
- **Impact:** Pantry deduction after cooking fails for common ingredients. `ingredientMatches` still works due to the `includes` fallback, but direct equality checks (`normalizedPantry === normalizedRecipe`) fail.
- **Suggested fix:** Add an `oes` → `o` rule before the generic `s` removal:

```typescript

```

#### MEDIUM

**[CR-006]** In-memory rate limit map leaks entries for inactive IPs

- **File:** `src/middleware.ts:35-40`
- **Issue:** Expired entries are only cleaned when that specific key is accessed again, or when map size exceeds 1000. IPs that make a burst of requests and never return leave entries in the map until the 1000-entry threshold triggers bulk cleanup.
- **Impact:** Slow memory leak in long-running processes. In serverless this is mitigated by ephemeral instances, but on persistent servers (Docker/VPS) memory grows unbounded.
- **Suggested fix:** Add a periodic cleanup interval or use a `Map` with LRU eviction (e.g., `lru-cache`).

**[CR-007]** Comment image validation leaks Cloudinary configuration status

- **File:** `src/app/api/recipes/[id]/comments/route.ts:89-91`
- **Issue:** When `CLOUDINARY_CLOUD_NAME` is not set, the endpoint returns `{ error: 'Image upload not configured' }` with status 500. This reveals infrastructure configuration state to any authenticated user.
- **Impact:** Attackers can probe which infrastructure services are configured.
- **Suggested fix:** Return a generic error: `{ error: 'Image upload is currently unavailable' }`.

**[CR-008]** Notification polling exponential backoff lacks jitter

- **File:** `src/components/Navigation.tsx:195-199`
- **Issue:** `Math.min(BASE_INTERVAL * Math.pow(2, failures), MAX_INTERVAL)` produces identical retry times across all browser tabs/users. If a transient server error affects many users simultaneously, they all retry at the same intervals, creating a thundering herd.
- **Impact:** Cascading retries amplify load on a recovering server.
- **Suggested fix:** Add random jitter:

```typescript
const jitter = Math.random() * BASE_INTERVAL * 0.5;
const backoffMs = Math.min(BASE_INTERVAL * Math.pow(2, failures) + jitter, MAX_INTERVAL);
```

**[CR-009]** "Already cooked today" error message is misleading

- **File:** `src/app/api/cooked-recipes/route.ts:92`
- **Issue:** The 24-hour duplicate window is a rolling window (`Date.now() - 24h`), but the error says "Recipe already marked as cooked today". If a user cooks at 11 PM, they can't re-mark until 11 PM the next day, not midnight.
- **Impact:** User confusion. Not a security issue, but incorrect UX messaging.
- **Suggested fix:** Change to `"Recipe already marked as cooked in the last 24 hours"`.

#### LOW

**[CR-010]** Inconsistent rating precision between admin recalc and comment endpoints

- **File:** `src/app/api/admin/recalc-ratings/route.ts:22` vs `src/app/api/recipes/[id]/comments/[commentId]/route.ts:74`
- **Issue:** Admin recalc uses `ROUND(AVG("rating")::numeric, 1)::float` in SQL, while comment PATCH uses `Math.round(avg * 10) / 10` in JS. These can produce different results due to floating-point representation differences between PostgreSQL and JavaScript.
- **Impact:** Rating values may differ by ±0.1 depending on which code path last updated them.
- **Suggested fix:** Centralize the rounding logic in a shared utility function and use it everywhere.

**[CR-011]** General upload endpoint missing Content-Type header validation

- **File:** `src/app/api/upload/route.ts`
- **Issue:** Unlike the avatar upload route (`src/app/api/upload/avatar/route.ts:35-41`), the general upload endpoint does not validate the `Content-Type` header is `multipart/form-data`. A malformed request will throw from `request.formData()` and fall to the generic 500 catch.
- **Impact:** Inconsistent error responses; missing a 400 for client mistakes.
- **Suggested fix:** Add the same Content-Type check as the avatar endpoint.
