## Code Review — 2026-03-18

### Summary

Two critical runtime errors will crash production pages. The recipe matching endpoint has an undefined variable reference, and the home page references an undeclared `router`. Additional issues with CSP enforcement, unmemoized context values causing polling churn, and a TOCTOU race in recipe deletion.

### Findings

#### CRITICAL

**[CR-001]** Undefined variable `matchPercentage` in recipe match categorization

- **File:** `src/app/api/recipes/match/route.ts:131`
- **Issue:** The categorization loop references `matchPercentage` (a block-scoped variable from the first-pass loop) instead of `match.matchPercentage`. This is a `ReferenceError` that will crash the endpoint.
- **Impact:** `/api/recipes/match` returns 500 for every authenticated user with a pantry. The "Recipes Based on Your Pantry" feature is completely broken for any recipe that isn't a 100% match.
- **Suggested fix:**

```typescript
// Line 131: replace
} else if (matchPercentage >= 70) {
// with
} else if (match.matchPercentage >= 70) {
```

**[CR-002]** `router` referenced but never declared in home page

- **File:** `src/app/page.tsx:29`
- **Issue:** The `onCreateRecipe` callback references `router.push('/auth')` but `useRouter` is never imported or called. This throws a `ReferenceError` when an unauthenticated user clicks "Share Recipe".
- **Impact:** Runtime crash for all guest users who attempt to create a recipe from the home page feed.
- **Suggested fix:**

```typescript
// Add to imports and component body:
import { useRouter } from 'next/navigation';
// inside Home():
const router = useRouter();
```

#### HIGH

**[CR-003]** `logout` not memoized in AuthContext causes notification polling churn

- **File:** `src/contexts/AuthContext.tsx:95-117`
- **Issue:** `logout` is a plain async function recreated every render. `Navigation.tsx:180` includes `logout` in the `useCallback` dependency array of `fetchNotifications`, which is a dependency of the polling `useEffect`. Every `AuthProvider` re-render creates a new `logout` reference, tearing down and recreating the notification polling interval.
- **Impact:** Notification polling restarts on every context re-render, causing unnecessary API calls and potential flickering of notification state.
- **Suggested fix:** Wrap `logout` (and `login`, `register`, `updateProfile`) with `useCallback`:

```typescript
const logout = useCallback(async () => {
  setUser(null);
  // ... rest of implementation
}, []);
```

**[CR-004]** CSP `style-src` uses nonce-only, but MUI Emotion injects styles without nonce at runtime

- **File:** `src/middleware.ts:80`
- **Issue:** The CSP header is `style-src 'self' 'nonce-${nonce}' https://fonts.googleapis.com`. MUI/Emotion dynamically inserts `<style>` tags client-side that won't carry the nonce. The `AppRouterCacheProvider` with nonce handles SSR-rendered styles, but client-side theme changes, dynamic component rendering, and `sx` prop styles injected after hydration will be blocked by browsers enforcing CSP.
- **Impact:** Broken styling in production on browsers that enforce CSP (most modern browsers). Components rendered only on the client side will appear unstyled.
- **Suggested fix:** Either add `'unsafe-inline'` to `style-src` (weakens CSP) or configure Emotion's cache to use the nonce for all client-side insertions via `prepend` + `nonce` option. Since you're already passing nonce to `AppRouterCacheProvider`, ensure Emotion's sheet manager also receives it for client-side insertions.

**[CR-005]** TOCTOU race in recipe DELETE — ownership check and Cloudinary cleanup use stale data

- **File:** `src/app/api/recipes/[id]/route.ts:105-130`
- **Issue:** `findUnique` fetches `imageUrl` and `userId` for ownership check, then `recipeService.deleteRecipe` does its own atomic `deleteWhere`. Between the `findUnique` and `deleteWhere`, another request could delete the recipe, causing the service to throw "not found" while the route handler already retrieved the `imageUrl`. The Cloudinary cleanup would then attempt to delete an image for a recipe that was already deleted by someone else (race between two concurrent DELETE requests).
- **Impact:** Orphaned Cloudinary images or double-deletion attempts. Low probability but the pattern is wrong — the ownership check in the route handler is redundant with the service's atomic check.
- **Suggested fix:** Remove the route-level `findUnique` ownership check. Move the `imageUrl` retrieval inside or after `recipeService.deleteRecipe`, or have the service return the deleted record's `imageUrl`.

#### MEDIUM

**[CR-006]** Recipe match endpoint hardcoded to 200 most recent recipes

- **File:** `src/app/api/recipes/match/route.ts:65-72`
- **Issue:** `take: 200, orderBy: { createdAt: 'desc' }` means only the 200 newest recipes are ever considered for pantry matching. Older recipes are permanently excluded regardless of ingredient match quality.
- **Impact:** Users never see matches for older recipes, making the feature progressively less useful as the recipe database grows.
- **Suggested fix:** Remove the `take` limit or increase it significantly, and consider querying by ingredient overlap rather than brute-forcing all recipes.

**[CR-007]** Notification polling effect cleanup doesn't abort in-flight fetch on user change

- **File:** `src/components/Navigation.tsx:236-261`
- **Issue:** The `notificationAbortRef.current?.abort()` in the cleanup only aborts the previous fetch within `fetchNotifications`. But the `scheduleNext` timeout callback captures a stale `fetchNotifications` closure. When `user` changes (logout), the cleanup clears the timeout, but if `fetchNotifications` is already in-flight (not yet resolved), the `consecutiveFailuresRef.current = Infinity` on 401 response calls `logout()` again — a re-entrant call during cleanup.
- **Impact:** Potential double logout calls and state inconsistency during authentication transitions.
- **Suggested fix:** Add the AbortController abort to the effect cleanup:

```typescript
return () => {
  clearPolling();
  notificationAbortRef.current?.abort();
  document.removeEventListener('visibilitychange', handleVisibility);
};
```

This is already there — but `scheduleNext` captures `fetchNotifications` which itself captures `logout`. If `logout` changes (per CR-003), the scheduled callback runs with the old `logout`. Fix CR-003 first.

**[CR-008]** Follow endpoint has TOCTOU between `findUnique` check and `$transaction` create

- **File:** `src/app/api/users/[username]/follow/route.ts:44-56`
- **Issue:** The `existingFollow` check via `findUnique` is outside the `$transaction`. Two concurrent follow requests could both pass the check, then both enter the transaction. The catch block handles the unique constraint violation, but the follower count returned to the first successful request may be wrong because the second request's create hasn't been rolled back yet.
- **Impact:** Incorrect follower count returned in race conditions; duplicate follow notification possible.
- **Suggested fix:** Move the existence check inside an interactive `$transaction` or remove it entirely and rely solely on the unique constraint catch.

#### LOW

**[CR-009]** Environment validation false-positives on legitimate secrets containing "secret"

- **File:** `src/lib/env-validation.ts:95-104`
- **Issue:** `jwtSecret.includes(insecure)` checks if the secret _contains_ words like "secret". A legitimate 64-char random secret like `a8f3...secret...b2c1` would be flagged.
- **Impact:** False validation errors in production for legitimate secrets that happen to contain common English words.
- **Suggested fix:** Check for exact match or only flag very short secrets, not substring presence.

**[CR-010]** `RecipeCard` image `onError` handler uses `dataset.fallback` without proper typing

- **File:** `src/components/recipe/RecipeCard.tsx:120-123`
- **Issue:** `e.currentTarget.dataset.fallback` is used as a guard against infinite fallback loops, but `dataset` properties are always strings. The check `!e.currentTarget.dataset.fallback` will be falsy for any truthy string, which is correct, but `dataset.fallback` could be set by external HTML manipulation. Minor, but a boolean state variable would be more robust.
- **Impact:** Cosmetic only. Infinite image error loop is prevented but the mechanism is fragile.
