## Code Review — 2026-03-20

### Summary

Large recipe-sharing platform with solid architecture (DI container, clean layer separation, comprehensive tests). However, there is a critical bug in the recipe matching SQL pre-filter that silently drops valid matches, plus several high-severity inconsistencies and a floating promise.

### Findings

#### CRITICAL

**[CR-001]** Recipe match SQL pre-filter uses raw `lower()` but compares against normalized (plural-stripped) pantry names — causes silent false negatives

- **File:** `src/app/api/recipes/match/route.ts:113-121`
- **Issue:** `pantryNames` are processed through `normalizeIngredientName()` which strips plurals, special characters, etc. (e.g., "tomatoes" → "tomato"). The SQL query compares these against `lower(elem->>'name')` which only lowercases DB values (e.g., "Tomatoes" → "tomatoes"). Since `'tomato' != 'tomatoes'`, the recipe is excluded from the candidate set entirely and never reaches the in-memory matcher.
- **Impact:** Users with pantry items that have plural forms stored differently than recipe ingredients will see missing matches. This silently degrades the core feature of the app.
- **Suggested fix:** Apply the same normalization on the DB side, or compare against both normalized and raw forms:

```sql
-- Option A: Pre-compute both forms in the pantry patterns array
-- Include both "tomato" AND "tomatoes" in the ANY() array

-- Option B: Use LIKE/similarity instead of exact match
AND lower(elem->>'name') LIKE ANY(ARRAY[...patterns with % wildcards...])
```

Or better, normalize at write time by storing a `normalizedName` field on recipe ingredients.

#### HIGH

**[CR-002]** `normalizeIngredientName` won't strip trailing 's' from words ≤5 characters

- **File:** `src/lib/utils/ingredients.ts:56`
- **Issue:** The guard `normalized.length > 5` means ingredients like "limes" (5 chars), "peas" (4 chars), "figs" (4 chars), "clams" (5 chars) will never have their trailing 's' removed. This breaks matching against "lime", "pea", "fig", "clam" in recipes.
- **Impact:** Short-named ingredients fail to match their singular/plural counterparts, reducing match accuracy across the app (pantry matching, cooked recipe deductions, recipe suggestions).
- **Suggested fix:** Lower the threshold or use a more sophisticated approach:

```typescript
// Change from length > 5 to length > 3, and add a safe-word check
} else if (normalized.endsWith('s') && !normalized.endsWith('ss') && normalized.length > 3) {
  normalized = normalized.slice(0, -1);
}
```

**[CR-003]** Admin PATCH endpoint returns inconsistent response shapes for promote vs. demote

- **File:** `src/app/api/admin/users/[id]/route.ts:103-117`
- **Issue:** Promote returns raw `AdminUser` object directly. Demote returns `{ success: true, user: AdminUser }`. Any future client code that parses the response will break for one of the two cases.
- **Impact:** API contract is inconsistent. Currently masked because the frontend ignores the response body and refetches, but any future consumer will hit this.
- **Suggested fix:**

```typescript
if (action === 'promote') {
  const result = await adminService.promoteToAdmin(id);
  user = { success: true, user: result }; // Wrap consistently
} else {
  // ... existing demote code already wraps correctly
}
```

**[CR-004]** User profile DELETE fires Cloudinary cleanup as a floating promise

- **File:** `src/app/api/users/profile/route.ts:74`
- **Issue:** `Promise.allSettled(imageUrls.map(...)).catch(() => {})` is not awaited. In serverless environments (Vercel), the response is sent and the function may be terminated before the cleanup completes. The `.catch(() => {})` prevents unhandled rejection but doesn't prevent premature termination.
- **Impact:** Cloudinary images from self-deleted accounts are likely to remain orphaned in serverless deployments, accumulating storage costs faster than the cleanup script can handle.
- **Suggested fix:**

```typescript
// Await the cleanup (still best-effort due to allSettled)
await Promise.allSettled(imageUrls.map((url) => cleanupCloudinaryImage(url)));
```

#### MEDIUM

**[CR-005]** CSP `img-src` allows all of `res.cloudinary.com` when `CLOUDINARY_CLOUD_NAME` is unset

- **File:** `src/middleware.ts:148`
- **Issue:** When `CLOUDINARY_CLOUD_NAME` is not set, the CSP becomes `img-src 'self' data: https://res.cloudinary.com blob:` — allowing images from _any_ Cloudinary account, not just the app's.
- **Impact:** Reduces CSP effectiveness. An attacker who can inject image URLs could load tracking pixels or offensive content from any Cloudinary account.
- **Suggested fix:**

```typescript
const cloudImgSrc = process.env.CLOUDINARY_CLOUD_NAME
  ? `https://res.cloudinary.com/${process.env.CLOUDINARY_CLOUD_NAME}/`
  : ''; // Don't allow any Cloudinary if not configured
```

**[CR-006]** Upload route exposes Cloudinary `publicId` in response

- **File:** `src/app/api/upload/route.ts:83`
- **Issue:** The response includes `publicId` which is the Cloudinary internal identifier. Combined with the cloud name (in CSP headers), this gives clients enough info to construct transformation URLs or attempt Cloudinary admin API calls.
- **Impact:** Information disclosure. Low severity alone, but combined with a compromised Cloudinary API key, the publicId enables targeted image manipulation.
- **Suggested fix:** Remove `publicId` from the response — the client only needs `url`.

```typescript
return NextResponse.json({
  success: true,
  url: fileUrl,
  size: file.size,
  type: file.type,
});
```

**[CR-007]** Footer `sending` state timeout leaks on unmount

- **File:** `src/components/Footer.tsx:80`
- **Issue:** `setTimeout(() => { setSending(false); }, 3000)` has no cleanup. If the component unmounts before 3s (e.g., navigation), React will warn about state updates on unmounted components.
- **Impact:** React warning in console; minor memory leak. No data corruption.
- **Suggested fix:** Use a ref to track mount status, or clear the timeout in a useEffect cleanup.

**[CR-008]** Hardcoded theme colors in layout inline script can drift from ThemeContext

- **File:** `src/app/layout.tsx:87-88` vs `src/contexts/ThemeContext.tsx:161-170`
- **Issue:** The inline script hardcodes `#1E1E1E` (dark background) and `#FAFAFA` (light background). These same values appear in ThemeContext's palette. If one is changed without the other, there will be a visible flash during theme hydration.
- **Impact:** Visual glitch (FOUC) if colors diverge.
- **Suggested fix:** Extract these colors to `BRANDING` config or a shared constants file, and reference them in both places. Add a comment linking the two locations.

**[CR-009]** Recipe match endpoint lacks per-user rate limiting for expensive DB query

- **File:** `src/app/api/recipes/match/route.ts`
- **Issue:** The match endpoint runs a complex transaction with `jsonb_array_elements` cross join, in-memory matching with O(candidates \* ingredients) comparisons, and multiple batch fetches. While there's a middleware-level rate limit of 30 requests per window, a determined user polling this endpoint could cause significant DB load.
- **Impact:** Performance degradation under load; potential for DB connection pool exhaustion.
- **Suggested fix:** Add result caching with a short TTL (30-60s) keyed by `userId + pantry hash`, or add the per-user advisory lock that's already registered (`PG_ADVISORY_LOCK_MATCH = 48883`) but never used.

if (!ct?.startsWith('application/json'))

**[CR-011]** Admin email masking inconsistency

- **File:** `src/infrastructure/services/AdminService.ts` (masks emails in `getAllUsers`, `getAllRecipes`, `getAllComments`) vs `src/app/api/admin/users/[id]/route.ts:116` (demote response returns unmasked email from Prisma)
- **Issue:** The `AdminService` masks emails in list responses, but the demote transaction returns raw Prisma `user.update` output with the full email. The promote path goes through `AdminService.promoteToAdmin` which doesn't mask either.
- **Impact:** Admin panel leaks real emails in promote/demote API responses even though list views are masked.
- **Suggested fix:** Apply `maskEmail` consistently in all admin response paths, or decide to not mask at all (admins may need real emails).
