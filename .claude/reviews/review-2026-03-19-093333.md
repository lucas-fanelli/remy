## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured with good security patterns (httpOnly cookies, CSRF, CSP, rate limiting). However, several critical and high-severity issues exist around race conditions, missing authorization, information leaks, and unsafe patterns.

### Findings

#### CRITICAL

**[CR-001]** Recipe match endpoint leaks all recipes via `SET LOCAL statement_timeout` outside transaction

- **File:** `src/app/api/recipes/match/route.ts:113`
- **Issue:** `SET LOCAL statement_timeout = '5s'` is executed on the shared Prisma connection pool, not inside a transaction. `SET LOCAL` only scopes to a transaction — outside one, it becomes `SET` and affects the entire session, potentially impacting other concurrent queries on the same pooled connection.
- **Impact:** Other queries on the same connection may unexpectedly time out after 5 seconds, or the timeout has no effect at all (defeating its purpose).
- **Suggested fix:** Wrap in a transaction:

```ts
allCandidates = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SET LOCAL statement_timeout = '5s'`;
  return tx.$queryRaw`SELECT DISTINCT p.id ...`;
});
```

**[CR-002]** `auth_token` cookie not validated on admin DELETE user endpoint — allows last-admin deletion race

- **File:** `src/app/api/admin/users/[id]/route.ts:52-54`
- **Issue:** The advisory lock uses `hashtext(${id})` as the second key, scoping the lock per-target-user. Two concurrent requests to delete _different_ admin users can proceed in parallel, each seeing `count >= 2` admins, then both deleting, leaving zero admins.
- **Impact:** Complete lockout — no admin users remain.
- **Suggested fix:** Use a single global advisory lock key (not per-user) for the admin-count-check + delete section, or use `SELECT ... FOR UPDATE` on the entire admin user set.

**[CR-003]** `useNotificationPolling` confirms 401 via `/api/auth/me` but doesn't abort on unmount

- **File:** `src/hooks/useNotificationPolling.ts:87-95`
- **Issue:** The confirmation fetch (`/api/auth/me`) reuses the same `controller` signal, but if the polling cleanup runs between the notification fetch and the confirmation fetch, the controller is aborted, and the confirmation response is swallowed. The `onAuthInvalid()` (logout) is then never called OR called spuriously.
- **Impact:** User may be silently logged out due to a transient network error, or remain stuck in a logged-in state with an expired token.
- **Suggested fix:** Create a new AbortController for the confirmation request, and check `isMountedRef.current` before calling `onAuthInvalid()`.

#### HIGH

**[CR-004]** `recipes/match` endpoint has no pagination on the ingredient-matching loop — O(n\*m) unbounded

- **File:** `src/app/api/recipes/match/route.ts:130-165`
- **Issue:** After DB pre-filtering, all candidates (up to 200) are iterated with all pantry items (up to 500) for each ingredient in each recipe. With 200 recipes _ 20 ingredients _ 500 pantry items, this is up to 2M comparisons per request, blocking the Node.js event loop.
- **Impact:** Endpoint becomes slow under load, potentially causing request timeouts for other users.
- **Suggested fix:** Cap the number of pantry items used for matching (e.g., top 100), or move matching to a background worker.

**[CR-005]** Admin user email exposed in admin panel API responses

- **File:** `src/infrastructure/services/AdminService.ts:53` (getAllUsers select), `src/app/admin/users/page.tsx:189`
- **Issue:** User emails are returned in the admin users API and displayed in the admin table. While this is an admin-only endpoint, the client-side code renders emails in the DOM where browser extensions or XSS could harvest them.
- **Impact:** PII exposure if admin session is compromised or admin panel has XSS.
- **Suggested fix:** Mask emails in the API response (e.g., `t***@example.com`) or only show on explicit expand.

**[CR-006]** `cooked-recipes` DELETE uses query parameter instead of path parameter, enabling CSRF via GET

- **File:** `src/app/api/cooked-recipes/route.ts:230`
- **Issue:** The DELETE handler reads `id` from `searchParams.get('id')`. While the middleware blocks cross-origin DELETE, the comment says "Uses query param ?id= instead of a nested route" — this is architecturally fragile and breaks REST conventions.
- **Impact:** If a future middleware change relaxes CSRF for GET params, this becomes exploitable. Also confusing for API consumers.
- **Suggested fix:** Move to `/api/cooked-recipes/[id]/route.ts` with a DELETE handler.

**[CR-007]** `RecipeFeed` infinite scroll has no deduplication guard on intersection observer callback

- **File:** `src/components/recipe/RecipeFeed.tsx:176-189`
- **Issue:** The `lastLoadTimeRef` throttle of 500ms may not prevent duplicate loads when the intersection observer fires multiple times during a slow network response (the `loadingRef` check happens _after_ the timestamp check).
- **Impact:** Duplicate recipes rendered in the feed, potential duplicate React keys.
- **Suggested fix:** Check `loadingRef.current` _before_ the timestamp check in the observer callback.

**[CR-008]** `striptags` used for XSS sanitization in pantry routes but not for ingredient names

- **File:** `src/app/api/pantry/route.ts:103` vs `src/app/api/pantry/[id]/route.ts:83`
- **Issue:** Pantry POST sanitizes `category` with `striptags` but the `name` field in the PUT handler is not sanitized. The POST handler does sanitize `name` (line 103), but PUT does not apply `striptags` to `name` (line 83 just does `name.trim()`).
- **Impact:** Stored XSS via pantry item name update (if rendered as raw HTML anywhere).
- **Suggested fix:** Apply `striptags` to `name` in the PUT handler as well:

```ts
...(name !== undefined && { name: striptags(name.trim()) }),
```

#### MEDIUM

**[CR-009]** `console.info` used for audit logging instead of structured logger

- **File:** `src/app/api/admin/comments/[id]/route.ts:22`, `src/app/api/admin/recipes/[id]/route.ts:26`, `src/app/api/admin/users/[id]/route.ts:33`, `src/app/api/cooked-recipes/route.ts:222`
- **Issue:** Audit logs use `console.info` and `console.warn` which are unstructured and may not be captured by log aggregation systems. The `logServerError` utility exists but isn't used for audit events.
- **Impact:** Audit trail unreliable in production; hard to search/alert on admin actions.
- **Suggested fix:** Create a structured `logAuditEvent` utility that sends to Sentry breadcrumbs or a dedicated audit log.

**[CR-010]** `AdminService.getStats()` cache is module-level global, not invalidated on mutations

- **File:** `src/infrastructure/services/AdminService.ts:9-10`
- **Issue:** `statsCache` with 30s TTL is a module-level singleton. In serverless (Vercel), each instance has its own cache. In long-lived servers, admin deletions/promotions won't reflect in stats for up to 30 seconds.
- **Impact:** Admin dashboard shows stale data after mutations.
- **Suggested fix:** Invalidate cache on write operations (`deleteUser`, `deleteRecipe`, etc.), or reduce TTL to 5s.

**[CR-011]** `EditProfileModal` avatar upload doesn't validate file content on server if magic bytes check fails client-side

- **File:** `src/components/profile/EditProfileModal.tsx:91-107`
- **Issue:** Client-side magic byte validation is performed, but if it fails, the user just sees an error. If bypassed (e.g., via curl), the server's `validateImageMagicBytes` catches it — but the comment says "Client-side validation for fast UX feedback" without noting the server is the actual security boundary. This is fine architecturally but the client check uses `file.slice(0, 12)` while the server uses `buffer.length < 12` — if a file is exactly 12 bytes, the client reads all 12 but the server's `< 12` check rejects it.
- **Impact:** Edge case: 12-byte files pass client validation but fail server validation, confusing users.
- **Suggested fix:** Change server check to `buffer.length < 4` (minimum for any format check) or align both to the same threshold.

**[CR-012]** `Footer` contact form has no rate limiting on mailto link generation

- **File:** `src/components/Footer.tsx:52-60`
- **Issue:** The `handleSendEmail` function opens a `mailto:` link with user-provided content. While control characters are stripped, there's no limit on how frequently this can be triggered.
- **Impact:** Low — mailto links are client-side only, but rapid clicking could annoy the user's mail client.
- **Suggested fix:** Add a simple debounce or disable the button after click.

**[CR-013]** `useRecipe` hook's `keepPreviousData` causes stale recipe display during navigation

- **File:** `src/hooks/useRecipe.ts:60`
- **Issue:** `placeholderData: keepPreviousData` shows the _previous_ recipe's data while the new one loads. The recipe detail page renders a loading overlay (`isPlaceholderData`), but the old recipe's title, image, and content are visible underneath.
- **Impact:** User briefly sees wrong recipe content when navigating between recipes, which is confusing.
- **Suggested fix:** Show a skeleton/shimmer instead of the previous recipe's content, or remove `keepPreviousData`.

**[CR-014]** `normalizeIngredientName` has an inconsistent minimum-length guard

- **File:** `src/lib/utils/ingredients.ts:50-54`
- **Issue:** After plural stripping, if the cleaned result is less than 3 characters, the original name is returned. But the original name itself might be less than 3 characters (e.g., "ox"), which then gets returned as-is. The guard protects against over-stripping but doesn't handle naturally short names consistently.
- **Impact:** Ingredient matching may behave unexpectedly for very short ingredient names.
- **Suggested fix:** Document this behavior or remove the guard for names that were already short before stripping.

**[CR-017]** Test files mock `framer-motion` inconsistently across the codebase

- **File:** Multiple `__tests__` files
- **Issue:** Each test file has its own framer-motion mock with slightly different implementations. Some use `passthrough`, some use `mockMotion.create`, some use `React.forwardRef`. This makes tests brittle and hard to maintain.
- **Impact:** Maintainability — changing framer-motion usage requires updating many mock implementations.
- **Suggested fix:** Create a shared `__mocks__/framer-motion.ts` auto-mock at the project root.
