## Code Review — 2026-03-21

### Summary

A cooked-recipes API route with pantry deduction logic. Generally well-structured with good concurrency controls, but contains several bugs around data integrity, a potential DoS vector, and missing validation.

### Findings

#### CRITICAL

**[CR-001]** Pantry restoration on DELETE can exceed original quantity due to concurrent cooks

- **File:** `src/app/api/cooked-recipes/route.ts:247-253`
- **Issue:** When restoring pantry items, `restoredQuantity` caps at 10000 but does not cap at the _original_ quantity before deduction. If user cooks recipe A (deducts 5 flour), then manually adds 10 flour via pantry API, then deletes cooked recipe A, they get 5 flour for free. The `amount` stored in `deductedIngredients` is blindly added back regardless of current state.
- **Impact:** Users can inflate pantry quantities beyond what they actually have — a data integrity violation.
- **Suggested fix:** This is an inherent design limitation of storing deductions as a flat list. Document this as accepted behavior, or store a `restoredAt` flag on the cooked recipe to prevent double-restoration (the advisory lock only prevents concurrent deletes, not the logical duplication of restoring after manual pantry edits).

**[CR-002]** `striptags` does not prevent stored XSS for all contexts

- **File:** `src/app/api/cooked-recipes/route.ts:78-80` and others
- **Issue:** `striptags` only removes HTML tags. It does not escape characters like `"`, `'`, `&`, or backticks. If `deductedIngredients` or `insufficientIngredients` are rendered in an HTML attribute context or inside a JS template literal on the client, XSS is still possible via payloads like `" onmouseover="alert(1)` (no tags needed).
- **Impact:** Stored XSS if the frontend renders these values in attribute contexts without additional escaping.
- **Suggested fix:** Use a proper HTML entity escaping library (e.g., `he.encode()` or `DOMPurify`) in addition to or instead of `striptags`, or ensure the frontend framework (React) handles escaping (it does for JSX text content, but not for `dangerouslySetInnerHTML` or attribute interpolation).

#### HIGH

**[CR-003]** No pagination metadata returned from GET

- **File:** `src/app/api/cooked-recipes/route.ts:125`
- **Issue:** The GET endpoint returns `{ cookedRecipes, total }` but does not return `page`, `limit`, or `totalPages`. Clients cannot determine if there are more pages without performing arithmetic themselves.
- **Impact:** Clients must redundantly track pagination state; inconsistent with typical API contracts.
- **Suggested fix:**
  ```typescript
  return NextResponse.json({
    cookedRecipes,
    total,
    page,
    limit,
    totalPages: Math.ceil(total / limit),
  });
  ```

**[CR-004]** `request.json()` can be called after body is already consumed

- **File:** `src/app/api/cooked-recipes/route.ts:141-145`
- **Issue:** If `requireJsonContentType` internally reads the request body (depends on implementation), the subsequent `request.json()` call will fail with a "body already consumed" error. Without seeing `requireJsonContentType`, this is a latent bug if that function ever touches the body stream.
- **Impact:** 500 error on all POST requests if the content-type checker consumes the body.
- **Suggested fix:** Verify that `requireJsonContentType` only inspects headers and never reads the body. Add a comment to that function warning against body access.

**[CR-005]** Rating aggregation race between POST and DELETE

- **File:** `src/app/api/cooked-recipes/route.ts:214` (POST) and `src/app/api/cooked-recipes/route.ts:282` (DELETE)
- **Issue:** The POST handler locks the Post row with `SELECT ... FOR UPDATE` _after_ the `rating.upsert`. If two concurrent requests (one POST, one DELETE) target different cooked recipes for the same post, the upsert can complete on both before either acquires the row lock. The advisory lock is keyed per-user, so two _different_ users rating the same post concurrently are not serialized.
- **Impact:** `averageRating` and `reviewCount` on the Post can become inconsistent (lost update).
- **Suggested fix:** Move the `SELECT ... FOR UPDATE` to _before_ the `rating.upsert`:
  ```typescript
  if (rating !== undefined) {
    await tx.$executeRaw`SELECT id FROM "Post" WHERE id = ${postId} FOR UPDATE`;
    await tx.rating.upsert({
      /* ... */
    });
    // aggregate + update ...
  }
  ```

**[CR-006]** Unbounded transaction duration — no timeout

- **File:** `src/app/api/cooked-recipes/route.ts:163` and `src/app/api/cooked-recipes/route.ts:227`
- **Issue:** Both the POST and DELETE transactions acquire advisory locks and perform multiple queries but have no `timeout` option set on `$transaction`. A slow query or lock contention can hold the transaction (and the advisory lock) indefinitely, blocking other requests for that user.
- **Impact:** Resource exhaustion and request stacking under load; potential connection pool starvation.
- **Suggested fix:**
  ```typescript
  await prisma.$transaction(
    async (tx) => {
      /* ... */
    },
    { timeout: 10000 }
  );
  ```

#### MEDIUM

**[CR-007]** `ingredients` field cast from `unknown` with no schema validation

- **File:** `src/app/api/cooked-recipes/route.ts:186-193`
- **Issue:** `recipe.ingredients` is cast via `as unknown[]` and then filtered with a loose type guard. The `ingredientsValid` check on line 195 runs _after_ the `.map()` already produced strings via `String(...)`, so the validation is partially tautological — `typeof i?.name === 'string'` is always true after `String(i.name)`. The validation should run on the raw data before transformation.
- **Impact:** Corrupted or malicious ingredient data in the DB could produce unexpected deduction behavior.
- **Suggested fix:** Use Zod to validate `recipe.ingredients` before mapping:
  ```typescript
  const ingredientSchema = z.object({
    name: z.string().min(1).max(200),
    amount: z.union([z.string(), z.number()]),
    unit: z.string().max(50),
  });
  const parsed = z.array(ingredientSchema).safeParse(recipe.ingredients);
  if (!parsed.success) {
    deductionSkipped = true;
  } else {
    /* use parsed.data */
  }
  ```

**[CR-008]** Magic numbers scattered throughout

- **File:** `src/app/api/cooked-recipes/route.ts:248,253,258,240`
- **Issue:** `10000` (max quantity), `500` (max pantry items), `200` (max name length), `50` (max unit length) are hardcoded inline. Some of these also appear in the Zod schema on line 237 (`max(10000)`, `max(200)`, `max(50)`). These should be shared constants to prevent divergence.
- **Impact:** If limits change, developers must find and update every occurrence — easy to miss one.
- **Suggested fix:** Extract to constants in `@/lib/constants`:
  ```typescript
  export const MAX_PANTRY_QUANTITY = 10000;
  export const MAX_PANTRY_ITEMS = 500;
  export const MAX_INGREDIENT_NAME_LENGTH = 200;
  export const MAX_UNIT_LENGTH = 50;
  ```

**[CR-009]** `byNameUnit` map key collision when different items share normalized name + unit

- **File:** `src/app/api/cooked-recipes/route.ts:244`
- **Issue:** The `byNameUnit` map is built from `allPantryItems`, but if a user has two pantry items with the same normalized name and unit (possible if created through different flows), only the last one is stored in the map. Restoration may update the wrong item.
- **Impact:** Incorrect pantry item gets its quantity restored.
- **Suggested fix:** Use a `Map<string, PantryItem[]>` (multimap) and match against the first item, or deduplicate pantry items elsewhere in the system.

**[CR-010]** `console.warn` used instead of structured logger

- **File:** `src/app/api/cooked-recipes/route.ts:199`, `src/app/api/cooked-recipes/route.ts:236`
- **Issue:** `console.warn` is used for operational warnings while `logServerError` is available and used elsewhere. Inconsistent logging means these warnings won't appear in structured log aggregators.
- **Impact:** Operational issues (skipped deductions, invalid deductedIngredients) are invisible in production monitoring.
- **Suggested fix:** Replace with a `logServerWarn` or use `logServerError` with a non-error severity.

**[CR-011]** DELETE does not restore rating when a comment exists but the rating was from the cooked recipe

- **File:** `src/app/api/cooked-recipes/route.ts:275-279`
- **Issue:** The logic says "only delete the associated rating if user has no comment on this post" because "the rating was created via the comment flow." But what if the user created the rating via the _cooked recipe_ flow and _then_ left a comment? The comment's existence would prevent the rating from being cleaned up, even though it was originally created by the cooked recipe.
- **Impact:** Stale ratings persist after cooked recipe deletion when a comment exists, regardless of which flow created the rating.
- **Suggested fix:** Track the rating's origin (e.g., a `source` column on the Rating model: `'cook' | 'comment'`) to make correct deletion decisions.

#### LOW

**[CR-012]** `JSON.parse(JSON.stringify(deductedIngredients))` is a no-op deep clone

- **File:** `src/app/api/cooked-recipes/route.ts:208`
- **Issue:** `deductedIngredients` is already an array of plain objects with primitive values. The `JSON.parse(JSON.stringify(...))` round-trip is unnecessary overhead.
- **Impact:** Minor CPU waste on every POST with deductions; confusing intent.
- **Suggested fix:**
  ```typescript
  deductedIngredients: deductedIngredients.length > 0 ? deductedIngredients : undefined,
  ```

**[CR-013]** `force` parameter allows bypassing insufficient-ingredient check silently

- **File:** `src/app/api/cooked-recipes/route.ts:14`
- **Issue:** The `force` flag is not documented in an API schema or OpenAPI spec. A client that discovers this parameter can always bypass pantry checks. There's no audit trail distinguishing forced cooks from normal ones.
- **Impact:** Reduced auditability; potential misuse if pantry accuracy matters.
- **Suggested fix:** Log when `force` is used: `logAuditEvent('COOKED_RECIPE_FORCE', { userId: user.id, postId, insufficientCount: insufficientIngredients.length })`.

**[CR-014]** No test file for this route

- **File:** N/A
- **Issue:** No corresponding test file exists for this route (not included in the diff, no `__tests__` reference). A route with this much business logic — advisory locks, pantry deduction, rating aggregation, restoration on delete — without tests is a significant risk.
- **Impact:** Regressions will go undetected; the concurrency and edge-case logic is especially prone to subtle bugs.
- **Suggested fix:** Add integration tests covering: normal cook, duplicate cook (409), daily limit (429), insufficient ingredients with and without `force`, DELETE with pantry restoration, concurrent operations, and corrupted ingredient data.
