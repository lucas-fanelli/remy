## Code Review — 2026-03-19

### Summary

Large, well-structured Next.js recipe-sharing app with clean architecture (DI, repositories, services). Most critical paths are properly secured with auth, CSRF, and input validation. However, several data integrity bugs, performance concerns, and a few security gaps exist that need attention.

**[CR-001]** Pantry PUT `-0` normalization is ineffective — value never reaches Prisma

- **File:** `src/app/api/pantry/[id]/route.ts:72-78,96`
- **Issue:** The `-0` normalization assigns to local variable `parsed`, but the Prisma update data re-parses the original `quantity` input with `parseFloat(quantity)`, which re-introduces `-0`.

```typescript
}
// ...
data: {
  ...(normalizedQuantity !== undefined && { quantity: normalizedQuantity }),
```

**[CR-002]** Recipe match fallback path has no statement timeout

- **File:** `src/app/api/recipes/match/route.ts:131-137`
- **Issue:** When `nameConditions.length === 0` (user has only very short pantry names that get filtered out), the fallback query runs without `SET LOCAL statement_timeout`. The primary path wraps queries in a transaction with `statement_timeout = '5s'`, but the fallback does a full table scan with no timeout.
- **Impact:** Attackers can trigger unbounded queries by having only 1-character pantry items, potentially causing DB connection exhaustion under load.
- **Suggested fix:**

```typescript
allCandidates = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SET LOCAL statement_timeout = '5s'`;
  return tx.post.findMany({
    where: { ingredients: { not: Prisma.DbNull } },
    take: limit,
    orderBy: { averageRating: 'desc' },
    select: { id: true, ingredients: true },
  });
});
```

#### HIGH

**[CR-003]** Pantry deduction performs N sequential queries per ingredient

- **File:** `src/app/api/cooked-recipes/route.ts:67-78`
- **Issue:** `deductPantryItems` issues individual `pantryItem.update` and `pantryItem.delete` calls inside a loop within a transaction. A recipe with 20 ingredients means 20+ sequential DB round-trips while holding a transaction lock and advisory lock.
- **Impact:** Slow transactions under load, increased deadlock risk, poor user experience when marking recipes as cooked.
- **Suggested fix:** Batch updates with `updateMany` and `deleteMany`:

```typescript
// Batch all deductions
if (deductions.length > 0) {
  await Promise.all(
    deductions.map((d) =>
      tx.pantryItem.update({ where: { id: d.itemId }, data: { quantity: d.newQuantity } })
    )
  );
}
if (deletions.length > 0) {
  await tx.pantryItem.deleteMany({
    where: { id: { in: deletions.map((d) => d.id) } },
  });
}
```

**[CR-006]** `setInterval` in middleware leaks in serverless environments

- **File:** `src/middleware.ts:31-37`
- **Issue:** The rate limit cleanup interval is set globally with `setInterval(fn, 60_000)`. In serverless (Vercel/Lambda), each cold start creates a new interval that keeps the container warm unnecessarily, and the guard `__rateLimitCleanupInterval` stores a truthy value but the actual interval ID is discarded — it can never be cleared.
- **Impact:** Wasted compute in serverless; the interval cannot be cleaned up since the ID is not stored.
- **Suggested fix:** Either store the interval ID for potential cleanup, or remove the interval entirely and rely solely on the probabilistic + on-access cleanup that already exists:

```typescript
// Remove the setInterval block entirely — probabilistic cleanup (5% chance per

```

#### MEDIUM

**[CR-007]** Recipe match ingredient validation uses `< 200` instead of `<= 200`

- **File:** `src/app/api/recipes/match/route.ts:152,186`
- **Issue:** `i.name.length < 200` but `MAX_ITEM_NAME_LENGTH = 200`. An ingredient with exactly 200 characters (which is valid per the pantry API) would be rejected by the match endpoint.
- **Impact:** Recipes with max-length ingredient names are silently excluded from matching results.
- **Suggested fix:** `i.name.length <= MAX_ITEM_NAME_LENGTH`

**[CR-008]** Admin stats cache is module-level, not per-request, shared across all users

- **File:** `src/infrastructure/services/AdminService.ts:14-15`
- **Issue:** `statsCache` is a module-level singleton with 30s TTL. In a single-process deployment, all admin users see the same cached stats, which is fine. But the cache is never invalidated on non-admin mutations (user signups, recipe creation by regular users). The `statsCache = null` calls only happen on admin mutations.
- **Impact:** `newUsersToday` and `newRecipesToday` can be up to 30 seconds stale, which is acceptable. However, the comment says "30 seconds" but organic traffic (signups/posts) won't trigger cache invalidation at all — only admin actions do. Stats could be 30s stale indefinitely during high organic activity with no admin actions.
- **Suggested fix:** This is acceptable behavior for a dashboard. Document that the cache is invalidated only on admin actions, not organic activity.

**[CR-009]** `logout` retry sleeps 1 second on the main async flow

- **File:** `src/contexts/AuthContext.tsx:92`
- **Issue:** `await new Promise(r => setTimeout(r, 1000))` blocks the logout callback for 1 second before retrying. Since `setUser(null)` already cleared the UI optimistically, this 1-second block doesn't affect UX directly, but it keeps the async function pending, preventing garbage collection of the closure and any captured state.
- **Impact:** Minor: delayed GC of captured variables during logout. If the user navigates quickly after logout, the stale retry could fire against a new page context.
- **Suggested fix:** Fire the retry in the background instead of awaiting it:

```typescript
// First attempt
try {
  const response = await fetch('/api/auth/logout', { ... });
  if (response.ok) return;
} catch { /* continue to retry */ }
// Background retry — don't await
setTimeout(async () => {
  try {
    const response = await fetch('/api/auth/logout', { ... });
    if (!response.ok) window.dispatchEvent(new CustomEvent('auth:logout-failed'));
  } catch {
    window.dispatchEvent(new CustomEvent('auth:logout-failed'));
  }
}, 1000);
```

**[CR-010]** `RecipeFeed` infinite scroll sentinel has no upper bound on loaded recipes in DOM

- **File:** `src/components/recipe/RecipeFeed.tsx:80`
- **Issue:** `MAX_PAGES = 50` allows up to 600 recipes (50 \* 12) to accumulate in the React component state and DOM. Each `RecipeCard` renders an image, multiple MUI components, and motion wrappers. On mobile devices with limited memory, this can cause the browser tab to crash.

**[CR-011]** `PersistentSearchBar` creates AbortController outside setTimeout

- **File:** `src/components/search/PersistentSearchBar.tsx:115-145`
- **Issue:** The comment says "AbortController is intentionally created OUTSIDE the setTimeout" — but this means on every keystroke, a new AbortController is created and the previous one is aborted via cleanup. However, the abort happens in the cleanup function, which runs on re-render, not when the timeout fires. This means if the user types "a" then "ab" quickly, the first controller is aborted before its timeout even fires — which is correct. But the controller for the last keystroke is only aborted on unmount, not on successful fetch completion. The signal stays alive unnecessarily.
- **Impact:** Minor: dangling AbortController references until component unmount. No functional bug.
- **Suggested fix:** No action needed — the comment accurately describes the design and it works correctly.

**[CR-012]** `SearchResults` `truncateAtWord` can return empty string for edge case

- **File:** `src/components/SearchResults.tsx:39`
- **Issue:** `if (maxLen <= 0) return ''` — if `truncateAtWord` is called with `maxLen=0`, it returns empty string. If called with a string shorter than `maxLen`, it returns the full string. But `lastIndexOf(' ', maxLen)` returns -1 if there's no space before position 50, causing `substring(0, -1)` which returns empty string, then `'' + '...'` = `'...'`.
- **Impact:** A recipe description with no spaces in the first 50 characters (e.g., a single long word) would display as just `"..."` instead of truncating at the character limit.
- **Suggested fix:**

```typescript
const idx = text.lastIndexOf(' ', maxLen);
return text.substring(0, idx > 0 ? idx : maxLen) + '...';
// Already correct — the `idx > 0` fallback handles this. No change needed.
```

Actually, re-reading: `idx > 0` catches this. The current code is correct. Withdrawing this finding.
