**[CR-001]** Race condition in DELETE account: cascading deletes may fail silently

- **File:** `src/app/api/users/profile/route.ts:91-107`
- **Issue:** The transaction collects image URLs from posts and comments, then deletes the user. If the schema uses `CASCADE` on the foreign key, Prisma's `tx.user.delete` will cascade-delete posts and comments _before_ the URL collection queries run (depending on execution order). But if the schema does NOT use CASCADE, `tx.user.delete` will fail with a foreign key constraint error because posts/comments still reference the user. Neither case is handled — there's no explicit deletion of posts/comments before the user delete, and no error handling for FK violations.
- **Impact:** Account deletion could fail entirely with an unhandled Prisma error, or if CASCADE is configured, the code works by accident but the collect-then-delete ordering is fragile and undocumented.
- **Suggested fix:** Explicitly delete dependent records (posts, comments, likes, ratings, cooked recipes, follows, notifications, pantry) before deleting the user, or verify and document that CASCADE is configured and that `findMany` executes before `delete` within the transaction:

```typescript
// Explicit deletion order (safer):
await tx.comment.deleteMany({ where: { userId: user.id } });
await tx.like.deleteMany({ where: { userId: user.id } });
// ... other dependent tables
await tx.post.deleteMany({ where: { userId: user.id } });
await tx.user.delete({ where: { id: user.id } });
```

**[CR-002]** Unsanitized `instructions` JSON cast enables stored XSS via recipe ingredients

- **File:** `src/app/api/cooked-recipes/route.ts:163-169`
- **Issue:** `recipe.ingredients` is cast to `RecipeIngredient[]` with `as unknown as RecipeIngredient[]`. While the code validates field types and lengths, it never sanitizes the `name`, `amount`, or `unit` values with `striptags` before they are stored in `deductedIngredients` on the `cookedRecipe` record. The `deductedIngredients` JSON is later returned in API responses and could be rendered by the frontend. A malicious recipe author could set `ingredient.name` to `<img src=x onerror=alert(1)>` — it passes the `typeof === 'string'` and length checks, gets stored in `deductedIngredients`, and is served back to the user who cooked the recipe.
- **Impact:** Stored XSS — any user who views their cooked recipe history or the deducted ingredients response could execute attacker-controlled JavaScript.
- **Suggested fix:** Sanitize recipe ingredient fields before using them in deduction:

```typescript
const recipeIngredients = (recipe.ingredients as unknown as RecipeIngredient[]).map((i) => ({
  name: striptags(i.name),
  amount: striptags(String(i.amount)),
  unit: striptags(i.unit),
}));
```

**[CR-003]** `POST /api/recipes` does not sanitize instruction `image` URLs against path traversal or non-Cloudinary origins after initial validation

- **File:** `src/app/api/recipes/route.ts:189-193`
- **Issue:** `validateCloudinaryUrl` is called, but `createRecipeSchema` only checks `url.startsWith('https://res.cloudinary.com/')`. A URL like `https://res.cloudinary.com/../../evil.com/payload.js` passes both the Zod `refine` and potentially `validateCloudinaryUrl` (depending on its implementation). The instruction images are stored in the DB and rendered in the frontend, likely in `<img src=...>` tags. While browsers resolve `../../` in URLs (so the actual fetch would go to `evil.com`), the real risk depends on `validateCloudinaryUrl`'s implementation — if it only checks the prefix, this is exploitable.
- **Impact:** If `validateCloudinaryUrl` only does prefix checking, attackers can store arbitrary URLs that render in other users' browsers, enabling phishing or tracking pixel injection.
- **Suggested fix:** Parse the URL and validate the hostname explicitly:

```typescript
function isValidCloudinaryUrl(url: string): boolean {
  try {
    const parsed = new URL(url);
    return parsed.hostname === 'res.cloudinary.com' && parsed.protocol === 'https:';
  } catch {
    return false;
  }
}
```

**[CR-004]** `recipe.ingredients` JSON from DB is cast without runtime validation in match endpoint

- **File:** `src/app/api/recipes/match/route.ts:131-139`
- **Issue:** While there is a validation check (`recipeIngredients.every(i => ...)`), the `amount` field is typed as `number` in the `Ingredient` interface but the validation allows `typeof i?.amount === 'string' || typeof i?.amount === 'number'`. This type mismatch means downstream code in `ingredientMatches` receives a `string` where it may expect `number`, causing silent incorrect behavior. More critically, the `name` field from the raw JSON is passed directly to `ingredientMatches` and later to `striptags(i.name)` for output — but the raw SQL query in Phase 1 uses these names in LIKE patterns via `Prisma.join`. If a recipe's ingredient name contains backslash sequences that survive `escapeLike` incorrectly, the LIKE pattern could behave unexpectedly.
- **Impact:** Type confusion in matching logic produces incorrect match results. Malformed ingredient data from the DB could cause unexpected query behavior.
- **Suggested fix:** Define a strict Zod schema for runtime validation of DB-sourced ingredient JSON, and normalize the `amount` to a consistent type:

```typescript
const dbIngredientSchema = z.object({
  name: z.string().min(1).max(200),
  amount: z
    .union([z.string(), z.number()])
    .transform((v) => (typeof v === 'number' ? v : parseFloat(v))),
  unit: z.string().max(50),
});
const parseResult = z.array(dbIngredientSchema).safeParse(candidate.ingredients);
if (!parseResult.success) continue;
const recipeIngredients = parseResult.data;
```

**[CR-005]** `SET LOCAL statement_timeout` inside transaction is user-controllable DoS vector

- **File:** `src/app/api/recipes/match/route.ts:82`
- **Issue:** `SET LOCAL statement_timeout = '5s'` is hardcoded, but it only applies to individual statements within the transaction, not the transaction as a whole. The `{ timeout: 8000 }` on the transaction is a Prisma-level timeout (client-side), not a DB-level timeout. If the advisory lock `pg_advisory_xact_lock` blocks because another request from the same user is running, the 5s statement timeout will kill the `SELECT pg_advisory_xact_lock` statement, but Prisma will retry or throw — and the connection remains held. A malicious user sending many concurrent match requests could exhaust the connection pool since each blocked request holds a Prisma connection waiting for the advisory lock.
- **Impact:** Connection pool exhaustion causing denial of service for all users.
- **Suggested fix:** Use `pg_try_advisory_xact_lock` instead, which returns immediately with `false` if the lock is already held, allowing you to return a 429 response without holding a connection:

```typescript
const [{ locked }] = await tx.$queryRaw<[{ locked: boolean }]>`
  SELECT pg_try_advisory_xact_lock(${PG_ADVISORY_LOCK_MATCH}, hashtext(${user.id})) AS locked
`;
if (!locked) {
  throw new Error('MATCH_IN_PROGRESS');
}
```
