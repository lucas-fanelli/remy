## Code Review — 2026-03-21

### Summary

Three API route files with complex transactional logic. Several issues around error handling, data integrity, and potential denial-of-service vectors.

### Findings

#### CRITICAL

**[CR-001]** Fire-and-forget image cleanup in DELETE account runs outside transaction with no persistence

- **File:** `src/app/api/users/profile/route.ts:97-114`
- **Issue:** The image cleanup IIFE `(async () => { ... })()` runs after the transaction commits and the response is returned. If the server restarts, crashes, or the process is killed mid-cleanup, images are permanently orphaned with no record of what needs cleaning. The comment acknowledges a cron safety net exists, but the cron script has no way to know which images belonged to the now-deleted user.
- **Impact:** Permanent Cloudinary storage leak. Orphaned images accumulate over time with no way to trace them back to deleted users.
- **Suggested fix:** Persist the list of image URLs to a cleanup queue table inside the transaction (before user deletion). A background worker or cron job processes the queue. This makes cleanup durable and auditable:

```ts
await tx.imageCleanupQueue.createMany({
  data: imageUrls.map((url) => ({ url, reason: 'account_deletion', userId: user.id })),
});
```

**[CR-002]** `deductedIngredients` stored as JSON is trusted on restore without ownership verification of pantryItemId

- **File:** `src/app/api/cooked-recipes/route.ts:267-296`
- **Issue:** When restoring pantry items on DELETE, the code looks up `pantryItemId` from `deductedIngredients` JSON stored in the database. While Zod validates the shape, the `pantryItemId` is a UUID that was valid at creation time but could now belong to a different pantry item if the original was deleted and a new item was created with the same ID (UUIDs don't collide in practice, but the real issue is the `else if (pantry)` branch). When `pantryItemId` lookup fails, a **new** pantry item is created unconditionally — an attacker who deletes and re-creates cooked recipes repeatedly can inflate their pantry quantities indefinitely.
- **Impact:** Pantry quantity inflation exploit. A user can: cook recipe (deducts pantry) → manually delete pantry item via /api/pantry → delete cooked recipe (restores to new item) → repeat. Each cycle creates a new pantry item with the deducted amount, duplicating inventory.
- **Suggested fix:** Track whether the pantry item still exists with the same name/unit before creating a new one. Use a name+unit match as fallback instead of unconditional creation:

```ts
if (existingItem) {
  // update existing
} else if (pantry) {
  // Check if an item with same name+unit already exists before creating
  const existing = await tx.pantryItem.findFirst({
    where: { pantryId: pantry.id, name: safeName, unit },
  });
  if (existing) {
    await tx.pantryItem.update({
      where: { id: existing.id },
      data: { quantity: Math.min(existing.quantity + d.amount, 10000) },
    });
  } else {
    await tx.pantryItem.create({ ... });
  }
}
```

**[CR-003]** POST cooked-recipe rating lock is acquired AFTER the upsert planning, creating a TOCTOU window

- **File:** `src/app/api/cooked-recipes/route.ts:218-222`
- **Issue:** The `SELECT ... FOR UPDATE` on the Post row happens **after** the `cookedRecipe.create` and right before the `rating.upsert`. However, between the `cookedRecipe.create` and the lock acquisition, another concurrent transaction could modify the rating aggregation. The lock should be acquired **before** any rating-related reads or writes to fully serialize the critical section. Currently, two concurrent POST requests for different recipes by the same user are fine (advisory lock serializes), but two users rating the same recipe concurrently could race on the aggregation.
- **Impact:** Rating aggregation can become inconsistent — `averageRating` and `reviewCount` on the Post may not reflect the actual ratings.
- **Suggested fix:** Move the `FOR UPDATE` lock before the `rating.upsert`:

```ts
if (rating !== undefined) {
  await tx.$executeRaw`SELECT id FROM "Post" WHERE id = ${postId} FOR UPDATE`;
  await tx.rating.upsert({ ... });
  const ratingAggregation = await tx.rating.aggregate({ ... });
  await tx.post.update({ ... });
}
```

This is already the order in the code. On re-read, the lock IS before the upsert. Withdrawing this finding — the order is correct.

**[CR-003]** Recipe creation returns full `post` record including raw JSON fields to the client

- **File:** `src/app/api/recipes/route.ts:222`
- **Issue:** `tx.post.create({ data: recipeData })` returns the full Prisma model with no `select` clause. This exposes all database columns to the API consumer, including any future sensitive fields added to the Post model. Every other query in the codebase uses explicit `select`.
- **Impact:** Information disclosure if new columns are added to the Post model. Inconsistent API contract — the shape of the response depends on the full DB schema rather than an explicit selection.
- **Suggested fix:**

```ts
return tx.post.create({
  data: recipeData,
  select: {
    id: true,
    title: true,
    description: true,
    imageUrl: true,
    cookingTime: true,
    prepTime: true,
    servings: true,
    difficulty: true,
    ingredients: true,
    instructions: true,
    caption: true,
    createdAt: true,
    updatedAt: true,
    userId: true,
  },
});
```

**[CR-004]** `recipe.ingredients` cast to `RecipeIngredient[]` without runtime validation in match route

- **File:** `src/app/api/recipes/match/route.ts:136-142`
- **Issue:** The code casts `candidate.ingredients as unknown as Ingredient[]` and then validates with a structural check (`every(...)`). However, the `Ingredient` interface declares `amount: number` while the validation check allows `typeof i?.amount === 'string' || typeof i?.amount === 'number'`. This type mismatch means `missingIngredients` pushed to the result array may contain string amounts that are typed as `number`, corrupting downstream consumers.
- **Impact:** Type unsoundness — consumers of the API response receive `amount` as string when the TypeScript type says number. The `ingredientMatches` function may also behave unexpectedly with string amounts.
- **Suggested fix:** Either coerce amount to number at the validation boundary or fix the `Ingredient` interface:

```ts
interface Ingredient {
  name: string;
  amount: number | string;
  unit: string;
}
```

**[CR-005]** `recipes/match` Phase 3 query has no `isPrivate` check on the post's instructions/ingredients

- **File:** `src/app/api/recipes/match/route.ts:171-185`
- **Issue:** Phase 1 filters candidates with `u."isPrivate" = false`, and Phase 3 re-checks `user: { isPrivate: false }`. However, between Phase 1 (transaction) and Phase 3 (separate query), a user could set their profile to private. The Phase 3 query correctly re-checks — but the `matchLookup` still contains entries for recipes that Phase 3 filtered out, so `matchLookup.get(recipe.id)` simply won't find them. This is actually fine. **However**, the real issue is that the Phase 3 query returns `ingredients` in its select, and these ingredients for the matched recipes are returned to the client via `missingIngredients` from the match results (which were computed in Phase 2 from Phase 1 data). If a recipe becomes private between phases, its missing ingredient names still leak in the response from Phase 2's cached results — but since Phase 3 filters it out, this doesn't happen. Withdrawing.

**[CR-005]** No rate limit or authentication-level check on recipe GET endpoint allows enumeration

- **File:** `src/app/api/recipes/route.ts:55-140`
- **Issue:** The GET endpoint is unauthenticated and has no rate limiting visible in this code. Combined with the `userId` filter parameter, an attacker can enumerate all public recipes for any user by iterating through user IDs. While recipes are public, the `offset`-based pagination with no cursor allows scraping the entire recipe database efficiently.
- **Impact:** Full recipe database scraping. Competitor or bad actor can clone all recipe content.
- **Suggested fix:** Add rate limiting via middleware for unauthenticated recipe listing, and consider cursor-based pagination to make bulk enumeration harder:

```ts
// In middleware.ts, add rate limit for /api/recipes GET
// Or add a maximum offset cap:
const offset = Math.min(1000, Math.max(0, parseInt(searchParams.get('offset') || '0') || 0));
```

**[CR-006]** `striptags` on `ingredient.name` in match response does not prevent stored content from reaching client unsanitized in other fields

- **File:** `src/app/api/recipes/match/route.ts:199`
- **Issue:** `missingIngredients` applies `striptags(i.name)` but the `title`, `description`, and other recipe fields returned in the response are taken directly from the database without sanitization. If stored XSS exists in recipe titles/descriptions (bypassing creation-time sanitization), the match endpoint serves it raw.
- **Impact:** Stored XSS via recipe title/description fields if the creation-time sanitization in `/api/recipes` POST is ever bypassed (e.g., direct DB edit, migration, admin override).
- **Suggested fix:** Apply `striptags` to `title` and `description` at the response boundary, or trust creation-time sanitization consistently (and don't selectively sanitize only `missingIngredients`).
