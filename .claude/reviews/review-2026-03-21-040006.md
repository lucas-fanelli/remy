## Code Review — 2026-03-21

### Summary

Three API route files with transaction-heavy logic, pantry deduction, and recipe matching. Several critical issues found around data integrity, denial of service vectors, and unsafe type handling.

### Findings

#### CRITICAL

**[CR-001]** Unbounded `Promise.allSettled` on account deletion can exhaust Cloudinary API limits or memory

- **File:** `src/app/api/users/profile/route.ts:101-110`
- **Issue:** The `imageUrls` array is unbounded — a user with thousands of posts, each with multi-step instructions containing images, could produce thousands of URLs. `Promise.allSettled` fires all cleanup requests concurrently with no concurrency limit, potentially exhausting Cloudinary rate limits, file descriptors, or memory.
- **Impact:** Denial of service against the Cloudinary API; potential OOM on the server if a prolific user deletes their account.
- **Suggested fix:** Batch the cleanup with a concurrency limiter (e.g., `p-limit` or manual chunking):
  ```typescript
  import pLimit from 'p-limit';
  const limit = pLimit(10);
  Promise.allSettled(imageUrls.map((url) => limit(() => cleanupCloudinaryImage(url))));
  ```

**[CR-002]** `updateProfileSchema.parse(body)` passes unsanitized data directly to `prisma.user.update` — mass assignment risk

- **File:** `src/app/api/users/profile/route.ts:31-42`
- **Issue:** `profileData` is set to `validatedData` and passed directly to `data: profileData` in `tx.user.update`. If `updateProfileSchema` ever includes or is modified to include fields like `role`, `isVerified`, `email`, or `id`, users can escalate privileges. The route has no explicit allowlist of updatable fields — it relies entirely on the Zod schema being correct, which is a single point of failure for authorization.
- **Impact:** Privilege escalation if schema drifts. A single field added to the Zod schema without security review grants users the ability to modify that field.
- **Suggested fix:** Explicitly pick allowed fields after validation:
  ```typescript
  const { fullName, avatar, bio, website, isPrivate } = validatedData;
  const profileData = { fullName, avatar, bio, website, isPrivate };
  ```

**[CR-003]** Race condition in DELETE pantry restoration — `findFirst` by name can match wrong item

- **File:** `src/app/api/cooked-recipes/route.ts:246-249`
- **Issue:** When `pantryItemId` lookup fails (item was deleted and recreated), the fallback `findFirst` matches by `name` and `unit`. If the user has multiple pantry items with the same normalized name and unit (e.g., added separately), the quantity is restored to an arbitrary matching item. Combined with the fact that `deductedIngredients` is stored as JSON and could reference items from a different pantry state, this can produce incorrect quantities.
- **Impact:** Data integrity — pantry quantities can be silently inflated or applied to the wrong item.
- **Suggested fix:** When falling back to name-based lookup, use `findMany` and pick the item with the lowest quantity (most likely the depleted one), or store enough context in `deductedIngredients` to unambiguously identify the item:
  ```typescript
  // Store the original item name + unit + pantryId at deduction time
  // On restore, if pantryItemId fails, create a new item rather than guessing
  if (!existingItem) {
    const pantry = await tx.userPantry.findUnique({ where: { userId: user.id } });
    if (pantry) {
      await tx.pantryItem.create({
        data: { pantryId: pantry.id, name: safeName, quantity: d.amount, unit },
      });
    }
  }
  ```

**[CR-004]** `POST /api/recipes` — `recipeData` spreads validated user input into `tx.post.create` without filtering, allowing `userId` override attempt

- **File:** `src/app/api/recipes/route.ts:167-169`
- **Issue:** `recipeData` is `{ ...validated, userId: user.id }`. The `createRecipeSchema` uses `.strict()`, which should reject extra fields. However, the spread pattern is fragile: if `.strict()` is ever removed or a `userId` field is added to the schema, the user-supplied `userId` would be overwritten — but only because it comes first in the spread. The intent is unclear and the ordering is load-bearing.
- **Impact:** If the schema is modified to include `userId` (e.g., for admin recipe creation), the spread order silently determines which value wins. This is a latent privilege escalation vector.
- **Suggested fix:** Destructure explicitly and construct `data` with only known fields:
  ```typescript
  const {
    title,
    description,
    imageUrl,
    cookingTime,
    prepTime,
    servings,
    difficulty,
    ingredients,
    instructions,
    caption,
  } = validated;
  const recipeData = {
    title,
    description,
    imageUrl,
    cookingTime,
    prepTime,
    servings,
    difficulty,
    ingredients,
    instructions,
    caption,
    userId: user.id,
  };
  ```

**[CR-005]** Recipe match endpoint raw SQL query is vulnerable to ReDoS via crafted pantry item names

- **File:** `src/app/api/recipes/match/route.ts:93-95`
- **Issue:** `normalizeIngredientName` is called on pantry item names, and the result is used in SQL `LIKE` patterns. While `escapeLike` handles SQL wildcards, the `normalizeIngredientName` function's behavior is unknown from this diff. If it preserves Unicode or special characters, and if `ingredientMatches` (used in Phase 2) uses regex internally, crafted pantry item names could trigger catastrophic backtracking.
- **Impact:** ReDoS causing CPU exhaustion on the server, blocking the event loop for other requests.
- **Suggested fix:** Verify `normalizeIngredientName` strips all non-alphanumeric characters. Add a regex complexity guard or use simple string comparison in `ingredientMatches`:
  ```typescript
  const pantryPatterns = pantryNames
    .filter((n) => n.length >= 2 && n.length <= MAX_ITEM_NAME_LENGTH && /^[a-z0-9\s-]+$/.test(n))
    .slice(0, 20);
  ```

**[CR-006]** `instructions` JSON field cast without runtime validation in account deletion

- **File:** `src/app/api/users/profile/route.ts:96-100`
- **Issue:** `post.instructions` is cast to `{ image?: string }[]` without any runtime type checking. If a post has malformed instruction data (e.g., instructions is an object, not an array, or entries lack the expected shape), the `for...of` loop will silently skip or throw, potentially aborting the transaction and preventing account deletion.
- **Impact:** Users with corrupted instruction data cannot delete their accounts. The transaction rolls back, and the error is caught as a generic 500.
- **Suggested fix:**
  ```typescript
  if (Array.isArray(post.instructions)) {
    for (const instr of post.instructions) {
      if (
        instr &&
        typeof instr === 'object' &&
        'image' in instr &&
        typeof (instr as Record<string, unknown>).image === 'string'
      ) {
        urls.push((instr as { image: string }).image);
      }
    }
  }
  ```
