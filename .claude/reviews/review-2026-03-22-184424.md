## Code Review — 2026-03-22

### Summary

Auth routes have a consistent structure but contain a security leak in the login response, timing oracle potential, and the upload route exposes internal error messages. The recalc-ratings endpoint has a race condition window.

### Findings

#### CRITICAL

**[CR-001]** Login response leaks token in JSON body alongside httpOnly cookie

- **File:** `src/app/api/auth/login/route.ts:27-30`
- **Issue:** `result.token` is set as an httpOnly cookie (good) but `result` — which contains `token` — is also serialized into the JSON response body (`data: result`). This completely defeats the purpose of httpOnly cookies. Any XSS can read the token from the response body or from JS-accessible storage if the client persists it.
- **Impact:** Token exfiltration via XSS. The entire httpOnly cookie migration is security theater if the token is also in the response body.
- **Suggested fix:**

```ts
const { token, ...safeResult } = result;
const response = NextResponse.json(
  { success: true, data: safeResult, message: 'Login successful' },
  { status: 200 }
);
setAuthCookie(response, token);
```

**[CR-002]** Register response has the same token leak

- **File:** `src/app/api/auth/register/route.ts:27-30`
- **Issue:** Identical problem as CR-001. `result` containing the token is sent in the JSON body.
- **Impact:** Same as CR-001.
- **Suggested fix:** Same pattern — destructure `token` out before serializing.

**[CR-003]** Upload error handler leaks internal error messages to client

- **File:** `src/app/api/upload/route.ts:91-94`
- **Issue:** `error.message` is returned verbatim to the client. Cloudinary SDK errors, database errors, or any unexpected exception message will be exposed. This can leak internal infrastructure details (hostnames, API keys in error strings, stack details).
- **Impact:** Information disclosure. Attackers learn about internal services, SDK versions, and infrastructure.
- **Suggested fix:**

```ts
logServerError('Error uploading file:', error);
return NextResponse.json({ error: 'Failed to upload file' }, { status: 500 });
```

#### HIGH

**[CR-004]** Login credential error matching uses `.includes()` — brittle and bypassable

- **File:** `src/app/api/auth/login/route.ts:37`
- **Issue:** `error.message.includes('Invalid credentials')` is substring matching. If the auth service ever changes the message text, wraps it, or localizes it, this silently falls through to the generic 500 handler — returning "Internal Server Error" instead of 401. This is not a hypothetical: any refactor of the auth service error messages will break this.
- **Impact:** Changed error messages cause login failures to return 500 instead of 401, breaking the client and leaking that something went wrong server-side.
- **Suggested fix:** Use typed error classes instead of string matching:

```ts
// domain/errors.ts
export class InvalidCredentialsError extends Error { ... }

// In route:
if (error instanceof InvalidCredentialsError) {
  return ApiResponseHelper.unauthorized(error.message);
}
```

**[CR-005]** Same brittle string matching in register route

- **File:** `src/app/api/auth/register/route.ts:37`
- **Issue:** `error.message.includes('already exists')` — same fragility as CR-004.
- **Impact:** A reworded error message turns a 409 Conflict into a 500 Internal Server Error.
- **Suggested fix:** Use a typed `ConflictError` or `UserExistsError` class.

**[CR-006]** Same brittle string matching in change-password route (two instances)

- **File:** `src/app/api/auth/change-password/route.ts:37, 45`
- **Issue:** Both `'Authentication required'` and `'Current password is incorrect'` are matched by exact string equality (`===`), which is slightly better than `.includes()` but still fragile. These should be typed errors.
- **Impact:** Same class of bug as CR-004/CR-005.
- **Suggested fix:** Use typed error classes.

**[CR-007]** Upload route does not rate-limit or throttle

- **File:** `src/app/api/upload/route.ts`
- **Issue:** Any authenticated user can call this endpoint in a tight loop, uploading 5MB files repeatedly. There is no per-user rate limit, no concurrent upload cap, and no daily quota. Cloudinary storage and bandwidth costs are unbounded.
- **Impact:** Resource exhaustion, cost explosion, potential denial of service against Cloudinary quota.
- **Suggested fix:** Add per-user rate limiting (e.g., X uploads per minute/hour) at the middleware or route level.

**[CR-008]** `recalc-ratings` advisory lock does not handle lock contention gracefully

- **File:** `src/app/api/admin/recalc-ratings/route.ts:22`
- **Issue:** `pg_advisory_xact_lock` is a **blocking** call. If a second admin triggers recalc while one is running, the second request blocks until the first completes (up to 35s timeout), then runs the full recalc again. There is no "already in progress" response. The 30s `statement_timeout` applies per-statement, not to the lock wait, so the second caller could wait 30s for the lock + 30s for its own execution.
- **Impact:** Under concurrent admin requests: cascading timeouts, connection pool exhaustion, duplicate work.
- **Suggested fix:** Use `pg_try_advisory_xact_lock` which returns `false` immediately if the lock is held:

```ts
const [{ locked }] = await tx.$queryRaw<[{ locked: boolean }]>`
  SELECT pg_try_advisory_xact_lock(${PG_ADVISORY_LOCK_RECALC_RATINGS}, 0) as locked
`;
if (!locked) {
  throw new Error('Recalculation already in progress');
}
```

#### MEDIUM

**[CR-009]** `requireAuth` returns a user object on throw — control flow via exceptions

- **File:** `src/app/api/auth/change-password/route.ts:16, 37`
- **Issue:** `requireAuth` apparently throws on failure (caught at line 37), but the caller treats the return value as a user object. This means authentication failures are communicated via exceptions with magic string messages. This is the same problem as CR-006 but at the architectural level — the auth check should return a discriminated result, not throw.
- **Impact:** Any change to `requireAuth`'s error message breaks the catch clause. Mixing control flow with exceptions makes the code harder to reason about.
- **Suggested fix:** Have `requireAuth` return `{ success: true, user } | { success: false, response: NextResponse }` (similar to `requireAdmin`'s pattern which already does this correctly).

**[CR-010]** Upload route uses `as File` type assertion without runtime check ordering

- **File:** `src/app/api/upload/route.ts:49-54`
- **Issue:** Line 49 does `as File` cast, then line 54 checks `instanceof File`. The `as` cast at line 49 doesn't throw if `formData.get('file')` returns a string (which it does for non-file fields). The `instanceof` check at 54 catches this, but the `as File` cast is misleading — it should be `as File | null` or the check should come first.
- **Impact:** Low runtime risk (the check does exist), but the code reads as if the cast guarantees the type, which it doesn't. Misleading for maintainers.
- **Suggested fix:**

```ts
const file = formData.get('file');
if (!file || !(file instanceof File)) {
  return NextResponse.json({ error: 'No file provided' }, { status: 400 });
}
// file is now narrowed to File
```

**[CR-011]** Inconsistent error response format between upload route and auth routes

- **File:** `src/app/api/upload/route.ts` vs `src/app/api/auth/login/route.ts`
- **Issue:** Auth routes use `ApiResponseHelper` for consistent response shapes. Upload route manually constructs `NextResponse.json({ error: ... })`. This means clients must handle two different error response formats depending on which endpoint they call.
- **Impact:** Frontend must implement two error-parsing paths. Bugs will arise when a developer assumes one format and hits the other.
- **Suggested fix:** Use `ApiResponseHelper` consistently in the upload route.

**[CR-012]** Recalc-ratings returns `post.count()` which is not the count of updated rows

- **File:** `src/app/api/admin/recalc-ratings/route.ts:41`
- **Issue:** `tx.post.count()` returns the total number of posts, not the number of rows actually updated by the raw SQL. If the UPDATE affected 0 rows (e.g., table name mismatch, schema change), the response would still report the full count, giving a false sense of success.
- **Impact:** Silent failures — admin sees "Recalculated ratings for 500 recipes" when 0 were actually updated.
- **Suggested fix:** Capture the affected row count from the raw query:

```ts
const updatedCount = await tx.$executeRaw`UPDATE "Post" p SET ...`;
return updatedCount; // $executeRaw returns affected row count
```

**[CR-013]** `file.type` is client-controlled and checked before magic bytes

- **File:** `src/app/api/upload/route.ts:58-63`
- **Issue:** The MIME type check at line 59 uses `file.type`, which is set by the client and trivially spoofable. While magic byte validation at line 73 is the real security gate, rejecting early on `file.type` can give a false sense of security and produces confusing error messages when a valid image has a non-standard MIME type from the browser.
- **Impact:** Low security impact (magic bytes are checked), but the early MIME check could reject valid uploads from non-standard user agents that report different MIME types.
- **Suggested fix:** Either remove the MIME type check entirely (rely only on magic bytes) or move it after magic byte validation as a secondary signal.

#### LOW

**[CR-014]** Redundant `NextResponse` import in login and register routes

- **File:** `src/app/api/auth/login/route.ts:1`, `src/app/api/auth/register/route.ts:1`
- **Issue:** `NextResponse` is imported and used directly for the success response, while `ApiResponseHelper` is used for errors. The success response should also use `ApiResponseHelper.success()` for consistency, which would make the `NextResponse` import unnecessary.
- **Impact:** Inconsistency.
- **Suggested fix:** Use `ApiResponseHelper` for success responses too, or document why the success path needs direct `NextResponse` access (likely for `setAuthCookie` which needs the response object).

- **File:** `src/app/api/admin/recalc-ratings/route.ts:22`

- **Impact:** Minor readability concern.
- **Suggested fix:** Add a comment or use a constant for the second argument.
