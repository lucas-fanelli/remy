### Findings

#### CRITICAL

**[CR-001]** Fire-and-forget image cleanup after account deletion runs detached from request lifecycle

- **File:** `src/app/api/users/profile/route.ts:109-120`
- **Issue:** The IIFE `(async () => { ... })()` runs completely detached. If the Node.js process recycles (common in serverless/edge), batches after the first may never execute. More critically, unhandled rejections inside `Promise.allSettled` result callbacks won't be caught by the outer `.catch()` because `allSettled` never rejects — but `logServerError` itself could throw (e.g., if the logger's transport is closed), and that _would_ be an unhandled rejection inside the IIFE's `for` loop.
- **Impact:** Orphaned Cloudinary images accumulate with no visibility. If `logServerError` throws, it becomes an unhandled promise rejection that can crash the process in Node 15+.
- **Suggested fix:** Use `Promise.allSettled` at the top level instead of sequential batches in a detached IIFE. Or better, push cleanup jobs to a durable queue (e.g., BullMQ, database-backed job table) that the cron script can pick up:
  ```typescript
  // At minimum, don't nest async control flow in a detached IIFE
  for (const batch of batches) {
    Promise.allSettled(batch.map((url) => cleanupCloudinaryImage(url)))
      .then((results) => {
        const failures = results
          .map((r, i) => (r.status === 'rejected' ? { url: batch[i], reason: r.reason } : null))
          .filter(Boolean);
        if (failures.length > 0) logServerError(`...`, failures);
      })
      .catch((err) => logServerError('...', err));
  }
  ```

**[CR-002]** `instructions` field from DB is cast to `RecipeIngredient[]` without structural validation

- **File:** `src/app/api/cooked-recipes/route.ts:107-110`
- **Issue:** `post.instructions` is a Prisma `Json` field. The code iterates it with `(instr as Record<string, unknown>).image` but the outer cast `post.instructions.slice(0, 50)` assumes it's an array of objects. If a corrupted or maliciously crafted JSON value is stored (e.g., `[1, "string", null]`), the `'image' in instr` check would throw on primitives because `in` operator on a non-object throws a `TypeError`.
- **Impact:** A single corrupted recipe record causes the entire DELETE account transaction to fail, preventing the user from deleting their account.
- **Suggested fix:**
  ```typescript
  for (const instr of (post.instructions as unknown[]).slice(0, 50)) {
    if (instr != null && typeof instr === 'object' && !Array.isArray(instr) && 'image' in (instr as object)) {
  ```
  The existing code already has `typeof instr === 'object'` but `typeof null === 'object'` is true in JS. The `instr &&` guard handles this, but the `!Array.isArray(instr)` check happens _after_ `'image' in instr` could be evaluated on an array. Wait — re-reading: the check is `instr && typeof instr === 'object' && !Array.isArray(instr) && 'image' in instr`. Short-circuit evaluation means `'image' in instr` only runs if all prior checks pass. This is actually safe. **Retracted.**

**[CR-003]** Recipe ingredients cast from JSON without validation in `POST /cooked-recipes`

- **File:** `src/app/api/cooked-recipes/route.ts:196-200`
- **Issue:** `recipe.ingredients` is a Prisma `Json` field cast directly to `RecipeIngredient[]`: `(recipe.ingredients as unknown as RecipeIngredient[])`. While there's a subsequent `ingredientsValid` check, that check runs _after_ the `.map()` on line 196 which calls `String(i.name || '')` — if `recipe.ingredients` contains non-object elements (e.g., `[null, 42, "string"]`), accessing `i.name` on a primitive won't throw but `i` itself being `null` will throw `Cannot read properties of null (reading 'name')`.
- **Impact:** A corrupted recipe JSON blob crashes the transaction, returning a generic 500 to the user instead of gracefully skipping deduction.
- **Suggested fix:**

  ```typescript
  const rawIngredients = recipe.ingredients as unknown;
  if (!Array.isArray(rawIngredients)) {
    deductionSkipped = true;
  } else {
    const recipeIngredients = rawIngredients
      .filter((i): i is Record<string, unknown> => i != null && typeof i === 'object')
      .map((i) => ({
        name: striptags(String(i.name || '')),
        amount: String(i.amount || ''),
        unit: striptags(String(i.unit || '')),
      }));
    // ... proceed with validation
  }
  ```

**[CR-004]** N+1 queries in DELETE pantry restoration loop

- **File:** `src/app/api/cooked-recipes/route.ts:289-316`
- **Issue:** For each deducted ingredient, the code does a `findFirst` by `pantryItemId`, and if not found, another `findFirst` by name+unit, then an `update` or `create`. For a recipe with 30 ingredients, that's up to 90 queries inside a transaction holding an advisory lock. The pantry lookup is hoisted but individual item lookups are not.
- **Impact:** Long transaction hold times under load. The advisory lock serializes all cooked-recipe operations per user, so a slow DELETE blocks POST operations for that user.
- **Suggested fix:** Batch-fetch all pantry items for the user upfront (already have `pantry` but not `pantry.items`), build a Map by ID and by name+unit, then do lookups in-memory:
  ```typescript
  const allItems = await tx.pantryItem.findMany({
    where: { pantry: { userId: user.id } },
  });
  const byId = new Map(allItems.map((i) => [i.id, i]));
  const byNameUnit = new Map(allItems.map((i) => [`${i.name}|${i.unit}`, i]));
  ```

**[CR-005]** `striptags` applied to ingredient names from DB but not to `missingIngredients` in match response

- **File:** `src/app/api/recipes/match/route.ts:183`
- **Issue:** `missingIngredients` is populated from `candidate.ingredients` which is raw JSON from the database. The code sanitizes with `striptags(i.name)` only at the final response mapping (line 224), but the `Ingredient` objects stored in `missingIngredients` retain the raw `name`, `amount`, and `unit` fields. The `amount` and `unit` fields are never sanitized — they're returned to the client as-is.
- **Impact:** Stored XSS if a recipe's ingredient `unit` or `amount` contains HTML/script tags and the client renders them without escaping.
- **Suggested fix:**
  ```typescript
  missingIngredients: match.missingIngredients.map(i => ({
    name: striptags(String(i.name)),
    amount: striptags(String(i.amount)),
    unit: striptags(String(i.unit)),
  })),
  ```
  But note line 224 currently returns only `striptags(i.name)` as a string array — the type mismatch with `MatchedRecipeData.missingIngredients: string[]` means `amount` and `unit` of missing ingredients are silently dropped from the response. If the client needs them, the type and sanitization need updating together.

**[CR-006]** `error.message.includes('validation failed')` matches too broadly

- **File:** `src/app/api/recipes/route.ts:240-242`
- **Issue:** Any error whose message happens to contain the substring "validation failed" (including Prisma errors, third-party library errors, etc.) will be returned as a 400 with the full error message exposed to the client. Prisma constraint violation messages can contain table/column names, leaking schema information.
- **Impact:** Information disclosure — internal error messages containing DB schema details returned to end users.
- **Suggested fix:** Use a custom error class instead of string matching:
  ```typescript
  class RecipeValidationError extends Error {
    constructor(message: string) {
      super(message);
      this.name = 'RecipeValidationError';
    }
  }
  // In catch:
  if (error instanceof RecipeValidationError) {
    return NextResponse.json({ error: error.message }, { status: 400 });
  }
  ```

**[CR-007]** `rating_asc` sort puts NULL ratings first despite `nulls: 'last'`

- **File:** `src/app/api/recipes/route.ts:106`
- **Issue:** The sort `{ averageRating: { sort: 'asc', nulls: 'last' } }` is correct for ascending with nulls last. However, this means recipes with a rating of `0` or very low ratings appear first. Since `averageRating` ranges 1-5 (from the rating schema `min(1).max(5)`), a `0` shouldn't exist — but the `safeRating` utility on line 138 likely handles null→0 conversion. If `averageRating` is stored as `null` for unrated recipes and `0` is never stored, this is fine. **Retracted on closer inspection** — the nulls handling is correct.

**[CR-009]** `parseAmount` return value `NaN` silently skips deduction without logging

- **File:** `src/app/api/cooked-recipes/route.ts:69`
- **Issue:** When `parseAmount(ingredient.amount)` returns `NaN` or `<= 0`, the ingredient is silently skipped with `continue`. No logging or indication is given to the caller that an ingredient was not deducted. The caller receives `deductedIngredients` without these items, but there's no `skippedIngredients` field, so the user has no way to know some pantry items weren't deducted.
- **Impact:** Silent data inconsistency — user thinks all ingredients were deducted but some were silently skipped. The response doesn't distinguish "not in pantry" from "unparseable amount".
- **Suggested fix:** Track skipped ingredients and return them in the response:
  ```typescript
  const skippedIngredients: string[] = [];
  // ...
  if (isNaN(recipeAmount) || recipeAmount <= 0) {
    skippedIngredients.push(ingredient.name);
    continue;
  }
  ```
