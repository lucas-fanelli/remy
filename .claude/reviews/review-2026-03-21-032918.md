### Findings

#### CRITICAL

**[CR-001]** Race condition between avatar fetch and profile update in PUT handler

- **File:** `src/app/api/users/profile/route.ts:47-50`
- **Issue:** The current avatar is fetched outside any transaction, then the profile is updated separately. A concurrent request can change the avatar between the read and the update, causing the wrong image to be cleaned up (deleting the new avatar instead of the old one) or skipping cleanup entirely.
- **Impact:** Data loss — a user's newly uploaded avatar could be deleted from Cloudinary, leaving a broken image reference in the database.
- **Suggested fix:** Wrap the read + update in a transaction, or fetch the old avatar from the return value of the update (using Prisma's `select` on the previous state). Simplest approach:

```typescript
const updatedUser = await prisma.$transaction(async (tx) => {
  const currentUser = await tx.user.findUnique({
    where: { id: user.id },
    select: { avatar: true },
  });
  const updated = await userService.updateProfile(user.id, profileData);
  // Return both for cleanup logic
  return { previous: currentUser, updated };
});
// Now cleanup using updatedUser.previous.avatar vs updatedUser.updated.avatar
```

Note: this requires `userService.updateProfile` to accept a transaction client, or the cleanup logic must accept the small window. If the service cannot be refactored, at minimum document the race.

**[CR-002]** `hasMore` pagination flag uses wrong comparison — returns false on exact boundary

- **File:** `src/app/api/recipes/route.ts:137`
- **Issue:** `hasMore: recipes.length === limit` is incorrect when the total number of remaining recipes is exactly equal to `limit`. It returns `true`, which is correct in that case — but the real problem is the inverse: if a filter or DB change causes fewer results than `limit` even though more exist (e.g., privacy filter applied post-query, or concurrent deletion), `hasMore` will incorrectly return `false`, silently truncating pagination. More critically, this heuristic provides no guarantee — the standard pattern is `offset + limit < total`.
- **Impact:** Clients may stop paginating prematurely, missing recipes.
- **Suggested fix:**

```typescript
hasMore: offset + limit < total,
```

**[CR-003]** Pantry item restoration on DELETE can exceed original quantity due to concurrent cooks

- **File:** `src/app/api/cooked-recipes/route.ts:243-280`
- **Issue:** When deleting a cooked recipe, pantry items are restored by incrementing the current quantity by the deducted amount. If the user cooked the same recipe twice (on different days) and both deducted from the same pantry item, deleting both cooked recipes restores the full amount twice — even if the pantry was restocked in between. The `deductedIngredients` snapshot records what was deducted at cook time, but restoration doesn't verify the pantry item's state is consistent with the deduction history. Additionally, the name-based fallback lookup (`findFirst` by name+unit) can match a _different_ pantry item than the one originally deducted from, if the user deleted and re-added an item with the same name.
- **Impact:** Pantry quantities can silently inflate beyond what the user actually has, leading to incorrect ingredient matching and user confusion.
- **Suggested fix:** Store a version/checksum on pantry items and validate before restoring, or cap restoration so quantity never exceeds a reasonable bound. At minimum, add a check:

```typescript
// Cap restored quantity to prevent inflation
const maxReasonableQuantity = 10000;
const newQuantity = Math.min(existingItem.quantity + (d.amount as number), maxReasonableQuantity);
await tx.pantryItem.update({
  where: { id: existingItem.id },
  data: { quantity: newQuantity },
});
```

**[CR-004]** Raw SQL query in recipe match is vulnerable to unvalidated ingredient array length

- **File:** `src/app/api/recipes/match/route.ts:100-114`
- **Issue:** `pantryPatterns` is sliced to 50, but the raw SQL query uses `Prisma.join(likePatterns)` which inlines up to 50 LIKE patterns into the query. While Prisma parameterizes the values, PostgreSQL's query planner performance degrades significantly with large `ANY(ARRAY[...])` containing LIKE patterns — each pattern requires a sequential scan of the jsonb array elements. With 50 patterns against recipes with up to 100 ingredients, this is 5,000 LIKE comparisons _per candidate row_ before the `LIMIT` kicks in. The `statement_timeout` of 10s may not be sufficient under load; if the GIN index referenced in the comment doesn't exist or doesn't cover this query pattern (GIN indexes don't help with LIKE on jsonb text extraction), this becomes a full table scan.
- **Impact:** Database CPU exhaustion under concurrent usage; potential denial of service for other queries sharing the connection pool.
- **Suggested fix:** Verify the GIN index actually accelerates this query with `EXPLAIN ANALYZE`. If it doesn't, replace the LIKE-based approach with a GIN trigram index (`pg_trgm`) or pre-compute normalized ingredient names in a separate indexed column/table. As an immediate mitigation, reduce the pattern limit:

```typescript
const pantryPatterns = pantryNames
  .filter((n) => n.length >= 2) // also filter single-char names
  .slice(0, 20); // reduce from 50 to 20
```

**[CR-005]** Account deletion does not invalidate active sessions

- **File:** `src/app/api/users/profile/route.ts:75-96`
- **Issue:** The DELETE handler clears the auth cookie on the _current_ response, but if the user has active sessions in other browsers/devices (or if the auth token is stored elsewhere), those sessions remain valid. After the user record is deleted, `requireAuth` calls in other routes will attempt to look up a non-existent user — the behavior depends entirely on how `requireAuth` handles a missing user. If it throws, all other endpoints return 401 (acceptable). If it returns null or a partial object, downstream code will crash with unhandled errors.
- **Impact:** Deleted user's sessions may continue to operate in an undefined state, potentially causing 500 errors or data integrity issues if any route assumes the user exists after `requireAuth` succeeds.
- **Suggested fix:** After deleting the user, invalidate all sessions (e.g., increment a token version in a sessions table, or if using JWTs, add the user ID to a short-lived blocklist). Verify that `requireAuth` returns a clear 401 when the user record doesn't exist.
