## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing app with clean architecture. Solid defensive patterns overall (advisory locks, CSRF, CSP), but several real bugs, a critical data integrity issue, and meaningful security gaps remain.

### Findings

#### CRITICAL

**[CR-001]** Race condition in cooked-recipe DELETE pantry restoration can produce negative quantities

- **File:** `src/app/api/cooked-recipes/route.ts:215-230`
- **Issue:** When restoring pantry items during cooked-recipe deletion, `existingItem.quantity + d.amount` is computed without checking if the pantry item was modified between the advisory lock acquisition and the update. More critically, if the same cooked recipe is deleted concurrently by two requests (e.g., double-click), the `findFirst` + `update` pattern is not atomic — one request could find and restore, then the second request also restores, doubling the quantity.
- **Impact:** Pantry item quantities can become inflated or inconsistent.
- **Suggested fix:** Use `cookedRecipe.delete` with a unique constraint or `deleteMany` with `count` check to ensure exactly-once semantics. The advisory lock already serializes per-user, but the `findFirst` by `id` followed by `findFirst` by `name` fallback can match the wrong item if the original was deleted and a new one with the same name was created.

**[CR-002]** `striptags` does not sanitize attribute-based XSS — comment imageUrl from Cloudinary is rendered as `<img src=...>` without Content Security Policy `img-src` covering all cases

- **File:** `src/components/recipe/CommentsSection.tsx:587-620`
- **Issue:** Comment images are rendered with `isCloudinaryUrl` gate, but the comment `imageUrl` is only validated at write time via `validateCloudinaryUrl`. If the Cloudinary cloud name env var changes between write and read, previously-valid URLs would fail the `isCloudinaryUrl` check silently (no rendering), but if an attacker gains access to the configured Cloudinary account, they could host malicious content at a valid Cloudinary URL. The CSP `img-src` allows `https://res.cloudinary.com` broadly (any cloud name).
- **Impact:** If the Cloudinary account is compromised, attacker-controlled images (including SVGs with embedded scripts if the browser renders them inline) could be served. CSP `img-src` should be scoped to the specific cloud name.
- **Suggested fix:**

```typescript
// In middleware.ts CSP:
`img-src 'self' data: https://res.cloudinary.com/${process.env.CLOUDINARY_CLOUD_NAME}/ blob:`;
```

**[CR-003]** User account self-deletion via `DELETE /api/users/profile` has no orphaned image cleanup

- **File:** `src/app/api/users/profile/route.ts:60-75`
- **Issue:** When a user deletes their own account, `userService.deleteUser(user.id)` cascades the DB delete but does not collect or clean up Cloudinary images (avatar, recipe images, comment images). The admin delete route (`/api/admin/users/[id]`) has image cleanup, but self-deletion does not.
- **Impact:** Orphaned Cloudinary images accumulate with no database reference, increasing storage costs. The cleanup script will catch them, but only if it's scheduled — and the code explicitly relies on it being run as a cron job.
- **Suggested fix:** Extract the image collection logic from the admin delete route into a shared function and call it in the self-deletion route as well.

#### HIGH

**[CR-004]** Recipe match endpoint loads all candidate ingredients into memory with no cap on ingredient array size per recipe

- **File:** `src/app/api/recipes/match/route.ts:120-145`
- **Issue:** The SQL query caps `jsonb_array_length(p.ingredients) <= 100`, but the in-memory matching loop processes up to `MAX_COMPARISONS = 50_000` comparisons. With 200 candidates each having 100 ingredients and 50 pantry items, that's `200 * 100 = 20,000` comparisons per request. Under concurrent load from multiple users, this can consume significant CPU.
- **Impact:** Endpoint is vulnerable to CPU exhaustion under moderate concurrency.
- **Suggested fix:** Reduce `MAX_COMPARISONS` or add per-user rate limiting specifically for this endpoint (already has `MATCH_RATE_LIMIT_MAX_REQUESTS = 30`, but that's per 15-minute window — a burst of 30 concurrent requests can still overwhelm).

**[CR-005]** `RecipeFeed` infinite scroll has no deduplication on append when filter changes race with scroll

- **File:** `src/components/recipe/RecipeFeed.tsx:159-167`
- **Issue:** The `requestIdRef` guard prevents stale responses from updating state, but the `existingIds` dedup in the append path only prevents duplicate IDs within the same state update. If `loadRecipes(true)` (reset) and `loadRecipes()` (append) are called in quick succession due to filter change + scroll intersection, and the abort doesn't fire in time, the append response could contain recipes that were already in the reset response.
- **Impact:** Duplicate recipe cards rendered temporarily until next re-render.
- **Suggested fix:** The existing code already handles this via `existingIds` Set — but the `recipesLengthRef` is updated inside the filter function, which can be stale. Consider using a functional update that reads current state length instead of the ref.

**[CR-006]** `EditProfileModal` website URL validation allows `javascript:` protocol on the client side if URL constructor doesn't throw

- **File:** `src/components/profile/EditProfileModal.tsx:131-144`
- **Issue:** The client-side validation checks `startsWith('http://') || startsWith('https://')` but only as a string prefix check. A URL like `http://evil.com\@legitimate.com` could pass the prefix check. The server-side `updateProfileSchema` has proper URL validation with `z.string().url()` and protocol checks, but the client-side validation is inconsistent.
- **Impact:** Low risk due to server-side validation, but confusing UX — client allows URLs that server will reject.
- **Suggested fix:** Use `new URL()` for client-side validation (already done), but ensure the `parsed.protocol` check is the primary gate, not the `startsWith` prefix.

**[CR-007]** Notification polling `useNotificationPolling` doesn't abort the `/api/auth/me` confirmation request on unmount

- **File:** `src/hooks/useNotificationPolling.ts:100-115`
- **Issue:** The `meAbortRef` is created and assigned, and its abort is called in the cleanup function of the polling `useEffect`. However, if the component unmounts while the `/api/auth/me` confirmation is in-flight, and the abort fires, the catch block at line 113 will set `pollingStoppedRef.current = true` and `setIsPollingPaused(true)` — but `isMountedRef.current` is already false, so the `setIsPollingPaused` call is a React state update on an unmounted component.
- **Impact:** React "Can't perform a React state update on an unmounted component" warning (React 18 removed this warning, but it's still a code smell).
- **Suggested fix:** Add `if (!isMountedRef.current) return;` before the `setIsPollingPaused` call in the catch block at line 113.

#### MEDIUM

**[CR-008]** `AdminService.getStats()` uses 7 subqueries in a single SQL statement — no caching

- **File:** `src/infrastructure/services/AdminService.ts:245-260`
- **Issue:** Every admin dashboard load executes 7 `COUNT(*)` subqueries. On tables with millions of rows, `COUNT(*)` on PostgreSQL requires a sequential scan (no index-only count).
- **Impact:** Slow admin dashboard load under large datasets.
- **Suggested fix:** Cache stats with a short TTL (30-60s) using in-memory cache or Redis, or use approximate counts via `reltuples` from `pg_class`.

**[CR-009]** `Footer` contact form `mailto:` link length check uses encoded length but the `1500` limit is arbitrary

- **File:** `src/components/Footer.tsx:60-66`
- **Issue:** The 1500-character limit on the `mailto:` URI is checked after URL encoding, which is correct. However, the `sanitize` function only strips control characters but doesn't prevent header injection in the `mailto:` body (e.g., `%0d%0aBcc: attacker@evil.com`). While `encodeURIComponent` handles this for the body parameter, the subject line uses `encodeURIComponent('Contact from ' + name)` — if `name` contains `\r\n`, the sanitize function strips it, so this is actually safe.
- **Impact:** No actual vulnerability due to sanitize + encodeURIComponent, but the comment about "defense-in-depth" is misleading since `encodeURIComponent` is doing all the heavy lifting.
- **Suggested fix:** No code change needed, but the comment should be updated to clarify that `encodeURIComponent` is the primary defense, not the sanitize function.

**[CR-010]** `useCreateRecipe` hook doesn't include credentials in fetch options

- **File:** `src/hooks/useCreateRecipe.ts:12`
- **Issue:** The fetch call includes `credentials: 'same-origin'`, which is actually the default for same-origin requests. However, it's inconsistent with other fetch calls in the codebase that omit `credentials` entirely (e.g., `RecipeFeed`, `MatchedRecipes`).
- **Impact:** No functional bug, but inconsistency in credential handling across fetch calls.
- **Suggested fix:** Either add `credentials: 'same-origin'` to all authenticated fetch calls or remove it (since it's the default).

**[CR-011]** `PersistentSearchBar` live search doesn't encode special regex characters in the query

- **File:** `src/components/search/PersistentSearchBar.tsx:159`
- **Issue:** The search query is passed via `encodeURIComponent` in the URL, which is correct for URL safety. However, on the server side (`src/app/api/search/route.ts`), the query is used with Prisma's `contains` mode which auto-escapes SQL wildcards. This is fine.
- **Impact:** No vulnerability — Prisma handles escaping correctly.
- **Suggested fix:** No fix needed. The existing comment in the search route correctly notes this.

**[CR-012]** `RecipeCard` fires `console.warn` on every render for non-Cloudinary images in development

- **File:** `src/components/recipe/RecipeCard.tsx:74-77`
- **Issue:** The `useEffect` that warns about non-Cloudinary URLs fires on every render since it depends on `recipe.id` and `recipe.imageUrl`. If a recipe has a non-Cloudinary URL, this will spam the console on every component render.
- **Impact:** Developer console noise during development.
- **Suggested fix:** Use a `useRef` to track whether the warning has already been logged for this recipe.

**[CR-013]** `cooked-recipes` POST accepts `notes` field but sanitizes with `striptags` — XSS via `deductedIngredients` JSON

- **File:** `src/app/api/cooked-recipes/route.ts:170`
- **Issue:** The `deductedIngredients` array is stored as JSON in the database. The ingredient `name` values come from the recipe's `ingredients` JSON field, which was sanitized at recipe creation time. However, if a recipe was created before sanitization was added (legacy data), the ingredient names could contain HTML that gets stored in `deductedIngredients` and later displayed in the UI.
- **Impact:** Low — React auto-escapes JSX output, so stored HTML in JSON fields won't execute as XSS. But it could cause display issues.
- **Suggested fix:** Sanitize ingredient names read from the recipe before storing in `deductedIngredients`.

**[CR-015]** Multiple admin pages (`comments`, `recipes`, `users`) have identical error handling patterns that could be extracted

- **File:** `src/app/admin/comments/page.tsx`, `src/app/admin/recipes/page.tsx`, `src/app/admin/users/page.tsx`
- **Issue:** All three admin pages duplicate the same patterns: loading state, error state, pagination, debounced search, delete dialog, action loading. This is ~200 lines of duplicated logic per page.
- **Impact:** Maintenance burden — a bug fix in one admin page must be replicated to all three.
- **Suggested fix:** Extract a generic `AdminTable` component with configurable columns, actions, and fetch logic.

**[CR-016]** `SearchPage` wraps `SearchPageContent` in `Suspense` but the fallback is `null`

- **File:** `src/app/search/page.tsx:169-173`

- **Impact:** Minor UX — users see a flash of empty content before search results appear.
- **Suggested fix:** Add a minimal loading skeleton as the fallback.

**[CR-017]** `MotionContext` dev warning for usage outside provider fires on every render
