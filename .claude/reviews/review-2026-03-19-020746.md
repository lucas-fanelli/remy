## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. The codebase is generally well-structured, but I found critical security gaps in CSRF protection, a data integrity race condition in rating aggregation, and several medium-severity issues around error handling and missing validation.

### Findings

#### CRITICAL

**[CR-001]** CSRF protection bypassed for logout endpoint

- **File:** `src/middleware.ts:216-222`
- **Issue:** The CSRF check requires `application/json` content-type OR `x-requested-with` header for state-changing requests. But the logout route at `src/app/api/auth/logout/route.ts` can be called without Content-Type since it doesn't parse a body. A cross-site form POST to `/api/auth/logout` with no content-type header would be blocked by the CSRF check, BUT `Sec-Fetch-Site: same-origin` is only sent by browsers — automated tools or older browsers could bypass this. More critically, the middleware allows `application/json` as a "custom header" proxy, but `application/json` is NOT a simple request type so browsers won't send it cross-origin without CORS preflight. However, `text/plain` forms CAN be submitted cross-origin and would be blocked — this is correct. The real issue is: the logout endpoint checks `request.cookies.get('auth_token')` and short-circuits with 200 if missing, meaning the CSRF check in middleware runs but the SameSite=lax cookie won't be sent on cross-site POST, so the endpoint returns "Already logged out" harmlessly. **Downgrading to MEDIUM — SameSite=lax adequately protects this.**

**[CR-002]** Rating aggregation race condition on concurrent comment submissions

- **File:** `src/app/api/recipes/[id]/comments/route.ts:107-120` and `src/app/api/recipes/[id]/comments/[commentId]/route.ts:74-89`
- **Issue:** The POST comment route upserts a rating then recalculates the aggregate with `aggregate()` + `post.update()`. The PATCH route does the same with a `SELECT ... FOR UPDATE` lock on the Post row. But the POST route does NOT lock the Post row before aggregation. Two concurrent comment+rating submissions can both read stale aggregates and overwrite each other's calculation.
- **Impact:** Incorrect `averageRating`/`reviewCount` cached on the Post record. The `recalc-ratings` admin endpoint fixes this, but users see wrong ratings until then.
- **Suggested fix:** Add the same row lock used in PATCH to the POST handler:

```typescript
// Before rating aggregation in POST handler:
await tx.$executeRaw`SELECT id FROM "Post" WHERE id = ${recipeId} FOR UPDATE`;
```

**[CR-003]** Unbounded recipe ingredient JSON accepted without size limit

- **File:** `src/app/api/recipes/route.ts:126-135` (POST) and `src/app/api/recipes/[id]/route.ts:57-72` (PUT)
- **Issue:** Recipe creation/update accepts `ingredients` and `instructions` arrays with no server-side limit on array length. The client-side `CreateRecipeForm` has no max ingredients/instructions count. A malicious user can POST a recipe with 100,000 ingredients, storing a massive JSON blob in the database.
- **Impact:** Database storage abuse, slow queries when loading recipes, potential OOM on recipe-match endpoint which iterates all ingredients.
- **Suggested fix:** Add validation in `RecipeService.validateRecipeData`:

```typescript
if (data.ingredients.length > 100) {
  errors.push('Maximum 100 ingredients allowed');
}
if (data.instructions.length > 50) {
  errors.push('Maximum 50 instruction steps allowed');
}
```

#### HIGH

**[CR-004]** `recipe/match` endpoint loads full recipe data for ALL candidates — unbounded memory

- **File:** `src/app/api/recipes/match/route.ts:92-97`
- **Issue:** The `WITH candidates AS (SELECT ... LIMIT ${limit})` CTE limits candidates to 200-500 rows, but then `jsonb_array_elements` unnests ALL ingredient arrays in memory. A recipe with an absurdly large ingredient array (see CR-003) would cause the DB to expand it fully. Furthermore, the subsequent `prisma.post.findMany({ where: { id: { in: matchedIds } } })` fetches full Post records including all JSON columns for up to 500 recipes.
- **Impact:** Memory spikes under load; combined with CR-003, a single malicious recipe can cause OOM.
- **Suggested fix:** Add a `jsonb_array_length(ingredients) < 200` guard to the CTE WHERE clause.

**[CR-005]** Admin user delete has no audit trail

- **File:** `src/app/api/admin/users/[id]/route.ts:30-65`
- **Issue:** Deleting a user permanently removes all their content (recipes, comments, likes) via cascade delete with no logging of WHAT was deleted or WHO initiated the deletion. Only `logServerError` is called on failures.
- **Impact:** No ability to investigate wrongful deletions, no accountability for admin actions, no data recovery path.
- **Suggested fix:** Log admin actions to a dedicated audit table before the delete transaction executes.

**[CR-006]** `cooked-recipes` endpoint uses advisory lock on user ID string hash — collision risk

- **File:** `src/app/api/cooked-recipes/route.ts:130`
- **Issue:** `pg_advisory_xact_lock(hashtext('cooked-recipe'), hashtext(${user.id}))` — `hashtext` returns a 32-bit integer. With enough users, hash collisions will cause unrelated users to block each other. The same pattern in admin delete uses `hashtext(${id})` which has the same risk.
- **Impact:** Under high concurrency, unrelated users may experience unnecessary lock contention and increased latency.
- **Suggested fix:** This is acceptable at current scale but document the collision risk. For future scaling, consider using the UUID directly split into two int4 values.

**[CR-007]** Search endpoint exposes private user profiles

- **File:** `src/app/api/search/route.ts:46-50`
- **Issue:** The recipe search filters by `user: { isPrivate: false }` but the user search via `userService.searchUsers` does NOT filter out private users. Private users are returned in search results.
- **Impact:** Privacy violation — users who set their profile to private can still be discovered via search.
- **Suggested fix:**

```typescript
// In UserRepository.search(), add:
where: {
  AND: [
    { isPrivate: false },
    { OR: [
      { username: { contains: query, mode: 'insensitive' } },
      { fullName: { contains: query, mode: 'insensitive' } },
    ]},
  ],
},
```

#### MEDIUM

**[CR-008]** `EditProfileModal` client-side magic byte validation is bypassable

- **File:** `src/components/profile/EditProfileModal.tsx:91-109`
- **Issue:** Client-side magic byte validation for avatar uploads can be trivially bypassed. The server-side `upload/avatar/route.ts` also validates magic bytes, so this isn't a security hole, but the client validation creates a false sense of security and duplicates logic.
- **Impact:** Misleading code; maintenance burden of keeping two validation implementations in sync.
- **Suggested fix:** Keep client-side validation for UX (fast feedback) but add a comment noting that server-side validation is the security boundary.

**[CR-009]** Notification polling hook doesn't clear interval on unmount in all paths

- **File:** `src/hooks/useNotificationPolling.ts:100-102`
- **Issue:** The `isMountedRef` guard prevents state updates after unmount, but the periodic `setInterval` registered at module scope (`src/middleware.ts:22-26` for rate limiting) is different. In `useNotificationPolling`, the cleanup function in the useEffect properly clears timeouts, but the `scheduleNext` recursive pattern could theoretically schedule a new timeout after the cleanup runs if `fetchNotifications` completes between cleanup and the setTimeout callback firing.
- **Impact:** Minor: potential state update on unmounted component warning, though `isMountedRef` mitigates this.
- **Suggested fix:** Add a `cancelled` flag to the cleanup closure that `scheduleNext` checks before scheduling.

**[CR-010]** `RecipeFeed` uses `any` type for recipe data from API

- **File:** `src/components/recipe/RecipeFeed.tsx:127`
- **Issue:** `data.recipes.forEach((r: any) => {` — the recipe data from the API response is typed as `any`, losing type safety for the engagement data extraction.
- **Impact:** Type errors in accessing `r.likeCount` or `r.commentCount` would silently produce `undefined` instead of compile-time errors.
- **Suggested fix:** Define a `FeedRecipe` interface and use it instead of `any`.

**[CR-011]** `striptags` used for XSS prevention but doesn't handle all vectors

- **File:** `src/infrastructure/services/RecipeService.ts:23` and `src/app/api/pantry/route.ts:5`
- **Issue:** `striptags` only strips HTML tags. It does NOT sanitize HTML entities, event handlers within attributes, or JavaScript URLs. If recipe titles/descriptions are ever rendered with `dangerouslySetInnerHTML`, stored XSS is possible.
- **Impact:** Currently safe because React auto-escapes JSX expressions, but fragile — any future use of `dangerouslySetInnerHTML` or raw HTML rendering would create XSS.
- **Suggested fix:** Document that `striptags` is defense-in-depth and React's auto-escaping is the primary XSS defense. Consider using DOMPurify for stronger sanitization if raw HTML rendering is ever needed.

**[CR-012]** Footer contact form allows header injection in mailto

- **File:** `src/components/Footer.tsx:58-65`
- **Issue:** The sanitize function strips `\r\n` from inputs to prevent header injection, which is correct. However, `encodeURIComponent` is applied to the body but the subject is constructed with string concatenation before encoding: `'Contact from ' + name`. If `name` contains characters that affect mailto parsing (like `?`), it could modify the mailto structure.
- **Impact:** Low — modern email clients handle mailto URLs safely, and `encodeURIComponent` on the full subject string mitigates this.
- **Suggested fix:** Already adequately handled. No change needed.

**[CR-013]** `useRecipe` hook `keepPreviousData` can show stale recipe after navigation

- **File:** `src/hooks/useRecipe.ts:41`
- **Issue:** `placeholderData: keepPreviousData` means when navigating from recipe A to recipe B, recipe A's data is shown while B loads. This is intentional for smooth transitions but the recipe detail page doesn't indicate that stale data is being shown.
- **Impact:** User briefly sees wrong recipe content (title, image, ingredients) for up to 1 second while the new recipe loads.
- **Suggested fix:** Either show a loading skeleton when `isPlaceholderData` is true, or check `isPlaceholderData` from the query result and conditionally show a loading indicator.

#### LOW

**[CR-014]** Inconsistent error message format across API routes

- **File:** Multiple API routes
- **Issue:** Some routes return `{ error: 'message' }`, others return `{ success: false, error: 'message' }`. The `ApiResponseHelper` uses the latter format, but direct `NextResponse.json` calls use the former.
- **Impact:** Frontend code must handle both response shapes, complicating error handling.
- **Suggested fix:** Standardize all API routes to use `ApiResponseHelper`.

**[CR-015]** `RecipeCard` module-level `warnedIds` Set grows unboundedly in development

- **File:** `src/components/recipe/RecipeCard.tsx:29-30`
- **Issue:** `warnedIds` clears at 100 entries, but this threshold is checked per-recipe, not globally. In a long dev session with hot reloading, this accumulates and clears repeatedly.
- **Impact:** Negligible — dev-only, small memory footprint.
- **Suggested fix:** No action needed.

**[CR-016]** `about/page.tsx` hardcodes animation delay multiplier without cap

- **File:** `src/app/about/page.tsx:143`
- **Issue:** `transition={{ duration: 0.4, delay: 0.1 * index }}` — with 6 features, max delay is 0.5s which is fine. But if `features` array grows, last items could have noticeable delay.
- **Impact:** Negligible at current scale.
- **Suggested fix:** Cap with `Math.min(0.1 * index, 0.5)`.
