## Code Review — 2026-03-19

### Summary

Large, well-structured Next.js recipe-sharing application. Clean Architecture with DI container, comprehensive test coverage. Several security and correctness issues require attention, most notably an unrate-limited notification polling endpoint and a recipe matching bug that silently drops candidates.

### Findings

#### CRITICAL

**[CR-001]** GET `/api/notifications` completely bypasses rate limiting

- **File:** `src/middleware.ts:186-191`
- **Issue:** The middleware exempts `GET /api/notifications` from all rate limiting (both IP-based and per-user). The comment claims "per-user rate limiting handles abuse" but per-user limiting only applies to write operations (`POST`/`PUT`/`PATCH`/`DELETE`) at line 258. An unauthenticated attacker can flood this endpoint at arbitrary volume — each request hits the database.
- **Impact:** Database DoS. A single client can issue thousands of requests/second to an endpoint that runs multiple DB queries (findByRecipientId + getUnreadCount).
- **Suggested fix:** Apply IP-based rate limiting with a higher threshold instead of skipping entirely:

```typescript
if (request.nextUrl.pathname === '/api/notifications' && request.method === 'GET') {
  const notifKey = getRateLimitKey(request) + ':notif';
  const notifLimit = checkRateLimit(notifKey, 200); // 200 per 15min window
  if (!notifLimit.allowed) {
    return NextResponse.json({ error: 'Too many requests' }, { status: 429 });
  }
  return response;
}
```

**[CR-002]** Recipe matching silently drops candidates when pantry exceeds 20 items

- **File:** `src/app/api/recipes/match/route.ts:82-84`
- **Issue:** `.slice(0, 20)` limits the DB pre-filter to the first 20 normalized pantry names. Recipes that only match ingredients 21+ are never fetched from the database. With `MAX_PANTRY_ITEMS = 500`, most pantry items are ignored for the DB query.
- **Impact:** Users with well-stocked pantries get incomplete match results. A 100% match recipe could be invisible if its ingredients only overlap with items beyond position 20.
- **Suggested fix:** Use a larger slice or restructure the query. At minimum, sort pantry names by frequency/importance before slicing, or increase the limit:

```typescript
.slice(0, 50) // at least cover common pantry sizes
```

**[CR-004]** Hardcoded magic number for daily cook limit

- **File:** `src/app/api/cooked-recipes/route.ts:139`
- **Issue:** `if (dailyCookCount >= 20)` uses a magic number. The 429 error message also hardcodes "20 per day". This is the only rate limit in the app not defined as a constant.
- **Impact:** Maintenance risk. Changing the limit requires updating two locations and is easy to miss.
- **Suggested fix:**

```typescript
// In src/lib/constants.ts:
export const MAX_DAILY_COOKS = 20;

// In route:
if (dailyCookCount >= MAX_DAILY_COOKS) {
  throw new Error('DAILY_LIMIT_REACHED');
}
// In error handler:
{
  error: `Daily cook limit reached (${MAX_DAILY_COOKS} per day).`;
}
```

**[CR-005]** Potential deadlock in admin user deletion

- **File:** `src/app/api/admin/users/[id]/route.ts:38-42`
- **Issue:** The transaction locks the target user row with `FOR UPDATE`, then locks ALL admin rows via `SELECT COUNT(*) ... WHERE role = 'ADMIN' FOR UPDATE`. If two concurrent requests delete different admin users, they each hold one user's lock and both try to acquire the other's lock through the count query, causing a deadlock.
- **Impact:** PostgreSQL detects and resolves deadlocks by aborting one transaction, returning a 500 error. Not a data integrity issue, but a poor UX under concurrent admin operations.
- **Suggested fix:** Use a single advisory lock for admin-count-sensitive operations to serialize them without row-level lock contention:

```typescript
await tx.$executeRaw`SELECT pg_advisory_xact_lock(48880, 0)`; // register in constants
// Then do the count check without FOR UPDATE
```

#### MEDIUM

**[CR-006]** Inconsistent auth patterns across API routes

- **File:** Multiple: `src/app/api/pantry/[id]/route.ts`, `src/app/api/notifications/[id]/route.ts`, vs `src/app/api/cooked-recipes/route.ts`
- **Issue:** Some routes use `requireAuth(request)` (which returns a user object), while others manually call `extractAuthToken` + `tokenService.verify`. Both work, but the manual pattern duplicates boilerplate and doesn't benefit from centralized auth changes.
- **Impact:** Maintenance burden. If auth logic changes (e.g., token rotation), manual routes need individual updates.
- **Suggested fix:** Standardize on `requireAuth` for all authenticated routes. Refactor pantry and notification routes to use it.

**[CR-007]** `normalizeIngredientName` produces incorrect stems for edge-case words

- **File:** `src/lib/utils/ingredients.ts:51-65`
- **Issue:** The stemming logic strips 's' from words > 4 chars that don't end in 'ss'. Words like "alias" become "alia", "atlas" becomes "atla". The guard only catches results < 3 chars. The exception list covers common cooking terms but can't cover all edge cases.
- **Impact:** Incorrect pantry matching for uncommon ingredient names. Could cause false matches or missed matches.
- **Suggested fix:** Consider using a proper stemming library (e.g., `stemmer` or `natural`) or at minimum, add a broader exception list for common words ending in 's' that aren't plurals.

**[CR-008]** `RecipeCard` silently replaces non-Cloudinary URLs with fallback

- **File:** `src/components/recipe/RecipeCard.tsx:141-142`
- **Issue:** `src={recipe.imageUrl && isCloudinaryUrl(recipe.imageUrl) ? recipe.imageUrl : '/chef-logo.png'}` — any recipe with a non-Cloudinary image URL (e.g., from a data migration or older version) silently shows the logo instead of the actual image. The dev warning only fires in development.
- **Impact:** Users see incorrect images with no indication of why. Data migration issues are hidden.
- **Suggested fix:** Log a warning in production (via Sentry) when a non-Cloudinary URL is encountered, and consider showing the original URL with the fallback only on error:

```typescript
src={recipe.imageUrl || '/chef-logo.png'}
// Keep the onError handler as the safety net
```

#### LOW

**[CR-009]** `RecipeFeed` has loading guard that may silently drop requests

- **File:** `src/components/recipe/RecipeFeed.tsx:133`
- **Issue:** `if (loadingRef.current && !reset) return;` — if the user scrolls to trigger infinite scroll while a filter change (reset) is in-flight, the scroll-triggered load is silently dropped. The next scroll intersection event will retry, but there's a brief window where the user might think loading stalled.
- **Impact:** Minor UX: user might see "reached the end" briefly before the real load kicks in.
- **Suggested fix:** No action required — the abort controller handles filter changes correctly and the sentinel will re-trigger.

**[CR-010]** `Footer` contact form `mailto:` link length check uses wrong threshold

- **File:** `src/components/Footer.tsx:60`
- **Issue:** `if (mailtoLink.length > 8000)` — RFC 2368 doesn't specify a max length for `mailto:` URIs, but most browsers and email clients have a practical limit of ~2000 characters for URLs. The 8000 threshold is too generous and will fail silently on most platforms.
- **Impact:** Users with long messages get their email client opened but the message is truncated without warning.
- **Suggested fix:** Lower the threshold to 2000 or switch to a server-side contact form.
