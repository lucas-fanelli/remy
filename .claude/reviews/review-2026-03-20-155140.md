## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured with good security practices (httpOnly cookies, CSRF protection, advisory locks). However, several security gaps, race conditions, and logic bugs exist across the codebase.

### Findings

#### CRITICAL

**[CR-001]** Cooked recipe DELETE does not verify rating ownership before deleting

- **File:** `src/app/api/cooked-recipes/route.ts:222-230`
- **Issue:** When deleting a cooked recipe, the code checks if a comment exists before deleting the rating. But it never verifies the rating actually belongs to the cooked recipe flow. A user could have a rating from a comment AND a cooked recipe simultaneously — deleting the cooked recipe would incorrectly delete the comment's rating too if the comment was deleted between the check and the delete.
- **Impact:** Rating data loss; averageRating/reviewCount becomes incorrect.
- **Suggested fix:** Track the source of each rating (cooked vs comment) in the Rating table, or at minimum use a single combined rating per user per post and don't delete it on cooked recipe removal.

**[CR-002]** `striptags` import missing in cooked-recipes route

- **File:** `src/app/api/cooked-recipes/route.ts:9`
- **Issue:** `striptags` is imported but there's no `package.json` entry verification shown. More critically, the notes field is sanitized with `striptags` but the function `deductPantryItems` operates on recipe ingredients from the database which are trusted — however, the `notes` field sanitization happens AFTER the Zod schema validation, meaning a user could pass `notes: "<script>alert(1)</script>"` and it would pass schema validation, then get stripped. The schema should reject HTML.
- **Impact:** Defense-in-depth gap; stored XSS if striptags fails or is bypassed.
- **Suggested fix:** Add `.refine(val => !val || !/<[^>]*>/.test(val), 'HTML not allowed')` to the Zod schema for notes.

**[CR-003]** Admin user delete collects images BEFORE cascade delete — race window

- **File:** `src/app/api/admin/users/[id]/route.ts:60-70`
- **Issue:** The comment at line 55 acknowledges this race: images are collected before `user.delete`, so posts/comments created between collection and deletion will have orphaned images. The mitigation (cleanup script) is stated as a cron job but there's no evidence it's actually scheduled.
- **Impact:** Cloudinary storage cost leak; orphaned images accumulate indefinitely without the cron job.
- **Suggested fix:** Add a deployment checklist item or health check that warns if the cron job isn't configured. Consider using a database trigger or post-delete hook instead.

**[CR-004]** Recipe match endpoint has no authentication-based result isolation

- **File:** `src/app/api/recipes/match/route.ts:78-82`
- **Issue:** The SQL query fetches all posts matching pantry ingredients without filtering by `user.isPrivate`. Private users' recipes are exposed in match results.
- **Impact:** Privacy violation — private users' recipes leak through the pantry matching feature.
- **Suggested fix:**

```sql
AND NOT EXISTS (SELECT 1 FROM "User" u WHERE u.id = p."userId" AND u."isPrivate" = true)
```

#### HIGH

**[CR-005]** `useNotificationPolling` AbortController leak on auth confirmation

- **File:** `src/hooks/useNotificationPolling.ts:96-106`
- **Issue:** When a 401 is received, a new `meAbortRef` AbortController is created for the `/api/auth/me` confirmation request. But the cleanup in the polling effect only aborts `meAbortRef.current` on unmount. If multiple 401s arrive before cleanup, previous `/api/auth/me` requests may complete and trigger logout multiple times.
- **Impact:** Multiple logout calls, potential race condition in auth state.
- **Suggested fix:** Abort the previous `meAbortRef` before creating a new one:

```typescript
meAbortRef.current?.abort();
const meController = new AbortController();
meAbortRef.current = meController;
```

**[CR-006]** Footer contact form mailto link susceptible to length-based DoS

- **File:** `src/components/Footer.tsx:57-67`
- **Issue:** The form fields have `maxLength` attributes (100/254/1000) but these are client-side only. The `handleSendEmail` function sanitizes control characters and checks the mailto link length against 1500, but a malicious caller could bypass client-side validation. More importantly, `window.open` with a very long URL could crash some email clients.
- **Impact:** Low — client-side only, but poor UX if email client crashes.
- **Suggested fix:** Validate lengths in `handleSendEmail` before constructing the mailto link:

```typescript
if (name.length > 100 || email.length > 254 || message.length > 1000) {
  setMailtoError('Input too long');
  return;
}
```

**[CR-007]** `RecipeFeed` infinite scroll has no deduplication for concurrent intersection callbacks

- **File:** `src/components/recipe/RecipeFeed.tsx:162-167`
- **Issue:** The IntersectionObserver callback checks `loadingRef.current` and a 500ms throttle, but `loadRecipes` itself aborts previous requests and uses `requestIdRef` for stale response detection. However, if two intersection events fire within 500ms but after the first `loadRecipes` completes, the second could trigger a duplicate page load because `lastLoadTimeRef` is only checked against `Date.now()`, not against whether the previous load already incremented `pageRef`.
- **Impact:** Potential duplicate recipe entries in the feed (mitigated by the dedup `Set` in line 158, but wastes API calls).
- **Suggested fix:** Also check `loadingRef.current` inside the throttle guard or use a single request-in-flight flag.

**[CR-008]** `EditProfileModal` website URL validation is client-side only for credential check

- **File:** `src/components/profile/EditProfileModal.tsx:138-148`
- **Issue:** The client-side validation checks for `http://` or `https://` prefix and embedded credentials, but the server-side `updateProfileSchema` in `schemas.ts` also validates this. However, the client catches `URL` parsing failures silently with a comment "will be caught by server-side validation" — but the server validation uses Zod `.url()` which has different parsing behavior than `new URL()`.
- **Impact:** Inconsistent validation between client and server could allow malformed URLs through one path but not the other.
- **Suggested fix:** Remove the redundant client-side URL parsing and rely entirely on server-side Zod validation. The client should only do UX-level checks.

**[CR-009]** Admin recipes/comments API leaks masked but guessable email patterns

- **File:** `src/infrastructure/services/AdminService.ts:14-19`
- **Issue:** `maskEmail` only masks the local part and domain name, preserving the first character of each and the TLD. For common email providers (gmail.com, outlook.com), the first character + domain gives significant information for social engineering.
- **Impact:** Partial email disclosure to admin users (who are already trusted, but defense-in-depth applies).
- **Suggested fix:** Use a more aggressive mask: `t***@g***.com` → `***@***.***` or just don't return emails to the admin frontend at all since they're not displayed.

#### MEDIUM

**[CR-010]** `PersistentSearchBar` search results include user IDs in the response

- **File:** `src/components/search/PersistentSearchBar.tsx:16-19`
- **Issue:** The `SearchResultUser` interface includes `id` field. The `/api/search` endpoint strips IDs from users (`({ email: _email, id: _id, ...rest }) => rest` in `src/app/api/users/search/route.ts`), but the main `/api/search/route.ts` does NOT strip IDs from users — it only strips email.
- **Impact:** User IDs are exposed in search results, enabling enumeration.
- **Suggested fix:** Strip `id` from user results in `src/app/api/search/route.ts`:

```typescript
const users = (await userService.searchUsers(query.trim(), limit, offset)).map((u) => ({
  username: u.username,
  fullName: u.fullName,
  avatar: u.avatar,
  bio: u.bio,
}));
```

Wait — looking again, it already does this at line 27. But the `PersistentSearchBar` component types expect `id` in `SearchResultUser`. The types are wrong but harmless since the API doesn't send it.

**[CR-011]** `RecipeCard` dev warning uses unbounded `Set` with manual 100-entry clear

- **File:** `src/components/recipe/RecipeCard.tsx:57-62`
- **Issue:** `warnedRecipeIds` is a module-level `Set` that grows until it hits 100 entries, then clears entirely. This means: (1) after clear, all warnings fire again, (2) the Set grows unboundedly in production where the warning doesn't fire but the `useEffect` still runs.
- **Impact:** Minor memory leak in development; unnecessary `useEffect` execution in production.
- **Suggested fix:** Gate the entire `useEffect` behind `process.env.NODE_ENV === 'development'` or use a `WeakSet` pattern.

**[CR-012]** `getQueryClient` in `QueryProvider` returns a new client on server but `getQueryClient()` is also called in `AuthContext.logout`

- **File:** `src/providers/QueryProvider.tsx:20-28` and `src/contexts/AuthContext.tsx:74`
- **Issue:** `AuthContext.logout` calls `getQueryClient()?.clear()` which on the server would create a throwaway QueryClient just to call `.clear()` on it. The try-catch prevents errors, but it's a no-op allocation.
- **Impact:** Minor — negligible performance impact, but confusing semantics.
- **Suggested fix:** Only call `getQueryClient()?.clear()` when `typeof window !== 'undefined'`.

**[CR-013]** `CommentsSection` doesn't abort in-flight upload on unmount

- **File:** `src/components/recipe/CommentsSection.tsx:105-133`
- **Issue:** When submitting a comment with an image, the upload request (`fetch('/api/upload', ...)`) is not tied to an AbortController. If the user navigates away during upload, the fetch continues in the background and may call `setState` on an unmounted component.
- **Impact:** React "setState on unmounted component" warning; wasted bandwidth.
- **Suggested fix:** Use an AbortController in the upload fetch, abort on unmount.

**[CR-014]** Pantry item PUT route allows updating to an existing item name (no duplicate check)

- **File:** `src/app/api/pantry/[id]/route.ts:87-111`
- **Issue:** The PUT endpoint updates a pantry item's name without checking if another item with the same name already exists. The POST endpoint has a duplicate check, but PUT does not.
- **Impact:** Users can create duplicate pantry items by renaming an existing item to match another.
- **Suggested fix:** Add a case-insensitive uniqueness check before updating:

```typescript
if (name !== undefined) {
  const existing = await prisma.pantryItem.findFirst({
    where: {
      pantry: { userId: user.id },
      name: { equals: name.trim(), mode: 'insensitive' },
      id: { not: itemId },
    },
  });
  if (existing)
    return NextResponse.json({ error: 'Item with this name already exists' }, { status: 409 });
}
```

**[CR-015]** `useCreateRecipe` hook doesn't return the created recipe data

- **File:** `src/hooks/useCreateRecipe.ts:17`
- **Issue:** `createRecipe` calls `response.json()` at the end but doesn't await or return the parsed data meaningfully. The caller in `Navigation.tsx` doesn't use the return value, but `Home.tsx` calls `await createRecipe(data)` expecting it to resolve — the missing `await` on `response.json()` means the promise resolves to a pending promise.
- **Impact:** Callers cannot access the created recipe ID for navigation.
- **Suggested fix:** `return await response.json();` (add `await`).
