## Code Review — 2026-03-21

### Summary

A cooked-recipes API route with pantry deduction logic. Generally well-structured with good concurrency handling, but has several issues around data integrity, missing validation, and a subtle race condition in the DELETE path.

### Findings

#### CRITICAL

**[CR-001]** Pantry restoration in DELETE does not normalize unit before map lookup

- **File:** `src/app/api/cooked-recipes/route.ts:257`
- **Issue:** The `byNameUnit` map is keyed by raw `item.unit`, but the lookup key uses `unit` (from `striptags(d.unit)`). If the stored pantry item unit has different casing or whitespace than what was saved in `deductedIngredients`, the lookup silently fails and a duplicate pantry item is created instead of restoring the existing one.
- **Impact:** Duplicate pantry items accumulate; user sees phantom ingredients after undoing a cook.
- **Suggested fix:**

```typescript
// Build map with normalized keys
const byNameUnit = new Map(
  allPantryItems.map((i) => [
    `${normalizeIngredientName(i.name)}|${i.unit.trim().toLowerCase()}`,
    i,
  ])
);
// ...
// Lookup with same normalization
const lookupKey = `${normalizeIngredientName(safeName)}|${unit.trim().toLowerCase()}`;
const existingItem =
  (d.pantryItemId ? byId.get(d.pantryItemId) : undefined) ?? byNameUnit.get(lookupKey);
```

**[CR-002]** Rating aggregation race in POST: advisory lock and row lock are acquired in wrong order

- **File:** `src/app/api/cooked-recipes/route.ts:213-214`
- **Issue:** The `SELECT ... FOR UPDATE` on the Post row happens _after_ `pg_advisory_xact_lock`. In the DELETE handler, the advisory lock is acquired first, then the Post `FOR UPDATE` lock. If two concurrent requests (one POST, one DELETE for the same user and post) acquire locks in different orders on different resources, this is a textbook deadlock scenario. The advisory lock namespace is the same (`PG_ADVISORY_LOCK_COOKED_RECIPE`) and keyed on the same user, so in practice they serialize — but only because both use the same user key. If a POST by user A rates post X while a DELETE by user B (who also cooked post X) runs concurrently, the advisory locks use different keys (different users) but both try `FOR UPDATE` on the same Post row — no deadlock there. However, the POST path acquires the advisory lock _before_ the `FOR UPDATE`, while conceptually the advisory lock is for pantry and the row lock is for ratings. This coupling is fragile. More importantly: the `FOR UPDATE` in POST is acquired _after_ the `cookedRecipe.create`, meaning there's a window where the cookedRecipe exists but the rating hasn't been written yet.
- **Impact:** Under concurrent load with the same user, potential for stale rating aggregation if the lock ordering assumptions change.
- **Suggested fix:** Move the `SELECT ... FOR UPDATE` on the Post row to immediately before the rating upsert, and document that the advisory lock serializes all pantry + rating operations per-user.

#### HIGH

**[CR-003]** `byNameUnit` map key in DELETE restoration doesn't use `normalizeIngredientName` consistently

- **File:** `src/app/api/cooked-recipes/route.ts:257`
- **Issue:** The map is built with raw `i.name` in the key: `` `${normalizeIngredientName(i.name)}|${i.unit}` `` — this part is correct. But the lookup at line 264 uses `normalizeIngredientName(safeName)` where `safeName = striptags(d.name).slice(0, 200)`. If `striptags` alters the name differently than the original stored name, normalization may not match. The real problem: the map update at line 275 uses `` `${safeName}|${unit}` `` _without_ `normalizeIngredientName`, so subsequent iterations in the same loop won't find the item they just created.
- **Impact:** Within a single DELETE, if two deducted ingredients normalize to the same name, the second one creates a duplicate instead of incrementing the first.
- **Suggested fix:**

```typescript
// Line 275: use normalized key
byNameUnit.set(`${normalizeIngredientName(safeName)}|${unit}`, newItem);
```

**[CR-004]** No pagination metadata returned from GET

- **File:** `src/app/api/cooked-recipes/route.ts:128`
- **Issue:** The GET response returns `{ cookedRecipes, total }` but doesn't include `page`, `limit`, or `totalPages`. Clients have to track pagination state themselves and cannot determine if there are more pages.
- **Impact:** Frontend pagination is fragile; clients can request pages beyond the last page and get empty arrays with no indication they've overshot.
- **Suggested fix:**

```typescript
return NextResponse.json({
  cookedRecipes,
  total,
  page,
  limit,
  totalPages: Math.ceil(total / limit),
});
```

**[CR-005]** `striptags` applied inconsistently — some paths double-sanitize, others miss it

- **File:** `src/app/api/cooked-recipes/route.ts:78,95,100`
- **Issue:** In `deductPantryItems`, `striptags` is called on `ingredient.name` and `ingredient.unit` when building `insufficientIngredients` (line 78-79) and `deductedIngredients` (lines 95, 100). But the input `recipeIngredients` were _already_ sanitized with `striptags` at line 196. This is double-sanitization — harmless but wasteful. More critically, in the DELETE restoration path (line 260), `striptags` is applied to `d.name` from the stored `deductedIngredients`, which was already sanitized before storage. If `striptags` is not idempotent for edge cases (e.g., `"a < b"` → `"a "` on first pass), double-application could truncate data.
- **Impact:** Potential data truncation on ingredient names containing `<` characters that aren't HTML tags.
- **Suggested fix:** Sanitize once at the boundary (when reading from DB/user input) and document that downstream functions receive pre-sanitized data.

#### MEDIUM

**[CR-006]** `console.warn` used directly instead of structured logger

- **File:** `src/app/api/cooked-recipes/route.ts:204,244`
- **Issue:** Two `console.warn` calls bypass `logServerError`/`logAuditEvent`, making these warnings invisible to any structured logging pipeline.
- **Impact:** Operational blind spot — ingredient validation failures and corrupted deduction data won't appear in log aggregation or alerting.
- **Suggested fix:** Replace with `logServerError` or a dedicated `logWarning` utility.

**[CR-007]** Hardcoded pantry item limit of 500 in DELETE restoration

- **File:** `src/app/api/cooked-recipes/route.ts:272`
- **Issue:** `byId.size < 500` is a magic number with no corresponding constant. If a max pantry size constant exists elsewhere, this should reference it; if not, this silently drops ingredient restoration without notifying the user.
- **Impact:** Users with large pantries silently lose ingredients on cook undo. The limit is undocumented.
- **Suggested fix:** Extract to a named constant (e.g., `MAX_PANTRY_ITEMS`) and return a warning in the response when items are skipped.

**[CR-008]** Restored quantity cap of 10000 is a magic number

- **File:** `src/app/api/cooked-recipes/route.ts:267`
- **Issue:** `Math.min(existingItem.quantity + d.amount, 10000)` — the cap of 10000 is undocumented and not extracted to a constant. Same value appears in the Zod schema at line 240 (`z.number().positive().max(10000)`).
- **Impact:** Maintenance burden; if the limit changes, it must be updated in multiple places.
- **Suggested fix:** Extract `MAX_PANTRY_QUANTITY = 10000` to `constants.ts`.

**[CR-009]** No index hint or comment on the `cookedAt >= twentyFourHoursAgo` queries

- **File:** `src/app/api/cooked-recipes/route.ts:168,174`
- **Issue:** Two queries filter on `(userId, cookedAt)` — one also includes `postId`. If there's no composite index on `(userId, postId, cookedAt)` or `(userId, cookedAt)`, these become sequential scans per-user under load.
- **Impact:** Slow POST endpoint under high usage.
- **Suggested fix:** Verify a composite index exists on `cookedRecipe(userId, postId, cookedAt)` in the Prisma schema. Add `@@index([userId, cookedAt])` if missing.

**[CR-010]** `JSON.parse(JSON.stringify(deductedIngredients))` is unnecessary

- **File:** `src/app/api/cooked-recipes/route.ts:217`
- **Issue:** `deductedIngredients` is an array of plain objects with string and number fields — no circular refs, no class instances. The round-trip through JSON is a no-op that wastes CPU.
- **Impact:** Minor performance waste; confusing to readers who wonder what edge case it guards against.
- **Suggested fix:** Pass `deductedIngredients` directly:

```typescript
deductedIngredients: deductedIngredients.length > 0 ? deductedIngredients : undefined,
```

#### LOW

**[CR-011]** Error control flow uses thrown strings matched by `error.message`

- **File:** `src/app/api/cooked-recipes/route.ts:87,166,172,179`
- **Issue:** Using `throw new Error('RECIPE_NOT_FOUND')` and then matching `error.message === 'RECIPE_NOT_FOUND'` in the catch block is fragile. If any library throws an error with one of these message strings, it'll be mishandled.
- **Impact:** Low probability but hard-to-debug misrouting of errors.
- **Suggested fix:** Use custom error classes or a typed result pattern:

```typescript
class RecipeNotFoundError extends Error {
  readonly code = 'RECIPE_NOT_FOUND' as const;
}
```

**[CR-012]** `force` parameter in POST allows bypassing insufficient ingredient check with no audit trail

- **File:** `src/app/api/cooked-recipes/route.ts:82-84`
- **Issue:** When `force=true`, insufficient ingredients are deducted (consumed entirely) and the cook proceeds. This is logged nowhere — `logAuditEvent` is only called in DELETE. A user repeatedly force-cooking could drain their pantry without any audit log.
- **Impact:** No observability into forced deductions; makes debugging pantry discrepancies harder.
- **Suggested fix:** Add `logAuditEvent('COOKED_RECIPE_FORCE_DEDUCTION', { userId: user.id, postId, insufficientIngredients })` when force is used.

**[CR-013]** `parseAmount` return value NaN check could mask bad data

- **File:** `src/app/api/cooked-recipes/route.ts:64`
- **Issue:** `if (isNaN(recipeAmount) || recipeAmount <= 0) continue;` silently skips ingredients with unparseable amounts. This is correct for "to taste" entries, but also silently ignores corrupted data like `amount: "abc"`.
- **Impact:** Corrupted recipe data causes silent partial deductions with no warning.
- **Suggested fix:** Log a warning when an amount can't be parsed and isn't a known skip-pattern like "to taste".
