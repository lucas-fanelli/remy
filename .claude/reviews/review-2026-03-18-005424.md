## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security gaps in auth handling, race conditions in data mutations, and missing input validation across API routes.

### Findings

#### CRITICAL

**[CR-001]** Recipe match endpoint loads all recipes into memory without pagination

- **File:** `src/app/api/recipes/match/route.ts:68-83`
- **Issue:** `take: 100` fetches up to 100 full recipe objects including JSON ingredient arrays into memory, then iterates over all of them in a loop. As the database grows, this becomes an OOM risk and a performance bottleneck.
- **Impact:** Server crashes under load or with large datasets. Matching logic is O(recipes \* ingredients).
- **Suggested fix:** Move ingredient matching to a database query or implement cursor-based pagination with streaming. At minimum, select only the fields needed for matching.

**[CR-002]** CSRF protection is bypassable — content-type check is too permissive

- **File:** `src/middleware.ts:128-145`
- **Issue:** The CSRF check allows any request with `content-type: application/json` or `multipart/form-data` or `authorization` header. A malicious page can set `Content-Type: application/json` on a `fetch()` call cross-origin (simple request headers are allowed by CORS preflight rules only for certain content types, but `application/json` triggers preflight). However, the `Sec-Fetch-Site` check is good — but it falls through to the weaker checks via `||`. If `Sec-Fetch-Site` is missing (older browsers, non-browser clients), any request with `Content-Type: application/json` passes.
- **Impact:** CSRF attacks possible from older browsers that don't send `Sec-Fetch-Site`.
- **Suggested fix:** Make `Sec-Fetch-Site` the primary check and only fall back to custom header checks (`x-requested-with`) for non-browser API clients. Remove `content-type` and `authorization` as CSRF tokens — they're not CSRF-proof.

**[CR-003]** `cooked-recipes` POST deducts pantry items without validating sufficient quantity

- **File:** `src/app/api/cooked-recipes/route.ts:122-142`
- **Issue:** When deducting pantry items, if `unitsCompatible` is true, it subtracts the recipe amount from pantry quantity. But if `recipeAmount > pantryQuantity`, it deletes the item, potentially hiding negative balances. There's no check that the user actually has enough of each ingredient. The `matchedPantryIds` set prevents double deduction per recipe ingredient, but multiple recipe ingredients could match the same pantry item name if the `ingredientMatches` function returns true for similar names.
- **Impact:** Pantry quantities silently go to zero when user doesn't have enough, with no user feedback about insufficient stock.
- **Suggested fix:** Add a validation pass before deduction to check if the user has enough of each ingredient, and return a warning if not.

**[CR-004]** Admin middleware JWT verification in middleware.ts doesn't check token expiration robustly

- **File:** `src/middleware.ts:153-177`
- **Issue:** The manual JWT verification in middleware uses `payload.exp > now` but `exp` is optional (`!payload.exp || payload.exp > now`). If a JWT is generated without an `exp` claim (which shouldn't happen but could via a misconfigured token service), it would be treated as valid forever.
- **Impact:** Tokens without expiry bypass admin access control indefinitely.
- **Suggested fix:** Change to `payload.exp && payload.exp > now` — require expiry to be present.

```typescript
isAdmin = payload.role === 'ADMIN' && payload.exp && payload.exp > now;
```

#### HIGH

**[CR-005]** `POST /api/recipes/[id]/comments` checks recipe existence outside transaction

- **File:** `src/app/api/recipes/[id]/comments/route.ts:91-96`
- **Issue:** The recipe existence check (`prisma.post.findUnique`) happens before the transaction. Between the check and the `tx.comment.create`, the recipe could be deleted by another request, causing a foreign key violation.
- **Impact:** 500 error on concurrent recipe deletion + comment creation.
- **Suggested fix:** Move the recipe existence check inside the transaction.

**[CR-006]** Notification polling creates exponential backoff that never resets on re-mount

- **File:** `src/components/Navigation.tsx:166-180`
- **Issue:** `consecutiveFailuresRef` is reset on user change but the polling `scheduleNext` closure captures a stale ref. When visibility changes, a new `scheduleNext` chain starts without clearing the old timeout, potentially creating duplicate polling chains.
- **Impact:** Multiple concurrent polling chains cause excessive API calls and potential rate limiting.
- **Suggested fix:** Store the timeout ID in a ref and clear it before starting a new chain on visibility change. The current code partially does this but has a race condition between `clearTimeout(timeout)` and `scheduleNext()`.

**[CR-007]** `fetchStats` in admin dashboard has `isAuthenticated` in dependency array but doesn't use it

- **File:** `src/app/admin/page.tsx:42`
- **Issue:** `fetchStats` callback depends on `isAuthenticated` but the function body doesn't reference it. This is a stale closure risk — if auth state changes, the memoized callback won't reflect it, but it also won't re-fetch.
- **Impact:** Potential stale data after auth state changes; misleading dependency array.
- **Suggested fix:** Remove `isAuthenticated` from the dependency array or add a guard inside the function.

**[CR-008]** Search endpoint doesn't paginate users

- **File:** `src/app/api/search/route.ts:24`
- **Issue:** `userService.searchUsers(query.trim(), limit)` is called but the `offset` parameter is only applied to recipe search, not user search. If there are many matching users, pagination is impossible.
- **Impact:** Users can't paginate through user search results; potential performance issue with many matches.
- **Suggested fix:** Pass `offset` to `searchUsers` or document that user search doesn't support pagination.

**[CR-009]** `loadPantry` has `isAuthenticated` in dependency but doesn't check it

- **File:** `src/app/pantry/page.tsx:87`
- **Issue:** `loadPantry` callback lists `isAuthenticated` as a dependency but doesn't use it inside the function body. The `useEffect` does check `isAuthenticated`, but the callback itself will still be re-created unnecessarily.
- **Impact:** Misleading dependency; no guard inside the fetch function.
- **Suggested fix:** Either add `if (!isAuthenticated) return;` inside `loadPantry` or remove from deps.

#### MEDIUM

**[CR-010]** `about/page.tsx` imports `NextLink` but the branding config `BRANDING.youtube` is an external URL rendered with `<Link href={...}>` without `target="_blank"`... actually it does have `target="_blank"`. However, `techStack` is hardcoded

- **File:** `src/app/about/page.tsx:63-70`
- **Issue:** `techStack` array is hardcoded in the component. If the tech stack changes, this requires a code change rather than a config update.
- **Impact:** Low maintainability for static content.
- **Suggested fix:** Move to branding config or accept as static content.

**[CR-011]** `RecipeFeed` infinite scroll uses `setTimeout` throttle instead of `requestAnimationFrame` or `IntersectionObserver`

- **File:** `src/components/recipe/RecipeFeed.tsx:132-141`
- **Issue:** Scroll-based infinite loading uses `setTimeout(handleScroll, 200)` which is less efficient than `IntersectionObserver`. The scroll handler fires repeatedly and checks `document.documentElement.scrollHeight` on every tick.
- **Impact:** Performance degradation on low-end devices, unnecessary scroll event processing.
- **Suggested fix:** Replace with `IntersectionObserver` on a sentinel element at the bottom of the list.

**[CR-012]** `handleFollow` in followers/following pages doesn't show error feedback to user

- **File:** `src/app/profile/[username]/followers/page.tsx:63-78`
- **Issue:** On follow/unfollow failure, the state is silently reverted but no toast or error message is shown to the user.
- **Impact:** User doesn't know why the follow action didn't work.
- **Suggested fix:** Add error toast/snackbar notification on failure.

**[CR-013]** `PersistentSearchBar` creates a new `AbortController` on every query change without cleanup guarantee

- **File:** `src/components/search/PersistentSearchBar.tsx:121-124`
- **Issue:** The `abortControllerRef.current?.abort()` call aborts the previous request, but the cleanup function in `useEffect` also calls `controller.abort()`. If the component unmounts while a request is in-flight, both the ref abort and cleanup abort fire, which is fine. However, the `AbortError` catch silently swallows errors without distinguishing between user-initiated aborts and network failures.
- **Impact:** Minor — swallowed errors could mask real network issues during development.
- **Suggested fix:** The current `DOMException` check is correct. This is acceptable.

**[CR-014]** `loadProfile` in profile page depends on `isAuthenticated` but uses it as a signal to fetch — could cause double fetch

- **File:** `src/app/profile/[username]/page.tsx:79`
- **Issue:** `loadProfile` has `isAuthenticated` in its dependency array and `username` is also a dependency. When both change simultaneously (e.g., login while viewing a profile), the effect fires twice.
- **Impact:** Double API call on simultaneous state changes.
- **Suggested fix:** Remove `isAuthenticated` from `loadProfile` deps — the API handles auth via cookies regardless.

**[CR-015]** `RecipeCard` image `onError` handler only prevents one fallback cycle

- **File:** `src/components/recipe/RecipeCard.tsx:127-131`
- **Issue:** If the fallback image `/placeholder-recipe.png` also fails to load, the `dataset.fallback` check prevents an infinite loop but leaves a broken image.
- **Impact:** Broken image display if placeholder is missing.
- **Suggested fix:** Acceptable as-is — the fallback guard is correct.

**[CR-017]** `averageRating` field has inconsistent naming — sometimes `averageRating`, sometimes used as `totalRatings` vs `reviewCount`

- **File:** Multiple files (e.g., `src/app/api/recipes/route.ts:89`, `src/app/api/recipes/[id]/route.ts:24`)

- **Impact:** Confusion for frontend consumers; potential bugs when refactoring.

- **Issue:** Framer Motion wrapper creation uses two different patterns: `motion(Box)` and `motion.create(Box)`.
- **Impact:** Code style inconsistency; both work but it's confusing.

**[CR-019]** `global-error.tsx` doesn't import `React` explicitly

- **File:** `src/app/global-error.tsx`
- **Issue:** File uses JSX but doesn't import React. This works with the automatic JSX runtime but is inconsistent with other files that do import React.
- **Impact:** Style inconsistency only.
- **Suggested fix:** Either add `import React from 'react'` or remove it from files that don't need it — pick one convention.

**[CR-020]** `sitemap.ts` returns `lastModified: new Date()` which changes on every request

- **File:** `src/app/sitemap.ts:8`
- **Issue:** `lastModified` is set to `new Date()` which means every time the sitemap is generated, the date changes, potentially causing search engines to re-crawl unchanged pages.
- **Impact:** Unnecessary crawl budget consumption.
- **Suggested fix:** Use a fixed date or derive from actual content modification timestamps.
