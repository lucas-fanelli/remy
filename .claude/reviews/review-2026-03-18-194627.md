## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing application with clean architecture. Generally well-structured with proper DI container, repository pattern, and service layers. However, fragile error-message routing in API routes, inconsistent validation across endpoints, a 900+ line navigation component, and several silent error-swallowing patterns create real risk.

### Findings

#### CRITICAL

**[CR-001]** Error-message string matching determines HTTP status codes in recipe API routes

- **File:** `src/app/api/recipes/[id]/route.ts:96-105, 147-156`
- **Issue:** PUT and DELETE handlers use `error.message.includes('not authorized')` / `includes('permission')` to decide between 403, 404, and 500. If the service layer message changes even slightly (e.g., capitalization, rewording), the API silently returns 500 instead of the correct status.
- **Impact:** Any refactor to `RecipeService` error messages breaks HTTP status mapping without any compile-time or test-time signal. Clients get 500 for permission errors.
- **Suggested fix:** Use typed error classes instead of message matching:

```typescript
// domain/errors.ts
export class NotFoundError extends Error {
  constructor(msg: string) {
    super(msg);
    this.name = 'NotFoundError';
  }
}
export class ForbiddenError extends Error {
  constructor(msg: string) {
    super(msg);
    this.name = 'ForbiddenError';
  }
}

// In route handler:
if (error instanceof ForbiddenError)
  return NextResponse.json({ error: error.message }, { status: 403 });
if (error instanceof NotFoundError)
  return NextResponse.json({ error: error.message }, { status: 404 });
```

**[CR-002]** General upload endpoint missing Content-Type validation

- **File:** `src/app/api/upload/route.ts:17-28`
- **Issue:** Unlike `upload/avatar/route.ts` which validates `Content-Type: multipart/form-data`, the general upload route calls `request.formData()` without checking. Non-multipart requests cause an unhandled parse error that leaks implementation details in the 500 response.
- **Impact:** Malformed requests expose internal error messages. The `upload/avatar/route.ts` has this check but `upload/route.ts` doesn't — inconsistency suggests oversight.
- **Suggested fix:** Add the same check from avatar upload:

```typescript
const contentType = request.headers.get('content-type');
if (!contentType || !contentType.includes('multipart/form-data')) {
  return NextResponse.json({ error: 'Expected multipart/form-data' }, { status: 400 });
}
```

#### HIGH

**[CR-003]** `extractBearerToken` name is misleading — reads httpOnly cookie, not Bearer header

- **File:** `src/lib/utils/auth.ts:7-9`
- **Issue:** Function is named `extractBearerToken` but reads `request.cookies.get('auth_token')`. Every call site reads this name and assumes it processes an `Authorization: Bearer` header. After the migration to httpOnly cookies, the name was not updated.
- **Impact:** Misleads developers. New contributors may add Bearer header logic thinking it's missing, or may not find the auth extraction when searching for "cookie".
- **Suggested fix:** Rename to `extractAuthToken` and update all import sites.

**[CR-004]** `updateRecipe` skips all validation, unlike `createRecipe`

- **File:** `src/infrastructure/services/RecipeService.ts:36-50`
- **Issue:** `createRecipe` calls `validateRecipeData()` which enforces title length (100), description length (500), cooking time bounds, servings bounds, ingredient completeness, and instruction ordering. `updateRecipe` passes data directly to the repository with zero validation.
- **Impact:** A PUT request with `cookingTime: -999`, `servings: 0`, or `title: 'a'.repeat(10000)` goes straight to the database. The database schema may or may not enforce these constraints — if it doesn't, invalid data persists.
- **Suggested fix:** Add validation in `updateRecipe` for any field that is provided:

```typescript
async updateRecipe(id: string, userId: string, data: UpdateRecipeDTO): Promise<Recipe> {
  if (data.title !== undefined && data.title.length > 100) throw new Error('...');
  if (data.cookingTime !== undefined && data.cookingTime <= 0) throw new Error('...');
  // ... etc
}
```

**[CR-005]** Empty catch blocks silently swallow all errors including infrastructure failures

- **File:** `src/app/api/users/[username]/recipes/route.ts:30`, `src/app/api/users/[username]/stats/route.ts:24`
- **Issue:** `try { tokenService.verify(token); } catch {}` catches **all** exceptions, including unexpected errors like `TypeError` from a misconfigured DI container. The intent is "optional auth" but the implementation masks real bugs.
- **Impact:** If `container.getTokenService()` throws because of a configuration issue, the endpoint silently treats the user as unauthenticated instead of failing fast. Bug goes undetected.
- **Suggested fix:**

```typescript
try {
  const tokenService = container.getTokenService();
  const payload = tokenService.verify(token);
  if (payload) currentUserId = payload.userId;
} catch (error) {
  // Expected: JWT verification errors (expired, malformed)
  // Unexpected: DI errors — log them
  if (
    !(error instanceof Error) ||
    !['JsonWebTokenError', 'TokenExpiredError'].includes(error.name)
  ) {
    console.error('Unexpected token verification error:', error);
  }
}
```

Note: `src/app/api/users/[username]/profile/route.ts:65-76` already does this correctly — follow that pattern.

**[CR-006]** Unfollow endpoint uses separate non-atomic queries

- **File:** `src/app/api/users/[username]/unfollow/route.ts:41-47`
- **Issue:** `deleteMany` and then `follow.count` are two separate queries. The follow endpoint uses `$transaction` for atomicity, but unfollow does not. The returned `followersCount` could be stale.
- **Impact:** The UI could display incorrect follower counts, especially under concurrent access.
- **Suggested fix:** Wrap in `$transaction`:

```typescript
const [result, followersCount] = await prisma.$transaction([
  prisma.follow.deleteMany({
    where: { followerId: payload.userId, followingId: userToUnfollow.id },
  }),
  prisma.follow.count({ where: { followingId: userToUnfollow.id } }),
]);
```

**[CR-007]** Pantry item update allows unbounded `notes` and `category` fields

- **File:** `src/app/api/pantry/[id]/route.ts:47-82`
- **Issue:** The PUT endpoint validates `name` length (`MAX_ITEM_NAME_LENGTH`) and `quantity` bounds (`MAX_QUANTITY`) but does not validate `notes` length or `category` length. Meanwhile, `src/app/api/cooked-recipes/route.ts:87` validates `notes` against `MAX_NOTES_LENGTH`.
- **Impact:** An attacker can store multi-megabyte strings in the `notes` or `category` fields, causing database bloat and slow queries.
- **Suggested fix:** Add length checks:

```typescript
if (notes !== undefined && notes !== null && notes.length > MAX_NOTES_LENGTH) {
  return NextResponse.json(
    { error: `Notes must be ${MAX_NOTES_LENGTH} characters or less` },
    { status: 400 }
  );
}
if (category !== undefined && category !== null && category.length > MAX_ITEM_NAME_LENGTH) {
  return NextResponse.json({ error: 'Category name too long' }, { status: 400 });
}
```

#### MEDIUM

**[CR-008]** Navigation component is 900+ lines with 6+ responsibilities

- **File:** `src/components/Navigation.tsx:1-900+`
- **Issue:** Handles desktop nav, mobile nav, drawer menu, search dialog, notification dropdown, recipe creation dialog, tab management, and notification polling. This is well beyond any reasonable single-component scope.
- **Impact:** Any change to navigation risks regressions across all features. Test file is 1800+ lines. Cognitive load for contributors is high.
- **Suggested fix:** Extract into: `DesktopNavBar`, `MobileNavBar`, `MobileDrawer`, `NotificationDropdown`, `CreateRecipeDialog`. Keep `Navigation` as a thin coordinator.

**[CR-009]** Admin page auth pattern duplicated across 3 pages

- **File:** `src/app/admin/comments/page.tsx:57-72`, `src/app/admin/recipes/page.tsx:70-85`, `src/app/admin/users/page.tsx:77-91`
- **Issue:** All three admin pages repeat the same `authLoading` / `isAdmin` / `useEffect` redirect pattern with identical comments. The comments and recipes pages are copy-paste of each other.
- **Impact:** If the auth check logic needs updating (e.g., adding a toast on redirect), 3 files must be changed in lockstep.
- **Suggested fix:** Extract into a `useAdminGuard()` hook or a `withAdminAuth()` HOC.

**[CR-010]** `insufficientIngredients` returned from cooked-recipes API is never displayed to users

- **File:** `src/app/api/cooked-recipes/route.ts:160-164`, `src/app/recipe/[id]/page.tsx:329-352`
- **Issue:** The API calculates and returns `insufficientIngredients` with detailed info (name, required, available, unit). The client (`handleMarkAsCooked`) only shows a generic success/error message and ignores this data entirely.
- **Impact:** Users don't know their pantry deduction was partial. If they had 100g of flour but the recipe needed 200g, all 100g is silently deducted and the user is never informed.
- **Suggested fix:** Display `insufficientIngredients` in the success snackbar, e.g., "Recipe marked as cooked! Note: insufficient flour (had 100g, needed 200g)."

**[CR-011]** Notification mark-as-read uses two separate non-atomic queries

- **File:** `src/app/api/notifications/[id]/route.ts:33-48`
- **Issue:** `findFirst` then `update` are not wrapped in a transaction. If the notification is deleted between the two queries, the update throws an unhandled Prisma error.
- **Impact:** Rare race condition returns 500 instead of 404 to the client.
- **Suggested fix:** Use `updateMany` with ownership check in a single query, or wrap in `$transaction`.

**[CR-012]** Recipe match excludes ingredients shorter than 3 characters after normalization

- **File:** `src/app/api/recipes/match/route.ts:79-81`
- **Issue:** `.filter((n) => n.length >= 3)` excludes normalized ingredient names under 3 chars. After normalization, "rye" stays 3 chars (passes), but "ox" or "go" (2 chars) would be excluded. More critically, if normalization strips a suffix (e.g., "gins" → "gin" is fine, but hypothetical edge cases could truncate below 3).
- **Impact:** Users with short-named pantry items may not see matching recipes.
- **Suggested fix:** Lower threshold to 2, or document the limitation.

**[CR-013]** Pantry POST `category` field not length-validated

- **File:** `src/app/api/pantry/route.ts:62-100`
- **Issue:** The POST endpoint validates `name` and `quantity` but accepts any `category` string without length bounds. Same issue as CR-007 but for the create path.
- **Impact:** Unbounded string stored in database.
- **Suggested fix:** Add `if (category && category.length > MAX_ITEM_NAME_LENGTH)` validation.

#### LOW

**[CR-014]** Hardcoded tech stack in about page

- **File:** `src/app/about/page.tsx:66-77`
- **Issue:** The `techStack` array is hardcoded directly in the component. It will drift from reality as dependencies change.
- **Impact:** Misleading information shown to users.
- **Suggested fix:** Move to `config/branding.ts` alongside other branding constants, or auto-generate from `package.json`.

**[CR-015]** Rate limit map entries from one-time visitors never cleaned until bulk threshold

- **File:** `src/middleware.ts:78-92`
- **Issue:** Expired rate limit entries are cleaned on individual access and when map size exceeds 500. IPs that visit once and never return accumulate until the 500-entry threshold triggers bulk cleanup.
- **Impact:** Minor memory leak in long-running servers with diverse traffic below 500 unique IPs per 15-minute window. Negligible in practice but not zero.
- **Suggested fix:** Add a periodic cleanup interval, or clean expired entries probabilistically on each request (e.g., 1% chance to scan for expired entries).

**[CR-016]** `getDifficultyColor` default case returns `'default'` without logging

- **File:** `src/lib/utils/recipe.ts:14-23`
- **Issue:** Unknown difficulty values silently fall through to `'default'` color. If a new difficulty level is added to the schema without updating this function, it renders with the wrong color.
- **Impact:** Visual inconsistency, not a bug. But it could be caught earlier with a `console.warn` in development.
- **Suggested fix:** Add a dev-only warning for unknown difficulty values.
