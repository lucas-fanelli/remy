## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured, but several security gaps, race conditions, and data integrity issues exist across API routes and client components.

### Findings

#### CRITICAL

**[CR-001]** Cooked recipe DELETE does not restore fully-consumed pantry items, silently losing data

- **File:** `src/app/api/cooked-recipes/route.ts:232-236`
- **Issue:** When a pantry item is fully consumed (quantity reaches 0, item deleted), the DELETE handler cannot restore it because the `pantryId` is unknown. The comment acknowledges this but treats it as acceptable. However, this means undoing a "mark as cooked" silently loses pantry items with no user notification.
- **Impact:** Users lose pantry data permanently when they undo a cooked recipe that fully consumed ingredients. No error or warning is shown.
- **Suggested fix:** Store the `pantryId` in `deductedIngredients` alongside `pantryItemId`, or look up the user's pantry and recreate deleted items:

```typescript
if (!existingItem) {
  const pantry = await tx.userPantry.findUnique({ where: { userId: user.id } });
  if (pantry) {
    await tx.pantryItem.create({
      data: { pantryId: pantry.id, name: d.name, quantity: d.amount, unit: d.unit },
    });
  }
}
```

**[CR-002]** Recipe match endpoint vulnerable to denial-of-service via CPU exhaustion

- **File:** `src/app/api/recipes/match/route.ts:140-170`
- **Issue:** The matching loop has a 4-second wall-clock limit and 50,000 comparison cap, but these are per-request limits with no per-user rate limiting on this specific endpoint. The middleware rate limit is 30 requests per 15-minute window, but 30 concurrent requests each burning 4 seconds of CPU can still overwhelm a single-instance server.
- **Impact:** An authenticated user can send 30 requests in rapid succession, each consuming up to 4 seconds of CPU, degrading service for all users.
- **Suggested fix:** Add a per-user concurrent request guard (e.g., advisory lock or in-memory semaphore) so only one match request per user runs at a time.

**[CR-003]** Upload endpoints lack per-user ownership tracking — any authenticated user can reference any uploaded image

- **File:** `src/app/api/upload/route.ts:16-19`
- **Issue:** The TODO comment acknowledges this. Any authenticated user who knows a Cloudinary URL (or can enumerate them) can set it as their recipe image. While Cloudinary URLs contain random public IDs, this is security-by-obscurity.
- **Impact:** An attacker could reference another user's uploaded image in their own recipe, or use an image that was uploaded as part of a comment on someone else's recipe.
- **Suggested fix:** Create an `Upload` table mapping `publicId -> userId`, and validate ownership in recipe/comment creation routes.

#### HIGH

**[CR-004]** Admin user DELETE has a race window where new posts can be created between image collection and cascade delete

- **File:** `src/app/api/admin/users/[id]/route.ts:62-72`
- **Issue:** Comments in the code acknowledge a race window between collecting image URLs and the cascade delete. Posts created in this window will have their DB records deleted but their Cloudinary images orphaned.
- **Impact:** Cloudinary storage leak. The cleanup script mitigates this, but only if it's actually scheduled.
- **Suggested fix:** Use a `SELECT ... FOR UPDATE` on the user row before collecting images, or move image collection to a post-delete audit log trigger.

**[CR-005]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:160-167`
- **Issue:** When `loadRecipes(reset=false)` appends recipes, it filters duplicates against existing IDs. But when filters change, `loadRecipes(true)` resets completely. If a user scrolls, changes a filter, then changes back, the `recipesLengthRef` and `pageRef` are reset but the stale request check (`thisRequestId !== requestIdRef.current`) can let old responses through in edge cases where the abort doesn't fire before the response arrives.
- **Impact:** Potential duplicate recipe cards or lost scroll position.
- **Suggested fix:** The abort controller pattern is good, but add a guard to also check `reset` flag consistency:

```typescript
if (thisRequestId !== requestIdRef.current) return;
```

This exists but should also verify the `reset` parameter matches expectations.

**[CR-006]** Notification polling hook doesn't abort in-flight `/api/auth/me` on unmount

- **File:** `src/hooks/useNotificationPolling.ts:100-108`
- **Issue:** The `meAbortRef` is created but the cleanup in the polling effect only aborts `notificationAbortRef` and `meAbortRef`. However, if the component unmounts while the `/api/auth/me` confirmation is in-flight, `isMountedRef` prevents state updates but the fetch itself still completes and calls `onAuthInvalid()` which triggers logout.
- **Impact:** User could be logged out after navigating away from a page due to a stale 401 confirmation completing after unmount.
- **Suggested fix:** Check `isMountedRef.current` before calling `onAuthInvalid()`:

```typescript
if (meResp.status === 401 && isMountedRef.current) {
```

This is already present at line 104 — actually this is fine. The issue is the `catch` block at line 108 doesn't check `isMountedRef` before `setIsPollingPaused`. Wait, it does check at the top of catch. This is actually handled. Withdrawing this finding.

**[CR-007]** `striptags` is used for XSS prevention but does not handle attribute injection

- **File:** `src/app/api/cooked-recipes/route.ts:7`, `src/app/api/pantry/route.ts:3`, multiple routes
- **Issue:** `striptags` strips HTML tags but doesn't sanitize attribute-based XSS vectors in contexts where the output might be rendered in HTML attributes. For example, a note like `" onmouseover="alert(1)` would pass through striptags unchanged.
- **Impact:** If any of these values are ever rendered in an HTML attribute context without proper escaping, XSS is possible. React's JSX escaping mitigates this for the current frontend, but API consumers or future SSR changes could be vulnerable.
- **Suggested fix:** Use DOMPurify for server-side sanitization, or ensure all outputs go through React's JSX escaping (which they currently do). Document this assumption explicitly.

**[CR-008]** Comment deletion deletes associated rating without checking if rating was from cooked-recipe flow

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:134-156`
- **Issue:** When a comment is deleted, the associated rating is also deleted and averageRating is recalculated. But if the user also rated via the cooked-recipe flow, deleting the comment would delete the shared rating record, losing the cooked-recipe rating.
- **Impact:** Users who both commented with a rating and marked a recipe as cooked will lose their rating when they delete their comment.
- **Suggested fix:** The cooked-recipe DELETE handler (line 224) checks for this in the reverse direction but the comment DELETE handler doesn't. Add a similar check:

```typescript
const cookedRecipe = await tx.cookedRecipe.findFirst({
  where: { userId: user.id, postId: recipeId },
});
if (!cookedRecipe) {
  await tx.rating.deleteMany({ where: { userId: user.id, postId: recipeId } });
  // recalculate...
}
```

#### MEDIUM

**[CR-009]** Footer contact form is vulnerable to mailto: link length overflow on some clients

- **File:** `src/components/Footer.tsx:67-74`
- **Issue:** The 1500-character limit on the mailto link is checked after encoding, which is correct, but the `window.open` call with `_blank` may be blocked by popup blockers. The `sending` state is set to `true` and only reset after 3 seconds via `setTimeout`, during which the user cannot retry.
- **Impact:** If the mailto link fails to open (popup blocker), the user sees no error and the button is disabled for 3 seconds.
- **Suggested fix:** Use `window.location.href = mailtoLink` instead of `window.open` to avoid popup blockers, and detect whether the mailto actually opened.

**[CR-010]** Admin stats cache is never invalidated by organic activity

- **File:** `src/infrastructure/services/AdminService.ts:18-20`
- **Issue:** The stats cache comment acknowledges this: "Organic activity (new user signups, recipe creation, likes, comments) will not appear in stats until the TTL expires." With a 10-second TTL this is acceptable, but the comment about serverless environments having low hit rates means the cache provides almost no benefit in production (Vercel).
- **Impact:** Wasted code complexity for near-zero benefit in serverless deployment.
- **Suggested fix:** Either remove the cache (simplify code) or replace with Redis/Upstash for actual caching benefit.

**[CR-011]** `EditProfileModal` doesn't validate website URL for `javascript:` protocol

- **File:** `src/components/profile/EditProfileModal.tsx:128-137`
- **Issue:** Client-side validation checks for `http://` or `https://` prefix, but the `new URL()` constructor would accept `javascript:alert(1)` as a valid URL. The server-side `UserService.updateProfile` validates protocol correctly, but the client-side validation has a gap.
- **Impact:** Low — server-side validation catches it. But the client-side error message would be confusing ("Website must start with http:// or https://") vs a URL parse error.
- **Suggested fix:** Check protocol after `new URL()`:

```typescript
if (!['http:', 'https:'].includes(url.protocol)) {
  setFormErrors({ website: 'Website must use http:// or https://' });
  return;
}
```

**[CR-012]** Pantry item PUT endpoint allows setting quantity to 0 via `-0`

**[CR-014]** Search API exposes user IDs in `/api/search/route.ts` but strips them in `/api/users/search/route.ts`

- **File:** `src/app/api/search/route.ts:38-40`
- **Issue:** The `/api/search` route strips email from user results but the comment says "defense-in-depth" for email. However, it doesn't strip `id` from the user results. The `/api/users/search` route strips both `email` and `id`. Inconsistent behavior.
- **Impact:** User IDs are exposed through the search endpoint. While UUIDs aren't directly exploitable, consistent data minimization is better practice.
- **Suggested fix:** Strip `id` from search results in `/api/search/route.ts` to match `/api/users/search`:

```typescript
const users = (await userService.searchUsers(query.trim(), limit, offset)).map((u) => ({
  username: u.username,
  fullName: u.fullName,
  avatar: u.avatar,
  bio: u.bio,
}));
```

This is already done. The actual mismatch is that `/api/users/search` also strips `id` via destructuring. Both are consistent. Withdrawing — the search route already only returns `username, fullName, avatar, bio`.

**[CR-015]** `RecipeCard` image fallback chain silently hides broken images with no user feedback

**[CR-016]** `handleMarkAsCooked` in recipe detail page doesn't invalidate React Query cache

- **File:** `src/app/recipe/[id]/page.tsx:276-314`
- **Issue:** After marking a recipe as cooked (which updates ratings), the React Query cache for the recipe is not invalidated. The rating display will be stale until the user navigates away and back.
- **Impact:** User marks recipe as cooked with a rating, but the displayed average rating doesn't update.
- **Suggested fix:** Add `queryClient.invalidateQueries({ queryKey: ['recipe', recipeId] })` after successful cook:

```typescript
if (response.ok) {
  queryClient.invalidateQueries({ queryKey: ['recipe', recipeId] });
  // ... existing snackbar code
}
```
