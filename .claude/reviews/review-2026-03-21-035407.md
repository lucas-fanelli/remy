## Code Review — 2026-03-21

### Summary

Three API route files with transaction-heavy logic. Several critical issues found around race conditions, data integrity, and security.

### Findings

#### CRITICAL

**[CR-001]** Recipe creation uses two separate persistence mechanisms that are not in the same transaction

- **File:** `src/app/api/recipes/route.ts:193-206`
- **Issue:** The advisory lock + daily limit check runs inside `prisma.$transaction`, but `recipeService.createRecipe(recipeData)` is called inside that same transaction callback using the _outer_ `prisma` instance (via the container service), not the transactional `tx` client. The service likely uses its own `prisma` import, so the recipe creation happens outside the transaction's isolation. If `createRecipe` fails after the transaction commits the lock release, or if it uses a different connection, the daily limit check and the actual insert are not atomic.
- **Impact:** A user can bypass the daily recipe limit via concurrent requests — the count check passes on both, then both create recipes outside the transaction boundary.
- **Suggested fix:** Pass `tx` to the service method, or move the `post.create` call directly into the transaction:

```typescript
const recipe = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(...)`;
  // ... daily limit check with tx ...
  return tx.post.create({ data: recipeData });
});
```

**[CR-002]** Pantry restoration logic inverted — restores items for OLD cooks, blocks restoration for RECENT ones

- **File:** `src/app/api/cooked-recipes/route.ts:238-240`
- **Issue:** The condition `if (cookedRecipe.deductedIngredients && !isRecentCook)` only restores pantry items when the cook is _older_ than 1 hour. The comment says this prevents a "cook → delete → repeat" exploit, but the logic is backwards: it should restore for recent deletes (user changed their mind) and _not_ restore for old ones (ingredients already consumed). As written, a user who immediately realizes they made a mistake gets no restoration, while someone deleting a week-old entry gets phantom ingredients back.
- **Impact:** Data integrity bug. Users get incorrect pantry quantities — ingredients materialize from old cooks, and legitimate undo within minutes doesn't work.
- **Suggested fix:** Invert the condition to restore only recent cooks:

```typescript
if (cookedRecipe.deductedIngredients && isRecentCook) {
```

**[CR-003]** `DELETE /api/cooked-recipes` does not require `Content-Type` or CSRF header validation

- **File:** `src/app/api/cooked-recipes/route.ts:218`
- **Issue:** The comment on line 216 claims "CSRF protection: middleware requires X-Requested-With header on mutating requests," but DELETE requests using query parameters (not a JSON body) are commonly exempt from such middleware checks since they look like simple GET-style requests. If the middleware only checks `Content-Type: application/json` or only validates POST/PUT, this DELETE is unprotected. The route takes a destructive action (deletes data, restores pantry items) based solely on a cookie-authenticated session with no CSRF token.
- **Impact:** CSRF attack — a malicious page can trigger `DELETE /api/cooked-recipes?id=<known-id>` via a form submission or fetch, deleting the user's cooked recipe and corrupting pantry quantities.
- **Suggested fix:** Verify the middleware explicitly covers DELETE methods. If not, add explicit CSRF header validation in the handler:

```typescript
if (!request.headers.get('x-requested-with')) {
  return NextResponse.json({ error: 'Forbidden' }, { status: 403 });
}
```

**[CR-004]** Raw SQL query in match route is vulnerable to JSON array element injection via recipe ingredient names

- **File:** `src/app/api/recipes/match/route.ts:90-99`
- **Issue:** The `LIKE ANY` query matches against `lower(elem->>'name')` where `elem` comes from user-created recipe data (`p.ingredients` JSON column). While the _pantry names_ are parameterized via `Prisma.join`, the recipe ingredient names stored in the DB are not sanitized at creation time (the schema allows any string up to 200 chars). A malicious user can create a recipe with an ingredient name containing control characters or crafted patterns that, combined with `LIKE`, cause excessive backtracking or unexpected matches. More critically, `jsonb_array_elements` on malformed JSON could cause query errors for all users.
- **Impact:** A single malicious recipe with a crafted ingredients array can degrade match performance for every user or cause query failures.
- **Suggested fix:** Add a `jsonb_array_length` upper bound (already present — good), but also validate ingredient name format at recipe creation time with a regex pattern, and add a `length()` guard in the SQL:

```sql
WHERE lower(elem->>'name') LIKE ANY(...) AND length(elem->>'name') <= 200
```

**[CR-005]** Account deletion awaits Cloudinary cleanup — serverless timeout risk with unbounded image count

- **File:** `src/app/api/users/profile/route.ts:85-90`
- **Issue:** `Promise.allSettled(imageUrls.map(url => cleanupCloudinaryImage(url)))` is awaited. A user with hundreds of posts/comments will trigger hundreds of parallel HTTP requests to Cloudinary. In a serverless environment (Vercel), the function has a timeout (typically 10-60s). If the cleanup takes too long, the response never reaches the client, even though the DB deletion already committed. The user sees an error but their account is actually deleted — they can't retry and can't log in.
- **Impact:** Data loss UX — user believes deletion failed, but their account and all data are gone. Additionally, hundreds of concurrent outbound requests can exhaust connection limits.
- **Suggested fix:** Fire-and-forget the cleanup (or batch it), and return the response immediately:

```typescript
// Don't await — the user record is already deleted
Promise.allSettled(imageUrls.map((url) => cleanupCloudinaryImage(url))).then((results) => {
  const failures = results.filter((r) => r.status === 'rejected');
  if (failures.length > 0) logServerError('Cleanup failures', failures);
});
const response = ApiResponseHelper.success(null, 'Account deleted successfully');
```
