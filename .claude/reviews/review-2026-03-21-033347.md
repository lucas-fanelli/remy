## Code Review — 2026-03-21

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured with good security practices (httpOnly cookies, CSRF protection, advisory locks). However, several critical and high-severity issues exist around race conditions, missing input validation, and potential denial-of-service vectors.

### Findings

#### CRITICAL

**[CR-001]** Unbounded `striptags` import used without HTML entity decoding — stored XSS via entities

- **File:** `src/app/api/cooked-recipes/route.ts:8`, `src/app/api/pantry/route.ts:3`, multiple routes
- **Issue:** `striptags` strips HTML tags but does NOT decode HTML entities. An attacker can inject `&lt;script&gt;alert(1)&lt;/script&gt;` which passes striptags unchanged, and if any consumer renders with `dangerouslySetInnerHTML` or a non-React renderer, it executes. The comment in `RecipeService.ts:5` acknowledges this but dismisses it.
- **Impact:** Stored XSS if any rendering path ever uses raw HTML (email notifications, PDF export, SSR meta tags).
- **Suggested fix:** Use DOMPurify server-side or decode entities after stripping: `import { decode } from 'html-entities'; const clean = decode(striptags(input));`

**[CR-002]** `deductPantryItems` has no transaction-level lock before reading pantry — concurrent cooks can over-deduct

- **File:** `src/app/api/cooked-recipes/route.ts:153-157`
- **Issue:** The advisory lock is acquired at line 153 using `hashtext(user.id)`, but `pantryItems` is passed as a parameter read _outside_ the `deductPantryItems` function. If two requests read the same pantry state before either acquires the lock, the second request operates on stale data. The lock is inside the transaction, but the pantry read at line 158 happens after the lock — this is actually correct. However, the `deductPantryItems` function receives `pantryItems` as a pre-read parameter, not a fresh read inside the lock.
- **Impact:** Race condition: two concurrent "mark as cooked" requests for the same user could deduct the same pantry items twice, producing negative quantities (which are deleted, losing items permanently).
- **Suggested fix:** Read pantry inside `deductPantryItems` after the lock is held, not before. Pass `tx` and `userId` instead of pre-fetched `pantryItems`.

**[CR-003]** Recipe match endpoint loads all candidate recipes into memory with no streaming

- **File:** `src/app/api/recipes/match/route.ts:120-160`
- **Issue:** Up to 200 candidate recipes are loaded into memory, then all ingredients are compared in nested loops with a 20,000 comparison cap. Each recipe's full `ingredients` JSON is loaded. With 200 recipes × 100 ingredients each, this is up to 20,000 objects in memory per request.
- **Impact:** Under concurrent load (multiple users matching simultaneously), this can cause Node.js heap exhaustion and OOM kills. The advisory lock serializes per-user, but doesn't limit total concurrent users.
- **Suggested fix:** Add a global concurrency semaphore (e.g., max 10 concurrent match operations) or move matching logic to the database with a SQL query that computes match percentages.

**[CR-004]** Admin user delete collects images before cascade delete — TOCTOU window for orphaned images

- **File:** `src/app/api/admin/users/[id]/route.ts:81-93`
- **Issue:** The code collects user post/comment images, then deletes the user (cascade deletes posts/comments). Between the image collection queries and the `user.delete`, new posts/comments could be created. The comment acknowledges this ("small race window") but the orphaned images are a data integrity issue.
- **Impact:** Cloudinary images accumulate without cleanup. The script `cleanup-orphaned-images.ts` exists but is not automatically scheduled — it requires manual cron setup that may be forgotten.
- **Suggested fix:** Use `RETURNING` clause or a database trigger to capture deleted image URLs atomically. Alternatively, use `ON DELETE` hooks in Prisma.

#### HIGH

**[CR-005]** `parseAmount` returns `NaN` for non-numeric strings but callers use `isNaN` check inconsistently

- **File:** `src/lib/utils/ingredients.ts:6`
- **Issue:** `parseAmount("to taste")` returns `NaN`, and in `deductPantryItems` (cooked-recipes/route.ts:67) the check `if (isNaN(recipeAmount) || recipeAmount <= 0) continue;` handles it, but `parseFloat("")` returns `NaN` too. The issue is that `parseFloat("2 cups")` returns `2` (ignoring trailing text), which could lead to incorrect deductions if amount strings contain units.
- **Impact:** Incorrect pantry deductions if ingredient amount strings are malformed (e.g., "2 cups" stored as amount instead of "2").
- **Suggested fix:** Add strict numeric validation: `if (!/^[\d./]+$/.test(trimmed)) return NaN;`

**[CR-006]** No rate limiting on the cooked-recipes DELETE endpoint for pantry restoration abuse

- **File:** `src/app/api/cooked-recipes/route.ts:208-290`
- **Issue:** The DELETE endpoint restores pantry items from `deductedIngredients`. An attacker could repeatedly create and delete cooked recipes to inflate pantry quantities beyond what they actually have, since the restoration logic recreates deleted pantry items.
- **Impact:** Pantry quantity manipulation — a user could cook a recipe (deducting items) then delete it (restoring items) repeatedly to duplicate pantry items.
- **Suggested fix:** Add a rate limit to cooked recipe deletions, or add a cooldown period before pantry restoration is allowed.

**[CR-007]** `maskEmail` doesn't handle edge cases — single-character local parts leak the full character

- **File:** `src/app/api/admin/users/[id]/route.ts:21-29`, `src/infrastructure/services/AdminService.ts:10-19`
- **Issue:** For email `a@b.com`, `maskedLocal` becomes `a**` which still reveals the full local part. For very short domains like `a.co`, the domain name is fully visible.
- **Impact:** Email enumeration through admin endpoints — admins can partially reconstruct user emails.
- **Suggested fix:** For local parts ≤ 2 characters, mask entirely: `const maskedLocal = local.length <= 2 ? '***' : local[0] + '*'.repeat(...)`.

**[CR-008]** `escapeLike` in recipe match doesn't escape backslashes correctly for all PostgreSQL drivers

- **File:** `src/app/api/recipes/match/route.ts:21-23`
- **Issue:** The escape function replaces `\` with `\\\\` (4 backslashes). With Prisma's tagged template literals and PostgreSQL's `ESCAPE '\'` clause, the actual number of escapes needed depends on the string processing layers. Over-escaping may cause legitimate ingredient names containing backslashes to fail to match.
- **Impact:** Potential false negatives in recipe matching for ingredient names with special characters.
- **Suggested fix:** Test with actual PostgreSQL to verify the escape chain. Consider using `ILIKE` with proper parameterization instead of manual escaping.

**[CR-009]** Notification polling has no maximum backoff for circuit breaker resets

- **File:** `src/hooks/useNotificationPolling.ts:142-148`
- **Issue:** `breakerTripCountRef` is capped at 10, but the cooldown formula `5min * 2^(tripCount-1)` at tripCount=10 is `5 * 512 = 2560 minutes`, far exceeding the 30-minute cap. The Math.min catches this, but the comment says "which would yield 2560min" suggesting the author expected it to happen. The real issue: after 30 minutes of cooldown, the breaker resets and immediately re-trips if the server is still down, creating a loop of 30-minute waits with no notification to the user that polling is effectively dead.
- **Impact:** Users lose notifications silently for extended periods with no UI indication beyond the initial "paused" state.
- **Suggested fix:** After N consecutive breaker trips (e.g., 3), show a persistent banner: "Notifications unavailable. Please refresh."

**[CR-010]** `cleanupCloudinaryImage` silently swallows all errors including auth failures

- **File:** `src/lib/utils/cloudinary-cleanup.ts:9`
- **Issue:** `.catch(() => {})` swallows every error, including Cloudinary API key misconfiguration or rate limiting. Failed cleanups are never retried or logged.
- **Impact:** Orphaned images accumulate silently if Cloudinary credentials are invalid or expired.
- **Suggested fix:** Log the error: `.catch((err) => logServerError('Cloudinary cleanup failed:', err))`.

#### MEDIUM

**[CR-011]** `features` array in about page is defined outside the component — prevents tree-shaking

- **File:** `src/app/about/page.tsx:26-62`
- **Issue:** The `features` array and `techStack` destructuring are module-level constants. While not a bug, they prevent Next.js from tree-shaking the MUI icon imports if the page is never rendered.
- **Impact:** Slightly larger bundle size. Minor.
- **Suggested fix:** Move inside the component or use dynamic imports for icons.

**[CR-012]** Duplicate `maskEmail` function defined in two files

- **File:** `src/app/api/admin/users/[id]/route.ts:21`, `src/infrastructure/services/AdminService.ts:10`
- **Issue:** Identical `maskEmail` function copied in two places. If one is updated, the other may not be.
- **Impact:** Maintenance burden, potential inconsistency in email masking behavior.
- **Suggested fix:** Extract to a shared utility: `src/lib/utils/mask.ts`.

**[CR-013]** `RecipeFeed` uses `useRef` for pagination state but `useState` for `hasMore` — inconsistent state management

- **File:** `src/components/recipe/RecipeFeed.tsx:45-48`
- **Issue:** `pageRef` and `recipesLengthRef` are refs (not reactive), but `hasMore` is state. When `hasMore` changes, it triggers a re-render, but changes to `pageRef` don't. This creates a subtle inconsistency where the sentinel IntersectionObserver may fire based on stale `hasMore` state while `pageRef` has already been updated.
- **Impact:** Potential double-fetch or missed pagination in edge cases.
- **Suggested fix:** Use either all refs or all state for pagination control. If using refs, check `hasMore` via a ref too.

**[CR-014]** `Footer` component stores `sendingTimeoutRef` but doesn't clear it on contact form re-open

- **File:** `src/components/Footer.tsx:35-38`
- **Issue:** If the user opens the contact dialog, clicks send, then quickly reopens and clicks send again before the 3-second timeout clears `sending`, the second send will be blocked. The timeout ref is cleared on unmount but not on dialog close.
- **Impact:** Minor UX issue — user may be unable to send a second contact email within 3 seconds.
- **Suggested fix:** Clear the timeout in `handleCloseContact`.

**[CR-015]** `PersistentSearchBar` creates a new `AbortController` on every query change but doesn't abort the outer one

- **File:** `src/components/search/PersistentSearchBar.tsx:131-159`
- **Issue:** The `useEffect` cleanup aborts `controller`, and the effect body aborts `searchAbortRef.current`. But `searchAbortRef.current` is only assigned inside `setTimeout`, so if the effect reruns before the timeout fires, the previous controller is never aborted (the ref still points to the old one from the previous setTimeout that did fire).
- **Impact:** In rapid typing scenarios, multiple in-flight search requests may exist simultaneously, wasting bandwidth.
- **Suggested fix:** Abort `searchAbortRef.current` at the top of the effect, not just the new `controller` in cleanup.

**[CR-016]** Admin comments page shows user emails in the table — potential PII exposure

- **File:** `src/app/admin/comments/page.tsx:133`
- **Issue:** The admin comments table displays `comment.user.email` directly. While the backend masks emails via `AdminService`, the interface type `AdminComment` includes `email` as a string, and the API returns masked emails. But the frontend TypeScript type suggests full emails are expected.
- **Impact:** If the masking is ever removed server-side, emails would be exposed to any admin.
- **Suggested fix:** Remove email from the `AdminComment` interface on the client side, or rename to `maskedEmail` to make the contract explicit.

**[CR-018]** `useReducedMotion` imported from framer-motion but not used consistently across pages

- **File:** `src/app/about/page.tsx:20`, `src/app/page.tsx:7`
- **Issue:** About page uses `useReducedMotion()` to disable animations, but the home page uses `useReducedMotion()` inconsistently — some `motion.div` elements get the reduced motion treatment, others don't.
- **Impact:** Accessibility inconsistency for users who prefer reduced motion.
- **Suggested fix:** Create a shared `useAnimationProps()` hook that returns consistent fade/slide props based on reduced motion preference.

**[CR-019]** Test files use `any` types extensively in mocks

- **File:** `src/components/recipe/__tests__/RecipeFeed.test.tsx:23`, many test files
- **Issue:** `const mockMotion: any = ...` and similar patterns throughout tests. While acceptable in tests, it masks type errors in mock implementations.
- **Impact:** Tests may pass even when component prop types change, reducing test effectiveness.
- **Suggested fix:** Type mocks where practical, especially for component props.
