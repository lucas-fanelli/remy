## Code Review — 2026-03-21

### Summary

Generally well-structured API code with good use of transactions and advisory locks. However, there are several data integrity gaps, missing input validation, and a significant security issue in the profile update endpoint.

### Findings

#### CRITICAL

**[CR-001]** Profile PUT catches all `Error` instances as bad requests — leaks internal errors to clients

- **File:** `src/app/api/users/profile/route.ts:64-66`
- **Issue:** After the ZodError catch, any `Error` instance is returned as a 400 with `error.message`. This means Prisma errors, database connection failures, or any other internal exception that extends `Error` will have their raw message sent to the client.
- **Impact:** Information disclosure — internal error messages (e.g., Prisma schema details, connection strings in error messages) are leaked to unauthenticated or malicious users.
- **Suggested fix:**

```typescript
// Remove this catch block entirely:
// if (error instanceof Error) {
//   return ApiResponseHelper.badRequest(error.message);
// }

// The ZodError block above handles validation. Everything else should fall through
// to the generic 500 handler below it.
```

**[CR-002]** `deductPantryItems` applies `striptags` only on deduction names, not deletion names — inconsistent XSS sanitization

- **File:** `src/app/api/cooked-recipes/route.ts:97-101`
- **Issue:** In the deductions loop, `striptags(d.name)` is applied. In the deletions loop (line 101), `d.name` is pushed raw. The `deductedIngredients` array is stored in the database and returned to the client.
- **Impact:** Stored XSS if ingredient names contain HTML and the deletion path is exercised.
- **Suggested fix:**

```typescript
for (const d of deletions) {
  await tx.pantryItem.delete({ where: { id: d.id } });
  deductedIngredients.push({
    name: striptags(d.name),
    amount: d.amount,
    unit: d.unit,
    pantryItemId: d.id,
  });
}
```

#### HIGH

**[CR-003]** Recipe creation does not validate `body` against a schema before passing to service

- **File:** `src/app/api/recipes/route.ts:152-159`
- **Issue:** The POST handler spreads `body` directly into `CreateRecipeDTO` with only a Cloudinary URL check. No Zod schema validates field types, lengths, or required fields. The `recipeService.createRecipe` may do internal validation, but the route itself trusts arbitrary JSON keys — including potential prototype pollution via `__proto__` or `constructor` keys from the spread.
- **Impact:** Unexpected fields passed to Prisma, potential data corruption, or bypassed validation if the service layer has gaps.
- **Suggested fix:** Add a Zod schema for recipe creation at the route level, consistent with how `cooked-recipes/route.ts` validates input.

**[CR-004]** DELETE account collects images outside the deletion transaction — race allows orphaned images to escape collection

- **File:** `src/app/api/users/profile/route.ts:82-85`
- **Issue:** `findMany` queries for posts and comments happen outside any transaction, then `deleteUser` runs separately. The code acknowledges the TOCTOU race in a comment but the mitigation (cleanup script) is external and not guaranteed to be running.
- **Impact:** Orphaned Cloudinary images accumulate indefinitely if the cron job is not configured. The code creates a hard dependency on an external process with no runtime check that it exists.
- **Suggested fix:** Move image collection inside the same transaction as deletion, as is already done in the admin user delete endpoint (`src/app/api/admin/users/[id]/route.ts`). At minimum, wrap both in `prisma.$transaction`.

**[CR-005]** Pantry restoration on cooked recipe DELETE doesn't sanitize `d.name` before creating new pantry items

- **File:** `src/app/api/cooked-recipes/route.ts:251-256`
- **Issue:** When restoring deducted ingredients, `d.name as string` is written directly to the database without `striptags`. The `deductedIngredients` JSON was stored earlier with partial sanitization (see CR-002), but the restoration path re-uses the raw stored value and creates new `pantryItem` records with it.
- **Impact:** If the stored name somehow contains HTML (via CR-002's deletion path), it propagates into new pantry items.
- **Suggested fix:**

```typescript
await tx.pantryItem.create({
  data: {
    pantryId: pantry.id,
    name: striptags(d.name as string),
    quantity: d.amount as number,
    unit,
  },
});
```

**[CR-006]** `RecipeFeed` never checks `liked` state from server — all recipes show as not liked

- **File:** `src/components/recipe/RecipeFeed.tsx:120`
- **Issue:** When building `newLikes`, `liked` is hardcoded to `false`. The API response includes `likeCount` but there's no server-side check for whether the current user has liked each recipe. The `liked` prop on `RecipeCard` will always be `false` on initial load and after filter changes.
- **Impact:** Users see recipes they've liked appear as not-liked until they interact. Toggling a like on an already-liked recipe would send a duplicate like or unlike incorrectly.
- **Suggested fix:** Add a `likedByUser` field to the `/api/recipes` GET response (requires a join against the likes table for the authenticated user), or fetch liked status in a separate call.

**[CR-007]** `match/route.ts` transaction indentation inconsistency — entire transaction body is under-indented

- **File:** `src/app/api/recipes/match/route.ts:60-205`
- **Issue:** The transaction callback body starting at line 61 is not indented relative to the `await prisma.$transaction(async (tx) => {` call. This is not just cosmetic — it makes it hard to see where the transaction boundary ends (line 205 with `}, { timeout: 15000 });`).

**[CR-009]** `PATCH` admin users endpoint does not validate Content-Type

- **File:** `src/app/api/admin/users/[id]/route.ts:107-112`
- **Issue:** The PATCH handler calls `request.json()` without first calling `requireJsonContentType(request)`, unlike other mutating endpoints in the codebase (e.g., `cooked-recipes/route.ts`).
- **Impact:** Inconsistent API behavior. While not directly exploitable, it deviates from the pattern established elsewhere and could allow non-JSON content types to be processed.
- **Suggested fix:**

```typescript
const ctError = requireJsonContentType(request);
if (ctError) return ctError;
```

**[CR-011]** `matchResult` transaction timeout is 15s but `statement_timeout` is 5s — timeout mismatch

- **File:** `src/app/api/recipes/match/route.ts:59,93,103`
- **Issue:** The Prisma transaction timeout is 15000ms, but individual SQL statements have `SET LOCAL statement_timeout = '5s'`. However, the `statement_timeout` is set _after_ the advisory lock acquisition (line 61), meaning the lock acquisition itself has no timeout and could block indefinitely if another user's match query is running long.
- **Impact:** Under contention, a request could hang at the advisory lock with no timeout, exhausting connection pool slots.
- **Suggested fix:** Set `statement_timeout` before the advisory lock:

```typescript
const matchResult = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SET LOCAL statement_timeout = '10s'`;
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(...)`;
  // Then set tighter timeout for queries
  await tx.$executeRaw`SET LOCAL statement_timeout = '5s'`;
```

**[CR-012]** `RecipeFeed` animation delay grows linearly with index — unbounded on large pages

- **File:** `src/components/recipe/RecipeFeed.tsx:321`
- **Issue:** `transition={{ delay: index * 0.05 }}` uses the global `index` from the `recipes` array. After several pages of infinite scroll, `index` can be 100+ (up to 300 = 25 pages \* 12), causing delays up to 15 seconds for newly loaded recipes.
- **Impact:** Recipes loaded via infinite scroll appear to "not load" because their animation delay is several seconds long.
- **Suggested fix:** Use a page-relative index:

```typescript
transition={{ delay: (index % PAGE_SIZE) * 0.05 }}
```

**[CR-014]** `handleDeleteConfirm` doesn't verify recipe ownership before calling DELETE

- **File:** `src/components/recipe/RecipeFeed.tsx:182`
- **Issue:** The client sends a DELETE without any client-side ownership check. The server should enforce this, but the client shows delete buttons for all recipes (controlled by `showActions={true}`). If `RecipeCard` renders delete for non-owned recipes, users see an error.
- **Impact:** Confusing UX — users may attempt to delete recipes they don't own.
- **Suggested fix:** Pass ownership info: `showActions={recipe.userId === user?.id}`

**[CR-015]** `cookedRecipeSchema` allows `notes` to be `null` but `striptags(null)` would throw

- **File:** `src/app/api/cooked-recipes/route.ts:150`
- **Issue:** `notes` is typed as `string | null | undefined`. Line 150: `const validatedNotes = notes ? striptags(notes.trim()) : notes;` — the falsy check handles `null` and `undefined`, but if `notes` were an empty string `""`, `striptags` would still be called (which is fine). However, the schema allows `.nullable()` which means `null` passes through unchanged and is stored. This is technically correct but the type gymnastics are fragile.
- **Impact:** Low — currently works, but the nullable + optional + striptags interaction is a maintenance trap.
- **Suggested fix:** Simplify: use `.transform()` in the schema to handle sanitization at parse time.
