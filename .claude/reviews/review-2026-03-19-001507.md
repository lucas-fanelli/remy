## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing app with clean architecture. The codebase has solid patterns (DI container, repository pattern, atomic DB operations) but contains several security gaps, a memory leak, race conditions, and data integrity issues that need attention.

### Findings

#### CRITICAL

**[CR-001]** In-memory match cache in API route leaks memory unboundedly

- **File:** `src/app/api/recipes/match/route.ts:41-42`
- **Issue:** `matchCache` is a module-level `Map` with a 60s TTL but no size limit or eviction. Every authenticated user who hits this endpoint adds an entry. In a long-running Node process, this grows without bound.
- **Impact:** Memory exhaustion causing OOM crashes in production.
- **Suggested fix:**

```typescript
const MAX_CACHE_SIZE = 1000;
// Before setting:
if (matchCache.size >= MAX_CACHE_SIZE) {
  const oldest = [...matchCache.entries()].sort((a, b) => a[1].timestamp - b[1].timestamp);
  for (let i = 0; i < oldest.length - MAX_CACHE_SIZE + 1; i++) {
    matchCache.delete(oldest[i][0]);
  }
}
matchCache.set(payload.userId, { result: responseData, timestamp: Date.now() });
```

**[CR-002]** Logout endpoint requires `application/json` Content-Type but sends no body

- **File:** `src/app/api/auth/logout/route.ts:5-8`
- **Issue:** The logout route checks for `application/json` content type, but the `AuthContext.logout()` sends `headers: { 'Content-Type': 'application/json' }` without a body. While this works today, the explicit content-type check on a bodyless request is fragile. More critically, the logout route does NOT validate the auth token — any request with the right content-type clears the cookie. This is benign but indicates the endpoint isn't verifying who is logging out.
- **Impact:** Low direct impact, but the content-type check is cargo-culted and makes the logout flow fragile if the client changes.
- **Suggested fix:** Remove the content-type check from logout — it's a cookie-clearing operation that doesn't need a JSON body.

**[CR-003]** `POST /api/notifications` (mark all as read) lacks Content-Type validation in client

- **File:** `src/app/notifications/page.tsx:62-63`
- **Issue:** `markAllAsRead` calls `fetch('/api/notifications', { method: 'POST' })` without `Content-Type: application/json` header, but the API route uses `requireJsonContentType`. This will return 415 in production.
- **Impact:** "Mark all as read" is broken — returns 415 Unsupported Media Type silently.
- **Suggested fix:**

```typescript
const response = await fetch('/api/notifications', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
});
```

**[CR-004]** Admin user deletion race condition: admin count check uses `COUNT(*)::int` but cast truncates on overflow

- **File:** `src/app/api/admin/users/[id]/route.ts:42-45`
- **Issue:** The admin count query casts `COUNT(*)` to `int` and then to JS `Number`. While the `bigint` is cast to `int` in SQL, the `FOR UPDATE` lock is applied to all admin rows — but the `userToDelete` query also uses `FOR UPDATE` on a single row. If the user was already deleted between the first query and the delete, the transaction still succeeds, returning stale data.
- **Impact:** Minor — the `FOR UPDATE` locking prevents the last-admin race, but the error handling for `USER_NOT_FOUND` checks `Array.isArray(userToDelete)` which is incorrect since `$queryRaw` returns an array, meaning `userToDelete` is always defined (it's `[{ role: 'ADMIN' }]` or `[]`). The `if (!userToDelete || ...)` check should be `if (!userToDelete || (Array.isArray(userToDelete) && userToDelete.length === 0))` — wait, it already does this, but the logic is confusing: `[{ role: string }] | []` means the destructured `[userToDelete]` would be `undefined` for empty arrays. Actually the destructuring `const [userToDelete] = await tx.$queryRaw<...>` would set `userToDelete` to `undefined` if the array is empty, so the `!userToDelete` check works. Disregard this specific issue.
- **Impact:** N/A — false alarm on the type, the logic is actually correct.

**[CR-006]** Recipe detail page `handleShare` leaks URL to clipboard without sanitization

- **File:** `src/app/recipe/[id]/page.tsx:219-230`
- **Issue:** `window.location.href` is copied directly. While this is the current page URL and not user-controlled, in a scenario where the recipe ID contains special characters (it shouldn't, given UUID validation), this could be problematic. The real issue is that `navigator.share` is called with `recipe?.title` and `recipe?.description` which could contain HTML if the sanitization in `RecipeService.stripHtml` is bypassed.
- **Impact:** Low — the `stripHtml` regex in `RecipeService` (`s.replace(/<[^>]*>/g, '')`) is weak and can be bypassed with malformed HTML like `<img src=x onerror=alert(1)` (no closing `>`). However, these values are displayed as text content in React (not `dangerouslySetInnerHTML`), so XSS is mitigated by React's escaping.
- **Suggested fix:** While React escaping prevents XSS in rendering, the `stripHtml` in RecipeService should use a proper sanitizer like DOMPurify for stored data integrity:

```typescript
private stripHtml(s: string): string {
  // This regex misses unclosed tags like <img src=x onerror=alert(1)
  // Consider using a proper library if HTML content is expected
  return s.replace(/<[^>]*>?/g, '');  // Note the ? to match unclosed tags
}
```

#### HIGH

**[CR-007]** `warnedRecipeImages` Set in RecipeCard grows without bound

- **File:** `src/components/recipe/RecipeCard.tsx:58-59`
- **Issue:** Module-level `Set` tracks warned recipe IDs. The `clear()` at 1000 is only triggered on subsequent insertions, and between clears the set grows. This is a minor memory leak in a client component, but since RecipeCard is rendered for every recipe in the feed, the set can accumulate thousands of entries during a session.
- **Impact:** Memory leak proportional to number of recipes viewed in a session.
- **Suggested fix:** Use a bounded LRU or just remove the dedup tracking — console warnings should be cheap.

**[CR-008]** `RecipeFeed` uses `generationRef` counter that overflows silently on `Number.MAX_SAFE_INTEGER`

- **File:** `src/components/recipe/RecipeFeed.tsx:77`
- **Issue:** `generationRef.current += 1` on every filter change. While this would take billions of changes to overflow, it's theoretically unsound. More importantly, the `generationRef` guard `if (currentGeneration !== generationRef.current) return;` is a race condition mitigation, but the `AbortController` already handles this. The dual mechanism is redundant and adds complexity.
- **Impact:** Low — redundant complexity, not a practical bug.
- **Suggested fix:** Remove `generationRef` since `AbortController` already handles cancellation.

**[CR-011]** `EditProfileModal` sends avatar file bytes through `FileReader.readAsArrayBuffer` for magic-byte validation, then re-reads with `FileReader.readAsDataURL` for preview

- **File:** `src/components/profile/EditProfileModal.tsx:84-115`
- **Issue:** The file is read twice — once as ArrayBuffer for magic byte validation, then as DataURL for preview. This is inefficient for large files and creates two in-memory copies. More importantly, the `file.slice(0, 12)` for magic byte detection is correct for header validation.
- **Impact:** Minor performance issue — double file read.
- **Suggested fix:** Read the full file as ArrayBuffer once, validate magic bytes from the first 12 bytes, then convert to DataURL from the ArrayBuffer.

#### MEDIUM

**[CR-012]** `normalizeIngredientName` can produce incorrect stems for short words

- **File:** `src/lib/utils/ingredients.ts:50-67`
- **Issue:** The plural stripping logic checks `normalized.length > 4` for `ies` and `ves` suffixes, but `normalized.length > 3` for the final `s` stripping. A word like "bus" (3 chars) would not be stripped (correct), but "bass" (4 chars ending in `ss`) would not be stripped either (correct due to `!normalized.endsWith('ss')`). However, "lass" (4 chars, not ending in `ss`) would be stripped to "las" which is wrong. The guard at the end catches this (cleaned.length < 3 falls back), but "las" is 3 chars so it passes.
- **Impact:** Incorrect ingredient matching for some edge-case names.
- **Suggested fix:** Add more exception words to `noStripSuffixWords` or increase the minimum length threshold.

**[CR-014]** `matchCache` in recipe match endpoint is not cleared when user's pantry changes

- **File:** `src/app/api/recipes/match/route.ts:41`
- **Issue:** The 60-second TTL cache means that if a user adds/removes pantry items and immediately re-checks matches, they'll get stale results for up to 60 seconds.

**[CR-018]** `useAdminGuard` redirects non-admin users to `/` but doesn't prevent rendering

- **File:** `src/hooks/useAdminGuard.ts:9-12`
- **Issue:** The hook calls `router.push('/')` in a `useEffect`, but the component renders before the redirect takes effect. Any admin page using this hook briefly renders its content before redirecting. The middleware check on `/admin` routes mitigates this (redirects to `/`), but if the JWT is stale, the middleware passes and the client-side guard briefly shows admin UI.
- **Impact:** Brief flash of admin UI for unauthorized users during the redirect.
- **Suggested fix:** Return a flag from the hook that the component uses to render null: `return { isReady: !isLoading && isAdmin, isLoading, shouldRedirect: !isLoading && (!user || !isAdmin) };`
