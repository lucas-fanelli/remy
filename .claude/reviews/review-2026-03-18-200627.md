## Code Review — 2026-03-18

### Summary

Large codebase with solid architecture (clean DI, atomic transactions, CSRF protection). However, API routes accept unvalidated JSON structures that can cause runtime crashes, and several data integrity and dead-code issues need attention.

### Findings

#### CRITICAL

**[CR-001]** Recipe API routes accept unvalidated ingredient/instruction structure

- **File:** `src/app/api/recipes/route.ts:147`, `src/app/api/recipes/[id]/route.ts:67`
- **Issue:** Recipe creation and update endpoints type-assert the JSON body as `CreateRecipeDTO`/`UpdateRecipeDTO` without runtime schema validation. The service-level `validateRecipeData` checks field presence but not types. A client can send `{ "amount": 42 }` (number instead of string) for an ingredient, which gets stored in the JSONB column. When later read back by `/api/cooked-recipes` or `/api/recipes/match`, `parseAmount(ingredient.amount)` calls `.trim()` on a number, causing a runtime crash.
- **Impact:** Any malformed recipe data silently persists and crashes downstream endpoints (`cooked-recipes`, `match`, recipe detail page) for all users.
- **Suggested fix:** Add Zod validation for the recipe body in both POST and PUT handlers:

```ts
const recipeBodySchema = z.object({
  title: z.string().min(1),
  description: z.string().min(1),
  imageUrl: z.string().url(),
  ingredients: z.array(
    z.object({
      name: z.string().min(1),
      amount: z.string(),
      unit: z.string().min(1),
    })
  ),
  instructions: z.array(
    z.object({
      step: z.number().int().positive(),
      description: z.string().min(1),
      image: z.string().optional(),
    })
  ),
  // ... other fields
});
const validatedBody = recipeBodySchema.parse(body);
```

**[CR-002]** `parseAmount` crashes on non-string input from malformed JSONB data

- **File:** `src/lib/utils/ingredients.ts:5`
- **Issue:** `parseAmount` calls `amount.trim()` without checking the input type. Since ingredient data is stored as JSONB and cast at runtime, numeric or null values will throw `TypeError: amount.trim is not a function`.
- **Impact:** Server 500 errors in cooked-recipes and recipe-matching endpoints.
- **Suggested fix:**

```ts
export function parseAmount(amount: unknown): number {
  if (typeof amount === 'number') return amount;
  if (typeof amount !== 'string') return NaN;
  const trimmed = amount.trim();
  // ... rest of function
}
```

#### HIGH

**[CR-003]** Partial pantry deductions create inconsistent inventory state

- **File:** `src/app/api/cooked-recipes/route.ts:120-145`
- **Issue:** When marking a recipe as cooked, ingredients with sufficient stock are deducted, but insufficient ones are skipped and reported in `insufficientIngredients`. This means a user who "cooks" a recipe loses some ingredients but not others, with no ability to undo the partial deduction. The response returns 201 (success) even when pantry data is partially inconsistent.
- **Impact:** Users lose pantry inventory for recipes they couldn't fully make. No rollback mechanism exists.
- **Suggested fix:** Either deduct all-or-nothing (fail the transaction if any ingredient is insufficient), or make partial deduction opt-in with a `force: true` parameter.

**[CR-004]** Recipe matching SQL cannot use indexes — O(n) table scan

- **File:** `src/app/api/recipes/match/route.ts:96-107`
- **Issue:** The pre-filtering query uses `lower(elem->>'name') LIKE '%term%'` with a leading wildcard. This forces PostgreSQL into a sequential scan on `jsonb_array_elements` output. The comment claims "a GIN index… should be used" but GIN indexes support `@>` containment, not `LIKE` with leading wildcards (which requires `pg_trgm`).
- **Impact:** Query time degrades linearly with recipe count. At 10K+ recipes, this endpoint will be slow.
- **Suggested fix:** Use `@>` containment queries instead of LIKE, or add a `pg_trgm` GIN index on a materialized ingredient name column. Alternatively, maintain a normalized `recipe_ingredients` join table.

**[CR-005]** Cloudinary URL path traversal check is dead code

- **File:** `src/app/api/recipes/[id]/comments/route.ts:62`, `src/app/api/recipes/route.ts:153`, and 4 other files
- **Issue:** `url.pathname.includes('..')` is checked after `new URL(imageUrl)` which normalizes the path — `..` segments are resolved during URL parsing. So `https://res.cloudinary.com/cloud/../secret` becomes `https://res.cloudinary.com/secret` and `includes('..')` returns false. The check never catches anything.
- **Impact:** False sense of security. The `startsWith(`/${cloudName}/`)` check is the actual protection, but the dead `..` check misleads future maintainers.
- **Suggested fix:** Remove the `includes('..')` check since it's unreachable, and add a comment explaining that `new URL()` normalization handles path traversal.

#### MEDIUM

**[CR-006]** Admin pages import unused variables from auth context

- **File:** `src/app/admin/comments/page.tsx:37`, `src/app/admin/recipes/page.tsx:44`, `src/app/admin/users/page.tsx:48`
- **Issue:** All three admin pages destructure `user` and `isAuthenticated` from `useAuth()` but never use them — `useAdminGuard()` handles the auth check.
- **Impact:** Dead code, potential confusion about which auth mechanism is authoritative.
- **Suggested fix:** Remove unused destructured variables:

```ts
const { isAdmin } = useAuth();
```

**[CR-007]** Notification polling circuit breaker cannot self-recover without visibility change

- **File:** `src/hooks/useNotificationPolling.ts:114-120`
- **Issue:** When the circuit breaker trips (`pollingStoppedRef.current = true`), the `scheduleNext` function checks if 5 minutes have passed and resets. But after tripping, `scheduleNext` returns early without scheduling another call. The only recovery path is `handleVisibility` firing when the user switches tabs. If the user keeps the tab visible, polling never resumes.
- **Impact:** Users who stay on the tab during a temporary server outage permanently lose notification polling until they switch tabs.
- **Suggested fix:** Schedule a recovery check timeout when the breaker trips:

```ts
if (failureTimestampsRef.current.length >= 10) {
  pollingStoppedRef.current = true;
  breakerTrippedAtRef.current = Date.now();
  // Schedule recovery attempt
  setTimeout(() => {
    pollingStoppedRef.current = false;
    scheduleNext();
  }, 5 * 60_000);
}
```

**[CR-008]** Comment imageUrl validation inconsistent with recipe imageUrl validation

- **File:** `src/app/api/recipes/[id]/comments/route.ts:55-68`
- **Issue:** Comment imageUrl validation accesses `process.env.CLOUDINARY_CLOUD_NAME` at request time and returns 400 if not configured. But recipe imageUrl validation in `src/app/api/recipes/route.ts:153` silently falls through to the `!cloudName` check inside the URL validation block. Different error handling for the same scenario across endpoints.
- **Impact:** Inconsistent user experience and error messages.
- **Suggested fix:** Extract Cloudinary URL validation into a shared utility function used by all endpoints.

**[CR-009]** Search endpoint leaks `email` field in stripping logic comment but relies on repository

- **File:** `src/app/api/search/route.ts:25-29`
- **Issue:** The comment says "Defense-in-depth: UserRepository.search already excludes email at query level, but we strip it here too in case the repository implementation changes." However, the destructuring `({ email, ...rest }) => rest` relies on `email` being present on the object. If the repository already excludes it, this destructuring creates an `undefined` variable on every call — harmless but wasteful. More importantly, the `User` type returned by the repository cast still claims `email` exists when the `select` explicitly excludes it.
- **Impact:** Type unsafety — the code works at runtime but the types are incorrect.
- **Suggested fix:** Define a `UserSearchResult` type without `email` and use it as the repository's return type for search.

#### LOW

**[CR-010]** Logout retry has no delay between attempts

- **File:** `src/contexts/AuthContext.tsx:97-110`
- **Issue:** The logout retry loop immediately retries on failure: `for (let attempt = 0; attempt < 2; attempt++)`. If the first attempt fails due to a transient network issue, the immediate retry likely hits the same issue.
- **Impact:** Retry is ineffective for transient network errors.
- **Suggested fix:** Add a small delay before retry:

```ts
if (attempt === 0) await new Promise((r) => setTimeout(r, 1000));
```

**[CR-011]** `safeRating` returns 0 for null which is ambiguous

- **File:** `src/lib/utils/recipe.ts:7`
- **Issue:** `safeRating(value)` returns 0 for both "no rating" (null) and a hypothetical "zero rating". The comment says "A return value of 0 means 'no rating'" but the consuming code (RecipeCard, search, profile) doesn't distinguish — it displays "No ratings yet" only when `totalRatings > 0` is checked separately.
- **Impact:** Fragile coupling between `safeRating` return value and display logic. If any consumer forgets to also check `totalRatings`, they'll display 0 stars instead of "no ratings".
- **Suggested fix:** Return `null` from `safeRating` for unrated recipes and let consumers handle null explicitly.
