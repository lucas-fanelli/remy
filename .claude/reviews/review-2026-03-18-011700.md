## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Several notification error-handling inconsistencies across follow/unfollow routes can return 500 to clients despite successful mutations. Recipe matching is limited to 100 most-recent recipes. Overall architecture is solid but has gaps that need addressing.

### Findings

#### CRITICAL

**[CR-001]** Follow route: notification failure returns 500 despite successful follow

- **File:** `src/app/api/users/[username]/follow/route.ts:76-82`
- **Issue:** `notificationService.createFollowNotification()` is called inside the same try-catch as the follow transaction. If the notification throws a non-unique-constraint error, the catch block re-throws, and the outer catch returns 500. The follow is already persisted in the DB.
- **Impact:** Client receives 500 error, may retry the follow, hitting the "Already following" path. User sees an error despite the action succeeding.
- **Suggested fix:**

```typescript
const [, followersCount] = await prisma.$transaction([...]);

// Non-critical: don't let notification failure mask follow success
try {
  const notificationService = container.get<INotificationService>('INotificationService');
  await notificationService.createFollowNotification(payload.userId, userToFollow.id);
} catch (notifError) {
  console.warn('Failed to create follow notification:', notifError);
}

return NextResponse.json({ success: true, message: 'Followed successfully', followersCount });
```

**[CR-002]** Unfollow route: notification deletion failure returns 500 despite successful unfollow

- **File:** `src/app/api/users/[username]/unfollow/route.ts:47-49`
- **Issue:** `notificationService.deleteFollowNotification()` is called without try-catch. If it throws, the entire request returns 500 even though the unfollow (deleteMany) already succeeded.
- **Impact:** Same as CR-001. Client sees error, unfollow is persisted, state diverges.
- **Suggested fix:**

```typescript
// Non-critical notification cleanup
try {
  const notificationService = container.get<INotificationService>('INotificationService');
  await notificationService.deleteFollowNotification(payload.userId, userToUnfollow.id);
} catch (notifError) {
  console.warn('Failed to delete follow notification:', notifError);
}
```

#### HIGH

**[CR-003]** Recipe matching only considers 100 most-recent recipes

- **File:** `src/app/api/recipes/match/route.ts:67-68`
- **Issue:** `take: 100, orderBy: { createdAt: 'desc' }` means older recipes are never matched against the user's pantry. As the recipe count grows, match quality degrades silently.
- **Impact:** Users miss relevant matches from older recipes. No indication that results are incomplete.
- **Suggested fix:** Either increase the limit, use cursor-based pagination with multiple batches, or move matching to a database query (e.g., using ingredient name overlap via SQL).

**[CR-004]** Save-status GET endpoint makes unnecessary recipe existence check

- **File:** `src/app/api/recipes/[id]/save/route.ts:19-27`
- **Issue:** The GET endpoint queries `prisma.post.findUnique` just to check if the recipe exists before checking the save status. For unauthenticated users (no token), it returns `{ saved: false }` early, but for authenticated users it makes two sequential queries.
- **Impact:** Doubled database load for every save-status check. On a recipe page with 1000 views, that's 1000 extra queries.
- **Suggested fix:** Remove the recipe existence check. If the recipe doesn't exist, `savedRecipe.findUnique` returns null, which maps to `saved: false` — the correct behavior.

**[CR-005]** Cloudinary image cleanup reads recipe before delete, creating a TOCTOU gap

- **File:** `src/app/api/recipes/[id]/route.ts:109-115`
- **Issue:** `recipeForCleanup` is fetched before `recipeService.deleteRecipe()`. If the recipe is updated (new image) between the fetch and the delete, the old image URL becomes stale — the wrong Cloudinary image gets deleted.
- **Impact:** Orphaned images in Cloudinary (old image not deleted) or wrong image deleted if recipe was updated concurrently.
- **Suggested fix:** Have `deleteRecipe` return the deleted record's imageUrl, or fetch and delete atomically.

**[CR-006]** User search endpoint lacks offset/pagination for users

- **File:** `src/app/api/search/route.ts:26`
- **Issue:** Recipe results support `offset` pagination, but user results are fetched via `userService.searchUsers(query.trim(), limit)` which has no offset parameter. Users beyond the first page are unreachable.
- **Impact:** Search results page cannot load more users beyond the initial limit.
- **Suggested fix:** Add offset parameter to `IUserService.searchUsers` and `UserRepository.search`.

#### MEDIUM

**[CR-007]** Inconsistent notification error handling across routes

- **File:** Multiple API routes
- **Issue:** `like` route (line 55-60) and `comment` route (line 151-155) correctly wrap notification calls in try-catch with `console.warn`. `follow` and `unfollow` routes do not. This inconsistency suggests the pattern was adopted mid-development without retrofitting older routes.
- **Impact:** Maintenance confusion. New developers may copy either pattern.
- **Suggested fix:** Standardize all notification side-effects with try-catch wrappers.

**[CR-008]** `USERNAME_REGEX` in constants allows 1-character usernames

- **File:** `src/lib/constants.ts:15`
- **Issue:** `USERNAME_REGEX = /^[a-zA-Z0-9_]{1,30}$/` allows single-character usernames. The registration schema enforces min 3, but this regex is used for URL parameter validation in API routes. A crafted request to `/api/users/a/profile` would pass validation and hit the database.
- **Impact:** Minor — the DB query returns null for non-existent users. But it's a pointless database hit.
- **Suggested fix:** `export const USERNAME_REGEX = /^[a-zA-Z0-9_]{3,30}$/;`

**[CR-009]** `RecipeFeed` scroll handler doesn't debounce independent of render cycle

- **File:** `src/components/recipe/RecipeFeed.tsx:119-126`
- **Issue:** The scroll handler uses `setTimeout(..., 200)` for throttling, but `clearTimeout` only clears on remount. Rapid scrolling can queue multiple timeouts before the first clears. The `loadingRef` guard prevents double-loading, but the timeout accumulation is wasteful.
- **Impact:** Minor performance — multiple no-op scroll handler invocations.
- **Suggested fix:** Use a proper throttle utility or `requestAnimationFrame`.

**[CR-010]** `about` page feature icons are instantiated at module scope with JSX

- **File:** `src/app/about/page.tsx:23-59`
- **Issue:** `features` array contains JSX elements (`<Restaurant sx={{ fontSize: 40 }} />`) created at module scope. These React elements are created once and reused across renders, which works but violates the convention that JSX should be in render functions. If these icons ever needed to consume context or hooks, they'd break silently.
- **Impact:** Low — works today, fragile for future changes.
- **Suggested fix:** Move `features` inside the component or store icon components (not elements) and render in JSX.

**[CR-011]** Admin page comment delete error check is fragile

- **File:** `src/app/api/admin/comments/[id]/route.ts:23-26`
- **Issue:** Error detection relies on string matching: `error.message === 'COMMENT_NOT_FOUND' || error.message.includes('Record to delete does not exist')`. Prisma error messages are not guaranteed stable across versions.
- **Impact:** A Prisma upgrade could change error messages, causing 500 instead of 404.
- **Suggested fix:** Use Prisma error codes (`error.code === 'P2025'`) instead of string matching.

#### LOW

**[CR-012]** `EditRecipeModal` ingredient validation differs from `CreateRecipeForm`

- **File:** `src/components/recipe/EditRecipeModal.tsx:117-124` vs `src/components/recipe/CreateRecipeForm.tsx:79-88`
- **Issue:** Create form allows partial ingredients (validates `some(i => i.name.trim() !== '')`), while edit form requires `every(...)` — all ingredients must be valid. Different validation standards for the same data type.
- **Impact:** Users can create recipes with partial ingredient rows but can't save edits with the same data.
- **Suggested fix:** Align validation logic. Either both filter out incomplete rows or both require complete rows.

**[CR-013]** `LoadingBar` flickers on every route change

- **File:** `src/components/LoadingBar.tsx:13-18`
- **Issue:** Shows a 500ms loading bar on every `pathname` or `searchParams` change, even for instant client-side navigations that don't actually load data. The bar appears and disappears within 500ms, causing a visual flicker.
- **Impact:** Minor visual annoyance on fast navigations.
- **Suggested fix:** Use Next.js router events or `useTransition` to only show the bar during actual pending navigations.

**[CR-014]** `PersistentSearchBar` abort controller ref is never nulled after cleanup

- **File:** `src/components/search/PersistentSearchBar.tsx:120`
- **Issue:** `abortControllerRef.current?.abort()` is called on cleanup, and a new controller is assigned, but the old aborted controller stays in the ref if the effect cleanup runs. Minor memory/reference concern.
- **Impact:** Negligible.
