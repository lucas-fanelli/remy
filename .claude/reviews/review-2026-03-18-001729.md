## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Several security vulnerabilities around auth token handling, race conditions in concurrent operations, and inconsistent error handling patterns across API routes.

### Findings

#### CRITICAL

**[CR-001]** Auth token leaked to client after cookie migration

- **File:** `src/contexts/AuthContext.tsx:82-83`
- **Issue:** After migrating to httpOnly cookies, `login()` still stores the JWT in React state via `setToken(data.data.token)` and exposes it to all components. The token is also returned in the JSON response body from `/api/auth/login`. This defeats the purpose of httpOnly cookies — any XSS can exfiltrate the token from React state or the response body.
- **Impact:** XSS vulnerability negates httpOnly cookie security. Token accessible via `useAuth().token` throughout the entire client app, used in dozens of `Authorization: Bearer` headers.
- **Suggested fix:** Stop returning `token` in the login/register API JSON responses. Remove `setToken` from AuthContext. Rely exclusively on the httpOnly cookie sent automatically with `credentials: 'same-origin'`. Migrate all client `fetch` calls to use `credentials: 'same-origin'` instead of `Authorization` headers.

**[CR-002]** CSRF protection bypass via auth cookie presence

- **File:** `src/middleware.ts:146-158`
- **Issue:** The CSRF check allows requests that have `request.cookies.has('auth_token')`. Since the httpOnly cookie is sent automatically by the browser on every same-site request, any same-origin form submission (even from an XSS-injected form) satisfies this check. The CSRF protection is effectively a no-op for authenticated users.
- **Impact:** Authenticated users are vulnerable to CSRF attacks via simple form POST submissions from malicious pages (if SameSite somehow weakens, e.g., Safari quirks, or via subdomain takeover).
- **Suggested fix:** Remove `request.cookies.has('auth_token')` from the `hasCustomHeader` check. Require an explicit non-cookie header (like `Content-Type: application/json` or a dedicated CSRF token) for state-changing requests.

**[CR-003]** Race condition in recipe save toggle allows duplicate saves

- **File:** `src/app/api/recipes/[id]/save/route.ts:68-100`
- **Issue:** The `existingSave` lookup and `create`/`delete` happen inside a transaction, but the recipe existence check (`prisma.post.findUnique`) happens outside the transaction. Two concurrent toggle requests can both read `existingSave = null`, then both try to create, causing a unique constraint violation. The catch for `Unique constraint` on line 92 masks this but returns `saved: true` for both, making the toggle non-deterministic.
- **Impact:** Inconsistent save state. User clicks "save" once but two requests fire — the second silently succeeds as "already saved" even though the first request's response also said "saved."
- **Suggested fix:** Move the recipe existence check inside the transaction, or use an upsert pattern. Better: use `deleteMany` + count pattern like the like toggle does for atomic unsave.

**[CR-004]** `recalc-ratings` endpoint uses raw SQL without parameterization safety

- **File:** `src/app/api/admin/recalc-ratings/route.ts:18-33`
- **Issue:** While the raw SQL uses template literals with Prisma's tagged template (which does parameterize), the query operates on ALL posts in the database with no pagination or batching. On a large dataset, this locks the `Post` and `Rating` tables for the duration of the transaction.
- **Impact:** Database lock contention. In production with thousands of recipes, this can block all reads/writes to `Post` and `Rating` tables for seconds or longer, causing request timeouts.
- **Suggested fix:** Batch the update in chunks (e.g., 500 posts per iteration) or run outside a transaction with `FOR UPDATE SKIP LOCKED`.

#### HIGH

**[CR-005]** Recipe match endpoint loads all recipes into memory

- **File:** `src/app/api/recipes/match/route.ts:60-67`
- **Issue:** Fetches up to 100 recipes with all their ingredients into memory, then iterates over every recipe's ingredients for every pantry item. With large ingredient lists, this is O(recipes _ recipe_ingredients _ pantry_items) with no caching.
- **Impact:** Memory pressure and slow response times as recipe count grows. 100 recipes with 10 ingredients each and a user with 50 pantry items = 50,000 comparisons per request.
- **Suggested fix:** Move ingredient matching to a database query using `jsonb` operators, or implement server-side caching of normalized ingredient indexes.

**[CR-006]** Notification polling creates unbounded timer chains

- **File:** `src/components/Navigation.tsx:218-249`
- **Issue:** The polling implementation uses recursive `setTimeout` with exponential backoff on failure, but `consecutiveFailuresRef` is never reset on component re-render with new token. If a user logs out and back in, the ref retains the old failure count, starting with an inflated backoff interval.
- **Impact:** After a logout/login cycle with prior notification failures, notifications may not update for up to 5 minutes.
- **Suggested fix:** Reset `consecutiveFailuresRef.current = 0` when `token` changes.

**[CR-007]** Admin delete comment recalculates ratings inside transaction but may deadlock

- **File:** `src/infrastructure/services/AdminService.ts:205-230`
- **Issue:** The `deleteComment` method runs `findUnique` + `delete` + `aggregate` + `update` inside a single Prisma interactive transaction. The aggregate query on `Rating` while holding a lock on `Comment` can deadlock with concurrent user rating operations that lock `Rating` first then touch `Post`.
- **Impact:** Potential database deadlocks under concurrent admin + user operations.
- **Suggested fix:** Perform the rating recalculation outside the transaction, or use a single raw SQL statement that combines delete + recalculate.

**[CR-008]** No test coverage for API route handlers

- **File:** All files under `src/app/api/`
- **Issue:** There are zero integration or unit tests for any API route handler. All test coverage is limited to UI components, services, and repositories. The API layer — which handles request parsing, validation, authorization, and error mapping — is entirely untested.
- **Impact:** Regressions in auth checks, input validation, or error handling in routes go undetected. The review found multiple issues in routes that tests would have caught.
- **Suggested fix:** Add integration tests for at least the auth, recipe CRUD, and admin API routes using `NextRequest` mocks.

#### MEDIUM

**[CR-009]** Inconsistent auth patterns across API routes

- **File:** Multiple API route files
- **Issue:** Some routes use `requireAuth()` helper (e.g., `change-password`, `me`, `profile`), others manually call `extractBearerToken` + `container.getTokenService().verify()` (e.g., `cooked-recipes`, `pantry`, `notifications`, `comments`). The manual pattern is ~10 lines of boilerplate repeated in 15+ routes.
- **Impact:** Increased maintenance burden. A change to auth logic requires updating dozens of files. Risk of inconsistent error responses.
- **Suggested fix:** Standardize on `requireAuth()` across all authenticated routes.

**[CR-010]** `cooked-recipes` POST reads recipe then modifies pantry non-atomically

- **File:** `src/app/api/cooked-recipes/route.ts:106-107`
- **Issue:** The recipe is fetched outside the transaction (`prisma.post.findUnique`), then pantry modifications happen inside the transaction. If the recipe is deleted between the lookup and the transaction, the transaction proceeds with a stale recipe object and creates a `cookedRecipe` referencing a deleted post.
- **Impact:** Orphaned `cookedRecipe` records pointing to non-existent posts. Foreign key constraint may fail depending on schema cascade rules.
- **Suggested fix:** Move the recipe lookup inside the transaction.

**[CR-011]** `PersistentSearchBar` creates new `AbortController` on every keystroke

- **File:** `src/components/search/PersistentSearchBar.tsx:110-115`
- **Issue:** The `useEffect` creates a new `AbortController` and aborts the previous one on every `query` change, but the abort happens via `abortControllerRef.current?.abort()` before the 300ms debounce fires. This means the controller is aborted and recreated on every keystroke, but the debounced fetch uses the last controller. If the user types fast, the cleanup function also calls `controller.abort()`, which aborts the final debounced request.
- **Impact:** The last character typed may trigger a search that gets immediately aborted by the cleanup function, resulting in dropped search results.
- **Suggested fix:** Only abort the controller when the debounce timer is cleared, not in the cleanup function.

**[CR-012]** `website` field in profile not validated for SSRF on the server

- **File:** `src/infrastructure/services/UserService.ts:37-48`
- **Issue:** Website URL validation only checks protocol and embedded credentials, but doesn't prevent internal network URLs like `http://169.254.169.254/` (AWS metadata) or `http://localhost:3000/api/admin/`. While this is a stored URL and not fetched server-side, it could be exploited if any future feature fetches user-provided URLs.
- **Impact:** Low risk currently, but stored SSRF vector if URL is ever fetched server-side.
- **Suggested fix:** Add a blocklist for private IP ranges and internal hostnames.

**[CR-013]** `search` API route doesn't validate `offset` parameter for recipes but does for users

- **File:** `src/app/api/search/route.ts:27-28`
- **Issue:** Recipe search uses `offset` from query params but user search via `userService.searchUsers` ignores offset entirely. The user search always returns the first N results regardless of pagination.
- **Impact:** Users cannot paginate through user search results. If there are 100 matching users, only the first `limit` are ever returned.
- **Suggested fix:** Pass `offset` to `userService.searchUsers()` and propagate it to the repository `search` method.

**[CR-014]** `RecipeFeed` scroll handler throttle can miss final scroll event

- **File:** `src/components/recipe/RecipeFeed.tsx:172-181`
- **Issue:** The scroll handler uses `setTimeout` with 200ms delay for throttling, but clears the timeout on each scroll event. If the user scrolls to the bottom and stops, the 200ms timer fires. But if they scroll and release exactly at the bottom, the browser might not fire another scroll event after the timeout, and the handler might not trigger because `scrollY` hasn't changed between the timeout and the check.
- **Impact:** Occasional failure to load next page when scrolling to bottom.
- **Suggested fix:** Use `requestAnimationFrame` or `IntersectionObserver` instead of scroll throttling.

#### LOW

**[CR-015]** Hardcoded `en-US` locale in date formatting

- **File:** `src/app/admin/comments/page.tsx:156`, `src/app/admin/recipes/page.tsx:229`, `src/app/admin/users/page.tsx:243`
- **Issue:** `toLocaleDateString('en-US')` is hardcoded across all admin pages. Should use a constant or respect user's locale.
- **Impact:** Non-English users see US date format in admin panel.
- **Suggested fix:** Extract locale to a constant or use `Intl.DateTimeFormat` with browser locale.

**[CR-016]** `averageRating` field uses `?? 0` in some places and `|| 0` in others

- **File:** `src/app/api/recipes/route.ts:100`, `src/app/api/search/route.ts:65`, `src/app/api/users/[username]/profile/route.ts:131`
- **Issue:** Inconsistent nullish handling. `?? 0` treats only `null`/`undefined` as falsy, while `|| 0` also treats `0` as falsy. For ratings, `0` is a valid value meaning "no ratings" vs `null` meaning "not calculated."
- **Impact:** Minor — `0` and `null` both map to `0` in practice, but semantics differ.
- **Suggested fix:** Standardize on `?? 0` everywhere for rating fields.

**[CR-017]** `motion.create()` used inconsistently vs `motion()`

- **File:** Multiple component files
- **Issue:** Some files use `motion.create(Box)` (newer API) while others use `motion(Box)` (legacy API). Both work but the codebase should be consistent.
- **Impact:** Maintainability. Confusing for contributors about which pattern to follow.
- **Suggested fix:** Standardize on `motion.create()` across all files.

**[CR-018]** `techStack` array in about page is hardcoded

- **File:** `src/app/about/page.tsx:63-71`
- **Issue:** Technology stack is hardcoded in the component. Should be in `BRANDING` config or a separate config file.
- **Impact:** Minor maintainability issue.
- **Suggested fix:** Move to `src/config/branding.ts` or a dedicated config.
