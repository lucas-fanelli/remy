## Code Review — 2026-03-18

### Summary

Large Next.js recipe platform with clean architecture. The codebase is mature with good patterns (DI container, repositories, atomic DB operations), but has security gaps in CSRF handling, several silent-failure patterns in error handling, and missing input validation in API routes.

### Findings

#### CRITICAL

**[CR-001]** Logout request blocked by CSRF middleware in browsers without `Sec-Fetch-Site`

- **File:** `src/contexts/AuthContext.tsx:101-104`
- **Issue:** The logout fetch sends `POST` to `/api/auth/logout` with `credentials: 'same-origin'` but no custom headers. The middleware CSRF check requires either `Sec-Fetch-Site: same-origin`, JSON content-type, `Authorization`, or `X-Requested-With`. Browsers without `Sec-Fetch-Site` support (older Safari, WebViews) will have the request rejected with 403.
- **Impact:** Users on older browsers/WebViews cannot log out. The cookie persists until expiry.
- **Suggested fix:**

```typescript
await fetch('/api/auth/logout', {
  method: 'POST',
  credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json' },
});
```

**[CR-002]** Notification 401 handling can log out user on transient network failure

- **File:** `src/components/Navigation.tsx:242-253`
- **Issue:** When notification fetch returns 401, the code calls `/api/auth/me` to confirm. If `/api/auth/me` also fails (network blip, server restart, CDN timeout), the user is logged out. A single transient failure during polling destroys the session.
- **Impact:** Authenticated users randomly logged out during brief network disruptions.
- **Suggested fix:** Require multiple consecutive 401s from `/api/auth/me` before logging out, or only logout if `/api/auth/me` returns 401 specifically (not network errors):

```typescript
if (response.status === 401) {
  try {
    const meResp = await fetch('/api/auth/me', { signal: controller.signal });
    if (meResp.status === 401) {
      // Only 401, not other failures
      pollingStoppedRef.current = true;
      logout();
    }
  } catch {
    // Network error — don't logout, just stop polling temporarily
    pollingStoppedRef.current = true;
  }
  return;
}
```

**[CR-003]** `postId` and `userId` query params in admin API routes not validated for UUID format

- **File:** `src/app/api/admin/comments/route.ts:14-15`
- **Issue:** The `postId` and `userId` query parameters are passed directly to Prisma without UUID validation. While Prisma won't SQL-inject, malformed UUIDs cause Prisma query errors that leak internal error details to the 500 response.
- **Impact:** Information disclosure via error messages; unnecessary database round-trips with invalid input.
- **Suggested fix:**

```typescript
if (postId && !UUID_REGEX.test(postId)) {
  return NextResponse.json({ error: 'Invalid postId format' }, { status: 400 });
}
if (userId && !UUID_REGEX.test(userId)) {
  return NextResponse.json({ error: 'Invalid userId format' }, { status: 400 });
}
```

Same issue in `src/app/api/admin/recipes/route.ts:15` and `src/app/api/admin/users/route.ts:15`.

#### HIGH

**[CR-004]** Admin page delete operations silently swallow errors

- **File:** `src/app/admin/comments/page.tsx:86-89`, `src/app/admin/recipes/page.tsx:96-99`, `src/app/admin/users/page.tsx:103-106`
- **Issue:** The `handleDelete` functions catch errors and only log to `console.error`. No user-facing error state is set. The dialog closes via `fetchComments()` on success, but on failure the dialog also closes (via `finally` block setting `actionLoading` false) with no feedback.
- **Impact:** Admin thinks delete succeeded when it failed. Data inconsistency between UI and database.
- **Suggested fix:**

```typescript
const handleDelete = async () => {
  if (!selectedComment || !isAuthenticated) return;
  setActionLoading(true);
  try {
    const response = await fetch(`/api/admin/comments/${selectedComment.id}`, { method: 'DELETE' });
    if (!response.ok) throw new Error('Failed to delete comment');
    setDeleteDialogOpen(false);
    fetchComments();
  } catch (error) {
    setError('Failed to delete comment. Please try again.');
    console.error('Error deleting comment:', error);
  } finally {
    setActionLoading(false);
  }
};
```

**[CR-005]** Cloudinary regex for image cleanup misses URLs with transformations or query params

- **File:** `src/app/api/recipes/[id]/route.ts:131`
- **Issue:** The regex `/\/upload\/(?:v\d+\/)?(.+)\.\w+$/` assumes the URL ends with a file extension. Cloudinary URLs with query params (`?w=200`), format transformations (`/f_auto/`), or no extension will not match, leaving orphaned images.
- **Impact:** Storage leak in Cloudinary; orphaned images accumulate over time.
- **Suggested fix:**

```typescript
const match = imageUrl.match(/\/upload\/(?:v\d+\/)?(.+?)(?:\.\w+)?(?:\?.*)?$/);
```

**[CR-006]** `CLOUDINARY_CLOUD_NAME` validated per-request instead of at startup

- **File:** `src/app/api/recipes/[id]/comments/route.ts:107-111`
- **Issue:** Multiple API routes check `process.env.CLOUDINARY_CLOUD_NAME` at request time. If the env var is missing, every image-containing request returns 400 with "Image upload is currently unavailable" — an opaque error for users.
- **Impact:** Image uploads silently broken in production if env var is misconfigured. Every request pays the cost of checking.
- **Suggested fix:** Add `CLOUDINARY_CLOUD_NAME` to the required variables in `src/lib/env-validation.ts`:

```typescript
const required: (keyof EnvConfig)[] = [
  'DATABASE_URL',
  'JWT_SECRET',
  'JWT_EXPIRES_IN',
  'NEXTAUTH_URL',
  'NEXTAUTH_SECRET',
  'NODE_ENV',
  'NEXT_PUBLIC_APP_URL',
  'CLOUDINARY_CLOUD_NAME',
];
```

**[CR-007]** Unsafe type cast in recipe detail page

- **File:** `src/app/recipe/[id]/page.tsx:253`
- **Issue:** `(recipe as unknown as DomainRecipe)` double-casts the API response to the domain type. The API recipe type (`ApiRecipe` from `useRecipe` hook) has different field shapes than `DomainRecipe` (e.g., `user` vs `author`, string dates vs Date objects).
- **Impact:** Runtime errors in EditRecipeModal when accessing mismatched fields; modal may crash or show wrong data.
- **Suggested fix:** Create a proper adapter function or use the API type directly:

```typescript
<EditRecipeModal
  open={editModalOpen}
  recipe={recipe ? mapApiRecipeToRecipe(recipe) : null}
  onClose={() => setEditModalOpen(false)}
  onSuccess={handleEditSuccess}
/>
```

#### MEDIUM

**[CR-008]** Profile endpoint hardcodes 50-item limit with no pagination

- **File:** `src/app/api/users/[username]/profile/route.ts:72,119`
- **Issue:** Both user posts (`take: 50`) and saved recipes (`take: 50`) are hardcoded limits with no offset parameter. Users with more than 50 recipes/saved items lose access to older content.
- **Impact:** Data truncation for power users; no way to view beyond first 50 items.
- **Suggested fix:** Accept `limit` and `offset` query params, or implement cursor-based pagination.

**[CR-009]** Comment edit cannot remove or change attached image

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:38-42`
- **Issue:** The PATCH endpoint only updates `text` and `rating`. The `imageUrl` field is not included in the update. Users who post a comment with an incorrect/inappropriate image cannot remove or change it.
- **Impact:** Users must delete and recreate comments to fix image issues. Inappropriate images cannot be quickly corrected.
- **Suggested fix:** Add `imageUrl` to the PATCH body handling (with the same Cloudinary validation as POST).

**[CR-010]** `recalc-ratings` reports stale total count

- **File:** `src/app/api/admin/recalc-ratings/route.ts:38`
- **Issue:** `prisma.post.count()` runs outside the transaction, so the `total` in the response may not reflect the actual number of recipes that were recalculated (recipes could be created/deleted between transaction commit and count).
- **Impact:** Misleading admin feedback; minor data inconsistency in response.
- **Suggested fix:** Move the count inside the transaction or remove it from the response.

**[CR-011]** `toLocaleDateString()` without locale specification in admin tables

- **File:** `src/app/admin/comments/page.tsx:142`, `src/app/admin/recipes/page.tsx:187`, `src/app/admin/users/page.tsx:221`
- **Issue:** `new Date(comment.createdAt).toLocaleDateString()` produces different formats depending on the browser's locale. Admin users in different locales see different date formats.
- **Impact:** Inconsistent UX across admin users; dates may be ambiguous (e.g., 01/02/2024 = Jan 2 or Feb 1).
- **Suggested fix:** Use explicit locale or `Intl.DateTimeFormat`:

```typescript
{
  new Date(comment.createdAt).toLocaleDateString('en-US', {
    year: 'numeric',
    month: 'short',
    day: 'numeric',
  });
}
```

**[CR-012]** `RecipeFeed` like handler reverts on JSON parse failure even when server succeeded

- **File:** `src/components/recipe/RecipeFeed.tsx:291-296`
- **Issue:** If the server processes the like successfully but returns malformed JSON (e.g., truncated response due to proxy), the optimistic update is reverted. The user sees their like disappear even though the server state changed.
- **Impact:** UI/server state desynchronization after network issues.
- **Suggested fix:** Only revert on non-ok responses; for parse failures on ok responses, keep the optimistic state:

```typescript
if (response.ok) {
  try {
    const data = await response.json();
    setRecipeLikes((prev) => ({
      ...prev,
      [recipeId]: { liked: data.liked, count: data.likesCount },
    }));
  } catch {
    // JSON parse failed but server processed — keep optimistic state
  }
}
```
