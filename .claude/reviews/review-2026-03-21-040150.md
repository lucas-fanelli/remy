**[CR-001]** Unvalidated `instructions` JSON field used in account deletion without type guard

- **File:** `src/app/api/users/profile/route.ts:103-110`
- **Issue:** `post.instructions` is typed as `Prisma.JsonValue` (could be any JSON). The code does `Array.isArray(post.instructions)` then iterates, casting elements to `Record<string, unknown>`. However, `post.instructions` entries could be arrays, strings, numbers, or nested objects with prototype pollution payloads. The `'image' in instr` check on a non-object (e.g., a string or number) will silently fail in JS, but if `instr` is an array, `'image' in [...]` checks numeric indices — not a security issue per se, but the `typeof instr === 'object'` check passes for arrays and `null`. `null` is guarded by the `instr &&` check, but arrays slip through and `(instr as Record<string, unknown>).image` on an array returns `undefined`, which is benign. However, the real issue is that `instructions` could contain thousands of deeply nested entries — there is no length cap on iteration, unlike the recipe creation schema which caps at 50 instructions. A maliciously crafted recipe with 10,000+ instruction entries would cause the deletion transaction to hold the connection for an extended period.
- **Impact:** A single account deletion could monopolize a DB connection for seconds or longer if the user created recipes with bloated `instructions` JSON (bypassed via direct DB manipulation or older API versions without the cap). This is a DoS vector against the connection pool during account deletion.

**[CR-002]** `DELETE /cooked-recipes` pantry restoration creates unbounded pantry items without limit check

- **File:** `src/app/api/cooked-recipes/route.ts:278-295`
- **Issue:** When restoring pantry items on cooked recipe deletion, the code creates new `pantryItem` entries without checking how many items the user's pantry already has. The `deductedArraySchema` caps at 100 items, but each restoration can create a new item if the original was deleted. Repeatedly cooking and un-cooking recipes (each with different ingredients) can grow the pantry unboundedly. More critically, the code queries `tx.userPantry.findUnique` inside a loop (up to 100 iterations) — this is an N+1 query pattern. The pantry lookup should be hoisted outside the loop.
- **Impact:** N+1 queries inside a transaction holding an advisory lock. With 100 deducted ingredients, this executes up to 100 extra `findUnique` calls plus 100 creates, all serialized. Under concurrent load, this blocks other cooked-recipe operations for the same user.
- **Suggested fix:**

```typescript
// Hoist pantry lookup outside the loop
const pantry = await tx.userPantry.findUnique({ where: { userId: user.id } });

for (const d of validDeducted) {
  const safeName = striptags(d.name).slice(0, 200);
  if (!safeName) continue;
  const pantryItemId = d.pantryItemId;
  const unit = striptags(d.unit).slice(0, 50);
  let existingItem = null;
  if (pantryItemId) {
    existingItem = await tx.pantryItem.findFirst({
      where: { id: pantryItemId, pantry: { userId: user.id } },
    });
  }
  if (existingItem) {
    const restoredQuantity = Math.min(existingItem.quantity + d.amount, 10000);
    await tx.pantryItem.update({
      where: { id: existingItem.id },
      data: { quantity: restoredQuantity },
    });
  } else if (pantry) {
    // Check total item count before creating
    const itemCount = await tx.pantryItem.count({ where: { pantryId: pantry.id } });
    if (itemCount >= 200) {
      console.warn(`[COOKED-RECIPES] Skipping pantry restore for ${safeName}: pantry full`);
      continue;
    }
    await tx.pantryItem.create({
      data: { pantryId: pantry.id, name: safeName, quantity: d.amount, unit },
    });
  }
}
```

**[CR-003]** Recipe creation double-validates but bypasses service-layer sanitization

- **File:** `src/app/api/recipes/route.ts:191-211`
- **Issue:** The code calls `recipeService.validateRecipeData(recipeData)` for validation/sanitization, but then passes the original `recipeData` (not the sanitized result) to `tx.post.create`. If `validateRecipeData` performs sanitization (stripping HTML, normalizing fields), those sanitized values are discarded. The raw Zod-validated but unsanitized data goes directly to the database. This defeats the purpose of the service-layer sanitization step.
- **Impact:** If the service layer strips XSS payloads or normalizes data, those protections are bypassed. Any stored XSS vectors that pass Zod validation but are caught by the service sanitizer will persist in the database.

if (!validationResult.valid) {

// Use sanitized data from the service if available
const sanitizedData = validationResult.sanitizedData ?? recipeData;

const recipe = await prisma.$transaction(async (tx) => {
  // ... advisory lock and daily limit check ...
  return tx.post.create({ data: sanitizedData });

**[CR-004]** `SET LOCAL statement_timeout` without resetting allows timeout to leak within transaction retry

- **File:** `src/app/api/recipes/match/route.ts:88`
- **Issue:** `SET LOCAL statement_timeout = '5s'` is scoped to the transaction, which is correct for normal flow. However, the transaction has an 8-second Prisma-level timeout (`{ timeout: 8000 }`). If the `statement_timeout` fires mid-query, PostgreSQL cancels the current statement and throws an error, which causes Prisma to abort the transaction. But the error type is a generic Prisma error, not `MATCH_IN_PROGRESS` — it falls through to the generic 500 handler. The user gets "Failed to match recipes" instead of a meaningful timeout message.
- **Impact:** Users experiencing slow queries (large pantries, many recipes) get opaque 500 errors instead of actionable feedback. No retry guidance is provided. Additionally, the 5s statement timeout applies to ALL statements in the transaction including the advisory lock acquisition and simple selects, not just the expensive candidate query.
- **Suggested fix:**

```typescript
// Apply statement_timeout only to the expensive query, not the entire transaction
// Remove: await tx.$executeRaw`SET LOCAL statement_timeout = '5s'`;

// Instead, wrap the expensive query and catch timeout specifically:
try {
  allCandidates = await tx.$queryRaw<{ id: string; ingredients: unknown }[]>`
    SELECT /*+ statement_timeout(5000) */ ...
  `;
} catch (err) {
  if (err instanceof Error && err.message.includes('statement timeout')) {
    throw new Error('MATCH_TIMEOUT');
  }
  throw err;
}
```

Then handle `MATCH_TIMEOUT` in the outer catch with a 504 or 408 status.

**[CR-005]** Race condition: recipe creation validates `imageUrl` outside the transaction

- **File:** `src/app/api/recipes/route.ts:176-189`
- **Issue:** `validateCloudinaryUrl` is called before the transaction begins. Between the validation and the `tx.post.create` inside the transaction, there is a window where the validated URL could become invalid (e.g., Cloudinary image deleted). More importantly, the `createRecipeSchema` already validates the URL format with `.refine()`, making the second `validateCloudinaryUrl` call redundant — unless it performs additional checks (like verifying the image actually exists on Cloudinary). If it does make a network call to Cloudinary, doing it outside the transaction is correct for performance but should be documented. If it doesn't make a network call, it's dead code duplication.
- **Impact:** If `validateCloudinaryUrl` is purely a format check, it duplicates the Zod `.refine()` check. If it's a network check, the TOCTOU gap could allow a deleted image URL to be persisted.
- **Suggested fix:** Verify what `validateCloudinaryUrl` does. If format-only, remove the redundant call. If network-based, document the TOCTOU trade-off or move validation into the transaction (accepting the performance cost).
