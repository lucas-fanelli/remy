## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing app with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes, middleware, and client components.

### Findings

#### CRITICAL

**[CR-001]** Cooked recipe DELETE endpoint lacks CSRF header requirement

- **File:** `src/app/api/cooked-recipes/route.ts:248`
- **Issue:** The DELETE handler for cooked recipes does not enforce the `X-Requested-With` header check, unlike every other mutating endpoint. The middleware CSRF check only applies when the header is missing AND `sec-fetch-site` is not `same-origin`, but the comment claims "requires the X-Requested-With header (defense-in-depth)" while the handler doesn't send it.
- **Impact:** Inconsistency with defense-in-depth strategy; the comment is misleading about what protection is actually applied.
- **Suggested fix:** The middleware actually enforces this at the middleware level for all POST/PUT/PATCH/DELETE, so the handler itself doesn't need to check. But the comment on line 241-244 is misleading — it should be removed or clarified to say "CSRF protection is enforced by middleware" rather than claiming the handler does it.

**[CR-002]** `cleanupCloudinaryImage` in recipe DELETE is not fire-and-forget — errors propagate

- **File:** `src/app/api/recipes/[id]/route.ts:113-115`
- **Issue:** Unlike the admin recipe delete (which wraps in try/catch), the user recipe delete calls `await cleanupCloudinaryImage(imageUrl)` without a try/catch. If Cloudinary is down, the user gets a 500 even though the DB delete succeeded.
- **Impact:** Successful recipe deletion returns 500 to user if Cloudinary cleanup fails; user may retry and get 404.
- **Suggested fix:**

```typescript
if (imageUrl) {
  try {
    await cleanupCloudinaryImage(imageUrl);
  } catch (err) {
    logServerError('Failed to cleanup Cloudinary image:', err);
  }
}
```

**[CR-003]** Race condition in cooked recipe rating aggregation

- **File:** `src/app/api/cooked-recipes/route.ts:199-220`
- **Issue:** The code locks the Post row with `SELECT ... FOR UPDATE` before upserting the rating and recalculating averages. However, the lock is acquired AFTER the `cookedRecipe.create` and pantry deduction. If two concurrent requests for different recipes share pantry deductions, one transaction holds the pantry advisory lock while waiting for the Post lock, and another holds a different Post lock — no deadlock. But if the same user concurrently cooks the same recipe (bypassing the 24h check via clock skew), both could pass the duplicate check and create two cooked entries.
- **Impact:** The 24-hour duplicate check uses `Date.now()` which is server-local time. Clock skew between server instances could allow duplicates.
- **Suggested fix:** Use database `NOW()` instead of JavaScript `Date.now()` for the time comparison, or add a unique constraint on `(userId, postId)` with a partial index on recent entries.

**[CR-004]** Admin user delete leaks timing of advisory lock to client

- **File:** `src/app/api/admin/users/[id]/route.ts:42-43`
- **Issue:** The 30-second statement timeout and 35-second transaction timeout mean that if the cascade delete is slow (large user with many posts/comments), the transaction will fail with a timeout error that bubbles up as a generic 500. But more critically, the `SET LOCAL statement_timeout` only applies within the transaction — if Prisma retries, the timeout won't carry over.
- **Impact:** For users with thousands of posts, the delete could timeout and leave partial state if Prisma's transaction timeout fires before the statement timeout.
- **Suggested fix:** Set `timeout: 60000` on the transaction and `statement_timeout = '55s'` to ensure the statement timeout fires first, giving the transaction a clean rollback.

#### HIGH

**[CR-005]** `extractAuthToken` returns cookie value without signature verification for optional-auth endpoints

- **File:** `src/app/api/recipes/[id]/like/route.ts:78-86`
- **Issue:** The GET endpoint extracts the token from the cookie and calls `tokenService.verify()`. If verify returns null (expired/invalid token), it returns `liked: false`. But if verify throws (malformed token causing jsonwebtoken to throw a non-standard error), the error propagates to the catch block which returns `{ liked: false, likesCount: 0 }` — losing the actual likes count.
- **Impact:** A malformed auth cookie causes the API to return `likesCount: 0` instead of the real count for ALL users on that recipe until the cookie is cleared.
- **Suggested fix:** Move the `likesCount` query before the token verification, or separate the try/catch blocks:

```typescript
const likesCount = await prisma.like.count({ where: { postId: recipeId } });
// Then do token verification in a separate try/catch
```

**[CR-006]** Recipe match endpoint has no timeout for the JavaScript matching loop

- **File:** `src/app/api/recipes/match/route.ts:136-155`
- **Issue:** The DB query has a 5-second timeout, but the JavaScript matching loop (`for (const candidate of allCandidates)`) has a `MAX_COMPARISONS = 50_000` guard but no time limit. With 200 candidates each having 100 ingredients matched against 100 pantry items, that's 200 _ 100 _ 100 = 2M comparisons (capped at 50K). But `ingredientMatches` calls `normalizeIngredientName` twice per comparison, which does regex replacements — this could be slow for pathological inputs.
- **Impact:** A user with many pantry items and recipes with many ingredients could cause the endpoint to take several seconds, blocking the Node.js event loop.
- **Suggested fix:** Add a wall-clock time check inside the loop (e.g., `if (Date.now() - startTime > 4000) break;`).

**[CR-007]** `notifications/[id]/route.ts` PATCH has no auth-first pattern — UUID validation runs before auth

- **File:** `src/app/api/notifications/[id]/route.ts:15-22`
- **Issue:** The UUID validation happens before authentication. While this is not a security vulnerability (it just returns 400 vs 401), it leaks information about which notification IDs are valid UUIDs to unauthenticated users. More importantly, this is inconsistent with other routes that check auth first.
- **Impact:** Information disclosure (minor); inconsistent pattern that could lead to copy-paste bugs.
- **Suggested fix:** Move `requireAuth` before UUID validation, consistent with other routes.

**[CR-008]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:130-171`
- **Issue:** When `loadRecipes(true)` is called on filter change, it sets `pageRef.current = 1` and replaces recipes. But the abort controller abort happens AFTER `pageRef.current` is set. If the aborted request's `.then()` still runs (race between abort and response), the `thisRequestId` check should catch it — but `pageRef.current` has already been mutated to 1, so the next `loadRecipes(false)` call uses `offset = 1 * PAGE_SIZE` which is correct. However, if the abort fires after the response is received but before state is set, `thisRequestId` prevents stale data. This seems correct but is fragile.
- **Impact:** Potential for duplicate recipes appearing in the feed under rapid filter switching, though the deduplication in `setRecipes` mitigates this.
- **Suggested fix:** The existing `thisRequestId` pattern is sufficient, but the `pageRef.current` mutation before the fetch is a code smell. Consider moving it after the successful response.

**[CR-009]** Notification polling `fetchNotifications` doesn't guard against concurrent calls from visibility handler

- **File:** `src/hooks/useNotificationPolling.ts:68-71`
- **Issue:** `isFetchingRef` is set to `true` on line 70, but the previous fetch is aborted on line 67. The abort causes the previous fetch's `finally` block to set `isFetchingRef.current = false` (line 125). If the abort's `finally` runs AFTER the new fetch sets `isFetchingRef.current = true`, it gets reset to `false`, defeating the guard.
- **Impact:** Overlapping notification fetches could occur, wasting bandwidth and potentially causing UI flicker.
- **Suggested fix:** Don't reset `isFetchingRef` in the `finally` block when the error is an `AbortError`:

```typescript
} finally {
  // Don't reset if this fetch was aborted (a newer one is in flight)
  if (!controller.signal.aborted) {
    isFetchingRef.current = false;
  }
}
```

#### MEDIUM

**[CR-010]** `EditProfileModal` doesn't sanitize website URL before sending to API

- **File:** `src/components/profile/EditProfileModal.tsx:131-135`
- **Issue:** Client-side validation checks `http://` or `https://` prefix, but doesn't check for embedded credentials (`https://user:pass@evil.com`). The server-side `UserService.updateProfile` does check for credentials, but the error message is generic.
- **Impact:** Poor UX — user submits a URL with credentials, gets a server error instead of a client-side validation message.
- **Suggested fix:** Add client-side credential check:

```typescript
try {
  const url = new URL(websiteValue);
  if (url.username || url.password) {
    setFormErrors({ website: 'URL must not contain credentials' });
    return;
  }
}
```

**[CR-011]** `AdminService.getStats` cache is shared across all admin users

- **File:** `src/infrastructure/services/AdminService.ts:256-260`
- **Issue:** The stats cache is a module-level variable. In a serverless environment (Vercel), this cache lives per-instance and may serve stale data. The cache TTL is 30 seconds, which is reasonable, but the cache is never invalidated on organic activity (new signups, recipes). The comment documents this trade-off, but the cache invalidation on mutations only clears the cache for the same instance.
- **Impact:** Different admin users on different server instances could see different stats for up to 30 seconds.
- **Suggested fix:** This is documented and acceptable for the current scale. No change needed, but consider adding a comment about multi-instance behavior.

**[CR-012]** `useReducedMotion` check on about page applies inconsistently

- **File:** `src/app/about/page.tsx:68-69`
- **Issue:** When `shouldReduceMotion` is true, `fadeUp` is set to `{}` (no animation props). But the `transition` prop is still passed as `undefined` (not omitted). Framer Motion treats `undefined` transition differently from omitting it entirely — it falls back to default transitions.
- **Impact:** Users with reduced motion preference may still see brief default transitions.
- **Suggested fix:** Also conditionally omit the `transition` prop or set it to `{ duration: 0 }`.

**[CR-013]** Footer contact dialog mailto link length check is post-encoding but uses raw character count

- **File:** `src/components/Footer.tsx:67-71`
- **Issue:** The comment says "Check length AFTER encoding" but `mailtoLink.length` counts UTF-16 code units of the encoded string. The actual limit should be on the byte length of the URL, not the character count. `encodeURIComponent` expands characters (e.g., spaces become `%20`, 3 chars per space), so a 1500-character mailtoLink could represent far fewer actual message characters than expected.
- **Impact:** Users may hit the length limit sooner than expected for messages with special characters.
- **Suggested fix:** Either use `new Blob([mailtoLink]).size` for byte length, or lower the character threshold to account for encoding expansion (current 1500 is conservative enough).

**[CR-014]** Search page user interface type has `id` field that doesn't come from the API

- **File:** `src/app/search/page.tsx:16-21`
- **Issue:** The `User` interface defines `id: string`, but the `/api/search` route strips IDs from user results (returns only `username`, `fullName`, `avatar`, `bio`). The `id` field will always be `undefined`, but it's used as the React key in `users.map`.
- **Impact:** React key warnings or unexpected behavior if `id` is undefined. Currently works because `user.id` would be `undefined` and React would use index.
- **Suggested fix:** Use `user.username` as the key instead of `user.id`, and update the interface to match the API response:

```typescript
interface User {
  username: string;
  fullName?: string | null;
  avatar?: string;
  bio?: string;
}
// In JSX: key={user.username}
```

**[CR-015]** `useCreateRecipe` hook doesn't invalidate `recipe` query keys

- **File:** `src/hooks/useCreateRecipe.ts:16-17`
- **Issue:** After creating a recipe, the hook invalidates `['recipes']` query key. But the `RecipeFeed` component uses direct `fetch` calls, not React Query, so this invalidation has no effect on the feed. The comment on line 21-23 acknowledges this but the `queryClient.invalidateQueries` call is dead code.
- **Impact:** No functional impact (dead code), but misleading.
- **Suggested fix:** Remove the React Query invalidation or add a comment that it's for future use when RecipeFeed migrates to React Query.

**[CR-018]** `PersistentSearchBar` creates new AbortController outside setTimeout

- **File:** `src/components/search/PersistentSearchBar.tsx:127-133`
- **Issue:** The comment explains this is intentional for cleanup, but the AbortController is created on every effect run even when the query is too short to trigger a search. When `query.trim().length < 2`, the controller is created and immediately returned from the cleanup without ever being used.
- **Impact:** Minor memory churn — creating unused AbortControllers.
- **Suggested fix:** Move the controller creation inside the `if (query.trim().length >= 2)` block.
