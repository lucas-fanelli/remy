## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured, but several security gaps, race conditions, and data integrity issues exist across API routes and client components.

### Findings

#### CRITICAL

**[CR-001]** Notification polling 401 handler calls logout without confirming auth is truly invalid on network error

- **File:** `src/hooks/useNotificationPolling.ts:113-119`
- **Issue:** When the `/api/auth/me` confirmation fetch itself throws a network error (catch block), the code sets `pollingStoppedRef.current = true` but does NOT call `onAuthInvalid()`. However, the comment says "don't logout, just pause". This is correct behavior but inconsistent with the 401 path above it where `onAuthInvalid()` IS called. The real issue: if `/api/auth/me` returns a non-401 error (e.g., 500), it falls through to the catch with no handling — the user gets silently logged out of polling with no recovery.
- **Impact:** Transient server errors on `/api/auth/me` can permanently pause notifications with no auto-recovery until page refresh.
- **Suggested fix:**

```typescript
const meResp = await fetch('/api/auth/me', { signal: meController.signal });
if (meResp.status === 401 && isMountedRef.current) {
  pollingStoppedRef.current = true;
  setIsPollingPaused(true);
  onAuthInvalid();
} else if (!meResp.ok) {
  // Non-auth server error — treat as transient, don't logout
  failureTimestampsRef.current.push(Date.now());
}
```

**[CR-002]** Cooked recipe DELETE does not restore pantry items

- **File:** `src/app/api/cooked-recipes/route.ts:215-268`
- **Issue:** When a cooked recipe is deleted, the associated rating is conditionally removed and averageRating recalculated, but the pantry items that were deducted during the POST are never restored. This is a data integrity issue — users lose ingredients permanently even if they undo the "cooked" action.
- **Impact:** Users permanently lose pantry quantities with no way to recover them short of manually re-adding.
- **Suggested fix:** Store `deductedIngredients` on the `CookedRecipe` record (as JSON) during creation, and reverse the deductions in the DELETE handler inside the transaction.

**[CR-003]** `striptags` does not sanitize notes in pantry POST

- **File:** `src/app/api/pantry/route.ts:122`
- **Issue:** The `notes` field is stored as `notes?.trim() || null` without calling `striptags()`. The PUT handler at `src/app/api/pantry/[id]/route.ts:103` does sanitize `notes` with striptags, but the POST handler does not. This inconsistency means XSS payloads can be stored via the creation path.
- **Impact:** Stored XSS if notes are ever rendered as raw HTML (React's JSX escaping mitigates this, but it's defense-in-depth failure).
- **Suggested fix:**

```typescript
notes: notes ? striptags(notes.trim()) || null : null,
```

#### HIGH

**[CR-004]** Recipe match endpoint has no statement_timeout in fallback path

- **File:** `src/app/api/recipes/match/route.ts:118-124`
- **Issue:** The fallback query path (when `pantryPatterns.length === 0`) uses `tx.post.findMany` inside a transaction with `SET LOCAL statement_timeout = '5s'`, but if `prisma.post.findMany` is used directly (the code does use a transaction here, so this specific instance is OK). However, the `allCandidates` processing loop at line 131 has a 4-second wall-clock limit AND a 50K comparison limit, but the batch fetch at line 166 (`prisma.post.findMany` with `where: { id: { in: batchIds } }`) runs OUTSIDE any transaction/timeout, with no limit on batch count.
- **Impact:** If matching produces hundreds of results, the batch fetch loop could issue multiple unbounded queries without timeout protection.
- **Suggested fix:** Cap `matchResults` to a reasonable limit (e.g., 60) before the batch fetch, or add a statement timeout to the batch queries.

**[CR-005]** Admin user delete collects images before deletion, creating a race window

- **File:** `src/app/api/admin/users/[id]/route.ts:68-78`
- **Issue:** The code acknowledges this in a comment ("small race window"), but the image URLs are collected BEFORE `tx.user.delete()`. If new posts/comments are created between the collection queries and the cascade delete, those images become orphaned. The advisory lock only serializes admin deletes, not user content creation.
- **Impact:** Orphaned Cloudinary images that the cleanup script must catch.
- **Suggested fix:** This is documented and mitigated by the cleanup script. Acceptable if the cleanup script is actually scheduled. Verify the cron job exists.

**[CR-006]** `RecipeFeed` infinite scroll has no deduplication for intersection observer triggers

- **File:** `src/components/recipe/RecipeFeed.tsx:182-193`
- **Issue:** The IntersectionObserver callback checks `loadingRef.current` and `hasMore`, and has a 500ms debounce via `lastLoadTimeRef`. However, if the observer fires twice within the same frame (possible with rapid scroll), `loadingRef.current` may not yet be true when the second callback fires, causing a duplicate fetch.
- **Impact:** Duplicate recipes in the feed (mitigated by the `existingIds` Set, but wastes network requests).
- **Suggested fix:** Set `loadingRef.current = true` synchronously inside the observer callback before calling `loadRecipes()`, or use a `requestAnimationFrame` guard.

**[CR-007]** `EditProfileModal` website validation only checks prefix, not full URL validity

- **File:** `src/components/profile/EditProfileModal.tsx:133-145`
- **Issue:** Client-side validation checks `startsWith('http://')` or `startsWith('https://')`, then does `new URL()` but catches errors silently with a comment "will be caught by server-side validation". If the URL constructor fails, the form submits anyway with an invalid URL.
- **Impact:** Invalid URLs can be submitted; server-side Zod validation catches this, but the UX is poor (server returns error after upload completes).
- **Suggested fix:** Show the validation error immediately when `new URL()` throws:

```typescript
try {
  new URL(websiteValue);
} catch {
  setFormErrors({ website: 'Please enter a valid URL' });
  return;
}
```

**[CR-008]** `AuthContext` logout retry fires custom event that may never be handled

- **Issue:** On logout failure, `window.dispatchEvent(new CustomEvent('auth:logout-failed'))` is fired. The Navigation component listens for this, but if Navigation isn't mounted (e.g., on /auth page where it's hidden), the event is lost silently.

**[CR-009]** `Footer` contact form has no rate limiting on `handleSendEmail`

- **File:** `src/components/Footer.tsx:68-78`
- **Issue:** `sendingRef.current` provides a 3-second cooldown, but this is client-side only. A user can repeatedly trigger `window.open(mailtoLink)` by clicking rapidly before the 3-second timeout.
- **Impact:** Minor annoyance (rapid mailto: popups), not a server-side concern since it uses mailto:.

**[CR-010]** `useNotificationPolling` exponential backoff cooldown math can overflow

- **File:** `src/hooks/useNotificationPolling.ts:156-160`
- **Issue:** `5 * 60 * 1000 * Math.pow(2, breakerTripCountRef.current - 1)` — with `breakerTripCountRef` capped at 10, `Math.pow(2, 9) = 512`, giving `5 * 60000 * 512 = 153,600,000ms` (~42 hours). The `Math.min(..., 30 * 60 * 1000)` correctly caps this. However, the cap at line 103 uses `Math.min(breakerTripCountRef.current, 10)` which is technically not needed since the formula already caps. The concern is that `breakerTripCountRef.current++` at line 100 can increment beyond 10 before the cap at 103, and if two failures race, the count could briefly exceed 10.
- **Impact:** Cosmetic — the Math.min on cooldown handles it. No real bug.
- **Suggested fix:** Move the cap before the increment: `breakerTripCountRef.current = Math.min(breakerTripCountRef.current + 1, 10)`.

**[CR-012]** `RecipeCard` image fallback creates infinite error loop potential

- **File:** `src/components/recipe/RecipeCard.tsx:110-120`

**[CR-014]** Admin stats cache not invalidated by organic activity

- **File:** `src/infrastructure/services/AdminService.ts:11-12`
- **Issue:** The comment explains this is intentional (30s TTL), but the cache is a module-level variable. In serverless (Vercel), each instance has its own cache, so the effective cache hit rate is very low. The 30s TTL provides negligible benefit in serverless while adding complexity.
- **Impact:** Minimal performance benefit in the primary deployment target; adds cognitive overhead.
- **Suggested fix:** Either remove the cache (it's a single SQL query) or document that it's only effective in long-lived processes.

**[CR-015]** `updateProfileSchema` website field transforms empty string to null after URL validation

- **File:** `src/lib/validation/schemas.ts:48-55`
- **Issue:** The schema uses `.url()` then `.or(z.literal(''))` then `.transform(v => v === '' ? null : v)`. This works but the `.url()` validator runs first and rejects empty strings, then the `.or(z.literal(''))` allows them through. The refine for credentials check catches `try/catch` failures with `return true`, deferring to `.url()`. This is correct but fragile — reordering the chain would break it.
- **Impact:** Works correctly but is a maintenance trap.
- **Suggested fix:** Use `z.union([z.literal(''), z.string().url().refine(...)])` for clearer intent.
