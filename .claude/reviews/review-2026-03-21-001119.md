## Code Review — 2026-03-21

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured with good separation of concerns, but has several security gaps, race conditions, and data integrity issues that need attention.

### Findings

#### CRITICAL

**[CR-001]** Cloudinary image cleanup awaited in request path blocks response

- **File:** `src/app/api/admin/recipes/[id]/route.ts:43-48`
- **Issue:** `cleanupCloudinaryImage` is `await`ed inside the request handler. If Cloudinary is slow or down, the DELETE response is delayed or times out, even though the DB deletion already succeeded.
- **Impact:** User-facing latency on recipe deletion; potential timeout errors despite successful deletion.
- **Suggested fix:** Fire-and-forget with `.catch()` instead of `await`:

```ts
if (imageUrl) {
  cleanupCloudinaryImage(imageUrl).catch((err) =>
    logServerError('Failed to delete image from Cloudinary:', err)
  );
}
```

**[CR-002]** `cooked-recipes` DELETE restores pantry items without validating deducted data shape

- **File:** `src/app/api/cooked-recipes/route.ts:225-255`
- **Issue:** `cookedRecipe.deductedIngredients` is cast from `JsonValue` to a typed array with no runtime validation. If the stored JSON is malformed (e.g., missing `amount` or `pantryItemId`), the loop will silently produce NaN quantities or skip items.
- **Impact:** Corrupted pantry quantities; items restored with `NaN` or `undefined` amounts.
- **Suggested fix:** Validate each deducted ingredient before restoring:

```ts
for (const d of deducted) {
  if (typeof d.amount !== 'number' || !d.name) continue;
  // ... restore logic
}
```

**[CR-003]** Recipe match endpoint has no per-user serialization despite comment claiming availability

- **File:** `src/app/api/recipes/match/route.ts:30-31`
- **Issue:** The comment says "advisory lock key PG_ADVISORY_LOCK_MATCH is available if per-user serialization is ever needed" but the endpoint loads all pantry items + does heavy in-memory matching. Two concurrent requests from the same user will each execute the full query and matching, doubling DB and CPU load.
- **Impact:** Under concurrent usage, the 5s statement_timeout could be exhausted, and the application-level 4s wall-clock limit may produce inconsistent partial results.
- **Suggested fix:** Either add the advisory lock or implement request deduplication per user to prevent concurrent expensive queries.

**[CR-004]** `users/profile/route.ts` DELETE collects images before deletion with TOCTOU race

- **File:** `src/app/api/users/profile/route.ts:79-86`
- **Issue:** Images are collected from `post.findMany` and `comment.findMany` before `userService.deleteUser`, but new posts/comments could be created between the queries and the cascade delete. This is the same race documented in the admin user delete but without the advisory lock protection.
- **Impact:** Orphaned Cloudinary images from posts/comments created in the race window.
- **Suggested fix:** Wrap image collection and deletion in a transaction, or at minimum document the dependency on the cleanup script.

#### HIGH

**[CR-005]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:134-170`
- **Issue:** When filters change, `loadRecipes(true)` resets state, but the `existingIds` dedup Set in the append path (line 163) only guards within a single non-reset call. If a stale response from a previous filter arrives after the reset (despite the requestId guard), duplicates could slip through.
- **Impact:** Duplicate recipe cards with identical React keys causing rendering issues.
- **Suggested fix:** The triple-guard (AbortController + requestId + existingIds) is already robust. However, the `recipesLengthRef` is updated outside the requestId guard on line 159 (`recipesLengthRef.current = data.recipes.length`). Move this inside the guard.

**[CR-006]** `maskEmail` in admin routes does not handle edge cases

- **File:** `src/app/api/admin/users/[id]/route.ts:13-18`
- **Issue:** `maskEmail` splits on `@` and `.` but doesn't handle emails with no TLD extension (e.g., `user@localhost`) — `rest.join('.')` would produce an empty string. Also, single-char local parts produce `a**` (3 chars) which reveals length information differently.
- **Impact:** Information leakage for unusual email formats; potential crash for malformed emails stored in DB.
- **Suggested fix:**

```ts
function maskEmail(email: string): string {
  const atIdx = email.indexOf('@');
  if (atIdx < 1) return '***@***';
  // ... rest of masking
}
```

**[CR-007]** Notification polling has no upper bound on retry escalation in edge cases

- **File:** `src/hooks/useNotificationPolling.ts:156-162`
- **Issue:** `breakerTripCountRef` is capped at 10 but the cooldown formula `5min * 2^(tripCount-1)` with tripCount=10 yields 2560 minutes before the `Math.min(…, 30min)` cap. This is correct, but the `failureTimestampsRef` array can grow without limit within a 10-minute window if the user rapidly triggers retries.
- **Impact:** Memory growth from failure timestamps array; unlikely but possible with automated tools.
- **Suggested fix:** Cap the `failureTimestampsRef` array length (e.g., keep only last 20 entries).

**[CR-008]** `EditProfileModal` doesn't revoke blob URL when component unmounts during upload

- **File:** `src/components/profile/EditProfileModal.tsx:74-77`
- **Issue:** The cleanup effect revokes the blob URL on unmount, but only if `avatarPreview` starts with `blob:`. If the user selects a file, then the modal is force-closed (e.g., navigation), the `avatarFile` state may hold a reference preventing GC, and the effect may not fire if the component is already unmounted.
- **Impact:** Memory leak from unreleased object URLs on rapid open/close cycles.
- **Suggested fix:** The current implementation is actually correct for normal usage. Mark as acknowledged.

#### MEDIUM

**[CR-009]** `about/page.tsx` feature animation delay grows unbounded for large arrays

- **File:** `src/app/about/page.tsx:150`
- **Issue:** `Math.min(0.08 * index, 0.5)` caps at 0.5s, which is fine for 6 features. But the `features` array could grow, and the `Math.min` cap means all features beyond index 6 animate simultaneously.
- **Impact:** Poor animation choreography if features array grows.
- **Suggested fix:** Acceptable for current size. No change needed.

**[CR-010]** Admin pages share identical table/pagination/dialog patterns with no abstraction

- **File:** `src/app/admin/comments/page.tsx`, `src/app/admin/recipes/page.tsx`, `src/app/admin/users/page.tsx`
- **Issue:** The TODO comment at `admin/page.tsx:1-3` acknowledges this. All three admin sub-pages duplicate: fetch-with-pagination, search debounce, delete dialog, error state, loading state. Each is ~200 lines of near-identical code.
- **Impact:** Maintenance burden; bugs fixed in one page must be replicated to others.
- **Suggested fix:** Extract `useAdminTable<T>` hook and `AdminTablePage` component.

**[CR-011]** `cooked-recipes` POST validates ingredient shape but uses `console.warn` on failure

- **File:** `src/app/api/cooked-recipes/route.ts:175-178`
- **Issue:** When ingredient validation fails, the code logs a warning and silently skips deduction. The user receives a success response with no indication that pantry deduction was skipped.
- **Impact:** User believes ingredients were deducted when they weren't, leading to incorrect pantry state.
- **Suggested fix:** Include a flag in the response indicating deduction was skipped:

```ts
return {
  cookedRecipe,
  insufficientIngredients,
  deductedIngredients,
  deductionSkipped: !ingredientsValid,
};
```

**[CR-012]** `PersistentSearchBar` live search doesn't debounce on rapid pathname changes

- **File:** `src/components/search/PersistentSearchBar.tsx:109-113`
- **Issue:** `prevPathnameRef` clears query on pathname change, but the debounced search effect (line 121) may fire for the previous query after the clear, causing a flash of stale results.
- **Impact:** Brief flash of search results from the previous page's query.
- **Suggested fix:** The AbortController in the search effect handles this. No change needed.

**[CR-013]** `Footer` contact form mailto link has no rate limiting on the `sending` timeout

- **File:** `src/components/Footer.tsx:73-77`
- **Issue:** `sending` state is reset after 3 seconds via `setTimeout`. A user could rapidly click "Send Email" every 3 seconds, generating mailto links each time. Not a server issue, but UX annoyance.
- **Impact:** Minor — repeated mailto attempts.
- **Suggested fix:** Acceptable behavior for a mailto link. No change needed.

**[CR-014]** `recipes/route.ts` GET does not validate `sort` parameter against allowed values

- **File:** `src/app/api/recipes/route.ts:36`
- **Issue:** `sort` is read from query params and used in a switch statement. Invalid values fall through to the default case (newest), which is safe. But no 400 error is returned for invalid sort values.
- **Impact:** Silent fallback to default sort may confuse API consumers.
- **Suggested fix:** Add validation:

```ts
const validSorts = ['newest', 'rating_desc', 'rating_asc', 'most_reviewed'];
if (sort && !validSorts.includes(sort)) {
  return NextResponse.json({ error: 'Invalid sort parameter' }, { status: 400 });
}
```

**[CR-015]** `notifications/[id]/route.ts` PATCH doesn't verify ownership atomically

- **File:** `src/app/api/notifications/[id]/route.ts:24-36`
- **Issue:** `findFirst` + `update` is two separate queries. Between them, another request could delete the notification. The `update` would fail with a Prisma error that isn't caught specifically.
- **Impact:** Unhandled Prisma error on concurrent delete → 500 response.
- **Suggested fix:** Wrap in try/catch for P2025, or use `updateMany` with compound where clause.
