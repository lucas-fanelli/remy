## Code Review — 2026-03-21

### Summary

A cooked-recipes API route handling GET/POST/DELETE with pantry deduction logic. Generally well-structured with good concurrency controls, but contains several bugs and gaps worth fixing.

### Findings

#### CRITICAL

**[CR-001]** Pantry restoration overflow: quantity can exceed cap across multiple deducted items

- **File:** `src/app/api/cooked-recipes/route.ts:267`
- **Issue:** `Math.min(existingItem.quantity + d.amount, 10000)` caps each individual restoration, but the in-memory mutation on line 272 (`existingItem.quantity = restoredQuantity`) means subsequent iterations accumulate correctly in-memory. However, the `byNameUnit` map is keyed on `striptags(i.name)` (from the DB), but lookups use `striptags(d.name)` from the deducted record. If the stored name in DB differs slightly from the deducted name after `striptags` (e.g., DB has leading/trailing whitespace that `striptags` doesn't remove), the lookup misses and a duplicate pantry item is created instead of incrementing the existing one.
- **Impact:** Duplicate pantry items created for the same ingredient, corrupting pantry state.
- **Suggested fix:** Normalize names consistently. Use `normalizeIngredientName` (already imported) for map keys and lookups, matching what `deductPantryItems` does:

```ts
const byNameUnit = new Map(
  allPantryItems.map((i) => [`${normalizeIngredientName(i.name)}|${i.unit}`, i])
);
// ...
const key = `${normalizeIngredientName(safeName)}|${unit}`;
const existingItem = (d.pantryItemId ? byId.get(d.pantryItemId) : undefined) ?? byNameUnit.get(key);
```

**[CR-002]** `UUID_REGEX` used as both a Zod regex and a `RegExp.test()` target — stateful `lastIndex` bug if `g` flag is set

- **File:** `src/app/api/cooked-recipes/route.ts:12` and `:240`
- **Issue:** If `UUID_REGEX` is defined with the `g` flag, calling `.test()` on line 240 will alternate between `true` and `false` due to `lastIndex` state. Zod's `.regex()` also calls `.test()` internally, compounding the issue.
- **Impact:** Intermittent 400 errors on valid DELETE requests (every other call fails).
- **Suggested fix:** Verify `UUID_REGEX` has no `g` flag. If it does, remove it or create a new `RegExp` per test:

```ts
if (!cookedRecipeId || !new RegExp(UUID_REGEX.source).test(cookedRecipeId)) {
```

#### HIGH

**[CR-003]** DELETE does not check `cookedAt` freshness before restoring pantry — stale deletions restore ingredients that may have been consumed by other cooks

- **File:** `src/app/api/cooked-recipes/route.ts:248-280`
- **Issue:** A user cooks recipe A (deducts 2 eggs), then manually adds 2 eggs back to pantry, then cooks recipe B (deducts 2 eggs). If they now delete recipe A's cooked entry, 2 eggs are restored — giving them 2 extra eggs they don't have. The `deductedIngredients` snapshot is from cook-time, not current state.
- **Impact:** Pantry quantities drift from reality over time. This is a fundamental design issue with snapshot-based restoration.
- **Suggested fix:** At minimum, add a time limit (e.g., 1 hour) after which pantry restoration is skipped, and document this behavior. Or add a `restorable: boolean` flag that gets set to `false` after subsequent pantry mutations.

**[CR-004]** `console.warn` used instead of `logServerError`/structured logger

- **File:** `src/app/api/cooked-recipes/route.ts:204` and `:258`
- **Issue:** Two `console.warn` calls bypass the structured logger used everywhere else in this file. In production, these may not be captured by log aggregation.
- **Impact:** Silent failures in pantry deduction/restoration that are invisible in monitoring.
- **Suggested fix:**

```ts
logServerError('[COOKED-RECIPES] Skipping pantry deduction: ingredient validation failed', {
  postId,
});
```

**[CR-005]** No pagination metadata returned from GET

- **File:** `src/app/api/cooked-recipes/route.ts:131`
- **Issue:** The GET response returns `{ cookedRecipes, total }` but not `page`, `limit`, or `totalPages`. Clients cannot reliably paginate without knowing the current page context.
- **Impact:** Client-side pagination bugs; clients must track page state independently and hope it stays in sync.
- **Suggested fix:**

```ts
return NextResponse.json({
  cookedRecipes,
  total,
  page,
  limit,
  totalPages: Math.ceil(total / limit),
});
```

**[CR-006]** Rating aggregation race between POST and DELETE

- **File:** `src/app/api/cooked-recipes/route.ts:222` (POST) and `:296` (DELETE)
- **Issue:** The POST handler locks the Post row with `SELECT ... FOR UPDATE` _after_ the `rating.upsert`. If two concurrent requests (one POST, one DELETE) target different cooked recipes for the same post, the upsert can succeed on both before either acquires the post lock, leading to a stale aggregation read.
- **Impact:** `averageRating` and `reviewCount` on `Post` can be incorrect.
- **Suggested fix:** Move the `SELECT ... FOR UPDATE` on the Post row to _before_ the `rating.upsert` in the POST handler:

```ts
if (rating !== undefined) {
  await tx.$executeRaw`SELECT id FROM "Post" WHERE id = ${postId} FOR UPDATE`;
  await tx.rating.upsert({ ... });
  // ...
}
```

Wait — it's already in that order on line 222-223. But the advisory lock is per-user (`hashtext(user.id)`), so two _different_ users rating the same post simultaneously are not serialized by the advisory lock. The `FOR UPDATE` on the Post row does serialize them, but it's acquired after the upsert. Move it before.

#### MEDIUM

**[CR-007]** `deductedIngredients` stored via `JSON.parse(JSON.stringify(...))` — unnecessary serialization round-trip

- **File:** `src/app/api/cooked-recipes/route.ts:214`
- **Issue:** `JSON.parse(JSON.stringify(deductedIngredients))` is used to store a plain array of simple objects. Prisma handles JSON serialization automatically for `Json` fields. This round-trip is unnecessary overhead.
- **Impact:** Minor performance waste; confusing for maintainers who wonder what edge case it handles.
- **Suggested fix:**

```ts
deductedIngredients: deductedIngredients.length > 0 ? deductedIngredients : undefined,
```

**[CR-008]** Ingredient validation after `striptags` + `String()` coercion is partially redundant

- **File:** `src/app/api/cooked-recipes/route.ts:196-202`
- **Issue:** The code calls `striptags(String(i.name || ''))` on line 195, then checks `typeof i?.name === 'string'` on line 198. After the `.map()`, `i.name` is always a string — the type check is vacuously true. The validation should either run _before_ the map (on raw data) or check the _mapped_ values for semantic validity only.
- **Impact:** False sense of validation; the `ingredientsValid` check can never fail on type, only on length. Not a bug, but misleading.
- **Suggested fix:** Validate raw ingredients before mapping, or simplify the post-map check to only length checks.

**[CR-009]** `byId.size < 500` hardcoded pantry item limit in DELETE restoration

- **File:** `src/app/api/cooked-recipes/route.ts:276`
- **Issue:** The 500-item limit for pantry creation during restoration is hardcoded. If the actual pantry limit is defined elsewhere (or changes), this silently diverges.
- **Impact:** Inconsistent pantry limits between creation and restoration paths.
- **Suggested fix:** Extract to a shared constant like `MAX_PANTRY_ITEMS` in `constants.ts`.

**[CR-010]** `normalizeIngredientName` used in deduction but not in restoration — asymmetric matching

- **File:** `src/app/api/cooked-recipes/route.ts:53-55` vs `:260-265`
- **Issue:** `deductPantryItems` matches pantry items using `normalizeIngredientName`, but the DELETE restoration path matches using raw `striptags(i.name)`. If normalization lowercases or trims, a deducted item may not be found during restoration.
- **Impact:** Pantry items not restored on delete, or duplicates created.
- **Suggested fix:** Use `normalizeIngredientName` consistently in both paths (overlaps with CR-001).

#### LOW

**[CR-011]** `force` parameter allows bypassing insufficient ingredient checks without audit logging

- **File:** `src/app/api/cooked-recipes/route.ts:82-84`
- **Issue:** When `force=true` is used and ingredients are insufficient, the operation proceeds silently. There's no audit log entry for forced cooks, making it harder to debug pantry discrepancies.
- **Impact:** Reduced observability for pantry drift investigations.
- **Suggested fix:** Add `logAuditEvent('COOKED_RECIPE_FORCE', { userId: user.id, postId, insufficientIngredients })` when force is used with insufficient ingredients.

**[CR-012]** Error flow control via thrown string-keyed errors is fragile

- **File:** `src/app/api/cooked-recipes/route.ts:172-183` and `:296-316`
- **Issue:** Transaction errors are communicated via `throw new Error('RECIPE_NOT_FOUND')` etc., then caught by string comparison. This pattern is fragile — a typo in either the throw or catch silently falls through to a generic 500.
- **Impact:** Refactoring risk; no compile-time safety.
- **Suggested fix:** Use a discriminated error class:

```ts
class AppError extends Error {
  constructor(
    public code: 'RECIPE_NOT_FOUND' | 'ALREADY_COOKED' | 'DAILY_LIMIT_REACHED',
    message?: string
  ) {
    super(code);
  }
}
```

**[CR-013]** DELETE handler comment says "throws P2025 if already gone" but advisory lock + findFirst makes this unreachable

- **File:** `src/app/api/cooked-recipes/route.ts:243-245`
- **Issue:** The comment and outer catch for P2025 suggest concurrent deletes are handled via Prisma's "record not found" error. But the per-user advisory lock serializes all operations, and `findFirst` returns null if not found (line 252), causing an early `return null` before the `delete` is reached. The P2025 catch is dead code for same-user concurrency. It could only trigger for a cross-user race, but ownership is checked in `findFirst`.
- **Impact:** Dead code / misleading comments. Not harmful, but confusing for maintainers.
- **Suggested fix:** Remove the P2025 catch or document the exact scenario where it could still fire (e.g., cascade deletes from another table).
