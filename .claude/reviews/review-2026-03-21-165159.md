## Code Review — 2026-03-21

### Summary

Auth routes are clean but formulaic. The cooked-recipes route is a 300+ line monolith with several correctness bugs, a race condition gap, and maintainability problems.

### Findings

#### CRITICAL

**[CR-001]** Pantry restoration uses stale in-memory lookup maps after mutations

- **File:** `src/app/api/cooked-recipes/route.ts:261-268`
- **Issue:** `byNameUnit` map is keyed by `${i.name}|${i.unit}` using the _original_ pantry item names, but lookups use `${safeName}|${unit}` where `safeName` is `striptags(d.name)`. If the pantry item name contains HTML tags (stored pre-sanitization), the lookup will never match, causing duplicate pantry items to be created instead of quantities being restored.
- **Impact:** Duplicate pantry items after deleting a cooked recipe; quantity restoration silently fails.
- **Suggested fix:** Normalize the map key the same way:

```ts
const byNameUnit = new Map(allPantryItems.map((i) => [`${striptags(i.name)}|${i.unit}`, i]));
```

**[CR-002]** `deductPantryItems` uses `striptags` on ingredient names from DB but `normalizeIngredientName` for matching — sanitization/matching mismatch

- **File:** `src/app/api/cooked-recipes/route.ts:56-60`
- **Issue:** During deduction, matching uses `normalizeIngredientName()` to compare pantry items and recipe ingredients. But the `deductedIngredients` output uses `striptags(d.name)` (line 102). During restoration (DELETE handler), the lookup uses `striptags(d.name)` against raw pantry names. If `normalizeIngredientName` transforms differently than `striptags` (e.g., lowercasing, trimming whitespace), the deducted item recorded won't match the pantry item during restoration.
- **Impact:** Pantry restoration fails silently — ingredients deducted on cook are never restored on delete.
- **Suggested fix:** Use a consistent normalization function for both matching and recording. Store the pantry item's actual name (or its ID — which is already stored) and rely on ID-based lookup for restoration.

**[CR-003]** Advisory lock namespace collision risk

- **File:** `src/app/api/cooked-recipes/route.ts:188` and `src/app/api/cooked-recipes/route.ts:232`
- **Issue:** `PG_ADVISORY_LOCK_COOKED_RECIPE` is used as the first key, with `hashtext(user.id)` as the second. `hashtext` returns a 32-bit int. The comment acknowledges collision risk at <1M users, but this is a **production advisory lock** — a collision means User A's cook operation blocks User B's entirely unrelated cook operation (or worse, User A's DELETE blocks User B's POST, causing timeouts under load).
- **Impact:** Under moderate concurrency, unrelated users can deadlock or experience elevated latency due to hash collisions.
- **Suggested fix:** Use `pg_advisory_xact_lock(hashtext(user.id || '::cooked'))` (single-key form with a feature-scoped salt) or split the UUID into two deterministic 32-bit integers instead of relying on `hashtext`.

#### HIGH

**[CR-004]** Login response leaks token in JSON body AND sets httpOnly cookie

- **File:** `src/app/api/auth/login/route.ts:28-33`
- **Issue:** The token is returned in the JSON response body (`data: result`) _and_ set as an httpOnly cookie. The entire point of httpOnly cookies is to prevent JavaScript access to the token. Returning it in the response body defeats this — any XSS can read the response and exfiltrate the token.
- **Impact:** httpOnly cookie security is nullified; XSS can steal auth tokens.
- **Suggested fix:** Remove the token from the response body. Return only user data:

```ts
const response = NextResponse.json(
  { success: true, data: { user: result.user }, message: 'Login successful' },
  { status: 200 }
);
```

**[CR-005]** Same token leak on register

- **File:** `src/app/api/auth/register/route.ts:28-33`
- **Issue:** Same as CR-004 — token returned in body alongside httpOnly cookie.
- **Impact:** Same as CR-004.
- **Suggested fix:** Same pattern — strip token from response body.

**[CR-006]** No rate limiting on login endpoint

- **File:** `src/app/api/auth/login/route.ts`
- **Issue:** No rate limiting or brute-force protection. The cooked-recipes endpoint has `MAX_DAILY_COOKS`, but login has nothing.
- **Impact:** Credential stuffing and brute-force attacks are trivially easy.
- **Suggested fix:** Add rate limiting (e.g., by IP or username) via middleware or an in-route check. At minimum, add exponential backoff or account lockout after N failures.

**[CR-007]** No rate limiting on registration endpoint

- **File:** `src/app/api/auth/register/route.ts`
- **Issue:** No rate limiting. An attacker can create unlimited accounts.
- **Impact:** Account spam, resource exhaustion.
- **Suggested fix:** Rate limit by IP. Consider CAPTCHA for registration.

**[CR-008]** `deductPantryItems` silently skips ingredients with unparseable amounts

- **File:** `src/app/api/cooked-recipes/route.ts:67`
- **Issue:** `if (isNaN(recipeAmount) || recipeAmount <= 0) continue;` — if `parseAmount` returns NaN (e.g., for "a handful" or malformed data), the ingredient is silently skipped. The user gets no indication that a pantry deduction was incomplete.
- **Impact:** User thinks pantry was fully deducted but some items were silently skipped. Pantry quantities become inaccurate over time.
- **Suggested fix:** Track skipped ingredients and return them in the response so the user knows what wasn't deducted.

**[CR-009]** POST handler validates ingredient lengths _after_ calling `striptags` but recipe ingredients from DB may have been stored without length limits

- **File:** `src/app/api/cooked-recipes/route.ts:200-205`
- **Issue:** The validation checks `i.name.length <= 200` and `i.unit.length < 50` on data already processed through `striptags(String(...))`. But `striptags` can _increase_ apparent length in edge cases (e.g., if the name is mostly tags and what remains is short). More importantly, this validation runs on _already-stored DB data_ — if it fails, the user can never cook that recipe. There's no admin path to fix it.
- **Impact:** Recipes with oversized ingredient names in the DB become permanently uncookable (pantry deduction skipped silently with only a `console.warn`).
- **Suggested fix:** Truncate rather than reject. The data is already in the DB; rejecting it punishes users for data they can't control:

```ts
name: striptags(String(i.name || '')).slice(0, 200),
```

#### MEDIUM

**[CR-010]** Cooked-recipes route is ~300 lines with business logic inline in the route handler

- **File:** `src/app/api/cooked-recipes/route.ts`
- **Issue:** Three HTTP methods (GET, POST, DELETE) plus a helper function and multiple interfaces are all in one file. The POST handler alone is ~120 lines of transaction logic. This violates the service layer pattern used by the auth routes (which delegate to `authService`).
- **Impact:** Hard to test, hard to maintain, inconsistent architecture.
- **Suggested fix:** Extract pantry deduction and rating recalculation logic into a `CookedRecipeService` following the existing container/service pattern.

**[CR-011]** Inconsistent error response format between auth routes and cooked-recipes

- **File:** `src/app/api/cooked-recipes/route.ts` vs `src/app/api/auth/*/route.ts`
- **Issue:** Auth routes use `ApiResponseHelper` for structured responses. Cooked-recipes uses raw `NextResponse.json({ error: ... })`. Clients must handle two different error shapes.
- **Impact:** Frontend error handling becomes fragile and inconsistent.
- **Suggested fix:** Use `ApiResponseHelper` in cooked-recipes route.

**[CR-012]** Error flow control via thrown string messages is fragile

- **File:** `src/app/api/cooked-recipes/route.ts:180,184,190`
- **Issue:** Business logic errors are thrown as `new Error('RECIPE_NOT_FOUND')` then caught and matched by string comparison. Typos in either location silently fall through to the generic 500. Auth routes have the same pattern (`error.message === 'Authentication required'`).
- **Impact:** A typo in an error string = silent 500 instead of the correct status code. No compiler help.
- **Suggested fix:** Use typed error classes:

```ts
class RecipeNotFoundError extends Error { ... }
// then: if (error instanceof RecipeNotFoundError)
```

**[CR-013]** `change-password` doesn't invalidate existing sessions/tokens

- **File:** `src/app/api/auth/change-password/route.ts:31`
- **Issue:** After changing the password, existing tokens remain valid. If the password was changed because the account was compromised, the attacker's existing session continues to work.
- **Impact:** Password change doesn't fully secure a compromised account.
- **Suggested fix:** Invalidate all existing tokens/sessions on password change (rotate JWT secret per-user, or use a token blocklist, or increment a token version counter).

**[CR-014]** `DELETE` handler doesn't clear the rating cache if the cooked recipe had a rating but a comment also exists

- **File:** `src/app/api/cooked-recipes/route.ts:281-284`
- **Issue:** When `userComment` exists, the rating is preserved — but what if the cooked recipe had a _different_ rating than the comment? The comment's rating and the cooked recipe's rating may conflict, and the stale cooked-recipe rating lingers.
- **Impact:** Rating data inconsistency — the user's rating may reflect a deleted cooked recipe rather than their active comment.
- **Suggested fix:** Document the expected behavior clearly, or always recalculate the aggregate regardless of whether the rating row was deleted.

#### LOW

**[CR-015]** `UUID_REGEX` used both as schema validator and runtime test

- **File:** `src/app/api/cooked-recipes/route.ts:14,224`
- **Issue:** `UUID_REGEX` is used in the Zod schema (line 14) and again via `.test()` (line 224). If it's a regex with the global flag, `.test()` has stateful `lastIndex` behavior that can cause intermittent validation failures.
- **Impact:** Potential intermittent UUID validation failures if the regex has the `g` flag.
- **Suggested fix:** Verify `UUID_REGEX` does not use the `g` flag. If it does, remove it or use a fresh regex instance for `.test()`.

**[CR-016]** Magic number `500` for pantry item limit

- **File:** `src/app/api/cooked-recipes/route.ts:275`
- **Issue:** `byId.size < 500` is a hardcoded pantry size limit with no corresponding constant.
- **Impact:** Inconsistent limits if other code uses a different number.
- **Suggested fix:** Extract to a named constant like `MAX_PANTRY_ITEMS` in `constants.ts`.

**[CR-017]** `JSON.parse(JSON.stringify(deductedIngredients))` is unnecessary

- **File:** `src/app/api/cooked-recipes/route.ts:218`
- **Issue:** `deductedIngredients` is an array of plain objects with primitive values. The round-trip serialization is unnecessary overhead.
- **Impact:** Minor performance waste; confusing to readers.
- **Suggested fix:** Pass `deductedIngredients` directly. Prisma handles JSON serialization.

**[CR-018]** `logServerError` logs the full error object which may contain sensitive data

- **File:** All files
- **Issue:** `logServerError('Change password error:', error)` — if the error contains request body details (e.g., passwords in the stack trace), these end up in logs.
- **Impact:** Potential credential leakage in log aggregators.
- **Suggested fix:** Ensure `logServerError` sanitizes sensitive fields, or log only `error.message` and `error.stack` without the full object.
