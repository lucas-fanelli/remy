## Code Review — 2026-03-21

### Summary

A cooked-recipes API route with pantry deduction logic. Reasonably well-structured with advisory locks and transactional consistency, but contains several bugs, a security gap, and redundant/dead logic.

### Findings

#### CRITICAL

**[CR-001]** DELETE handler restores pantry then sets `restoredAt`, but still deletes the record — `restoredAt` guard is useless

- **File:** `src/app/api/cooked-recipes/route.ts:247-252`
- **Issue:** The code sets `restoredAt` on the cooked recipe to "prevent double-restoration", then immediately deletes the record on line 255. The `restoredAt` field can never be read by a future request because the row is gone. The advisory lock is the only thing preventing double-restoration — the `restoredAt` check is dead code that gives a false sense of safety. If the advisory lock is ever removed or bypassed (e.g., different lock namespace, code refactor), there is no durable guard.
- **Impact:** False safety guarantee. If concurrency control changes, double-restoration (duplicating pantry quantities) becomes possible.
- **Suggested fix:** Either keep the record as a soft-delete (don't call `tx.cookedRecipe.delete`) and rely on `restoredAt` as the guard, or remove the `restoredAt` update entirely since it's dead code. Pick one strategy.

**[CR-002]** `striptags` applied inconsistently — raw ingredient data flows into `deductedIngredients` JSON column via DELETE restoration path

- **File:** `src/app/api/cooked-recipes/route.ts:221-222`
- **Issue:** During restoration in DELETE, `striptags` is applied to `d.name` and `d.unit` before writing back to pantry. But the `deductedIngredients` JSON was written during POST (line 188) using values that were already sanitized. The real problem is the opposite direction: during POST, the `deductedIngredients` array stores `striptags(d.name)` from `deductPantryItems`, but the `amount` field in `deductPantryItems` line 97/102 comes from the parsed numeric `recipeAmount`/`pantryQuantity` — if `parseAmount` returns `Infinity` (e.g., for input `"1e999"`), it passes the `> 0` check on line 68 and gets stored, later bypassing the Zod `.max(10000)` restoration validation.
- **Impact:** A crafted recipe ingredient amount like `"1e999"` could produce `Infinity` in the deducted record if `parseAmount` doesn't guard against it, corrupting pantry quantities on restoration.
- **Suggested fix:** Add `isFinite(recipeAmount)` check alongside `isNaN`:

```typescript
if (isNaN(recipeAmount) || !isFinite(recipeAmount) || recipeAmount <= 0) continue;
```

#### HIGH

**[CR-003]** Validation of `recipeIngredients` is performed AFTER `striptags` and `String()` coercion — the length checks validate sanitized strings, not originals

- **File:** `src/app/api/cooked-recipes/route.ts:179-184`
- **Issue:** Ingredients are mapped through `striptags(String(i.name || ''))` on line 176, then validated for length on line 180. But `striptags` can dramatically shorten a string (e.g., `"<script>".repeat(100)` becomes `""`). The validation passes on the shortened string, but the original DB data was already used to compute the normalized name for matching. This means a maliciously crafted ingredient name with HTML that strips down to a valid-looking string could match an unintended pantry item.
- **Impact:** Incorrect pantry deductions if ingredient names in the DB contain HTML tags that normalize differently after stripping.
- **Suggested fix:** Validate the raw ingredient data BEFORE sanitizing, or reject ingredients that change length significantly after stripping.

**[CR-004]** `UUID_REGEX` used as both a schema pattern and a `RegExp.test()` call — if it has the global flag, `.test()` is stateful

- **File:** `src/app/api/cooked-recipes/route.ts:238`
- **Issue:** `UUID_REGEX.test(cookedRecipeId)` on line 238 — if `UUID_REGEX` is defined with the `/g` flag, `.test()` advances `lastIndex` on each call, causing alternating true/false results for valid UUIDs. The same regex is used in the Zod schema on line 16. Cannot confirm without seeing the constant definition, but this is a known footgun.
- **Impact:** Intermittent 400 errors on valid DELETE requests if the regex is global.
- **Suggested fix:** Verify `UUID_REGEX` does not use the `/g` flag. If it does, remove it or use `RegExp(UUID_REGEX.source).test(...)`.

**[CR-005]** POST handler does not enforce `Content-Length` or body size limit before `request.json()`

- **File:** `src/app/api/cooked-recipes/route.ts:138`
- **Issue:** `request.json()` will attempt to parse arbitrarily large bodies. While Next.js has a default body size limit, relying on framework defaults without explicit enforcement is fragile. A large JSON payload with deeply nested objects could cause CPU spikes during parsing.
- **Impact:** Potential DoS via large request bodies if the framework default is misconfigured or raised.
- **Suggested fix:** Configure `bodyParser` size limits explicitly in the Next.js route config, or check `Content-Length` before parsing.

**[CR-006]** No test file exists for this route

- **File:** `src/app/api/cooked-recipes/route.ts`
- **Issue:** No corresponding test file found in the diff or file listing for the cooked-recipes route. This is a complex route with transaction logic, pantry deduction, restoration, advisory locks, and multiple edge cases — all untested.
- **Impact:** Regressions in pantry deduction, double-delete handling, rating recalculation, or restoration logic will go undetected.
- **Suggested fix:** Write integration tests covering: normal cook, duplicate cook (409), daily limit (429), insufficient ingredients with/without force, DELETE with restoration, DELETE outside restoration window, concurrent requests.

} else if (pantry && byId.size < MAX_PANTRY_ITEMS) {

**[CR-009]** `JSON.parse(JSON.stringify(deductedIngredients))` is unnecessary overhead

- **File:** `src/app/api/cooked-recipes/route.ts:190`
- **Issue:** `deductedIngredients` is an array of plain objects with string and number properties — no Date objects, no circular references, no class instances. The round-trip through `JSON.parse(JSON.stringify(...))` is a no-op deep clone that wastes CPU. Prisma accepts plain objects for JSON columns.
- **Impact:** Unnecessary serialization/deserialization on every cook request.
- **Suggested fix:** Pass `deductedIngredients` directly:

```typescript
deductedIngredients: deductedIngredients.length > 0 ? deductedIngredients : undefined,
```

**[CR-010]** Rating aggregation logic duplicated between POST and DELETE

- **File:** `src/app/api/cooked-recipes/route.ts:202-215, 268-279`
- **Issue:** The pattern of locking the Post row, aggregating ratings, and updating `averageRating`/`reviewCount` is copy-pasted in both handlers. This violates DRY and increases the risk of divergence if the calculation logic changes.
- **Suggested fix:** Extract into a helper function:

```typescript
async function recalculatePostRating(tx: ..., postId: string) {
  await tx.$executeRaw`SELECT id FROM "Post" WHERE id = ${postId} FOR UPDATE`;
  const agg = await tx.rating.aggregate({ ... });
  await tx.post.update({ ... });
}
```

**[CR-011]** DELETE does not validate `Content-Type` but POST does — inconsistent API surface

- **File:** `src/app/api/cooked-recipes/route.ts:229`
- **Issue:** DELETE reads from query params, not body, so `requireJsonContentType` isn't needed. However, there's no validation that the request body is empty. A client sending a JSON body to DELETE would have it silently ignored, which could mask client bugs.
- **Impact:** Minor — client confusion if they expect body params to work on DELETE.
- **Suggested fix:** Document that DELETE uses query params only, or return 400 if a body is present.

**[CR-013]** `force` defaults to `undefined`, treated as falsy — works but `?? false` would be clearer

- **File:** `src/app/api/cooked-recipes/route.ts:148, 172`
- **Issue:** `force` is declared as `boolean | undefined` and later compared with `force === true`. This works but the intermediate `force = parsed.force` leaves it as `undefined` when not provided. Using `?? false` at parse time would make the type `boolean` throughout.
- **Impact:** Readability only.
- **Suggested fix:** `force = parsed.force ?? false;`
