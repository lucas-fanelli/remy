### Findings

#### CRITICAL

**[CR-001]** Race condition between avatar fetch and profile update in PUT handler

- **File:** `src/app/api/users/profile/route.ts:48-51`
- **Issue:** The current avatar is fetched outside the `updateProfile` call with no transaction or row lock. A concurrent request can change the avatar between the `findUnique` and the `updateProfile`, causing the wrong image to be cleaned up (or cleanup to be skipped entirely).
- **Impact:** Orphaned Cloudinary images accumulating (cost), or deletion of the user's current avatar (data loss).
- **Suggested fix:** Move the old-avatar fetch and the update into a single transaction with a `SELECT ... FOR UPDATE` on the user row, or have `updateProfile` return the previous avatar value atomically:

```ts
const { updatedUser, previousAvatar } = await prisma.$transaction(async (tx) => {
  const current = await tx.user.findUnique({ where: { id: user.id }, select: { avatar: true } });
  // perform update inside tx
  const updated = await tx.user.update({ where: { id: user.id }, data: profileData });
  return { updatedUser: updated, previousAvatar: current?.avatar };
});
if (previousAvatar && previousAvatar !== updatedUser.avatar && isCloudinaryUrl(previousAvatar)) {
  cleanupCloudinaryImage(previousAvatar).catch(/* ... */);
}
```

**[CR-002]** `DELETE /api/cooked-recipes` restores pantry items without validating `amount` upper bound or `name` length

- **File:** `src/app/api/cooked-recipes/route.ts:260-295`
- **Issue:** The `deductedIngredients` JSON is stored in the DB and later read back as `unknown[]`. While `amount > 0` and `typeof name === 'string'` are checked, there is no upper bound on `amount` and no length limit on `name`. A tampered or corrupted `deductedIngredients` value (e.g., `amount: 999999999`) would restore an arbitrarily large quantity to the pantry. The `striptags` call on `name` mitigates XSS but not overflow.
- **Impact:** An attacker who can manipulate the stored JSON (e.g., via a separate SQL injection or direct DB access) can give themselves unlimited pantry quantities. Even without malice, a data corruption bug could produce nonsensical pantry state.
- **Suggested fix:** Cap the restored amount to a reasonable maximum and validate name length:

```ts
const MAX_RESTORE_AMOUNT = 10000;
const MAX_NAME_LENGTH = 200;
if (typeof d.amount !== 'number' || d.amount <= 0 || d.amount > MAX_RESTORE_AMOUNT) continue;
if (!d.name || typeof d.name !== 'string' || d.name.length > MAX_NAME_LENGTH) continue;
```

**[CR-003]** Recipe matching endpoint leaks private-user recipes in the fallback path

- **File:** `src/app/api/recipes/match/route.ts:112-118`
- **Issue:** When `pantryPatterns.length === 0` (all pantry item names are empty after filtering), the fallback query uses `user: { isPrivate: false }` correctly. However, the `allCandidates` from the raw SQL path are later batch-fetched via `tx.post.findMany({ where: { id: { in: batchIds } } })` at line ~165 without re-checking `isPrivate`. If a recipe's author toggles their profile to private between the candidate query and the batch fetch, the full recipe data (title, description, image, author info) is still returned. More critically, the raw SQL query only checks `u."isPrivate" = false` at query time — this is a snapshot read, and Prisma's `findMany` at line ~165 does not re-filter. This is a minor window but a real privacy violation.
- **Impact:** Private user recipes could be exposed to other users.
- **Suggested fix:** Add the privacy filter to the batch fetch:

```ts
const batch = await tx.post.findMany({
  where: { id: { in: batchIds }, user: { isPrivate: false } },
  // ...
});
```

**[CR-004]** `hasMore` pagination flag is incorrect — returns false positives

- **File:** `src/app/api/recipes/route.ts:140`
- **Issue:** `hasMore: recipes.length === limit` is wrong. If there are exactly `limit` recipes remaining, `hasMore` will be `true` but the next page will be empty. This is a well-known off-by-one pattern, but more critically, this causes clients to make an unnecessary extra request on every "last page" — and if the client uses this to render infinite scroll, users see a loading spinner that resolves to nothing.
- **Impact:** Broken pagination UX; unnecessary API calls under load.
- **Suggested fix:** Fetch `limit + 1` and use the extra row to determine `hasMore`:

```ts
const recipes = await prisma.post.findMany({
  where,
  // ...
  take: limit + 1,
  skip: offset,
});
const hasMore = recipes.length > limit;
const trimmedRecipes = recipes.slice(0, limit);
```

**[CR-005]** `GET /api/recipes` exposes full `ingredients` and `instructions` JSON blobs in list endpoint

- **File:** `src/app/api/recipes/route.ts:118-133`
- **Issue:** The list endpoint returns `ingredients: recipe.ingredients || []` and `instructions: recipe.instructions || []` for every recipe in the response. These are potentially large JSON arrays (up to 100 ingredients, 50 instructions with 5000-char descriptions each). For a listing page that only shows cards, this is an enormous amount of unnecessary data transfer — a single page of 20 recipes could be several MB.
- **Impact:** Severe performance degradation for mobile clients; excessive bandwidth usage; slow time-to-first-paint. This is effectively a self-inflicted DoS vector — an attacker can request `limit=100` and force the server to serialize and transmit megabytes of JSON.
- **Suggested fix:** Remove `ingredients` and `instructions` from the list response, or add a `fields` parameter. The detail endpoint (`GET /api/recipes/[id]`) should be the only place that returns full recipe data:

```ts
const recipesWithRatings = recipes.map((recipe) => ({
  id: recipe.id,
  title: recipe.title,
  description: recipe.description,
  imageUrl: recipe.imageUrl,
  // ... other summary fields
  // DO NOT include: ingredients, instructions
}));
```

**[CR-006]** Unbounded `deductedIngredients` JSON stored without size validation

- **File:** `src/app/api/cooked-recipes/route.ts:214-217`
- **Issue:** `deductedIngredients` is stored as a JSON column via `JSON.parse(JSON.stringify(deductedIngredients))`. The recipe can have up to 100 ingredients (per schema), each with a name up to 200 chars, but `striptags` is applied to `d.name` in `deductPantryItems` — the stripped output could still be up to 200 chars. With 100 items, this JSON blob could be several KB per cooked recipe. More critically, there is no schema validation on this JSON — the `deductedIngredients` type is defined in-code but Prisma stores it as raw `JsonValue`. On read-back during DELETE, the code trusts `d.pantryItemId` to be a valid UUID without validation.
- **Impact:** Storing `pantryItemId` values that aren't valid UUIDs could cause unexpected Prisma behavior during pantry restoration. A corrupted or maliciously crafted `deductedIngredients` JSON could inject bad data into the pantry.
- **Suggested fix:** Validate `pantryItemId` against `UUID_REGEX` before using it in the query:

```ts
const pantryItemId =
  typeof d.pantryItemId === 'string' && UUID_REGEX.test(d.pantryItemId)
    ? d.pantryItemId
    : undefined;
```
