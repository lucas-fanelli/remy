## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Several security logic errors, duplicated validation code, and a few race condition windows.

### Findings

#### CRITICAL

**[CR-001]** Origin check in logout route is a prefix match — bypasses CSRF

- **File:** `src/app/api/auth/logout/route.ts:11`
- **Issue:** `!appUrl.startsWith(origin)` passes for any origin that is a prefix of the app URL. If `appUrl` is `http://localhost:3000`, then `origin = "http://localhost:300"` (port 300) or `"http://localhost:3"` would pass the check.
- **Impact:** Cross-origin logout CSRF bypass. An attacker on a host whose origin is a prefix of yours can force-logout users.
- **Suggested fix:**

```typescript
const appOrigin = new URL(appUrl).origin;
if (origin && origin !== appOrigin) {
  return NextResponse.json({ error: 'Invalid origin' }, { status: 403 });
}
```

**[CR-002]** Advisory lock on non-existent pantry row acquires no lock

- **File:** `src/app/api/cooked-recipes/route.ts:113`
- **Issue:** `SELECT id FROM "UserPantry" WHERE "userId" = ... FOR UPDATE` returns zero rows if user has no pantry, so no lock is acquired. Two concurrent "mark as cooked" requests can both read the pantry and deduct ingredients, producing negative quantities on a pantry created between requests.
- **Impact:** Negative ingredient quantities, data integrity violation.
- **Suggested fix:** Use `pg_advisory_xact_lock` on the user ID hash instead, or wrap the pantry existence check and creation inside the lock scope.

#### HIGH

**[CR-003]** Missing `requireJsonContentType` on several POST/DELETE endpoints

- **File:** `src/app/api/cooked-recipes/route.ts:78` (POST), `src/app/api/recipes/[id]/like/route.ts:10` (POST), `src/app/api/recipes/[id]/save/route.ts:42` (POST), `src/app/api/notifications/route.ts:48` (POST)
- **Issue:** These endpoints accept `request.json()` but do not enforce `Content-Type: application/json`. The middleware's CSRF check allows requests with `application/json` content type, but these endpoints don't verify it, relying solely on middleware. If middleware config changes, these are exposed.
- **Impact:** Inconsistent defense-in-depth; these endpoints could accept non-JSON requests if middleware is modified.
- **Suggested fix:** Add `requireJsonContentType(request)` at the top of each handler, consistent with other write endpoints.

**[CR-004]** Cloudinary URL validation logic duplicated across 6+ files

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:50-66`, `src/app/api/recipes/[id]/comments/route.ts:80-96`, `src/app/api/recipes/[id]/route.ts:68-82`, `src/app/api/recipes/route.ts:126-140`, `src/app/api/users/profile/route.ts:23-36`
- **Issue:** Identical Cloudinary URL validation (protocol, hostname, path traversal, cloud name check) is copy-pasted across at least 6 route files. Any fix must be applied to all copies.
- **Impact:** Maintenance burden; one copy could diverge. High risk of inconsistent security enforcement.
- **Suggested fix:** Extract to a shared `validateCloudinaryUrl(url: string): NextResponse | null` utility in `src/lib/utils/`.

**[CR-005]** Recipe match endpoint fetches recipes in 3 serial rounds with no caching

- **File:** `src/app/api/recipes/match/route.ts:100-160`
- **Issue:** The endpoint (1) runs a raw SQL query to find candidate IDs, (2) fetches candidates in batches of 100 for ingredient matching, (3) fetches full recipe data for matched IDs in batches of 100. For a user with many pantry items, this is 3+ sequential DB round trips loading up to 200 recipes.
- **Impact:** Slow response times under load; O(n) DB queries where n = number of candidates.
- **Suggested fix:** Combine steps 2 and 3 into a single query that fetches all needed fields. Or fetch full recipe data in step 1 directly with the SQL join.

**[CR-006]** `RecipeFeed` abort controller not cleaned up on unmount

- **File:** `src/components/recipe/RecipeFeed.tsx:93-118`
- **Issue:** `abortControllerRef.current` is set during `loadRecipes` but the effect at line 120 (`useEffect(() => { loadRecipes(true) }, [...])`) doesn't return a cleanup function that aborts in-flight requests when the component unmounts.
- **Impact:** State updates on unmounted component causing React warnings; wasted network requests.
- **Suggested fix:**

```typescript
useEffect(() => {
  loadRecipes(true);
  return () => {
    abortControllerRef.current?.abort();
  };
}, [difficultyFilter, timeFilter, sortOrder, loadRecipes]);
```

#### MEDIUM

**[CR-007]** Notification polling resets backoff on every tab focus

- **File:** `src/hooks/useNotificationPolling.ts:128-133`
- **Issue:** When `visibilityState` changes to visible, `failureTimestampsRef.current = []` resets the backoff even if previous failures were genuine server errors. A flapping server would be hammered every time the user tabs back.
- **Impact:** Amplifies load on a struggling server instead of backing off.
- **Suggested fix:** Only reset failure timestamps after a successful fetch, not on visibility change.

**[CR-008]** `safeRating` returns `null` for `undefined` but the DB column is `Float?`

- **File:** `src/lib/utils/recipe.ts:13`
- **Issue:** `safeRating` maps `undefined` to `null`, but callers already default `averageRating ?? null` or `averageRating ?? 0` inconsistently. In `src/app/api/search/route.ts:68`, it's `safeRating(recipe.averageRating)`, but in `RecipeFeed` the API response already includes the value. The semantics of "null = unrated" vs "0 = unrated" are used inconsistently across the codebase.
- **Impact:** UI may show "0 stars" instead of "No ratings yet" for some unrated recipes, depending on which API endpoint serves the data.
- **Suggested fix:** Standardize: DB `null` = unrated. All API responses should preserve `null`, never convert to `0`. Update `safeRating` callers to stop using `?? 0`.

**[CR-009]** `EditProfileModal` client-side magic bytes check reads only 12 bytes but WebP needs all 12

- **File:** `src/components/profile/EditProfileModal.tsx:89-96`
- **Issue:** `file.slice(0, 12)` reads the first 12 bytes. The WebP check needs bytes 0-3 and 8-11 (indices 0-11), so 12 bytes is exactly right. However, if the file is smaller than 12 bytes, `arrayBuffer` returns fewer bytes and the WebP check accesses `bytes[11]` which is `undefined`, causing a false rejection.
- **Impact:** Files smaller than 12 bytes (edge case) silently rejected with misleading error.
- **Suggested fix:** Add `if (bytes.length < 12) { showError('File is too small'); return; }` before the magic bytes check.

**[CR-010]** `PersistentSearchBar` live search fires on every keystroke with 300ms debounce but doesn't cancel on unmount

- **File:** `src/components/search/PersistentSearchBar.tsx:127-155`
- **Issue:** The `useEffect` for debounced search creates an `AbortController` and sets a timeout, and the cleanup aborts + clears timeout. However, `isMountedRef.current = false` is set in a separate `useEffect` cleanup. If the component unmounts during the 300ms window, the timeout fires, checks `isMountedRef`, and returns — but the fetch may have already started before the ref was set to false.
- **Impact:** Minor: potential state update after unmount in a race window.
- **Suggested fix:** The abort controller cleanup already handles this correctly (abort cancels the fetch). This is low risk.

#### LOW

**[CR-011]** `CommentsSection` declares `imageUrl` with `let` outside `try` block

- **File:** `src/components/recipe/CommentsSection.tsx:96`
- **Issue:** `let imageUrl: string | undefined;` is declared before `try` to be accessible in `catch` for orphan cleanup comments. But the catch block doesn't actually clean up the orphaned image — it just logs a comment about running `npm run cleanup:images`. The variable serves no purpose in the catch block.
- **Impact:** Dead code; misleading comment suggests cleanup happens but it doesn't.
- **Suggested fix:** Move `imageUrl` inside `try` block. Remove the orphan cleanup comments or implement actual cleanup.

**[CR-012]** `SearchResults` truncation logic can break words

- **File:** `src/components/SearchResults.tsx:139`
- **Issue:** `recipe.description.lastIndexOf(' ', 50)` finds the last space before position 50, but if `lastIndexOf` returns -1 (no space in first 50 chars), it falls back to position 50, which could truncate mid-word due to `> 0` check. Should use `>= 0` or `-1` check.
- **Impact:** Cosmetic: rare truncation mid-word for descriptions without spaces in the first 50 characters.
- **Suggested fix:** `const breakPoint = recipe.description.lastIndexOf(' ', 50); const truncateAt = breakPoint > 0 ? breakPoint : 50;`

**[CR-013]** `about/page.tsx` YouTube link hardcoded via BRANDING but icon color hardcoded

- **File:** `src/app/about/page.tsx:205`
- **Issue:** The YouTube icon hover color is hardcoded to `#FF0000` instead of using theme colors. Minor inconsistency with the design system.
- **Impact:** Cosmetic only.
- **Suggested fix:** Use `theme.palette.error.main` or a branding constant.
