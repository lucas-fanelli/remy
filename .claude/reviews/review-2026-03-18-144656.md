## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing app with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes, auth flow, and client components.

### Findings

#### CRITICAL

**[CR-001]** Admin middleware JWT verification bypassed by stale role in token

- **File:** `src/middleware.ts:120-145`
- **Issue:** The admin page gate in middleware verifies the JWT signature and checks `payload.role === 'ADMIN'`, but this uses the role from the JWT which may be stale after demotion. The API routes correctly re-check DB role via `requireAdmin`, but the middleware allows rendering the admin SPA pages to a demoted user until their JWT expires.
- **Impact:** Demoted admin can access admin UI pages (though API calls will fail). Information disclosure of admin dashboard structure and potentially cached data.
- **Suggested fix:** Also verify role from DB in middleware, or accept this as defense-in-depth since API routes do check DB. At minimum, add a comment documenting this intentional tradeoff.

**[CR-002]** `recalc-ratings` endpoint uses raw SQL without parameterization safeguard documentation

- **File:** `src/app/api/admin/recalc-ratings/route.ts:18-32`
- **Issue:** While Prisma's `$executeRaw` with tagged template literals is safe from SQL injection, the raw SQL queries UPDATE all posts unconditionally. There is no concurrency guard — if two admins trigger this simultaneously, the transaction isolation level may cause inconsistent intermediate states depending on the database's default isolation.
- **Impact:** Potential for incorrect rating values during concurrent execution.
- **Suggested fix:** Add an advisory lock or a mutex check:

```typescript
await tx.$executeRaw`SELECT pg_advisory_xact_lock(12345)`;
```

**[CR-003]** No CSRF token validation for cookie-based auth on state-changing requests

- **File:** `src/middleware.ts:155-170`
- **Issue:** The CSRF check relies on `Sec-Fetch-Site`, `Content-Type: application/json`, or custom headers. However, `Sec-Fetch-Site` is not supported in all browsers (notably older Safari versions). For those browsers, a `Content-Type: application/json` header sent via `fetch()` from a malicious page with CORS mode `no-cors` would fail, but a request from a browser extension or non-browser client could bypass this. The `SameSite: strict` cookie mitigates most browser attacks, but the defense is layered incorrectly — `multipart/form-data` requests (used by `/api/upload`) only pass because of the `x-requested-with` header manually added in client code. If any upload client forgets this header, the request is rejected.
- **Impact:** Fragile CSRF protection that depends on client-side cooperation.
- **Suggested fix:** Document the requirement clearly. Consider a double-submit cookie pattern as a more robust fallback.

#### HIGH

**[CR-004]** Notification polling continues after logout — fetches with stale cookie

- **File:** `src/components/Navigation.tsx:225-270`
- **Issue:** The notification polling `useEffect` depends on `[user, fetchNotifications]`. When `logout()` sets `user` to `null`, the effect cleanup runs. However, there's a race: `fetchNotifications` may already be in-flight. The 401 handler calls `logout()` which sets user to null, but if the component re-renders between the state update and the cleanup, `fetchNotifications` could be called again before the effect's cleanup fires.
- **Impact:** Potential infinite logout loop if timing is unlucky (401 → logout → re-render → fetch → 401).
- **Suggested fix:** Add an `AbortController` to the fetch and abort it in the cleanup function:

```typescript
const controller = new AbortController();
// pass { signal: controller.signal } to fetch
return () => { controller.abort(); clearPolling(); ... };
```

**[CR-005]** `cooked-recipes` POST deducts pantry items without verifying sufficient quantity

- **File:** `src/app/api/cooked-recipes/route.ts:115-137`
- **Issue:** When deducting pantry items, the code subtracts `recipeAmount` from `pantryQuantity` and deletes the item if the result is `<= 0`. But it doesn't check if the pantry has _enough_ of the ingredient before deducting. If a recipe needs 500g of flour but the pantry only has 100g, the pantry item is deleted entirely with no warning to the user.
- **Impact:** Silent data loss — users lose track of actual pantry quantities.
- **Suggested fix:** Only deduct if the pantry has sufficient quantity, or at minimum inform the user that their pantry was insufficient:

```typescript
if (unitsCompatible && pantryQuantity >= recipeAmount) {
  // deduct
} else {
  // skip deduction or warn
}
```

**[CR-006]** `recipes/match` loads up to 100 full recipe records into memory for matching

- **File:** `src/app/api/recipes/match/route.ts:62-76`
- **Issue:** `take: 100` recipes with all their ingredients loaded into memory, then iterated with nested loops per pantry item. With large ingredient lists, this is O(recipes × ingredients × pantryItems) in-memory.
- **Impact:** High memory usage and slow response times as recipe count grows. Could cause OOM on serverless with constrained memory.
- **Suggested fix:** Move matching logic to a SQL query that filters on ingredient names, or paginate the matching process.

**[CR-007]** No test coverage for API routes

- **File:** All `src/app/api/**/*.ts` files
- **Issue:** Zero integration or unit tests for any API route handler. All tests are for components, services, and repositories — the actual HTTP layer is untested.
- **Impact:** Regressions in request parsing, response formatting, error handling, and auth checks go undetected.
- **Suggested fix:** Add integration tests using `NextRequest`/route handler invocation for critical paths (auth, recipes CRUD, admin).

**[CR-008]** `AuthContext` logout retry can force-redirect during normal operation

- **File:** `src/contexts/AuthContext.tsx:107-119`
- **Issue:** If both logout attempts fail (e.g., server is temporarily down), the code does `window.location.href = '/'`. This is a hard redirect that discards all client state. The user may not have intended to navigate away — they might be mid-editing a recipe.
- **Impact:** Data loss on force-redirect during transient network issues.
- **Suggested fix:** Show a toast/warning instead of force-redirecting. The user is already logged out client-side.

#### MEDIUM

**[CR-009]** `about/page.tsx` imports `YouTube` icon but it's used only once for a tiny link

- **File:** `src/app/about/page.tsx:3`
- **Issue:** MUI icons are tree-shaken, but the `YouTube` import adds to the page bundle. The about page also hardcodes feature descriptions that duplicate `BRANDING` config patterns.
- **Impact:** Minor bundle bloat.
- **Suggested fix:** Use a named import from `@mui/icons-material/YouTube` for optimal tree-shaking.

**[CR-010]** `PersistentSearchBar` debounce doesn't cancel on unmount properly

- **File:** `src/components/search/PersistentSearchBar.tsx:127-153`
- **Issue:** The cleanup function aborts the controller, but `searchTimeoutRef.current` might already be null if the timeout fired. The `clearTimeout` is called but the fetch may already be in-flight. The abort controller ref is overwritten on each query change, but the previous controller is only aborted at the start of the effect — if the component unmounts during the timeout window, the previous fetch is not aborted.
- **Impact:** Memory leak / state update on unmounted component.
- **Suggested fix:** The cleanup already handles this correctly via `controller.abort()`, but the `abortControllerRef` pattern is redundant with the local `controller`. Remove the ref:

```typescript
// Remove abortControllerRef entirely, use only the local controller in the effect
```

**[CR-011]** `RecipeFeed` infinite scroll uses `scrollY` which doesn't account for all layouts

- **File:** `src/components/recipe/RecipeFeed.tsx:176-183`
- **Issue:** The scroll handler uses `window.innerHeight + window.scrollY >= document.documentElement.scrollHeight - 500`. If the feed is inside a scrollable container (not the window), this won't trigger.
- **Impact:** Infinite scroll may not work in certain layout configurations.
- **Suggested fix:** Use `IntersectionObserver` for more robust infinite scroll detection.

**[CR-012]** Admin comment deletion recalculates ratings for unrelated recipe

- **File:** `src/infrastructure/services/AdminService.ts:218-233`
- **Issue:** After deleting a comment, the code recalculates the recipe's average rating from the `Rating` table. But comments and ratings are separate entities — deleting a comment doesn't delete its associated rating. The recalculation is correct but unnecessary (the rating hasn't changed). This adds latency to every comment deletion.
- **Impact:** Unnecessary database queries on every admin comment deletion.
- **Suggested fix:** Only recalculate if the comment's user also has a rating for that recipe that was deleted.

**[CR-013]** `email` leaked in admin user listing

- **File:** `src/app/admin/users/page.tsx:232`
- **Issue:** The admin users page displays user emails in the table. While this is behind admin auth, the client-side code receives and renders the full email. If the admin page is XSS-vulnerable (unlikely with React but possible), emails could be exfiltrated.
- **Impact:** Email exposure in admin UI stored in browser memory/DOM.
- **Suggested fix:** This is acceptable for admin views, but consider masking emails (e.g., `t***@example.com`) in the UI.

**[CR-014]** `search` API doesn't validate `userId` parameter

- **File:** `src/app/api/recipes/route.ts:37`
- **Issue:** The `userId` query parameter is passed directly to Prisma's `where` clause without UUID validation. While Prisma handles invalid UUIDs gracefully (no match), it would be cleaner to validate.
- **Impact:** Minor — unnecessary database queries with invalid inputs.
- **Suggested fix:** Add `UUID_REGEX.test(userId)` check.

#### LOW

**[CR-015]** `Post` model field `averageRating` default not documented

- **File:** `src/app/api/recipes/[id]/route.ts:20-21`
- **Issue:** The code uses `recipe.averageRating ?? 0` as a fallback. It's unclear if the Prisma schema defaults this field to 0 or null. This pattern is repeated across multiple files.
- **Impact:** Inconsistent handling if schema changes.
- **Suggested fix:** Centralize the default in the repository's `mapToRecipe` method.

**[CR-016]** Unused `Post` model fields in schema

- **File:** `src/infrastructure/repositories/RecipeRepository.ts:25`
- **Issue:** The `Post` model apparently has fields like `dietaryTags`, `calories`, `protein`, `carbs`, `fat` (visible in test mocks) that are never used in the application.
- **Impact:** Dead schema fields consuming storage.
- **Suggested fix:** Remove unused columns via migration or document them as future features.

**[CR-017]** `motion.create()` called at module scope in multiple components

- **File:** `src/app/about/page.tsx:20-21`, `src/components/recipe/RecipeCard.tsx`, etc.
- **Issue:** `const MotionBox = motion.create(Box)` at module scope creates new components on every module evaluation. While React reconciles correctly, this pattern creates unnecessary wrapper components.
- **Impact:** Negligible runtime cost but code smell.
- **Suggested fix:** This is Framer Motion's documented pattern. No change needed.

**[CR-018]** `handleCreateRecipe` in `page.tsx` duplicated in `Navigation.tsx`

- **File:** `src/app/page.tsx:34-52`, `src/components/Navigation.tsx:356-376`
- **Issue:** The recipe creation logic (fetch POST, invalidate cache, handle errors) is duplicated between the home page and navigation component.
- **Impact:** Maintenance burden — changes must be made in two places.
- **Suggested fix:** Extract into a shared hook `useCreateRecipe()`.
