## Code Review — 2026-03-19

### Summary

Large recipe-sharing platform with solid architecture (clean DI, proper auth). Multiple security gaps, race conditions, and data integrity issues found across API routes and client components.

### Findings

#### CRITICAL

**[CR-001]** Recipe match endpoint loads all pantry items into memory without pagination

- **File:** `src/app/api/recipes/match/route.ts:68-70`
- **Issue:** `pantry.items` is loaded entirely into memory via `include: { items: true }`. While `cappedItems` limits to 100, the initial query fetches ALL items from DB. A user with 500 pantry items (the max) sends all 500 over the wire before JS trims to 100.
- **Impact:** Unnecessary memory/bandwidth for users near the 500-item limit.
- **Suggested fix:** Add `take: 100, orderBy: { createdAt: 'desc' }` to the Prisma include query for items.

**[CR-002]** `cooked-recipes` POST endpoint has no Content-Type check bypass for `requireJsonContentType` false positive path

- **File:** `src/app/api/cooked-recipes/route.ts:108`
- **Issue:** The `requireJsonContentType` is called but JSON body parsing failure is handled separately. However, the `DELETE` handler at line 186 has no CSRF `X-Requested-With` header check — it relies solely on middleware. If middleware is bypassed (misconfigured matcher), DELETE has no defense.
- **Impact:** Low risk given middleware covers it, but violates defense-in-depth principle applied to other DELETE handlers.
- **Suggested fix:** Add `headers: { 'X-Requested-With': 'fetch' }` requirement documentation or an explicit check consistent with other routes.

**[CR-003]** Admin user delete race window allows orphaned images

- **File:** `src/app/api/admin/users/[id]/route.ts:54-60`
- **Issue:** Comment in code acknowledges a race: new posts/comments can be created between querying images and cascade-deleting the user. The cleanup script is mentioned but there's no evidence it's actually scheduled anywhere (no cron job, no Vercel cron config).
- **Impact:** Permanent orphaned Cloudinary images accumulating over time, costing storage money.
- **Suggested fix:** Either add a cron configuration (e.g., Vercel `vercel.json` cron) for `cleanup-orphaned-images.ts`, or document the operational requirement explicitly.

**[CR-005]** `validateCloudinaryUrl` path traversal check is incomplete

- **File:** `src/lib/utils/cloudinary-validation.ts:18-19`
- **Issue:** Checks for `..` and `%` in decoded path, but `decodeURIComponent` is called once. Double-encoding (`%252e%252e`) would decode to `%2e%2e` on first pass, then `..` on second. The single decode + `%` check blocks this, but only because `%` is blanket-banned — which also blocks legitimate Cloudinary URLs with encoded characters in filenames.
- **Impact:** Over-restrictive: legitimate image URLs with special characters in public IDs will be rejected. Under-restrictive: unlikely but complex encoding bypass scenarios.
- **Suggested fix:** Replace blanket `%` ban with a proper allowlist of the expected Cloudinary URL path structure: `/cloudname/image/upload/vXXX/folder/publicid.ext`.

**[CR-006]** Notification polling hook doesn't abort in-flight `/api/auth/me` confirmation request on unmount

- **File:** `src/hooks/useNotificationPolling.ts:98-105`
- **Issue:** When a 401 is received, a separate `meController` AbortController is created for the `/api/auth/me` confirmation. But this controller is never aborted on component unmount — only `notificationAbortRef` is aborted in cleanup. If the component unmounts during the confirmation request, state updates (`setIsPollingPaused`, `onAuthInvalid`) will fire on an unmounted component.
- **Impact:** React state update on unmounted component warning; potential double-logout in edge cases.
- **Suggested fix:** Track `meController` in a ref and abort it in the cleanup function, or check `isMountedRef.current` before calling `onAuthInvalid`.

#### HIGH

**[CR-007]** `RecipeFeed` infinite scroll has no deduplication for concurrent IntersectionObserver triggers

- **File:** `src/components/recipe/RecipeFeed.tsx:130-133`
- **Issue:** The `loadingRef` guard prevents concurrent calls, but `intersectionCallback` fires with `rootMargin: '500px'` which can trigger multiple times as the user scrolls. The `lastLoadTimeRef` 500ms debounce helps, but if the first request takes >500ms, a second request can still fire before the first completes because `loadingRef` is only set inside the async function, not at the IntersectionObserver callback level.
- **Impact:** Duplicate recipes loaded (mitigated by the `existingIds` dedup in state setter, but wasteful API calls).
- **Suggested fix:** Set `loadingRef.current = true` synchronously in the observer callback before calling `loadRecipes()`.

**[CR-008]** Admin stats cache is module-level singleton shared across requests

- **File:** `src/infrastructure/services/AdminService.ts:18-19`
- **Issue:** `statsCache` is a module-level variable. In serverless environments (Vercel), this works per-instance but in long-running Node processes, it's shared across all concurrent requests. The 30s TTL mitigates staleness but the cache is never invalidated by organic activity (new users, recipes, comments from non-admin actions).
- **Impact:** Admin dashboard shows stale stats for up to 30 seconds after organic activity. Documented in comments but still a correctness issue.
- **Suggested fix:** Accept the trade-off (it's documented) or reduce TTL to 10s for better freshness.

**[CR-009]** `pantry/[id]` PUT allows setting `quantity` to exactly 0 via `-0` normalization but doesn't validate semantic meaning

- **File:** `src/app/api/pantry/[id]/route.ts:53-55`
- **Issue:** The `-0` normalization is correct, but `quantity: 0` combined with `unit: "g"` or `unit: "cups"` is semantically meaningless (you can't have 0 cups of flour). Only `unit: "to taste"` makes sense with `quantity: 0`. No validation enforces this.
- **Impact:** Confusing pantry data that breaks the "to taste" UX pattern.
- **Suggested fix:** Either warn users when setting quantity to 0 with a measured unit, or document that 0 means "to taste" regardless of unit.

**[CR-010]** `useRecipe` hook uses `isPlaceholderData` but never sets `placeholderData` option

- **File:** `src/hooks/useRecipe.ts:65-69` and `src/app/recipe/[id]/page.tsx:87`
- **Issue:** `isPlaceholderData` is destructured from `useRecipe` but the `useQuery` call never sets `placeholderData` option. `isPlaceholderData` will always be `false`, making the loading overlay at `page.tsx:303-320` dead code.
- **Impact:** Dead code; loading overlay never shows. Users see no feedback when transitioning between recipes.
- **Suggested fix:** Either remove the `isPlaceholderData` overlay, or add `placeholderData` to the query config (e.g., using previously cached recipe data).

#### MEDIUM

**[CR-011]** `Footer.tsx` mailto link length check uses 2000 chars but `mailto:` has no universal limit

- **File:** `src/components/Footer.tsx:53-55`
- **Issue:** The 2000-character check is arbitrary. Different browsers/OS have different limits (IE: 2083, Chrome: ~2M, some mail clients: 1024). The `window.open` approach is more robust than `href`, but the error message references a specific limit.
- **Impact:** Users on restrictive clients may still fail; users on permissive clients are unnecessarily blocked.
- **Suggested fix:** Lower to 1500 for safety or switch to a proper contact form backend.

**[CR-012]** `EditProfileModal` doesn't revoke blob URL when a new file is selected before saving

- **File:** `src/components/profile/EditProfileModal.tsx:84-88`
- **Issue:** The cleanup effect revokes URL on unmount, but if the user selects file A (creating blob URL A), then selects file B (creating blob URL B), blob URL A is never revoked. Only the latest `avatarPreview` is tracked.
- **Impact:** Memory leak proportional to number of file selections in a single session.
- **Suggested fix:** Revoke the previous blob URL in `handleAvatarChange` before setting the new one.

**[CR-013]** `CommentsSection` image upload doesn't validate Cloudinary URL server-side before storing

- **File:** `src/app/api/recipes/[id]/comments/route.ts:70-72`
- **Issue:** `validateCloudinaryUrl` is called, but if the user manually constructs a request with a valid-looking Cloudinary URL that points to someone else's upload, the comment will store it. The `KNOWN LIMITATION` in `upload/route.ts` acknowledges this for recipes but the same applies to comment images.
- **Impact:** Users can reference any Cloudinary image in their comments (low severity since URLs are unguessable).
- **Suggested fix:** Document the limitation consistently or implement upload ownership tracking.

**[CR-014]** `PersistentSearchBar` creates new AbortController on every query change but doesn't abort the timeout

- **File:** `src/components/search/PersistentSearchBar.tsx:127-153`
- **Issue:** Comment says "AbortController is intentionally created OUTSIDE setTimeout". The timeout is cleared via `clearTimeout`, but if the timeout has already fired and `fetch` is in-flight, the previous controller's `abort()` only happens when the effect cleanup runs (on next query change). There's a gap where two fetches could be in-flight simultaneously if the user types fast enough to change query before the 300ms debounce and the previous fetch hasn't completed.
- **Impact:** Stale search results briefly appearing before being replaced. Minor UX issue.
- **Suggested fix:** Move `controller.abort()` to the beginning of the timeout callback, before `setIsSearching(true)`.

**[CR-016]** `RecipeCard` warns about non-Cloudinary URLs in dev but still renders them in production

- **File:** `src/components/recipe/RecipeCard.tsx:60-64`
- **Issue:** The `useEffect` warns in dev about non-Cloudinary URLs, but the `src` fallback on line 127 uses the raw `recipe.imageUrl` if it's not a Cloudinary URL. This means if bad data gets into the DB, non-Cloudinary images render silently in production.
- **Impact:** If an attacker or bug inserts a malicious image URL, it renders in the card. The CSP `img-src` directive in middleware limits sources, but `https://res.cloudinary.com` is the only allowed external source, so non-Cloudinary URLs would be blocked by CSP anyway. This is defense-in-depth working correctly.
- **Suggested fix:** The CSP handles it. Consider using the fallback image (`/chef-logo.png`) for non-Cloudinary URLs in the component as well for consistency.
