## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured with good security hardening, but several real bugs and security gaps exist in transaction handling, race conditions, and input validation.

### Findings

#### CRITICAL

**[CR-001]** Cloudinary cleanup script uses wrong advisory lock key format

- **File:** `src/scripts/cleanup-orphaned-images.ts:108`
- **Issue:** Uses single-key `pg_advisory_lock(48882)` but the constant `PG_ADVISORY_LOCK_CLEANUP` is designed for two-key form `pg_advisory_xact_lock(key1, key2)` as documented in `src/lib/constants.ts`. Single-key locks occupy a different namespace and could collide with two-key locks from other features.
- **Impact:** Concurrent runs of different features could interfere with each other due to lock namespace collision.
- **Suggested fix:**

```sql
SELECT pg_advisory_lock(48882, 0)
-- and unlock:
SELECT pg_advisory_unlock(48882, 0)
```

**[CR-002]** Cooked recipe DELETE restores pantry items by name, not by pantryItemId

- **File:** `src/app/api/cooked-recipes/route.ts:226-240`
- **Issue:** When restoring pantry items after deleting a cooked recipe, the code finds items by `name` match instead of using the stored `pantryItemId`. If a user renamed a pantry item between cooking and deleting, restoration goes to the wrong item or creates a duplicate.
- **Impact:** Data integrity issue — pantry quantities become incorrect after undoing a cooked recipe.
- **Suggested fix:** Look up by `pantryItemId` first, fall back to name only if the original item was deleted:

```typescript
const existingItem = await tx.pantryItem.findUnique({
  where: { id: d.pantryItemId },
});
if (!existingItem) {
  // Item was deleted, try by name
  const byName = await tx.pantryItem.findFirst({
    where: { pantry: { userId: user.id }, name: d.name },
  });
  // ...
}
```

**[CR-003]** `striptags` import missing in cooked-recipes route at module level

- **File:** `src/app/api/cooked-recipes/route.ts:11`
- **Issue:** `striptags` is imported but the import uses a default import syntax. If the `striptags` package exports differently than expected (ESM vs CJS), this could fail silently at runtime in certain bundler configurations. More critically, the `validatedNotes` sanitization happens before the transaction, but the `notes` field is also used inside `cookedRecipeSchema` which doesn't sanitize — if Zod validation passes HTML, it gets stored.
- **Impact:** Stored XSS potential if notes are ever rendered as raw HTML in a future feature.
- **Suggested fix:** The current flow is actually safe since `striptags` runs before DB write. No action needed — downgrading to informational.

#### HIGH

**[CR-004]** Recipe match endpoint holds advisory lock for entire transaction including HTTP response serialization

- **File:** `src/app/api/recipes/match/route.ts:72-73`
- **Issue:** The per-user advisory lock is held for the entire `$transaction` which includes multiple DB queries, in-memory matching computation (up to 4 seconds wall-clock), and batch fetches. The `timeout: 15000` means the lock can be held for up to 15 seconds.
- **Impact:** If a user opens two tabs simultaneously, the second request blocks for up to 15 seconds. The advisory lock provides no benefit here since reads don't need serialization — this is a read-only endpoint.
- **Suggested fix:** Remove the advisory lock. The endpoint only reads data; concurrent reads don't produce inconsistent state. If deduplication is needed, use a short-lived cache key instead.

**[CR-005]** `user.email` exposed in admin user listing despite `maskEmail`

- **File:** `src/infrastructure/services/AdminService.ts:47-48`
- **Issue:** `maskEmail` only masks the display, but the admin users page search filter (`search: 'test'`) queries `email: { contains: options.search, mode: 'insensitive' }`. An admin can enumerate exact emails by binary-searching character by character.
- **Impact:** Email enumeration by any admin user, violating the principle of masking emails.
- **Suggested fix:** Remove email from the search OR clause in `getAllUsers`, or accept that admin users should have email access and remove the masking.

**[CR-006]** No CSRF protection on logout endpoint

- **File:** `src/app/api/auth/logout/route.ts:4-14`
- **Issue:** The logout endpoint skips cookie check if no `auth_token` present (idempotent), but more importantly, the middleware CSRF check requires `X-Requested-With` header. The `AuthContext.logout()` sends this header, but if a user is tricked into visiting a page that triggers a POST to `/api/auth/logout`, the middleware would block it. However, the check in `AuthContext` sends `Content-Type: application/json` which isn't a "simple" content type, so the CSRF layer works. No actual bug here.
- **Impact:** None — downgrading. The existing CSRF middleware protects this.

**[CR-007]** `RecipeFeed` infinite scroll can fire duplicate loads

- **File:** `src/components/recipe/RecipeFeed.tsx:127-131`
- **Issue:** The `loadRecipes` function aborts the previous controller and checks `loadingRef.current`, but `AbortController.abort()` is called before the guard check. If `loadingRef.current` is true and `reset` is false, the function returns early — but it already aborted the in-flight request. This means a filter change during loading aborts the current request without starting a new one.
- **Impact:** User sees stale results after changing filters while a load is in progress. The aborted request sets `loading=false` in `finally`, but no new request starts.
- **Suggested fix:** Move the abort after the early return check, or always proceed with a new request when `reset=true` (which it does — this only affects non-reset appends).

**[CR-008]** Comment image URLs accept any Cloudinary URL without ownership tracking

- **File:** `src/app/api/recipes/[id]/comments/route.ts:55-56`
- **Issue:** The comment explicitly notes this as a "KNOWN LIMITATION" but it's still a real issue. Any authenticated user can reference any Cloudinary URL uploaded by any other user in their comments. Since Cloudinary URLs contain the cloud name, an attacker who knows the cloud name can construct valid URLs to reference other users' private uploads.
- **Impact:** Content attribution bypass — users can embed others' uploaded images.
- **Suggested fix:** Track upload ownership in a DB table mapping `publicId -> userId`, validate on write.

#### MEDIUM

**[CR-009]** `safeRating` function is a no-op that adds confusion

- **File:** `src/lib/utils/recipe.ts:12-14`
- **Issue:** `safeRating` converts `undefined` to `null` but passes through `null` and numbers unchanged. This is used in 5+ API routes. The function name implies sanitization but does almost nothing — it doesn't clamp values, validate ranges, or handle NaN.
- **Impact:** Misleading API surface. If `averageRating` in the DB is somehow `NaN` or negative, it passes through unchecked.
- **Suggested fix:** Either remove the function and use `?? null` inline, or make it actually validate:

```typescript
export function safeRating(value: number | null | undefined): number | null {
  if (value == null) return null;
  if (!Number.isFinite(value) || value < 0 || value > 5) return null;
  return Math.round(value * 10) / 10;
}
```

**[CR-010]** `sanitize` in Footer mailto only strips control chars, not full injection vectors

- **File:** `src/components/Footer.tsx:63-65`
- **Issue:** The `sanitize` function strips `\x00-\x1F\x7F` but doesn't strip other problematic characters for mailto URIs like `%0A` (newline after encoding) which could inject extra headers in some email clients. However, `encodeURIComponent` runs after sanitize, so raw newlines would be encoded. The real risk is the comment acknowledges: encoded characters expand the URL, and the 1500-char limit may not be sufficient.
- **Impact:** Low — `encodeURIComponent` handles the actual encoding safely. The sanitize step is defense-in-depth as documented.

**[CR-011]** Notification polling `fetchNotifications` can cause state updates after unmount

- **File:** `src/hooks/useNotificationPolling.ts:76-77`
- **Issue:** The `isMountedRef` check happens after `await fetch()` but the `finally` block only checks `controller.signal.aborted`. If the component unmounts between the fetch completing and the `isMountedRef` check on line 97, `setNotifications` and `setUnreadCount` can fire on an unmounted component. The `isMountedRef` checks at lines 90 and 97 handle the main path, but the `failureTimestampsRef.current.push(now)` on line 112 and `setIsPollingPaused(true)` on line 120 don't check `isMountedRef`.
- **Impact:** React warning "Can't perform a React state update on an unmounted component" in edge cases.
- **Suggested fix:** Add `if (!isMountedRef.current) return;` before `setIsPollingPaused(true)` on lines 120 and 131.

**[CR-012]** Admin delete user transaction timeout mismatch

- **File:** `src/app/api/admin/users/[id]/route.ts:45-46`
- **Issue:** `SET LOCAL statement_timeout = '55s'` but the Prisma transaction timeout is `60000ms` (60s). The statement timeout is per-statement, not per-transaction. A cascade delete with many related records could have individual statements under 55s but the total transaction exceeding 60s, causing a Prisma timeout that doesn't release the advisory lock cleanly (advisory locks auto-release on transaction end, so this is actually fine).
- **Impact:** Low — the advisory lock releases on transaction rollback. But the 5-second gap between statement timeout and transaction timeout is unnecessarily tight.

**[CR-013]** `EditProfileModal` website validation allows `javascript:` URLs via timing gap

- **File:** `src/components/profile/EditProfileModal.tsx:113-125`
- **Issue:** Client-side validation checks `http://` or `https://` prefix, but the server-side `updateProfileSchema` in `schemas.ts` uses Zod's `.url()` which accepts any valid URL. The server-side `UserService.updateProfile` also validates protocol, so this is caught. However, the Zod schema's `.refine()` for protocol only runs if `.url()` passes first, creating a complex validation chain.
- **Impact:** None in practice — server catches it. But the duplicated validation logic across 3 layers (component, Zod schema, service) is fragile.

**[CR-014]** `useRecipe` hook `select` transform runs on every render

- **File:** `src/hooks/useRecipe.ts:76`
- **Issue:** `select: (data) => data.recipe` creates a new function reference on every render, causing React Query to re-run the selector unnecessarily.
- **Impact:** Minor performance — React Query's structural sharing mitigates this, but the selector function should be stable.
- **Suggested fix:**

```typescript
const selectRecipe = (data: RecipeResponse) => data.recipe;
// ...
select: selectRecipe,
```
