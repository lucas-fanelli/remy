## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. The codebase is generally well-structured, but has several security gaps, race conditions, and error handling issues that need attention.

### Findings

#### CRITICAL

**[CR-001]** Unvalidated recipe ingredient structure enables DoS via crafted JSON

- **File:** `src/app/api/cooked-recipes/route.ts:131`
- **Issue:** `recipe.ingredients` is cast to `RecipeIngredient[]` with only a shallow `every(i => typeof i?.name === 'string')` check. A malicious user who created a recipe with deeply nested objects or extremely long string values in `amount`/`unit` fields could cause excessive memory usage or slow processing in `deductPantryItems`.
- **Impact:** Denial of service via crafted recipe data that passes the shallow type check but causes expensive operations.
- **Suggested fix:** Add Zod validation for the ingredient structure before processing, or at minimum validate `amount` and `unit` are strings with bounded length:

```ts
if (
  !recipeIngredients.every(
    (i) =>
      typeof i?.name === 'string' &&
      i.name.length < 200 &&
      typeof i?.amount === 'string' &&
      i.amount.length < 50 &&
      typeof i?.unit === 'string' &&
      i.unit.length < 50
  )
)
  continue;
```

**[CR-002]** `extractAuthToken` used inconsistently — some routes use `requireAuth`, others manually extract and verify

- **File:** `src/app/api/recipes/route.ts:133-144`, `src/app/api/recipes/match/route.ts:49-56`, `src/app/api/recipes/suggest/route.ts:20-28`
- **Issue:** `POST /api/recipes`, `GET /api/recipes/match`, and `POST /api/recipes/suggest` manually extract tokens and call `tokenService.verify()` instead of using `requireAuth()`. This bypasses any future centralized auth logic (e.g., token revocation, session validation) and duplicates auth code.
- **Impact:** Inconsistent auth enforcement. If `requireAuth` is updated (e.g., to check DB for banned users), these routes won't benefit.
- **Suggested fix:** Replace manual token extraction with `requireAuth(request)` in all three routes.

**[CR-003]** `logout` route doesn't invalidate the JWT server-side

- **File:** `src/app/api/auth/logout/route.ts:1-15`
- **Issue:** Logout only clears the httpOnly cookie. The JWT remains valid until expiry (7 days per `cookies.ts:4`). If the cookie is captured before logout (e.g., via XSS in a dependency, or from browser storage forensics), the token can be replayed.
- **Impact:** Session remains valid for up to 7 days after logout. Combined with the `sameSite: 'lax'` setting, this is a residual session risk.
- **Suggested fix:** Implement a server-side token denylist (Redis/DB) checked in `requireAuth`, or reduce JWT expiry to 1 hour with a refresh token mechanism.

#### HIGH

**[CR-004]** Race condition in comment PATCH: rating recalculation is not atomic

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:81-99`
- **Issue:** The rating upsert, aggregate, and post update happen in a transaction, but two concurrent comment edits with ratings can interleave their aggregations. Transaction isolation level (default `READ COMMITTED` in Postgres) doesn't prevent this — both transactions can read the same pre-update aggregate.
- **Impact:** `averageRating` on the post could be stale or incorrect after concurrent rating updates.
- **Suggested fix:** Use `SELECT ... FOR UPDATE` on the post row before the aggregate, or use a serializable transaction for the rating update portion.

**[CR-005]** `RecipeFeed` doesn't deduplicate on filter change with concurrent fetches

- **File:** `src/components/recipe/RecipeFeed.tsx:107-170`
- **Issue:** While `abortControllerRef` cancels the previous fetch, there's a window where the `requestIdRef` check at line ~146 races with the state update. The `setRecipes` call uses a Set-based dedup, but the `setRecipeLikes` and `setRecipeComments` maps are spread without dedup — stale data from an earlier request ID could update engagement state.
- **Impact:** UI could briefly show stale like/comment counts after rapid filter changes.
- **Suggested fix:** Move the `thisRequestId !== requestIdRef.current` check before _all_ state updates, not just `setRecipes`.

**[CR-006]** `useNotificationPolling` auto-reset breaker could cause infinite retry loops

- **File:** `src/hooks/useNotificationPolling.ts:121-128`
- **Issue:** The circuit breaker auto-resets after 5 minutes in `scheduleNext()`. If the underlying issue persists (e.g., server is down), it will trip again after 10 failures, then auto-reset again — creating an infinite retry cycle that wastes bandwidth.
- **Impact:** Continuous failed requests every 5 minutes for the entire session duration when the server is down.
- **Suggested fix:** Use exponential backoff for the breaker cooldown period (5min, 10min, 20min, etc.) instead of a fixed 5-minute reset.

**[CR-007]** Admin user delete has no protection against deleting the requesting admin

- **File:** `src/app/api/admin/users/[id]/route.ts:29-31`
- **Issue:** While self-deletion is checked (`id === authResult.userId`), there's no check for the case where the admin demotes themselves first in another tab, then this request proceeds. The `authResult` was verified at the top, but by the time the transaction runs, the requesting user might no longer be admin.
- **Impact:** Low probability race, but a demoted admin could still complete an in-flight delete.
- **Suggested fix:** Re-verify the requesting user's admin role inside the transaction.

**[CR-008]** `Footer.tsx` mailto link is vulnerable to header injection

- **File:** `src/components/Footer.tsx:56-60`
- **Issue:** `formData.subject` and `formData.name` are interpolated into the mailto URI via `encodeURIComponent`, but `formData.email` entered by the user is placed in the body without sanitization. A crafted email address containing newlines could inject additional mailto headers in some email clients.
- **Impact:** Email header injection in legacy email clients.
- **Suggested fix:** Strip newlines from all user inputs before constructing the mailto link:

```ts
const sanitize = (s: string) => s.replace(/[\r\n]/g, '');
```

#### MEDIUM

**[CR-009]** `RecipeCard` warns on non-Cloudinary URLs but still renders them

- **File:** `src/components/recipe/RecipeCard.tsx:68-72`
- **Issue:** The dev warning for non-Cloudinary URLs is logged, but the image is still rendered. This inconsistency with `CommentsSection` (which uses `isCloudinaryUrl` as a guard) means recipe cards could render attacker-controlled image URLs if data is corrupted.
- **Impact:** Potential for tracking pixels or offensive content via non-Cloudinary image URLs in recipes.
- **Suggested fix:** Either enforce Cloudinary-only URLs in the API layer (reject on create/update) or add the same `isCloudinaryUrl` guard in the render path.

**[CR-010]** `PersistentSearchBar` creates AbortController outside setTimeout, leaking on rapid typing

- **File:** `src/components/search/PersistentSearchBar.tsx:119-147`
- **Issue:** The comment says this is intentional, but creating the AbortController before the timeout means each keystroke creates a controller that won't be used if the timeout is cleared. While the cleanup function aborts it, this creates unnecessary AbortController instances during rapid typing.
- **Impact:** Minor memory churn during fast typing. Not a bug, but the comment claims it's "correct as-is" when it's actually slightly wasteful.
- **Suggested fix:** Create the AbortController inside the setTimeout callback instead, and use a ref to track whether cleanup should abort.

**[CR-011]** `isClient` state initialization in `RecipeTemplate` is incorrect

- **File:** `src/app/recipe/[id]/template.tsx:18`
- **Issue:** `const [isClient, setIsClient] = useState(typeof window !== 'undefined')` — during SSR, `typeof window` is `'undefined'`, so `isClient` starts as `false`. But during client hydration, `typeof window !== 'undefined'` is `true`, so the initial state is `true`, causing a hydration mismatch — the exact thing the pattern is supposed to prevent.
- **Impact:** Potential hydration mismatch on first render. The `useEffect` on line 21 is redundant since `isClient` is already `true` on the client.
- **Suggested fix:**

```ts
const [isClient, setIsClient] = useState(false);
useEffect(() => {
  setIsClient(true);
}, []);
```

**[CR-012]** `pantry/page.tsx` client-side duplicate check uses `normalizeIngredientName` but server uses case-insensitive DB query

- **File:** `src/app/pantry/page.tsx:172-178` vs `src/app/api/pantry/route.ts:119-122`
- **Issue:** Client checks `normalizeIngredientName(item.name) === normalizeIngredientName(formData.name.trim())`, but the server checks `name: { equals: name.trim(), mode: 'insensitive' }`. These are different algorithms — `normalizeIngredientName` strips plurals and special chars, while Prisma's insensitive mode only folds case. A name like "tomatoes" would match "tomato" on the client but not on the server.
- **Impact:** Client shows "already exists" dialog for items the server would accept as new, or vice versa.
- **Suggested fix:** Use the same normalization on both sides, or remove the client-side check and rely solely on the server's 409 response.

**[CR-013]** `SearchResults` component `truncateAtWord` can return empty string

- **File:** `src/components/SearchResults.tsx:39`
- **Issue:** `text.lastIndexOf(' ', maxLen)` returns -1 if there's no space before `maxLen`. The ternary `idx > 0 ? idx : maxLen` handles this, but if the text is exactly `maxLen` characters with no spaces, it returns the full text without ellipsis, which is correct — but if `maxLen` is 0, it returns `"..."` which is wrong.
- **Impact:** Edge case only (maxLen is hardcoded to 50), but the function is fragile.
- **Suggested fix:** Guard against edge cases:

```ts
function truncateAtWord(text: string, maxLen: number): string {
  if (!text || maxLen <= 0) return '';
  if (text.length <= maxLen) return text;
  const idx = text.lastIndexOf(' ', maxLen);
  return text.substring(0, idx > 0 ? idx : maxLen) + '...';
}
```

**[CR-014]** `MatchedRecipes` doesn't show loading feedback during fetch

- **File:** `src/components/recipe/MatchedRecipes.tsx:53-68`
- **Issue:** Both `loading` states return `null`, so the user sees nothing while matched recipes are being loaded. Combined with the `RecipeFeed` below it (which also returns nothing while loading), the home page appears completely empty for authenticated users during initial load.
- **Impact:** Poor UX — authenticated users see a blank page until both fetches complete.
- **Suggested fix:** Show a skeleton or loading indicator instead of returning `null`.
