## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured with good security practices (httpOnly cookies, CSRF protection, advisory locks). However, several critical and high-severity issues exist around race conditions, missing authorization, information leakage, and denial-of-service vectors.

### Findings

#### CRITICAL

**[CR-001]** Recipe match endpoint has no pagination on DB pre-filter, enabling DoS

- **File:** `src/app/api/recipes/match/route.ts:108-117`
- **Issue:** The raw SQL `LIMIT ${limit}` applies to the _outer_ `candidates` CTE, but the `DISTINCT` + `jsonb_array_elements` lateral join can produce far more intermediate rows than `limit`. With many recipes and ingredients, this query scans the entire `Post` table (the CTE has no index-friendly filter before the lateral join).
- **Impact:** A single authenticated request with `limit=500` can cause significant DB load, potentially a DoS vector.
- **Suggested fix:** Add a WHERE clause to the CTE that pre-filters by `createdAt` or uses a GIN `@>` containment operator instead of lateral-join matching. Alternatively, enforce a hard cap lower than 500.

**[CR-002]** `averageRating` set to 0 instead of null when all ratings are deleted

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:95`
- **Issue:** When recalculating after a rating update, if `_avg.rating` is null (no ratings left), the code sets `averageRating: 0` instead of `null`. The domain type declares `averageRating` as `number | null`, and the recalc-ratings endpoint correctly uses `NULL` for unrated recipes. This inconsistency means a recipe that had ratings removed shows "0.0" instead of "No ratings yet".
- **Impact:** Data integrity — unrated recipes display misleading 0.0 rating.
- **Suggested fix:**

```typescript
averageRating: ratingAggregation._avg.rating != null
  ? Math.round(ratingAggregation._avg.rating * 10) / 10
  : null,  // not 0
```

**[CR-003]** Admin user deletion collects all images but cascade-deletes posts first

- **File:** `src/app/api/admin/users/[id]/route.ts:56-62`
- **Issue:** Inside the transaction, `userPosts` and `userComments` are fetched, then `tx.user.delete` cascade-deletes posts and comments. If the Prisma schema has `onDelete: Cascade`, the `findMany` must happen _before_ the delete — which it does. However, `post.findMany` and `comment.findMany` are not locked with `FOR SHARE`, so a concurrent insert of a new post/comment between the reads and the delete will orphan that image in Cloudinary permanently.
- **Impact:** Orphaned Cloudinary images on concurrent writes during user deletion.
- **Suggested fix:** Add `FOR SHARE` locks on the post/comment queries, or accept the race and rely on the orphan cleanup script (which exists).

**[CR-004]** `search` route exposes recipes from private users

- **File:** `src/app/api/recipes/route.ts:62-93`
- **Issue:** The `GET /api/recipes` endpoint has no filter for `user.isPrivate`. Any recipe from a private user appears in the public feed and search results. The `/api/search/route.ts:56` correctly filters `user: { isPrivate: false }`, but the main recipes endpoint does not.
- **Impact:** Privacy violation — private users' recipes are publicly visible.
- **Suggested fix:**

```typescript
const where: Prisma.PostWhereInput = {
  user: { isPrivate: false },
};
```

#### HIGH

**[CR-005]** User deletion endpoint lacks statement timeout

- **File:** `src/app/api/admin/users/[id]/route.ts:47-63`
- **Issue:** The admin user deletion transaction acquires advisory locks and performs multiple queries but has no `statement_timeout`. A user with thousands of posts/comments could cause the transaction to hold locks for an extended period.
- **Impact:** Long-running transaction can block other operations and exhaust DB connections.
- **Suggested fix:** Add `SET LOCAL statement_timeout = '30s'` at the start of the transaction, similar to the recalc-ratings endpoint.

**[CR-006]** `cooked-recipes` POST validates ingredient structure but doesn't sanitize ingredient names

- **File:** `src/app/api/cooked-recipes/route.ts:152-158`
- **Issue:** The ingredient structure validation checks `typeof i?.name === 'string' && i.name.length < 200` but the recipe's `ingredients` JSON comes from untrusted user input (stored when recipe was created). If a recipe's ingredient name contains SQL metacharacters, the `normalizeIngredientName` function processes it, but the pantry deduction uses `normalizeIngredientName` which only does string operations — no SQL injection risk here. However, the 200-char check silently skips matching for oversized names rather than failing, which could cause pantry deductions to silently not happen.
- **Impact:** Silent data inconsistency — pantry items not deducted if ingredient names are malformed.
- **Suggested fix:** Log a warning when skipping ingredient validation so issues are detectable.

**[CR-007]** Notification polling `fetchNotifications` can be called before `user` check in visibility handler

- **File:** `src/hooks/useNotificationPolling.ts:145-147`
- **Issue:** The `handleVisibility` callback inside `useEffect` captures `fetchNotifications` which checks `if (!user) return;`. But between the time `user` changes to null (logout) and the effect cleanup runs, a visibility change can trigger a fetch with stale closure. The fetch will return 401, trigger the `onAuthInvalid` callback, which calls `logout` again.
- **Impact:** Double logout on tab switch during logout; potential infinite loop if `onAuthInvalid` re-triggers state changes.
- **Suggested fix:** Check `isMountedRef.current` and `pollingStoppedRef.current` in `handleVisibility` before calling `fetchNotifications`.

**[CR-008]** `RecipeFeed` infinite scroll has no deduplication across filter changes

- **File:** `src/components/recipe/RecipeFeed.tsx:159-162`
- **Issue:** When `loadRecipes(reset=true)` is called, it sets `recipes` to the new data. But if two rapid filter changes both trigger `reset=true`, the second response may arrive after the first, causing the first response's recipes to flash briefly. The `requestIdRef` check on line 148 handles this, but there's a window where `setRecipes` from the first call executes before the second call's guard triggers.
- **Impact:** Brief visual flicker of wrong results during rapid filter changes.
- **Suggested fix:** Move the `requestIdRef` check before _all_ state updates, not just after `json()`.

**[CR-009]** `pantry/[id]/route.ts` PUT allows setting quantity to exactly 0 via `-0` normalization but doesn't handle `NaN` from `parseFloat` of non-numeric strings

- **File:** `src/app/api/pantry/[id]/route.ts:52-55`
- **Issue:** The validation checks `isNaN(parsed) || !isFinite(parsed)` which correctly rejects NaN and Infinity. However, the final `data` object uses `parseFloat(quantity)` again on line 93 without the validation, meaning if `quantity` was modified between validation and usage (unlikely in this flow but a defensive coding gap), it could produce unexpected results. More importantly, the response fetches the updated item in a _separate_ query (line 96), creating a TOCTOU window.
- **Impact:** The returned item may not reflect the exact state written if concurrent updates occur.
- **Suggested fix:** Return the updated item from `updateMany` result or use `update` with ownership in the where clause and return the result directly.

#### MEDIUM

**[CR-010]** `about/page.tsx` hardcodes YouTube and creator info despite BRANDING config

- **File:** `src/app/about/page.tsx:175-180`
- **Issue:** The YouTube link uses `BRANDING.youtube` correctly, but the creator section hardcodes the avatar gradient and uses `BRANDING.creator.initials` — no actual avatar image support. This is inconsistent with how branding is intended to work.
- **Impact:** Maintainability — rebranding requires code changes beyond config.
- **Suggested fix:** Add `creator.avatar` to BRANDING config or document this limitation.

**[CR-011]** `RecipeCard` fallback image logic exposes internal path

- **File:** `src/components/recipe/RecipeCard.tsx:102-104`
- **Issue:** If `recipe.imageUrl` is not a Cloudinary URL, the card falls back to `/chef-logo.png`. This means any non-Cloudinary URL stored in the DB (e.g., from before the Cloudinary validation was added) gets replaced with the logo, with no indication to the user that their image is missing.
- **Impact:** User confusion — old recipes may silently lose their images.
- **Suggested fix:** Show a "broken image" indicator or log a warning when non-Cloudinary URLs are encountered.

**[CR-012]** `middleware.ts` rate limit map has no max size enforcement that scales

- **File:** `src/middleware.ts:67-78`
- **Issue:** The eviction logic on line 74 only removes _one_ oldest entry when over 500. Under a DDoS with many unique IPs, the map grows to 500, evicts one, adds one, net zero — but the linear scan on every request is O(n). With 500 entries, each request scans the entire map, plus the 5% probabilistic scan.
- **Impact:** Performance degradation under high-cardinality IP attack.
- **Suggested fix:** Evict a batch (e.g., 50) entries when over threshold, or use an LRU structure.

**[CR-013]** `Footer.tsx` contact form `mailto` link has 2000 char limit but `maxLength` on message is 2000

- **File:** `src/components/Footer.tsx:55-61`
- **Issue:** The mailto URL includes the name, email, subject line, and encoded message. With a 2000-char message plus the other fields, the total URL can easily exceed the 2000-char limit checked on line 58. The check is on `mailtoLink.length`, not just `message.length`, so it's correct — but the UX feedback ("Please shorten it") comes via `alert()` which is jarring.
- **Impact:** Poor UX — users can fill the form completely but then get a browser alert.
- **Suggested fix:** Show an inline error or reduce `maxLength` to ~1500 to account for encoding overhead.

**[CR-014]** `useCreateRecipe` hook doesn't invalidate feed cache properly

- **File:** `src/hooks/useCreateRecipe.ts:17`
- **Issue:** `queryClient.invalidateQueries({ queryKey: ['recipes'] })` invalidates React Query cache, but `RecipeFeed` uses `fetch` directly, not React Query. The invalidation has no effect on the feed.
- **Impact:** New recipes don't appear in the feed without manual refresh.
- **Suggested fix:** Either migrate `RecipeFeed` to use React Query, or trigger the reload via the `onSuccess` callback (which `Navigation.tsx` does with `router.refresh()`).

**[CR-015]** `profile/[username]/page.tsx` followers/following pages don't handle unauthenticated users

- **File:** `src/app/profile/[username]/followers/page.tsx:37`
- **Issue:** `if (!isAuthenticated) return;` inside useEffect prevents fetching but doesn't redirect or show any UI. The page just hangs with `loading=true` forever for unauthenticated users.
- **Impact:** Blank page for unauthenticated users visiting follower/following pages.
- **Suggested fix:** Redirect to `/auth` or show a "sign in to view" message.

#### LOW

**[CR-016]** `logServerError` uses dynamic `import()` for Sentry on every error

- **File:** `src/lib/utils/logger.ts:9`
- **Issue:** Every call to `logServerError` triggers a dynamic import of `@sentry/nextjs`. While the module is cached after first load, the promise chain adds unnecessary overhead and the `.catch()` swallows import errors silently in production.
- **Impact:** Minor performance overhead; silent Sentry misconfiguration in production.
- **Suggested fix:** Import Sentry once at module level with a `try/catch`, or cache the import promise.

**[CR-017]** `getDifficultyColor` warns once per unique difficulty value but the `Set` grows unbounded

- **File:** `src/lib/utils/recipe.ts:18`
- **Issue:** `warnedDifficulties` is a module-level `Set` that grows with each new unknown difficulty value. In a long-running server process, this is a minor memory leak if many unique values are encountered.
- **Impact:** Negligible memory leak in practice; cosmetic issue.
- **Suggested fix:** Use a bounded cache (e.g., max 100 entries) or skip the deduplication.

**[CR-018]** `EditRecipeModal` review step shows empty ingredients/instructions from blank rows

- **File:** `src/components/recipe/EditRecipeModal.tsx:473-490`
- **Issue:** The review step renders `ingredients.length` and `instructions.length` counts including blank rows that will be filtered on submission. Users see "Ingredients (3)" but only 2 are filled.
- **Impact:** Misleading review count; cosmetic issue.
- **Suggested fix:** Filter before counting: `ingredients.filter(i => i.name.trim()).length`.
