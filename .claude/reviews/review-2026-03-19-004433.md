## Code Review — 2026-03-19

### Summary

Large Next.js recipe-sharing app with clean architecture. Generally well-structured with good security patterns (httpOnly cookies, CSRF layering, advisory locks). Several data validation gaps, missing error propagation paths, and one rate-limit bypass under load.

### Findings

#### CRITICAL

**[CR-001]** Rate-limit eviction under load bypasses protection

- **File:** `src/middleware.ts:~143-150`
- **Issue:** When `rateLimitMap` hits 500 entries, the eviction strategy removes oldest entries to make room. Under high traffic from many IPs, active rate-limit entries for abusive IPs get evicted, resetting their counter and effectively bypassing the rate limit.
- **Impact:** An attacker orchestrating requests from a moderate botnet can cause legitimate rate-limit entries to be evicted, allowing sustained abuse of auth endpoints (login brute-force).
- **Suggested fix:** Replace time-based eviction with LRU eviction that preserves entries with the highest `count` values, or switch to a sliding window counter backed by Redis/Upstash as the code already warns about.

#### HIGH

**[CR-003]** Admin user PATCH returns 500 instead of 404 for non-existent user

- **File:** `src/app/api/admin/users/[id]/route.ts:80-100`
- **Issue:** When `promoteToAdmin` or `demoteToUser` targets a non-existent user ID, Prisma throws `P2025`, which falls through to the generic 500 handler (`logServerError`). No Prisma error check exists in the PATCH handler unlike the DELETE handler.
- **Impact:** Admin dashboard shows generic "Failed to update user role" instead of "User not found". False error alerts in monitoring.
- **Suggested fix:**

```typescript
} catch (error) {
  if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === 'P2025') {
    return NextResponse.json({ error: 'User not found' }, { status: 404 });
  }
  logServerError('Error updating user role:', error);
  return NextResponse.json({ error: 'Failed to update user role' }, { status: 500 });
}
```

**[CR-004]** Pantry `unit` field has no maximum length validation

- **File:** `src/app/api/pantry/route.ts:73-78` and `src/app/api/pantry/[id]/route.ts:55-58`
- **Issue:** The POST and PUT pantry endpoints validate that `unit` is not empty but never check its length. `name` is capped at `MAX_ITEM_NAME_LENGTH` (200), but `unit` can be arbitrarily long.
- **Impact:** A malicious user can store multi-KB unit strings, bloating the database and causing rendering issues in the UI.
- **Suggested fix:**

```typescript
if (unit !== undefined && unit.length > 50) {
  return NextResponse.json({ error: 'Unit too long (max 50 characters)' }, { status: 400 });
}
```

**[CR-005]** Missing `Content-Type` validation on change-password route

- **File:** `src/app/api/auth/change-password/route.ts:8`
- **Issue:** Unlike `login`, `register`, and other mutation routes, `change-password` does not call `requireJsonContentType(request)`. While the middleware CSRF check protects against cross-origin attacks, this is an inconsistency that could cause confusion during refactoring.
- **Impact:** A same-origin request with `Content-Type: text/plain` gets a vague "Invalid JSON body" error instead of the clear 415 "Content-Type must be application/json".
- **Suggested fix:** Add `const ctError = requireJsonContentType(request); if (ctError) return ctError;` before body parsing.

**[CR-006]** Saved recipes endpoint missing rating data

- **File:** `src/app/api/users/[username]/saved/route.ts:57-70`
- **Issue:** The formatted response maps `likesCount` and `commentsCount` but omits `averageRating` and `totalRatings` (reviewCount). The profile endpoint (`/api/users/[username]/profile`) correctly includes these fields for saved recipes.
- **Impact:** Any client using the standalone saved-recipes endpoint cannot display ratings, creating an inconsistent UX if this endpoint is consumed independently.
- **Suggested fix:**

```typescript
const formattedRecipes = savedRecipes.map(({ post }) => ({
  // ... existing fields
  averageRating: safeRating(post.averageRating),
  totalRatings: post.reviewCount ?? 0,
}));
```

#### MEDIUM

**[CR-007]** `RecipeCard` logs console warning on every mount for non-Cloudinary images

- **File:** `src/components/recipe/RecipeCard.tsx:64-67`
- **Issue:** The `useEffect` calls `console.warn` for every non-Cloudinary `imageUrl` on mount. In feeds with many recipes, this spams the console and has a per-render cost.
- **Impact:** Console noise in development; minor performance overhead in production from string concatenation on each render.
- **Suggested fix:** Remove the effect entirely or gate it behind `process.env.NODE_ENV === 'development'` with a Set to deduplicate warnings.

**[CR-008]** `SearchResults` uses IIFE in JSX for text truncation

- **File:** `src/components/SearchResults.tsx:128-130`
- **Issue:** `(() => { const idx = recipe.description.lastIndexOf(' ', 50); return recipe.description.substring(0, idx > 0 ? idx : 50) + '...'; })()` — an immediately-invoked function expression inside JSX is hard to read and creates a new function on every render.
- **Impact:** Readability and minor GC pressure.
- **Suggested fix:** Extract to a `truncateDescription(text: string, maxLen: number)` utility function.

**[CR-010]** Footer mailto link truncation uses magic number

- **File:** `src/components/Footer.tsx:54-59`
- **Issue:** `if (mailtoLink.length > 2000)` uses a hardcoded 2000 limit. The actual browser limit varies (Chrome ~2MB, IE ~2083, Safari ~80K). The fallback opens `mailto:` with no subject/body, losing the user's message entirely.
- **Impact:** Users who write long messages have their content silently dropped.
- **Suggested fix:** Use a higher limit (e.g., 8000) and show a toast/warning when falling back, or copy the message to clipboard before opening mailto.

**[CR-011]** Admin stats query creates a date without timezone awareness

- **File:** `src/infrastructure/services/AdminService.ts:203-204`
- **Issue:** `const today = new Date(); today.setHours(0, 0, 0, 0);` uses the server's local timezone, not UTC. If the server runs in UTC but users are in different timezones, "new today" counts will be off.
- **Impact:** `newUsersToday` and `newRecipesToday` stats are timezone-dependent on the server process.
- **Suggested fix:** Use UTC explicitly: `today.setUTCHours(0, 0, 0, 0);` and ensure the SQL comparison uses the same timezone basis.

**[CR-013]** `MotionProvider` state updates could be batched

- **File:** `src/contexts/MotionContext.tsx:38-41`
- **Issue:** `setSource` calls three separate `setState` functions (`setSourceType`, `setRecipeId`, `setLayoutId`). In React 18+, these are auto-batched in event handlers, but in async contexts they could cause three re-renders.
- **Impact:** Minor performance; three re-renders instead of one in edge cases.
- **Suggested fix:** Consolidate into a single state object: `const [motion, setMotion] = useState({ sourceType: null, recipeId: null, layoutId: null })`.

**[CR-014]** `useAdminGuard` redirects on every render while loading

- **File:** `src/hooks/useAdminGuard.ts:9-11`
- **Issue:** The `useEffect` depends on `[user, isAdmin, isLoading, router]`. When `isLoading` transitions from `true` to `false`, if the user is not admin, it calls `router.push('/')`. This is correct, but the returned `shouldRedirect` boolean is never used by any consumer — all admin pages check `isReady` or `guardLoading`.
- **Impact:** Dead code (`shouldRedirect` return value).
