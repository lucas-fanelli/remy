## Code Review — 2026-03-21

### Summary

A cooked-recipes API route with pantry deduction logic. Generally well-structured with advisory locks and transaction safety, but contains several bugs around data integrity, a potential DoS vector, and multiple maintainability issues.

### Findings

#### CRITICAL

**[CR-001]** Pantry restoration uses unsanitized `striptags` key for lookup but original DB name for storage — key mismatch

- **File:** `src/app/api/cooked-recipes/route.ts:247-248`
- **Issue:** `byNameUnit` map is keyed by `striptags(i.name)` of the _current_ pantry item, but the lookup key uses `striptags(d.name)` from the _deducted record_. If a pantry item was renamed between cooking and deletion, or if `striptags` produces different results on the stored name vs the original name (e.g., the DB name has HTML that was stripped during deduction but re-added via a different flow), the lookup silently fails and a duplicate pantry item is created instead of restoring the existing one.
- **Impact:** Duplicate pantry items, incorrect quantities after restore.
- **Suggested fix:** Normalize both sides consistently — use `normalizeIngredientName` (same function used during deduction) instead of raw `striptags` for the map key:

```ts
const byNameUnit = new Map(
  allPantryItems.map((i) => [`${normalizeIngredientName(i.name)}|${i.unit}`, i])
);
// ...
const existingItem =
  (d.pantryItemId ? byId.get(d.pantryItemId) : undefined) ??
  byNameUnit.get(`${normalizeIngredientName(safeName)}|${unit}`);
```

**[CR-002]** `deductPantryItems` throws a bare `Error` with an attached property — the catch block casts unsafely

- **File:** `src/app/api/cooked-recipes/route.ts:88` and `src/app/api/cooked-recipes/route.ts:262`
- **Issue:** `throw Object.assign(new Error('INSUFFICIENT_INGREDIENTS'), { insufficientIngredients })` attaches data to the error. The catch block at line 262 uses `(error as Error & { insufficientIngredients: ... }).insufficientIngredients`. If Prisma wraps this error (which it can in `$transaction`), the `insufficientIngredients` property is lost, and the response sends `undefined` to the client.
- **Impact:** Client receives `{ error: "...", insufficientIngredients: undefined }` — the user cannot see which ingredients are insufficient.
- **Suggested fix:** Use a custom error class that Prisma won't swallow, or catch inside the transaction and return a discriminated result instead of throwing:

```ts
// Inside the transaction, instead of throwing:
if (insufficientIngredients.length > 0 && !force) {
  return { type: 'INSUFFICIENT' as const, insufficientIngredients };
}
// Then check the return type outside the transaction.
```

**[CR-003]** Rating aggregation race: POST locks Post row _after_ the rating upsert

- **File:** `src/app/api/cooked-recipes/route.ts:213-215`
- **Issue:** The `SELECT ... FOR UPDATE` on the Post row happens _after_ the `rating.upsert`. Two concurrent requests can both upsert their ratings, then both read stale aggregation results. The lock must be acquired _before_ the upsert to serialize the entire rating mutation + aggregation cycle.
- **Impact:** `averageRating` and `reviewCount` on Post can be incorrect (last writer wins with stale data).
- **Suggested fix:** Move the `FOR UPDATE` lock before the `rating.upsert`:

```ts
if (rating !== undefined) {
  await tx.$executeRaw`SELECT id FROM "Post" WHERE id = ${postId} FOR UPDATE`;
  await tx.rating.upsert({ ... });
  const ratingAggregation = await tx.rating.aggregate({ ... });
  // ...
}
```

#### HIGH

**[CR-004]** `parseAmount` return value `NaN` is checked but `Infinity` is not

- **File:** `src/app/api/cooked-recipes/route.ts:65`
- **Issue:** `parseAmount(ingredient.amount)` — if the function returns `Infinity` (e.g., `"1/0"`), the check `isNaN(recipeAmount) || recipeAmount <= 0` passes, and `pantryQuantity >= Infinity` is false, pushing to `insufficientIngredients`. With `force=true`, this silently deletes the pantry item. More critically, if `parseAmount` ever returns a very large finite number from malformed input, it could wipe pantry quantities.
- **Impact:** Malformed recipe ingredient data can cause incorrect pantry deductions.
- **Suggested fix:**

```ts
if (isNaN(recipeAmount) || recipeAmount <= 0 || !isFinite(recipeAmount) || recipeAmount > 10000)
  continue;
```

**[CR-005]** No pagination metadata returned from GET

- **File:** `src/app/api/cooked-recipes/route.ts:128`
- **Issue:** The GET response returns `{ cookedRecipes, total }` but no `page`, `limit`, `totalPages`, or `hasMore`. Clients cannot paginate without knowing how many pages exist or which page they're on.
- **Impact:** Frontend must re-derive pagination state or guess, leading to off-by-one errors or infinite scroll bugs.
- **Suggested fix:**

```ts
return NextResponse.json({
  cookedRecipes,
  total,
  page,
  limit,
  totalPages: Math.ceil(total / limit),
});
```

**[CR-006]** `console.warn` used instead of `logServerError` for operational warnings

- **File:** `src/app/api/cooked-recipes/route.ts:199` and `src/app/api/cooked-recipes/route.ts:242`
- **Issue:** Two `console.warn` calls bypass the structured logger (`logServerError` / a `logWarn` equivalent). In production, these may be lost or unindexed depending on the logging infrastructure.
- **Impact:** Operational issues (corrupted ingredients, invalid deducted shapes) go undetected in monitoring.
- **Suggested fix:** Use the project's structured logger consistently.

**[CR-007]** Restored pantry item quantity can exceed the 10000 cap when a new item is created

- **File:** `src/app/api/cooked-recipes/route.ts:261`
- **Issue:** When an existing item is found, `Math.min(existingItem.quantity + d.amount, 10000)` caps the quantity. But when creating a _new_ pantry item (line 268), `d.amount` is used directly — it could be up to 10000 (from the Zod schema), but there's no cap on the create path. This is inconsistent; the Zod schema allows `amount: 10000` which is fine for a single item, but the inconsistency signals a missing invariant.
- **Impact:** Minor — the Zod schema caps at 10000, so a new item can't exceed that. But if the schema changes, this becomes a bug. Inconsistent capping is a code smell.
- **Suggested fix:** Apply `Math.min(d.amount, 10000)` on the create path too, or extract a constant.

#### MEDIUM

**[CR-008]** `UUID_REGEX` used as both a Zod schema pattern and a `.test()` guard — regex statefulness risk

- **File:** `src/app/api/cooked-recipes/route.ts:12` and `src/app/api/cooked-recipes/route.ts:227`
- **Issue:** If `UUID_REGEX` has the global (`g`) flag, `.test()` is stateful — it advances `lastIndex` on each call, causing alternating true/false results. Without seeing the constant definition, this is a latent bug if anyone adds the `g` flag.
- **Impact:** DELETE endpoint intermittently rejects valid UUIDs.
- **Suggested fix:** Verify `UUID_REGEX` does not use the `g` flag. If it does, use `UUID_REGEX.test(cookedRecipeId)` after resetting `lastIndex`, or create a new RegExp each time. Better: use `z.string().uuid()` for the query param too.

**[CR-009]** `deductPantryItems` applies updates sequentially — could be batched

- **File:** `src/app/api/cooked-recipes/route.ts:93-103`
- **Issue:** Each pantry item is updated with a separate `await` inside a loop. For recipes with many ingredients, this creates many sequential round-trips to the database inside a transaction (holding the advisory lock).
- **Impact:** Increased transaction duration under load, higher lock contention, slower response times.
- **Suggested fix:** Use `Promise.all` for the updates since they're independent within the transaction, or use raw SQL `UPDATE ... FROM (VALUES ...)` for a single round-trip.

**[CR-010]** `JSON.parse(JSON.stringify(deductedIngredients))` is a no-op deep clone

- **File:** `src/app/api/cooked-recipes/route.ts:207`
- **Issue:** `deductedIngredients` is an array of plain objects with primitive values. The `JSON.parse(JSON.stringify(...))` clone is unnecessary — Prisma will serialize it to JSON on its own. This adds CPU overhead and obscures intent.
- **Impact:** Wasted CPU cycles, confusing code.
- **Suggested fix:**

```ts
deductedIngredients: deductedIngredients.length > 0 ? deductedIngredients : undefined,
```

**[CR-011]** Transaction isolation level not specified — default may allow phantom reads

- **File:** `src/app/api/cooked-recipes/route.ts:161` and `src/app/api/cooked-recipes/route.ts:233`
- **Issue:** `prisma.$transaction(async (tx) => { ... })` uses the default isolation level (typically `READ COMMITTED` in PostgreSQL). The advisory locks mitigate per-user concurrency, but two different users rating the same recipe concurrently could produce stale aggregation results since the `aggregate()` call reads committed data from the other transaction mid-flight.
- **Impact:** Rare but possible incorrect `averageRating`/`reviewCount` values when multiple users rate simultaneously.
- **Suggested fix:** The `FOR UPDATE` on the Post row (if moved before upsert per CR-003) serializes per-post, which is sufficient. Ensure CR-003 is fixed and this becomes a non-issue.

**[CR-012]** DELETE handler restores pantry items but doesn't validate that the pantry still belongs to the same user

- **File:** `src/app/api/cooked-recipes/route.ts:244`
- **Issue:** `tx.userPantry.findUnique({ where: { userId: user.id } })` correctly scopes to the user. But `tx.pantryItem.findMany({ where: { pantryId: pantry.id } })` trusts that `pantry.id` belongs to the user. If `userPantry` has a bug where the `userId` unique constraint is violated (two pantries for one user), you'd fetch items from the wrong pantry. This is defensive, but the lack of a join means you're trusting the data model invariant.
- **Impact:** Low probability but could restore items to wrong pantry.
- **Suggested fix:** Use `include: { items: true }` on the `findUnique` call (same pattern as POST) to avoid the separate query and ensure items are scoped correctly.

**[CR-014]** `striptags` called redundantly on the same data

- **File:** `src/app/api/cooked-recipes/route.ts:73-74`, `96`, `101`, `190-193`, `252-253`
- **Issue:** `striptags` is called on `ingredient.name` and `ingredient.unit` in both `deductPantryItems` (lines 73-74, 96, 101) _and_ in the caller that builds `recipeIngredients` (lines 190-193). The data is stripped twice. Similarly, in the DELETE handler, `striptags` is called on data that was already stripped when it was stored.
- **Impact:** Wasted CPU, code confusion about where sanitization is the "source of truth".
- **Suggested fix:** Strip once at the boundary (when building `recipeIngredients`), and document that `deductPantryItems` expects pre-sanitized input.

**[CR-015]** `force` parameter is not documented in the response for insufficient ingredients

- **File:** `src/app/api/cooked-recipes/route.ts:262-268`
- **Issue:** When `INSUFFICIENT_INGREDIENTS` is caught, the response tells the client to "Send force: true" but the successful response (line 233) doesn't indicate whether `force` was used. A client retrying with `force: true` has no confirmation that the force flag was honored vs. ingredients being sufficient on retry.
- **Impact:** Minor UX confusion for API consumers.
- **Suggested fix:** Include `forced: true` in the 201 response when `force` was used and there were insufficient ingredients.
