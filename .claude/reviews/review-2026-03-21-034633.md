**[CR-001]** SQL injection via unsanitized `likePatterns` in raw query

- **File:** `src/app/api/recipes/match/route.ts:101-110`
- **Issue:** `pantryNames` are derived from user-controlled pantry item names. While `escapeLike` escapes `%`, `_`, and `\`, the values are interpolated into a raw SQL query via `Prisma.join(likePatterns)`. Prisma's tagged template parameterization handles scalar values, but `Prisma.join()` produces a `Prisma.Sql` fragment that is spliced directly into the query. If a pantry item name contains a single quote or other SQL metacharacters beyond LIKE wildcards, this can break the query or enable injection depending on the Prisma version's `join` implementation.
- **Impact:** Potential SQL injection leading to data exfiltration or manipulation.
- **Suggested fix:** Validate/sanitize pantry item names before using them in raw queries, or use parameterized `ANY($1::text[])` with a single array parameter instead of `Prisma.join`:

```ts
const likePatterns = pantryPatterns.map((name) => `%${escapeLike(name)}%`);
allCandidates = await tx.$queryRaw<{ id: string; ingredients: unknown }[]>`
  SELECT p.id, p.ingredients
  FROM "Post" p
  JOIN "User" u ON u.id = p."userId"
  WHERE u."isPrivate" = false
    AND p.ingredients IS NOT NULL AND jsonb_typeof(p.ingredients) = 'array' AND jsonb_array_length(p.ingredients) <= 100
    AND EXISTS (
      SELECT 1 FROM jsonb_array_elements(p.ingredients) AS elem
      WHERE lower(elem->>'name') LIKE ANY(${likePatterns}::text[]) ESCAPE '\\'
    )
  ORDER BY p.id
  LIMIT ${limit}
`;
```

**[CR-002]** Pantry restoration on DELETE can create unlimited pantry items (no cap on array length)

- **File:** `src/app/api/cooked-recipes/route.ts:268-307`
- **Issue:** When restoring deducted ingredients on cooked recipe deletion, the code iterates over `cookedRecipe.deductedIngredients` (a JSON column) and creates new `pantryItem` records for items that no longer exist. There is no limit on how many items can be created. An attacker could craft a cooked recipe with a large `deductedIngredients` array (up to whatever the JSON column allows), then delete it to flood the pantry with thousands of items. The `deductedIngredients` field is stored at creation time from `deductedIngredients` computed during POST, but the POST path has no cap on the number of recipe ingredients (the recipe schema allows up to 100 ingredients, and the deduction loop processes all of them). More critically, `deductedIngredients` is a JSON column — if the stored data was tampered with (e.g., via direct DB access or another bug), the restoration loop has no bound.
- **Impact:** Resource exhaustion — a user's pantry could grow unbounded, degrading database performance and UI rendering.
- **Suggested fix:** Add a cap on the number of items restored:

```ts
const deducted = cookedRecipe.deductedIngredients as unknown[];
const MAX_RESTORE_ITEMS = 100;
for (const raw of deducted.slice(0, MAX_RESTORE_ITEMS)) {
```

**[CR-003]** `DELETE /api/users/profile` does not revoke existing JWT tokens beyond cookie clearing

- **File:** `src/app/api/users/profile/route.ts:95-102`
- **Issue:** The comment claims "other active sessions are automatically invalidated because requireAuth calls validateToken, which does a DB lookup." However, if `validateToken` caches results or if there is any token validation path that doesn't hit the DB (e.g., JWT signature-only validation), deleted user tokens remain valid. The code relies entirely on an undocumented implementation detail of `validateToken`. If that function is ever optimized to skip the DB lookup (a common performance optimization), all sessions for deleted users remain active.
- **Impact:** Deleted user accounts could retain active authenticated sessions, accessing resources they shouldn't.
- **Suggested fix:** Implement an explicit token blocklist or session table that is cleared on account deletion, rather than relying on user record absence:

```ts
// Before deleting the user, explicitly invalidate all sessions
await tx.session.deleteMany({ where: { userId: user.id } });
// Then delete the user
await tx.user.delete({ where: { id: user.id } });
```

**[CR-004]** Race condition in recipe rating aggregation during POST cooked-recipes

- **File:** `src/app/api/cooked-recipes/route.ts:227-229`
- **Issue:** The `SELECT ... FOR UPDATE` lock on the Post row is acquired _after_ the `rating.upsert` call. A concurrent request could upsert a rating between the first request's upsert and its aggregate, causing the aggregate to include the concurrent rating but the subsequent post update to be overwritten by the other transaction's aggregate (which may not include the first rating). The lock must be acquired _before_ the upsert to serialize the entire read-modify-write cycle.
- **Impact:** Rating averages can become inconsistent, showing stale or incorrect values.
- **Suggested fix:** Move the `FOR UPDATE` lock before the `rating.upsert`:

```ts
if (rating !== undefined) {
  // Lock FIRST, then upsert + aggregate
  await tx.$executeRaw`SELECT id FROM "Post" WHERE id = ${postId} FOR UPDATE`;

  await tx.rating.upsert({
    where: { userId_postId: { userId: user.id, postId } },
    create: { userId: user.id, postId, rating },
    update: { rating },
  });

  const ratingAggregation = await tx.rating.aggregate({
    // ...
  });
  // ...
}
```

**[CR-005]** `createRecipeSchema` allows `imageUrl` to be any URL — SSRF via Cloudinary validation bypass

- **File:** `src/app/api/recipes/route.ts:180-183`
- **Issue:** The schema requires `imageUrl: z.string().min(1).url()` and then validates it against Cloudinary. However, if `validateCloudinaryUrl` only checks the URL prefix/domain and the Cloudinary cloud name is guessable, an attacker could craft a URL like `https://res.cloudinary.com/<cloud_name>/image/upload/../../internal-endpoint` to potentially reach internal services via Cloudinary's fetch/remote capabilities. More importantly, the `validated.imageUrl` check is `if (validated.imageUrl)` — but `imageUrl` is required by the schema (no `.optional()`), so this condition is always truthy. If the schema ever changes to make `imageUrl` optional, the fallthrough would silently skip validation. This is not a bug today but is a latent critical path.
- **Impact:** If Cloudinary URL validation is insufficient, SSRF attacks could probe internal infrastructure.
- **Suggested fix:** Add strict URL pattern validation in the Zod schema itself as defense-in-depth:

```ts
imageUrl: z.string().min(1).url().refine(
  (url) => url.startsWith('https://res.cloudinary.com/'),
  'Image must be a Cloudinary URL'
),
```
