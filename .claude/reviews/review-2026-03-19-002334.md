## Code Review — 2026-03-19

### Summary

Large recipe-sharing platform with clean architecture. Solid auth, transaction safety, and test coverage. Several issues found: one stack-overflow crash path, orphaned resource cleanup gaps, and serverless-hostile patterns.

### Findings

#### CRITICAL

**[CR-001]** Stack overflow in avatar preview for files over ~1MB

- **File:** `src/components/profile/EditProfileModal.tsx:104`
- **Issue:** `btoa(String.fromCharCode(...new Uint8Array(fullBuffer)))` spreads the entire file buffer as function arguments. For a 5MB file, this creates ~5.2 million arguments, causing `RangeError: Maximum call stack size exceeded`.
- **Impact:** Avatar upload crashes the browser tab for any image larger than ~1-2MB, despite the 5MB limit being advertised.
- **Suggested fix:**

```typescript
// Replace:
const base64 = btoa(String.fromCharCode(...new Uint8Array(fullBuffer)));
// With chunked conversion:
const bytes = new Uint8Array(fullBuffer);
let binary = '';
const chunkSize = 8192;
for (let i = 0; i < bytes.length; i += chunkSize) {
  binary += String.fromCharCode(...bytes.subarray(i, i + chunkSize));
}
const base64 = btoa(binary);
```

**[CR-002]** Admin user deletion leaks orphaned Cloudinary images

- **File:** `src/app/api/admin/users/[id]/route.ts:38-42`
- **Issue:** Only `Post.imageUrl` is collected for Cloudinary cleanup. `Comment.imageUrl` and `User.avatar` are ignored, leaving orphaned images in Cloudinary after user deletion.
- **Impact:** Accumulated storage costs and data that should have been deleted per user request persists indefinitely.
- **Suggested fix:**

```typescript
const userPosts = await tx.post.findMany({ where: { userId: id }, select: { imageUrl: true } });
const userComments = await tx.comment.findMany({
  where: { userId: id },
  select: { imageUrl: true },
});
const userAvatar = await tx.user.findUnique({ where: { id }, select: { avatar: true } });
await tx.user.delete({ where: { id } });
const imageUrls = [
  ...userPosts.map((p) => p.imageUrl),
  ...userComments.map((c) => c.imageUrl),
  userAvatar?.avatar,
].filter(Boolean);
```

#### HIGH

**[CR-003]** In-memory recipe match cache is ineffective in serverless

- **File:** `src/app/api/recipes/match/route.ts:42-43`
- **Issue:** `matchCache` is a module-level `Map` with 10s TTL. In serverless (Vercel), each cold start creates a new empty map. Under load, requests hit different instances with independent caches, making hit rates near zero while still consuming memory.
- **Impact:** False sense of caching; memory consumed without benefit. Cache poisoning across users is also possible since keys are userId-based but responses are shared state.
- **Suggested fix:** Remove the in-memory cache entirely (the endpoint is already scoped to authenticated users and capped at 200 rows), or use Redis/Vercel KV if caching is needed.

**[CR-004]** Recipe match raw query crashes on non-array ingredients

- **File:** `src/app/api/recipes/match/route.ts:110-119`
- **Issue:** `jsonb_array_elements(p.ingredients)` will throw a Postgres error if any `ingredients` column contains a JSON object instead of an array. The `IS NOT NULL` check doesn't prevent this.
- **Impact:** A single corrupted recipe record breaks the entire match endpoint for all users.
- **Suggested fix:**

```sql
WHERE p.ingredients IS NOT NULL
  AND jsonb_typeof(p.ingredients) = 'array'
  AND (${Prisma.join(nameConditions, ' OR ')})
```

**[CR-005]** CSP `img-src` allows loading images from any HTTPS origin

- **File:** `src/middleware.ts:178`
- **Issue:** `img-src 'self' data: https: blob:` allows images from any HTTPS domain. A stored XSS via image URL (if validation is bypassed) could load tracking pixels or exploit image-based vulnerabilities.
- **Impact:** Weakened CSP; third-party image loading enables user tracking and potential exfiltration.
- **Suggested fix:**

```typescript
"img-src 'self' data: https://res.cloudinary.com blob:",
```

#### MEDIUM

**[CR-006]** Dead/incorrect code in admin user deletion

- **File:** `src/app/api/admin/users/[id]/route.ts:33`
- **Issue:** `Array.isArray(userToDelete)` after `const [userToDelete] = await tx.$queryRaw<...>` is always false. Destructuring extracts the first element (an object or undefined), never an array. The `!userToDelete` check already handles the empty-result case.
- **Impact:** Dead code that confuses maintainers about the expected shape of raw query results.
- **Suggested fix:**

```typescript
if (!userToDelete) throw new Error('USER_NOT_FOUND');
```

**[CR-007]** Notification polling backoff is effectively binary (60s or 5min)

- **File:** `src/hooks/useNotificationPolling.ts:139-142`
- **Issue:** `BASE_INTERVAL * Math.pow(2, failureCount)` — with `BASE_INTERVAL=60000`, one failure yields 120s, two yields 240s, three yields 480s (already near 5min cap). The exponential curve collapses to the cap almost immediately, providing no meaningful graduated backoff.
- **Impact:** After any transient failure, polling jumps to maximum interval, delaying recovery.
- **Suggested fix:** Use a smaller base or linear backoff: `Math.min(BASE_INTERVAL * (failureCount + 1), MAX_INTERVAL)`.

**[CR-008]** `searchParams.get('limit')` parsed with fallback hides invalid input

- **File:** `src/app/api/recipes/route.ts:22` (and many other routes)
- **Issue:** `parseInt(searchParams.get('limit') || '20') || 20` silently falls back to 20 for strings like `"abc"` or `"0"`. While not a security issue, it masks client-side bugs.
- **Impact:** API consumers sending malformed parameters get silent defaults instead of 400 errors, making debugging harder.
- **Suggested fix:** Validate with Zod `paginationSchema` (already exists) consistently across routes.

**[CR-009]** `secure` cookie flag is `false` on non-production HTTPS environments

- **File:** `src/lib/utils/cookies.ts:12`
- **Issue:** `secure: process.env.NODE_ENV === 'production'` means staging/preview environments on HTTPS (where `NODE_ENV=development` or `staging`) send auth cookies over insecure connections.
- **Impact:** Auth tokens can be intercepted on staging environments served over HTTP (or mixed content).
- **Suggested fix:** Default to `true` unless explicitly in development: `secure: process.env.NODE_ENV !== 'development'`.

#### LOW

**[CR-010]** Admin stats endpoint fires 7 independent count queries

- **File:** `src/infrastructure/services/AdminService.ts:201-218`
- **Issue:** Seven separate `count()` calls execute as individual queries. While `Promise.all` parallelizes them, each is a full table scan. A single query with `COUNT(*) FILTER (WHERE ...)` would be faster.
- **Impact:** Unnecessary database load on the admin dashboard.
- **Suggested fix:** Combine into a raw query:

```sql
SELECT
  (SELECT COUNT(*) FROM "User") AS "totalUsers",
  (SELECT COUNT(*) FROM "User" WHERE role = 'ADMIN') AS "totalAdmins",
  ...
```

**[CR-011]** `console.error` calls in production API routes

- **File:** Multiple API routes (e.g., `src/app/api/recipes/[id]/route.ts:97`, `src/app/api/pantry/route.ts:113`)
- **Issue:** Many routes use `console.error` for error logging. Some use `logServerError` (which integrates Sentry), but the majority don't.
- **Impact:** Inconsistent error observability; production errors may go unnoticed without Sentry.
- **Suggested fix:** Replace all `console.error` in API routes with `logServerError` for consistent monitoring.
