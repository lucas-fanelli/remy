### Findings

#### CRITICAL

**[CR-001]** DELETE account cleanup IIFE swallows unhandled rejections silently in edge cases

- **File:** `src/app/api/users/profile/route.ts:117-127`
- **Issue:** The outer `.catch()` on the IIFE only catches errors from the IIFE setup itself. If `Promise.allSettled` throws synchronously (e.g., `cleanupCloudinaryImage` is not a function due to a bad import), the `.catch()` handles it. However, the batched sequential loop means if the first batch succeeds but a later batch throws a non-rejection error (e.g., TypeError), the remaining batches are silently abandoned with no indication of how many images were orphaned.
- **Impact:** Orphaned Cloudinary images with no diagnostic trail of which batches completed.
- **Suggested fix:** Log the batch index and total count so the cleanup cron can reconcile:

```typescript
for (let batchIdx = 0; batchIdx < batches.length; batchIdx++) {
  const batch = batches[batchIdx];
  const results = await Promise.allSettled(batch.map((url) => cleanupCloudinaryImage(url)));
  const failures = results
    .map((r, i) => (r.status === 'rejected' ? { url: batch[i], reason: r.reason } : null))
    .filter(Boolean);
  if (failures.length > 0)
    logServerError(`Failed to cleanup images batch ${batchIdx + 1}/${batches.length}`, failures);
}
```

**[CR-002]** `instructions` field treated as `unknown[]` without JSON column type guard

- **File:** `src/app/api/cooked-recipes/route.ts:106-113`
- **Issue:** `post.instructions` comes from a Prisma JSON column. The code checks `Array.isArray(post.instructions)` but then iterates with `post.instructions.slice(0, 50)` and accesses `.image` on elements. If a malicious or corrupted DB row has `instructions` as an array of strings or numbers, `'image' in instr` will throw because `in` operator requires an object. The `typeof instr === 'object' && !Array.isArray(instr)` guard catches arrays and primitives, but `null` passes `typeof === 'object'` and then `'image' in null` throws a TypeError.
- **Impact:** A single corrupted recipe row crashes the entire account deletion transaction, preventing the user from deleting their account.
- **Suggested fix:** Add a null check:

```typescript
if (instr && typeof instr === 'object' && !Array.isArray(instr) && 'image' in instr) {
```

Wait — `instr &&` is already there, which guards against `null`. I retract this specific crash path. However, the `instr` variable is typed from `.slice()` on `unknown`, so TypeScript won't catch regressions. The real issue is that a corrupted row with non-object array elements silently skips cleanup. This is **downgraded to MEDIUM** — see CR-012.

**[CR-003]** Race condition: `clearAuthCookie` applied to response object but other sessions remain valid indefinitely if token is JWT-based

- **File:** `src/app/api/users/profile/route.ts:137-143`
- **Issue:** The lengthy comment acknowledges this risk but treats it as a future concern. If `validateToken` is ever changed to skip DB lookup (a common optimization), deleted users retain access. There is no runtime assertion or test enforcing that `validateToken` always hits DB. This is a ticking time bomb with no guardrail.
- **Impact:** Deleted users could access the application after account deletion if auth is refactored.
- **Suggested fix:** Add a runtime integration test that asserts a deleted user's token returns 401. This converts the comment into an enforceable contract:

```typescript
// In test suite:
it('should reject tokens for deleted users', async () => {
  const token = await createUserAndGetToken();
  await deleteUser();
  const res = await callProtectedEndpoint(token);
  expect(res.status).toBe(401);
});
```

**[CR-004]** `rating_asc` sort puts NULLs last, making it useless for "lowest rated" queries

- **File:** `src/app/api/recipes/route.ts:109`
- **Issue:** `{ sort: 'asc', nulls: 'last' }` means unrated recipes appear after rated ones. A user requesting "lowest rated" would see 1-star recipes first, then unrated recipes — which is arguably correct. But `rating_desc` ALSO uses `nulls: 'last'`, meaning both ascending and descending put nulls last. This is inconsistent: `rating_asc` should probably put nulls first (unrated = no endorsement = effectively zero).
- **Impact:** Confusing UX. No client can distinguish "unrated" from "highly rated" in ascending sort.
- **Suggested fix:**

```typescript
case 'rating_asc':
  orderBy = [{ averageRating: { sort: 'asc', nulls: 'first' } }, { createdAt: 'desc' }, { id: 'asc' }];
  break;
```

**[CR-005]** No Content-Type check on DELETE endpoint for cooked-recipes

- **File:** `src/app/api/cooked-recipes/route.ts:236`
- **Issue:** POST checks `requireJsonContentType` but DELETE does not. While DELETE uses query params (no body), the absence of any CSRF token or origin check beyond the middleware `X-Requested-With` header means if the middleware is ever bypassed or misconfigured, DELETE is unprotected. The comment on line 233 says "CSRF protection: middleware requires X-Requested-With header" but this is a defense-in-depth gap — the route itself has zero protection.
- **Impact:** If middleware CSRF check is bypassed, accounts can have cooked recipes deleted via CSRF.
- **Suggested fix:** Add explicit `X-Requested-With` validation in the route handler as defense-in-depth, or at minimum validate the `Origin`/`Referer` header.

**[CR-006]** `deductedIngredients` stored as JSON in DB can be tampered with if DB access is compromised

- **File:** `src/app/api/cooked-recipes/route.ts:278-304`
- **Issue:** On DELETE, `deductedIngredients` is read from DB and used to restore pantry quantities. The Zod validation on line 283-288 is good, but `amount` allows up to 10000. An attacker with DB write access (SQL injection elsewhere, compromised backup, etc.) could set `amount: 10000` for every ingredient, inflating pantry quantities massively upon deletion.
- **Impact:** Pantry quantity inflation if DB integrity is compromised.
- **Suggested fix:** Cross-validate restored amounts against the recipe's actual ingredient amounts, or cap restoration to the original recipe amount:

```typescript
// Store the original recipe ingredient amounts at cook time for cross-validation
```

**[CR-007]** `striptags` does not prevent all XSS vectors

- **File:** `src/app/api/recipes/route.ts:189` and multiple other locations
- **Issue:** `striptags` only strips HTML tags. It does not handle attribute-based XSS (`javascript:` URLs in href), event handlers in already-rendered contexts, or template injection. If any of these string values are rendered in a `dangerouslySetInnerHTML` or similar unescaped context on the frontend, XSS is still possible.
- **Impact:** Stored XSS if frontend renders any of these values without escaping.
- **Suggested fix:** Verify all frontend rendering uses React's default escaping (JSX `{value}`) and never `dangerouslySetInnerHTML`. If any unescaped rendering exists, switch to a proper sanitizer like `DOMPurify` server-side.

**[CR-008]** `POST /api/recipes` returns the full `recipe` object from `tx.post.create`

- **File:** `src/app/api/recipes/route.ts:229`
- **Issue:** `tx.post.create({ data: recipeData })` without a `select` clause returns ALL columns, including any future sensitive fields added to the Post model. The GET endpoint carefully selects specific fields, but POST returns everything.
- **Impact:** Information leakage if sensitive columns are added to Post in the future.
- **Suggested fix:** Add a `select` clause matching the GET response shape:

```typescript
return tx.post.create({
  data: recipeData,
  select: {
    id: true,
    title: true,
    description: true,
    imageUrl: true,
    cookingTime: true,
    prepTime: true,
    servings: true,
    difficulty: true,
    ingredients: true,
    instructions: true,
    caption: true,
    createdAt: true,
    updatedAt: true,
    userId: true,
  },
});
```

**[CR-009]** Inconsistent error response format across routes

- **File:** `src/app/api/cooked-recipes/route.ts` vs `src/app/api/users/profile/route.ts`
- **Issue:** `profile/route.ts` uses `ApiResponseHelper` for all responses. `cooked-recipes/route.ts` and `recipes/route.ts` use raw `NextResponse.json()`. Clients must handle two different response envelope shapes depending on the endpoint.
- **Impact:** Frontend must implement two response parsing paths, increasing bug surface.
- **Suggested fix:** Standardize on `ApiResponseHelper` across all routes, or at minimum ensure the JSON shape (`{ error: string }` vs `{ success: false, error: string }`) is consistent.

**[CR-010]** `escapeLike` doesn't handle all Postgres LIKE special characters

- **File:** `src/app/api/recipes/match/route.ts:12-14`
- **Issue:** The `ESCAPE '\\'` clause in the SQL (line 93) tells Postgres that `\` is the escape character. `escapeLike` correctly escapes `\`, `%`, and `_`. However, some Postgres builds with custom locales may have additional pattern characters. More critically, the function is defined locally but could be reused — it should be in a shared utility.
- **Impact:** Minor. Could cause incorrect LIKE matches in edge cases with unusual input.
- **Suggested fix:** Move `escapeLike` to `src/lib/utils/` for reuse and testability.

**[CR-011]** Magic numbers throughout match/route.ts

- **File:** `src/app/api/recipes/match/route.ts:129,142,148,174,183,192,193`
- **Issue:** `50` (min limit), `200` (max limit), `100` (pantry items take), `20` (pantry patterns slice), `20000` (max comparisons), `4000` (wall-clock ms), `30` (min match %), `60` (capped results), `20` (per-category cap) — all hardcoded. These are tuning parameters that should be named constants.

**[CR-012]** `instructions` JSON field parsed with `as unknown as` casts, no runtime validation

- **File:** `src/app/api/cooked-recipes/route.ts:106`, `src/app/api/recipes/match/route.ts:155`
- **Issue:** `recipe.ingredients as unknown as RecipeIngredient[]` and similar casts bypass TypeScript's type system entirely. If the DB contains malformed JSON (e.g., `[{"name": 123}]`), the code will produce incorrect results or throw at runtime with unhelpful errors. The cooked-recipes route does a runtime check on line 181-185, but match/route.ts line 155 also validates — this validation logic is duplicated.
- **Impact:** Fragile code that will break silently on malformed data. Duplicated validation logic.
- **Suggested fix:** Create a shared `parseRecipeIngredients(json: unknown): RecipeIngredient[] | null` utility with Zod validation, used by both routes.

**[CR-013]** `deductPantryItems` uses sequential awaits inside transaction

- **File:** `src/app/api/cooked-recipes/route.ts:86-97`
- **Issue:** Pass 2 applies deductions and deletions one at a time with `await` in a for-loop inside a transaction. Each await is a separate round-trip to the DB. With 100 ingredients, that's up to 100 sequential queries holding a transaction open.
- **Impact:** Slow transaction under load; potential connection pool exhaustion.
- **Suggested fix:** Batch the updates using `Promise.all` (safe inside a transaction since they operate on different rows):

```typescript
await Promise.all([
  ...deductions.map((d) =>
    tx.pantryItem.update({ where: { id: d.itemId }, data: { quantity: d.newQuantity } })
  ),
  ...deletions.map((d) => tx.pantryItem.delete({ where: { id: d.id } })),
]);
```

**[CR-014]** `difficulty` filter in GET /api/recipes accepts any string

- **File:** `src/app/api/recipes/route.ts:86`
- **Issue:** `where.difficulty = difficulty` sets the filter to whatever string the client sends. While Prisma won't crash (it'll just return no results for invalid values), it means invalid requests get 200 with empty results instead of 400.
- **Impact:** Silent failures. A client sending `difficulty=Easy` (capitalized) gets empty results with no error.
- **Suggested fix:**

```typescript
const validDifficulties = ['easy', 'medium', 'hard'];
if (difficulty && !validDifficulties.includes(difficulty)) {
  return NextResponse.json(
    { error: 'Invalid difficulty. Must be: easy, medium, hard' },
    { status: 400 }
  );
}
```

**[CR-015]** Pantry restoration in DELETE creates items without validating pantry item count limit

- **File:** `src/app/api/cooked-recipes/route.ts:310-314`
- **Issue:** When restoring pantry items on cooked recipe deletion, new `pantryItem.create` calls are made without checking if the user's pantry is at its item limit. If the original item was deleted and the user has since filled their pantry to the limit, restoration could exceed the limit.
- **Impact:** Users can exceed pantry item limits through the delete-restore cycle.
- **Suggested fix:** Check current pantry item count before creating new items, and skip creation if at limit (logging the skip).
