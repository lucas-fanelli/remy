## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Generally well-structured with good test coverage, but several security gaps, race conditions, and data integrity issues exist across the API layer.

### Findings

#### CRITICAL

**[CR-001]** Recipe match endpoint raw SQL injection via pantry names

- **File:** `src/app/api/recipes/match/route.ts:89-93`
- **Issue:** `escapeLike` only escapes `%`, `_`, and `\` for LIKE patterns, but pantry item names are interpolated into raw SQL via `Prisma.sql` template literals. While Prisma's tagged template does parameterize values, the `LIKE` pattern itself is constructed by string concatenation (`%${escapeLike(name)}%`), meaning a pantry item name containing a single quote embedded in the template string value is safe — but the `ESCAPE '\\'` clause uses a hardcoded backslash which may conflict with PostgreSQL's `standard_conforming_strings` setting. More critically, if `escapeLike` is ever bypassed or the pattern is used outside of `Prisma.sql`, it becomes injectable.
- **Impact:** Currently mitigated by Prisma parameterization, but fragile. Low risk now, high risk if refactored.
- **Suggested fix:** Use Prisma's `contains` filter with `mode: 'insensitive'` instead of raw SQL for the pre-filter, or at minimum add a comment documenting the safety invariant.

**[CR-002]** `cooked-recipes` POST deducts pantry but proceeds even when ingredients are insufficient

- **File:** `src/app/api/cooked-recipes/route.ts:131-148`
- **Issue:** When a pantry item has less quantity than required, the item is added to `insufficientIngredients` but the transaction continues and the recipe is still marked as cooked. The insufficient items are never deducted (correct), but the sufficient items ARE deducted. This means partial deductions happen silently — the user loses some pantry items even though they didn't have enough to actually cook the recipe.
- **Impact:** Data integrity issue. Users lose pantry items for recipes they couldn't fully cook. The response includes `insufficientIngredients` but the client may not prominently warn the user before the deduction is committed.
- **Suggested fix:** Either block the entire operation when any ingredient is insufficient, or make the "deduct anyway" behavior explicit with a client-side confirmation step (e.g., `force: true` parameter).

**[CR-003]** No CSRF token validation on logout — relies solely on cookie presence check

- **File:** `src/app/api/auth/logout/route.ts:4-7`
- **Issue:** The comment says "CSRF protection is handled by middleware (Sec-Fetch-Site / Content-Type check)" but the middleware CSRF check at `middleware.ts:181-195` only requires `application/json` content type OR `sec-fetch-site: same-origin`. A cross-site attacker can send a POST with `Content-Type: application/json` from JavaScript (which IS blocked by CORS preflight), but if the browser doesn't enforce preflight (older browsers, certain configurations), the logout endpoint is vulnerable to CSRF logout attacks.
- **Impact:** An attacker could force-logout users, causing denial of service and session disruption.
- **Suggested fix:** The current layered defense (SameSite cookie + Sec-Fetch-Site + Content-Type) is actually reasonable for modern browsers. Add a comment clarifying the threat model. The real risk is minimal.

#### HIGH

**[CR-004]** `RecipeFeed` like handler silently swallows JSON parse failures with stale optimistic state

- **File:** `src/components/recipe/RecipeFeed.tsx:280-302`
- **Issue:** When the like API returns `ok: true` but the response body isn't valid JSON, the catch block tries to refetch the status via GET. If that also fails, the comment says "keep optimistic state" — but the optimistic state is wrong (it was toggled before the request). The user sees an incorrect like state with no error message.
- **Impact:** UI shows incorrect like state permanently until page refresh. Silent data inconsistency.
- **Suggested fix:** Revert to the pre-optimistic state in the inner catch block instead of keeping wrong optimistic state:

```typescript
} catch {
  // Can't reconcile — revert to previous state
  setRecipeLikes(prev => ({ ...prev, [recipeId]: currentLikeState }));
}
```

**[CR-005]** Admin delete user has TOCTOU race between admin count check and deletion

- **File:** `src/app/api/admin/users/[id]/route.ts:34-40`
- **Issue:** The "prevent deleting last admin" check reads `adminCount` and then deletes the user in separate queries without a transaction. Two concurrent admin deletion requests could both pass the count check (count=2) and both proceed to delete, leaving zero admins.
- **Impact:** Could result in zero admin users in the system, locking out all admin functionality.
- **Suggested fix:** Wrap the check and delete in a `prisma.$transaction` with `SELECT ... FOR UPDATE` on the user row.

**[CR-006]** Comment image URLs are not validated on the PATCH (edit) endpoint

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:46-63`
- **Issue:** The Cloudinary URL validation checks `url.pathname.includes('..')` and requires `url.pathname.startsWith(`/${cloudName}/`)`. However, `..` check is insufficient — URL-encoded traversal (`%2e%2e`) bypasses it. The `new URL()` constructor normalizes `%2e%2e` to `..`, so this is actually safe in practice, but the defense is not obvious.
- **Impact:** Low risk due to URL constructor normalization, but the pattern is fragile.
- **Suggested fix:** Add a comment explaining why this is safe, or use a stricter regex pattern for Cloudinary URLs.

**[CR-007]** `useNotificationPolling` circuit breaker can be reset by tab visibility change, masking persistent failures

- **File:** `src/hooks/useNotificationPolling.ts:142-149`
- **Issue:** When the tab becomes visible again and `timeSinceLastFailure > 2 minutes`, `pollingStoppedRef` is reset to false. But `failureTimestampsRef` is NOT reset (comment says "let sliding window expire naturally"). If the server is still failing, the breaker trips again immediately after the first retry. However, the visibility handler also calls `fetchNotifications()` and `scheduleNext()` without checking if the previous attempt completed, potentially causing concurrent fetches.
- **Impact:** Multiple concurrent notification fetches after tab becomes visible, causing unnecessary server load.
- **Suggested fix:** Check `loadingRef` or `notificationAbortRef` before initiating a new fetch in the visibility handler.

#### MEDIUM

**[CR-008]** `PersistentSearchBar` live search fires API calls without authentication check

- **File:** `src/components/search/PersistentSearchBar.tsx:118-143`
- **Issue:** The debounced search effect calls `/api/search` on every keystroke (after 300ms debounce) regardless of whether the user is authenticated. While the search API itself is public, this creates unnecessary load and exposes search behavior to unauthenticated users who may be typing in the nav bar.
- **Impact:** Minor — the search endpoint is public by design. But unauthenticated users generate API traffic that could contribute to rate limiting.
- **Suggested fix:** No action needed if search is intentionally public. Document the design decision.

**[CR-009]** `EditProfileModal` sends avatar URL directly from upload response without re-validation

- **File:** `src/components/profile/EditProfileModal.tsx:115-123`
- **Issue:** After uploading an avatar to `/api/upload/avatar`, the response URL is passed directly to `updateProfile` without validating it's a Cloudinary URL. The server-side profile update endpoint does validate, but the client could be modified to send arbitrary URLs.
- **Impact:** Low — server-side validation catches this. Defense-in-depth only.
- **Suggested fix:** No action needed; server validates.

**[CR-010]** `safeRating` returns 0 for unrated recipes, which is displayed differently across components

- **File:** `src/lib/utils/recipe.ts:7`
- **Issue:** `safeRating` converts `null` (unrated) to `0`. Some components check `> 0` to show ratings, others check `!== undefined`. The `Recipe` type has `averageRating?: number | null`, creating three possible states (undefined, null, 0) that all mean "unrated" but are handled inconsistently.
- **Impact:** UI inconsistency — some views may show "0.0 (0 reviews)" instead of "No ratings yet".
- **Suggested fix:** Standardize on `null` for "no rating" and only use `safeRating` at the API boundary, not in components.

**[CR-011]** `RecipeFeed` IntersectionObserver infinite scroll has no maximum page limit

- **File:** `src/components/recipe/RecipeFeed.tsx:168-182`
- **Issue:** The infinite scroll continues loading pages indefinitely as long as `hasMore` is true (response returns exactly 12 items). There's no upper bound, so a user scrolling continuously could load thousands of recipes into memory.
- **Impact:** Memory exhaustion on client for large databases. Performance degradation.
- **Suggested fix:** Add a maximum page count (e.g., 50 pages = 600 recipes) and show a "Load more" button after that.

**[CR-012]** `CommentsSection` orphaned Cloudinary images on failed comment POST

- **File:** `src/components/recipe/CommentsSection.tsx:134-143`
- **Issue:** If image upload succeeds but the comment POST fails, the uploaded Cloudinary image is orphaned. The code has comments acknowledging this ("can be cleaned by a periodic server-side cron job") but no such cron job exists in the codebase.
- **Impact:** Cloudinary storage leak over time. Each orphaned image consumes storage quota.
- **Suggested fix:** Implement the mentioned cron job, or attempt client-side cleanup by calling a delete endpoint on failure.

**[CR-013]** `about/page.tsx` hardcodes branding text that contradicts `BRANDING` config

- **File:** `src/app/about/page.tsx:114-115`
- **Issue:** The description text hardcodes "Named after the famous chef rat from Ratatouille" and "anyone can cook", but uses `BRANDING.name` for the app name. If the app is rebranded, these hardcoded references to Ratatouille won't update.
- **Impact:** Broken rebranding if `BRANDING.name` is changed.
- **Suggested fix:** Move these descriptions into `BRANDING` config.

**[CR-014]** `middleware.ts` rate limit map grows unbounded between probabilistic cleanups

- **File:** `src/middleware.ts:67-82`
- **Issue:** The bulk cleanup at size > 500 runs after the probabilistic cleanup (5% chance). Between cleanups, the map can grow well beyond 500 entries under high traffic. The 500-entry cap is soft, not hard.
- **Impact:** Memory growth under sustained high traffic. In serverless environments, this is per-instance so impact is limited.
- **Suggested fix:** Check size BEFORE inserting new entries, not just during cleanup passes.

**[CR-016]** `Footer` contact form has no email validation

- **Issue:** The contact form opens a `mailto:` link with user-provided name, email, and subject. There's no validation that the email field contains a valid email address before constructing the mailto link.

**[CR-017]** `RecipeCard` image fallback chain could show broken image briefly

- **File:** `src/components/recipe/RecipeCard.tsx:100-108`
- **Issue:** Non-Cloudinary URLs fall back to `/chef-logo.png` immediately (not via onError). If `/chef-logo.png` itself fails, `imgHidden` is set and a placeholder icon is shown. But between the first error and the fallback load, there's a brief flash of broken image.
- **Impact:** Minor visual glitch. No functional impact.
- **Suggested fix:** Accept as-is or add a loading skeleton during the fallback attempt.

**[CR-018]** `ThemeContext` hydration sync has a 50ms hardcoded delay

- **File:** `src/contexts/ThemeContext.tsx:33-42`
- **Issue:** The 50ms setTimeout for hydration sync is an arbitrary magic number. On slow devices, hydration may not be complete in 50ms, causing a theme flash.
- **Impact:** Potential theme flash on slow devices/connections.
- **Suggested fix:** Use `useLayoutEffect` or React 18's `useSyncExternalStore` instead of a timer.
