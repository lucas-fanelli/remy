### Findings

#### CRITICAL

**[CR-001]** Transaction in PUT profile uses `userService.updateProfile` which likely uses its own Prisma client, not the transaction client `tx`

- **File:** `src/app/api/users/profile/route.ts:49`
- **Issue:** The code wraps a read and update in `prisma.$transaction(async (tx) => { ... })` but calls `userService.updateProfile(user.id, profileData)` which almost certainly uses the singleton `prisma` client internally, not the transactional `tx` client. This means the update executes **outside** the transaction, completely defeating the purpose of the transaction (preventing concurrent avatar changes).
- **Impact:** Race condition on concurrent profile updates. Two simultaneous PUT requests can both read the same old avatar, both update successfully, and only one old avatar gets cleaned up — the other leaks in Cloudinary. The transaction provides zero protection here.
- **Suggested fix:** Either pass `tx` to the service method, or do the update directly via `tx.user.update(...)`:

```typescript
const { previousAvatar, updatedUser } = await prisma.$transaction(async (tx) => {
  const current = await tx.user.findUnique({ where: { id: user.id }, select: { avatar: true } });
  // Use tx directly instead of the service
  const updated = await tx.user.update({
    where: { id: user.id },
    data: profileData,
    // select the fields you need
  });
  return { previousAvatar: current?.avatar ?? null, updatedUser: updated };
});
```

**[CR-002]** `deductPantryItems` uses `striptags` on output but not on input — stored XSS via ingredient names in `deductedIngredients` JSON

- **File:** `src/app/api/cooked-recipes/route.ts:100-106`
- **Issue:** `striptags(d.name)` is applied to deduction records but the original `ingredient.name` from the recipe's JSON blob is used for the `insufficientIngredients` array (line 87) and in the `normalizeIngredientName` comparison. If an attacker crafts a recipe with `<script>` tags in ingredient names, the `insufficientIngredients` array returned in the 409 response (line 247) contains unsanitized HTML. The client renders this in the UI.
- **Impact:** Stored XSS — an attacker creates a recipe with malicious ingredient names, another user tries to cook it, and the error response includes the raw HTML/JS which is rendered client-side.
- **Suggested fix:** Sanitize `ingredient.name` at the point of comparison or sanitize the entire `insufficientIngredients` response:

```typescript
insufficientIngredients.push({
  name: striptags(ingredient.name),
  required: recipeAmount,
  available: pantryQuantity,
  unit: striptags(ingredient.unit),
});
```

**[CR-003]** `DELETE /api/cooked-recipes` restores pantry quantities without validating `d.unit` for injection or sanitizing `d.name` before database write

- **File:** `src/app/api/cooked-recipes/route.ts:290-310`
- **Issue:** The `deductedIngredients` JSON stored in the database is treated as trusted when restoring pantry items on delete. While `d.name` is passed through `striptags` on the `pantryItem.create` path (line 308), the `findFirst` lookup on line 302 uses `d.name as string` directly without sanitization. More critically, `d.unit` is used as-is (`typeof d.unit === 'string' ? d.unit : ''`) with no length or content validation — it could contain arbitrary strings up to the DB column limit.
- **Impact:** If the `deductedIngredients` JSON is tampered with (e.g., via direct DB access or a bug in the write path), the restore logic will write arbitrary data into pantry items. The `findFirst` with unsanitized `name` could also match unintended pantry items.
- **Suggested fix:**

```typescript
const name = typeof d.name === 'string' ? striptags(d.name).slice(0, 200) : null;
const unit = typeof d.unit === 'string' ? striptags(d.unit).slice(0, 50) : '';
if (!name) continue;
```

Apply `striptags` and length limits to both `name` and `unit` before using them in queries or writes.

**[CR-004]** Recipe match endpoint holds a transaction open for up to 15 seconds with CPU-intensive in-memory matching

- **File:** `src/app/api/recipes/match/route.ts:73-213`
- **Issue:** The entire matching logic — including the 4-second wall-clock matching loop, the batch fetches, and all categorization — runs inside a single `prisma.$transaction` with a 15-second timeout. During this time, a PostgreSQL connection is held from the pool, and the advisory lock is held. Under moderate concurrent load (e.g., 10 users hitting match simultaneously), this will exhaust the connection pool (default 5-10 connections in most setups), causing all other database operations across the entire application to queue or timeout.
- **Impact:** Denial of service under normal load. A handful of concurrent match requests can starve the connection pool and bring down the entire application's database access. The advisory lock serializes per-user, but cross-user concurrency still exhausts the pool.
- **Suggested fix:** Split the transaction: use a short transaction for the advisory lock + candidate fetch, then do the CPU-intensive matching outside the transaction, then use a second short transaction (or no transaction) for the batch detail fetch:

```typescript
// Short transaction: lock + fetch candidates
const { pantry, allCandidates } = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SET LOCAL statement_timeout = '3s'`;
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(...)`;
  // fetch pantry + candidates
  return { pantry, allCandidates };
}, { timeout: 5000 });

// CPU matching outside transaction (no DB connection held)
const matchResults = computeMatches(pantry, allCandidates);

// Simple query for full recipe data (no transaction needed)
const recipes = await prisma.post.findMany({ where: { id: { in: matchedIds } }, ... });
```

**[CR-005]** `DELETE /api/users/profile` account deletion races with concurrent recipe/comment creation

- **File:** `src/app/api/users/profile/route.ts:82-97`
- **Issue:** The transaction collects image URLs from posts, comments, and avatar, then deletes the user. Due to foreign key cascades, the posts and comments are also deleted. However, the comment notes that a cleanup script is needed as a safety net, and the image collection happens at a snapshot in time. If a user's post receives a comment with an image from _another_ user between the `findMany` and the `delete`, those comment images are cascade-deleted from the DB but their Cloudinary URLs are never collected for cleanup. The transaction's snapshot isolation prevents seeing concurrent inserts.
- **Impact:** Cloudinary image leaks — images from other users' comments on the deleted user's posts are orphaned in Cloudinary storage permanently (until the safety-net cron runs, if configured). The code comment acknowledges this but treating it as "edge case" for a cron job that may not be configured is a data leak.
- **Suggested fix:** Collect images _after_ the cascade delete using a `RETURNING`-style approach, or use database triggers to log deleted image URLs. Alternatively, ensure the cleanup cron job is mandatory infrastructure, not optional:

```typescript
// Instead of collecting before delete, use ON DELETE CASCADE
// with a trigger that logs URLs to a cleanup queue table
```
