**[CR-001]** Pantry restoration logic is inverted — restores only RECENT cooks, should restore only OLD cooks

- **File:** `src/app/api/cooked-recipes/route.ts:261-263`
- **Issue:** The comment says "Only restore pantry items if the cooked recipe is older than 1 hour" to prevent exploit loops, but the condition `isRecentCook` is used to gate the restoration. This means pantry items are restored for _recent_ cooks (< 1 hour) and _not_ restored for old cooks — the exact opposite of what the comment states and the exact exploit it claims to prevent. A user can cook (deducting ingredients), immediately delete (restoring ingredients), and repeat to generate infinite pantry items.
- **Impact:** Pantry item duplication exploit. Users can generate unlimited pantry quantities by cooking and immediately deleting.
- **Suggested fix:**

```typescript
// Change line 263 from:
if (cookedRecipe.deductedIngredients && isRecentCook) {
// To:
if (cookedRecipe.deductedIngredients && !isRecentCook) {
```

**[CR-002]** `password` field leaked in profile update response

- **File:** `src/app/api/users/profile/route.ts:47-49`
- **Issue:** The transaction returns `userWithoutPassword` using destructuring `const { password: _, ...userWithoutPassword } = updated;`, but there is no guarantee that `updated` from `tx.user.update` won't include additional sensitive fields added in the future (e.g., `passwordResetToken`, `emailVerificationToken`). More critically, if the Prisma schema has a `select` or `omit` feature change, or if `password` is renamed, the destructuring silently stops working. However, the immediate critical issue is that this relies on runtime destructuring rather than a Prisma `select` clause — if Prisma serializes the full model before returning (e.g., in logging middleware or Prisma extensions), the password hash could be exposed in logs.
- **Impact:** Password hash exposure in logs/middleware if Prisma extensions or query logging are enabled.
- **Suggested fix:**

```typescript
const updated = await tx.user.update({
  where: { id: user.id },
  data: profileData,
  select: {
    id: true,
    username: true,
    fullName: true,
    email: true,
    avatar: true,
    bio: true,
    isPrivate: true,
    createdAt: true,
    updatedAt: true,
  },
});
return { previousAvatar: current?.avatar ?? null, updatedUser: updated };
```

**[CR-003]** `createRecipeSchema` accepts arbitrary URL in instruction images after initial Cloudinary check

- **File:** `src/app/api/recipes/route.ts:27`
- **Issue:** `instructionSchema` defines `image: z.string().url().optional()` which accepts any URL. While there is a subsequent `validateCloudinaryUrl` check in the POST handler (line 185), the `imageUrl` field on the root schema (line 20) has an inline `.refine()` that enforces Cloudinary — but `instructionSchema` does not. If `validateCloudinaryUrl` is ever bypassed, relaxed, or the validation loop is refactored, non-Cloudinary URLs (including `javascript:`, `data:`, or internal network URLs via SSRF) could be stored. The real critical issue: `validated.imageUrl` on line 180 is always truthy (it's `z.string().min(1)`) so the check always runs, but the instruction image loop on line 186 uses `instruction.image` which is optional — this is fine. **However**, the `createRecipeSchema` does not validate that `instruction.step` values are sequential and non-duplicate. Two instructions with `step: 1` are accepted, leading to data integrity issues and undefined rendering behavior.
- **Impact:** Duplicate step numbers cause unpredictable recipe instruction ordering on the frontend, potential data corruption.
- **Suggested fix:**

```typescript
const createRecipeSchema = z
  .object({
    // ... existing fields ...
    instructions: z
      .array(instructionSchema)
      .min(1)
      .max(50)
      .refine((instructions) => {
        const steps = instructions.map((i) => i.step);
        return new Set(steps).size === steps.length;
      }, 'Instruction steps must be unique'),
  })
  .strict();
```

**[CR-004]** Unescaped `missingIngredients` names returned directly from untrusted JSON column

- **File:** `src/app/api/recipes/match/route.ts:179`
- **Issue:** `missingIngredients: match.missingIngredients.map(i => i.name)` returns ingredient names directly from the `ingredients` JSON column in the database. This column is populated from user input during recipe creation. While `createRecipeSchema` validates max length, it does not sanitize HTML/script content in ingredient names. These names are returned in the API response and likely rendered on the frontend. If the frontend renders them without escaping (e.g., via `dangerouslySetInnerHTML` or a framework that doesn't auto-escape), this is a stored XSS vector. Notably, the cooked-recipes route uses `striptags()` on ingredient names (line 82), but the match route does not apply any sanitization.
- **Impact:** Stored XSS if frontend renders ingredient names without escaping. Inconsistent sanitization across endpoints means at least one path is vulnerable.
- **Suggested fix:**

```typescript
import striptags from 'striptags';
// ...
missingIngredients: match.missingIngredients.map(i => striptags(i.name)),
```

**[CR-005]** Account deletion does not cascade-delete `CookedRecipe.deductedIngredients` references, leaving dangling pantry item IDs

- **File:** `src/app/api/users/profile/route.ts:82-93`
- **Issue:** The DELETE handler collects image URLs from posts and comments, then deletes the user (which cascades to related records via Prisma/DB cascades). However, if another user has `deductedIngredients` JSON containing `pantryItemId` references that point to the deleted user's pantry items, those IDs become dangling. While this isn't exploitable directly, the cooked-recipes DELETE handler (line 280) does `tx.pantryItem.findFirst({ where: { id: pantryItemId, pantry: { userId: user.id } } })` which safely scopes to the current user. The **actual critical issue** is different: the transaction collects `userPosts`, `userComments`, and `userRecord` but does **not** collect images from `CookedRecipe.deductedIngredients` or any recipe instruction images (`instructions` JSON field may contain `image` URLs). These Cloudinary images become orphaned with no cleanup path if the cron job doesn't know to scan instruction images.
- **Impact:** Permanent Cloudinary storage leak for instruction step images on account deletion. Accumulates over time, increasing cloud storage costs with no automated cleanup.
- **Suggested fix:**

```typescript
const userPosts = await tx.post.findMany({
  where: { userId: user.id },
  select: { imageUrl: true, instructions: true },
});
// After collecting URLs:
for (const post of userPosts) {
  if (Array.isArray(post.instructions)) {
    for (const instr of post.instructions as { image?: string }[]) {
      if (instr.image && isCloudinaryUrl(instr.image)) {
        // add to imageUrls
      }
    }
  }
}
```
