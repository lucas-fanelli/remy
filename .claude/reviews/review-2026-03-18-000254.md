## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing platform with clean architecture. Several security vulnerabilities in auth handling, race conditions in data mutations, and inconsistent error handling across API routes.

### Findings

#### CRITICAL

**[CR-001]** httpOnly cookie auth token exposed via in-memory `token` state

- **File:** `src/contexts/AuthContext.tsx:56-57`
- **Issue:** After migrating to httpOnly cookies, `fetchCurrentUser` sets `setToken('cookie-auth')` — a hardcoded sentinel string. But components like `Navigation.tsx:191` send this literal string as `Authorization: Bearer cookie-auth` to API endpoints. The `extractBearerToken` function checks the cookie first, so this works by accident, but any endpoint that only checks the Authorization header (or a future refactor) will break auth silently.
- **Impact:** Auth fragility — if cookie is missing but token state is set, requests send an invalid bearer token. Also leaks the auth mechanism to client-side code.
- **Suggested fix:** Don't store a sentinel. Set `token` to the actual JWT from login/register responses (which you already do on lines 73/87), but set it to `null` in `fetchCurrentUser` and have components use `credentials: 'same-origin'` instead of Bearer headers for cookie-based auth.

**[CR-002]** CSRF protection bypassed by `content-type: multipart/form-data`

- **File:** `src/middleware.ts:133-143`
- **Issue:** The CSRF check requires `content-type: application/json`, `authorization`, or `x-requested-with` headers. File upload endpoints (`/api/upload`, `/api/upload/avatar`) use `multipart/form-data` which does NOT contain `application/json`. They work only because `Authorization` header is also sent. If the cookie-only auth migration completes and Authorization headers are removed, uploads will be blocked by CSRF middleware with a 403.
- **Impact:** Upload endpoints will break once Bearer header fallback is removed.
- **Suggested fix:**

```typescript
const hasCustomHeader =
  (contentType &&
    (contentType.includes('application/json') || contentType.includes('multipart/form-data'))) ||
  request.headers.has('authorization') ||
  request.headers.has('x-requested-with') ||
  request.cookies.has('auth_token');
```

**[CR-003]** DELETE comment in `CommentsSection` has TOCTOU race but API DELETE route also has TOCTOU

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:118-131`
- **Issue:** The DELETE handler performs a `findUnique` ownership check then a separate `delete`. Between these two queries, another request could delete the same comment. The PATCH handler correctly uses a transaction (line 56), but DELETE does not.
- **Impact:** Potential Prisma error on concurrent deletes, leaking internal error to client as 500.
- **Suggested fix:** Use `deleteMany` with ownership filter (atomic) like the save toggle does, or wrap in a transaction like PATCH.

**[CR-004]** Recipe image URL validation inconsistent — POST allows bypass

- **File:** `src/app/api/recipes/route.ts:139-149`
- **Issue:** The POST handler for creating recipes checks `imgUrl.hostname !== 'res.cloudinary.com'` but does NOT check `['http:', 'https:'].includes(imgUrl.protocol)`. The PUT handler at `src/app/api/recipes/[id]/route.ts:67-76` correctly checks protocol. An attacker could submit `javascript:alert(1)//res.cloudinary.com/...` as imageUrl.
- **Impact:** Stored XSS via recipe imageUrl. The `<img src>` would not execute JS, but if imageUrl is ever rendered as a link `href` or in a different context, it's exploitable.
- **Suggested fix:** Add protocol check to POST handler matching PUT:

```typescript
if (!['http:', 'https:'].includes(imgUrl.protocol) || imgUrl.hostname !== 'res.cloudinary.com' || ...) {
```

#### HIGH

**[CR-005]** Notification polling triggers logout on any non-200 response

- **File:** `src/components/Navigation.tsx:206-208`
- **Issue:** When notification fetch returns 401 or 403, the component calls `logout()`. But a 403 could also be returned by rate limiting (middleware returns 429, but a misconfigured proxy could return 403). Also, the `logout` function is destructured from `useAuth` but not listed in the `useCallback` dependency array for `fetchNotifications` (line 217), causing stale closure.
- **Impact:** User gets unexpectedly logged out on transient errors. Stale `logout` reference could cause issues.
- **Suggested fix:** Only logout on 401 (not 403). Add `logout` to the dependency array or use a ref.

**[CR-006]** `recalc-ratings` endpoint uses raw SQL without parameterization guard

- **File:** `src/app/api/admin/recalc-ratings/route.ts:19-34`
- **Issue:** While the raw SQL itself is safe (no user input interpolated), using `$executeRaw` with template literals bypasses Prisma's type safety. If this query is ever modified to include user-provided values, it becomes a SQL injection vector. Also, no pagination/batching — on a large dataset this could be extremely slow or OOM.
- **Impact:** Performance risk on large datasets. Future SQL injection risk if modified carelessly.
- **Suggested fix:** Add a comment warning against interpolating user input. Consider batching with `LIMIT`/`OFFSET` for large datasets.

**[CR-007]** `cooked-recipes` POST allows marking any recipe as cooked with no rate limit beyond once-per-day

- **File:** `src/app/api/cooked-recipes/route.ts:100-103`
- **Issue:** The duplicate check uses `cookedAt: { gte: today }` where `today` is set to midnight UTC. A user in timezone UTC-12 could mark a recipe as cooked twice in a 24-hour window. Also, the pantry deduction logic runs unconditionally even if the user's pantry doesn't have matching items — it just silently skips.
- **Impact:** Timezone edge case allows duplicate entries. Pantry items silently deleted without user confirmation.
- **Suggested fix:** Use a 24-hour rolling window instead of midnight-based check: `cookedAt: { gte: new Date(Date.now() - 24 * 60 * 60 * 1000) }`.

**[CR-008]** No test coverage for API route handlers

- **File:** All `src/app/api/*/route.ts` files
- **Issue:** None of the API route handlers have tests. All tests are for components, services, and repositories. The actual HTTP layer (parameter parsing, error responses, auth middleware integration) is untested.
- **Impact:** Regressions in API routes go undetected. The TOCTOU bugs and validation inconsistencies (CR-003, CR-004) would have been caught with route-level tests.
- **Suggested fix:** Add integration tests for API routes using `NextRequest`/`NextResponse` mocks.

#### MEDIUM

**[CR-009]** `recipe/match` loads all recipes into memory

- **File:** `src/app/api/recipes/match/route.ts:53-54`
- **Issue:** `take: 100` limits to 100 recipes, but each includes full ingredient arrays. With complex recipes this could be several MB of data loaded into memory per request. The matching algorithm is O(recipes _ ingredients _ pantryItems).
- **Impact:** Memory pressure under load. Response time degrades with recipe count.
- **Suggested fix:** Consider a database-level ingredient matching query or caching strategy.

**[CR-010]** `AuthContext` logout doesn't clear React Query cache

- **File:** `src/contexts/AuthContext.tsx:95-101`
- **Issue:** On logout, user/token state is cleared but React Query cache retains authenticated data (recipes, like status, save status). If another user logs in, they could briefly see stale cached data from the previous session.
- **Impact:** Data leakage between user sessions via query cache.
- **Suggested fix:** Call `queryClient.clear()` on logout, or invalidate all queries.

**[CR-011]** Duplicate code across admin API routes

- **File:** `src/app/api/admin/comments/[id]/route.ts`, `src/app/api/admin/recipes/[id]/route.ts`, `src/app/api/admin/users/[id]/route.ts`
- **Issue:** All three DELETE handlers follow the exact same pattern: `requireAdmin` → UUID validation → service call → error handling. This is repeated verbatim across files.
- **Impact:** Maintenance burden. A bug fix in one must be replicated in all three.
- **Suggested fix:** Extract a shared `adminDeleteHandler` helper.

**[CR-012]** `PersistentSearchBar` leaks AbortController on unmount

- **File:** `src/components/search/PersistentSearchBar.tsx:130-131`
- **Issue:** The `abortControllerRef` is used to cancel in-flight requests, but the cleanup function only aborts the controller created in the current effect run. If the component unmounts between the `setTimeout` firing and the `fetch` completing, the fetch continues in the background.
- **Impact:** Memory leak and wasted network requests after navigation away from search.
- **Suggested fix:** The cleanup already calls `controller.abort()` which should handle this. However, the `setLiveResults` and `setIsSearching` calls after abort could cause "setState on unmounted component" warnings. Add an `isMounted` ref check.

**[CR-013]** `website` field in profile allows open redirect

- **File:** `src/infrastructure/services/UserService.ts:37-43`
- **Issue:** Website validation checks for `http:` or `https:` protocol, but any URL is accepted. This is then rendered as a clickable link in `src/app/profile/[username]/page.tsx:307-319` with `target="_blank"`. An attacker could set website to `https://evil-phishing-site.com` — this is by design for external links, but there's no `rel="noopener noreferrer"` on the link.
- **Impact:** The link does have `rel="noopener noreferrer"` — false alarm on that. But profile website has no sanitization against URLs with embedded credentials like `https://user:pass@evil.com`.
- **Suggested fix:** Strip userinfo from URLs: reject URLs containing `@` before the hostname.

**[CR-014]** `search` API exposes user data without authentication

- **File:** `src/app/api/search/route.ts:19`
- **Issue:** The search endpoint is completely unauthenticated. While email is stripped from results (good), the user list still includes `id`, `username`, `fullName`, `avatar`, and `bio`. This enables user enumeration.
- **Impact:** Anyone can enumerate all users by searching common names.
- **Suggested fix:** This is a design decision, but consider rate limiting search more aggressively or requiring auth for user search results.

#### LOW

**[CR-015]** Hardcoded `'en-US'` locale in date formatting

- **File:** `src/app/admin/comments/page.tsx:142`, `src/app/admin/recipes/page.tsx:201`, `src/app/admin/users/page.tsx:207`
- **Issue:** `toLocaleDateString('en-US')` is hardcoded. Should use browser locale or a configurable constant.
- **Impact:** Non-US users see dates in unfamiliar format.
- **Suggested fix:** Use `toLocaleDateString()` without arguments to use browser locale, or make configurable.

**[CR-016]** `averageRating` field has `??` nullish coalescing mixed with `||` or defaults

- **File:** `src/app/api/recipes/[id]/route.ts:22-23`, `src/app/api/search/route.ts:67-68`, `src/app/api/recipes/route.ts:106`
- **Issue:** Some places use `recipe.averageRating ?? 0` and others use `recipe.averageRating || 0`. Since `averageRating` could be `0` (a valid value meaning zero ratings), `||` would incorrectly treat `0` as falsy. The `??` usage is correct; `||` is wrong.
- **Impact:** If a recipe has `averageRating: 0`, the `||` paths would not return 0 but would return the fallback, which is also 0. So the bug is technically harmless here, but the inconsistency could cause issues if defaults change.
- **Suggested fix:** Standardize on `??` everywhere.

**[CR-017]** `Navigation.tsx` is 1000+ lines

- **File:** `src/components/Navigation.tsx`
- **Issue:** This file contains desktop nav, mobile nav, drawer, notification dropdown, create recipe dialog, mobile search dialog, and notification polling logic. It's over 1000 lines and handles too many concerns.
- **Impact:** Difficult to maintain, test, and review. The test file is also massive (~2500 lines).
- **Suggested fix:** Extract into `DesktopNav`, `MobileNav`, `NotificationDropdown`, `NotificationPoller` components.
