## Code Review — 2026-03-18

### Summary

Large codebase with solid architecture (DI, clean separation) but contains a type contract violation in the repository layer, fragile error detection via string matching, duplicate validation logic, and an overly permissive CSP.

### Findings

#### CRITICAL

**[CR-001]** IRecipeRepository.deleteWhere return type violates interface contract

- **File:** `src/domain/repositories/IRecipeRepository.ts:42` / `src/infrastructure/repositories/RecipeRepository.ts:153`
- **Issue:** Interface declares `deleteWhere(id: string, userId: string): Promise<void>` but the implementation returns `Promise<{ imageUrl: string | null }>`. `RecipeService.deleteRecipe` relies on this return value to clean up Cloudinary images. TypeScript may not catch this if the service file doesn't re-type-check against the interface.
- **Impact:** If the interface is used as the type constraint (e.g., in tests or a different implementation), the `imageUrl` return value disappears silently, leaving orphaned Cloudinary images.
- **Suggested fix:**

```typescript
// IRecipeRepository.ts
deleteWhere(id: string, userId: string): Promise<{ imageUrl: string | null }>;
```

**[CR-002]** Follow route detects unique constraint via fragile string matching

- **File:** `src/app/api/users/[username]/follow/route.ts:47`
- **Issue:** `err.message.includes('Unique constraint')` relies on Prisma's English error message text. Prisma throws `PrismaClientKnownRequestError` with a `code` property (`P2002`). The message format can change across Prisma versions.
- **Impact:** A Prisma upgrade could break duplicate-follow detection, causing unhandled 500 errors instead of the intended idempotent response.
- **Suggested fix:**

```typescript
import { Prisma } from '@prisma/client';
// ...
} catch (err: unknown) {
  if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === 'P2002') {
    // Already following — idempotent response
```

#### HIGH

**[CR-003]** CSP `connect-src` allows any HTTPS endpoint

- **File:** `src/middleware.ts:82`
- **Issue:** `connect-src 'self' https:` permits fetch/XHR to any HTTPS origin. An XSS payload could exfiltrate data to `https://attacker.com`.
- **Impact:** Weakens CSP's data exfiltration protection. If an attacker achieves script injection (even via a third-party dependency), they can send data to arbitrary HTTPS endpoints.
- **Suggested fix:**

```typescript
`connect-src 'self' https://res.cloudinary.com https://*.sentry.io https://*.vercel-analytics.com`,
```

**[CR-004]** Recipe match endpoint loads up to 1000 recipes into memory

- **File:** `src/app/api/recipes/match/route.ts:51`
- **Issue:** `take: 1000` fetches up to 1000 recipe rows with their JSON ingredients into Node.js memory for every authenticated user request. The two-pass optimization reduces the second query, but the first pass still materializes all 1000 rows.
- **Impact:** At scale, concurrent requests will cause memory pressure and potential OOM. Each recipe's `ingredients` JSON can be several KB.
- **Suggested fix:** Use database-side filtering with a `jsonb` operator or limit the candidate pool more aggressively. Consider caching match results per-user with a short TTL.

**[CR-005]** Comments GET endpoint returns no total count for pagination

- **File:** `src/app/api/recipes/[id]/comments/route.ts:12-46`
- **Issue:** Returns `{ comments }` without a `total` count. The client has no way to know if more pages exist, making pagination unusable.
- **Impact:** Clients cannot implement "load more" or page navigation for comments. Currently masked by the large default limit (50).
- **Suggested fix:**

```typescript
const [comments, total] = await Promise.all([
  prisma.comment.findMany({ ... }),
  prisma.comment.count({ where: { postId: recipeId } }),
]);
return NextResponse.json({ comments: commentsWithRatings, total });
```

**[CR-006]** Duplicate secret length validation in env-validation

- **File:** `src/lib/env-validation.ts:113-115` and `src/lib/env-validation.ts:128-133`
- **Issue:** `JWT_SECRET` and `NEXTAUTH_SECRET` length are checked twice — once via `MIN_SECRET_LENGTH` (32) and again hardcoded as `< 32`. Both produce separate error messages for the same condition.
- **Impact:** Users see duplicate error messages. Maintenance burden: a developer might change one threshold and not the other.
- **Suggested fix:** Remove the second duplicate block (lines 128-133).

**[CR-008]** User search in `/api/search` is not paginated

- **File:** `src/app/api/search/route.ts:30`
- **Issue:** `userService.searchUsers(query.trim(), limit)` applies `limit` but ignores `offset`. Recipe search uses both `limit` and `offset`, creating inconsistent pagination behavior.
- **Impact:** Cannot paginate user search results. All results beyond `limit` are inaccessible.
- **Suggested fix:** Pass `offset` to `searchUsers` and update `IUserService` and `UserRepository.search` to accept it.

**[CR-009]** Notification polling backoff uses `Infinity` as exponent

- **File:** `src/components/Navigation.tsx:209`
- **Issue:** On 401, `consecutiveFailuresRef.current = Infinity`. The backoff formula `Math.pow(2, Infinity)` = `Infinity`, and `setTimeout(fn, Infinity)` effectively never fires. While functionally correct (polling stops), it's a non-obvious side effect that will confuse future developers.
- **Impact:** Readability/maintainability issue. A future developer might add arithmetic on this value and get unexpected NaN/Infinity results.
- **Suggested fix:** Use a separate `stopPolling` boolean ref or return early from `scheduleNext` when the user is logged out.

**[CR-010]** `RecipeService.deleteRecipe` return type doesn't match interface

- **File:** `src/infrastructure/services/RecipeService.ts:49`
- **Issue:** `IRecipeService.deleteRecipe` returns `Promise<void>` but the implementation returns `Promise<{ imageUrl: string | null }>`. This compounds CR-001.
- **Impact:** Same as CR-001 — interface consumers lose the imageUrl. The API route handler in `src/app/api/recipes/[id]/route.ts:114` casts the return type correctly only because it calls the concrete service, not the interface.
- **Suggested fix:** Update `IRecipeService` to return `Promise<{ imageUrl: string | null }>`.

**[CR-011]** `global-error.tsx` renders unstyled HTML without MUI ThemeProvider

- **File:** `src/app/global-error.tsx`
- **Issue:** Uses MUI components (`Container`, `Box`, `Typography`, `Button`) but renders raw `<html>` without any MUI provider, ThemeProvider, or CssBaseline. MUI components require a theme context to render properly.
- **Impact:** The global error page will render with broken/default styling. Typography, spacing, and button styles will be inconsistent or missing.
- **Suggested fix:** Use plain HTML/CSS for the global error boundary (it must be self-contained since the root layout has failed), or inline a minimal MUI setup.

#### LOW

**[CR-012]** Hardcoded `en-US` locale in admin date formatting

- **File:** `src/app/admin/comments/page.tsx:143`, `src/app/admin/recipes/page.tsx:191`, `src/app/admin/users/page.tsx:234`
- **Issue:** `new Date(comment.createdAt).toLocaleDateString('en-US')` hardcodes locale. Should respect user's browser locale or be configurable.
- **Impact:** Non-English users see US date format (MM/DD/YYYY) which may be confusing.
- **Suggested fix:** Use `toLocaleDateString()` without arguments to respect browser locale, or use a shared date formatting utility.

**[CR-013]** `searchSchema` limit defaults differ from API route defaults

- **File:** `src/lib/validation/schemas.ts:65` vs `src/app/api/search/route.ts:14`
- **Issue:** `searchSchema` defaults to `limit: 10`, but the search API route defaults to `limit: 20`. The schema is only used in `src/app/api/users/search/route.ts`, not the main search route, creating inconsistent default behaviors.
- **Impact:** User search defaults to 10 results; recipe+user search defaults to 20. Minor UX inconsistency.

**[CR-014]** `Post.averageRating` null safety in `mapToRecipe`

- **File:** `src/infrastructure/repositories/RecipeRepository.ts:211`
- **Issue:** `averageRating: post.averageRating ?? undefined` — the `Post` model has `averageRating` as `Float` with `@default(0)`, so it should never be null after creation. The `?? undefined` is defensive but unnecessary and hides the invariant.
- **Impact:** No runtime impact, but obscures the data model guarantee.
- **Suggested fix:** Assert the invariant: `averageRating: post.averageRating` (or add a comment explaining why the fallback exists).
