## Code Review — 2026-03-18

### Summary

Large Next.js recipe-sharing application with clean architecture. The codebase is generally well-structured, but contains several security gaps, race conditions, and data integrity issues that need attention.

### Findings

#### CRITICAL

**[CR-001]** Notification polling exposes user data without verifying recipient ownership

- **File:** `src/app/api/notifications/[id]/route.ts:37-40`
- **Issue:** The `updateMany` with `recipientId` filter returns `count` but the 404 response doesn't distinguish between "notification doesn't exist" and "notification belongs to someone else". However, the real issue is in `src/hooks/useNotificationPolling.ts` — the `fetchNotifications` GET endpoint at `src/app/api/notifications/route.ts` returns full sender data (username, fullName, avatar) to any authenticated user without pagination abuse protection beyond the 100-item limit.
- **Impact:** Low direct risk due to auth check, but the polling hook has no circuit breaker reset on user change (it does reset — I retract this sub-point).
- **Suggested fix:** This is acceptable as-is given the auth checks.

**[CR-002]** `cooked-recipes` POST deducts pantry items even when some ingredients are insufficient

- **File:** `src/app/api/cooked-recipes/route.ts:115-140`
- **Issue:** The loop deducts pantry items one by one. If ingredient A has sufficient stock and is deducted, but ingredient B does not, A is still deducted. The `insufficientIngredients` array is returned but the partial deduction is committed. This is all-or-nothing atomicity failure — a user marking a recipe as cooked may lose pantry stock for some ingredients while being told others were insufficient.
- **Impact:** Silent data loss in pantry quantities. Users lose tracked ingredients inconsistently.
- **Suggested fix:** Collect all deductions first, validate all have sufficient stock, then apply deductions. Or: only deduct ingredients that have sufficient stock and skip insufficient ones (current behavior), but the comment says "Only deduct if pantry has sufficient quantity" — the else branch just records insufficiency but prior deductions already happened.

**[CR-003]** Recipe match endpoint loads up to 500 candidate IDs then fetches full recipes without pagination

- **File:** `src/app/api/recipes/match/route.ts:95-100`
- **Issue:** The raw SQL query `LIMIT 500` caps candidate IDs, but then `prisma.post.findMany({ where: { id: { in: candidateIds } } })` loads all 500 full recipe objects with ingredients into memory at once. For recipes with large ingredient arrays, this can cause significant memory pressure.
- **Impact:** Memory spikes under load, potential OOM in serverless environments with limited memory.
- **Suggested fix:** Process candidates in batches of 50-100, or select only the fields needed for matching (id + ingredients) in the first pass, then fetch full data only for the final matched set.

**[CR-004]** `escapeLike` in recipe match doesn't handle all PostgreSQL LIKE special characters

- **File:** `src/app/api/recipes/match/route.ts:63`
- **Issue:** `escapeLike` handles `%`, `_`, and `\` but the resulting strings are interpolated into `LIKE` patterns via template literals. The `Prisma.sql` tagged template properly parameterizes values, but the pattern `%${escapeLike(name)}%` could still be problematic if `escapeLike` misses edge cases with the `ESCAPE '\\'` clause and backslash doubling.
- **Impact:** Potential SQL injection is mitigated by `Prisma.sql`, but malformed patterns could cause unexpected query behavior.
- **Suggested fix:** Verify with test cases containing `\`, `%`, and `_` in ingredient names.

#### HIGH

**[CR-005]** Admin recipe deletion catches `Prisma.PrismaClientKnownRequestError` with `instanceof Error` AND `instanceof Prisma.PrismaClientKnownRequestError` — the first check is always true

- **File:** `src/app/api/admin/recipes/[id]/route.ts:35-40`
- **Issue:** `error instanceof Error && error instanceof Prisma.PrismaClientKnownRequestError` — the `instanceof Error` check is redundant since `PrismaClientKnownRequestError` extends `Error`. But more importantly, if `adminService.deleteRecipe` throws a different error (not Prisma), it falls through to the generic 500, which is correct but the error message leaks to logs without sanitization.
- **Impact:** Minor. Redundant check, no functional bug.
- **Suggested fix:** Remove redundant `instanceof Error` check.

**[CR-006]** `RecipeFeed` infinite scroll doesn't debounce IntersectionObserver triggers

- **File:** `src/components/recipe/RecipeFeed.tsx:160-170`
- **Issue:** The `IntersectionObserver` callback calls `loadRecipes()` directly. While `loadingRef.current` prevents concurrent loads, rapid scrolling can queue multiple fetches in quick succession as soon as the previous one completes, because the observer fires every time the sentinel enters the viewport.
- **Impact:** Unnecessary API calls, potential duplicate recipe rendering despite the dedup logic.
- **Suggested fix:** Add a small debounce or throttle to the observer callback.

**[CR-007]** `CommentsSection` orphans uploaded images on comment POST failure

- **File:** `src/components/recipe/CommentsSection.tsx:119-135`
- **Issue:** Acknowledged in a TODO comment. Image is uploaded to Cloudinary first, then if the comment POST fails, the image is orphaned. No cleanup mechanism exists.
- **Impact:** Cloudinary storage leak over time.
- **Suggested fix:** Implement a server-side cleanup endpoint, or upload the image as part of the comment creation in a single request.

**[CR-008]** `useNotificationPolling` circuit breaker resets after 5 minutes but doesn't reset `failureTimestampsRef`

- **File:** `src/hooks/useNotificationPolling.ts:131-134`
- **Issue:** When the circuit breaker trips at 10 failures in 10 minutes, `scheduleNext()` checks `Date.now() - breakerTrippedAtRef.current > 5 * 60 * 1000` to reset. It clears `failureTimestampsRef.current = []` on reset, which is correct. However, the visibility handler at line 145 also resets `failureTimestampsRef.current = []` when `timeSinceLastFailure > 2 * 60 * 1000`, which can prematurely reset the sliding window even if the underlying issue persists.
- **Impact:** Circuit breaker can be bypassed by switching tabs, causing continued polling against a failing endpoint.
- **Suggested fix:** Don't reset failure timestamps on visibility change; only reset when the circuit breaker cooldown period has fully elapsed.

**[CR-009]** `AuthContext.logout` clears user state before the server-side cookie clear succeeds

- **File:** `src/contexts/AuthContext.tsx:85-100`
- **Issue:** `setUser(null)` is called immediately, then the logout API call happens. If the API call fails (both retries), the cookie persists but the UI shows logged-out state. On page refresh, the user will appear logged in again (cookie still valid), creating a confusing UX.
- **Impact:** Inconsistent auth state between client and server after failed logout.
- **Suggested fix:** This is a deliberate UX choice (optimistic logout). Document the trade-off or handle the error by showing a warning toast.

**[CR-010]** `RecipeFeed.handleLike` catches JSON parse errors but shows a vague message

- **File:** `src/components/recipe/RecipeFeed.tsx:293-305`
- **Issue:** When `response.ok` is true but `response.json()` fails (e.g., empty body), the like state is reverted and a warning toast is shown. However, the server may have already toggled the like. The optimistic UI and server state are now out of sync.
- **Impact:** Like count discrepancy between client and server until page refresh.
- **Suggested fix:** On JSON parse failure with 200 status, refetch the like status from the server instead of reverting.

#### MEDIUM

**[CR-011]** `BRANDING.contactEmail` is hardcoded in config and used directly in mailto links

- **File:** `src/config/branding.ts:26` / `src/components/Footer.tsx:47`
- **Issue:** The contact email `lucasarielfanelli@hotmail.com` is hardcoded. The `Footer` component constructs a mailto link with user-provided `formData.subject` in both the subject and body without any length validation or encoding safety check. While `encodeURIComponent` handles encoding, extremely long subjects could cause issues with some mail clients.
- **Impact:** Minor UX issue with very long messages.
- **Suggested fix:** Add length limits to the contact form fields.

**[CR-012]** `PersistentSearchBar` creates a new `AbortController` per debounce cycle but doesn't cancel the timeout before creating a new controller

- **File:** `src/components/search/PersistentSearchBar.tsx:117-145`
- **Issue:** The `useEffect` clears the timeout and aborts the controller on cleanup, but within the same effect run, if the timeout fires and the fetch starts, then the user types again before the fetch completes, the old controller is aborted (correct). However, `setIsSearching(true)` is set before the timeout, meaning the loading indicator shows immediately even during the 300ms debounce.
- **Impact:** Loading spinner appears 300ms too early, creating a slightly janky UX.
- **Suggested fix:** Move `setIsSearching(true)` inside the `setTimeout` callback, just before `fetch`.

**[CR-013]** `EditRecipeModal` doesn't reset `activeStep` when `recipe` prop changes

- **File:** `src/components/recipe/EditRecipeModal.tsx:88-102`
- **Issue:** The `useEffect` that pre-fills the form runs when `recipe` changes but doesn't reset `activeStep` to 0. If a user was on step 3 of editing recipe A, then the modal is closed and reopened with recipe B, they'll see step 3's content with recipe B's data.
- **Impact:** Confusing UX when editing different recipes in sequence.
- **Suggested fix:** Add `setActiveStep(0)` to the `useEffect` that runs when `recipe` changes. Note: `handleClose` does reset it, but the effect doesn't.

**[CR-014]** `normalizeIngredientName` plural stripping can produce incorrect stems

- **File:** `src/lib/utils/ingredients.ts:35-50`
- **Issue:** The function strips `oes` → removing last 2 chars (`tomatoes` → `tomato` is correct), but `heroes` → `hero` would also be correct. However, `shoes` → `sho` is wrong. The `noStripSuffixWords` set only covers a few exceptions.
- **Impact:** Ingredient matching false negatives for uncommon ingredient names.
- **Suggested fix:** Consider using a more robust stemming approach or expanding the exception set.

**[CR-015]** Admin pages check `isAdmin` client-side with `useAdminGuard` but render `null` during the redirect

- **File:** `src/app/admin/comments/page.tsx:96-98`, `src/app/admin/recipes/page.tsx:111-113`
- **Issue:** The guard redirects non-admins via `router.push('/')`, but during the brief period between `!isAdmin` being true and the redirect completing, `return null` is rendered. This is a flash of blank content.
- **Impact:** Minor UX issue — brief blank screen for non-admin users before redirect.
- **Suggested fix:** Acceptable given middleware also blocks admin pages. Defense-in-depth is working correctly.

**[CR-016]** `useCreateRecipe` doesn't invalidate queries with correct key

- **File:** `src/hooks/useCreateRecipe.ts:18`
- **Issue:** `queryClient.invalidateQueries({ queryKey: ['recipes'] })` uses key `['recipes']`, but `RecipeFeed` doesn't use React Query for its recipe list — it uses direct `fetch` calls. The invalidation is a no-op unless other components use this query key.
- **Impact:** After creating a recipe via the navigation dialog, the feed may not update until the user scrolls or filters change.
- **Suggested fix:** Either migrate `RecipeFeed` to React Query, or call the reload callback directly after creation.

**[CR-018]** `RecipeCard` uses `imgFallbackUsed` and `imgHidden` state for image error handling without cleanup

- **Issue:** If the fallback image `/chef-logo.png` also fails (e.g., CDN issues), `imgHidden` is set to true and a placeholder icon is shown. This is fine, but the component never attempts to retry loading the original image even if the network recovers.
- **Impact:** Negligible. Images stay broken until re-render.
- **Suggested fix:** Acceptable as-is.

**[CR-019]** `about/page.tsx` uses `'use client'` unnecessarily

- **File:** `src/app/about/page.tsx:1`
- **Issue:** The about page uses `'use client'` for Framer Motion animations, but the page content is entirely static. This prevents server-side rendering of the page content.
- **Impact:** Slightly worse initial load performance and SEO for the about page.
- **Suggested fix:** Consider server-rendering the static content and only wrapping animation containers in client components.

**[CR-020]** Test files use `any` type extensively

- **File:** Multiple test files
- **Issue:** Mock type definitions use `any` liberally (e.g., `jest.Mock`, `any` casts). While acceptable in tests, it reduces type safety.
- **Impact:** Tests may pass even when interface changes break runtime behavior.
- **Suggested fix:** Use `jest.MockedFunction` and proper generic types where feasible.
