## Code Review — 2026-03-21

### Summary

Three API route files with transaction-heavy logic, pantry deduction, and recipe matching. Several critical issues found around data integrity, security, and error handling.

### Findings

#### CRITICAL

**[CR-001]** Race condition in PUT profile: transaction does not lock the user row before reading

- **File:** `src/app/api/users/profile/route.ts:44-53`
- **Issue:** The comment says "atomically in a transaction to prevent a concurrent PUT from changing the avatar between the read and update," but a default READ COMMITTED transaction does **not** prevent a concurrent `UPDATE` from committing between the `findUnique` and `update`. Without `SELECT ... FOR UPDATE` or serializable isolation, two concurrent PUTs can both read the same old avatar, both succeed, and only one cleanup fires — the other old avatar is leaked forever in Cloudinary.
- **Impact:** Orphaned Cloudinary images that are never cleaned up, accumulating storage costs.
- **Suggested fix:**

```ts
const current = await tx.$queryRaw`SELECT avatar FROM "User" WHERE id = ${user.id} FOR UPDATE`;
```

**[CR-002]** `deductedIngredients` stored as JSON is attacker-controllable on restore — no schema validation on read

- **File:** `src/app/api/cooked-recipes/route.ts:266-295`
- **Issue:** On DELETE, `cookedRecipe.deductedIngredients` is read from the database as `unknown[]` and fields are accessed with loose type checks (`typeof d.amount !== 'number'`). If an attacker can craft a cooked recipe with manipulated `deductedIngredients` JSON (e.g., via direct DB access, API bypass, or a future bug), they can restore arbitrary quantities to any pantry item ID they guess — the `pantryItemId` is trusted from the stored data and only checked for UUID format, not that it was originally deducted from _this_ user's pantry in _this_ transaction. The `findFirst` with `pantry: { userId: user.id }` mitigates cross-user writes, but a user can still inflate their own pantry quantities by replaying or tampering with `deductedIngredients`.
- **Impact:** Pantry quantity inflation; a user could delete and re-cook the same recipe to accumulate pantry items beyond what they actually have, since the `deductedIngredients` blob is trusted without cross-referencing original deduction records.
- **Suggested fix:** Store deducted ingredients in a normalized child table (`CookedRecipeDeduction`) with foreign keys to `PantryItem`, rather than a freeform JSON blob. This makes the data tamper-evident via referential integrity. At minimum, record a hash/checksum of the deduction data at creation time and verify it before restoring.

**[CR-003]** Recipe creation does not enforce per-user rate limiting or duplicate detection

- **File:** `src/app/api/recipes/route.ts:161-198`
- **Issue:** The POST endpoint creates recipes without any rate limiting or duplicate detection. An authenticated user can create unlimited recipes in rapid succession. Unlike the cooked-recipes endpoint which has `MAX_DAILY_COOKS`, there is no equivalent protection here.
- **Impact:** A single compromised or malicious account can flood the database with thousands of recipes, consuming storage and degrading search/feed performance for all users.
- **Suggested fix:** Add a daily creation limit check similar to `MAX_DAILY_COOKS`:

```ts
const twentyFourHoursAgo = new Date(Date.now() - 24 * 60 * 60 * 1000);
const dailyPostCount = await prisma.post.count({
  where: { userId: user.id, createdAt: { gte: twentyFourHoursAgo } },
});
if (dailyPostCount >= MAX_DAILY_POSTS) {
  return NextResponse.json({ error: 'Daily recipe creation limit reached' }, { status: 429 });
}
```

**[CR-004]** SQL injection via `Prisma.join` with LIKE patterns is safe, but `ORDER BY p.id` produces non-deterministic results with `LIMIT` — match results are silently incomplete and biased

- **File:** `src/app/api/recipes/match/route.ts:91-102`
- **Issue:** `ORDER BY p.id LIMIT ${limit}` returns the first N rows by primary key, which is typically a UUID. This means the candidate set is determined by the lexicographic order of random UUIDs, not by any relevance metric. Users will consistently miss recipes whose UUIDs sort after the cutoff. With a growing recipe table, this becomes increasingly incomplete. The comment claims the rate limit is the "primary protection," but the real issue is correctness — users get a biased, arbitrary subset of candidates.
- **Impact:** Recipe matching silently excludes potentially perfect matches. Users see inconsistent results that don't improve as more recipes are added.
- **Suggested fix:** Order candidates by a relevance signal (e.g., number of matching pantry ingredients, `averageRating`, or `createdAt DESC`) so the LIMIT captures the most relevant candidates:

```sql
ORDER BY p."averageRating" DESC NULLS LAST, p."createdAt" DESC
LIMIT ${limit}
```

**[CR-005]** `DELETE /api/cooked-recipes` restores pantry items but does not validate that the cooked recipe is old enough to delete

- **File:** `src/app/api/cooked-recipes/route.ts:237-330`
- **Issue:** A user can immediately delete a just-created cooked recipe to get their pantry items restored. Combined with the 24-hour duplicate window check on POST, this creates an exploit loop: cook (deducts pantry) → immediately delete (restores pantry) → wait 24h → repeat. The user gets the "cooked" record history benefit without actually consuming pantry items. More critically, if the 24-hour window uses `cookedAt` from the _deleted_ record, the window check in POST won't find the deleted record, allowing immediate re-cooking.
- **Impact:** Users can game the cooked recipe system to maintain inflated cooking stats without actually consuming pantry items. The rating system is also affected since deleting removes the rating.
- **Suggested fix:** Either soft-delete cooked recipes (keep the record but mark as deleted, still count for the 24h window), or don't restore pantry items on delete:

```ts
// Option 1: Soft delete
await tx.cookedRecipe.update({
  where: { id: cookedRecipeId },
  data: { deletedAt: new Date() },
});
// Option 2: Remove pantry restoration entirely
// (Users accepted the deduction when they cooked)
```
