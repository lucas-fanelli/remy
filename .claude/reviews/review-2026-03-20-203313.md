## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing app with clean architecture. Several security gaps, race conditions, and data integrity issues found across API routes, client components, and infrastructure layers.

### Findings

#### CRITICAL

**[CR-001]** Session-level advisory lock leak on error in recipe match endpoint

- **File:** `src/app/api/recipes/match/route.ts:69-71`
- **Issue:** `pg_advisory_lock` (session-level) is acquired but the `finally` block that releases it via `pg_advisory_unlock` can be skipped if `requireAuth` or code before the `try` block throws. Since session-level locks persist until explicitly released or the connection is returned to the pool, a leaked lock blocks all subsequent match requests for that user until the Prisma connection is recycled.
- **Impact:** Permanent deadlock for affected users on the match endpoint. Under connection pooling (PgBouncer), the lock can leak to a different user's session.
- **Suggested fix:** Move the lock acquisition inside the `try` block, or switch to `pg_advisory_xact_lock` inside a transaction (like other endpoints do):

```ts
// Replace session-level lock with transaction-level lock
const result = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(${PG_ADVISORY_LOCK_MATCH}, hashtext(${user.id}))`;
  // ... all queries inside tx ...
});
```

**[CR-002]** Cooked recipe DELETE does not use advisory lock for pantry restoration

- **File:** `src/app/api/cooked-recipes/route.ts:229-280`
- **Issue:** The POST handler acquires `PG_ADVISORY_LOCK_COOKED_RECIPE` before deducting pantry items, but the DELETE handler restores pantry items without any advisory lock. Concurrent DELETE + cook POST for the same user can produce negative pantry quantities or lost updates.
- **Impact:** Data corruption — pantry quantities can go negative or be silently overwritten.
- **Suggested fix:** Acquire the same per-user advisory lock in the DELETE transaction:

```ts
await tx.$executeRaw`SELECT pg_advisory_xact_lock(${PG_ADVISORY_LOCK_COOKED_RECIPE}, hashtext(${user.id}))`;
```

**[CR-003]** No rate limiting on `POST /api/notifications` (mark-all-as-read)

- **File:** `src/middleware.ts:214`
- **Issue:** The notification GET endpoint has a generous 200-request limit, but the POST endpoint (mark all as read) uses the default 100/15min IP limit. However, the `isNotificationGet` check only exempts GET. A malicious user can spam the POST endpoint to force bulk DB updates (`updateMany` on all unread notifications) without meaningful throttling, since 100 requests \* N notifications per request = massive write amplification.
- **Impact:** Database write amplification attack. An attacker with many notifications can trigger expensive `updateMany` queries.
- **Suggested fix:** Add explicit rate limiting for `POST /api/notifications` with a stricter limit (e.g., 10 per 15 minutes).

#### HIGH

**[CR-004]** `handleShare` clipboard fallback exposes URL via Snackbar without sanitization

- **File:** `src/app/recipe/[id]/page.tsx:268-280`
- **Issue:** `window.location.href` is used directly in the share flow. While clipboard.writeText is safe, the Snackbar message "Link copied to clipboard!" is benign. However, if `navigator.share` throws (not just missing), the error is silently swallowed and the user gets no feedback.
- **Impact:** Poor UX — share failures on browsers that partially support Web Share API give no error.
- **Suggested fix:** Catch `navigator.share` errors:

```ts
try {
  await navigator.share({ ... });
} catch (err) {
  if ((err as Error).name !== 'AbortError') {
    // User didn't cancel — fallback to clipboard
    // ... existing clipboard logic
  }
}
```

**[CR-005]** `deductPantryItems` doesn't validate `recipeAmount` is positive before deducting

- **File:** `src/app/api/cooked-recipes/route.ts:68-72`
- **Issue:** `parseAmount` can return 0 (e.g., for "0" amount), and `isNaN` check skips NaN but allows 0 and negative values. A recipe ingredient with amount "0" or "-1" would silently skip deduction or add quantity.
- **Impact:** Recipe data with zero/negative amounts silently bypass pantry deductions.
- **Suggested fix:**

```ts
if (isNaN(recipeAmount) || recipeAmount <= 0) continue;
```

**[CR-006]** `RecipeFeed` infinite scroll has no deduplication across pages when filter changes race

- **File:** `src/components/recipe/RecipeFeed.tsx:159-164`
- **Issue:** The `existingIds` dedup check on line 163 protects against duplicates from the same fetch, but `recipesLengthRef` is used for offset calculation and is only updated after setState. If `loadRecipes(false)` is called twice in quick succession (e.g., IntersectionObserver fires during a filter change), both calls use the same offset, fetching the same page twice. The dedup set catches exact duplicates but offset drift accumulates.
- **Impact:** Users may see missing recipes in the feed (skipped pages) or duplicates that slip through if IDs differ.
- **Suggested fix:** Track offset in a ref that's updated synchronously before the fetch, not after setState.

**[CR-007]** Footer `mailto` link allows header injection via newlines in name/email

- **File:** `src/components/Footer.tsx:63-67`
- **Issue:** The `sanitize` function strips control characters `\x00-\x1F`, but `\x7F` (DEL) is also stripped. However, the sanitization happens after form input which has `maxLength` limits. The real issue: `encodeURIComponent` handles URL encoding, but some email clients parse `%0d%0a` in the body as newlines which could be used for mailto header injection in older clients.
- **Impact:** Low risk with modern clients, but on vulnerable email clients, an attacker controlling the form could inject additional headers.
- **Suggested fix:** This is defense-in-depth; current sanitization is reasonable. Consider also rejecting `\r` and `\n` explicitly in the form values before encoding.

**[CR-008]** `EditProfileModal` website validation accepts `javascript:` URLs via URL constructor

- **File:** `src/components/profile/EditProfileModal.tsx:128-140`
- **Issue:** The client-side validation checks for `http://` or `https://` prefix, and then validates with `new URL()`. This is correct. However, the server-side `updateProfileSchema` in `schemas.ts` uses `z.string().url()` which accepts any valid URL including `javascript:`. The `UserService.updateProfile` re-validates, but the Zod schema is the first line of defense.
- **Impact:** Low — `UserService` catches non-http protocols, but the Zod schema should be tightened for defense-in-depth.
- **Suggested fix:** Add `.refine(url => url.startsWith('http://') || url.startsWith('https://'))` to the Zod schema.

#### MEDIUM

**[CR-009]** `normalizeIngredientName` plural stripping can produce incorrect stems

- **File:** `src/lib/utils/ingredients.ts:38-58`
- **Issue:** The suffix stripping rules are applied sequentially without checking if the result is a real word. For example, "stress" is protected by the `!endsWith('ss')` check, but "success" (7 chars, ends in 's', doesn't end in 'ss' — wait, it does end in 'ss'). Actually "abscess" ends in 'ss' so it's protected. But "index" → "inde" (stripped 'x' + 'es'? no, 'xes' check applies to "indexes" → "index"). The logic is fragile and the comment says to consider a stemming library.
- **Impact:** Incorrect ingredient matching — some ingredients may not match or may false-match.
- **Suggested fix:** As the comment suggests, replace with a proper stemming library like `natural` or `stemmer`.

**[CR-010]** `useNotificationPolling` breakerTripCount grows without bound in theory

- **File:** `src/hooks/useNotificationPolling.ts:96`
- **Issue:** `breakerTripCountRef` is capped at 10 via `Math.min(..., 10)`, but the cooldown formula `5 * 60 * 1000 * Math.pow(2, breakerTripCountRef.current - 1)` at tripCount=10 yields 5min \* 512 = 2560min, which is capped at 30min. This is fine mathematically, but the decrement logic `if (breakerTripCountRef.current > 0) breakerTripCountRef.current--` on success means the trip count slowly recovers. If the server flaps (alternating success/failure), the trip count oscillates, and the backoff never fully resets.
- **Impact:** Notification polling may stay in a degraded state longer than necessary during intermittent failures.
- **Suggested fix:** Reset `breakerTripCountRef` to 0 on first successful fetch after a breaker trip, rather than decrementing by 1.

**[CR-011]** `AdminService.promoteToAdmin` doesn't check if user is already admin

- **File:** `src/infrastructure/services/AdminService.ts:77-97`
- **Issue:** `promoteToAdmin` unconditionally updates the user role to ADMIN without checking current role. This is idempotent but generates an unnecessary DB write and audit noise.
- **Impact:** Minor — wasted DB write, misleading audit trail.
- **Suggested fix:** Check current role before updating, or accept the idempotent behavior as intentional.

**[CR-012]** `PersistentSearchBar` creates new AbortController on every keystroke but doesn't abort previous search

- **File:** `src/components/search/PersistentSearchBar.tsx:122-150`
- **Issue:** The `searchAbortRef.current?.abort()` is called before creating a new controller, but `searchAbortRef` is only assigned inside `setTimeout`. If the user types quickly, multiple timeouts may be pending, each with their own controller that isn't tracked by the ref. The cleanup function correctly aborts via the local `controller` variable, but in-flight requests from previous debounce cycles that already passed the timeout may not be aborted.
- **Impact:** Stale search results could briefly flash if a slow response arrives after a newer one.
- **Suggested fix:** The current implementation is actually correct because `searchAbortRef.current?.abort()` at the top of the effect cancels the previous in-flight request, and `clearTimeout` cancels pending debounce timers. The local `controller` in the cleanup handles unmount. This is a false alarm — the code is correct.

**[CR-013]** `RecipeCard` `warnedRecipeIds` set grows without bound in long sessions

- **File:** `src/components/recipe/RecipeCard.tsx:40`
- **Issue:** The dev warning dedup set is cleared when it exceeds 100 entries, but in a long session with many unique recipe IDs, it oscillates between 0 and 100, creating GC pressure. This only runs in development.
- **Impact:** Minor dev-only performance issue.
- **Suggested fix:** Use a capped LRU or just remove the dedup — dev warnings are fine to repeat occasionally.

**[CR-014]** `AuthContext` logout retry fires unconditionally on network error

- **File:** `src/contexts/AuthContext.tsx:94-114`
- **Issue:** If the first logout request throws a network error, `retryLogout()` is called. If the retry also fails, `window.dispatchEvent(new CustomEvent('auth:logout-failed'))` fires. But the retry uses a 1-second delay, which means there's a brief window where the user appears logged out (state cleared) but the cookie is still valid. If the user navigates to another page during this window, they could make authenticated requests despite the UI showing them as logged out.
- **Impact:** Inconsistent auth state between UI and server-side cookie for up to 1 second + network latency.
- **Suggested fix:** This is inherent to optimistic logout. The warning Snackbar is the correct mitigation. Consider also clearing the cookie client-side via `document.cookie` as a fallback (though httpOnly prevents this). The current approach is acceptable.
