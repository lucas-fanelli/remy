## Code Review — 2026-03-20

### Summary

Large Next.js recipe-sharing application with clean architecture. Generally well-structured with good security practices (httpOnly cookies, CSRF protection, advisory locks). However, several real bugs, race conditions, and security gaps exist across the codebase.

### Findings

#### CRITICAL

**[CR-001]** Race condition in Cloudinary cleanup during avatar upload — old avatar deleted after new one is set

- **File:** `src/app/api/upload/avatar/route.ts:82-85`
- **Issue:** The old avatar is cleaned up _after_ the database is updated with the new avatar URL. If cleanup fails silently and the new upload also fails on a subsequent retry, the user's avatar points to a deleted image. More critically, if the server crashes between `prisma.user.update` and `cleanupCloudinaryImage`, the old image is orphaned with no record of it.
- **Impact:** Orphaned Cloudinary images accumulating storage costs; potential broken avatar if new upload is lost.
- **Suggested fix:** The cleanup script handles this, but the comment says "best-effort" without `try/catch`. Add explicit error logging:

```typescript
if (existingUser?.avatar) {
  try {
    await cleanupCloudinaryImage(existingUser.avatar);
  } catch (err) {
    logServerError('Failed to cleanup old avatar:', err);
  }
}
```

**[CR-002]** `striptags` not applied to comment text on creation or update

- **File:** `src/app/api/recipes/[id]/comments/route.ts:89` and `src/app/api/recipes/[id]/comments/[commentId]/route.ts:68`
- **Issue:** Comment `text` is stored raw — only `text.trim()` is applied. The cooked-recipes route uses `striptags` on notes, and pantry routes use `striptags` on names, but comments do not. While React auto-escapes JSX output, if comment text is ever rendered with `dangerouslySetInnerHTML` or in email notifications, stored XSS becomes exploitable.
- **Impact:** Stored HTML in comment text; defense-in-depth violation given all other text fields are stripped.
- **Suggested fix:**

```typescript
import striptags from 'striptags';
// In both POST and PATCH handlers:
text: striptags(text.trim()),
```

**[CR-003]** Notification polling 401 confirmation can trigger logout on transient auth failures

- **File:** `src/hooks/useNotificationPolling.ts:88-101`
- **Issue:** When `/api/notifications` returns 401, the hook calls `/api/auth/me` to confirm. If `/api/auth/me` _also_ fails due to a transient network error (caught in the `catch` block at line 98), it calls `onAuthInvalid()` which logs the user out. A temporary network blip during notification polling destroys the user's session.
- **Impact:** Users randomly logged out during intermittent network issues.
- **Suggested fix:** Only logout on confirmed 401 from `/api/auth/me`, not on network errors:

```typescript
} catch (err) {
  // Network error confirming auth — don't logout, just pause polling
  if (!isMountedRef.current) return;
  pollingStoppedRef.current = true;
  setIsPollingPaused(true);
  // Don't call onAuthInvalid() on network errors
}
```

#### HIGH

**[CR-004]** `cooked-recipes` DELETE does not use Content-Type check but relies on query param for ID — no body parsing needed, but missing CSRF header documentation

- **File:** `src/app/api/cooked-recipes/route.ts:208-210`
- **Issue:** The DELETE handler uses `searchParams.get('id')` instead of a body. The comment says "CSRF protection is enforced by middleware for all DELETE requests" but the middleware checks for `x-requested-with` header. The client-side code at `src/app/recipe/[id]/page.tsx` doesn't show the cooked-recipe DELETE being called with `X-Requested-With` header — it's unclear if the fetch includes it, since the `sendCookRequest` function uses POST (not DELETE).
- **Impact:** Potential CSRF bypass if DELETE is called without the custom header.
- **Suggested fix:** Verify the client sends `X-Requested-With: fetch` on all DELETE calls to this endpoint, or add explicit documentation.

**[CR-005]** Recipe match endpoint has no statement timeout on the fallback branch

- **File:** `src/app/api/recipes/match/route.ts:108-115`
- **Issue:** The fallback branch (when `pantryPatterns.length === 0`) wraps queries in a transaction with `SET LOCAL statement_timeout = '5s'`, but uses `prisma.post.findMany` with `orderBy: { averageRating: 'desc' }` which could be slow without an index on `averageRating`. The main query branch correctly sets a statement timeout.
- **Impact:** Unbounded query time on the fallback path could cause request timeouts under load.
- **Suggested fix:** Both branches already set `statement_timeout = '5s'` — this is actually fine on re-reading. No fix needed. _(Retracted)_

**[CR-006]** `adminService.demoteToUser` in PATCH handler races with the advisory lock check

- **File:** `src/app/api/admin/users/[id]/route.ts:127-137`
- **Issue:** The transaction acquires the advisory lock and checks admin count, but then calls `adminService.demoteToUser(id)` which runs _outside_ the transaction (it's a separate Prisma call). Between the count check and the actual role update, another request could demote a different admin.
- **Impact:** Could potentially demote below the minimum admin count in a race condition.
- **Suggested fix:** Move the `user.update` into the same transaction:

```typescript
user = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(...)`;
  const [{ count }] = await tx.$queryRaw<...>`SELECT COUNT(*)::int ...`;
  if (count <= 1) throw new Error('LAST_ADMIN');
  return tx.user.update({
    where: { id },
    data: { role: 'USER' },
    select: { /* ... */ },
  });
}, { timeout: 10000 });
```

**[CR-007]** `EditProfileModal` allows `javascript:` URLs in the website field

- **File:** `src/components/profile/EditProfileModal.tsx:130-137`
- **Issue:** Client-side validation checks for `http://` or `https://` prefix, but the `new URL()` check can pass `javascript:` URLs if the user types `javascript:alert(1)` — actually, `new URL('javascript:alert(1)')` does parse successfully with `protocol = 'javascript:'`. The server-side `UserService.updateProfile` validates `url.protocol`, but the profile page renders the website as a clickable `<a href>` link at `src/app/profile/[username]/page.tsx:290`, which would execute JavaScript.
- **Impact:** Stored XSS via profile website field if server validation is bypassed or has a gap.
- **Suggested fix:** The server-side check in `UserService.ts:41` correctly validates `['http:', 'https:']`, so this is defense-in-depth. The client check is also correct. However, the `updateProfileSchema` in `schemas.ts` uses `z.string().url()` which accepts any valid URL including `javascript:`. Add protocol validation to the Zod schema:

```typescript
website: z.string()
  .url()
  .refine((url) => !url || /^https?:\/\//.test(url), 'Website must start with http:// or https://');
```

Wait — this already exists at line 53. So this is actually covered. _(Retracted)_

**[CR-008]** Email exposed in admin user list response despite masking

- **File:** `src/infrastructure/services/AdminService.ts:82`
- **Issue:** `maskEmail` replaces characters but preserves the structure (e.g., `t**@e**.com`). The admin user management page at `src/app/admin/users/page.tsx:209` displays this masked email. However, the admin comments page at `src/app/admin/comments/page.tsx` and admin recipes page display the raw `user.email` from the comment/recipe join — these are NOT masked because `getAllComments` and `getAllRecipes` don't apply `maskEmail`.
- **Impact:** Full email addresses of users exposed in admin comments and recipes views, inconsistent with the masking on the users page.
- **Suggested fix:** Apply `maskEmail` to emails in `getAllRecipes` and `getAllComments` responses as well.

#### MEDIUM

**[CR-009]** `RecipeFeed` infinite scroll has no deduplication guard on rapid IntersectionObserver triggers

- **File:** `src/components/recipe/RecipeFeed.tsx:135-139`
- **Issue:** The `loadingRef.current` guard prevents concurrent calls, but if the observer fires while a reset is in progress (`reset = true`), `loadingRef.current` is already set to true on the reset path. The `abortControllerRef.current?.abort()` at the top handles this, but the aborted request still increments `pageRef.current` in the stale response handler because the `thisRequestId` check only covers state updates, not the page ref increment at line 157.
- **Impact:** Potential skipped page in infinite scroll after rapid filter changes.
- **Suggested fix:** Move `pageRef.current` increment inside the `thisRequestId` check.

**[CR-010]** `logServerError` uses a module-level `sentryPromise` that may resolve after app shutdown

- **File:** `src/lib/utils/logger.ts:7-8`
- **Issue:** `sentryPromise` is a fire-and-forget import that runs at module load. If Sentry fails to load, `SentryModule` stays `null` forever, and the fallback `.then()` in `logServerError` creates a microtask that may execute after the process is shutting down.
- **Impact:** Minor — lost error reports if Sentry SDK fails to load; no functional impact.
- **Suggested fix:** Accept as-is; the pattern is reasonable for optional dependency loading.

**[CR-011]** `useCreateRecipe` hook doesn't invalidate React Query cache

- **File:** `src/hooks/useCreateRecipe.ts:14-15`
- **Issue:** After creating a recipe, `RecipeFeed` uses direct fetch (not React Query), so there's no cache to invalidate. However, the recipe detail page uses `useRecipe` (React Query). If a user creates a recipe and immediately navigates to it, the stale cache could show a 404.
- **Impact:** Unlikely in practice since the recipe is new, but architecturally inconsistent.
- **Suggested fix:** This is acceptable given the current flow navigates to `/` after creation.

**[CR-012]** Footer contact form has no rate limiting on mailto generation

- **File:** `src/components/Footer.tsx:54-66`
- **Issue:** The `handleSendEmail` function opens a `mailto:` link. While this is client-side only and doesn't hit the server, there's no debounce — rapid clicks generate multiple `window.open` calls.
- **Impact:** Minor UX annoyance; no security impact since mailto is client-side.
- **Suggested fix:** Add a simple flag to prevent rapid re-clicks.

**[CR-013]** Pantry PUT endpoint accepts `category` but doesn't validate against known categories

- **File:** `src/app/api/pantry/[id]/route.ts:67-68`
- **Issue:** `sanitizedCategory` strips HTML but accepts any string as a category. The client uses a fixed list plus custom categories, but the server doesn't validate. An attacker could set absurdly long categories (up to `MAX_ITEM_NAME_LENGTH = 200`).
- **Impact:** Data quality issue; categories could contain arbitrary text up to 200 chars.
- **Suggested fix:** This is intentional (freeSolo Autocomplete allows custom categories). The length limit is sufficient.

**[CR-014]** `SearchResults` component `truncateAtWord` returns empty string for `maxLen <= 0`

- **File:** `src/components/SearchResults.tsx:35`
- **Issue:** `truncateAtWord` handles `maxLen <= 0` by returning `''`, but if called with a negative value (which shouldn't happen from current code), it silently swallows content. More importantly, `lastIndexOf(' ', maxLen)` returns -1 if no space is found before `maxLen`, and the fallback `idx > 0 ? idx : maxLen` uses `maxLen` which could split mid-word on short descriptions.
- **Impact:** Minor — could truncate mid-word for descriptions with no spaces in first 50 chars.
- **Suggested fix:** Acceptable behavior for edge case.
