## Code Review — 2026-03-21

### Summary

Several API routes with solid transaction handling and concurrency controls, but meaningful bugs in edge cases, a potential data leak in the user service interface, and duplicated error-handling boilerplate that will rot.

### Findings

#### CRITICAL

**[CR-001]** `IUserService.updateProfile` returns full `User` minus password — leaks email to client

- **File:** `src/domain/services/IUserService.ts:12`
- **Issue:** `UserPublicProfile = Omit<User, 'password'>` still includes `email`, `role`, and any other sensitive fields. The PUT handler in `src/app/api/users/profile/route.ts:53` passes `updatedUser` directly into the JSON response. Every profile update leaks the user's email address (and role, verification status, etc.) to the client.
- **Impact:** PII exposure. Any authenticated user can see their own raw email in network tab, but more critically if this type is reused elsewhere (e.g., admin endpoints returning other users' profiles), it leaks other users' emails.
- **Suggested fix:** Define an explicit safe projection type and select only safe fields:

```typescript
export type UserPublicProfile = Pick<
  User,
  | 'id'
  | 'username'
  | 'fullName'
  | 'bio'
  | 'avatar'
  | 'website'
  | 'isPrivate'
  | 'isVerified'
  | 'createdAt'
>;
```

**[CR-002]** Race condition in PUT profile: avatar cleanup fires even if the update fails validation in the service layer

- **File:** `src/app/api/users/profile/route.ts:46-53`
- **Issue:** `currentUser` is fetched _before_ `userService.updateProfile()` is called. If `updateProfile` throws a non-Zod, non-auth error (e.g., a unique constraint violation or DB timeout), execution jumps to the outer catch, but `currentUser` was already fetched. This is fine _currently_ because the cleanup is after the success path. However, the real bug is that `currentUser` and `updatedUser` are not read atomically — another concurrent PUT could change the avatar between the `findUnique` and `updateProfile` calls, causing the wrong image to be deleted.
- **Impact:** Deleting a Cloudinary image that is still in use by the user's current profile if two profile updates race.
- **Suggested fix:** Wrap the read + update in a transaction, or have `updateProfile` return the previous avatar so cleanup can be done safely:

```typescript
const { previous, updated } = await userService.updateProfileReturningPrevious(user.id, profileData);
if (previous?.avatar && previous.avatar !== updated.avatar && isCloudinaryUrl(previous.avatar)) {
  cleanupCloudinaryImage(previous.avatar).catch(…);
}
```

**[CR-003]** `deductPantryItems` uses `striptags` on ingredient names during deduction but not during matching

- **File:** `src/app/api/cooked-recipes/route.ts:97-99`
- **Issue:** The `name` field from `recipeIngredients` is used raw for matching (`normalizeIngredientName(ingredient.name)`) but then stored via `striptags(d.name)` in `deductedIngredients`. If an ingredient name contains HTML tags, the matching will succeed against the raw name, but the stored `deductedIngredients.name` will differ from the original. On DELETE (undo), the restore logic looks up by `name` as a fallback (`where: { name: d.name as string }`), which will now search for the stripped name — potentially matching the wrong pantry item or failing to match at all.
- **Impact:** Pantry restoration on cooked-recipe deletion could fail silently or restore to the wrong item when ingredient names contain angle brackets.
- **Suggested fix:** Sanitize ingredient names once at the top of `deductPantryItems` before both matching and storage, or sanitize at recipe creation time so the data is clean by the time it reaches this code.

**[CR-004]** Unhandled `Promise` in DELETE account — `Promise.allSettled` is fire-and-forget but not awaited, risks unhandled rejection in edge runtime

- **File:** `src/app/api/users/profile/route.ts:85-93`
- **Issue:** `Promise.allSettled(…).then(…).catch(() => {})` is not `await`ed. While the `.catch(() => {})` suppresses the outer rejection, the inner `.then()` callback itself calls `logServerError` which could throw (e.g., if the logger's transport is broken). That throw inside `.then()` creates a new rejected promise that is _not_ caught — the `.catch` is chained on the _outer_ promise, not on the `.then()` return. This is a promise chain ordering bug.
- **Impact:** Unhandled promise rejection crash in edge cases; in Vercel Edge Runtime this can terminate the function.
- **Suggested fix:**

```typescript
Promise.allSettled(imageUrls.map((url) => cleanupCloudinaryImage(url)))
  .then((results) => {
    const failures = results
      .map((r, i) => (r.status === 'rejected' ? { url: imageUrls[i], reason: r.reason } : null))
      .filter(Boolean);
    if (failures.length > 0)
      logServerError('Failed to cleanup images for deleted account', failures);
  })
  .catch(() => {}); // This catch is on the .then() return, which is correct
```

Wait — re-reading: `.then().catch()` chains correctly. The `.catch` _does_ catch errors from the `.then`. I retract the chain ordering concern. However, the fire-and-forget pattern still means the response is sent before cleanup finishes, and if the serverless function shuts down, cleanup is silently dropped. This is documented as intentional but still a data integrity risk. Downgrading to HIGH because orphaned images accumulate.

**[CR-005]** `GET /api/recipes` exposes `ingredients` and `instructions` JSON blobs in list endpoint

- **File:** `src/app/api/recipes/route.ts:122-123`
- **Issue:** The recipe list endpoint maps `recipe.ingredients` and `recipe.instructions` into every item in the response. These are potentially large JSON arrays (up to 100 ingredients, 50 instructions with 5KB descriptions each). For a list page showing 20 recipes, this could mean sending megabytes of data the client doesn't render in the feed.
- **Impact:** Significant bandwidth waste and slower page loads, especially on mobile. Also increases Prisma memory usage since these columns aren't excluded from the query.
- **Suggested fix:** Remove `ingredients` and `instructions` from the list response, or add a `select` clause to the Prisma query that excludes them:

```typescript
select: {
  id: true, title: true, description: true, imageUrl: true,
  userId: true, cookingTime: true, prepTime: true, servings: true,
  difficulty: true, caption: true, createdAt: true, updatedAt: true,
  averageRating: true, reviewCount: true,
  user: { select: { id: true, username: true, fullName: true, avatar: true } },
  _count: { select: { likes: true, comments: true } },
}
```

**[CR-006]** Recipe match endpoint holds advisory lock + transaction for entire computation including in-memory matching

- **File:** `src/app/api/recipes/match/route.ts:79-211`
- **Issue:** The entire match computation — DB queries, in-memory ingredient matching loop (up to 20K comparisons), and batch recipe fetches — runs inside a single `$transaction` with advisory lock. The 10s `statement_timeout` only applies to individual SQL statements, not to the total transaction duration (the 15s outer timeout is the real bound). Holding a transaction open for up to 15 seconds while doing CPU-bound work in the application layer is an anti-pattern: it holds a DB connection from the pool and prevents other requests from the same user from proceeding.
- **Impact:** Under load, the connection pool can be exhausted. A user making a match request ties up a DB connection for up to 15 seconds.
- **Suggested fix:** Split into two phases: (1) a short transaction to read pantry + candidates, (2) in-memory matching outside the transaction, (3) a second short read for full recipe data. The advisory lock can be acquired/released in the first transaction.

**[CR-008]** Duplicated error-handling pattern for auth across every route handler

- **Files:** `src/app/api/cooked-recipes/route.ts:106-110`, `src/app/api/recipes/match/route.ts:54-58`, `src/app/api/notifications/[id]/route.ts:16-21`, and others
- **Issue:** Every route repeats the same try/catch pattern for `requireAuth`:

```typescript
let user;
try {
  user = await requireAuth(request);
} catch {
  return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
}
```

This is duplicated across at least 6 files in this diff. Some routes (e.g., `profile/route.ts`) use a different pattern where auth errors are caught in the outer catch via message comparison. Inconsistent and repetitive.

- **Impact:** Maintenance burden; easy to forget the pattern in a new route; inconsistent error response shapes (`ApiResponseHelper.unauthorized()` vs raw JSON).
- **Suggested fix:** Make `requireAuth` return a `NextResponse | User` discriminated result, or use a middleware/wrapper:

```typescript
const [user, authError] = await tryAuth(request);
if (authError) return authError;
```

**[CR-009]** `maskEmail` in admin route doesn't handle edge cases

- **File:** `src/app/api/admin/users/[id]/route.ts:11-19`
- **Issue:** If `email` is an empty string, `atIdx` is -1, early return `'***@***'` is fine. But if `local` is exactly 1 character (e.g., `a@b.com`), `maskedLocal = 'a' + '*'.repeat(max(0,2)) = 'a**'` which implies a 3-char local part for a 1-char input. Minor misrepresentation, but more importantly, for emails like `a@b.c`, `domainName` is `'b'` (length 1), so `maskedDomain = '***'` — the mask reveals that the domain is very short, which is arguably more info than the original.
- **Impact:** Minor information leakage about email structure; non-standard masking that could confuse admin users.
- **Suggested fix:** Use a simpler, consistent mask: `a***@b***.com` regardless of length.

**[CR-010]** `cookedRecipeSchema` allows `notes` to be an empty string

- **File:** `src/app/api/cooked-recipes/route.ts:12`
- **Issue:** `notes: z.string().max(MAX_NOTES_LENGTH).optional().nullable()` — an empty string `""` passes validation. Then `striptags("".trim())` returns `""`, and `"" || null` evaluates to `null`. So it works by accident, but the schema should be explicit about rejecting empty strings if they're not meaningful.
- **Impact:** Low — works by accident. But if `striptags` behavior changes or the fallback is removed, empty strings would be stored.
- **Suggested fix:** Add `.min(1)` before `.optional().nullable()`, or use `.transform(v => v?.trim() || null)` in the schema.

```typescript
const likingRef = useRef<Set<string>>(new Set());

  try {
    /* ... */
  } finally {
    likingRef.current.delete(recipeId);
  }
};
```
