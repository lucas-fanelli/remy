## Code Review — 2026-03-18

### Summary

Large recipe-sharing platform with Next.js, Prisma, MUI, and a clean DI architecture. Several privacy bypasses, a permanently-broken notification poller, and unescaped LIKE wildcards in a raw SQL query stand out. The test suite is extensive but masks real runtime issues.

### Findings

#### CRITICAL

**[CR-001]** Private profile data leakage through standalone API endpoints

- **File:** `src/app/api/users/[username]/followers/route.ts`, `following/route.ts`, `recipes/route.ts`, `stats/route.ts`
- **Issue:** The combined profile endpoint (`/api/users/[username]/profile`) correctly enforces `isPrivate` by returning limited data for non-owners. However, the standalone `/followers`, `/following`, `/recipes`, and `/stats` endpoints perform **zero privacy checks**. An attacker can fully enumerate a private user's social graph and recipe list by calling these endpoints directly.
- **Impact:** Complete bypass of profile privacy controls. Users who set their accounts to private believe their data is hidden, but it is fully accessible.
- **Suggested fix:**

```typescript
// Add to each standalone endpoint after fetching the user:
if (user.isPrivate && (!currentUserId || currentUserId !== user.id)) {
  return NextResponse.json({ error: 'This profile is private' }, { status: 403 });
}
```

**[CR-002]** SQL LIKE wildcard injection in recipe match endpoint

- **File:** `src/app/api/recipes/match/route.ts:95-97`
- **Issue:** Pantry item names are interpolated into a `LIKE` pattern (`%${name}%`) without escaping `%` and `_` characters. While Prisma.sql parameterizes the value (preventing SQL injection), the LIKE wildcards are interpreted by PostgreSQL. A pantry item named `%` would match every recipe ingredient; an item named `_salt` would match any single-character prefix + "salt".
- **Impact:** Incorrect recipe matching results; potential DoS if a wildcard-heavy name causes expensive full-table scans.
- **Suggested fix:**

```typescript
function escapeLikePattern(s: string): string {
  return s.replace(/[%_\\]/g, '\\$&');
}

const nameConditions = pantryNames
  .filter((n) => n.length >= 3)
  .slice(0, 50)
  .map(
    (name) => Prisma.sql`lower(elem->>'name') LIKE ${`%${escapeLikePattern(name)}%`} ESCAPE '\\'`
  );
```

#### HIGH

**[CR-003]** Notification polling permanently stops after transient failures

- **File:** `src/components/Navigation.tsx:~195-210`
- **Issue:** After 10 consecutive fetch failures, `pollingStoppedRef.current = true` and polling never resumes — not on visibility change, not on successful navigation, never. A few seconds of network instability permanently disables notifications for the session.
- **Impact:** Users silently lose all notification delivery until they refresh the page. No error indicator is shown.
- **Suggested fix:** Reset `consecutiveFailuresRef.current` and `pollingStoppedRef.current` on visibility change to `visible`, or cap backoff at MAX_INTERVAL instead of stopping entirely:

```typescript
const handleVisibility = () => {
  if (document.visibilityState === 'hidden') {
    clearPolling();
  } else {
    // Resume polling on tab focus, even if previously stopped
    pollingStoppedRef.current = false;
    consecutiveFailuresRef.current = 0;
    fetchNotifications();
    scheduleNext();
  }
};
```

**[CR-004]** No rate limiting on comment, like, follow, and save operations

- **File:** `src/middleware.ts`
- **Issue:** Rate limiting is applied to auth (10/15min) and upload (20/15min) endpoints, but comment creation, likes, follows, saves, and recipe creation share the general 100/15min bucket keyed by IP. A single user can spam hundreds of comments, likes, or follows from different accounts on the same IP without throttling.
- **Impact:** Enables notification spam attacks (each like/follow/comment creates a notification for the target), potential DB bloat, and harassment vectors.
- **Suggested fix:** Add per-user rate limiting for write operations (keyed by `userId` from token, not just IP), with limits like 30 comments/15min, 60 likes/15min.

**[CR-005]** Admin email masking is trivially reversible

- **File:** `src/app/admin/users/page.tsx:~205`
- **Issue:** The email masking regex `u.email.replace(/^(.{2})(.*)(@.*)$/, ...)` only replaces the middle portion with asterisks but preserves the first 2 characters and full domain. For short emails like `jo@gmail.com`, this reveals `jo******@gmail.com` which is effectively unmasked. Meanwhile, the admin API at `/api/admin/users` returns full unmasked emails.
- **Impact:** Inconsistent data exposure. The admin API gives full emails to any admin, while the UI pretends to mask them. If the intent is to protect emails, the API should enforce it; if admins should see emails, don't mask.
- **Suggested fix:** Either show full emails (admins are trusted) or mask in the API response, not the client.

#### MEDIUM

**[CR-006]** Followers/following endpoints expose user data without authentication

- **File:** `src/app/api/users/[username]/followers/route.ts:~20-30`, `following/route.ts`
- **Issue:** Authentication is optional (`const token = extractBearerToken(request)` with graceful null handling). Any unauthenticated visitor can enumerate the full follower/following list of any user, including usernames, full names, avatars, and bios.
- **Impact:** User enumeration and social graph mapping by unauthenticated crawlers or scrapers.
- **Suggested fix:** At minimum, require authentication to view follower lists, or paginate with a lower default limit for unauthenticated requests.

**[CR-007]** `averageRating` cache becomes stale on rating deletion

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts` (DELETE handler)
- **Issue:** When a comment is deleted, the associated rating record is NOT deleted, and `averageRating`/`reviewCount` on the Post are not recalculated. If a user's rating was part of the cached aggregate, deleting the comment leaves the rating "orphaned" — the user can't edit it (the UI is gone) but it still affects the average. The admin delete has the same issue.
- **Impact:** Stale rating data that cannot be corrected by the user.
- **Suggested fix:** Either delete the associated rating when the comment is deleted and recalculate, or provide a standalone rating management endpoint.

**[CR-008]** Recipe match endpoint has no result-set bound on candidate query

- **File:** `src/app/api/recipes/match/route.ts:~100-110`
- **Issue:** The raw SQL query `SELECT DISTINCT p.id FROM "Post" p, jsonb_array_elements(...)` scans all recipes with ingredients and has no `LIMIT`. The fallback path does `take: 500`, but the primary path returns unbounded results. With a large recipe database, this query could return thousands of IDs and trigger a massive follow-up `findMany`.
- **Impact:** Increasing query time and memory usage as the recipe database grows. Potential OOM or timeout under load.
- **Suggested fix:** Add `LIMIT 500` to the raw SQL query.

**[CR-009]** Inconsistent field naming: `totalRatings` vs `reviewCount`

- **File:** `src/app/api/recipes/route.ts`, `src/app/api/recipes/[id]/route.ts`, `src/app/api/search/route.ts`, `src/app/api/users/[username]/profile/route.ts`
- **Issue:** The DB field is `reviewCount`. Some API responses map it to `totalRatings`, others return `reviewCount`. The domain type `Recipe` has both `reviewCount` and `totalRatings` as optional fields. Frontend components check `recipe.totalRatings`, meaning any endpoint returning `reviewCount` instead will show "No ratings yet" even for rated recipes.
- **Impact:** Inconsistent rating display across different pages.
- **Suggested fix:** Pick one name and use it consistently everywhere.

**[CR-010]** `useEffect` dependency on `isAuthenticated` in followers/following pages is missing

- **File:** `src/app/profile/[username]/followers/page.tsx:~45`, `following/page.tsx:~45`
- **Issue:** The `useEffect` that fetches followers/following has `isAuthenticated` in its dependency array but doesn't pass an auth token. The fetch relies on httpOnly cookies (automatic), so the dependency on `isAuthenticated` is misleading — the effect re-runs when auth state changes but the fetch behavior doesn't actually change. More importantly, the `isFollowing` state from the API response depends on being authenticated, but if the user logs in after the initial fetch, the following state won't update.
- **Impact:** Stale "Follow"/"Following" button state after login on followers/following pages.
- **Suggested fix:** Remove `isAuthenticated` from deps if it doesn't affect the fetch, or re-fetch when it changes.

#### LOW

**[CR-011]** Pantry search input not debounced

- **File:** `src/app/pantry/page.tsx:~290`
- **Issue:** The search query `searchQuery` is used directly in the filter without debouncing. While this only filters client-side (no API calls), it causes a re-render and filter recalculation on every keystroke for potentially hundreds of pantry items.
- **Impact:** Minor UI jank on slower devices with large pantries.
- **Suggested fix:** Use the same debounce pattern used in admin search (300ms timeout).

**[CR-012]** `handleProfileClick` in mobile bottom nav always fires

- **File:** `src/components/Navigation.tsx:~780`
- **Issue:** The profile avatar button in the mobile bottom nav calls `handleProfileClick` which navigates to `/profile/${user.username}` when `user` exists. When `user` is null (guest), it only calls `handleMenuClose()` which is a no-op (menu isn't open). The guest gets no feedback — the button appears clickable but does nothing.
- **Impact:** Poor UX for guest users on mobile — silent no-op button.
- **Suggested fix:** Navigate to `/auth` for guests, similar to how the drawer handles it.

**[CR-013]** `motion.create` called but `motion()` used inconsistently

- **File:** `src/components/auth/LoginForm.tsx:11`, `src/components/auth/RegisterForm.tsx:11`
- **Issue:** LoginForm and RegisterForm use `motion(Box)` directly instead of `motion.create(Box)` used everywhere else. Both work, but `motion()` is the legacy API.
- **Impact:** Inconsistency; no runtime issue currently.
- **Suggested fix:** Use `motion.create(Box)` for consistency with the rest of the codebase.
