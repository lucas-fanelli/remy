### Summary

Multiple API routes with solid transaction handling and concurrency controls, but several bugs, security gaps, and maintainability issues across the reviewed files.

### Findings

#### CRITICAL

**[CR-001]** Race condition in profile DELETE: user object read before transaction

- **File:** `src/app/api/users/profile/route.ts:80`
- **Issue:** `user.avatar` is read from the `requireAuth` result outside the transaction, but the avatar could change between auth check and the `tx.user.delete` call. More critically, if the user object from `requireAuth` has a stale or incomplete avatar field, it will be included in the cleanup list incorrectly.
- **Impact:** Orphaned images not cleaned up, or wrong images deleted if avatar changed concurrently.
- **Suggested fix:** Read the avatar inside the transaction like posts/comments are:

```typescript
const userRecord = await tx.user.findUnique({ where: { id: user.id }, select: { avatar: true } });
// ...
const userAvatar = userRecord?.avatar;
```

**[CR-002]** `deductPantryItems` returns insufficient ingredients when `force=true` but POST handler still includes them in 201 response without clear indication deductions were partial

- **File:** `src/app/api/cooked-recipes/route.ts:85-89`
- **Issue:** When `force=true` and pantry has insufficient quantities, the item is fully deleted (consuming whatever is available), but the `insufficientIngredients` array still contains the original required vs available mismatch. The `deductedIngredients` will show the _available_ amount was deducted, but the caller has no way to know the deduction was partial vs full for that ingredient.
- **Impact:** Client receives contradictory data — an ingredient appears in both `deductedIngredients` and `insufficientIngredients` with different amounts, making it impossible to reconcile actual pantry state.
- **Suggested fix:** Add a `partial: boolean` flag to `DeductedIngredient` when force-deducting less than required:

```typescript
if (force && pantryQuantity > 0) {
  deletions.push({
    id: pantryItem.id,
    name: ingredient.name,
    amount: pantryQuantity,
    unit: ingredient.unit,
  });
  deductedIngredients.push({
    ...ingredient,
    amount: pantryQuantity,
    pantryItemId: pantryItem.id,
    partial: true,
  });
}
```

**[CR-004]** Pantry restoration on DELETE creates items without unit validation

- **File:** `src/app/api/cooked-recipes/route.ts:267-275`
- **Issue:** When restoring pantry items from `deductedIngredients` on cooked recipe deletion, the code creates new pantry items with `unit` defaulting to empty string if the stored data has no unit. It also does a name-based fallback lookup (`findFirst where name = d.name`) which could match a different pantry item with the same name but different unit.
- **Impact:** Pantry corruption: wrong item gets quantity restored, or items created with empty units causing downstream matching failures.
- **Suggested fix:** Include unit in the fallback lookup:

```typescript
existingItem = await tx.pantryItem.findFirst({
  where: { pantry: { userId: user.id }, name: d.name as string, unit: unit },
});
```

**[CR-005]** `hasMore` calculation is unreliable

- **File:** `src/components/recipe/RecipeFeed.tsx:140`
- **Issue:** `setHasMore(data.hasMore ?? data.recipes.length === PAGE_SIZE)` — if the API returns exactly `PAGE_SIZE` results on the last page, `hasMore` will be true, triggering one extra fetch. But the bigger issue: the API's `hasMore` is `recipes.length === limit` (in `src/app/api/recipes/route.ts`), which has the same off-by-one flaw.
- **Impact:** Every feed that ends on an exact page boundary makes one unnecessary API call. Minor performance issue but also causes a brief loading flicker.
- **Suggested fix:** In the API, use `hasMore: offset + recipes.length < total`:

```typescript
hasMore: offset + recipes.length < total,
```

**[CR-006]** `createRecipeSchema` validates `imageUrl` as `z.string().min(1)` but only conditionally validates it as Cloudinary URL

- **File:** `src/app/api/recipes/route.ts:39` / `src/app/api/recipes/route.ts:185-188`
- **Issue:** The Cloudinary URL validation is inside `if (validated.imageUrl)` — but `imageUrl` is required (min 1), so this is always truthy. However, the schema allows _any_ non-empty string to pass Zod validation first. If `validateCloudinaryUrl` has a bug or is bypassed, arbitrary URLs get stored. More concerning: `instructions[].image` is `z.string().optional()` with zero URL validation.
- **Impact:** Instruction step images can be any arbitrary URL — potential stored XSS vector if rendered in an `<img>` tag with a `javascript:` or `data:` URI, or SSRF if the server fetches these URLs.
- **Suggested fix:** Validate instruction images the same way:

```typescript
const instructionSchema = z
  .object({
    step: z.number().int().positive(),
    description: z.string().min(1).max(5000),
    image: z.string().url().optional(),
  })
  .strict();
// And in the handler, validate each instruction image against Cloudinary
```

**[CR-007]** `recipes/match/route.ts` — raw SQL `LIKE ANY` is vulnerable to performance abuse

- **File:** `src/app/api/recipes/match/route.ts:118-127`
- **Issue:** `escapeLike` handles `%`, `_`, and `\\`, but each pantry name gets wrapped in `%...%` for a leading-wildcard LIKE. PostgreSQL cannot use B-tree indexes for leading-wildcard LIKE patterns. The GIN index on jsonb helps with containment queries but not with `LIKE` on extracted text. With 50 patterns in `LIKE ANY(ARRAY[...])`, this becomes a sequential scan on every recipe's ingredient names.
- **Impact:** Under load, this query can monopolize DB resources. The 10s statement_timeout mitigates total duration but not CPU/IO pressure during execution.
- **Suggested fix:** Use PostgreSQL full-text search or trigram indexes (`pg_trgm`) for substring matching, or switch to exact normalized name matching (eliminating leading `%`):

```sql
AND lower(elem->>'name') = ANY(ARRAY[${Prisma.join(pantryPatterns)}])
```

**[CR-009]** Duplicated error handling pattern for `requireAuth` across all routes

- **File:** `src/app/api/cooked-recipes/route.ts:104-109`, `src/app/api/recipes/match/route.ts:56-61`, etc.
- **Issue:** Every route has the same try/catch pattern around `requireAuth` with slightly different response formats. Some use `ApiResponseHelper.unauthorized()`, others use `NextResponse.json({ error: 'Unauthorized' }, { status: 401 })`. Inconsistent error response format across the API.
- **Impact:** Client-side error handling must account for different error shapes. Duplicated boilerplate across every route.
- **Suggested fix:** Make `requireAuth` return a discriminated union or have it return the NextResponse directly on failure, so routes can do:

```typescript
const auth = await requireAuth(request);
if (auth.error) return auth.response;
const user = auth.user;
```

**[CR-010]** `deductedIngredients` stored as JSON but validated loosely on read

- **File:** `src/app/api/cooked-recipes/route.ts:246-249`
- **Issue:** On DELETE, `deductedIngredients` is read as `unknown[]` and each element is cast to `Record<string, unknown>` with manual type checks. If the stored JSON was corrupted or schema changed, the validation (`typeof d.amount !== 'number'`) silently skips items. There's no schema validation (e.g., Zod) on this stored data.
- **Impact:** Silent data loss during pantry restoration if stored format changes.
- **Suggested fix:** Define a Zod schema for `DeductedIngredient[]` and validate on read:

```typescript
const deductedSchema = z.array(
  z.object({
    name: z.string(),
    amount: z.number().positive(),
    unit: z.string(),
    pantryItemId: z.string().optional(),
  })
);
const parsed = deductedSchema.safeParse(cookedRecipe.deductedIngredients);
if (!parsed.success) {
  /* log warning, skip restoration */
}
```

**[CR-012]** `matchResults` not sorted before slicing

- **File:** `src/app/api/recipes/match/route.ts:153`
- **Issue:** `matchResults.slice(0, 60)` caps results, but `matchResults` is in candidate iteration order (DB order), not match quality order. High-quality matches from later candidates may be dropped in favor of lower-quality matches that happened to appear first.
- **Impact:** Users get suboptimal match results — a 95% match could be dropped while a 31% match is kept.
- **Suggested fix:**

```typescript
matchResults.sort((a, b) => b.matchPercentage - a.matchPercentage);
const cappedResults = matchResults.slice(0, 60);
```

**[CR-015]** `await Promise.allSettled` in profile DELETE is fire-and-forget but awaited

- **File:** `src/app/api/users/profile/route.ts:88`
- **Issue:** `await Promise.allSettled(imageUrls.map(...))` blocks the response until all Cloudinary deletions complete. For a user deleting their account with many posts, this could add significant latency. The PUT handler correctly uses fire-and-forget (`.catch()`), but DELETE doesn't.
- **Impact:** Slow account deletion response time proportional to number of images.
- **Suggested fix:** Fire and forget like the PUT handler, or move to a background job:

```typescript
Promise.allSettled(imageUrls.map((url) => cleanupCloudinaryImage(url))).then((results) => {
  const failed = results.filter((r) => r.status === 'rejected');
  if (failed.length) logServerError('Failed to cleanup images', failed);
});
```

**[CR-016]** `maskEmail` doesn't handle edge cases

- **File:** `src/app/api/admin/users/[id]/route.ts:12-22`
- **Issue:** For very short emails like `a@b.c`, `maskedLocal` = `a**` (correct), `maskedDomain` = `b` → `b` (length 1, so `b[0]` + `'*'.repeat(0)` = `b`), leaking the full domain name. Also, `'***@***'` for emails without `@` is a data integrity issue that should be logged.
- **Impact:** Short domain names are not effectively masked.
- **Suggested fix:**

```typescript
const maskedDomain =
  domainName.length <= 1 ? '***' : domainName[0] + '*'.repeat(Math.max(domainName.length - 1, 2));
```

**[CR-017]** `notification/[id]` PATCH returns success for already-read or non-existent notifications

- **File:** `src/app/api/notifications/[id]/route.ts:33-35`
- **Issue:** When `updateMany` returns `count === 0`, the route returns `{ success: true }`. The comment says "for idempotency" but this also masks authorization failures — if user A tries to mark user B's notification as read, they get `{ success: true }`.
- **Impact:** No information leakage (the notification content isn't returned), but the client cannot distinguish "already read" from "doesn't exist" from "not yours" — makes debugging harder.
- **Suggested fix:** Consider returning `{ success: true, alreadyRead: true }` or `204 No Content` when count is 0, after first verifying the notification exists and belongs to the user.
