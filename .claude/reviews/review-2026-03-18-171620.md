## Code Review — 2026-03-18

### Summary

Large full-stack Next.js recipe app with clean architecture. Several security and correctness issues found, most notably an unsigned JWT read in middleware rate limiting, fragile error detection in the recipe service, and a broken test mock.

### Findings

#### CRITICAL

**[CR-001]** Per-user rate limit reads JWT payload without signature verification

- **File:** `src/middleware.ts:224-237`
- **Issue:** The per-user write rate limiting extracts `userId` from the JWT cookie payload via `JSON.parse(atob(...))` without verifying the HMAC signature. A user who manually crafts a cookie with a different `userId` can exhaust another user's rate limit bucket.
- **Impact:** Targeted rate-limit exhaustion against specific users (denial of service for their write operations). The IP-based rate limit still applies, but the per-user bucket is trivially spoofable.
- **Suggested fix:** Reuse the HMAC verification logic already written for the `/admin` guard above, or extract it into a shared helper:

```typescript
// Extract into helper at top of middleware:
async function verifyJwtPayload(
  token: string,
  secret: string
): Promise<Record<string, unknown> | null> {
  try {
    const parts = token.split('.');
    if (parts.length !== 3) return null;
    const header = JSON.parse(b64UrlDecode(parts[0]));
    if (header.alg !== 'HS256') return null;
    const encoder = new TextEncoder();
    const key = await crypto.subtle.importKey(
      'raw',
      encoder.encode(secret),
      { name: 'HMAC', hash: 'SHA-256' },
      false,
      ['verify']
    );
    const valid = await crypto.subtle.verify(
      'HMAC',
      key,
      decodeSignature(parts[2]),
      encoder.encode(`${parts[0]}.${parts[1]}`)
    );
    if (!valid) return null;
    return JSON.parse(b64UrlDecode(parts[1]));
  } catch {
    return null;
  }
}
```

**[CR-002]** Test uses wrong mock method name — `generateToken` instead of `generate`

- **File:** `src/infrastructure/services/__tests__/unit/AuthService.test.ts:268`
- **Issue:** `mockTokenService.generateToken.mockReturnValue('test-token')` mocks a non-existent method. The `ITokenService` interface defines `generate`, not `generateToken`. The deep mock silently creates a property that never intercepts the real call.
- **Impact:** The test passes but does not actually verify token generation for the ADMIN registration path. A regression in token generation for admin registration would go undetected.
- **Suggested fix:**

```typescript
mockTokenService.generate.mockReturnValue('test-token');
```

#### HIGH

**[CR-003]** Fragile error string matching in `RecipeService.updateRecipe`

- **File:** `src/infrastructure/services/RecipeService.ts:34`
- **Issue:** `error.message.includes('Record to update not found')` depends on Prisma's exact English error message text. A Prisma version upgrade could change this wording silently. The adjacent `deleteRecipe` method correctly uses `Prisma.PrismaClientKnownRequestError` with error code `P2025`.
- **Impact:** A Prisma upgrade could cause update authorization checks to stop working, turning 403 errors into 500 errors.
- **Suggested fix:**

```typescript
async updateRecipe(id: string, userId: string, data: UpdateRecipeDTO): Promise<Recipe> {
  try {
    return await this.recipeRepository.updateWhere(id, userId, data);
  } catch (error: unknown) {
    if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === 'P2025') {
      const exists = await this.recipeRepository.exists(id);
      throw new Error(
        exists ? 'Unauthorized: You can only update your own recipes' : 'Recipe not found'
      );
    }
    throw error;
  }
}
```

**[CR-004]** CSP `script-src` may break Vercel Analytics

- **File:** `src/middleware.ts:91` and `src/app/layout.tsx:96`
- **Issue:** The CSP sets `script-src 'self' 'nonce-${nonce}'` but `<Analytics />` from `@vercel/analytics/next` is rendered without receiving the nonce. If Vercel Analytics injects an inline script or loads from a third-party domain, it will be blocked by CSP.
- **Impact:** Vercel Analytics silently fails in production, resulting in no analytics data.
- **Suggested fix:** Either pass the nonce to the Analytics component or add the Vercel script source to the CSP:

```typescript
`script-src 'self' 'nonce-${nonce}' https://va.vercel-scripts.com`,
```

**[CR-005]** Comment deletion silently removes user's rating

- **File:** `src/app/api/recipes/[id]/comments/[commentId]/route.ts:138-143`
- **Issue:** When a user deletes their comment, the handler also deletes their rating for that recipe (`tx.rating.deleteMany`). There is no user confirmation or warning that deleting a comment will also remove their rating.
- **Impact:** Users lose their ratings unexpectedly. Recipes may see rating drops when users only intended to remove their comment text. This is a data integrity concern.
- **Suggested fix:** Either decouple rating deletion from comment deletion (let users keep their rating), or at minimum return the deleted rating info in the response so the frontend can warn the user.

**[CR-007]** Recipe match SQL query performance on large datasets

- **File:** `src/app/api/recipes/match/route.ts:97-107`
- **Issue:** The raw SQL query uses `jsonb_array_elements` with `LIKE '%...%'` on up to 50 OR conditions. The leading `%` wildcard prevents index usage. On a database with thousands of recipes, this performs a full scan of the JSONB ingredients for every row.
- **Impact:** Endpoint becomes progressively slower as recipe count grows. Could cause timeouts under load.
- **Suggested fix:** Add a GIN index on `ingredients` column for `@>` containment queries, or use PostgreSQL full-text search on a materialized ingredient name column instead of LIKE patterns.

**[CR-008]** Admin pages show no user-facing error on data fetch failure

- **File:** `src/app/admin/comments/page.tsx:55`, `src/app/admin/recipes/page.tsx:65`, `src/app/admin/users/page.tsx:71`
- **Issue:** When `fetchComments`/`fetchRecipes`/`fetchUsers` fails, the error is only logged to `console.error`. The UI shows the empty table with no error indication to the admin user.
- **Impact:** Admin users have no way to know if data failed to load vs. genuinely empty. Could lead to admins thinking there are no users/recipes/comments.
- **Suggested fix:** Add error state similar to the admin dashboard page:

```typescript
const [error, setError] = useState<string | null>(null);
// in catch block:
setError('Failed to load comments');
// in render:
{error && <Alert severity="error">{error}</Alert>}
```

**[CR-009]** `Slide` transition component passed incorrectly in Navigation

- **File:** `src/components/Navigation.tsx:580`
- **Issue:** `TransitionComponent={Slide}` and `TransitionProps={{ direction: 'up' } as any}` — the `as any` cast hides a type mismatch. MUI's Dialog `TransitionComponent` expects a `React.JSXElementConstructor<TransitionProps>`, and `Slide` from MUI does satisfy this, but the `direction` prop should be part of the component's own props, not passed via `TransitionProps`.
- **Impact:** Works at runtime but the `as any` suppresses legitimate type errors. Future MUI updates could break this silently.
- **Suggested fix:** Create a typed transition wrapper:

```typescript
const SlideUp = React.forwardRef<HTMLDivElement, TransitionProps & { children: React.ReactElement }>(
  (props, ref) => <Slide direction="up" ref={ref} {...props} />
);
// Then: TransitionComponent={SlideUp}
```

#### LOW

**[CR-010]** `safeRating` function could mask legitimate zero ratings

- **File:** `src/lib/utils/recipe.ts:5`
- **Issue:** `return value ?? 0` treats `null`/`undefined` as 0, but a recipe with an actual average rating of 0 (all 0-star ratings, if possible) would be indistinguishable from "no ratings yet". However, the rating system uses 1-5 stars, so a legitimate 0 is impossible.
- **Impact:** None in current system (min rating is 1). But if the rating scale ever changes, this assumption breaks silently.
- **Suggested fix:** Add a comment documenting the assumption:

```typescript
// Ratings are 1-5, so 0 always means "no ratings". If scale changes, revisit.
export function safeRating(value: number | null | undefined): number {
  return value ?? 0;
}
```

**[CR-011]** Notification polling resets circuit breaker on every tab focus

- **File:** `src/components/Navigation.tsx:254-258`
- **Issue:** When the tab regains focus, `pollingStoppedRef.current = false` and `consecutiveFailuresRef.current = 0` reset the circuit breaker unconditionally. If the API is genuinely down, every tab focus triggers a new burst of retry attempts.
- **Impact:** If the notification API is unavailable for an extended period, users switching tabs repeatedly generate unnecessary network traffic.
- **Suggested fix:** Only reset the circuit breaker if the last failure was more than N minutes ago, or use a progressive reset that doesn't fully clear the failure count.
